### ★ 多 AI 防撞车（三道闸）

`--claim` 按序过三道闸，任何一道不过就如实报错并退回，绝不静默降级：

1. **全局锁** `_worker.lock` —— 目录级排他锁（`O_CREAT|O_EXCL` 原子创建）。
   同一时刻只允许一个 AI 领单。持锁者与年龄写进文件；超 1 小时视为陈旧锁自动清理。
2. **前置本地复核** —— 读真 `taskboard.md` 的状态字段再判一次前置。
   软件侧 `is_unlocked` 已保证，这里是双保险（exe 判定可能因 md 副本过期而误判）。
   复核不过 ⇒ 退回软件，不硬闯。
3. **施工锁** `_active.lock` —— 记录正在施工的任务 id 与持有者，
   领单时若该单已被别的 worker 持有则跳过。

`--done` 成功后释放施工锁（全局锁留着，让同一 worker 继续领下一单）。

## 4. 代码范式（照着写就不会错）

### 目录结构

```
kernel/varix/src/svstar2/
├─ mod.rs              域聚合器 + 落位纪律（含"不许写回前端"的断言）
├─ vea01_probe.rs      F0001 类型契约
├─ vea01_virtfeat.rs   F0001 虚拟化特征库（纯数据）
├─ vea01_engine.rs     F0001 探测引擎（三类识别/能力诚实/拓扑/指纹）
├─ vea01_arbitrate.rs  F0001 仲裁 + V01 口径对齐断言
├─ vea01_index.rs      F0001 统一出口 + 边界防护 + 自检 + 单元测试
├─ vea02_ctx.rs        F0002 上下文生命周期（四态/泄漏/强制回收）+ 自检
├─ vea03_sync.rs       F0003 围栏与同步原语（三类/死锁检测/等待链）
└─ vea03_checks.rs     F0003 自检与回归用例
```

新功能命名：`VE-F0004` → `vea04_xxx.rs`（VE-A 域 200 项；域字母按册内 `VE-x` 顺延）。

### 仓库既有范式（`svstar/` 与 `genstar2/` 是样板）

1. **每模块自带 `run_<name>_checks() -> CheckSet`**，登记进 `mod.rs` 域聚合器；
   聚合器在 `robust.rs` 以**单行注册**（不占 domains 定长数组名额）。
2. **每模块带 `#[cfg(test)] mod tests`**，宿主 `cargo test` 直跑。
3. **文件头 `//!` 注释必写**：UNREAL-X / VE-xNN / 册 / 锚点 / 职责定位 / 设计要点。
4. **零外部依赖**：只用 `crate::checks` + `alloc`（`String`/`Vec`/`format!`/`vec!`）。
5. **确定性算法、零 IO、可序列化**：时间用**逻辑 tick 注入**，不用墙钟——
   保证回归可复现、对拍可重现（对拍红线）。

### 错误分层（既有约定）

| 类别 | 处置 | 例子 |
|---|---|---|
| 构建期缺陷（规格漏实现） | 抛错 | 特征库漏了规格点名的平台 |
| 运行期降级 | 结构化结论 + 人话原因 + 修正建议，**不抛** | 探测失败、参数越界 |
| 审计留痕 | 不可变记录 + 必填 reason | 状态迁移、强制回收 |

**「异常零静默」是铁律**：任何失败都要显性化，禁止静默 catch；
拒绝必带 `suggestion`（修正建议）。

### 常量纪律

- `CheckSet` 上限见 `crate::checks::MAX_CHECKS`（当前 112），超限由模块自身裁剪，
  聚合器用 `!sub.truncated()` 如实反映截断态。
- 私有但跨模块需要的函数用 `pub(crate)`，不扩公开面。

### 本轮踩坑沉淀（下次直接用，别重新推演）

1. **任务板服务会随 WorkBuddy 关闭而退出**——开工第一步先
   `cmd /c start "" dist\VTaskBoard.exe`，35MB md 重新解析约 30 秒。
2. **onefile 的 `_MEIPASS` 让「相对路径往上找」全部失效**。
   已在 `vtaskboard.py` 修：MD_PATH 从 exe 目录**逐级向上**找最多 4 层
   （`dist/` → `VTaskBoard/` 命中）。别再写「exe 上级」——那是 `%TEMP%`。
3. **给诊断/建议系统做优化时，先问一句**：
   「被优化掉的那条路径上，有没有产生过这份系统需要的输入？」
   有的话，优化就是在丢输入。VE-F0004 的扩容建议恒等于当前容量，
   就是因为钳制分支（唯一产生"真实超容需求"的地方）直接 `return` 不记账。
4. **探针是抓这类 bug 最快的手段**。两条自检红着猜不出来，
   打印 `suggested=64` 立刻看出「建议值恒等于容量」这个规律。
   临时 `println!` 用完立刻删（别留在生产代码里）。
5. **断言要查结构化字段，不要查文案**。`verdict.contains("劣化")`
   会在分支优先级变化时静默失效；查 `level == PerfLevel::Alarming`。
6. **恒真断言是死代码**。我写过 `p.p90 <= p.p90` 占位，规范禁这种，删掉。

### 定位红项的现成工具

`CheckSet::red_items()` 返回 `([Option<Check>], usize)`，逐行枚举检查项——
仓库自带的红项定位面，比反复猜断言快。写法见 `vea01_index.rs` 的
`vea01_checks_all_green` 测试。

### 6.3 工具使用

- **Edit 会批量静默不落盘**——每次编辑后必须回读 `grep` 复核。
- Edit 的 `old_string` 若尾行数不对会匹配失败（文件是纯 LF）。
  此时改用 `python -c` 配 heredoc 精确替换，并加 `assert old in s` 兜底。
- **bash heredoc 会被内容里的引号打断**（`unexpected EOF`）。
  写长文件优先用 Write 工具；用 heredoc 时内容里避免中英文引号。

### 6.4 判据之间会互相约束

VE-F0001 施工时踩到：仲裁层把软渲染适配器选为 winner，
但 V01 契约规定「生效类别为 software 时 winner 必须为 null」——**两层自相矛盾**。
教训：**写代码前先把锚点里所有点名判据列出来对齐**，别写着才发现冲突。

### 6.5 测试文件自身的错也要认

VE-F0003 首轮 5 红，其中两条是**测试自己写错**：
- 拓扑用例里写了 `second.device_id = fp_a.first().map(|a| 0).unwrap_or(0x2484)`——笔误。
  修法是删掉那行（`physical()` 构造器本来就给对了 id），不是迁就测试。
- 边界用例断言查措辞「超上限」而实现写「超过上限」。修法是**改断言查事实**
  （`adapters.len() == MAX_ADAPTERS`），不是改实现迁就断言。

### 6.6 实现自身的错更要认

VE-F0003 另两条红是**实现真缺陷**：
- `wait()` 在预算未到时就把等待者摘出等待链 ⇒ 死锁检测看不见它，成环检测失效。
  修法：只在**真超时或死锁打破**时摘除。
- 白名单分支用 `break` 跳出循环 ⇒ `whitelisted` 标志丢失，
  上层分不清"真的没环"与"有环但被豁免"。修法：撞白名单时**直接 return** 带标志的结论。
