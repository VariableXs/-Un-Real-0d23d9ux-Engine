### 写在前面

你好。

如果你正在读这段文字，说明你至少对一件事情感到好奇：有没有一种工具，能让代码变得不那么"可怕"？

我们做 (Un)Real 0d23d9ux# Engine 的起因很简单。团队里有个设计师，每次看开发同事的屏幕都一脸茫然。那些花花绿绿的代码行对她来说就像天书。她问过很多次："你们到底在写什么？"开发同事试着解释，但总是越解释越复杂，最后两个人都放弃了。

后来我们开始想一个问题：代码本身是逻辑，逻辑是可以被可视化的，那为什么不能让一个完全不懂编程的人，打开一个项目后，像看地图一样看懂代码的结构？

这个想法最终变成了 (Un)Real 0d23d9ux# Engine。

它不是一个独立的软件，而是嵌入在宿主应用里的一个功能模块。你可以把它理解为宿主软件里的一个"代码透视眼"。打开它，你看到的不再是密密麻麻的代码行，而是一棵发光的树、一张清晰的流程图、甚至一个旋转的三维大脑。

接下来，我想带你逛一逛这个引擎能做什么。不会讲太多技术细节，只讲你能看到什么、能做什么、能感受到什么。

### 第一印象：打开一个项目

假设你刚刚接手了一个陌生的项目，十万行代码，三百多个文件，你完全不知道从哪里开始。

打开 (Un)Real 0d23d9ux# Engine，加载这个项目。

屏幕上出现的不是文件列表，也不是代码编辑器。屏幕中央出现了一个发光的大圆点。它缓缓脉动着，像一颗心脏。旁边有一行小字："商城项目 · 45000行 · 320个文件"。

这就是你的项目。一个光点。

你点击它。

光点像烟花一样炸开，分裂成四五个中等大小的光点，每个光点旁边标着名字："用户系统"、"订单系统"、"支付系统"、"库存系统"。它们之间有细细的发光线条连接，表示它们之间的关系。

你再点击"用户系统"。

它又炸开了，变成"登录"、"注册"、"个人中心"三个更小的光点。

继续点"登录"，变成"login.ts"、"auth.ts"两个文件光点。再点"login.ts"，变成"validate()"、"authenticate()"、"redirect()"三个函数光点。

这就是我们的**七级光点下钻系统**。从整个项目到一行代码，一共七层，每一层点一下就展开下一层。宏观的时候你看到的是几个大光点，微观的时候你看到的是密密麻麻的小光点。整个过程就像在宇宙中飞行：远看是星系，近看是恒星，再近看是行星。

当你点到最底层——具体的几行代码时，画面下方会自动升起一个分析面板。左边是代码编辑器，右边是这几行代码的流程图，底部是一段大白话解释："这段代码在检查用户的令牌是不是空的。如果令牌是空的，说明用户没有登录，就直接返回失败。"

不需要懂代码，你也能看懂它在干什么。

### 能力一：让代码说人话

(Un)Real 0d23d9ux# Engine 最让人惊喜的能力之一，是它能把代码翻译成任何人都能看懂的大白话。

这不是简单的逐字翻译。它不是把 `if` 翻译成"如果"、把 `for` 翻译成"循环"就完事了。它会理解整段代码在做什么，然后用一个完整的故事告诉你。

举个例子。一段二十行的登录验证代码，引擎会这样翻译：

"这个功能在做一件事：检查用户的密码对不对。首先，它从用户输入中取出密码。然后，它去数据库里找到这个用户之前存的密码。接着，它把两个密码放在一起比较。如果一模一样，就让用户进去；如果不一样，就告诉用户密码错了。"

更厉害的是，它还会用比喻。比如它会说："这就像门卫检查你的通行证——通行证对了就放行，不对就拦下来。"

我们花了很多精力在比喻的准确性上。引擎内部有一套三层校验机制，确保比喻不会张冠李戴。比如"角色动作系统"不会被说成"发动机"，因为发动机是提供动力的，而动作系统是控制行为的，两者根本不是一回事。正确的比喻是"导演"——导演指挥演员做动作，动作系统指挥角色做动作，这才对得上。

翻译有三种模式。通俗模式给完全不懂代码的人看，全是故事和比喻。专业模式给开发者看，显示类型签名、复杂度指标、形式化断言。双屏模式上下分屏，上面通俗下面专业，适合团队里不同角色的人一起看。

### 能力二：七种方式看代码

代码的结构可以用很多种方式呈现，(Un)Real 0d23d9ux# Engine 提供了七种可视化模式，你可以随时切换。

**树根模式**是默认的。代码像一棵倒长的树，模块是粗壮的树干，文件是分支，函数是细根，代码行是根须。数据像树液一样沿着根系流动。这种模式最适合理解代码的层级结构。

**流程图模式**把代码变成你在教科书上见过的那种标准流程图。判断是菱形，处理是矩形，循环是六边形，开始和结束是圆角矩形。每个菱形旁边标注着条件，每条箭头旁边标注着走向。这种模式最适合理解具体的执行逻辑。

**3D神经系统模式**是最炫酷的。整个代码项目变成一个发光的大脑悬浮在黑色空间中。每个函数是一个发光的球体，函数之间的调用关系是一根根发光的神经纤维，数据流是沿着纤维移动的光脉冲。你可以用鼠标360度旋转这个大脑，从任何角度观察。旋转的速度被刻意调得很慢，不会让你头晕。松手后视角会缓缓停下，像在水中转动一个水晶球。

**思维导图模式**以项目名为中心，模块为一级分支，文件为二级分支，函数为三级分支，像一朵花一样向外辐射。适合做架构讨论和头脑风暴。

**星系模式**把项目变成一片宇宙。模块是星系，文件是恒星，函数是行星，依赖关系是引力线。适合超大项目的宏观总览，几千个函数在屏幕上像星星一样闪烁，非常壮观。

**电路模式**把代码变成一块电路板。函数是芯片，数据流是导线，判断是逻辑门。适合分析数据是怎么在代码中流动的。

**地铁模式**把执行路径变成一张地铁线路图。函数是站点，调用是线路，分支是换乘站。适合理解代码运行时的执行顺序。

七种模式共享同一份数据，切换时所有功能完整保留。从树根切到3D神经，你会看到平面上的光点缓缓升起变成立体球体，连线变成纤维，整个过程大约八百毫秒，像一场小型的视觉魔术。

### 能力三：拖拖拽拽改代码

(Un)Real 0d23d9ux# Engine 不只是用来看代码的，它还能改代码。而且改代码的方式，可能和你想象的不一样。

你不需要写一行代码。你只需要拖拽。

在流程图模式下，你想改变一个判断的分支走向？直接把菱形的箭头从A拖到B就行了。引擎会自动修改对应的 if 语句。你想在两个步骤之间加一个判断？从工具栏拖一个菱形放到两个方块之间，引擎会弹出一个填空框问你"条件是什么"，填完后自动插入 if 语句。你想加一个循环？拖一个六边形框住几个方块，引擎自动插入 for 循环。

所有拖拽操作都会实时同步到代码。你在流程图上改了什么，代码编辑器里对应的代码立刻跟着变。反过来也一样：你在代码编辑器里改了代码，流程图也会实时更新。

对于更复杂的改进，引擎提供了十二个一键按钮。"一键整洁"自动修复缩进和格式。"一键加速"自动检测并修复性能问题。"一键加固"自动添加安全检查。"一键精简"自动删除死代码。每个按钮点下去，画布上的节点会实时变化——被删除的节点淡出消失，被优化的节点从红色变绿色，被新增的检查节点带着绿色盾牌图标出现。

所有操作都支持撤销。而且不只是简单的 Ctrl+Z，引擎有一个完整的时间旅行系统。你可以打开编辑历史面板，看到过去每一次修改的记录，点击任意一个时间点，画布会像视频倒放一样回到那个状态。你甚至可以基于某个历史点创建分支，尝试不同的修改方案，最后选择最满意的那个合并回来。

### 能力四：一键查问题

代码里的 bug 就像藏在暗处的地雷，不踩到不知道它在那里。(Un)Real 0d23d9ux# Engine 提供了一套全面的检测系统，帮你把地雷全部标出来。

打开分析面板，你会看到一排检测开关：空指针检测、数据竞争检测、资源泄漏检测、死代码检测、性能热点检测、安全漏洞检测。每个开关旁边显示当前状态：绿色勾表示没问题，黄色三角表示有警告，红色叉表示有问题。

勾选任意一个开关，画布上会实时叠加对应的标记。有 bug 的节点会亮起红色脉冲，性能慢的节点会变成橙色，死代码会变成灰色半透明。你可以点击任意一个标记，画布会飞到问题所在的位置，底部终端会显示详细的问题描述和修复建议。

点"全部运行"，引擎会一次性执行所有检测，然后在底部问题面板列出所有发现的问题，按严重程度排序。每个问题都可以一键跳转到画布对应位置，也可以一键应用修复。

检测完成后，你还可以一键生成报告。"体检报告"给开发者看，列出所有指标和问题。"复杂度报告"给架构师看，分析哪些模块最复杂、最需要重构。"给老板的汇报"给项目经理看，用大白话总结项目的健康状况。

### 能力五：写新代码

除了看懂和修改现有代码，(Un)Real 0d23d9ux# Engine 也能帮你写新代码。

创作面板里有四个区域：生成器、模板、转换和续写。

生成器可以把各种输入转化为代码。粘贴一段 JSON，它能自动生成对应的类型定义。粘贴一段 SQL，它能自动生成 ORM 调用代码。上传一个 OpenAPI 文档，它能自动生成完整的 API 客户端。甚至在画布上画一个流程图，它都能把流程图转化为可执行的代码。

模板区提供了常见的代码模板。用户登录、增删改查、支付流程、文件上传、测试用例——选好模板，填写几个参数，引擎自动生成完整的代码骨架。

转换区可以在不同编程语言之间转换代码。Java 转 Python、Python 转 Go、回调转 async——引擎不是逐行硬翻，而是基于语义理解找到目标语言中最地道的等价写法。

续写功能可以在你写到一半的时候帮你补全。它不使用 AI 猜测，而是基于语法规则和类型约束，枚举所有合法的续写选项，按相关度排序推荐。推荐的每一个选项都是语法正确、类型匹配的，不会出现 AI 常见的"幻觉"问题。

### 能力六：命令系统

对于喜欢键盘操作的用户，(Un)Real 0d23d9ux# Engine 提供了一套完整的命令系统。

按 `/` 或 `T` 打开底部终端，输入 `/` 开头的命令即可执行任何操作`/improve speed` 一键加速`/scan all` 全量检测`/view neural` 切换到3D神经模式`/theme pixel` 切换像素风格。一共78条命令，覆盖全部功能。

输入 `/help` 可以看到完整的手册，按 A-Z 排列，分页显示。输入 `/help improve speed` 可以看到这条命令的详细用法、参数说明、使用示例和等效的按钮操作路径。

命令系统还有一个贴心的智能推荐功能。当你输入 `/im` 时，终端上方会浮现几条最相关的命令推荐。当你执行完一条命令后，终端会淡灰色显示几条关联命令。当你输错了命令，终端会推荐最接近的正确命令。这些推荐都用极淡的颜色显示，不抢视线，但需要的时候一眼就能看到。

### 界面与风格

(Un)Real 0d23d9ux# Engine 的界面设计遵循一个原则：**能不要的都不要**。

画布上只有可视化内容，没有多余的按钮和面板。所有功能控件都藏在边缘——左侧的活动栏、右侧的辅助栏、底部的终端——需要的时候滑出来，不需要的时候收回去。画布占据屏幕百分之九十以上的面积，给你最大的沉浸感。

但"极简"不意味着"单调"。引擎内置了八种作品级视觉风格，每种风格都是一个完整的视觉世界。

**像素风**以 Minecraft 为灵感。面板是石头纹理，按钮是钻石和木头材质，节点是不同材质的方块，连线是红石线，状态栏是生命条和经验条。连音效都是 Minecraft 风格的——放置方块、破坏方块、红石激活。打开像素风的那一刻，你会觉得自己在用 Minecraft 写代码。

**现代简约风**是 Apple 式的极简。纯白或纯黑背景，零贴图，零装饰，大量留白。所有元素都是淡色圆角矩形和极细线条。安静、专业、不压迫。

**星空风**是最浪漫的。深空黑背景上渲染着实时 WebGL 星场，节点是发光的星体，连线是光束，数据流是流星。整个画布像一片宇宙，代码在里面像星星一样闪烁。

还有清新风、赛博朋克风、玻璃拟态风、新拟态风、手绘风。每种风格都有完整的贴图、字体、图标、音效和着色器资产。切换风格时，整个界面会在八百毫秒内完成全局变形——颜色渐变、圆角变化、阴影消长、字体替换——像整个世界在你眼前换了一套皮肤。

除了八种风格，还有十二种主题色、八种动态效果、六种布局排布可以自由组合。算下来一共有两万七千多种界面组合，总有一种适合你的审美。

引擎还支持动态壁纸。你可以上传自己的视频壁纸，也可以从 Wallpaper Engine 创意工坊导入，还可以使用内置的八种实时渲染壁纸（星空、极光、深海、火焰等）。壁纸作为最底层，上面叠加半透明遮罩，再上面是 UI 层。遮罩的透明度和模糊度都可以调节，确保壁纸好看的同时不影响 UI 的可读性。

### 可拓展性：一个活的引擎

(Un)Real 0d23d9ux# Engine 从设计之初就不是一个封闭的系统。它是一个**可拓展的、可持续更新的活引擎**。

**知识库可拓展。** 引擎的翻译能力依赖七大知识库：语义词典、比喻库、翻译模板、错误诊断库、惯用法库、命名词典和领域术语库。这些知识库都有标准化的格式规范，任何 AI 或人工贡献者都可以按照规范直接补充新条目。比如当一种新的编程语言出现时，只需要在语义词典中添加该语言的关键词映射，引擎就能立刻理解这种新语言。当某个领域出现了新的技术术语时，只需要在领域术语库中添加条目和正确的比喻，翻译引擎就能准确翻译。

**视觉风格可拓展。** 每种视觉风格都是一个独立的资源包，包含贴图、字体、图标、音效和着色器。用户可以创建自己的资源包，导入导出，甚至从社区市场下载他人分享的风格。这意味着引擎的视觉表现力是无限的——只要有创作者愿意制作，就可以有无数种风格。

**命令系统可拓展。** 78 条内置命令只是起点。用户可以通过自定义按钮功能，将任何命令组合绑定到一个按钮上，放在界面任何位置。比如你可以创建一个叫"一键全扫"的按钮，绑定 `/scan all &amp;&amp; /improve clean &amp;&amp; /report health` 这条组合命令，放在底部工具栏。以后只需要点一下这个按钮，就能完成全量检测、代码整理和报告生成三个操作。

**可视化模式可拓展。** 七种内置可视化模式基于统一的渲染架构。开发者可以基于这个架构添加新的可视化模式，比如时序图、桑基图、力导向图等。只要数据接口一致，新的可视化模式可以无缝接入现有的交互系统。

**语言支持可拓展。** 引擎的解析层基于 Tree-sitter 和 ANTLR，这两种工具都支持通过语法文件扩展新语言。当一种新语言出现时，只需要编写对应的语法文件和语义映射表，引擎就能在很短时间内获得对新语言的支持。

**分析能力可拓展。** 静态分析子系统基于 LLVM IR 的 Pass 架构，新的分析 Pass 可以像插件一样插入。动态分析子系统基于 Frida 和 eBPF 的插桩框架，新的插桩规则也可以动态加载。

**功能模块可拓展。** 引擎的整体架构是模块化的。每个功能模块（续写、分析、翻译、可视化等）都是独立的组件，通过统一的接口与核心引擎通信。这意味着新功能可以作为独立模块开发，不影响现有功能的稳定性。

这种可拓展性确保了 (Un)Real 0d23d9ux# Engine 不会随着时间推移而变得过时。编程语言在进化，开发框架在更迭，用户需求在变化，但引擎的架构能够持续适应这些变化。它不是一个写完就定型的软件，而是一个不断生长的有机体。

### 最后

(Un)Real 0d23d9ux# Engine 目前有 530 项功能，78 条命令，68 个快捷键，8 种视觉风格，7 种可视化模式，3 种界面模式，支持 9 种编程语言的语义理解。

但数字不是重点。

重点是，我们希望这个引擎能改变人们与代码的关系。代码不应该是只有程序员才能看懂的天书。它应该像地图一样直观，像故事一样易懂，像积木一样可以随意拼装。

一个产品经理应该能打开项目，看懂代码在做什么，而不需要拉着开发同事问半天。一个设计师应该能理解前端代码的结构，从而更好地与开发协作。一个老板应该能一键生成项目健康报告，而不需要等团队花三天时间整理文档。一个初学者应该能打开一个开源项目，像读故事书一样理解它的逻辑，从而更快地学会编程。

## 十八、🔒 结构稳定性保证（#331–#336）

&gt; **核心承诺**：无论怎么切换级别/界面/可视化模式，树的整体形状和节点相对位置**永远不变**。
&gt;
&gt; **实现原理**：
&gt; 1. 首次加载时，布局引擎计算一次全局坐标，存入不可变坐标表
&gt; 2. 切换级别时，只修改节点的**内容**（标签文字/大小/透明度），不修改**坐标**
&gt; 3. 切换界面时，只修改节点的**渲染层**（文字/颜色），不修改**布局层**
&gt; 4. 切换可视化模式时，2D↔2D保持坐标，2D↔3D做坐标映射

| # | 功能名 | 原理 | 用户感知 |
|---|--------|------|---------|
| 331 | 固定布局引擎 | 首次计算全局坐标，后续只改内容 | 切级别时节点不跳动 |
| 332 | 弹性节点尺寸 | 大小随级别变，中心点不变 | 节点放大缩小但位置不动 |
| 333 | 连线锚点锁定 | 锚定节点中心 | 节点大小变化时连线自动伸缩 |
| 334 | 占位符机制 | 折叠节点保留空间 | 折叠后其他节点不移位 |
| 335 | 布局快照 | 手动调整后保存 | 切级别不覆盖手动布局 |
| 336 | 结构哈希校验 | 切换前后校验AST | 确保代码逻辑未被意外修改 |

## 二十九、🎨 颜色标记修复（#481–#490）

|------|------|-----|---------|------|---------|

# 完整UI设计规范 — 界面·按钮·布局 全部要求

## 一、整体布局要求

### 1.1 核心原则

| 原则 | 要求 | 反例 |
|------|------|------|
| **视觉层次** | 用户第一眼看到最重要的内容，第二眼看到次要内容 | 所有元素一样大一样亮 |
| **留白充足** | 内容区域占60-70%，留白占30-40% | 塞满整个屏幕 |
| **对齐统一** | 所有元素沿网格线对齐，不随意摆放 | 元素位置参差不齐 |
| **分组明确** | 相关功能放在一起，不相关的拉开距离 | 保存按钮和删除按钮紧挨着 |
| **一致性** | 相同功能用相同样式，不同功能用不同样式 | 两个相同按钮长得不一样 |

### 1.2 布局结构要求

```
┌──────────────────────────────────────────────┐
│ 顶部栏 (固定，40-56px) │
│ Logo + 导航 + 用户信息 │
├──────┬─────────────────────────┬─────────────┤
│ 侧栏 │ 主内容区 │ 辅助面板 │
│ 可选 │ 占最大面积 │ 可选 │
│200- │ │ 240-320px │
│280px │ │ │
├──────┴─────────────────────────┴─────────────┤
│ 底部栏 (可选，32-48px) │
│ 状态信息 / 工具 / 终端 │
└──────────────────────────────────────────────┘
```

**要求**：
- 主内容区必须占屏幕最大面积（≥60%）
- 侧栏可折叠，折叠后主内容区自动扩展
- 顶部栏固定不动，内容区可滚动
- 底部栏可选，不遮挡主内容

## 二、色彩要求

### 2.1 色彩数量限制

| 规则 | 要求 |
|------|------|
| 主色 | 1种，用于品牌/高亮/主要按钮 |
| 辅助色 | 1-2种，用于次要元素 |
| 中性色 | 3-5种（黑/深灰/中灰/浅灰/白） |
| 功能色 | 3-4种（成功绿/警告黄/错误红/信息蓝） |
| **总计** | **不超过8-10种颜色** |

### 2.2 色彩使用规则

| 规则 | 要求 | 反例 |
|------|------|------|
| 60-30-10 | 60%背景色+30%辅助色+10%强调色 | 满屏都是鲜艳颜色 |
| 对比度 | 文字与背景对比度≥4.5:1（WCAG AA） | 浅灰文字在白底上 |
| 一色一义 | 每种颜色只表示一种含义 | 红色既表示错误又表示重要 |
| 色盲友好 | 不单独依赖颜色传达信息，配合形状/图标 | 只用红绿区分状态 |

### 2.3 深色/浅色模式

| 要求 | 说明 |
|------|------|
| 必须支持 | 至少提供深色和浅色两种模式 |
| 不是简单反色 | 深色模式不是把白色变黑色，需要独立调色 |
| 背景 | 浅色用纯白或极浅灰，深色用深灰而非纯黑 |
| 文字 | 浅色模式深灰文字，深色模式浅灰文字（非纯白） |
| 阴影 | 浅色模式用阴影区分层级，深色模式用亮度区分 |

## 四、按钮设计要求（重点）

### 4.1 按钮层级体系

一个界面中按钮必须有明确的层级，不能所有按钮都一样显眼。

| 层级 | 类型 | 外观 | 使用场景 | 数量限制 |
|------|------|------|---------|---------|
| **一级** | 主按钮 | 实色填充+白字 | 页面最核心的操作 | 每屏最多1-2个 |
| **二级** | 次按钮 | 描边+彩色字 | 重要但非核心操作 | 每屏2-4个 |
| **三级** | 幽灵按钮 | 无边框+灰色字 | 次要操作 | 不限 |
| **四级** | 文字按钮 | 纯文字+下划线 | 最次要操作 | 不限 |
| **危险** | 危险按钮 | 红色填充/描边 | 不可逆操作（删除） | 谨慎使用 |

### 4.2 按钮尺寸规范

| 尺寸 | 高度 | 内边距 | 字号 | 使用场景 |
|------|------|--------|------|---------|
| 大 | 44-48px | 0 24px | 15-16px | 登录/注册/核心CTA |
| 中 | 36-40px | 0 16px | 13-14px | 常规操作（默认） |
| 小 | 28-32px | 0 12px | 11-12px | 工具栏/紧凑区域 |
| 迷你 | 22-24px | 0 8px | 10px | 标签内/表格内 |

### 4.3 按钮状态（必须全部实现）

| 状态 | 视觉变化 | 要求 |
|------|---------|------|
| **正常** | 默认样式 | 清晰可识别为按钮 |
| **悬停** | 背景变深/变浅5-10% | 给用户"可以点击"的反馈 |
| **按下** | 背景再深5%+缩小1-2% | 给用户"已经按下"的反馈 |
| **聚焦** | 外发光环2px | 键盘导航时可见 |
| **禁用** | 透明度40-50%+鼠标禁止 | 明确告知不可点击 |
| **加载中** | 显示旋转图标+文字变灰 | 告知正在处理 |

### 4.4 按钮分布要求

| 规则 | 要求 | 反例 |
|------|------|------|
| **主次分明** | 主按钮最显眼，次按钮退后 | 保存和取消一样显眼 |
| **位置固定** | 同类操作按钮位置一致 | 确认按钮有时在左有时在右 |
| **间距合理** | 按钮间距≥8px，主按钮与次按钮间距≥12px | 按钮挤在一起 |
| **对齐方式** | 表单底部右对齐，弹窗底部右对齐，工具栏左对齐 | 随意摆放 |
| **危险隔离** | 删除/危险按钮与其他按钮拉开距离 | 删除紧挨着保存 |
| **不超过7个** | 同一区域按钮不超过7个 | 一排15个按钮 |
| **图标+文字** | 重要按钮图标+文字，次要按钮可纯图标 | 所有按钮都纯图标 |

### 4.5 按钮排列顺序

**确认/取消类**（右对齐）：
```
[取消] [确认]
次按钮 主按钮
```

**操作工具栏**（左对齐）：
```
[新建] [编辑] [复制] [删除]
主 次 次 危险
```

**表单底部**（右对齐）：
```
[重置] [提交]
幽灵 主按钮
```

**危险操作确认**（居中或右对齐）：
```
[取消] [确认删除]
次按钮 危险按钮
```

📚 语言引擎知识库 — AI协作完善规范

一、核心思路

问题：语言引擎的知识库（语义词典、比喻库、翻译模板、错误诊断库等）非常庞大，单靠人工维护不现实。需要让任何AI都能按照统一规范来补充和完善。

解法：设计一套标准化的知识库规范，包括格式模板、质量规则、贡献流程。任何AI只要遵循这套规范，就能直接产出可用的知识库条目，无需人工二次加工。

二、知识库总结构

知识库分为 7大库，每个库有独立的格式规范：

库名	内容	条目数	更新频率

① 语义词典	编程概念的跨语言映射	~250概念	低频

② 比喻库	概念→生活比喻的映射	~500比喻	中频

③ 翻译模板	AST结构→中文句式的模板	~200模板	低频

④ 错误诊断库	报错信息→大白话解释	~1000条	高频

⑤ 惯用法库	各语言的常见写法模式	~500条	中频

⑥ 命名词典	英文缩写/变量名→中文	~2000条	高频

⑦ 领域术语库	游戏/电商/金融等领域术语	~500条	中频

三、每个库的格式规范

① 语义词典格式

AI贡献时需要填写的字段：

字段	必填	说明	示例

标准英文名	✅	最通用的英文叫法	Async Concurrency

所属领域	✅	可多选	通用、网络、IO

② 比喻库格式
