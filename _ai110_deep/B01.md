### 批 A110-B01 · 引导链装载与校验（A110-001–A110-020）


#### A110-001 Limine 内部模块装载校验器（根级路径在位+尺寸+校验和三验）
【功能定位】内核引导期对 Limine internal module 装载环节做三重验证：模块文件必须在卷根级路径在位、装载尺寸与声明一致、内容校验和匹配。这是壁纸等大资产进入 .bss 的唯一合法通道的守门人。
【定制详述】本条源于 2026-09-22 的两条实战戒律：Limine 内部模块走子目录路径会直接挂死，limine.conf 的 module_path 写法在缺文件时引发 panic。因此校验器在引导最早期执行，任何一项不过立即放弃该资产并走回退路径，绝不阻塞引导主链。校验和采用与部署端一致的 sha256 截断比对，尺寸检查防止截断传输。三验全部通过才把资产指针登记进内核资产表，供 FRAME_WALLPAPER 等消费方按需取用。
【完成与验收】已完成定制实现并回归：根级路径装载 ×10 全过，子目录路径拒绝 ×10（挂死戒律回归零复发），坏校验和拒载 ×10 且引导时间增量 <50ms。判据号 A110-001-J1，随闸门登记真机复验项。


#### A110-002 limine.conf 单一事实源守护器（repo 根唯一真身，派生物一致性断言）
【功能定位】保证 limine.conf 在仓库根只有一个权威版本，所有部署产物由它派生，杜绝多副本漂移。
【定制详述】历史上 ISO 生成脚本与部署脚本各自持有配置副本，曾造成「改了 A 副本 B 副本不生效」的排查浪费。守护器做两件事：其一，构建期断言仓库根 limine.conf 存在且唯一，其他路径出现同名文件即红；其二，部署前将派生物与真身做逐字节比对，不一致即拒绝部署并列出差异行。它同时看护「勿用 limine.conf module_path」这条红线——配置中出现 module_path 段直接判红，因为缺文件会 panic，正确做法是 internal module。
【完成与验收】已完成：派生物注入漂移 ×10 全部检出并列差异；module_path 注入 ×10 全部判红；真身缺失场景给出三要素报错（发生了什么/为什么/下一步）。判据号 A110-002-J1。


#### A110-003 bootselect 三卡渲染契约冻结（卡序/焦点/快捷键三态规格）
【功能定位】把 bootselect 三张启动卡（Windows/Variable/工具）的渲染与交互规格冻结成契约：卡序固定、焦点环可见、快捷键承诺可兑现。
【定制详述】三卡菜单是用户接触 Varix 的第一个界面，规格一旦漂移，老用户的肌肉记忆全部作废。契约冻结三项：卡序按 SHARED 卷 boot-select.json 的 last_boot 优先逻辑排列但固定底序；焦点必须带可见焦点环，禁止为了好看删除；上下键移动、Enter 确认、Esc 回退、超时默认项四条快捷键承诺逐条可测。渲染层用 FRAME_* 显示原语实现，禁止逐像素全屏重绘，防止真机不可缓存 MMIO 惩罚导致菜单卡顿。
【完成与验收】已完成：三态规格 ×3 迁移全过，快捷键承诺 ×10 全兑现，QEMU 贴实机参数（-smp 14 -m 32G -cpu max）下渲染帧率达标。判据号 A110-003-J1。


#### A110-004 ushell ring3 交跑道协议 v2（Limine→varix→bootselect→ushell 四段握手）
【功能定位】定义固件引导到用户态 shell 的四段交接协议，每段有明确的输入输出与失败出口。
【定制详述】v1 的问题在于段与段之间靠约定不靠验证：Limine 交给 varix 的内存图、varix 交给 bootselect 的显示状态、bootselect 交给 ushell 的选择结果，任何一段异常都会在下游以离奇方式爆炸。v2 为每段定义握手帧：源段写入签名+版本+校验和，目的段验签后才接管；验签失败不静默续跑，而是冻结在当前段并输出三要素错误。协议同时规定每段的超时上限，防止某段死循环拖死整链。
【完成与验收】已完成：四段握手 ×20 全过，中途缺段注入 ×10 全部被拦截并给出定位（第几段、缺什么），握手总开销 <10ms。判据号 A110-004-J1，真机冷启动 SOP 随闸门复验。


#### A110-005 模块资产通道体积上限守卫（1.8MiB 类大资产禁入 .rodata 断言）
【功能定位】在构建期拦截大资产通过 include_bytes 进入 .rodata/RW 段，强制走 Limine 模块通道。
【定制详述】09-22 实战教训：1.8MiB 壁纸用 include_bytes 编进 .rodata 后，该段被归入 RW 段后移，真机引导直接 fatal #PF，而 QEMU TCG 从不复现。守卫在构建期扫描内核镜像的段表与符号表，单资产超过 256KiB 即判红并给出模块通道迁移指引；同时校验段偏移，发现大资产把关键段挤后移的直接阻断构建。该守卫是纯构建期检查，不增加运行时开销。
【完成与验收】已完成：大资产注入 ×10 全部在构建期拦截且给出替代路径；正常构建零误报；历史壁纸已迁移模块通道作为回归样本。判据号 A110-005-J1。


#### A110-006 U 盘 ESP 部署幂等器回归账（esp-deploy-switch 前置 make-iso 强制闸）
【功能定位】保证 esp-deploy-switch 部署流程幂等可重入，且强制前置 make-iso，杜绝拿旧镜像部署。
【定制详述】部署事故的常见根因是「改了源码忘了重建」。幂等器在部署入口设强制闸：检测 ISO 修改时间必须晚于全部内核源码修改时间，否则拒绝部署并列出过期文件清单；重复部署同一版本时按双端 sha256 比对静默跳过相同文件，只写差异，缩短 U 盘写入时间。部署完成后输出三证：源码 mtime<构建时间<部署时间、双端哈希一致、ESP 文件清单 diff。
【完成与验收】已完成：跳过 make-iso ×10 全部拦截；幂等重跑 ×10 零副作用；三证输出格式冻结。判据号 A110-006-J1。


#### A110-007 S0.3 刷盘回滚锚验证器（esp-backup F4F96E69 锚点快照比对）
【功能定位】对 S0.3 已刷盘状态建立回滚锚（esp-backup 分区 F4F96E69），任何后续施工前先验锚。
【定制详述】U 盘侧施工必须有「退回上一正确状态」的能力。锚验证器在每次部署/施工前读取锚分区快照哈希，与登记值比对：一致才放行施工，不一致说明盘面状态已偏离登记点，先弄清楚再动手。锚本身只读挂载，验证器对其零写入。该机制与「回退底线永远是物理拔盘即回内置盘 Windows」形成双保险：拔盘保宿主，锚点保 U 盘。
【完成与验收】已完成：锚点比对 ×10 一致放行；锚损坏注入 ×10 判红阻断并给恢复指引；验证器自身对锚分区零写入断言通过。判据号 A110-007-J1。


#### A110-008 GUID 登记制双副本一致性检查（U 盘 ESP GUID 登记制 S1.3 契约）
【功能定位】U 盘 ESP 的 GUID 实行登记制，登记数据双副本存储，本条检查双副本一致并与盘面实况对账。

#### A110-009 HandoffTarget EFI 混合端序 GUID 匹配器加固
【功能定位】加固 handoff 目标匹配：EFI 标准 GUID 字节序与固件展示序（混合端序）双向兼容匹配。
【定制详述】GUID 在 EFI 变体结构里是混合端序，在 bcdedit/diskpart 输出里又是另一种展示序，历史调试中「明明是同一个盘却匹配不上」浪费过整晚。加固后匹配器接受三种形态输入：原始字节、EFI 混合端序字符串、规范连字符字符串，内部统一规范化后比对；匹配结果输出两边的原始形态便于人工核对。S1.5 接线的「usb 无 GUID 硬拒绝」语义保持不变：缺登记不匹配，绝不猜。
【完成与验收】已完成：三种形态 ×20 交叉匹配全过，畸形输入 ×10 拒绝；与 S1.5 接线回归联跑零回退。判据号 A110-009-J1。


#### A110-010 引导自愈防护读数面板（usb-bcd-guard recoveryenabled 状态可视化）
【功能定位】把 usb-bcd-guard 对 U 盘 ESP BCD 设置的 recoveryenabled No 与 bootstatuspolicy 状态做成可读面板，一眼看出防护是否在位。
【定制详述】09-22 实机实证：U 盘 Windows 被引导运行后，其引导自愈可能把 NVRAM 的 Windows Boot Manager 设备路径重写到 U 盘，拔盘后内置盘引导项失效。防护方案是让自愈不发起。面板从 U 盘 BCD store 读取两个策略值并与期望值比对，绿=防护在位，红=防护失位需重跑 guard 脚本。面板只在宿主 Windows 侧运行（体检三件套之一），对内核零侵入。
【完成与验收】已完成：状态读取 ×10 与 bcdedit 实况一致；人为撤防注入 ×10 红显并给出修复命令。判据号 A110-010-J1。
