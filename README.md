## 1. 这个项目是什么

一句话概括：**这是一个完整的、从零开始的桌面操作系统项目**。不是改 Linux，不是套壳，而是从"按下电源键之后 CPU 执行的第一条指令"开始，一路写到"桌面上有窗口、有任务栏、有开始菜单、能跑应用"。

整个项目分成两个大层面：

**内核层（VARIX-500）**
- 用 Rust 编写，目标平台是 `x86_64-unknown-none`——意思是"64 位 x86 裸机，没有操作系统可依赖"。
- 包含内存管理、进程调度、中断处理、系统调用、虚拟文件系统、设备驱动等操作系统最底层的部件。
- 目前已经能在 QEMU 模拟器里完整引导到 `boot complete`（启动完成），串口会输出完整的启动日志。

**桌面层（NOVA-500）**
- 包括窗口管理器（VWM）、桌面 shell、任务栏、开始菜单、通知中心、主题系统、国际化（中英文）。
- 还有一个雄心不小的部分：**应用兼容层**——探测 Windows 应用的窗口样式和行为，决定用哪种策略把它"接"进我们的桌面（包括对反作弊软件、独占全屏游戏这类"硬骨头"的让位处理）。
- 桌面端的启动器（Launcher）用 Tauri 框架开发，前端是 TypeScript + Vite。

这个项目另一个特殊之处在于：**它是一个多 AI 协作实验**。内核被切分成 20 个"域"（AI-01 到 AI-20），每个域由一个独立的 AI 会话负责开发，各自实现 25 项功能，互不越界。整个仓库里有大量的交付报告、验收清单、施工步骤图，记录了这场"AI 军团盖楼"实验的全过程。

如果你想了解"从零写操作系统"是怎么一回事，或者想研究"怎么组织几十个 AI 并行开发同一个代码库"，这个仓库都是一份不错的教材。

## 2. 用大白话理解操作系统

如果你不是系统编程出身，这一节用几个比喻把核心概念讲明白。懂行的人可以直接跳到第 3 节。

**内核是什么？**
把电脑想象成一栋大楼，内核就是物业。住户（应用程序）想用电（CPU 时间）、想用水（内存）、想坐电梯（访问硬盘、网卡），都得经过物业。物业还负责安全：不能让 A 住户随便进 B 住户的房间（进程隔离），不能让任何人私拉电线碰高压电（特权指令保护）。

**引导（Boot）是什么？**
按下电源键后，CPU 很"笨"，它只会去硬盘的固定位置读一小段代码开始执行。这段代码的任务就是把更聪明的代码（我们的内核）从硬盘搬进内存、做好各种准备工作，然后跳转到内核入口。这个"接力"过程叫引导。本项目用 **Limine** 引导程序完成这件事——它负责早期的内存布局探测、CPU 特性检查，然后把控制权交给我们的 Rust 代码。

**为什么要用 QEMU？**
写内核不能直接在真机上调试——写崩了就是死机重启，连报错都看不到。QEMU 是一个模拟整台电脑的软件，它有"暂停""查看寄存器""读串口日志"这些真机没有的超能力，所以内核开发 99% 的时间都在 QEMU 里进行，真机验收放在最后。

**系统调用（syscall）是什么？**
应用程序想做一些"危险"的事（读文件、开窗口、发网络包），不能自己动手，要"打报告"给内核。这个打报告的固定通道就是系统调用。每个系统调用有一个编号，比如本项目内核的号段是 `0x4000-0x40FF`。应用程序把编号和参数放进寄存器，执行一条特殊指令，CPU 就切换到内核态，内核办完事再把结果还给它。

**为什么用 Rust 写内核？**
操作系统最容易死于一万种内存错误：用完没释放（泄漏）、用了已释放的（use-after-free）、越界访问（buffer overflow）……C 语言把这些坑全留给你，而 Rust 的编译器在编译期就把绝大多数这类错误拦下来。对一个从零写的内核来说，等于随身带了一个不知疲倦的代码审查员。

## 3. 整体架构一览

从下往上，整个系统分五层：

```
┌─────────────────────────────────────────────┐
│  应用层    浏览器 / 终端 / 文件管理器 / 游戏      │  ← 将来跑在 NOVA 上的程序
├─────────────────────────────────────────────┤
│  桌面层    桌面 shell / 任务栏 / 开始菜单 / VWM  │  ← shell、vwm、ui 等模块
├─────────────────────────────────────────────┤
│  服务层    进程管理 / 通知 / 主题 / 兼容层探测    │  ← 系统服务与守护逻辑
├─────────────────────────────────────────────┤
│  内核层    内存 / 调度 / 中断 / 系统调用 / 文件系统│  ← VARIX-500 核心
├─────────────────────────────────────────────┤
│  硬件层    CPU / 内存条 / 硬盘 / 显卡 / 键鼠     │  ← Limine 引导 + 驱动对接
└─────────────────────────────────────────────┘
```

配套的代码也按这个层次分布在仓库里：

- `kernel/` —— 内核本体（Rust，`no_std`，目标 x86_64 裸机）
- `src/` + `dist/` —— 桌面前端（TypeScript + Vite，构建产物在 dist）
- `src-tauri/` —— Tauri 桌面端壳（Rust + WebView，承载启动器）
- `portable/` —— Windows 便携化与兼容性探测脚本（PowerShell）
- `tools/` —— 构建辅助、性能基准（bench）、QEMU 监控等工具
- `docs/` —— 几百份设计文档、施工步骤、验收报告
- `scripts/` + `tools/limine/` —— 打 ISO 镜像的脚本与引导程序二进制

**数据怎么流动？** 用户在桌面上点一个应用图标 → 桌面层向内核发起系统调用"请启动这个进程" → 内核分配内存、加载 ELF 可执行文件、建立页表 → 新进程开始运行，它的窗口被 VWM 管理 → 用户的键鼠输入经中断进入内核 → 内核分发给焦点窗口。整个链路每一环都对应仓库里的一组模块。

## 4. 内核：VARIX-500

内核是整个项目最硬核的部分，位于 `kernel/` 目录，是一个独立的 Cargo workspace：

- `kernel/varix/` —— 内核 crate 本体
- `kernel/userspace/` —— 若干用户态小 crate（各自带空 `[workspace]` 表自成一体）

### 4.1 模块的"域"划分

内核源码在 `kernel/varix/src/` 下，按功能切成一个个**域模块**，一域一文件。每个域由一个 AI 会话负责（编号 AI-01 ~ AI-20），必须实现 25 项功能。域和文件的对应关系大致是：

| 域 | 主题 | 典型文件 |
|---|---|---|
| AI-01/02/03 | 基础设施、内存、启动早期 | 与 boot、mm 相关模块 |
| AI-05 | 稳定性与健壮性 | `robust.rs` |
| AI-07/08 | 组件库、动效 | `ui/` 子目录 |
| AI-10/11 | 桌面、shell | `shell/mod.rs`、`desktop.rs` |
| AI-16 | 界面基础 | `ui.rs`（F376~F400） |
| 其他 | 电源、图形服务、窗口管理等 | `power.rs`、`gfxsrv.rs` 等 |

所有域的功能都带 `F` 编号（如 F158、F376），注释格式统一为 `// Fxxx 功能名`，全文检索 `F1`~`F4` 开头的编号就能定位任何一项功能。

### 4.2 域模块的实现铁律

因为跑在裸机上，内核代码有一套严格的约束，写代码前必须知道：

1. **禁用标准库**。没有 `std`，也就没有 `Vec`、`String`、`Box`。一切动态数据用**固定容量数组**，比如 `[(u64, u64); 64]`，容量满了要么拒绝要么覆盖最旧，绝不动态分配。
2. **一域一文件**。`kernel/varix/src/<domain>.rs`，别人不会来改你的文件，你也不去碰别人的。
3. **每域必须导出自检函数**。`pub fn run_<domain>_checks() -> CheckSet`，用 `CheckSet::new("domain")` 建集合，用 `set.add("Fxxx ...", 条件, "说明")` 逐项断言，自检项不少于 25 个。这些自检最终由 `robust::run_kernel_checkup()` 汇总，形成"内核给自己体检"的闭环。
4. **单测写在模块里**。`#[cfg(test)] mod tests`，命名 `f<编号>_<要点>`，比如 `f158_map_reuse`。
5. **登记类接口必须去重**。`register`/`record`/`add` 这类函数要自带去重，否则重复登记会静默改变计数，让自检假绿或假红。

### 4.3 CheckSet 的"末态读取"陷阱（本项目最重要的经验）

这是开发过程中反复踩坑后总结出的一条铁律，值得单独一节：

在 `set.add("…", 条件1 && 对象.字段 == X && …)` 这种复合断言里，**对可变对象字段的读取发生在整个表达式求值的末尾**。如果你写了"操作 A → 读状态 → 操作 B → 断言"，那么"读状态"读到的是操作 B 之后的**末态**，中间过程的读数被覆盖了，断言结果完全是假的。

正确做法：**任何中间读数先存进独立的 `let` 变量**，再用变量参与布尔表达式。F158、F159、F164、F165、F183、F185、F186、F190、F191 等一堆自检项都因为这条挂过。

调试手法：临时加一个 `#[cfg(test)] mod tmp_dbg` 模块，把复合断言拆成逐条 `assert!(…, "标签")`，一次定位到具体子条件；**验证完立刻删掉这个模块**，不许提交。

### 4.4 中断与"运行时生成代码"的特殊处理

x86_64 的中断处理要求入口代码所在的内存页**可执行**。而 Limine 引导会把 `.data` 段映射为不可执行（NX）。所以内核做了两件专门的事：

- 链接脚本 `linker.ld` 里有专门的页对齐 `.stubs` 段，放中断入口 stub；
- 运行时用 `harden_stub_mapping()` 走页表把这段内存的 NX 位清掉、写位清掉。

任何新的"运行时生成代码"需求都必须走这条路径，**不能把生成的代码塞进 `.data`**——那样一触发就是页错误。致命异常现在会打印 `err/rip/cr2` 三个关键地址（见 `cpu/idt.rs` 的 `isr_dispatch`），配合符号表能把崩溃定位到具体函数。

### 4.5 Rust 裸机开发的实战坑（血泪清单）

以下每条都是实际翻过车记录下来的，写内核代码前建议通读：

- **`const fn` 里不能用 `Ord::min`**：`1u64 << kind.min(63)` 报 E0658。手写 `if kind > 63 { 63 } else { kind }`。
- **非 `Copy` 类型的数组初始化**：`[None; N]` 要求元素可 `Copy`。带大缓冲的类型要写 `[const { None }; N]`（inline const block）。
- **`Result<&mut T, E>` 不能 `assert_eq!`**：`&mut T` 没有 `PartialEq` 和 `Debug`，连带 `Option<Result<(), E>>` 的 `==` 也不成立。用 `is_err()`，或先把字段拷成值再比。
- **fuzz 要偏置到有效号段**：纯随机的 `u64` 落到内核系统调用号段的概率约等于零，每轮都进 `ENOSYS`，"零 panic"是空证明。正确配比是 1/4 完全野生 + 1/4 原生带 + 1/4 兼容带 + 1/4 低位全谱。
- **清"未用导入"要连带查测试模块**：从模块顶部删掉的常量，`#[cfg(test)] mod tests` 里可能还在用，会报 E0425。正确做法是把该导入下沉进测试模块。

## 5. 引导与启动流程

从按下电源到内核跑起来，完整链路是这样的：

```
电源上电
  → UEFI/BIOS 固件自检
  → 读取 ISO 里的引导程序（Limine）
  → Limine 探测内存布局、CPU 特性，建立初始页表
  → 加载内核 ELF（cargo kbuild 的产物）
  → 跳转到内核入口（Rust 代码开始执行）
  → 内核初始化：串口 → 页表 → 中断 → 调度器 → 各域模块
  → 输出 "boot complete"，串口日志全程可查
```

**打 ISO 镜像**用 `scripts/make-iso.sh`，它**必须用 xorriso**（注意：`tools/build-iso.py` 的 pycdlib 产物 Limine 读不了大文件，这是个实测结论，别踩）。xorriso 的便携版解包在 `/tmp/xorr`，会话重启可能丢失，需要时从 msys2 包重新解。

**Limine 的发布包有个著名的坑**：GitHub 上 `limine-<ver>.tar.gz` 是**源码包**，里面没有任何预编译的 `.bin` 文件。要拿 `limine-bios-cd.bin`、`limine-uefi-cd.bin`、`limine-bios.sys` 这些引导二进制，必须下载 **`limine-binary.tar.gz`**，而且解包时**不要加 `--strip-components=1`**（它的首层目录就叫 `limine-binary/`，脚本按 `tools/limine/limine-binary/*.bin` 的路径找文件）。CI 里有 `test -f … || exit 1` 的硬门禁专门防这个。

启动完成后怎么"看见"内核？两条通道：

1. **串口日志**：QEMU 用 `-serial file:serialX.log` 把串口输出写到文件，启动过程、panic 信息全在这里。
2. **QEMU monitor**：用 `-monitor tcp:127.0.0.1:55xx,server,nowait` 开一个 TCP 控制口，用仓库自带的 `tools/qmon.py` 发 `info registers`、`xp /96xg 0x…` 之类的命令查看 CPU 状态和内存（脚本自带剥回显和 ANSI 转义）。

崩溃定位的标准流程：看串口最后一行 → 问 monitor 要 `info status` → 拿 RIP/CR2 → 用 Python 解析内核 ELF 的符号表把地址映射回函数名 → 反汇编确认。这套流程在多次真机调试中已经打磨成熟。

## 6. 窗口系统与桌面环境

窗口系统（VWM，Virtual Window Manager）是桌面层的核心，对应内核里的 `vwm` 模块和前端的 `vwm.ts`、`snapshots.ts`。它解决的问题是：多个应用的窗口如何在同一个屏幕上共存、争抢、被组织。

### 6.1 分层嵌入模型（tier）

VWM 把窗口分成 L1~L4 几个层级，不同的应用按特性进不同的层：

- **L1（主路径）**：普通应用的窗口，正常嵌入桌面合成。
- **L4（让位层）**：反作弊游戏、独占全屏应用这类"不服管"的程序。它们会被探测出来并**主动让位**——不强制重父级嵌入，交由运行时看护。这里有明确的归因信号 `compat.hint`，值是 `fullscreen`（独占全屏引擎窗口）或 `anticheat`（检测到反作弊服务特征）。归因为 anticheat 的还会停用键盘钩子并挂横幅提示。

曾经有个实际 bug：tier 路由的 `_` 兜底臂把 L4 也吞了，导致反作弊应用被错误强制嵌入。修复方式是补了显式的 L4 让位臂，`_` 兜底只服务 L1 主路径。这个案例说明：**兜底逻辑一定要想清楚"谁不应该走到这里"**。

### 6.2 窗口的其他机制

- **窗口快照**：`snapshots.ts` 负责窗口布局的保存与恢复。
- **DPI 适配**：混合 DPI 是桌面系统的经典难题，有专门的回归测试清单（10 款软件的验收矩阵）。
- **shell 看护**：`shell_watch.rs` 里有一份 15 类进程的白名单（唯一小写）、三态回收策略（默认"询问"，不自动回收），全部有契约单测盯着。
- **快捷键纪律**：键位有专门的纪律组（见 `docs/AI05-交付报告-键位纪律组.md`），避免和应用抢键。

### 6.3 主题与国际化

- 主题令牌有一份开放规范（`docs/AI14-主题令牌开放规范-Z50.md`）和扩展兼容承诺与版本矩阵，第三方主题按令牌接入就不会被升级打破。
- i18n 支持中/英双语，词典在 `src/i18n/dictionaries.ts`（约 278 KB 的单文件，新词条加在这里）。

## 7. 应用兼容层：让 Windows 程序跑起来

这是 NOVA-500 最有特色的部分。一个新操作系统最大的死穴是"没有软件"，所以项目花了大力气做兼容性探测与让位机制。

### 7.1 兼容探测（compat probe）

内核侧有 `compat_probe.rs`：启动应用时探测它的窗口样式、引擎特征、反作弊服务，输出一个 `CompatInfo`（含 tier 分层决策和 hint 归因）。这个探测器的分类逻辑和 PowerShell 侧的探测脚本（`portable/AI5/Compat-Matrix.ps1`）是**镜像关系**——两边用同一棵决策树，保证内核判断和外部验证口径一致。

### 7.2 兼容性矩阵工具

`portable/AI5/Compat-Matrix.ps1` 提供 `-Action Run-Embed / Report-Embed`：逐个启动真实软件 → 探测窗口样式分层 → 记录 `{tier, captureMs, crash, inputOk, dpiOk}`。其中 `inputOk/dpiOk` 这类必须真人操作才能确认的字段，脚本**诚实输出 `todo`** 等人工回填，绝不臆造。这个"脚本可以不知道，但不许编"的原则贯穿整个项目的验收体系。

### 7.3 性能预算

窗口捕获有明确的性能预算：端到端 P95 < 50ms（`tools/bench.cjs` 的 `captureE2E` 项）。真机未测量前报告如实写 SKIPPED 并附测量协议，测了就落盘到 `docs/bench/`。

## 8. 桌面端启动器（Launcher）

桌面端是一个 Tauri 应用：

- **壳**：`src-tauri/`（Rust），负责窗口、托盘、进程管理等原生能力。
- **前端**：`src/`（TypeScript + Vite），构建产物在 `dist/`。
- **测试**：`src-tauri/tests/`、`src-tauri/crates/` 下有自己的子 crate。

桌面端和内核的关系是"操盘手"：它在 Windows 宿主上运行，负责验证窗口嵌入、兼容探测这些逻辑（用真实 Windows 应用作靶子），验证通过的语义再下沉到内核的 VWM 实现。所以你在 `CHANGELOG.md` 里会看到大量"LauncherManager L4 徽标 + i18n"这类前后端联动记录——内核语义和桌面 UI 是同步演进的。

几个"为什么"：

## 11. 开发指南：域模块与"25 项功能"约定

想给内核加一个新域？照着这个流程走：

1. **建文件**：`kernel/varix/src/<你的域>.rs`，并在 `lib.rs` 加 `pub mod <你的域>;`（注意 `lib.rs` 的模块列表被多方追加，编辑前先 `git log` 和重读文件）。
2. **写功能**：25 项，每项用 `// Fxxx 名称` 注释分区；纯逻辑 + 固定容量数组。
3. **写自检**：导出 `pub fn run_<你的域>_checks() -> CheckSet`，`set.add` 逐项断言，≥25 条。
4. **写单测**：模块内 `#[cfg(test)] mod tests`，命名 `f<编号>_<要点>`。
5. **挂进体检**：在 `robust` 的聚合处把你的域加进去（`robust` 自身排除，避免递归）。
6. **跑 `cargo ktest --lib` 全绿、`cargo kbuild` 零告警**，然后提交。

**提交信息格式**：`varix500(ai-XX): Fxxx <功能名>`。一功能一提交或一域一提交，不许大杂烩。

**自检失败排查**：让测试 panic 出 `CheckSet::render` 的完整内容，否则你只能看到一句"domain self-test must pass"，定位不到具体 F 项。复合断言的坑见 4.3 节"末态读取"。

## 12. 测试与质量保障

这个项目的测试体系分四层：

1. **单元测试**（2114+ 个）：每个域模块内部，覆盖每项功能的核心行为。主机上跑（`cargo ktest --lib`），用 std 编译方便调试。
2. **域自检 CheckSet**：内核运行时给自己做的"体检"，25 项/域，由 `run_kernel_checkup()` 汇总。这是"功能在真实内核环境里也成立"的第二道保险。
3. **Fuzz**：对系统调用等入口做模糊测试。关键点：输入必须偏置到有效号段（见 4.5 节），否则是自欺欺人的"零 panic"。
4. **验收清单**：`docs/acceptance/` 下按批次组织的真机验收项。代码级完成 ≠ 验收通过，两者分得清清楚楚。

**CI**：`.github/workflows/ci.yml` 有三个 job——frontend（前端构建+测试）、backend（桌面端）、kernel（kcheck、ktest、fuzz、kbuild 并产出 ELF 构件）。

**基线命令**：任何改动合入前，本地必须跑过 canonical 命令组合：`cargo ktest`（全绿）+ `cargo kbuild`（零告警）。

## 13. 真机与 QEMU 验收

QEMU 的详细用法见第 5、10 节。这里补充验收视角的要点：

## 14. 多会话并行开发纪律

本项目大量采用"多个 AI 会话并行开发不同域"的模式，为此沉淀了一套纪律，人类协作同样适用：

### 14.1 文件边界

- 一域一文件，只改自己域的段落。共享文档（如 `docs/VARIX-500-*.md`）只改自己 `## AI-xx ·` 到下一个 `## AI-x` 之间的部分。
- 编辑共享文件前先 `git log` + 重读，并行会话可能刚改过它。

### 14.2 Git 操作（最重要的教训都在这）

- **绝对禁止 `git pull --rebase --autostash`**。这条命令曾经把本仓库的 `.git/objects/pack/*.pack` 整体删掉、`refs/heads/main` 弄丢，本地对象库报废。对齐远端的正确姿势：

  ```bash
  git fetch origin +refs/heads/main:refs/remotes/origin/main
  git reset --mixed <远端SHA>   # --mixed 保工作区
  ```

- **提交前先看状态**：`git log --oneline -1` + `git status --porcelain`，只 add 自己域的路径。并行会话的一句 `git add .` 会把别人未提交的文件卷进你的提交——这事真实发生过。
- **提交模块别忘了 lib.rs**：`pub mod` 列表是共享的，提交自己的新模块时要连带工作区里别人新增的模块文件（否则 HEAD 缺文件构建失败）。
- **GitHub 推送**：凭据在 Windows 凭据管理器时，注意 `~/.gitconfig` 里空的 `credential.helper=` 会清空助手链。可用 `git -c credential.helper= -c credential.helper=wincred push origin main`。本地代理对 github.com 间歇性 502，需循环重试。

### 14.3 隔离验证法

当并行会话把别处源码改坏、整个 crate 编不过时，你可以把自己的模块与 `checks.rs` 复制到一个临时 scratch crate（`/tmp/bcverify`，Cargo.toml 里 `[profile.test] panic = "unwind"`）单独验证，完全绕开他人的编译错误。**这是"不被队友堵死"的关键技能。**

## 15. 常见问题（FAQ）

**Q：为什么我 `cargo test` 全量跑会失败？**
A：内核 bin 目标（msvc target）不支持 unwinding panic，全量会挂。用 `cargo ktest --lib` 只跑库测试。

**Q：为什么打出来的 ISO 引导不了大文件？**
A：十有八九是用 `tools/build-iso.py`（pycdlib）打的。它生成的镜像 Limine 读不了大文件，必须用 `scripts/make-iso.sh`（xorriso）。

**Q：Limine 下载解压后找不到 .bin 文件？**
A：你下的是源码包 `limine-<ver>.tar.gz`。要下 `limine-binary.tar.gz`，且解包不加 `--strip-components=1`。

**Q：CI 的 Actions 一个 job 都没跑？**
A：这是 GitHub 账号层面的问题（额度/账单/被禁用），与代码无关。workflow 状态显示 active 但 run 全是 0 job。本地跑 canonical 命令作为替代门禁。

**Q：`kernel/userspace/<crate>` 编译报"believes it's in a workspace"？**
A：它在 `kernel/` workspace 目录树内但不是成员。给它加一个空 `[workspace]` 表自成一体，并在 `.gitignore` 加 `kernel/userspace/*/target/`。

**Q：怎么给 fuzz 写有效的输入？**
A：按 1/4 野生 + 1/4 原生号段 + 1/4 兼容带 + 1/4 低位全谱配比生成，保证处理逻辑真的被执行到。

**Q：为什么我的 CheckSet 断言"明明该过却不过"（或明明该挂却过了）？**
A：九成是"末态读取"（见 4.3 节）。把中间读数存进独立的 `let` 变量再参与断言。

**Q：仓库清理过吗？archive/ 是什么？**
A：2026-09-12 做过一次大清理：三个构建缓存目录（约 35 GB）已删（可再生）；根目录临时文件和调试截图移入 `archive/`（本地留底，可随时恢复）。

## 16. 术语表

| 术语 | 含义 |
|---|---|
| **no_std** | 不链接 Rust 标准库的编译模式，裸机/嵌入式必需 |
| **HHDM** | 更高半直接映射，Limine 建立的"物理地址+固定偏移"全量映射，内核访问物理内存的常用手段 |
| **NX** | No-eXecute，内存页不可执行位。Limine 把 `.data` 映射为 NX，所以运行时生成代码要走 `.stubs` 段 |
| **ELF** | 可执行链接格式，内核和应用二进制的标准格式 |
| **CR2 / RIP** | x86 控制寄存器（缺页地址）/ 指令指针，崩溃定位的三件套之一（另一个是错误码 err） |
| **CheckSet** | 本项目发明的域自检框架，`set.add(名称, 条件, 说明)` 逐项断言 |
| **tier（L1~L4）** | 兼容层给应用窗口的分层：普通嵌入 / … / 让位（反作弊与独占全屏） |
| **hint** | 兼容让位的归因信号：`fullscreen` 或 `anticheat` |
| **DoD** | Definition of Done，完成定义。本项目严格区分"代码级完成"与"验收通过" |
| **canonical 命令** | 合入前的基线验证命令：`cargo ktest` + `cargo kbuild` |

## 20. 内核子系统深入

这一节把内核的几个核心子系统单独展开讲，帮助你把第 4 节的概览落到具体机制上。

### 20.1 内存管理

裸机上没有"malloc"，内核要自己从 Limine 交来的物理内存地图里建立整个体系：

- **物理页帧管理**：把物理内存按 4 KiB 分页，用位图或空闲链表跟踪"哪些页在用、哪些空闲"。分配就是找到一页置位，释放就是清位——听起来简单，但要做到 O(1) 且无分配器可用时的自举（早期连位图本身都得静态预留），有很多讲究。
- **页表**：x86_64 是四级页表（PML4 → PDPT → PD → PT）。内核启动早期 Limine 已建好一套映射（内核自身 + HHDM 全物理映射），之后内核按需增删映射——映射 MMIO 设备、给新进程建地址空间等。改页表后要记得刷新 TLB（必要时 `invlpg` 或重载 CR3）。
- **内核堆**：有了页帧分配器后，在其上包一层"字节粒度"的堆分配器，内核内部的数据结构才能舒服一点。但即便如此，域模块约定仍然禁止 `Vec/String/Box`——固定容量数组让每处内存开销在编译期就一目了然，这对内核的可预测性是好事。

**中断和内存的耦合点**：`.stubs` 段的设计（见 4.4 节）本质上是内存保护属性问题——代码段、数据段、可执行段在页级各归各位。这也是为什么链接脚本 `linker.ld` 是内核仓库里最需要小心对待的文件之一。

### 20.2 中断与异常

x86_64 的中断体系分三类，内核对每类的处理都在 `cpu/idt.rs` 一带：

1. **异常（CPU 主动报错）**：缺页（14）、一般保护错（13）、除零（0）等。内核的 `isr_dispatch` 统一接管，致命异常会打印 `err / rip / cr2` 三元组。**cr2 是缺页时访问的坏地址，rip 是出错的指令位置**，两者一对照，配合 ELF 符号表，基本一枪定位。
2. **硬件中断（设备通知）**：定时器、键鼠、串口等。经过 APIC 路由进来，处理完要发 EOI，否则中断风暴直接卡死。
3. **系统调用（应用主动求助）**：走 `syscall/sysret` 快速通道，这是第 20.3 节的主角。

中断处理有一条铁律：**处理函数要短**。慢活儿（复制数据、唤醒进程）记下来放到下半部做，否则下一个中断来了你还没处理完，系统表现就是"莫名卡死"。

### 20.3 系统调用接口

内核的系统调用号规划了明确的号段，比如内核原生功能占 `0x4000-0x40FF`。每个域的功能暴露为系统调用后，应用层才能用到它。调用约定是经典的"寄存器传参"：编号进 rax，参数进 rdi/rsi/rdx……返回值和错误码也从寄存器回。

 fuzz 配比（1/4 野生 + 1/4 原生 + 1/4 兼容 + 1/4 低位全谱）就是为这个接口设计的：既保证处理逻辑真的被执行到，也不放过野指针式的异常输入——**一个被 fuzz 打崩的系统调用，比一百个测试通过的用例更值钱**。

### 20.4 进程与调度

调度的本质是"CPU 时间怎么分"。本项目采用域模块化实现（调度相关逻辑在对应域文件里），设计上强调：

- **可预测性优先**：固定容量的就绪队列、无动态分配，最坏情况有上界。这和桌面系统的流畅性目标是一致的——卡顿的根源往往就是"某个路径的时间不可预测"。
- **上下文切换**：保存当前任务寄存器组 → 换页表（如果换进程）→ 恢复下一个任务的寄存器组 → 返回。中断返回指令（`iretq`）天然是切换的载体。

### 20.5 自检闭环：内核如何"给自己体检"

第 4.2 节提到每个域要导出 `run_<domain>_checks()`。整个闭环是这样工作的：

```
robust::run_kernel_checkup()
  → 依次调用各域的 run_<domain>_checks()（robust 自己除外，防递归）
  → 每个域返回一个 CheckSet（若干条 add(名称, 条件, 说明)）
  → 全部通过：内核宣告健康；有失败：打印 CheckSet::render 的明细
```

这套机制的价值在于：单测在**主机**上验证逻辑，自检在**真内核环境**里验证行为，两层都绿才算真的成立。很多"主机测试全绿、内核里行为不对"的问题都是自检抓出来的。

## 21. 桌面端技术细节

### 21.1 Tauri 壳的职责

`src-tauri/` 的 Rust 壳不是"套壳浏览器"那么简单，它承担：

- **进程管理**：启动、监控、回收被测的真实 Windows 应用（配合兼容矩阵脚本）。
- **窗口操控**：句柄探测、样式读取、嵌入/脱离——这些正是内核 VWM 语义的"地面试验场"。
- **托盘与快捷键**：桌面系统集成面。

### 21.2 前端结构

- `src/i18n/dictionaries.ts`：双语词典。新增 UI 文案必须中英同步添加，i18n 键缺失在构建期就会暴露。
- VWM 前端逻辑在 `src/` 的 `vwm.ts`、`snapshots.ts`：窗口树的读写、快照的保存恢复。
- 主题走令牌（token）体系：颜色、间距、字号都不是硬编码，而是引用令牌名。第三方主题只需覆盖令牌表，不动布局代码——这就是"主题令牌开放规范"的出发点。

### 21.3 端到端联动示例：L4 让位

一个完整的功能从内核到 UI 是这样贯通的（以 L4 让位为例）：

1. 内核 `compat_probe.rs` 探测应用 → 输出 `CompatInfo { tier, hint }`；
2. 语义下沉：`hint` 进 serde 序列化，旧的 `apps.json` 平滑升级（default 字段）；
3. 前端消费：LauncherManager 显示 L4 徽标（AC/FS 图标），悬停给出完整说明；
4. i18n：徽标说明文案中英双语入词典；
5. 契约测试：`shell_watch.rs` 的单测锁住策略语义（三态、默认询问）；
6. 验收：`Compat-Matrix.ps1` 真机跑一遍，报告落盘。

一个功能的"完成"横跨这六步，缺一步都不算完——这也是 CHANGELOG 里每个批次条目都很长的原因。

## 22. Windows 开发环境搭建细节

本项目大量开发在 Windows 上进行，以下都是实测过的注意事项：

### 22.1 Rust 工具链

- 内核命令始终带 `RUSTUP_TOOLCHAIN=1.97.1-x86_64-pc-windows-msvc` 显式指定工具链，**绕过 `rust-toolchain.toml` 的自动 resync**——resync 一旦触发会回滚甚至删光已装工具链（真实事故）。
- rustup 工具链可能整体损坏（manifest Missing）。修法：uninstall 后以 minimal profile 重装 rustc/std/rust-src；损坏严重时直接从 static.rust-lang.org 的 dist 手工解包归档（注意归档内层还有同名目录要拍平）+ 手写 rustlib 的 manifest/components。
- 内核构建用 msvc target 出 ELF：`cd kernel && cargo kbuild`。

### 22.2 xorriso 与 QEMU 的便携化

- xorriso：从 msys2 包解压到 `/tmp/xorr`（或项目内固定路径），用时把它的 bin 加进 PATH。重启会话可能丢，丢了就重新解。
- QEMU：仓库 `qemu/` 目录有便携安装（1.2 GB，已 gitignore）。命令行参数见第 10.2 节。

### 22.3 代理与网络

- 本地代理（127.0.0.1）对 github.com 的 CONNECT 间歇性 502 / 连接中断，推送失败要循环重试 2~6 次；api.github.com 通常正常，别被它误导。
- `~/.gitconfig` 里若有空值 `credential.helper=`，会把凭据助手链清空，push 拿不到凭据。按第 17 节速查表的命令行参数方式绕过，不改全局配置。

### 22.4 路径与编码

- Windows 上含非 ASCII 路径的 `.ps1`/`.bat` 脚本文件容易编码损坏（文件名变乱码）。**批处理一律直接用命令行执行，不要落盘成脚本文件。**
- 整仓 `git fetch` 在 Windows 上可能因仓库里存在仅有大小写差异的分支/路径而失败，必要时只 fetch 需要的 ref。

## 24. 设计哲学：这个项目信什么

翻完整个仓库，可以提炼出几条一以贯之的原则。理解它们，比记住任何一条具体规则都重要。

### 24.1 诚实优先于好看

`inputOk` 没测就写 `todo`，P95 没量就写 `SKIPPED` 并附测量协议，真机没跑就标"待环境具备"。**这个项目宁可满篇 todo，也不造一个假绿。** 对应地，验收清单永远区分"代码级完成"和"验收通过"两个状态。

### 24.2 边界让协作成为可能

一域一文件、域间不越界、共享文件只改自己的段落、提交只挑自己的路径——这些纪律看起来繁琐，但它们是"几十个会话并行开发一个内核而互不踩脚"的前提。**自由来自边界，不是来自无序。**

### 24.3 固定容量是一种美德

内核里禁用 `Vec/String/Box`，乍看是自找苦吃，实则是把"最坏情况内存开销"变成编译期可知的常量。嵌入式和内核开发的共同信条：**可预测性 > 便利性**。

### 24.4 防呆靠机制不靠自觉

Limine 包下载有 `test -f … || exit 1` 硬门禁；`.stubs` 段有 `harden_stub_mapping()` 运行时加固；致命异常自动打印 err/rip/cr2；CheckSet 自检进内核运行时。**凡是踩过的坑，都尽量变成下次踩不进去的栅栏。**

### 24.5 每个清理都可逆

仓库大清理时，构建缓存删除（可再生），历史文件移入 `archive/` 留底，git 改动可随时 checkout 恢复。对仓库做减法的前提是**随时能加回来**。

## 28. 域功能举例：25 项功能长什么样

"每域 25 项功能"到底是 25 个什么东西？用几个真实域的典型功能给你具象化。

### 28.1 电源管理域（power.rs）

```
// F201 交流电源状态检测与切换事件记录
// F202 电池电量阈值（低电量/临界）判定
// F203 睡眠请求的资格检查（有未保存状态则拒绝）
// F204 休眠映像的完整性校验
// F205 处理器空闲态的投票统计
// ...共 25 项
```

每一项都是**一个可独立断言的行为**：给定这样的输入，系统应该有这样的输出/状态迁移。`set.add("F203 睡眠资格", 睡眠请求 && 有未保存状态 == 拒绝, "脏状态必须阻塞睡眠")` 就是自检项的样子。

### 28.2 健壮性域（robust.rs）

这个域比较特殊：它除了自己的 25 项，还承担**全内核自检的聚合**职责——`run_kernel_checkup()` 遍历调用其他所有域的 `run_*_checks()`（排除自身，防递归）。它自己的功能多是"元层面"的：

- CheckSet 渲染格式稳定（崩溃日志可解析）
- 自检项总数与登记数一致（防漏挂）
- 聚合过程自身零分配

### 28.3 图形服务域（gfxsrv.rs）

帧缓冲格式协商、脏矩形跟踪、帧提交时序……典型的 F 项比如"帧缓冲 stride 不等于宽度时的正确寻址"——这类 bug 在主机上永远测不出来，只有真内核里自检能抓到。这也再次印证第 12 节说的：单测和自检是互补的两层。

### 28.4 功能编号的全局索引

所有域的 F 编号是全局唯一的（AI-01 从 F001 起，AI-16 是 F376~F400……），所以：

- `grep -rn "F376" kernel/varix/src/` 一步定位任何功能；
- 提交信息 `varix500(ai-16): F376 xxx` 直接说明"谁改了哪个功能"；
- 验收清单按 F 编号勾选，代码、测试、验收三方对账用同一套编号。

**编号即接口**——这是本项目协作体系里最简洁也最有效的设计之一。

## 29. 构建系统全解

### 29.1 内核侧：Cargo 与自定义 target

内核是一个独立 workspace（`kernel/`），核心配置：

- **target**：`x86_64-unknown-none`——没有操作系统的 64 位裸机。这意味着所有依赖 crate 也必须是 `no_std` 兼容的。
- **构建产物**：release 模式的 ELF 内核。Limine 加载的就是它。
- **常用别名**（定义在 workspace 的配置里）：
  - `cargo kbuild` —— 构建内核 ELF
  - `cargo ktest` —— 主机单测（std 模式编译，方便 IDE 与调试）
  - `cargo kcheck` —— 最快的语法/类型检查

`cargo ktest` 有个已知坑：全量跑会因 bin 目标（msvc target）的 unwinding panic 失败，**日常用 `cargo ktest --lib`**。

### 29.2 内核 workspace 里的用户态 crate

`kernel/userspace/` 下的 crate 虽然物理上在 kernel 目录树里，但**不是** workspace 成员。它们各自带一个空 `[workspace]` 表"自成一体"，否则 cargo 会报"believes it's in a workspace when it's not"。配套的 `.gitignore` 规则 `kernel/userspace/*/target/` 防止它们的构建产物入库。

### 29.3 前端与桌面端

- `package.json` / Vite：前端构建，`npm run build` 出 `dist/`。
- `src-tauri/`：Tauri 项目自带 Cargo 工程，构建产物在 `src-tauri/target/`。
- 三者的构建互不依赖，可以并行开发。

### 29.4 ISO 打包链

`scripts/make-iso.sh` 做的事：建 ISO 目录树 → 拷内核 ELF 与 Limine 引导二进制 → 写 `limine.conf` → xorriso 出盘。三个易错点（都有硬门禁或注释防呆）：

1. 必须 xorriso，不能用 pycdlib 方案；
2. Limine 必须是 binary 包解出来的（`tools/limine/limine-binary/` 下三个 .bin/.sys）；
3. 解包 binary 包不加 `--strip-components=1`。

### 29.5 CI 三路流水线

`.github/workflows/ci.yml` 的三个 job：

| job | 内容 | 产物 |
|---|---|---|
| frontend | npm ci + vite build + 前端检查 | dist |
| backend | src-tauri 的 cargo test | — |
| kernel | kcheck + ktest + fuzz + kbuild | 内核 ELF 构件 |

## 30. 故障排查手册

按"症状 → 可能原因 → 动作"组织，都是实际出现过的问题。

### 内核类

| 症状 | 可能原因 | 动作 |
|---|---|---|
| QEMU 启动即死循环/重启 | 早期引导失败 | 检查 ISO 是否 xorriso 产物；串口日志首行 |
| boot complete 后输入无响应 | 中断未发 EOI 或 IDT stub 未映射对 | 查 `harden_stub_mapping()` 是否执行；`.stubs` 段是否页对齐 |
| fatal exception 14（缺页） | 访问未映射地址 | 读串口里的 err/rip/cr2，符号表定位 rip；cr2 是坏地址 |
| `.data` 里的代码一执行就崩 | Limine 把 .data 映射为 NX | 运行时生成代码必须走 `.stubs` 路径 |
| `cargo ktest` 全量挂 | bin 目标 unwinding panic | 用 `cargo ktest --lib` |
| 域自检只报 "must pass" | 没输出明细 | 让测试 panic 出 `CheckSet::render` 内容再定位 |

### 构建类

| 症状 | 原因与动作 |
|---|---|
| `Ord::min` 报 E0658 | const fn 里不能用；手写 if 分支 |
| `[None; N]` 报错 | 元素非 Copy；改用 `[const { None }; N]` |
| `assert_eq!(res, Err(e))` 编译不过 | `&mut T` 无 PartialEq/Debug；用 `is_err()` |
| E0425 找不到常量 | 删顶部导入时测试模块还在用；把导入下沉进 `mod tests` |
| userspace crate 报 workspace 错误 | 加空 `[workspace]` 表 |

### 协作类

| 症状 | 原因与动作 |
|---|---|
| push 拿不到凭据 | `.gitconfig` 空 helper 清空了助手链；用 `-c credential.helper=wincred` |
| push 间歇 502 | 本地代理对 github.com 不稳；循环重试 2~6 次 |
| `git pull --rebase --autostash` 后历史全丢 | 对象库被删；用 `git fetch` + `reset --mixed` 恢复（见 14.2） |
| 提交后发现多了别人的文件 | `git add .` 卷入；下次提交前按路径精确 add |
| 整仓 fetch 失败（Windows） | 分支存在仅大小写差异；只 fetch 需要的 ref |

## 34. QEMU 调试教程：把内核当进程调试

很多人以为内核调试只能靠 print，其实 QEMU 给了相当现代的调试手段。这里给一份进阶教程。

### 34.1 三种观测通道

1. **串口日志（最低成本）**：`-serial file:xxx.log`。内核的 `print!` 宏实现接到串口，启动全程、panic、自检明细都在这里。**先看最后一行，八成问题一眼可见。**
2. **QEMU monitor（状态快照）**：`-monitor tcp:…` 开 TCP 口，`tools/qmon.py` 发命令。常用命令：
   - `info status` —— CPU 是运行还是暂停
   - `info registers` —— 全部寄存器当前值
   - `xp /96xg 0x…` —— 按物理地址查看内存（注意：只能看已映射地址）
   - `info mtree` —— 内存映射树，查 MMIO 布局
3. **GDB 远程调试（大杀器）**：QEMU 加 `-s -S`（-s 开 gdbserver，-S 启动时暂停），然后：

   ```bash
   gdb kernel/target/x86_64-unknown-none/release/varix
   (gdb) target remote :1234
   (gdb) break <函数名>   # 带符号表的断点！
   (gdb) continue
   ```

   单步、看变量、看栈，和调试普通程序一样。**唯一注意**：内核运行在物理地址偏移上，符号地址与实际地址可能有偏差，必要时用 `add-symbol-file` 调整。

### 34.2 一次典型的崩溃解剖

假设串口末行是：

```
fatal exception 14, err=0x2 rip=0x401234 cr2=0xdead0000
```

解剖步骤：

1. err=0x2 → 缺页，读操作，内核态（按 x86 错误码位拆）；
2. rip=0x401234 → 用 Python 脚本解析 ELF symtab，落在某个函数的某条指令附近；
3. cr2=0xdead0000 → 访问的坏地址。看它像什么：是空指针加偏移？未映射的 MMIO？栈溢出到哨兵区？
4. `info registers` 对照其余寄存器，确定是哪个指针算坏了；
5. 修复 → `cargo kbuild` → 重新打 ISO → 复验。

整套流程十分钟内可以走完一轮，这就是"QEMU 里开发内核"的生产力。

### 34.3 截屏与录像

`qscreen*.ppm` 这些文件是怎么来的？QEMU monitor 的 `screendump` 命令可以随时把虚拟机画面存成 PPM 图（再转 PNG）。验收报告里的界面截图就是这么产生的——`python tools/qmon.py <port> "screendump shot.ppm"`。

## 36. 性能观：为什么处处讲 P95

`docs/bench/` 里所有性能指标都讲 P95（第 95 百分位），而不是平均值。原因值得展开讲：

- **平均值会说谎**。99 次捕获 10ms、1 次 800ms，平均 13ms 看起来很美，但用户记住的是那一次 800ms 的卡顿。
- **P95 是体验指标**。它直接回答"用户大多数时候会遭遇多慢"。窗口捕获预算 P95 < 50ms，意味着每 20 次里最多 1 次可以到 50ms 以上。
- **P95 可回归**。每次 bench 报告落盘（`docs/bench/日期.md`），P95 涨了就是退化，一目了然。

同样的道理也解释了内核为何执着于"固定容量、无动态分配"：**最坏情况有上界的系统，才谈得上 P95 达标**。桌面系统的"手感"，就是这一条条上界堆出来的。

## 37. 安全观：内核代码的攻击面意识

即使这是研究项目，内核代码也按"会被攻击"的标准写，几个具体体现：

1. **系统调用参数全量校验**：fuzz 的存在（尤其偏置配比）就是在模拟恶意调用者。所有指针参数、容量参数都要过校验层，不信任任何来自用户态的数字。
2. **登记表容量满的失败路径**：固定容量数组满了不是"悄悄丢弃"而是明确的错误返回——攻击者最喜欢的就是"满了以后行为未定义"的接口。
3. **最小特权**：hint=anticheat 的应用连键盘钩子都被停用——功能让位于安全边界。
4. **错误码文化**：宁可返回 `ENOSYS` 也不许"假装成功"。静默成功是安全漏洞之母。

2. **不做即时动态内存**——内核路径零动态分配，谁想引入 `Vec` 请先说服第 24.3 节。
3. **不做自动回收用户窗口**——shell 看护策略默认"询问"，绝不自动杀（契约单测锁死）。
4. **不伪造验收数据**——见 24.1，这是红线。
5. **不做不可逆操作**——清理进 archive、删除可再生、历史进 git，见 24.5。

## 附录 G：快速问答集（第二轮 FAQ）

第一轮 FAQ（第 15 节）偏技术排障，这一轮收录更像"人问的"问题：

**Q：这项目和 Linux 有什么关系？**
A：没有关系。不基于 Linux 内核、不用 GNU 工具链构建内核、不兼容 POSIX ABI。唯一的交集是都用 Limine 这类引导协议和 x86_64 硬件标准。

**Q：为什么内核测试能在主机上跑？裸机代码怎么会有单测？**
A：内核域模块被刻意设计成"纯逻辑 + 固定数组"，不碰硬件就能编译成普通 Rust 库（std 模式）在主机上测试。真正碰硬件的部分（页表切换、端口 IO）才需要在 QEMU 里验证。这套分层让 2114 个测试的绝大部分可以秒级跑完。

**Q：桌面端为什么要用 Tauri，而不是 GTK/Qt？**
A：因为桌面端目前的角色是"试验场与操盘手"——在真实 Windows 宿主上验证窗口嵌入、兼容探测的语义，验证通过后下沉到内核实现。Tauri 让团队用熟悉的前端技术栈快速搭 UI，把精力留给真正要验证的语义，而不是造一遍窗口控件。

**Q：archive/ 会不会被 git 忽略掉导致其实没备份？**
A：archive 里的文件在工作区磁盘上是真实存在的（这就是备份本身），部分被 git 跟踪（rename 进去），部分被 ignore（如截图）。无论哪种，文件本体都在磁盘上，不属于"只存在 git 里"的危险状态。

**Q：我改坏了内核，怎么快速回到能跑的状态？**
A：`git log --oneline -10` 找最近一次绿色提交（提交信息里带"ktest 全绿"字样的），`git checkout <SHA> -- kernel/` 恢复内核目录即可。

**Q：README 说 4 万字，实际多少？**
A：本文件全文约 4 万字符（中文以字符计），目录 47 个章节小节。事实类数字均来自 2026-09-12 实测：246 个内核源文件、2114 个单测、构建缓存约 35 GB 已清理。

## 附录 H：放到 U 盘 / 本地打开使用指南

很多朋友拿到这个项目后会问：**"我怎么把它装进 U 盘带走？或者在自己电脑上打开看看？"** 这一节按三种使用场景，把步骤一条条写全，照着做就行。

### H.1 先搞清楚：你有三种"打开"方式

| 你想要的效果 | 对应方式 | 需要准备 |
|---|---|---|
| 在自己电脑上模拟运行整个系统（推荐新手） | QEMU 模拟器跑 ISO | 装 QEMU 即可，不动硬盘 |
| 用 U 盘在真机上引导运行 | 把 ISO 写入 U 盘做成启动盘 | 一个 4GB 以上的 U 盘 |
| 只看桌面界面/前端，不跑内核 | 本地打开桌面端 | Node.js（看前端）或直接双击文件（看文档） |

**三种方式都不会改动你的电脑系统和硬盘数据**，放心操作。

---

### H.2 方式一：本地 QEMU 运行（最推荐，零风险）

这是体验 VARIX-500 最安全的方式——在一个"虚拟电脑"里跑，关掉就什么都没了。

**Windows 用户：**

1. 下载 QEMU：去 https://qemu.org/download/#windows 下载安装包，一路下一步（本项目 `qemu/` 目录里其实已经有一份便携版，可以直接用）。
2. 下载或构建 `varix.iso`（见第 10.2 节；如果你拿到的压缩包里已带 ISO 就跳过）。
3. 在 ISO 所在文件夹打开命令行，执行：

```bat
qemu-system-x86_64.exe -cdrom varix.iso -m 512M -M q35 -no-reboot -no-shutdown
```

4. 会弹出一个虚拟机窗口，看到启动画面和串口日志滚动，直到 `boot complete`，就成功了。

**macOS / Linux 用户：**

```bash
# macOS: brew install qemu   /   Linux: sudo apt install qemu-system-x86
qemu-system-x86_64 -cdrom varix.iso -m 512M -M q35 -no-reboot -no-shutdown
```

想看内核说了什么？加参数 `-serial file:serial.log`，运行完打开 `serial.log` 即可。

---

### H.3 方式二：U 盘启动盘（真机引导）

把系统装进 U 盘，插到任何一台电脑上从 U 盘启动，体验"真机"效果。**注意：这只读 U 盘和内存，不写你电脑的硬盘。**

**步骤（最简单的 Ventoy 方案，强烈推荐）：**

1. 准备一个 **4GB 以上**的 U 盘（里面的数据会被清空，先备份！）。
2. 下载 Ventoy：https://www.ventoy.net （开源免费，中文界面）。
3. 运行 Ventoy → 选中你的 U 盘 → 点"安装"。装好后 U 盘变成一个普通 U 盘的样子。
4. 把 `varix.iso` 直接**复制**到 U 盘里（就像拷贝文件一样，不用写入）。
5. 重启电脑，开机时狂按启动菜单键（多数品牌是 F12 / F11 / Esc / F9，苹果电脑不支持此法）。
6. 在启动菜单里选你的 U 盘 → Ventoy 菜单里选 `varix.iso` → 回车。
7. 看到内核启动日志滚动即成功。退出时直接关机，拔掉 U 盘，电脑恢复原样。

**备选：Rufus 方案**（Ventoy 不行时用）：

1. 下载 Rufus：https://rufus.ie （中文）。
2. 设备选 U 盘 → 引导类型选择 `varix.iso` → 点"开始"。
3. 警告会清空 U 盘 → 确认。完成后同上，从 U 盘启动。

**⚠️ 重要提醒：**
- 真机引导前请**保存好所有工作**，虽然内核目前只读不写你的硬盘，但万一触发内核 bug 死机，未保存的东西会丢。
- 部分老电脑/新电脑的 Secure Boot 需要在 BIOS 里临时关闭才能引导第三方系统。
- 如果启动后黑屏或卡住，属正常现象（真机验收项尚未全部完成），换回 QEMU 方式即可。

---

### H.4 方式三：本地直接打开看（不运行内核）

如果你只是想浏览项目、看看桌面界面长什么样：

**看文档/源码：**
- 用记事本、VS Code、Typora 等任何编辑器打开 `README.md`、`CHANGELOG.md`、`docs/` 下的文件即可，都是纯文本 Markdown。
- 推荐 VS Code：打开整个项目文件夹，能获得目录树、语法高亮和全文搜索。

**跑桌面前端界面：**

```bash
# 前提：安装了 Node.js 18+
npm install        # 第一次需要，下载依赖
npm run dev        # 启动开发服务器，浏览器会自动打开界面
```

**构建离线版本：** `npm run build` 后，`dist/` 目录里就是纯静态网页，可以：
- 直接双击 `dist/` 里的 html 打开（部分功能受浏览器限制）；
- 用任意静态服务器：`npx serve dist`，然后在浏览器访问提示的地址。

**整个项目拷进 U 盘带走：**
- 只拷源码和文档（约 30 MB）：排除 `node_modules/`、`src-tauri/target/`、`kernel/target/`、`qemu/`、`build/`、`dist/` 即可，到别的电脑 `npm install` 就能恢复开发环境。
- 拷完整可运行副本（约 1.5 GB）：连 `node_modules/` 和 `qemu/` 一起拷， Windows 之间互拷可直接用；跨系统（Windows→Mac/Linux）建议只拷源码到目标机器重装依赖。
- 注意路径不要太深、避免中文空格混排的怪路径，部分工具链对路径敏感。

### H.5 常见问题

**Q：QEMU 提示找不到命令？**
A：QEMU 没进 PATH。用完整路径调用，或把安装目录加进系统 PATH；也可以直接用项目 `qemu/` 目录里的便携版。

**Q：Ventoy 启动后选 ISO 没反应？**
A：确认 ISO 是用 `scripts/make-iso.sh`（xorriso）打包的版本；pycdlib 打的 ISO 在真机引导会翻车（见第 5 节）。可先用 QEMU 验证 ISO 本身能启动。

**Q：U 盘做完启动盘还能当普通 U 盘用吗？**
A：Ventoy 方案可以——它本来就是"普通 U 盘 + 引导能力"，平时正常存文件，需要时把 ISO 拷进去就能引导。Rufus 方案则整盘被占用，要恢复普通 U 盘需重新格式化。

**Q：从 U 盘启动会弄坏我的 Windows 吗？**
A：不会。U 盘引导只影响本次开机，拔掉 U 盘重启就回到原来的系统。项目内核目前对硬盘只有只读探测行为。

**Q：能在苹果电脑（Mac）上用 U 盘引导吗？**
A：Intel 芯片的 Mac 理论上可以通过外接引导方式尝试，Apple Silicon（M 系列）不行（架构不同，x86_64 内核无法运行）。Mac 用户请用第 H.2 节的 QEMU 方式。

后续所有文档、提交信息、验收清单中出现 VARIX / Varix / varix，指的都是这一个内核，不再使用其他名称。
