**环境阻塞，不是代码缺陷。** 限流重置时间：**2026-10-07 03:17:03 UTC+8**。

## 二·补3、第四轮实机（14:1x~14:2x）—— D11 真根因：填充从未进过 Slate 状态

### 事件背景

14:12 Variable 自行发车（`产线发车.bat`），W01~W05 五连败，全部卡在
「编辑器有字但发送键黑色点不动」。Variable 发截图报障。

### 诊断实验（三方法对照，零发送）

| 填充方法 | DOM 有字 | Slate 注册（按钮变亮） | 结论 |
|---|---|---|---|
| A `execCommand('insertText')`（旧 fill_js） | 是（17 字） | **否** | 只写 DOM，React 不认 |
| B 模拟 `ClipboardEvent('paste')` | 否（0 字） | - | Slate 不接收合成 paste |
| C **CDP `Input.insertText`** | 是（22 字） | 实弹确认 | 模拟真实 IME，trusted 事件 |

关键发现：按钮 HTML 为 `aria-disabled="false"` + class 恒 `cr-send-button`
——**按钮从未被禁用**。「黑色」是 React「编辑器为空」状态的视觉；
点击被空内容逻辑**静默吞掉**。DOM 里有字 = 孤儿文字，纯属假象。

### 归因修正（诚实记录）

第三轮（05:47）把发送失败全归因于 429 限流——**部分误判**。
真相是双重原因叠加：限流 + D11 填充失效。即便当时没有限流，
execCommand 填充的内容也发不出去。14:12 发车时限流已重置，
失败纯粹是 D11。

### 修复（产线化）

1. `send_selftest.py`：`fill_js` 删除 → 新增 `fill_cdp()`（CDP
   `Input.insertText` + `charsReal` 验证）+ `call_cdp_method()`（通用
   CDP 域方法通道）+ `clear_editor_cdp()`（trusted Ctrl+A+Backspace
   清理）；`restore()` 语义修正为「清空」（旧版用 execCommand 填回
   占位语，正是孤儿文字制造机）。
2. `dispatch_tower.py`：`send_text` 证据重写——E1 发送键进停止态
   （最强）/ E2 tag 入流（body 全文）/ E3 charsReal 归零且非 stop；
   废弃「会话数+1」（实测侧栏渲染延迟 30s+ 不可靠）与
   `[data-message-author-role]`（恒 0 个）。死代码 `JS_LAST_USER_MSG` 删除。

### 修复后端到端实弹（14:22）

```
填充 59 字 → fill_cdp OK（charsReal=59，Slate 注册）
点发送 → ok
① tag 入流: True   ★发送键进停止态: True
新会话 ee4447bf 创建，AI 回复:「好」（14s）
视图自动还原 → anchor
```

**整条自动化链路首次真正闭环：填 → 发 → AI 干活 → 有回复。**

fill→clear 闭环自检亦 PASS（填 32 字 / 清空 / charsReal=0，
零残留零发送）。

## 四、被推翻的一条旧结论（重要）

之前记在台账里的结论是：

> 「AI 回合内忙闲判据恒忙、发送必须回合间进行」

**这条是错的。** 实测：在我这个会话正在生成时，点「新建任务」切到空白会话，
那个会话的发送键立刻是「发送」（`cr-send-button`，无 `--stop`），aria-label = 发送。

也就是说：**忙闲是按会话算的，不是全局的。**
塔完全不必等"全局空闲"，只需等**目标会话**空闲即可串行派单。
这条推翻让整个 18 路并行的可行性从"存疑"变成"机制上成立"。
