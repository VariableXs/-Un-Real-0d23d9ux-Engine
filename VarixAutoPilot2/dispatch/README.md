# 18 路并行 AI 产线 · 调度塔架构

> 目标：18 个 AI 并行领取任务包，共用同一套提示词 / MD 规格 / 技能；
> 任何一个完成的一瞬间，调度塔立即补发下一个任务包，直到 50000 条计划全部完成。

## 为什么不用「界面里开 18 个新对话」

- WorkBuddy **没有对外 API** 去程序化新建对话、填入内容、点击发送——这就是之前屏幕自动化一直失败的根本原因：模拟点击对着一个没有自动化接口的界面，控件稍有变化就断。
- 「18 个全新对话」只是手段，真正的需求是「18 路 AI 并行 + 统一上下文 + 完成即续」。**会话内编排**用原生能力完整达成同样效果，且更强（见下）。

## 架构

```
                    ┌─────────────────────────────┐
                    │   调度塔（本对话 · 刃）        │
                    │  - 持有 PLAN（50000 条计划）   │
                    │  - 维护 LEDGER（派工台账）     │
                    │  - 收到完成通知 → 立即补位      │
                    └──────────┬──────────────────┘
           ┌─────────┬────────┼────────┬─────────┐
           ▼         ▼        ▼        ▼         ▼
        Worker1   Worker2  ...     Worker17  Worker18   （18 路并行子代理）
        同一提示词模板 + 同一 PLAN.md + 同一技能清单
        各自只写自己的输出目录（零文件冲突）
```

## 相比 18 个界面对话的优势

| 维度 | 界面 18 对话 + 模拟点击 | 会话内 18 路编排 |
|---|---|---|
| 触发补位 | 靠截图轮询，延迟分钟级 | 完成事件即时通知，秒级补位 |
| 上下文一致 | 每个对话要手动贴 MD/提示词 | 同一模板注入，100% 一致 |
| 冲突防护 | 无 | 调度塔按任务包分区，写路径互斥 |
| 异常处理 | 卡死无人知 | 台账记录，卡住立即换道 |
| 可观测 | 逐个窗口看 | 台账一行一条，全局时间轴 |

## 文件说明

- `PLAN.md` — 计划总表：50000 条按「任务包（Work Package）」切块，每个任务包有唯一 WP 编号、验收判据、输出路径。
- `WORKER_PROMPT.md` — 统一工人提示词模板：18 路共用，只有 `{WP_ID}` 一个变量。
- `LEDGER.md` — 派工台账：谁、领了哪个包、何时开始/结束、结果、缺陷记录。

## 发车需要的三样东西

1. **计划 MD**：50000 条计划的原文（或告诉我从哪份规格生成，我来切块成 PLAN.md）。
2. **工作目录**：工人产物写到哪个仓库/目录（默认当前 workspace 的 `kernel-wp/` 下按 WP 编号分目录）。
3. **技能清单**：每个工人必须加载的技能名称列表（写进 WORKER_PROMPT.md 的技能段）。

## 运行口令

三样就位后，说一句「**发车**」：调度塔立即并行派出 18 路工人领首批任务包；此后每个完成通知到达的瞬间自动补发，直至 LEDGER 显示 PLAN 清空、输出「50000 计划完成」收口报告。

## 红线（继承全局规则）

- 源码只增不减不移动；工人改内容不改文件的存在。
- 推送前必数文件数与行数；发现缺失立即停手归因。
- 🔴 缺陷即时修；🟡🟢 记台账不停手。
- 所有过程产物归 `_attic/`，交付物与过程产物严格分离。

## 自动化运行（2026-10-06 落地，实测通道）

上一节说「不用界面 18 对话」的前提是**没有自动通道**。现在通道已建成：
**CDP 发送（已实测）+ 文件总线（秒级补位）**，18 路界面会话方案成立。

### 三层自动化栈全景

| 层 | 工具 | 能力 | 适用 |
|---|---|---|---|
| 界面级全自动 | `tools/dispatch_tower.py` | 新建 18 会话、领任务、完成瞬间补位、直至 PLAN 清空 | **18 路产线（本文件的主角）** |
| 单会话半自动 | `VarixAutoPilot.exe` | 识别对话/模型/目录，手动触发填入发送 | 人工精确控制单发 |
| 平台原生 | WorkBuddy 内置定时任务 | 定时触发全新任务会话 | 周期性独立任务（不能续指定会话） |

### 文件总线协议（塔与工人的握手，比轮询 UI 快且准）

```
dispatch/workers/Wxx.conv    塔写：该工人的会话 id（data-conversation-id）
dispatch/workers/Wxx.state   工人写 BUSY <WP>（开工第一件事）/ READY <WP>（收工最后一步）
                             塔也写 BUSY（派工瞬间置位）
dispatch/reports/WP-xxx.md   工人收工报告（判据核对/变更清单/缺陷/证据）
dispatch/PLAN.md             唯一任务事实源；塔只改「状态:」一行
dispatch/LEDGER.md           派工/补位/失败/收口，一行一事件
```

工人靠提示词里的「文件总线协议」段执行握手（`render_first_prompt()` 自动注入）。
**READY 文件一落地，塔在下一个轮询周期（默认 20s）内补位**——这就是
「AI 完成的一瞬间继续运行」的实现方式；AI 完成时间不固定没有关系，
总线只认 READY，不猜时间。

### MD / 提示词 / 技能如何「完全被 WorkBuddy 识别」

不走输入框的 @上下文 chip / 斜杠指令注入（UI 机制脆且未实测），而是：
**提示词正文内嵌文件路径与技能名清单**，worker 用 WorkBuddy 原生能力加载——
读文件是它的内置工具，加载技能用它的 Skill 工具。文本指令驱动原生能力，
100% 识别，WorkBuddy 改版也不受影响。发车时通过
`--spec <规格MD路径> --skills 技能A,技能B --out kernel-wp` 注入，18 路内容完全一致。

### 发车步骤

1. `dispatch/PLAN.md` 切块就位（50000 条 → WP 任务包，判据可机械验证）；
2. WorkBuddy 带调试端口运行（`开端口.bat`；`curl http://127.0.0.1:9222/json/version` 验证）；
3. 双击 **`产线发车.bat`**（先只读体检，PASS 才发车），或命令行：
   ```
   python tools/dispatch_tower.py --dry-run            # 先演练（零 UI 动作）
   python tools/dispatch_tower.py --start 18 --watch   # 正式：建 18 会话+派首批+守护补位
   python tools/dispatch_tower.py --watch              # 中断后续跑（工人不受影响）
   ```
4. 想指定工人模型：发车前在 WorkBuddy 设置里改默认模型
   （塔 v1 不自动点模型菜单——cr-model-selector 菜单结构未实测，不赌）。

### 安全设计（全部来自实测教训）

- 忙时一个字不写：三判据（发送键态/停止按钮/生成动画）任一说忙就不动手；
- 发送自带双重证据（消息入流 或 编辑器清空），失败记 LEDGER 并重试；
- Ctrl+C 优雅停：正在跑的工人不受影响，重新 `--watch` 即恢复；
- BUSY 超 `--stale-min`（默认 120min）只在塔日志提示，不自动打断——换道由人裁决；
- 全局串行发送：同一时刻塔只对当前显示的会话动手，天然无并发写冲突。

### 已知限制（如实）

- 「新建任务」点击与「切换会话」点击的 DOM 动作首次实操在发车时进行，
  每步带证据回写 LEDGER；若 WorkBuddy 改版导致选择器失效，塔会显性报错而非误发；
- CDP 只能看到当前打开会话的消息流，因此塔的发送是串行的（18 路并行的是**工人的工作**，
  不是塔的发送动作——发送本身秒级，不构成瓶颈）；
- 18 个常开会话的上下文维护是 WorkBuddy 侧成本，与塔无关。
