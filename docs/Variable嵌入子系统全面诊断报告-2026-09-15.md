## 1. 架构现状（审计结论）

### 1.1 四个层级

```
probe_hwnd()  ← 唯一裁判，纯启发式
  ├─ UWP (AppX 包全名)                → L3
  ├─ DWM CLOAKED                      → L3
  ├─ 反作弊/独占全屏类名              → L4（让位）
  ├─ compted_reason(): WS_EX_NOREDIRECTIONBITMAP
  │  或 类名含 chrome_widgetwin / cefbrowserwindow /
  │     vgui_platform_window / sdl_app / valve001  → L3
  ├─ 有标题栏 + 非客户区 ≥8px         → L1（SetParent 真嵌入）
  ├─ 有标题栏 + 非客户区 <8px         → L2（容器包裹）
  └─ 其它                             → L2
```

- L1：`restyle_and_reparent()` — 剥掉标题栏样式 + `SetParent` 到桌面窗 + `SetWindowPos(240,140,900,600)`
- L2：`container.rs` 建 `VariableContainerHost` 宿主窗包裹
- L3：`capture.rs` 用 WGC(D3D11) 采帧 → 事件推前端 Canvas；真实窗口 `hide_offscreen()` 到 (-32000,-32000)
- L4：不接入，桌面智能让位

## 2. 根因逐条剖析

### R-A：一条路由打天下，判错无退路

**证据（本机日志，2026-09-15 22:29–22:40）：**

```
[watchdog] 发现逃逸窗口 hwnd=268010 image=windowsterminal.exe → 收编
[embed] attach windowsterminal.exe: → 层级 L3（appx package window）
[capture] L3 画面捕获已启动
```

`windowsterminal.exe` 明明是普通 Win32 应用，却被判成 **`appx package window` → L3**。原因在 `compat_probe.rs:156-165`：

```rust
let is_uwp = OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION, false, pid)
    .map(|proc| { GetPackageFullName(proc, ...).is_ok() })
    .unwrap_or(false);
```

`GetPackageFullName` 返回非零即判 UWP，**没有检查返回的错误码语义**。Terminal 这类通过 Store 分发的应用，`GetPackageFullName` 在特定权限/进程状态下会返回非 `APPMODEL_ERROR_NO_PACKAGE` 的错误 —— 被判成 UWP 后强制 L3。

**同类误判：**
- `composited_reason()` 只看类名子串。`chrome_widgetwin` 命中一切 Electron/CEF（WorkBuddy、Tabbit、Soda Music…）→ 一律 L3。
- `is_uwp` 分支在决策树**最前面**（第 171 行），优先级高于一切。

**为什么"没退路"：**

`attach_by_tier` 里每个分支命中即 `return`，**没有任何"先试后验"**。唯一自愈逻辑是 CEF 家族硬编码白名单（第 1173–1180 行）：

```rust
base == "steam.exe" || base == "steamwebhelper.exe" || base == "wallpaperui.exe"
```

—— 只有这 3 个 exe 享受"L3 失败自动降级 L1"的特权。**其它任何应用被判错 L3，就是永久黑屏**。

**实测黑屏链条**（`capture.rs:56-76` + 第 1236–1241 行）：

1. 判 L3 → `start_capture()` 启动 WGC
2. **立刻** `hide_offscreen(hwnd)` 把窗口移到 (-32000,-32000)
3. Chromium occlusion 检测发现窗口完全不可见 → **停止渲染**
4. WGC 只能抓到最后一帧或空帧 → 前端画布黑屏
5. 用户看到「黑屏/不加载」

`capture.rs:34` 的注释已经把这条结论写死了（"藏窗与 Chromium 根本冲突"），但**修复只覆盖了 3 个硬编码 exe**。

这就是症状 **1（黑屏/不加载）**、**4（跑 Windows 里）**、**9（兼容性差）** 的主因。

### R-B：L3 捕获链路的三重性能灾难

**灾难 1 — 分辨率不匹配（糊）**

`capture.rs:169-178` 采集池用 `item.Size()`（**物理像素**，如 1920×1080）。
`L3CaptureView.tsx:62-66` 把帧画到 `cv.width/cv.height`（**CSS 像素 × DPR**）：

```tsx
ctx.drawImage(buf, 0, 0, cv.width, cv.height);
```

**没有 `imageSmoothingEnabled` 控制，也没有 1:1 像素对齐**。125% DPI 下再叠一层双线性缩放 → 叠加模糊。这就是症状 **3（糊）**。

**灾难 2 — 单帧 8.3MB 走 base64 过 IPC**

`capture.rs:273-282`：

```rust
"bgra": base64::engine::general_purpose::STANDARD.encode(&buf),
```

1080p BGRA = 1920×1080×4 = **8.3MB**，base64 后膨胀到 **11MB 字符串**，每帧一次。

前端 `L3CaptureView.tsx:49-60` 再逐字节逆变换：

```tsx
const bin = atob(f.bgra);                      // 11MB 字符串解码
for (let i = 0; i < bin.length; i++) bytes[i] = bin.charCodeAt(i);  // 830万次循环
const img = new ImageData(w, h);
for (let i = 0; i < bytes.length; i += 4) {    // 再 830万次/4 循环做 BGRA→RGBA
  out[i] = bytes[i+2]; ...
}
bctx.putImageData(img, 0, 0);                  // 再一次全量拷贝
```

**每帧 = 1 次 base64 编码 + 1 次 atob + 200 万次 JS 循环 + 3 次全量内存拷贝。** 30fps 下这是 **每秒 250MB 的字符串吞吐**，全部走 Tauri 事件 IPC（JSON 序列化）。

**灾难 3 — `drawImage` 中间缓冲**

```tsx
const buf = document.createElement("canvas");  // 每次尺寸变化新建
bctx.putImageData(img, 0, 0);
ctx.drawImage(buf, 0, 0, cv.width, cv.height); // 再拷一次到可见画布
```

两次全量绘制，无 `createImageBitmap` / `OffscreenCanvas` / WebGL 加速。

**这就是症状 3（延迟很高）、5（界面分离）的机制来源。** 输入也跟着遭殃：`EmbedBridge` 每帧同步边界 + `forward_input` 走 IPC，视觉-输入时序天然错位 → 手感"分离"。

### R-C：隔离模型的结构性矛盾

**矛盾 1 — `SetParent` 跨进程 + `always_on_top` 打架**

`compat.rs:157-176` `apply_compat_mode()`：

```rust
let _ = w.set_always_on_top(true);   // 桌面窗永远置顶
tame_wallpaper_engine_windows();      // 把 WE 悬浮层压回普通层
```

桌面窗 `always_on_top` 意味着嵌入的 **原生子窗口不可能被任何其它窗口正确遮挡**。一旦有别的窗口（任务栏、输入法、通知）需要覆盖，就会出现：

- 子窗口"穿透"显示在最上层 → 视觉错乱
- 或 WebView2 合成层与原生子窗 z-order 冲突 → 症状 **5（界面分离）**

`capture.rs:1454-1458` 的注释就是证据：

> R4-B7（首轮 B-4）：收编子窗隐藏/最小化后 WebView2 合成层可能失效白屏

**矛盾 2 — 看门狗无差别收编制造"界面分离"**

本机日志（`applog-20711.log`）实测：

```
发现逃逸窗口总数: 150
其中：
  sodamusic.exe          36 次
  workbuddy.exe          26 次
  msedge.exe             19 次
  adobe desktop service  17 次
  lenovopcmanager.exe    14 次
  steamwebhelper.exe     11 次
  windowsterminal.exe     7 次
  snippingtool.exe        7 次      ← 用户明确要求内置忽略
  tabbit browser.exe      5 次
  weixin.exe              4 次
  wallpaperui.exe         1 次
```

`shell_watch.rs:215-285` 的扫描器**每 500ms 全量枚举**，用 `is_adoptable_main_window`（有标题栏 + 非 TOOLWINDOW + ≥160×100）当唯一闸门。

问题：
- `sodamusic.exe`、`adobe desktop service.exe`、`lenovopcmanager.exe` 这些**后台辅助进程的隐藏窗**也被判为"可收编主窗"
- 它们没有真正的 UI，收编后就是一个**空占位窗** → 用户看到一堆莫名的 Virtual 窗口 = 症状 **5（界面分离）**

**`WHITELIST` 现状**（`shell_watch.rs`，共 15 项）覆盖了 explorer/taskmgr/ctfmon/textinputhost/searchhost/shellexperiencehost/startmenuexperiencehost/runtimebroker/sihost/svchost/dllhost/conhost/consent/fontdrvhost/applicationframehost。

`snippingtool.exe` **已经在 `BUILTIN_IGNORED` 里**（`shell_watch.rs:74`），并在 `shell_watch.rs:87-89` 并入 `s.ignored`。已核验时序：这 7 次派发的时间戳是 `1789475982`，而当前 `variable.exe` 构建于 `1789482xxx`（22:28）—— **旧构建的行为，当前代码已修复**。此项无需再动。

`compat.rs:41-53` 的 `WE_PROCS` 已包含 `wallpaperui.exe`；`family_images`（`embed.rs:415-432`）也覆盖了它。**名字层面都对了，问题在时序与失败退路上**（见 R-A 第 3 条）。

**循环收编（steamwebhelper 11 次 / windowsterminal 12 次）** 说明"收编 → 窗口失效 → 重新逃逸 → 再收编"的抖动，每次抖动都在前端开一个新 Virtual 窗口。

**矛盾 3 — 隔离 vs 壁纸引擎（症状 7、8）**

Wallpaper Engine 2.8+ 架构：

```
wallpaper64.exe (主进程，渲染壁纸到 WorkerW 子层)
  └─ wallpaperui.exe (CEF 独立进程，UI 主窗)
steam.exe / steamwebhelper.exe (Steam 商店与创意工坊)
```

**实测关键证据**（`applog-20711.log:317`）：

```
1789475883.295 [watchdog] 发现逃逸窗口 hwnd=3083612 image=wallpaperui.exe title="Wallpaper UI" → 收编（policy=auto）
```

**这一行之后，日志里再没有任何 `embed_adopt wallpaperui.exe` 或 `attach wallpaperui.exe`。**

看门狗发现了它、派发了事件，但**收编流程静默中断**。原因链：

1. `watch://escape` 事件发到前端
2. 前端 `VirtualWindowManager.tsx:444` 开占位窗，`embedId = openVwmTpNew("tp:wallpaperui")`
3. 调 `ipc.embedAdopt(...)`
4. 后端 `embed_adopt` → `attach_by_tier` → 重探层级

`wallpaperui.exe` 是 CEF，`composited_reason` 命中 → L3 → 但它在 **`is_cef_l1_family` 白名单里**（第 1179 行），所以应该走 L1 真实嵌入。

**那为什么没走？** 看第 1173–1180 行的实现：

```rust
let is_cef_l1_family = {
    let img = win::window_pid(hwnd_from_isize(hwnd))
        .and_then(|p| win::process_image(p))
        .map(|s| s.to_lowercase())
        .unwrap_or_default();
    let base = img.rsplit(['\\','/']).next().unwrap_or("");
    base == "steam.exe" || base == "steamwebhelper.exe" || base == "wallpaperui.exe"
};
```

它**重新从 hwnd 反查进程映像名**。若此时 `window_pid()` 返回 `None`（权限/时序），`img` = `""` → `base` = `""` → 白名单不命中 → 掉进普通 L3 分支 → `hide_offscreen` → **CEF 停渲染 → 黑帧**，或者被 `needs_reveal` 逻辑还原后 `restyle_and_reparent` 失败 → `Attach::Skip`。

`Attach::Skip` 的结果是「保持独立窗口运行」= **症状 7（wallpaperui 无法在 Variable 独立运行 → 跑到 Windows 里）**。

**症状 8（无法在 Variable 内实时换壁纸）** 的根因是架构性的：

- Wallpaper Engine 的换壁纸动作发生在 **`wallpaperui.exe` 进程**
- 壁纸渲染发生在 **`wallpaper64.exe` 的 WorkerW 子窗口**
- WorkerW 是 **explorer.exe（Windows 桌面 shell）的宿主窗口**

Variable 的桌面是一个 **Tauri WebView 窗**，不是 Windows 的 WorkerW。所以：

- WE 把壁纸画到 Windows 的 WorkerW → **壁纸出现在 Windows 桌面，不在 Variable 里**（症状 8 的"要么就换到 windows 系统上了"）
- 你在 Variable 里操作 wallpaperui 的 UI，实际改的是 Windows 桌面壁纸
- Variable 自己的壁纸系统（`wallpaper.rs`）与 WE 是**两套独立机制**，没有打通

**这是"隔离"与"复用 Windows 生态"的根本矛盾**：要么 Variable 接管 WorkerW（放弃隔离），要么做一层壁纸镜像（工程量大），要么接受 WE 不能实时换 Variable 壁纸。

### R-D：应用自身反复重启，且存在**静默死亡**（最优先）

**铁证**（`variable.log`）：

```
window DESTROYED        144 次
window close REQUESTED   69 次   ← 用户/系统主动关窗
app bootstrap dirs ok   108 次
boot complete in 6~24ms
```

关键结构性发现 —— **`DESTROYED` 有 144 次但 `close REQUESTED` 只有 69 次**。在 `lib.rs:145-151` 里这两个事件是分开记录的：

```rust
tauri::WindowEvent::CloseRequested { .. } => log_line(&st, "window close REQUESTED"),
tauri::WindowEvent::Destroyed => { log_line(&st, "window DESTROYED"); ... }
```

正常关窗应成对出现（`REQUESTED` → `DESTROYED`，日志里大量成对样本可证）。**但尾部有 7 处 `DESTROYED` 前面完全没有 `REQUESTED`**：

```
1789476307 window DESTROYED          ← 无 REQUESTED
1789479918 window DESTROYED          ← 无 REQUESTED
1789480062 window DESTROYED          ← 无 REQUESTED
1789480166 window DESTROYED          ← 无 REQUESTED
1789482705 window DESTROYED          ← 无 REQUESTED
1789483161 window DESTROYED          ← 无 REQUESTED
1789483255 window close REQUESTED / window DESTROYED
```

`lib.rs:141-142` 的注释写明这两个事件的记录目的就是：

> Exit forensics: distinguish "someone requested close" from "the window died on its own" (webview crash / system).

**所以：这 7 次是宿主窗口自己在死**（webview 崩溃或系统级销毁），不是用户关的。

每一次 `window DESTROYED` 都会：

1. 销毁桌面窗 → 所有 `SetParent` 的子窗口**随之被销毁**（memory 已记录：R7 终局根因 —— Steam 单例主窗被 reparent 后随宿主窗销毁）
2. 所有 L3 采集线程失去目标窗，`frame_loop` 空转
3. 前端所有 Virtual 窗口状态丢失
4. 重启后重新收编 → 又是 150 次派发循环

**这是"软件打不开 / 黑屏 / 不加载"的最终放大器。** 即使嵌入逻辑 100% 正确，宿主每隔 1.5–4 分钟自杀一次，用户体验必然是"打开要么黑屏，要么不加载"。

**注意**：`boot complete in 7ms` 说明重启本身很快，所以用户感知到的是"闪一下窗口没了 / 一片黑"，而不是明显的崩溃对话框。

可能诱因（需按此顺序排查）：
1. **WebView2 崩溃** —— `lib.rs:149-150` 的 `X-1 扩展崩溃隔离` 注释暗示 webview 死亡是已知场景；需查 WebView2 的 `ProcessFailed` 事件
2. `embed_close_all` 30s 超时路径在窗口切换时误触发
3. 看门狗收编到自家家族窗口 —— `is_variable_family_image`（`shell_watch.rs:298`）只匹配 `variable*` 前缀，若自家 WebView2 子进程（`msedgewebview2.exe`）的映像名不命中该前缀，就会**收编自家窗 = 自毁**（`shell_watch.rs:209-211` 的注释已明确警告这一点）
4. `compat_apply` 的 `set_always_on_top` 与 Tauri 窗口生命周期冲突
5. `restyle_and_reparent` 里 `SetParent` 失败后的 `SetWindowLongPtrW` 已改样式但未改回 → 窗口状态不一致

## 4. 改造方案（按优先级）

### P0 — 修 R-D 崩溃循环（必做，否则一切白搭）

1. 在 `variable.log` 里给 `window DESTROYED` 加上 **调用栈/Reason**（Tauri `on_window_event` 的 `Destroyed` 分支打印 `CloseRequested` vs 系统销毁）
2. 复查 `embed_close_all` 的 30s 超时是否在窗口切换时被误触发
3. 复查 `is_variable_family_image`（`shell_watch.rs:298`）是否覆盖 WebView2 子进程映像名
4. 给所有 `embed_*` 命令加 `catch_unwind`，避免单点 panic 连带进程退出
5. **验收标准**：连续运行 10 分钟，`window DESTROYED` 计数 = 0

### P1 — 让分级有退路（修 R-A）

1. **`is_uwp` 收紧**：`GetPackageFullName` 必须返回 `ERROR_INSUFFICIENT_BUFFER(122)` 才判 UWP，其它错误码（尤其 `APPMODEL_ERROR_NO_PACKAGE=15700`）一律不算
2. **引入"试嵌-验证-降级"闭环**：L3 启动采集后，**等第一帧 + 校验非全黑**（抽样中心 64×64 像素的方差），黑帧则自动降级 L1；L1 `restyle_and_reparent` 后校验窗口可见性，失败则降 L2
3. **删掉 `is_cef_l1_family` 的映像名重查**，改为在 `attach_by_tier` 入参里**透传已经拿到的 exe 名**（`embed_launch` 本来就有 `target` 参数），消除时序依赖
4. **把 CEF 家族策略泛化**：不再硬编码 3 个 exe，改为"凡 `composited_reason` 命中 → 优先 L1 真嵌入，失败才 L3"
5. **`WHITELIST` 补齐**：`snippingtool.exe`、`shellexperiencehost.exe`、`textinputhost.exe`、`startmenuexperiencehost.exe`、`searchhost.exe` 等系统瞬时覆盖层

### P2 — 重写 L3 传输链路（修 R-B）

现状：`BGRA → base64 → JSON IPC → atob → 200万次循环 → putImageData → drawImage`

目标：**零拷贝 / GPU 直通**

1. **优先方案**：改用 `shared texture` 或 **`WebGPU/WebGL` 直上传**——D3D11 采集纹理直接共享给 WebView2（`IDXGIResource1::CreateSharedHandle` + WebView2 的 `D3D11` 互操作），前端用 WebGL `texImage2D` 上传，**完全绕开 base64 与 CPU 拷贝**
2. **过渡方案（低风险）**：把 base64 换成 **二进制 IPC**（Tauri v2 支持 `Uint8Array` payload）+ 前端用 `createImageBitmap(blob)` 一次性成图
3. **分辨率对齐**：采集池尺寸 = 显示画布物理尺寸，前端 `drawImage` 严格 1:1（`imageSmoothingEnabled = false` 或直接等尺寸）
4. **帧率策略**：当前"静止 5fps / 活动 30fps"用**全帧哈希**判定；改为**分块哈希**（如 8×8 块）实现局部更新
5. **输入同步**：把 `EmbedBridge` 的边界同步从"每帧"改为"仅变化时"；输入走**独立高优先级通道**，不等视觉帧

**收益**：延迟从 ~100ms 级降到 ~16ms 级，CPU 占用降一个数量级。

### P3 — 重构隔离模型（修 R-C）—— "要不要重做"的真正答案

> 用户问："隔离性太难受了，使得我有点想重做这个了"

**先回答"该不该重做"**：**不该推倒重做**。你的 L1（`SetParent`）方向是**对的**——这是 Windows 上唯一能做到真·原生嵌入、零延迟、零 CPU 开销的方案。真正的错误是：

- 把 L3（采集合成）当成了**主路径**，而它只是个**降级兜底**
- 隔离用 `always_on_top` 实现，与原生子窗口语义冲突

**建议的架构调整（不是重做，是收敛）：**

| 决策 | 建议 |
|---|---|
| L1 定位 | **唯一主路径**。所有能 `SetParent` 的一律 L1 |
| L3 定位 | **纯兜底**，且必须有"黑帧检测 → 自动回 L1"闭环 |
| L2 容器 | 评估收益：宿主窗与 `SetParent` 直嵌本质相同，多一层反而多一份 z-order 风险，考虑合并进 L1 |
| 隔离实现 | 放弃"桌面窗 always_on_top"；改为**显式 z-order 管理**（嵌入窗随 Virtual 窗口一起 raise/lower），让 Windows 原生语义为你工作 |
| WorkerW/WE | 承认 WE 的壁纸渲染天然属于 Windows shell。**要么**提供"接管 WorkerW"开关（放弃隔离换 WE 兼容），**要么**做 WE→Variable 壁纸镜像桥 |
| 看门狗 | 从"无差别收编"改为**用户显式授权 + 智能推荐**：检测到逃逸窗口时只在**侧边栏提示**，不自动开窗 |

**关键洞察**：症状 5/6 的根源是"你想让 Windows 窗口以为自己在一个假桌面里，同时又想让 Windows 的 z-order/通知/输入法照常工作"——这两件事有物理冲突。**放弃 `always_on_top`，改成真正的窗口层级管理，隔离感反而会更强**（因为不再有穿透与错位）。

## 6. 附录：本机日志关键统计

```
applog-20711.log（2026-09-15 22:29–22:40，约 11 分钟）
  逃逸窗口派发总数          150
  实际调用 embed_adopt       57
  收编失败（未接入）          3   ← 全部为 windowsterminal.exe 0x80070057

  L3 采集启动成功            ~10 次
  L3 采集启动失败            3 次（0x80070057 参数错误）

variable.log
  window DESTROYED          144
  window close REQUESTED     69     ← 差值 75 次；其中尾部 7 处确认为无 REQUESTED 的静默死亡
  app bootstrap dirs ok     108
  boot complete              6~24ms
  观察到的重启间隔            3s / 91s / 141s / 200s / 222s / 234s / 3113s
```

`0x80070057 (E_INVALIDARG)` 出现在 `Direct3D11CaptureFramePool::CreateFreeThreaded`。已核验 `capture.rs:169-178`：

```rust
let size = windows::Graphics::SizeInt32 {
    Width: item.Size().map_err(|e| e.to_string())?.Width,
    Height: item.Size().map_err(|e| e.to_string())?.Height,
};
let pool = Direct3D11CaptureFramePool::CreateFreeThreaded(..., 2, size)...
```

**代码只处理 `item.Size()` 返回 `Err` 的情况，完全没有校验 `Width`/`Height` 为 0 的情况。** 当窗口刚创建/正在销毁时 `item.Size()` 返回 `Ok(0×0)`，直接传进 `CreateFreeThreaded` 必然 `E_INVALIDARG`。

**修复**：在调用前加

```rust
if size.Width <= 0 || size.Height <= 0 {
    return Err("capture item size is 0x0 (window not ready)".into());
}
```

并在 `attach_by_tier` 的 L3 分支对失败做**短退避重试（如 3 次 ×300ms）**，仍失败才 `Attach::Skip` —— 这能直接消灭日志里那 3 次 `windowsterminal.exe` 收编失败。
