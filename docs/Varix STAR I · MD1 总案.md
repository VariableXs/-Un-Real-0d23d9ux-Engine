## 卷首语：STAR 的含义

STAR，是这一代 Varix 工程的代号。它取四个词的首字母，也是本总案的四根支柱：

- **S — Sovereign（自主）**：内核自研、引导自持、生态自主兼容。VARIX 不做任何现有系统的套壳，不依赖任何他方内核的恩赐。一台机器插上 U 盘，从电源键到屏幕上的每一个像素，主权归 VARIX。
- **T — Three-Legged（三足）**：原生应用、兼容层、Windows 域兜底，三条腿站立。任何一条腿的进展都不以牺牲另外两条为代价，任何一条腿的失败都不会令系统倒塌。
- **A — Assimilation（借力）**：站在三十年开源世界的肩膀上——Wine 的兼容实现、Servo 的渲染引擎、整个 Linux 发行版仓库的软件池。VARIX 自有代码刻意收敛在六十万行量级，撬动的是亿行级生态。
- **R — Relay（接力）**：双域同刻只有一个在跑，切换即接力。这是被硬件物理规律与工程可行性共同选定的形态，是 VARIX 与 Variable 两域关系的最终答案。

STAR I 是这条路线的第一代完整规划：从今天的 36 万行走到 60 万行基建完熟、再到 150 万应用生态、乃至更远的 300 万与 500 万——每一档都是可发布、可验收、可日常使用的产品状态，而不是憋出来的大招。

本总案正文十四章，依次回答：这是什么（第 1-2 章）、长什么样（第 3-5 章）、靠什么活（第 6 章）、怎么走过去（第 7 章）、长到多大（第 8 章）、用起来什么标准（第 9 章）、底线在哪里（第 10 章）、跑在什么机器上（第 11 章）、Variable 去哪里（第 12 章）、会死在哪（第 13 章）、以及一路走来每个决策为什么这么定（第 14 章）。

## 第 1 章 立项定位：Varix STAR I 是什么

### 1.1 一句话定义

Varix STAR I 是 VARIX-500 双域系统的第一代完整工程规划：**以自研 Rust 内核 VARIX 为主权核心，以 U 盘为整机载体，以接力式双域为使用形态，以"原生 + 兼容 + 兜底"三腿战略覆盖日常全部软件场景，以生态借力控制自有代码规模的一体化个人计算机系统。**

拆开读，这句话里有六个关键定语，每一个都是深思熟虑后的排除法产物：

**"自研 Rust 内核"**——不是 Linux 发行版、不是 BSD 改、不是 Android 改。VARIX 内核从引导到帧缓冲到进程调度全部自持，选 Rust 是因为内存安全、与 AI 协作的编译器护栏（详见 8.3 节）。这个定语的代价是最大的，回报也是最大的：主权完整、行为可预测、法律干净。

**"U 盘为整机载体"**——VARIX-500 的形态是"口袋里的整机"：插上任何一台 x86-64 电脑，从 U 盘引导，不碰对方硬盘，到哪台机器都是同一台"我的机器"。U 盘不是安装介质，是**计算机本体**。这个形态决定了分区布局、驱动策略（需适配任意宿主机硬件）、以及"内置盘只读不写"的礼貌原则。

**"接力式双域"**——VARIX 内核域与 Windows 域（Variable 所在）同刻只活一个，切换即重启交接。这是被三重约束锁定的选择：UEFI 规范（内核调 ExitBootServices 后无法再跳回 Windows 引导管理器，唯一复位重走）、单机单内核的物理事实、以及虚拟化路线（Hypervisor）被评估为年级工程且损坏双域性能后否决（详见第 3.5 节的方案排除记录）。

**"三腿战略"**——软件覆盖不押注单一路线。原生应用腿（内核自绘，最快最稳）、兼容层腿（Wine/Servo/翻译柜台，存量软件通吃）、Windows 域兜底腿（结构性跑不了的接力去跑）。三条腿互为备份、各有明确边界（详见第 5 章）。

**"生态借力"**——VARIX 自有代码刻意收敛在 60 万行量级（终态），通过自有实现的"翻译插座"（Linux syscall 转译层、Wine 支架、Servo 渲染）接入亿行级开源生态。不重造发动机，只造插座和支架（详见第 6 章）。

**"一体化"**——上述所有元素不是拼盘，是一体：内核为兼容层提供插座，兼容层为桌面供给软件，桌面为 Variable 提供归宿，Variable 为用户产出价值。缺一角，其余角的意义都要打折。

### 1.2 项目命名谱系

- **UNREAL-X**：整个工程的总代号（Un/Real 双关——虚拟与现实双域）。
- **VARIX**：自研内核的名字，也是内核域的名称。VA-RI-X 无实义，追求的是发音的力量感与唯一性。
- **Variable**：桌面域应用的名字，源自用户（VariableXs）之名。它先是 Windows 上的 Tauri 应用，终态将成为 VARIX 生态的首席应用（详见第 12 章归宿规划）。
- **VARIX-500**：双域整机系统的产品名（U 盘整机形态）。
- **STAR I**：第一代完整工程规划的代号（Sovereign / Three-legged / Assimilation / Relay）。后续大版本演进预留 STAR I start 等命名空间。

### 1.3 本工程要解决的根本问题

STAR I 立项要回答的根本问题只有一个：**一个人能否拥有一台"完全属于自己"的计算机？**

这句话里的"完全属于"包含五层：

1. **主权层**：从电源键按下那一刻，运行的内核是自己的代码。不存在"第三方引导管理器替你做决定"、"厂商远程管理你的设备"这类默认设定。
2. **软件层**：日常所需的软件都能跑——无论它是跨平台开源件、Windows 独占件还是 Web 形态件，总有一条路在 VARIX 的世界里打开它。
3. **数据层**：数据存在自己的 U 盘上，文件系统是自己可审计的，保险库是自己可掌控的。拔下 U 盘，数据随人走。
4. **体验层**：界面、交互、动画、节奏全部出自一套自己的设计系统，不向任何现有 OS 的审美低头，也不允许生态内的每个软件各自为政。
5. **演进层**：整个系统的每一步演进都可在实机上验收，每一行代码都有测试兜底，每一个决策都记录在案。系统是"长"出来的，不是"规划完再实现"的幻影。

传统路线在这五层的每一条上都留有缺口：Windows 不给你主权（1），Linux 发行版软件覆盖在本土场景有缺口（2），云方案数据不在自己手上（3），各家 UI 各自为政（4），碎片化发行版无法一体化演进（5）。STAR I 的立项就是要把这五个缺口一次补齐。

### 1.4 不做什么（负空间定义）

一个工程的成熟度，首先体现在它明确不做什么。STAR I 的负空间清单：

- **不做虚拟机宿主**：Hypervisor 路线（内核当 VMM、Windows 装进 VM）被正式否决。理由：年级工程量、GPU 直通在目标硬件（NVIDIA 消费卡）上不可行、双域性能双双受损、维护复杂度指数上升。本决策永久生效，除非 UEFI 规范或硬件格局发生结构性变化。
- **不自研 Wine/Servo/Mesa**：这三件是"借力"对象，VARIX 只做支架与适配，绝不重写它们的实现。任何"我们也自己写一个 Wine"的提案都是对 STAR I 资源模型的违背。
- **不做通用发行版**：VARIX 不追求"装到任何机器的硬盘上"的通用性。它的宿命载体是 U 盘整机（未来的移动介质演进除外）。这砍掉了大量硬件兼容性工程的复杂度。
- **不做云依赖**：系统的核心功能（引导、桌面、文件、编辑）必须离线完整可用。云是增强（云端构建、云 Windows 可选件），不是依赖。
- **不做移动端**：STAR I 周期内不考虑 ARM 手机/平板形态。x86-64 U 盘整机是唯一形态焦点。
- **不碰内置盘引导**：实机事故教训已入宪（引导设施红线，见 10.2 节）——VARIX 的一切施工只发生在 U 盘侧，内置盘的引导链视为不可侵犯的他人物业。

### 1.5 成功判据（STAR I 何时算完成）

STAR I 的完成判据不是代码量，不是版本号，而是六条可实机验收的状态：

1. **接力闭环**：开机 → VARIX Legend → 点「启动 Variable」→ 自动直达 Windows 桌面 → Variable 全屏弹出；点「返回 VARIX」→ 回到 Legend。全程无菜单、无人工干预，双向各 ≤ 30 秒。
2. **启动稳定**：连续 20 次冷启动，0 次蓝屏、0 次循环、0 次需要人工干预。
3. **桌面自持**：VARIX 桌面（合成器 + 任务栏 + 文件管理 + 终端 + 编辑器）在日常工作中可独立服役一天而不需要去 Windows 域。
4. **兼容首役**：清单制兼容层吃下第一批真实软件（目标：Neovim、git、一个 GUI 小工具），形成"软件分拣 → 施工 → 验收 → 入库"的可复制流水线。
5. **生态通水**：syscall 插座 + 显示适配 + 网络栈三者打通，VSCode Linux 版或同级 Electron 应用在 VARIX 桌面原生窗口中运行。
6. **Variable 归宿**：Variable 的界面在 VARIX 内（浏览器渲染或原生重写任一路径）可用，后端逻辑至少部分改接内核服务。

六条全绿，STAR I 摘星，STAR I start 立项窗口开启。

## 第 2 章 愿景与终态图景

### 2.1 一天的生活（终态体验白描）

为了让"终态"从概念变成可触摸的画面，先白描一天——**这不是愿景文学，这是验收基准**：终态的每一处细节都应能与本章对照验收。

**07:30 插上 U 盘，按下电源键。** 屏幕亮起，Limine 引导器静默工作（5 秒超时，默认项 VARIX），深空色背板上浮出 VARIX 字标与 Legend 主界面。没有 Windows 的蓝天白云，没有 OEM 厂商的 BIOS 广告页——从第一帧起，这台机器就是 VARIX 的。

**07:31 打开工作台。** Legend 界面上，代码工作台的磁贴一击即进：三联布局——左侧文件树（VARIX 文件管理器），中央编辑器（语法高亮、多标签），底部终端（ushell 全速待命）。昨天的项目原样摊开：文件在 U 盘的 VARIX_SYS 分区，git 仓库状态在终端标题栏。

**07:40 写码与构建。** 编辑、保存、git commit、git push——push 直达 GitHub（VARIX 网络栈已通）。CI 在云端构建，构建产物稍后拉回。需要跑构建产物时：静态链接 CLI 直接双击（PE 装载器 + 兼容层接管），或进 Linux 兼容柜台跑产物。

**09:00 需要 AI 助手。** 点开终端里的 AI CLI（它是个 Linux 版 Node/Rust 程序，走翻译柜台跑，速度与原生无异），对话、生成代码、自动改文件。它操作的文件就在 VARIX 文件系统里，与编辑器看到的是同一份。

**11:00 要用 VSCode 的某个专属插件。** VSCode 的 Linux 版就在 VARIX 桌面——点图标，Electron 走翻译柜台，窗口两秒弹出，界面 100% 是 VSCode，跑在 VARIX 的窗口面上。或者：Servo 浏览器开 vscode.dev，连云端 Codespaces，计算在云、画面在 VARIX。两条路都通，选哪条看心情。

**14:00 微信消息来了。** 微信没有 Linux 桌面版（或版本太旧）——Wine 兼容层吃下它，或点「Windows 域」磁贴：交接画面走起（"正在进入 VARIABLE"进度条，2.4 秒），机器重启，自动落进 Windows，微信已在托盘。用完点返回，30 秒内回到 VARIX 桌面，刚才的编辑器原样摊开（会话状态由 VARIX 桌面保存恢复）。

**22:00 收工。** 数据全部在 U 盘上：代码在 VARIX_SYS，保险库里是加密的私人文件，Variable 的笔记在它的数据库里。拔下 U 盘揣进口袋——这台"计算机"跟着人走，宿主机硬盘从头到尾没被碰过。

### 2.3 终态的五个"无"

- **无第二内核**：内存里任何时刻只有一个内核在跑（VARIX 或 Windows，接力互斥）。没有 Hypervisor，没有嵌套系统。
- **无套娃窗口**：所有窗口都是 VARIX 合成器的亲儿子，平级混排。没有"窗口里嵌另一个系统的屏幕"。
- **无模式切换**：打开 Linux 版软件不需要"进入 Linux 模式"，跑 exe 不需要"启动 Wine 环境"。点图标 → 窗口出现 → 用 → 关。
- **无文件孤岛**：原生应用、Linux 软件、Wine 软件、浏览器读写的是同一个 VARIX 文件系统。剪贴板全系统一份。
- **无强制联网**：核心功能离线完整。联网是增强项（云端构建、云 Windows、生态更新），不是活着的前提。

### 2.4 愿景的三条底线（不可谈判项）

以下三条在 STAR I 全周期内不可谈判，任何方案触碰即否决：

1. **主权底线**：引导链的最终决定权在 VARIX（Limine 配置是事实源，见 10.2 引导红线）。任何"为了兼容而让第三方组件获得引导决定权"的方案否决。
2. **稳定底线**：任何实验性功能不得进入默认引导路径。实验走 QEMU/独立配置（`_attic/limine-qemu-selftest.conf` 模式），实机默认路径只走验证过的代码。
3. **数据底线**：用户数据的删除、迁移、加密必须显式、可逆、可审计。静默吞错是 VARIX 工程师（含 AI）的红线中的红线。

## 第 3 章 双域架构总纲

### 3.1 为什么是"双域"

VARIX-500 的世界里有两个运行域，这不是设计偏好，而是被两个结构性事实逼出的最优解：

**事实一：Variable 结构性离不开 Windows。** Variable 是 Tauri 应用：Rust 壳 + WebView2 + 整套 Windows API。内核（`x86_64-unknown-none` 裸金属）里没有 Windows API、没有 WebView2、没有字体栈和网络栈——Variable 在内核里跑不起来，这不是工作量问题，是结构性不可能。

**事实二：UEFI 规范决定了域间切换必然包含一次复位。** 内核早期调用了 `ExitBootServices`，引导服务已交还固件，之后**无法再跳转到 Windows Boot Manager**——唯一的路是 `ResetSystem` 重走固件引导。所以"内核 → Variable"物理上必然包含一次重启。

两个事实合起来：**双域、接力、一次重启的切换成本**——这不是选择，是地形。STAR I 的架构工作是把这个地形上的路修到最好走（切换时间压短、状态保全、体验无缝），而不是幻想削平地形。

### 3.2 两个域的角色宪法

**VARIX 内核域（当家域）**：

- **大门**：开机第一手，Legend 主界面是系统的脸。
- **司闸员**：双域切换的指令（单次引导变量）由它写，带防自锁闸门——交接目标未验证则宁可不开闸。
- **应急自持域**：自带 ushell、文件管理、编辑器、应用管理器、帧缓冲图形。Windows 域彻底坏掉时，机器仍是可用的 VARIX 单机。
- **资产管理员**：U 盘部署检查、引导配置（boot-select.json）、数据保险库、驱动管理。

**Variable 域（产出域）**：

- 引擎室：U 盘 Windows 11（已加固）承载全部 Windows 生态能力。
- 首席应用：Variable（Tauri/WebView2）——终态双宿规划见第 12 章。
- 兜底跑量：结构上无法在内核侧跑的软件在这里跑。

**宪法条款**：两域互不干涉对方引导链；VARIX 是默认引导项（开机第一手）；Windows 域的进入必须经 VARIX 的交接指令（或 Limine 菜单的人工选择）；两域间的数据交换只走共享分区（SHARED 卷），不走任何"实时桥"。

### 3.3 接力模型的状态机

双域接力是一个显式状态机，全状态枚举如下：

```
┌──────────┐  点「启动 Variable」  ┌──────────────┐
│ VARIX 域  │ ──────────────────→ │ 交接中（VARIX 侧）│
│ (Legend/  │                     │ 画交接画面       │
│  桌面/ushell)│                   │ 写单次引导变量    │
└──────────┘                      │ ResetSystem     │
    ↑                             └───────┬────────┘
    │                                     ↓
    │                             ┌──────────────┐
    │  点「返回 VARIX」             │ 交接中（固件）   │
    └───────────────────────────── │ Limine 读 OneShot│
┌──────────────┐                   │ 单次链载 Windows │
│ Windows 域    │ ←──────────────── └──────────────┘
│ (Variable 全屏)│   自动登录→自启 Variable
└──────────────┘
```

状态机规则：

1. **单向唯一出口**：每个域到另一个域的转移只有一条边、一个触发动作。任何"快捷通道""并行通道"都是复杂度陷阱，禁止。
2. **交接必留痕**：每次交接在两侧各写一条日志（VARIX 侧内核日志、Windows 侧事件），内容含时间戳、触发源、目标。这是排查"循环""丢状态"类问题的唯一可靠依据。
3. **交接可拒绝**：目标侧就绪检查失败（如 Windows 引导项未验证、共享分区不可见）时，交接动作如实失败并留在当前域，绝不安格蒙交。
4. **防自锁闸门**：VARIX 侧写单次引导变量前必须验证目标项有效（`FilePathListLength > 4` 等闸门，源自 Boot2001 事故的教训）。未验证就盲写 = 无限重启循环，这是宪级禁令。

### 3.4 交接通道的最终定案：Limine LoaderEntryOneShot

交接通道经历了完整的选择过程，记录在此以绝后议：

| 候选通道 | 结论 | 原因 |
|---|---|---|
| 固件 BootNext（自建 NVRAM 项） | ❌ 判死 | 联想固件对自定义 NVRAM 引导项直接过滤（F12 不显示），实测实锤 |
| 固件 BootNext（指向固件原生项） | ⚠️ 备用 | 可行性存疑（Boot0002 "EFI USB Device" 指向 U 盘 ESP 的 BOOTX64，重启后又进 Limine，需配合默认项调整，有循环风险） |
| **Limine LoaderEntryOneShot（BLI 变量）** | ✅ **定案** | Limine 自己消费的单次引导变量：内核（作为 Limine 引导的客人）写 EFI Runtime 变量 → 重启 → Limine 读到 → 单次链载 Windows → 变量自动作废。**完全绕过固件过滤**，语义天生"一次性"，与"点按钮去一趟"的场景完美同构 |
| Hypervisor | ❌ 判死 | 见 3.5 |

**待验证事项**（阶段 1 第一件事）：本机 Limine 版本是否实现 BLI 的 LoaderEntryOneShot。若未实现：升级 U 盘 Limine 二进制（Limine 是无状态引导器，文件替换即可，配置向后兼容）。若升级后仍不支持：回退方案为"Limine 菜单默认项策略"（内核交接后重启，Limine 默认项在超时内可被 OneShot 覆盖——最终以实测为准，MD2 第 2 章有完整分支树）。

**返回通道**：Windows 侧写同一个 BLI 变量指向 VARIX 内核项 → 重启回 Legend。Windows 写 EFI 变量需 SeSystemEnvironmentPrivilege（提权），VARIX 侧提供签名脚本 + Variable 内置按钮双入口。

### 3.5 被排除的路线存档（为什么不是它们）

**Hypervisor（内核当虚拟机宿主）**：能让 Windows 与 VARIX 真同屏、真"同时"。否决理由四条：① 内核要先变成 VMM——VT-x/EPT/设备模型/ virtio，等于再造半个 VMware，年级工程；② Y7000 的 NVIDIA 消费卡直通几乎不可行（厂商反虚拟化），虚拟显卡下 Windows 图形体验劣化；③ 双域性能双损（VMM 开销 + 无直通 GPU）；④ 维护面指数扩大。结论：永久排除，除非硬件格局剧变。

**画面流（本机 Sunshine/Moonlight 模式）**：Windows 跑着、画面串给 VARIX 显示。否决理由：单机单内核——Windows 域跑着时 VARIX 已死，没有显示端。物理不可行（除非第二台设备）。

**云 Windows 作为主形态**：可作为**可选增强件**（浏览器里的网页 RDP），不可为主形态——离线即瘫、订阅依赖、延迟不可控。定位：终态里"有网时的锦上添花"。

**WSL2 式轻虚拟化**：同 Hypervisor 否决理由，且 Windows 域本就是"真 Windows"，无需再套。

### 3.6 双域的数据宪法

- **共享交换**：唯一合法通道是 SHARED 卷（exFAT/NTFS，两域都可挂）。VARIX_SYS 分区（系统+用户数据）对 Windows 域默认只读（防 Windows 侧软件污染 VARIX 的文件系统状态）。
- **状态保全**：VARIX 桌面在交接前保存会话状态（打开的窗口、编辑器缓冲、终端历史）到本域状态目录——回来时恢复。Windows 域侧同理（Variable 的状态由 Variable 自管理）。
- **时钟一致**：两域统一 UTC 存储、本地时区呈现，防止双域时间漂移导致的构建混乱。

## 第 4 章 交接协议详纲

（本章为 MD2 第 2 章的总纲级摘要；字段级细节、分支树、失败矩阵在 MD2 展开。）

### 4.1 去程协议（VARIX → Windows）

触发：Legend 界面「启动 Variable」动作（按键/点击，具体交互在阶段 2 的 ushell 重设计中定稿，功能上阶段 1 先以既有 handoff 路径接入）。

步骤序列（每步有验证点，失败即降级）：

1. **就绪检查**：确认 `handoff_to_variable` 开关开启、`handoff_target` 与 `usb_windows_esp_guid` 已登记（boot-select.json 单一事实源）。
2. **目标验证**：Limine 配置解析出 Windows 项（`protocol: efi` + GUID 路径），验证 ESP GUID 与登记一致。防自锁闸门：任何验证不过 → 降级留在内核（ushell），如实告警。
3. **状态保全**：桌面会话序列化到状态目录（阶段 2 起生效；阶段 1 的 ushell 场景无状态可保，跳过）。
4. **交接画面**：复用既有 `handoff::run` 的画面（wordmark + 副标题 + 进度条 + 底部说明行，PROMPT_MS 2400ms）——它是"无缝衔接"体验的前半段，与 Windows 侧 Variable 的开场动画构成完整的视觉接力。
5. **写 OneShot**：以 EFI Runtime Services 写 `LoaderEntryOneShot`（BLI GUID，值为 Limine 条目标题"Windows 11 (USB)"），写后回读验证。
6. **复位**：`ResetSystem`（冷复位）。此后永不返回；若复位不可用 → 如实降级 ushell 并 WARN。

### 4.2 回程协议（Windows → VARIX）

触发：Windows 桌面的「返回 VARIX」按钮（桌面脚本）或 Variable 内置按钮（阶段 2 后）。

步骤：提权（UAC）→ 写 BLI 变量值为 VARIX 内核项标题（"kernel/varix"）→ 可选：Windows 侧状态保存 → `shutdown /r /t 0`。重启后 Limine 读 OneShot → 链载回内核项 → Legend。

细节：Windows 写 EFI 变量需 `SetFirmwareEnvironmentVariableExW` + `SeSystemEnvironmentPrivilege`（VARIX 侧提供签名 PowerShell 脚本，沿用 `_attic` 提权脚本模板的安全规范：逐行落盘、excepthook 遗言、报告轮询）。

### 4.3 失败矩阵（摘要）

| 故障 | 表现 | 恢复 |
|---|---|---|
| OneShot 写失败（Runtime Services 不可用） | 交接画面后留在内核 | WARN + ushell；BIOS 引导场景如实说明 |
| OneShot 写成功但 Limine 不识别 | 重启后正常默认项（进 VARIX） | 表现为"点了没反应"——排查版本，升级 Limine |
| Windows 引导失败 | 0xED/0x7B 类蓝屏 | BCD 防自愈闸已设：自动重试；连续失败进 Windows 域修复流程（既有脚本族） |
| Variable 未自启 | 进桌面无窗口 | 自启链三查（Run 键/VC 运行库/ProfileList），既有脚本族 |

## 第 5 章 三腿战略（软件覆盖宪法）

### 5.1 为什么要三条腿

单一覆盖路线都有结构性死角：纯原生 = 软件荒（没人给 VARIX 原生开发全部软件）；纯兼容 = Wine 的 30 年证明兼容层永远追不上最新技术栈（Electron 即死角）；纯 Windows 域 = 主权旁落。三腿并立、边界清晰、互为备份，是覆盖与主权的最优平衡。

### 5.2 原生腿（第一优先）

- **定位**：日常高频功能用内核原生自绘实现——编辑器、终端、文件管理、保险库、四应用（code/fate/mind/write）原生版、设置中心。
- **优势**：最快最稳、体验完全统一（交互词典）、零兼容开销。
- **框架选型方向**：Rust GUI 框架（iced/egui/Slint 候选评估）+ cosmic-text（文本排版）+ 内核 winsurf 窗口面。MD2 第 10 章定稿。
- **纪律**：原生腿优先吃"高频 + 低复杂度"功能；复杂度爆炸的应用（视频剪辑级）不硬上原生，留给插座腿或兜底腿。

### 5.3 兼容层腿（覆盖主力）

三类入口，按软件出身分拣：

1. **Linux 翻译柜台**（主力，覆盖最大）：VSCode/Discord/Obsidian/Neovim/git/rustc/node 等一切有 Linux 版的软件 → Linux syscall 转译层 + 显示适配 → 原生窗口。**先例**：FreeBSD Linuxulator（20+ 年）、WSL1。**成本中心**：约 400 个 syscall 的转译 + X11/Wayland 显示适配，一次性基建。
2. **Wine 支架**（Windows 独占件）：只有 Windows 版的 exe（7-Zip 老、部分国产软件、老游戏）→ Wine 的 Win32 替身库 → 走同一个翻译柜台（Wine 有 Linux 版）。VARIX 不改 Wine 源码本体，只做支架适配与打包。
3. **Servo 渲染**（Web 形态软件）：vscode.dev、Figma、AI 网页版、云 Windows 客户端 → VARIX 内的浏览器 → 一切 Web 生态。

**软件分拣决策树**（每个新软件的入籍流程）：

```
新软件
 ├─ 有 Linux 版？→ 翻译柜台直插（成本最低）
 ├─ 纯 Win32 经典？→ Wine 支架（Gold 区概率高）
 ├─ Electron/新技术栈 且无 Linux 版？→ 找网页版/SaaS 替代 → Servo；都没有 → Windows 域
 └─ 带内核驱动（反作弊/加密狗）？→ Windows 域，没商量
```

### 5.4 Windows 域兜底腿

- **定位**：结构性跑不了的软件的真 Windows 环境 + Variable 的现有宿主 + 离线重案（兼容层全线故障时的可用系统）。
- **纪律**：兜底腿不发展"日常留在 Windows"的使用惯性——每次进域都应是为了具体软件的具体任务，办完回 VARIX。域内 Variable 依然自启（它是域的首席应用），但域的门永远为"回 VARIX"留着按钮。

### 5.5 覆盖率承诺（量化目标）

| 场景层 | 目标覆盖 | 达成阶段 |
|---|---|---|
| 开发工具链（git/编译器/编辑器/终端/AI CLI） | 95%+ | M2-M3 |
| 日常桌面（浏览器/办公/图像/音视频/笔记/IM） | 90%+（含国产软件 Linux 版） | M3 |
| Windows 独占工具 | 按清单窄而深 | 滚动 |
| 游戏（单机/独立） | 大部分 | M4+（依赖 GPU 驱动） |
| 带驱动/反作弊 | 0%（明确放弃，走域） | — |

## 第 6 章 生态借力战略（STAR 的 A）

### 6.1 借力的总原则

**VARIX 自有代码只写两样东西：插座和支架。** 插座 = 让外来软件能跑的接口层（syscall 转译、显示适配、libc 垫层）；支架 = 把上游项目接进 VARIX 的适配层（Wine 支架、Servo 支架）。上游的实现本体（Wine 的 Win32 替身、Servo 的渲染引擎、Mesa 的驱动）**永远不重写、不 fork 维护、不塞进内核**——以编译好的二进制随系统分发，跟随上游更新。

### 6.2 借力资产总表

| 资产 | 角色 | VARIX 侧工作量 | 语言亲和 |
|---|---|---|---|
| Wine / Proton | Win32 替身库（exe 兼容） | 支架适配 + 打包，本体不动 | C（只碰 ABI 边界） |
| Servo | Web 渲染引擎 | 用户态集成 + 显示/输入对接 | **Rust（同门）** |
| relibc | POSIX libc | 改造为 VARIX 后端 | **Rust（同门）** |
| smoltcp | TCP/IP 栈 | 集成为内核网络栈 | **Rust（同门）** |
| rustls | TLS | 网络栈组件 | **Rust（同门）** |
| cosmic-text | 文本排版 | 编辑器/桌面字排 | **Rust（同门）** |
| iced / egui | GUI 框架候选 | 原生应用框架基座 | **Rust（同门）** |
| Mesa | GPU 驱动（远期） | 后期评估移植 | C |
| 上游 Linux 仓库 | 软件池（数万包） | 零（二进制直插） | — |
| ReactOS | Win32 实现参考 | 只读参考 | — |

**Rust 同门红利**是借力战略的杠杆支点：标"同门"的资产与 VARIX 同语言，适配成本低一档、可读性高一档、长期维护可持续。

### 6.3 法律与许可立场

- **不碰 GPL 内核代码**：VARIX 不链接、不移植 Linux 内核的任何 GPL 组件——syscall 转译层是 VARIX 自有实现（参考公开文档与 FreeBSD 的方法论），立场与 WSL1/FreeBSD Linuxulator 同构，法律干净。
- **LGPL/MPL 类**（Wine、Mesa）：以独立二进制随系统分发、不静态合入 VARIX 内核，边界清晰。
- **MIT/Apache 类**（Rust 生态）：自由使用，保留版权声明。
- 上游软件的许可合规随分发走，VARIX 系统镜像内置的第三方软件清单在发布说明中全量披露。

### 6.4 借力的边界（什么时候必须自己写）

三件事永远自己写：① 内核本体（主权）；② 插座与支架（适配是 VARIX 独有形态）；③ 体验层（设计系统、交互词典——这是 VARIX 的脸，不接受上游审美）。除此之外，能用上游绝不自研。

| 远景 | ~500 万 | 完全体自研（浏览器引擎/兼容层/办公套件全自研） | 战略抉择点：借力转自研 |

### 8.2 为什么 60 万是刻意的

三个理由：① 借力战略的红利——60 万自有撬动亿行生态，性价比最优；② AI 协作的可及边界——自有代码保持在"模块化后可局部续写"的范围内，编译器+测试兜底质量；③ 维护现实——每一行自有代码都是永久负债（要测试、要文档、要跟 API 演进），60 万行是单人+AI 模式可长期健康维护的上限区间。**500 万行的路线存在（见 MD1 第 8 章 / 阶梯表），但它必须是能力需求拉动，且每档都是可发布产品——绝不憋大招。**

### 8.3 Rust 的治理红利

- 编译器极严：AI 续写幻觉出不存在的 API → 编译失败，当场暴露；内存安全类 bug 在编译期拦截一大类
- cargo 工作区：模块边界 = crate 边界，接口契约 = trait 签名，越界即编译错误
- 测试文化：既有 3150 项测试 + ktest 框架，"测试即规格"是 AI 协作的质量地基

### 8.4 治理纪律（全周期有效）

- 接口变更必走验证（编译 + 测试 + 实机三关）
- 文档与代码同步提交（文档过期 = 技术债利息最高的债）
- 每阶段产出 PPM 截图归档（视觉回归有据可查）
- 静默吞错 = 红线（错误要么处理并告警，要么如实上抛，绝不装死）

## 第 10 章 安全与自主

### 10.1 安全模型总纲

- **特权隔离**：内核态（VARIX 本体）与用户态（一切软件，含 Wine/Servo）硬隔离（ring0/ring3 + 页表）。兼容层软件不因"跑在翻译柜台"获得任何额外特权。
- **W^X**：可写页不可执行——PE/ELF 装载器已执行此口径（可写节强制 NX）。
- **引导链最小信任**：固件 → Limine → VARIX，三级各司其职；Limine 配置为引导行为唯一事实源。
- **翻译柜台的信任边界**：转译层对非法参数如实报错（Enosys 等），绝不猜测性执行——错误码穿透到软件，由软件自行处理。

### 10.2 引导设施红线（宪级）

2026-09-22 实机事故入宪：**永不删除/覆盖/降级/清除用户内置盘的 BIOS/UEFI 引导程序**——内置盘 Windows 引导文件（bootmgr/BCD/ESP 引导分区）、固件 NVRAM 引导项（BootOrder 首项）、主板固件本体，全部不可侵犯。引导链施工只允许在可移动介质（U 盘）侧进行；动内置盘引导相关的一切之前，必须列清单拿到 Variable 逐项确认。**本条凌驾于任何任务目标之上——哪怕是"为了修复引导"。**

### 10.3 数据主权

- 全部用户数据在 U 盘（VARIX_SYS / SHARED 卷），宿主机内置盘只读不写。
- 保险库（datavault）：用户可控的加密存储，密钥不出 U 盘。
- 兼容层软件的数据落在 VARIX 文件系统内的家目录映射，卸载软件可完整清除。
- 体验日志只记行为不记内容（密码、正文全文不入日志）。

## 第 14 章 决策档案（架构决策记录 ADR 摘要）

本总案的每一个重大决策都源于真实对话收敛与实机验证，档案化以绝后议：

- **ADR-001 接力而非同屏**：UEFI 物理约束 + Hypervisor 否决（3.5 节四理由）→ 接力式双域。
- **ADR-002 交接通道 = Limine OneShot**：固件过滤实锤（联想 F12 不显示自建项）→ 绕开固件，Limine 自有变量。BootNext 原生项降为备用。
- **ADR-003 三腿战略**：单路线死角分析 → 原生/兼容/兜底三腿宪法（第 5 章）。
- **ADR-004 Linux 插座统吃**：Electron 类软件有官方 Linux 版 → "跑 Linux 版"而非"跑 Windows 版" → syscall 转译层成为 Wine/Servo/Electron/CLI 的共同地基。FreeBSD Linuxulator/WSL1 为先例。
- **ADR-005 借力不自研**：Wine/Servo/Mesa/上游仓库永不重写，只做支架；Rust 同门件优先源码级融合。
- **ADR-006 内核最小化**：兼容本体全部用户态，内核只含翻译柜台与驱动；"塞内核"提案永久违规（8.4/10.1）。
- **ADR-007 代码量阶梯**：自有代码 60 万封顶（STAR I），500 万是能力拉动的远景阶梯而非目标；每档可发布。
- **ADR-008 UAS→BOT 降级**：0xED 实机竞态 + 掉线事故 → 稳定优先于速度。
- **ADR-009 引导红线入宪**：Boot2001 事故 → 内置盘引导链不可侵犯（10.2）。
- **ADR-010 Variable 双宿**：界面零改写（Servo 渲染）与原生重写并行，数据主权先行（datavault 内核版）。

## 第 3 章补 双域的历史演进（事故铸成的宪法）

STAR I 的双域架构不是纸上设计——它是三次实机危机淬炼出来的。记录这段历史，因为每一道闸门背后都有一块烧痕。

### 3.7.1 第一次危机：无限循环（2026-09-22 前）

现象：开机 → 三卡菜单 → VARIX 加载 → Legend → 重启 → 循环。根因链：Boot2001 空设备路径——`bcdedit /set device partition=Y:` 静默清空了 NVRAM 项继承的 96 字节 USB 路径。教训固化为两道闸门：① `bootnext.rs` 的 `FilePathListLength > 4` 闸门（END-only 空路径永不命中）；② 手写 212 字节 NVRAM Load Option 的能力（取证脚本 `_attic/vx-fix-boot2001.py`）。

### 3.7.2 第二次危机：固件过滤（2026-09-22）

现象：NVRAM 项修好了，但联想固件的 F12 菜单根本不显示自定义引导项——用户实验实锤。这条路线判死，催生了 Limine 链载方案（limine.conf 加 Windows 项）。教训：**NVRAM 是固件的地盘，固件有权过滤一切——交接通道不能建立在固件的善意上**。这条教训直接催生了 ADR-002（OneShot 定案）。

### 3.7.3 第三次危机：0xED 三层修复与掉线事故（2026-09-22~24）

Windows 域侧连续三层崩溃：0x7B（USB 驱动非引导级）→ 0xED（缺便携标志）→ 0xED 间歇（挂载库坏记录 + USB 就绪竞态）。修复链沉淀为脚本族（`vx-fix-*.py` 系列）；稳定性四板斧（UAS→BOT、禁选择性挂起、放宽超时、BCD 自动重试）后 0xED 绝迹。期间还实锤了一次 **U 盘瞬时掉线**（脚本执行中盘符消失）——廉价介质的物理现实。教训：① 稳定优先于速度（ADR-008）；② 介质升级是长期事项（R6）；③ 所有离线改 registry 的脚本必须带 excepthook 遗言 + 报告轮询（防御式脚本模板入宪）。

### 3.7.4 危机史带给宪法的东西

1. **防自锁闸门是宪级工程**——每一次"盲写引导变量"的提案都要被 3.7.1 的烧痕烫一下。
2. **不信任固件的善意**——一切交接走 Limine 自有变量（ADR-002 的血统）。
3. **默认路径只走验证过的代码**——实验隔离在 QEMU/独立配置（10.1）。
4. **防御式脚本模板**——提权脚本逐行落盘、遗言、报告轮询，是所有运维脚本的标准形态。

这段历史的完整取证脚本沉淀在 `_attic/vx-*.py`（14+ 个），它们是 VARIX-500 的"飞行记录仪"。

### 3.8 域内架构细节（VARIX 域的内部版图）

VARIX 域不是单块石头，它的内部版图（按既有代码域归口）：

- **引导族**：limine.rs（协议请求）、bootcfg.rs / bootopt.rs / bootselect.rs（菜单与决策）、bootnext.rs（固件变量 + 闸门）、handoff.rs（交接画面与协议）、bootchain.rs
- **图形族**：fb.rs（帧缓冲）、font.rs（字体引擎）、banner.rs（背板）、wallpaper.rs、progress.rs（进度条单一来源）、compositor 族、displaysrv、winsurf.rs（窗口面）、aurora 族（桌面实验）、designsys（设计系统）
- **进程族**：proc/ring3.rs（用户态）、proc/job.rs（调度）、proc/loader.rs（段翻译引擎）、proc/pe.rs + peblock.rs（PE 装载）、proc/winapi.rs（Win32 服务台）、exec.rs（执行域）、usrshell.rs
- **输入族**：ps2.rs、drivers/xhci.rs、inputsvc.rs
- **文件族**：fs 域、fileman 域
- **兼容族**：compatapi.rs / compatshim.rs / compatruntime.rs（兼容工程机制层）、compatruntime
- **支撑族**：cpu.rs、acpi.rs、cmdline.rs、checks.rs、timeline.rs、platform.rs、a11y 域、audio 域、gnet 雏形

阶段 2-3 的所有施工都在这张图上落子：桌面壳长在图形族上，翻译柜台长在进程族与 compat 族之间，网络栈是新开的一族。**每个新域入图前必须回答：它调谁、被谁调、崩了拖谁——三问不过不入图。**

## 第 4 章补 交接协议的工程细节

### 4.4 状态保全格式（阶段 2 生效）

VARIX 桌面交接前的会话序列化格式（v1 规格）：

```
/varix/state/session-<timestamp>.json
{
  "version": 1,
  "windows": [ { "app": "editor", "files": [...], "cursor": {...} },
               { "app": "terminal", "history_lines": n } ],
  "clipboard_meta": "...",
  "focus_restore": "editor"
}
```

- 只存元数据与轻量状态，**不存大文件内容**（编辑器缓冲的未保存内容由编辑器自己的草稿机制负责——数据安全红线：自动保存优先于交接保全）。
- 恢复策略：返回 VARIX 后按清单重开窗口，恢复失败的条目如实标记（不静默丢弃）。

### 4.5 交接时序预算

| 段 | 预算 | 说明 |
|---|---|---|
| VARIX 侧：验证+保全+写 OneShot | ≤ 500ms | 画面同时播（不阻塞观感） |
| 交接画面 | 2400ms | 固定（PROMPT_MS），给"正在进入"的仪式感 |
| 固件复位 + Limine | 3-8s | 硬件决定，不可控 |
| Windows 启动 + 自动登录 | 8-20s | 已加固后的实测区间 |
| Variable 自启到全屏 | ≤ 5s | WebView2 暖启动 |
| **单向总预算** | **≤ 30s** | 判据 1 的量化线 |

回程对称预算（Windows 侧脚本 + 重启 + Legend 就绪 ≤ 30s）。超预算即记体验日志（第十三章体系），连续超标触发性能专项。

### 4.6 交接体验的视觉接力（设计协同）

去程：VARIX 交接画面（深空背板、VARIX 字标、"ENTERING VARIABLE SYSTEM"、进度条走满）→ 黑场（固件复位）→ Windows 自动登录 → **Variable 开场动画必须以同色系（深空蓝 + 同款进度语言）承接**——用户视角是"同一扇门开两次"，不是"换了个世界"。

回程对称：Variable/桌面脚本触发"返回 VARIX"→ 简短确认 → 黑场 → Legend 原样浮现（它是"家"，不需要过渡动画，直接回来就是最好的仪式）。

这条设计协同是阶段 2 ushell 重设计与 Variable 界面改版的**硬约束**：两侧设计稿必须并排目检（PPM 归档对照）。

**判例 8：某静态链接 Rust CLI** → PE 格式 → PE 装载器 + Win32 首层即可尝试，甚至不必等插座。**预期：原生腿快速通道**。
**判例 9：Steam 客户端** → Linux 版成熟 + Proton 成熟 → 翻译柜台；游戏按 5.3 分拣。**预期：客户端绿、游戏分层**。
**判例 10：Keil/IAR 嵌入式 IDE** → Windows-only 闭源 → **Windows 域**；开源替代（PlatformIO/ rusty 工具链）可走插座。

## 第 6 章补 借力资产的集成协议

每个借力资产在 VARIX 内的"落位说明书"（统一模板，MD2 有字段级细节）：

**Wine 集成协议**
- 形态：上游源码交叉编译为 VARIX 目标 → 二进制树落在 `/opt/wine/`
- 支架：VARIX 提供 `posix-syscall 面`（Wine 的运行前提）+ X11/Wayland 子集（Wine 的显示出口）+ 打包脚本（版本锁定 + 补丁集）
- 升级：跟随上游 stable 分支，季度节奏；支架补丁集重放（目标：补丁数 < 20 个文件）
- 红线：不 fork 行为分叉——所有本地改动必须以"最终合入上游"或"明确永久分歧"归档

**Servo 集成协议**
- 形态：Rust 依赖树集成（Servo 的组件化程度允许按 crate 取用：渲染引擎/JS 引擎/网络可分层引入）
- 支架：窗口面输出适配（Servo 的 display list → winsurf 提交）、输入事件注入、网络走 smoltcp
- 升级：跟随上游 nightly 精选版，双周节奏；VA RIX 侧以 feature flag 隔离实验性能力

**relibc 集成协议**
- 形态：源码级融合（Rust 同门），作为翻译柜台的用户态伴生层
- VARIX 后端：relibc 的 syscall 抽象点逐个对准 VARIX 语义（文件/内存/线程/时钟）
- 测试：relibc 自带的一致性测试套全量跑绿为验收线

**上游跟进策略**：所有借力件登记在 `docs/upstream-registry.md`（版本、许可、补丁集、跟进人、节奏）——上游 Registry 是借力战略的仪表盘（MD3 任务 T-302）。

## 第 9 章补 体验宪章的 VARIX 落地（十四章逐章）

既有 14 章体验完整性体系是全局宪法，本章把它逐章"翻译"成 VARIX 语境的验收对象——每一条都是未来桌面走查清单的来源。

**第一章 归属与隔离** → VARIX 的应用：任何窗口（原生/翻译柜台/Wine）都必须完整活在 VARIX 桌面内：任务栏有它的按钮、Alt+Tab 有它的位、托盘区收它的托盘图标。**兼容层窗口"逃逸"（绕过合成器直写帧缓冲）是缺陷级 bug**——PE 装载与 Wine 支架的验收清单必含此项。Wine 的全屏独占模式（游戏）走"VARIX 授权的独占通道"，退出后桌面必须完好如初。

**第二章 浮层生命周期** → 桌面的浮层清单：开始磁贴、右键菜单、通知气泡、保险库解锁框、交接确认框。每一条的出路：点外关/即关/触发键再点关/失焦关/Esc 关，五路全通才可交付。判决标准沿用体系原文：**右键弹出的交互框，点击框外任意位置必须消失**。

**第三章 交互状态机** → 每个可交互元素的"乱点表"：连点（防抖）、点一半拖走（取消）、长按（进度感）、窗口切走再回（状态无损）。兼容层窗口的特殊项：Wine 应用假死的"强关"路径（VARIX 任务管理器可直接终结用户态进程，这正是进程隔离的红利）。

**第四章 键盘与焦点** → Tab 序、焦点环、浮层焦点进出、快捷键承诺表。VARIX 全局快捷键词典（阶段 2 定稿）初稿：`Win`=开始磁贴、`Alt+Tab`=窗口切换、`Ctrl+Alt+T`=终端、`Ctrl+Alt+V`=交接 Variable、`Ctrl+Alt+R`=返回 VARIX（域内）。**声明即承诺**：词典外不抢键，词典内必真实生效。

**第五章 微观手感** → 悬停变化、按压反馈、拖拽跟随、滚动边界、双击/右键分工。合成器的拖拽必须 1:1 跟手（窗口拖动是 VARIX 的脸面，60fps 是底线）。翻译柜台窗口的输入延迟预算：键盘 ≤ 20ms、鼠标 ≤ 16ms（柜台转发开销计入）。

**第六章 文本与输入** → 输入法（中文 IME）在 VARIX 的三处战场：原生编辑器（cosmic-text 的 IME 支持）、翻译柜台窗口（IME 事件翻译——Wine 生态的老大难，VARIX 从第一天就按一等公民设计）、终端。剪贴板：全系统一份、跨域经 SHARED 卷接力（明文不落盘）。

**第七章 窗口与环境** → 缩放（125%/150%/200%）、多显示器、分辨率热切换、亮暗主题、夜间对比度。Wine 应用在 HiDPI 下的模糊问题列入 Wine 支架验收项。

## 第 10 章补 安全详案

### 10.4 威胁模型（STAR I 口径）

STAR I 的威胁模型是**个人设备**，不是对抗性多用户系统。明确在保护范围内外的：

| 保护 | 不承诺 |
|---|---|
| 误操作损坏（回收站/确认/撤销链兜底） | 国家级攻击者 |
| 恶意软件的横向破坏（进程隔离+W^X+用户态边界） | 内核级 0day 级对抗 |
| 数据物理丢失（保险库加密+双副本） | 物理拷贝攻击（U 盘被取走后的离线破解——加密强度按预算持续加强） |
| 引导链被篡改（Limine 配置校验+红线） | 固件级攻击（BIOS rootkit——超出个人设备模型） |

### 10.5 权限矩阵（终态）

| 主体 | 内核内存 | 文件系统 | 网络 | 其他进程 |
|---|---|---|---|---|
| 内核本体 | 全部 | 全部 | 全部 | — |
| 原生应用（用户态） | 无（经 syscall） | 家目录+授权目录 | 经网络栈（可审计） | 隔离 |
| Linux 兼容层进程 | 无（经柜台） | 家目录映射 | 经柜台→网络栈 | 隔离 |
| Wine 进程 | 无（经柜台+Win32 替身） | 映射盘符（Z:→VARIX fs） | 经 Winsock 替身→柜台 | 隔离 |
| Servo | 无 | 缓存目录白名单 | 经内置网络栈 | 隔离 |

矩阵原则：**一切软件零内核特权**；文件访问默认最小化（家目录+显式授权）；网络可审计（连接表可查）。

### 10.6 防御式运维脚本规范（入宪）

实机脚本（提权改 registry/引导/文件）的标准形态，源自实战模板：

1. 逐行落盘日志（`_fh.flush()` 每行）——脚本死也留下遗言
2. `sys.excepthook` 全局遗言（traceback 全文落盘）
3. `ast.parse` 预检后再执行（语法错误不发车）
4. UAC 提权走 `ShellExecuteW runas` + 报告文件轮询（提权子进程静默崩溃的教训）
5. 每个写操作前三态检查（现状/目标/回滚路径）
6. 内置盘相关操作：清单前置 + 人工逐项确认（10.2 红线的执行件）

### 11.4 外设路线（U 盘整机的"任意机器"课题）

## 第 17 章 六子系统深挖（决策级）

MD1 前面十六章回答的是"STAR I 是什么、走哪条路、守什么规矩"；本章开始回答"VARIX 作为操作系统，它的每一个器官具体长什么样"。之所以叫"决策级"而不是"实现级"，是因为字段级的寄存器地址、结构体布局、协议报文格式全部下沉到 MD2《技术详案》，本章只锁死六个子系统各自的**职责边界、现态盘点、目标态、关键决策与验收判据**——这些是后续施工不允许悄悄改动的东西，改动必须走第 14 章的 ADR 程序。

六个子系统的选取标准很朴素：一台电脑从按下电源到用户能在屏幕上打字、看图、听声、上网、开软件，中间必经的六个关口。窗口面管"像素从哪来"，进程装载管"程序怎么跑起来"，文件系统管"数据存哪里"，网络栈管"包怎么出去"，音频管"声音怎么响"，输入管"手指怎么进"。任何一关断掉，VARIX 就退化成演示品而不是日用系统。下面逐一过。

### 17.1 窗口与合成面（Display & Compositing）

**职责边界一句话：屏幕上每一个像素是谁画的、谁叠上去的、谁决定它出现在哪——全部归本子系统管，其余任何子系统不许直接碰显存。**

**现态盘点（36 万行中的份额）。** VARIX 内核域目前已有：Limine 引导期申请高分辨率帧缓冲（1920×1080 起步）、内核侧基础点线面绘制与文字渲染（交接画面与内核自绘 UI 使用）、Variable 双宿模式下的"VARIX 作显示屏"通路雏形。尚没有的东西：窗口管理、多应用合成、浮层层级、剪贴板、DPI 缩放——这些全部是 STAR I 阶段要补的主体。

**决策 W-1：合成器放用户态，内核只交付帧缓冲。** 合成器（compositor）是一个普通用户态进程，唯一特权是持有最终写屏权；内核侧只维护"帧缓冲对象"（framebuffer 对象句柄、尺寸、像素格式、双缓冲翻页原语）和一块供各应用绘制用的共享内存缓冲区队列。这样切的理由有三条：其一，与 ADR-006（内核最小化）一致，内核不背界面逻辑；其二，崩溃隔离——合成器崩了，内核不倒，看门狗三秒内把它拉起来，已开窗口的表面缓冲还在共享内存里，会话不丢；其三，为将来 R3 攻坚线（GPU 加速）留位——届时替换的只是合成器内部的提交后端，客户端协议不动。

**决策 W-2：窗口协议自研极简版 VXWM，外加 Wayland 桥。** 合成器与客户端之间用一套自研的极简窗口协议 VXWM——消息种类硬上限 24 种（绑定、创建表面、提交缓冲、 damages、输入事件、拖放、剪贴板、关闭协商等），每种消息字段数不超过 12 个。自研而非直嵌 Wayland 的原因：VARIX 的常驻大客户端只有三类（原生应用、Wine、Servo 壳），它们要么可以直说 VXWM，要么需要一个翻译垫；用 Wayland 全集反而把十年累积的历史包袱全背进来。但为了借力，VXWM 旁边放一座"vx-wayland-bridge"小桥，把 VXWM 翻译成标准 Wayland 协议——Wine 新版自带 Wayland 驱动、Electron 类应用走 Wayland 后端，都能过桥进场。桥是单向垫片，出问题只影响过桥应用，不污染 VXWM 本体。

**帧调度与渲染管线。** 每个应用绘制到自己的缓冲区，提交时只报"脏区"（damage region）；合成器把各表面按 z 序合成到后备帧，脏区外绝不重画——这是 U 盘系统省 CPU 的生命线，因为 STAR I 阶段没有 GPU 硬加速，全部合成靠 CPU 软算，每多画一个像素都是烧 R3 阶段之前的性能预算。目标帧率 60fps，但合成器允许"事件驱动降帧"：画面静止时整帧停发，只维持光标层；动画期间满帧；空闲 CPU 占用（单核）必须低于 5%。双缓冲翻页用内核提供的原语完成，杜绝撕裂。

**像素格式与缩放。** 全系统统一 ARGB8888 为合成格式；应用可提交更低色深，合成时统一抬升。逻辑像素与物理像素 1:1 起步，缩放因子作为窗口协议的绑定参数下发（125%、150% 预留），字体与图标侧先支持——这是体验宪章第七章"不同 DPI 下布局成立"的工程前提。

**浮层生命周期（对接宪章第二章）。** VXWM 把浮层分为四类并给每类内置完整出路语义：瞬态提示（tooltip，失焦即灭）、菜单（点外即关、Esc 可关、再点触发物可关）、对话框（模态，Esc 语义明确、焦点困在框内）、抽屉与面板（跟窗生命周期）。合成器在协议层强制执行这些语义，客户端想做出"关不掉的框"都做不到——把体验宪章从"要求"变成"物理约束"，这是本子系统最值得骄傲的一条设计。

**文字与剪贴板。** 文字整形与排版交给 cosmic-text（借力清单成员）：它能处理中文折行、混排、字重替换，VARIX 只负责把它的输出位图搬进字形图集（glyph atlas）。剪贴板采用显式转发模型：只有获得焦点的窗口能"贴"，只有用户显式复制的窗口能"送"，内容类型先支持纯文本与位图，杜绝后台静默读剪贴板的越权行为。

**验收判据（并入 MD3 对应工作包）：**

| 编号 | 判据 | 达标线 |
| --- | --- | --- |
| D-01 | 窗口拖动帧率 | 1080p 单窗口拖动 ≥ 55fps（软渲染） |
| D-02 | 空闲合成开销 | 静止桌面 CPU ≤ 单核 5% |
| D-03 | 浮层出路 | 宪章第 2 章出路清单逐项全绿，物理强制 |
| D-04 | 合成器抗崩 | 杀掉合成器 ≤ 3s 恢复，窗口不丢、焦点恢复 |
| D-05 | 中英文混排 | cosmic-text 折行、省略号、emoji 回退不破版 |

### 17.2 进程与程序装载（Process & Loader）

**职责边界一句话：一个程序文件（无论 ELF 还是 PE）如何变成一个有地址空间、有信号语义、有父子关系的活进程——归本子系统管；跑起来之后怎么画、怎么存、怎么上网，归别的子系统。**

**现态盘点。** 内核已有：ELF64 装载器雏形、进程表、基础分页与每进程地址空间、relibc 作为原生 C 运行时的目标 ABI、W^X 强制。尚缺：完整信号体系、PE 侧接管（Wine 进程模型）、装载缓存、进程配额。

**决策 P-1：双装载器、一条货架。** 内核提供统一的进程创建入口，背后两条装载路：ELF 路服务于原生应用与 Linux 兼容层（装载后把系统调用引导到翻译柜台），PE 路不由内核负责——内核只把控制权交给 Wine 的预装载器（preloader），PE 解析、重定位、SEH 仿真、DLL 树全部是 Wine 用户态自己的事。这条分界是 ADR-006 的直接推论：内核认识 ELF 是"本职"，认识 PE 是"越权"。

**决策 P-2：PID 1 极简主义。** VARIX 的 init 进程只做三件事：拉起合成器、拉起兼容柜台（syscall 转译服务与 Wine 会话）、拉起会话管理；不做通用服务管理器。systemd 式的"万物皆 unit"在 U 盘系统上是负担不是能力——服务编排需求由一张静态启动表（JSON）覆盖，顺序固定、依赖显式、失败策略只有"重试一次然后降级"。

**决策 P-3：Wine 进程组与 wineserver 看门狗。** 每个Windows 程序在 Wine 模型下是一个进程组，组内共享一个 wineserver 单例（Windows 语义的协调者：句柄、同步对象、窗口站）。wineserver 是兼容腿的命门，给它三层保险：心跳看门狗（失联 2 秒判定）、崩溃自动重启（重建空协调态，已开应用逐个恢复）、会话快照（窗口清单与剪贴板入交接分区，重启后可提示恢复）。

**信号与异常的双语制。** 原生与 Linux 兼容侧讲 POSIX 信号语（1-64 号语义对齐 Linux，Linuxulator 负责映射）；Wine 侧讲 Windows 异常语（SEH），翻译工作全部在 Wine 用户态完成，内核只提供统一的底层陷阱分发。两侧永不互相发信号——不存在"给 Wine 进程发 SIGKILL"这种混合语义，杀 Wine 进程一律走 Wine 自己的终止协商。

**装载性能（U 盘特化）。** 冷启动读盘是 U 盘 BOT 协议的短板，装载器配三件套：按需分页（不整个读入）、读放大优化（装载段按 4MB 粒度预读）、热门程序指纹缓存（记录 VSCode 等常用程序的段清单，二次启动按清单预取）。预算写死：VSCode 冷启动 ≤ 15 秒、记事本类 ≤ 3 秒、二次启动减半。

**验收判据：**

| 编号 | 判据 | 达标线 |
| --- | --- | --- |
| P-01 | ELF 原生进程 | relibc 程序全功能（含信号、管道、环境变量） |
| P-02 | Wine 进程组 | 组内任一进程崩溃不拖垮组外应用 |
| P-03 | wineserver 恢复 | 杀 wineserver 后看门狗重建 ≤ 5s，前台应用可恢复 |
| P-04 | W^X | 任何页不可同时可写可执行，装载器强制 |
| P-05 | 冷启动预算 | VSCode ≤ 15s（USB3 BOT），二次启动 ≤ 8s |

### 17.3 文件系统与存储（Storage & FS）

**职责边界一句话：数据在 U 盘上怎么摆、怎么找、怎么保命，归本子系统管。**

**现态盘点。** 已有：FAT 只读（ESP）、ISO9660 只读（安装介质）、块设备层（USB 大容量存储，BOT 协议，实机四板斧已加固）。尚缺：可读写主文件系统、NTFS 桥、缓存与写合并、掉电保护。

**决策 F-1：ext4 借 Google ext4 crate 实现读写主文件系统。** VARIX 的主分区（VARIXSYS 与用户数据 DATA）采用 ext4，实现直接复用 Google 开源的 ext4 crate（crosvm 同源，Apache-2.0/MIT 双许可，与内核 GPL 立场无冲突）。这是"借力不自研"在存储侧的最大单笔：ext4 的一致性、日志、 extents 全部白得，VARIX 只做挂载层、缓存层与写合并层。首阶段日志重放实现只读路径（挂载时回放干净日志），崩溃恢复先保守后完善。

**决策 F-2：NTFS 只读桥。** 对 Windows 域分区（含 WINESP 与系统 NTFS）一律只读挂载。理由：用户态 NTFS 读写实现（ntfs-3g 路线）体量与风险都不划算，而"Windows 域负责写、VARIX 域负责读"恰好符合双域接力模型——VARIX 需要读 Windows 侧的文件（交接状态、Variable 应用资产），不需要写它。需要向 Windows 侧带话时，走交接分区的小文件通道（见 4.4 状态保全）。

**分区布局总表（thinkplus 1TB 实机版）：**

| 分区 | 文件系统 | 建议容量 | 归属域 | 用途 |
| --- | --- | --- | --- | --- |
| ESP | FAT32 | 1GB | 共享 | Limine、内核镜像、引导配置 |
| VARIXSYS | ext4 | 16GB | VARIX | 内核模块、系统资源、字体 |
| WINESP | FAT32 | 1GB | Windows | Windows 引导文件（交接目标） |
| WINOS | NTFS | 64GB | Windows | Windows 系统与 Variable 应用 |
| DATA | ext4 | 其余 | VARIX | 用户数据、Wine 前缀、应用缓存 |

**U 盘写保护与掉电纪律。** 三条铁律进实现：其一，写合并——所有小于 64KB 的元数据写延迟 5 秒合并落盘，顺序写优先；其二，关机闸——任何会话结束路径必须先冲刷 ext4 日志再允许断电，交接流程里"冲刷完成"是进入重启的硬前置；其三，拔出警告——系统运行期检测到 U 盘突然消失，立即全屏接管（保护现场信息），禁止静默继续运行在纯内存态。

**验收判据：** ext4 读写通过 fsx 类压力测试 24 小时；NTFS 只读挂载正确读出交接分区与 Windows 资产；写合并开启时元数据吞吐 ≥ BOT 通道极限的 80%；非正常断电 100 次抽测无文件系统损坏（日志重放成功）。

### 17.4 网络栈（Networking）

**职责边界一句话：包从网卡出去、从网卡进来、在进程之间递送——归本子系统管；至于包里装的是什么内容（网页、代码、聊天），归应用。**

**现态盘点。** 内核已有：PCI/PCIe 枚举框架、网卡的驱动位（骨架级）。尚缺：协议栈本体、socket 系统调用面、无线支持、DNS/TLS。

**决策 N-1：smoltcp 编译进内核，作为"驱动侧的协议栈"。** smoltcp 是 Rust 生态最成熟的 TCP/IP 栈（no_std 设计，本为嵌入式而生），拿来即用，符合借力清单。它放在内核侧而非用户态，理由：Linuxulator 转译柜台在内核处理 socket 类系统调用时需要直接命中协议栈，转一手用户态反而增加 2 微秒级延迟与一次上下文切换；同时 smoltcp 本质是"库"不是"内核服务"，把它视作网络驱动的一部分，与 ADR-006 的内核红线不冲突（内核只含驱动与转译柜台——协议栈随转译柜台走）。

**决策 N-2：socket 面向 POSIX，长度对齐 Linux。** 用户态暴露 `socket/bind/listen/connect/accept/send/recv/close` 等 POSIX 风格调用，语义与 Linux 对齐（这样 Linuxulator 的转译几乎是改名直通），errno 编号表照抄 Linux 值——转译柜台不需要查表换算。

**有线优先，无线后置。** Y7000 实机自带有线网口与 Intel 无线网卡。STAR I 阶段：有线（RTL8168 系）与 USB 网卡先行；WiFi 因固件装载链复杂（需从 linux-firmware 载入厂商固件 blob——blob 许可独立于 Linux 内核代码，装载合规，但链路长）放入阶段 3。用户兜底：WiFi 空窗期可用手机 USB 网络共享（RNDIS/NCM 类），这条便宜通道实测可用性高。

**上层服务全部用户态。** DNS 解析用 hickory-dns（原 trust-dns，Rust，MIT/Apache），TLS 用 rustls（借力清单成员），HTTP 服务端与客户端在原生框架里给 httprust 级封装。垃圾网址过滤、代理设置等策略层放会话服务，不进内核。

**网络诊断三件套是标配**：vx-ping、vx-route、vx-capture（抓包落 ext4，供判例归档）——兼容性判例十有八九要靠这三样归因，没有它们，"Steam 登不上"永远是一笔糊涂账。

**验收判据：** TCP 吞吐（有线千兆对拷）≥ 700Mbps；并发 256 连接无泄漏；Linux 兼容应用（curl、git）的网络调用全绿；rustls 握手通过 TLS1.3 全套互操作测试。

### 17.5 音频（Audio）

**职责边界一句话：应用说"我要发声"，本子系统负责把数字采样变成耳机里的模拟信号，且多个声音互不打架。**

**决策 A-1：单例混音器守护进程，类 PipeWire 极简版。** 一个用户态守护进程独占声卡，所有应用的音频流提交给它混音；流有独立音量、独立静音、优先级（通话类 > 媒体类 > 提示音）。不引入 PipeWire/PulseAudio 本体的原因：它们的完整特性面（蓝牙、网络音频、视频同步）在 STAR I 是包袱，而"每流混音 + 低延迟路径 + Wine 对接"三个真需求用一个两三千行的守护进程即可覆盖。这个决定在音频上是个例外——其他子系统都尽量整库借用，音频因为"够用的极简实现"确实小，自研更划算。

**驱动侧。** 第一目标声卡是 Y7000 的 Intel HDA（Realtek 编解码），驱动按 HDA 规范实现 CORB/RIRB 命令环与 DMA 位置上报，工作量集中在编解码器引脚配置（耳机/麦克风切换）。USB 音频类后置到阶段 3。

**Wine 对接。** Wine 侧把 winmm/waveOut、WASAPI 语义桥接到混音器：每个 Windows 进程的音频流映射为一条混音器流，音量合成器里可见、可单独调——Windows 软件的声音行为与在真 Windows 上一致。

**延迟预算**：端到端（应用提交到出声）≤ 40ms；混音器空闲 CPU ≤ 1% 单核。验收：多流混音无爆音、拔插耳机自动切换（HDA 引脚感知）、Wine 应用播放音视频声画同步（±80ms 内）。

### 17.6 输入与输入法（Input & IME）

**职责边界一句话：键盘、鼠标、触摸板的事件从硬件到窗口，归本子系统管；文字候选与上屏，也归它。**

**决策 I-1：输入子系统独立于窗口协议，但通过 VXWM 投递。** 驱动层（PS/2 控制器、USB HID）产出统一事件流，输入子系统做布局表翻译（自维护 JSON 布局，内置中英文），然后把事件交给合成器的焦点链路由——焦点在谁，键盘事件归谁；指针事件按命中测试归对应窗口。IME（输入法引擎）作为输入子系统的一个模块存在，不是独立进程：极简拼音引擎（声韵母组合、常用 3 万词库冻结版、整句候选）在 STAR I 内置，第一版不追求云词库与整句智能，追求"稳定、零延迟、永不崩"。

**IME 与 Wine 的协同是判例级难题**（Windows 程序里打中文）：裁决为"合成器层提供候选窗"——Wine 窗口收到的是合成器转换好的提交文本，候选窗是 VARIX 自己的浮层，定位跟随 Wine 窗口的光标上报点。这样 Wine 与 IME 完全解耦，Wine 不需要懂 XIM 或 TSF。判例库第 11 例（附录 A）收录此案。

**验收判据：** 键入至字符上屏 ≤ 16ms；拼音候选首屏 ≤ 100ms；全部交互元素键盘可达（Tab 序、焦点环、快捷键字典生效，对应宪章第四章）；快捷键总表全局唯一且 IME 组合期不劫持。

### 17.7 六子系统契约总表

子系统之间不是靠"默契"协作的，是靠下面这张契约表。契约违反等同 bug，走 20 维度验收第 12 项（一致性与开放性）扣分。

| 编号 | 契约 | 立约方 | 内容 |
| --- | --- | --- | --- |
| C-1 | 帧缓冲独占 | 合成器 ↔ 内核 | 仅合成器持写屏句柄；内核不提供其他直写通道 |
| C-2 | 表面限额 | 合成器 ↔ 应用 | 单应用表面 ≤ 64 个，单表面 ≤ 4K×4K，超限拒绝 |
| C-3 | 消息上限 | VXWM 全体 | 协议消息 ≤ 24 种，加消息必须过 ADR |
| C-4 | syscall 语义 | 转译柜台 ↔ 内核 | Linux 语义 errno 原值直通，不换算 |
| C-5 | wineserver 单例 | Wine 支架 ↔ 进程 | 每会话仅 1 个 wineserver，禁多开 |
| C-6 | NTFS 只读 | 存储 ↔ 全体 | Windows 分区全系统只读，任何模块不得申请写句柄 |
| C-7 | 音频独占 | 混音器 ↔ 驱动 | 仅混音器持声卡句柄 |
| C-8 | 事件单向流 | 输入 ↔ 合成器 | 事件只从驱动流向窗口，窗口不得伪造输入事件给其他窗口 |

## 第 18 章 生态运营与评级体系（STAR 的运营面）

STAR I 的"STAR"里有一个字母是给生态的。代码写完只是完成了一半——另一半是让软件"进得来、查得到、评得准、升得动"。本章是生态侧的宪法。

### 18.1 兼容评级体系（五级星标）

每个想在 VARIX 界面里被打开的软件，都会被归入五级中的一级，评级写进"星图"（Star Map）应用目录，用户在打开任何软件之前就知道它处于哪一档：

| 级别 | 名称 | 含义 | 判定标准 |
| --- | --- | --- | --- |
| ★★★★★ | 原生级 | 专门为 VARIX 构建的官方版本 | 用 vx-SDK 构建、全功能、性能达标 |
| ★★★★☆ | 直插级 | 有官方 Linux 版，经 Linuxulator 直插运行 | Electron/Java/Python 类，主功能全绿 |
| ★★★☆☆ | 兼容级 | 经 Wine 运行的 Windows 软件 | 判例全过、无 P1 级缺陷 |
| ★★☆☆☆ | 桥接级 | 经 Servo 壳承载的 Web/远程形态 | 核心功能可用，重交互受限 |
| ★☆☆☆☆ | 兜底级 | 需切 Windows 域运行 | 双域接力可达，计一次重启成本 |

评级不是终身制。每个软件的每次上游大版本升级都会触发复评——Windows 软件更新可能破坏 Wine 判例，Electron 升级可能改变 syscall 依赖面。复评结果更新星卡，星图目录同步刷新。

### 18.2 星卡（Star Card）：一张软件一份档案

星图目录里每个软件挂一张星卡，字段固定：软件名与版本、当前评级、构建/运行路径（原生/直插/兼容/桥接）、已过判例清单、未过判例与缺陷编号、资源占用实测（冷启动、内存峰值、CPU 空闲占用）、复评日期、负责批次。星卡是公开的——用户看得到每个软件的兼容真相，开发者看得到要修什么。星卡禁止写"基本可用"这种模糊语，判定只有"判例通过/未通过"两种。

示范星卡（三张，其余随施工产出）：

**《Visual Studio Code》**：直插级 ★★★★☆。走官方 Linux 版（deb 包解开直插），Linuxulator 承载，GPU 关闭用软件渲染路径。已过：启动、编辑、内置终端、扩展安装、git 集成。未过：Remote-SSH（依赖 OpenSSH 特定行为，阶段 3 复测）。实测：冷启动 14.2s / 内存峰值 1.1GB。判例编号 SC-001 至 SC-014。

**《7-Zip》**：兼容级 ★★★☆☆。Wine 运行官方 Windows 版，纯 Win32 界面恰好落在 Wine 强区。已过：压缩、解压、右键集成等价物、大文件（>4GB）。实测：冷启动 2.1s。判例 SC-021 至 SC-025。

**《Steam》**：桥接级 ★★☆☆☆。客户端界面经 Servo 壳承载（登录、商店、库列表），游戏本体的 Windows 版走 Wine 属长期攻坚项（反作弊是硬门槛），当前判例只承诺商店与社区浏览，游戏运行明确标注"兜底级——切 Windows 域"。这条诚实标注是星卡制度的自我要求：宁缺勿谎。

### 18.3 开发者移植三级火箭

面向想把软件带上 VARIX 的开发者（包括未来的我们自己），提供三级标准路径，每一级都比上一级更投入、也更彻底：

1. **第一级·直插**：软件有 Linux 版（无论闭源开源），打包进星图即可运行。成本最低，Linuxulator 托底。目标是把这一级覆盖到 60% 的常见软件。
2. **第二级·兼容**：只有 Windows 版的软件，走 Wine 判例流程：星卡建档 → 判例执行 → 缺陷归因（Wine 上游修/我们的垫片修/放弃）→ 评级定档。
3. **第三级·原生**：开源软件引导其上游增加 VARIX 后端（本质是 relibc/vx-SDK 目标三元组的移植），或我们自己维护构建脚本。原生级软件享受性能预算的全额配额。

三级火箭的入口统一是星图的开发者门户：一份《移植手册》（MD2 篇 10 细化）、vx-SDK 下载、判例自测脚本包。

### 18.4 上游关系协议（只用不改的运营侧）

第 6 章定了"借力不自研"的工程侧规矩，本章补运营侧四条：

1. **版本锁定表公开**：Wine、Servo、Mesa、relibc、smoltcp、rustls、cosmic-text、ext4 crate 各自的锁定版本号写进星图页面，用户与开发者随时可查"我们站在谁的哪个版本上"。
2. **季度升级窗**：每年 1/4/7/10 月为上游升级窗口，窗口内完成升级评估、回归测试与星卡批量复评；窗口外锁死版本，禁止顺手升级。
3. **修改需立案**：若某上游库必须改动才能用（预期极少发生），必须先立"上游修改案"（Fork Proposal）说明为什么不能在 VARIX 侧包垫片解决；批准后的修改独立成 patch 集维护，禁止直接改源码树内副本。
4. **回馈义务**：我们的垫片若发现上游缺陷，向上游提交 issue 是义务不是可选项；patch 能上游的上游，减少长期分叉。

### 18.5 星图的形态

星图既是目录也是门户：VARIX 桌面上的星图应用（原生构建）按评级分类展示软件，点击即启；数据文件是开放的 JSON 目录（开放性红线：数据不给用户上锁），支持离线更新包与在线刷新两种模式。星图里每个条目的"打开"按钮就是评级的一票否决权——兜底级的软件按钮会直接引导双域接力而不是假装能启动。

## 第 19 章 性能工程与预算（Performance Engineering）

性能不是调优出来的，是预算出来的。本章给 STAR I 全系统的性能预算表、测量方法与回归门。原则只有一条：**每个数字都要有测量脚本支撑，没有脚本的数字不许出现在预算表里。**

### 19.1 全系统预算表

| 预算项 | 目标值 | 硬约束来源 | 测量方式 |
| --- | --- | --- | --- |
| 冷启动到桌面 | ≤ 20s | U 盘 BOT 顺序读 ~35MB/s | 内核启动打点时间线 |
| 桌面空闲 CPU | ≤ 单核 5% | 软渲染成本 + 笔记本风扇噪音 | 合成器自报 + 外部观察 |
| 桌面空闲内存 | ≤ 1.5GB | 给 Wine/Electron 留 2.5GB | 内核内存账本 |
| 窗口拖动帧率 | ≥ 55fps | 软渲染 1080p | 合成器帧计时 |
| 应用切换延迟 | ≤ 300ms | 交互手感红线（宪章第八章） | VXWM 消息时间戳 |
| VSCode 冷启动 | ≤ 15s | BOT 读放大 + 装载预取 | 星卡实测 |
| VSCode 内存峰值 | ≤ 1.1GB | 预算配额（见 19.3） | 进程账本 |
| 端到端音频延迟 | ≤ 40ms | 手感红线 | 混音器打点 |
| 键入回显延迟 | ≤ 16ms | 一帧之内 | 输入链路打点 |
| TCP 吞吐（有线） | ≥ 700Mbps | 千兆线速 | iperf 等价物 |
| 元数据写吞吐 | ≥ BOT 极限 80% | 写合并有效性 | 存储基准 |
| syscal 转译开销 | ≤ 2μs/次 | Linuxulator 对标 | 柜台微基准 |

### 19.2 测量基建：vxbench

预算表里每一个数字对应 vxbench 的一条测量用例。vxbench 分三层：内核打点（启动时间线、内存账本、帧计时）、微基准（syscall 往返、页分配、上下文切换）、整机场景（冷启动、应用切换、多开组合）。每日构建自动跑全套，历史数据落 ext4 时序文件，偏差超过基线 10% 的项自动标红并阻断合入——性能回归与功能缺陷同罪。

### 19.3 内存配额治理

U 盘整机 + 软渲染意味着内存是第一稀缺资源，预算之外再配额：

| 配额项 | 上限 | 超限行为 |
| --- | --- | --- |
| 合成器 | 512MB（含表面缓冲记账） | 拒绝新表面并提示 |
| Wine 会话整体 | 2GB | 新进程按页限额降速 |
| 单个原生应用 | 1GB | 默认值，星卡可申请上调 |
| 磁盘缓存 | 512MB 自适应 | 内存紧张时收缩 |
| 内核本体 | 256MB 硬顶 | 超限即 bug，不妥协 |

### 19.4 启动时序预算分解

冷启动 20 秒的预算拆到每一段（U 盘 BOT 是全链条的物理下限，预算按最差 U 盘写）：

| 阶段 | 预算 | 内容 |
| --- | --- | --- |
| 固件自检 | 4s | 联想固件，不可控，实测计入 |
| Limine 引导 | 2s | 菜单 5s 超时可按任意键跳过 |
| 内核与驱动 | 4s | 页表、USB、块设备、四板斧校验 |
| 根文件系统就绪 | 3s | ext4 挂载、日志重放检查 |
| 会话拉起 | 5s | init 启动表、合成器、输入、混音器 |
| 桌面首帧 | 2s | 壁纸、任务栏、星图托起 |

每段都有独立打点，哪段超标哪段负责，不许"总体 20 秒"糊弄账。

### 19.5 回归门与预算变更程序

预算数字不是一成不变的，但改预算等于改宪法条款：任何预算项的调整必须走 ADR 程序，附测量数据与影响面分析。日常施工中，"实测达标"是合入判据之一（20 维度第 7 项），预算表就是验收时对答案的那张卷子。

## 第 20 章 STAR I start 预告（远期航图）

STAR I 的终点是 60 万行、四阶段判据全绿、一部 U 盘装下的完整日用系统。但 STAR 是一个系列，本章把 STAR I 主动不做的事、留给下一代的路，白纸黑字记下来——既防止 STAR I 阶段被远期诱惑带偏，也保证今天的每个决策没有把明天的路堵死。

### 20.1 GPU 硬加速（R3 攻坚线的终局）

STAR I 用 llvmpipe 类软渲染保底，STAR I start 的第一目标是真 GPU：Y7000 的 Intel UHD 630 核显走 Mesa iris 驱动路线（借力清单成员），Vulkan 化合成器替换 CPU 合成路径，预算全面改写——窗口拖动从"55fps 勉强及格"变成"144Hz 绰绰有余"，llvmpipe 退役为无 GPU 机器的回退路径。这条线在 STAR I 里只做两件事：合成器提交后端抽象化（保证未来可替换）、R3 阶段的可行性与驱动清单摸底。不提前写一行 GPU 代码——软渲染没达标的合成器，换 GPU 也救不回来。

### 20.2 vx-pkg 与应用商店

STAR I 的星图是"目录"，STAR I start 升格为"商店"：在线仓库、增量更新、签名分发、评分与评论。配套的包格式 vxapp 从"清单文件"升级为"带签名的分发单元"。STAR I 已为此留位：vxapp.toml 的字段设计与星图 JSON 目录的 schema 都按商店形态预留了扩展区。

### 20.3 双域接力的深度联动

STAR I 的双域接力是"重启 + 交接画面 + 交接分区小文件"。STAR I start 的目标是把这条通道修成高速路：剪贴板自动随行（切换时自动带过去）、文件级接力（VARIX 侧标记"待办文件"由 Windows 侧接力打开）、Windows 域无人值守化（开机自动进 Windows、自动拉起 Variable、完成后自动回写交接分区）。前提是 STAR I 把交接协议的可靠性判据全部走绿——高速路修在稳地基上。

### 20.4 远期航向（只立题目，不做承诺）

以下条目仅作为 STAR 系列的远景登记，任何一条都不构成 STAR I 的范围：多机型适配（Y7000 之外的硬件矩阵）、ARM 版本、多用户与账户体系、云同步（星图收藏与设置漫游）、Wine-Proton 分支评测（游戏专项）、自研窗口协议 VXWM 的对外标准化。远景每季度审视一次，有硬件或生态契机才立项，永远不为"功能多"而加功能。

## 第 21 章 全链路场景走查（一个真实的一天）

前二十章是解剖图，本章是活体观察：把一部装好 STAR I 的 thinkplus U 盘插进 Y7000，跟随一位真实用户从按下电源到深夜合盖，逐步走完所有关键路径。每个场景都标注"这一步站在哪些子系统和判据上"——它既是设计推演，也是 MD3 验收时的走查脚本母本（20 维度第 20 项"整体感受"的实体化）。

### 21.1 场景一：开机与域选择

按下电源，联想固件自检约四秒（这段谁也改不了，预算里如实计入），随后 Limine 接管，显示引导菜单：默认条目 VARIX，第二项"Windows 11 (USB)"，五秒倒计时。用户什么都不按，倒计时归零，VARIX 内核开始加载——打点时间线在内核日志里留下第一条记录。二十秒内，桌面首帧出现：壁纸、任务栏、星图托起，输入法图标就位。

这一步的守卫：启动时序预算（19.4）逐段打点；引导菜单的两条目对应 limine.conf 的两项配置，Windows 条目指向 WINESP 分区的引导文件——它的存在性由防自锁闸门在每次 VARIX 启动时校验，目标丢失则菜单上灰显并给出修复提示，而不是让用户在黑屏里猜。

如果用户要进 Windows 域，路径有两条：开机在 Limine 菜单直接选，或者在 VARIX 里走交接流程（场景五）。两条路殊途同归到同一个引导目标，这是"接力式双域"的对称性。

### 21.2 场景二：桌面初见与第一件事

用户第一次进桌面，看到的是空态引导而不是荒地（宪章第十一章）：星图窗口自动托起，展示"五个评级"的入口和首批软件列表；任务栏上有终端、文件、星图、设置的常驻图标；设置中心首页是三件事——网络、显示、关于本机。用户用拼音输入法在星图搜索框打出"code"，VSCode 的星卡弹出：直插级 ★★★★☆，冷启动实测 14.2 秒，判例 SC-001 至 SC-014 全绿。星卡是诚实的：它不吹"完美兼容"，它给的是实测数字。

这一步的守卫：星图目录 JSON 的开放格式（18.5）；空态引导只出现一次、可跳过可找回（宪章第十一章）；IME 首候选 ≤ 100ms（17.6）。

### 21.3 场景三：在 VARIX 里写代码

用户点开 VSCode——冷启动十五秒内出窗口（BOT 预取缓存第二次启动减半）。编辑、保存到 /home/projects/，内置终端里跑 git push——这条链路横跨五个子系统：进程装载器拉起 Electron（17.2）、窗口经 Wayland 桥进 VXWM（17.1）、文件落在 DATA 分区 ext4（17.3）、git 的网络调用被转译柜台改名直通到 smoltcp（17.4）、TLS 由 rustls 完成。任何一环超时，错误呈现三要素（宪章第九章）告诉用户发生了什么、为什么、下一步。

这一步的守卫：VSCode 冷启动 ≤ 15s、内存峰值 ≤ 1.1GB（19.1 预算表）；syscall 转译开销 ≤ 2μs；写合并让编辑器的频繁小保存不拖慢 U 盘（17.3）。

### 21.4 场景四：打开一个 Windows 软件

用户要解压一个 Windows 朋友发来的 rar。星图显示 7-Zip：兼容级 ★★★☆☆。点开，Wine 会话若未运行则冷起（wineserver 单例拉起，约三秒），7-Zip 窗口以 Windows 观感出现——标题栏是 VARIX 合成器的统一装饰，内容区是 Wine 渲染的 Win32 界面。解压 4GB 文件，进度条诚实移动，写合并层把零散小写合并成 BOT 喜欢的顺序大写。完成后用户把文件拖进文件管理器——跨 Wine/原生窗口的拖放由 VXWM 显式转发（17.1），没有"拖到一半消失"这种事故。

这一步的守卫：判例 5 章补的 Wine 判例流程；wineserver 看门狗（17.2）；跨表面拖放协议；星卡预期管理（它就是 Windows 软件的样子，不假装是原生的）。

### 21.5 场景五：交接去 Windows 域

用户要玩一个只有 Windows 版的游戏（判例 19 的诚实边界）。点任务栏"切换到 Windows"，交接流程启动：第一步，会话保全——VSCode 未保存文件进草稿、剪贴板写入交接分区（判例 12）、窗口清单快照；第二步，存储冲刷——ext4 日志落盘完成是硬前置，进度条显示"正在安全保存"；第三步，闸门校验——交接目标（WINESP 引导链）签名验证通过，防自锁闸门放行；第四步，写 OneShot 变量、显示交接画面（进度与"正在切换"的明确文案，不留黑箱等待）；第五步，重启，Limine 读到 OneShot，单次链载 Windows，变量作废。Windows 起来后 Variable 自动启动，弹出"来自 VARIX 的剪贴板"提示。

这一步的守卫：4.4 状态保全、4.5 时序预算（全程目标 ≤ 25 秒）、4.6 视觉接力（全程有画面无黑箱）、防自锁闸门（Boot2001 的教训在代码里 permanently 站岗）。

### 21.6 场景六：从 Windows 回 VARIX

游戏结束，用户在 Variable 侧边栏点"重启到 VARIX"：同样的保全-冲刷-闸门-写变量-重启流程反向执行。VARIX 起来后，会话恢复提示出现："上次会话：VSCode（2 个窗口）、7-Zip——恢复吗？"用户点恢复，窗口布局回位，草稿文件重新打开。一天的工作在两个域之间接了两次力，没有丢一个字节。

这一步的守卫：交接协议的对称性（VARIX→Windows 与 Windows→VARIX 用同一张状态保全 schema）；12 章补的 Variable 迁移细节。

### 21.7 场景七：异常路径（乱来的一天）

用户开始乱来——这是走查的意义。合成器被杀：三秒内看门狗拉起，窗口回位（D-04）。wineserver 被杀：五秒重建，7-Zip 恢复（P-03）。U 盘运行中被直接拔出：一秒内保护屏接管（判例 17），不假运行。断电重来：ext4 日志重放，20 次抽测无损坏（17.3 验收）。狂点关机：第二次点击显示"正在保存，请稍候"，防抖不重复提交（宪章第三章）。整夜挂机：空闲 CPU 5% 以内，风扇安静，内存配额无泄漏（19.3）。

### 21.8 走查结论模板

每个场景的走查结果按"顺畅 / 卡顿 / 无反馈 / 被打断 / 报错"五档记录（体验日志同构），阻断级问题不修完不交付。本章场景一至七的步骤表直接成为 MD3 验收协议的走查脚本——设计推演和验收脚本同源，中间不许出现"两个版本的事实"。

## 第 23 章 Wine 支架工程细则（决策级）

兼容腿的中坚是 Wine——约五百万行的上游资产，VARIX 对它的正确姿势是"搭好舞台，不改剧本"。本章定义舞台的每一块板子：版本、前缀、路径、显示、字体、禁区。字段级细节（注册表键值全表、DLL 覆盖清单）下沉 MD2 篇 9。

### 23.1 版本锁定与升级纪律

STAR I 锁定 Wine 10.x 稳定分支（具体小版本在 MD2 篇 9 的版本锁定表登记）。锁定理由：Wine 每个次要版本都可能改变行为面，兼容判例是在特定版本上验证的，版本漂移等于判例作废。升级走季度窗口（18.4）：升级窗口内完成全量判例回归，星卡批量复评，回归失败则整批回滚——绝不"先升了再说"。

### 23.2 Wine 前缀（prefix）管理

每个 Windows 应用一个独立前缀（WINEPREFIX），前缀内含虚拟 C 盘、注册表、DLL 状态。规则三条：其一，前缀根统一放在 /home/wine/〈应用名〉，随 DATA 分区走，备份与迁移天然成立；其二，前缀创建模板化——由 Wine 会话服务按模板生成（统一 Windows 版本伪装值、统一字体注入、统一环境变量），禁止应用自建前缀各自为政；其三，前缀损坏的恢复路径是"重建前缀 + 应用重装"，星卡上明示，不做前缀内手术（手术成本高于重建）。

### 23.3 路径与盘符映射

虚拟 C: 映射到前缀内部；D: 映射到 DATA 分区（用户文件交换区）；NTFS 只读分区呈现为 W:（只读盘，判例 C-6 在 Wine 侧同样生效）。路径映射由会话服务统一注入，应用不许私改。Unix 路径与 Windows 路径的转换由 Wine 自带机制承担，VARIX 不发明第二套。

### 23.4 显示与输入垫片

Wine 侧显示走其 Wayland 驱动，经 vx-wayland-bridge 进 VXWM（17.1 已述）。已知要做的三件垫片事：其一，窗口装饰统一——Wine 应用标题栏由 VARIX 合成器统一绘制，应用内自绘标题栏的（少数）允许但记录星卡；其二，光标管理统一——Wine 应用的自定义光标经协议上报，合成器渲染，杜绝双光标；其三，DPI 一致——Wine 的 DPI 虚拟值与 VARIX 缩放因子绑定，设置中心改缩放，Wine 窗口跟随。

### 23.5 字体与文本渲染

Windows 软件默认期待宋体/微软雅黑。VARIX 不内置这两者的商业字体，策略是开源替代：字体注入表把宋体/雅黑名映射到开源等价物（思源系列等，随 VARIXSYS 分发），映射表公开可改。文字渲染的最终整形仍走 cosmic-text 一致管线（17.1），保证 Wine 与原生应用的中文观感统一。

### 23.6 Wine 禁区清单（不做的事）

1. 不做 Wine 源码修改——缺陷向上游报告，垫片在 VARIX 侧。
2. 不承诺 Direct3D 重度游戏（内核级反作弊与 D3D12 重度依赖均在禁区，判例 19）。
3. 不做每个应用独立 Wine 版本（前缀模板统一，版本全局一致）。
4. 不承诺打印机、扫描仪在 Wine 内工作（外设长尾走 Windows 域，判例 20）。
5. 不做 .NET Framework 全家桶自动安装承诺——Wine-Mono 随模板提供，覆盖不到的应用星卡如实标注。

### 23.7 验收判据

7-Zip、记事本级 Win32 应用判例全绿；音频出声延迟 ≤ 40ms（17.5）；Wine 应用窗口的浮层出路符合宪章（合成器物理强制，见 17.1）；wineserver 崩溃恢复 ≤ 5s（17.2）；前缀重建时间 ≤ 3 分钟（模板化收益）。

## 第 24 章 Linux 直插细则（Linuxulator 决策级）

直插级是覆盖面最大的一腿——理论上任何官方 Linux 版软件都该"解包即跑"。这一章定义柜台侧的关键决策：装什么、怎么装、哪里有墙。方法论对标 FreeBSD Linuxulator 与 WSL1：实现思路自研（不碰 Linux 内核源码，GPL 立场见第 10 章），语义对齐 Linux 用户态约定。

### 24.1 直插的两类形态

**静态链接类**（Go/Rust 编译的 CLI 工具等）：最省事，无依赖树，装载即跑。柜台只需核心 syscall 面（文件、内存、进程、时间、信号）。**动态链接类**（Electron、Java、Python 等绝大多数）：需要 Linux 用户态世界——动态链接器、libc、共享库树。策略是"自带世界"：应用以包形式带来它需要的库（deb/rpm 包解开，或官方 tarball），装进 /compat/linux/〈应用名〉/ 独立目录，按应用隔离加载路径。不做全局共享库树（版本地狱），做每应用封闭依赖。

### 24.2 vxrun 启动包装

直插级应用的启动入口统一是 vxrun：它做四件事——设置隔离视图（/compat 树挂载为应用的 /）、注入会话环境变量（代理、主题、语言，判例 14）、注册到 Linuxulator 的 ABI 引导表（ELF 解释器指向 compat 树的 ld-linux）、拉起进程交给装载器（17.2）。vxrun 是薄壳，星图条目的启动命令都经它走。

### 24.3 伪文件系统面

Linux 应用期待 /proc、/sys、/dev 的存在。STAR I 的实现深度分级：/proc 的常用子集（self、cpuinfo、meminfo、 mounts）真实生成，数据来自内核账本；/sys 提供设备枚举所需的最小集；/dev 提供 null/zero/random/urandom/shm。明确不做：cgroup、systemd 相关面、io_uring（syscall 转译层返回 ENOSYS，见 MD2 篇 4 的差异表）。伪文件系统是"够用的假象"，每一项都登记在案，应用依赖了没实现的面时给出明确错误而不是诡异死法。

### 24.4 已知高墙（诚实清单）

| 高墙 | 原因 | 处置 |
| --- | --- | --- |
| systemd 依赖 | init 生态强耦合 | 拒绝运行，星卡标注"需 systemd，不支持" |
| io_uring 重度用户 | 异步 IO 语义深 | ENOSYS + 退化路径提示 |
| Linux 内核模块依赖 | 物理不可能 | 拒绝 |
| Docker/容器运行时 | 依赖 namespace/cgroup 全家 | 阶段外，星卡标注 |
| 特定 glibc 新符号 | 锁定世界内无此符号 | 提示缺符号名，引导带兼容库版本 |

高墙清单是星卡评级的输入之一：撞墙的应用不得评直插级，如实降级或标注。

### 24.5 Electron 专项（VSCode 级）

Electron 类是直插级的旗舰场景，专项保障：软件渲染路径验证（llvmpipe 下的 Chromium 绘制面）、沙箱降级（Electron 的 namespace 沙箱不可用，退化为单进程内沙箱开关 + 系统级 W^X 兜底，安全影响评估记入第 10 章威胁模型）、输入法对接（合成器层 IME，判例 11 同源）、字体走系统字体注入。VSCode 是这一项的验收载体，判例 SC-001 至 SC-014。

### 24.6 验收判据

静态类 20 个常用 CLI 工具全绿；动态类以 VSCode、一个 Java 运行时、一个 Python 运行时为验收载体；转译开销 ≤ 2μs（19.1）；compat 树磁盘占用单应用 ≤ 800MB（Electron 级）；伪文件系统缺口全部有登记、有明确报错。

## 第 25 章 会话与服务全景（谁在什么时候活着）

第 17 章讲了六个器官，本章讲它们的作息表：从内核把控制权交给用户态那一刻起，什么东西按什么顺序活起来、谁依赖谁、会话怎么结束。这是 P-2"PID 1 极简主义"的展开章。

### 25.1 启动表（静态 JSON，顺序即依赖）

| 序 | 服务 | 依赖 | 失败策略 | 说明 |
| --- | --- | --- | --- | --- |
| 1 | vx-init | 内核 | — | PID 1，只做拉起与监督 |
| 2 | 设备就绪服务 | 内核驱动 | 重试 1 次后降级 | 块设备、HDA、网卡枚举完成信号 |
| 3 | 存储挂载 | 2 | 阻断（转保护屏） | ext4 挂载、日志重放、交接分区就位 |
| 4 | 体验日志服务 | 3 | 静默降级（内存缓冲） | 宪章第十三章的落点，异步批量写 |
| 5 | 合成器 | 3 | 重试 3 次→恢复界面 | 窗口面的主人 |
| 6 | 输入子系统 | 5 | 重试后降级鼠标 | 含 IME 模块 |
| 7 | 混音器 | 3 | 静默降级（无声） | 音频缺席不阻断桌面 |
| 8 | 网络服务 | 2 | 静默降级（离线） | DHCP/链路、DNS 缓存 |
| 9 | 兼容柜台 | 3 | 阻断兼容腿仅 | Linuxulator 服务与 vxrun 注册 |
| 10 | Wine 会话服务 | 5,9 | 惰性启动 | 首个 Wine 应用点击时拉起 |
| 11 | 会话管理 | 5-10 | — | 环境注入、恢复提示、交接入口 |

设计原则显式化：**桌面永远比服务重要**。音频坏了桌面照开（图标灰显 + 提示），网络坏了桌面照开（离线态明确标注），唯独存储挂不起来才转全屏保护——因为那意味着任何后续动作都在制造损坏。

### 25.2 会话生命周期

U 盘整机没有"登录"概念：上电即会话，会话即用户。会话的开始 = 启动表走完 + 桌面首帧；会话的三种结束路径各有严格语义：

1. **交接结束（切域）**：21.5 全流程——保全、冲刷、闸门、OneShot、重启。唯一允许的"重启"路径。
2. **关机结束**：保全 → 冲刷 → 写"上次会话"快照 → 断电提示用户可安全拔电（U 盘系统没有电源控制权，关机的终点是"可以拔了"的画面，这是双域接力之外的诚实设计）。
3. **崩溃结束**：见第 26 章，内核 panic 的保护屏路径。

"重启到 VARIX"（Windows 域发起）本质是路径 1 的反向，同 schema。

### 25.3 服务监督（supervision）

vx-init 对每个服务的监督策略是三态：必需（挂了拖垮会话，如存储）、可降级（挂了带提示继续，如音频）、惰性（用时才拉，如 Wine 会话）。没有任何服务是"自动重启无限次"——无限重启是 Boot2001 式自锁的会话版，同样被禁止：连续三次失败进入降级态，降级态的恢复入口在设置中心"服务"页，用户可见可控（宪章第十二章：占用与状态透明）。

### 25.4 会话快照 schema（概要级）

快照存交接分区（FAT，跨域可读），字段概要：版本号、时间戳、来源域、窗口清单（应用 id/标题/几何/工作区）、草稿引用（文件路径 + 哈希）、剪贴板引用（文本内容或文件指针）、恢复标记。schema 带版本号向前兼容——STAR I start 的深度联动（20.3）靠它扩展，字段级定义在 MD2 篇 2。

## 第 26 章 崩溃与恢复全书（错误的每一种归宿）

健壮性不是"不崩"，是"崩得明白、恢复得干净"。本章给全系统每个可崩之物的崩溃语义与恢复路径——20 维度第 10 项（健壮性）与第 17 项（错误与恢复）的实现总纲。

### 26.1 崩溃分类学与恢复矩阵

| 层 | 崩溃物 | 表现 | 恢复路径 | 用户所见 |
| --- | --- | --- | --- | --- |
| 内核 | panic | 全停 | 保护屏 → 自动重启 → 引导进 VARIX 恢复会话 | 红色保护屏 + 三要素文案 + 重启倒计时 |
| 系统服务 | 合成器崩 | 画面冻结 | 看门狗 3s 拉起，表面缓冲在共享内存，窗口回位 | 闪一下，"桌面已恢复"轻提示 |
| 系统服务 | 输入/混音/网络崩 | 对应功能失效 | 三次重试→降级态 | 图标灰显 + 设置中心可查可重启 |
| 兼容层 | wineserver 崩 | Wine 应用失联 | 5s 重建 + 逐应用恢复 | "Windows 兼容环境已恢复" |
| 应用 | 原生应用崩 | 单窗口消失 | 崩溃报告（三要素 + 详情折叠）→ 可重开 | 对话框，不是沉默消失 |
| 应用 | Wine 应用崩 | 同上 | 同上，经 Wine 异常翻译 | 同上 |
| 应用 | Electron 主进程崩 | 窗口白屏 | 重开即恢复，草稿由应用自保 | VSCode 自身的恢复机制直插可用 |
| 存储 | ext4 检测到不一致 | 挂载告警 | 日志重放 → 重放失败转只读模式 | 顶栏黄条："已进入只读保护" |
| 存储 | U 盘失联 | 全系统失去根 | 保护屏冻结（判例 17） | "存储已移除"全屏接管 |

设计通则：**越底层的崩溃，用户看到的越少、恢复的越自动；越上层的崩溃，越尊重用户的知情权。**内核 panic 一屏说明加自动重启；应用崩溃要给用户选择（重开/放弃/查看详情）。

### 26.2 崩溃报告的三要素与详情折叠

每份崩溃报告（无论哪层）必有：发生了什么（人话："星图停止响应了"）、为什么（归因分类：内存超限/协议违规/未知缺陷/上游缺陷）、下一步（重开/恢复会话/上报）。技术细节——寄存器、调用栈、日志尾部——收进"详情"折叠区，可复制可导出到 DATA/crash/。崩溃报告自动并入体验日志的"报错"事件流（宪章第十三章），Top 挫败点进入月度施工单（16.3）。

### 26.3 内核 panic 保护屏规范

panic 保护屏是 VARIX 的"蓝屏"，规范五条：深色底 + 单色警示图（不用惊吓性红蓝爆闪）；文案三要素（"系统遇到无法继续的错误——正在保存现场""原因分类：〈分类〉""将在 10 秒后自动重启，未保存内容已尽力保全"）；倒计时可按键跳过；重启走防自锁闸门校验过的正常引导链；现场信息（panic 类型、模块、时间）写保护分区内存带（重启后可查）。

### 26.4 防自锁的会话级延伸

第 4 章的防自锁闸门防的是"引导层无限重启"；本章把同一哲学延伸到会话层：任何自动恢复路径都不允许形成"崩→自动重启→再崩"的循环——三次即止，转降级或转人工（恢复界面给出诊断步骤）。这一条写进所有看门狗的验收判据。

### 26.5 恢复演练制度

每一行恢复代码都必须有对应的"杀死演练"：合成器杀 100 次、wineserver 杀 100 次、断电 20 次、U 盘拔出 20 次、panic 注入 20 次——全部通过才算健壮性验收（MD3 对应工作包的判据）。恢复代码没有演练等于没写。

## 第 27 章 国际化与文案系统（先说人话，再谈多语）

VARIX 的第一语言是简体中文——这不是权宜，是定位：这是给 Variable 自己用、也面向中文用户的 U 盘整机系统。国际化架构为未来的多语留门，但 STAR I 只交付简体中文，把一门语言做到零瑕疵，好过十门语言各自半吊子。

### 27.1 文案系统的三层架构

第一层是字符串表：所有界面文案不允许硬编码在代码里，一律经 `vx-str()` 取自字符串表（JSON，随语言包加载）；键名按"界面.元素.状态"三级命名，全局唯一，重复键在构建期报错。第二层是文案规范（宪章第十三章的落地面）：错误消息三要素模板（发生了什么/为什么/下一步）、标点全角统一、数字与单位空格规则、术语表绑定（"切换域"不写成"切换系统"）、禁用词表（"可能"、"大概"、"似乎"不进界面——界面上要么确定要么不说）。第三层是文案评审：每个应用交付前文案全量走查（20 维度第 13 项），走查记录进星卡或发布检查单。

### 27.2 中文排版的工程底线

中文不是英文的替换品，有自己的排版学：混排时中西文之间自动加四分之一空宽（cosmic-text 支持，全局开启）；标点悬挂与避头尾规则交给排版库统一处理；等宽场景（终端、代码）中文按两格计宽，混排对齐不错位——这条在终端模拟器与编辑器里是高频坑，专项判例把关。字体链固定：界面默认思源黑体（VARIXSYS 分发），等宽场景 JetBrains Mono 开源等价物 + 中文回退，字体清单公开可换。

### 27.3 多语预留与不做清单

字符串表天然支持多语包（键值分离），架构上多语零障碍；但 STAR I 明确不做：英文界面包、输入法多语（只做拼音）、时区/locale 完整抽象。原因直白：每多一门语言，文案走查、字体覆盖、日期格式、排序规则的验收面翻倍，而这些人力在 STAR I 有更高价值的去处（兼容判例、体验打磨）。预留的门口是干净的：将来加语言包，不需要动任何代码，只需要加文件和走验收。

### 27.4 文案与体验日志的联动

文案缺陷是最高频的体验杀手（"重试失败请重试"这种循环话术）。体验日志对文案类挫败信号单独建分类：同一错误文案被用户连续遇到三次以上，自动进入"文案复检"清单——这句话要么说错了，要么这个错误根本不该发生三次。文案不是写完就完，是要被运营的。

### 28.2 去留的三条裁决原则

### 28.3 36 万到 60 万的缺口地图

按本名册推演，STAR I 终态 60 万行的构成大致是：现有 36 万（内核与既有资产）+ 新增原生应用与框架约 10 万 + 兼容层支架与转译层约 8 万 + 体验与测试资产约 6 万——增量 24 万行的分布与 MD3 工作包一一对应，工程量的账在 MD3 第 1 章对总账。

## 第 29 章 路线对比终审（我们不走的那几条路）

一个工程的可信度，不在于它说"我们选了 A"，而在于它能把 B、C、D 逐条摆出来并说清为什么不选。本章是路线选择的终审记录——讨论中出现过的每一条岔路都留档，防止三年后有人（包括我们自己）再把老路当新路提出来。

### 29.1 为什么不是虚拟机方案

在 VARIX 里跑一个虚拟机、虚拟机里装 Windows，软件就能"全兼容"。否决理由四条：其一，体验断裂——用户的软件跑在"系统里的系统"里，窗口、剪贴板、文件、快捷键全隔一层，违背"像 Windows 里一样原生打开"的立项原点；其二，性能双重税——软渲染的合成器再叠一层虚拟化，U 盘 IO 再被两套系统分抢，Y7000 的内存对半劈；其三，依赖反转——VARIX 会从"操作系统"退化成"虚拟机管理器"，自研内核的存在意义被架空；其四，Windows 许可——虚拟机内仍是完整 Windows，授权与激活一样不少，成本没有省。虚拟机方案唯一的价值场景是开发期调试（QEMU 测试内核），那是工具不是产品路线。

### 29.2 为什么不是改 Linux 内核

拿 Linux 内核裁剪定制（像发行版那样），兼容性白送。否决理由三条：其一，许可本质——GPL 传染性会迫使 VARIX 内核整体开源或被迫混淆回避，而我们明确选择不碰 Linux 代码、走 FreeBSD Linuxulator 与 WSL1 的方法论路线（第 10 章立场），这条红线不破；其二，体量失控——Linux 的可裁剪是出了名的难，"只留需要的"最终总是"留了大部分"，60 万行的阶梯目标会被一举击穿；其三，学习资产的错位——VARIX 的立身之本是"我们亲手理解每一行"，裁剪 Linux 得到的是别人的系统加我们的补丁，出错时两头都不懂。Linux 用户态世界（库、应用、约定）我们大量兼容，Linux 内核代码我们一行不抄。

### 29.3 为什么不是全自研

反面路径也审过：什么都不借，从 libc 到协议栈到浏览器全自己写。否决理由一句话：这会把 60 万行做成 600 万行还更差。Wine、Servo、Mesa、relibc、smoltcp、rustls、cosmic-text、ext4 crate——每一件都是十年级社区打磨过的资产，自研替代品在十年内不可能达到它们的健壮度。全自研的隐含假设是"上游不可信任"，而第 6 章的集成协议（版本锁定、季度窗口、修改立案、回馈义务）已经把信任问题工程化了。借力不是偷懒，是把自研的火力的集中在真正构成差异的地方：双域接力、窗口协议、转译柜台、体验宪章的落地。

### 29.4 为什么不是 Android 子系统 / WSA 类方案

Android 运行时能带来海量应用。否决理由：Android 应用生态与桌面软件生态几乎不相交（微信、游戏除外），而 STAR I 的目标软件面是生产力工具（编辑器、压缩、终端、Steam 库）；Android 运行时的体积（ART、AOSP 库）与 legality 复杂度远超收益；且其图形栈假设与 VARIX 软渲染现实冲突。留档即可，STAR 系列远期不排除重新评估。

### 29.5 终审结论表

| 岔路 | 裁决 | 一句话依据 |
| --- | --- | --- |
| 虚拟机装 Windows | 否 | 体验断裂 + 双重性能税 + 定位架空 |
| 裁剪 Linux 内核 | 否 | GPL 立场 + 体量失控 + 资产错位 |
| 全自研不借力 | 否 | 60 万行的野心装不下 600 万行的活 |
| Android 子系统 | 否（留档） | 生态错位 + 体积与图形栈不合 |
| Wine + Linuxulator + Servo 支架（选定） | 是 | 体验原生 + 许可干净 + 借力到位 |

此表与 ADR-001~010 互为表里：ADR 记"选了什么"，本章记"没选什么"。两份记录合起来才是完整的决策史。

## 第 31 章 红队百问（设计评审一百问）

把最刻薄的问题提前问完，好过上线后被现实问。本章是一百个红队问题与裁决——每个问题一句话裁决，裁决指向的章节即为依据。评审规则：任何新模块开工前，先把本章过一遍；百问之外的争议裁决后归档为第 101 问起的续编。

**引导与交接（10 问）**

**Q1：OneShot 变量写了但重启后固件没交给 Limine？** 闸门前置校验引导链完整性，交接画面显示"已请求切换"，失败时下次启动 VARIX 自动检测并提示重试——永不盲写。
**Q2：交接到一半断电？** 写变量是原子单步，重启后要么已写（进 Windows）要么没写（回 VARIX），无中间态；保全数据在断电前已冲刷。
**Q3：Windows 更新拆了我们的 BCD 防自愈闸？** 每次进 VARIX 校验闸值，被拆则交接入口提示一键重打（判例 18）。
**Q4：WINESP 分区 GUID 变了（重分区）？** 闸门按 GUID + 文件签名双因子校验，不符即拒绝交接并给出重配指引。
**Q5：Limine 菜单超时默认进错域？** 默认条目固定 VARIX，Windows 条目需显式选择或经交接流程，杜绝"不小心进了 Windows 丢了 VARIX 会话"。
**Q6：交接分区分区表损坏？** 快照 schema 带版本与校验和，读不出即放弃恢复并明示，不猜。
**Q7：NVRAM 写满（联想固件老毛病）？** 写前读余量，不足则清理过期条目（只清 VARIX 自建项），内置引导项永不碰（边界红线）。
**Q8：用户在固件里手动改了引导顺序？** 尊重用户——VARIX 每次启动不抢顺序，只保证自己可被选中；文档说明恢复方法。
**Q9：交接画面卡住不动超过 30 秒？** 交接流程每步带超时，超时打点上报并在下次会话首屏诊断提示。
**Q10：同一秒内两次交接请求？** 交接状态机互斥，第二次请求提示"正在交接中"（防抖，宪章第三章）。

**双域与 Variable（10 问）**

**Q11：Variable 在 Windows 域里改了交接分区文件？** schema 单写方原则：VARIX 写 VARIX 侧文件，Windows 助手写 Windows 侧文件，互不越界。
**Q12：用户在 Windows 域删了 Variable？** 回 VARIX 路径降级为 Limine 菜单选择，VARIX 启动时提示重装助手（链接与步骤）。
**Q13：剪贴板接力带走了密码？** 文本接力走用户确认弹窗，检测到来自密码管理器类窗口的复制默认不接力（隐私红线）。
**Q14：两个域的系统时间漂移？** 交接时同步时间戳到快照，VARIX 启动校准（RTC + 快照对照）。
**Q15：快照说恢复了 3 个窗口，应用已经卸载？** 恢复前逐项存在性校验，缺席项如实标注"已不存在"。
**Q16：U 盘插到第二台电脑？** 硬件矩阵变化触发驱动重枚举，用户目录不动；文档明示"整机系统换机需重走驱动摸底"。
**Q17：Windows 域蓝屏把引导搞乱？** VARIX 引导文件在 ESP 且 Windows 更新不触碰非默认条目（实机已验证）；恢复章（MD2 篇 12）提供修复介质步骤。
**Q18：Variable 大版本更新改变快照格式？** schema 版本号协商，旧格式兼容读、新格式降级写。
**Q19：用户想永久只用一个域？** 支持——设置里可关交接入口，菜单默认条目随之调整，尊重使用形态。
**Q20：接力过程中用户强制长按电源？** 等同 Q2 断电路径，无中间态承诺。

**兼容层（10 问）**

**Q21：Wine 应用把 C 盘写爆（前缀膨胀）？** 前缀配额监控，超限提示清理；磁盘满有 26 章 存储 保护屏兜底。
**Q22：Linux 应用 fork 炸弹？** 进程数配额（17.2），超限拒绝 fork 并报错，柜台不背锅。
**Q23：应用依赖我们 ENOSYS 的 syscall？** 明确报错指名 syscall 号与等价建议（24.4），星卡登记撞墙。
**Q24：两个 Wine 应用抢同一个 COM 口（串口感）？** 设备独占协调进 Wine 会话服务，后到者明确报"设备被占用"。
**Q25：Electron 沙箱退化后安全性？** W^X + 进程级隔离 + 来源分级（10 章补）兜底，威胁模型里明记此项残余风险。
**Q26：应用自带过老/过新 glibc？** 每应用封闭依赖树（24.1），互不污染；缺符号给出指名报错。
**Q27：Steam 登录页改版导致 Servo 渲染崩？** 星卡限期复评机制触发，归因分类"上游页面缺陷"，修复或降级。
**Q28：Wine 音频延迟突增？** 混音器打点定位（混音器侧/Wine 桥侧），判例复测。
**Q29：中文文件名在 Wine 应用乱码？** UTF-8 全链路统一 + 前缀模板注入 code page 映射，金丝雀判例 SC-053 把关。
**Q30：应用需要管理员权限（UAC）？** Wine 虚拟 UAC 默认拒绝提权到真实系统——兼容环境里没有"真管理员"可提。

**窗口与体验（10 问）**

**Q31：应用提交 4K×4K 表面 × 64 个，内存爆？** C-2 表面限额双层（数量与总面积），超限拒绝并提示。
**Q32：窗口拖到屏幕边缘一半卡住？** 拖拽路径全状态机化（宪章第五章），Esc 放弃复位。
**Q33：两个浮层抢焦点打架？** 合成器浮层栈唯一裁决，后开者置顶、先开者不失焦规则统一。
**Q34：用户狂点崩溃对话框？** 防抖 + 对话框自身永不崩（最小实现面）。
**Q35：IME 候选窗在 Wine 窗口边缘出屏？** 候选窗定位器带屏幕夹紧，永不出屏（判例 11 细则）。
**Q36：缩放 150% 下 Wine 应用模糊？** 字体与矢量 UI 按缩放渲染，位图类如实标注"该应用不支持缩放"。
**Q37：深色主题下 Wine 应用白块刺眼？** 主题垫片尽力（23.4），垫不到的如实呈现，不硬糊滤镜。
**Q38：任务栏图标太多挤爆？** 分区折叠 + 溢出菜单，交互词典统一行为。
**Q39：键盘用户够不到托盘图标？** 托盘全键盘可达（焦点环进托盘），宪章第四章判据。
**Q40：截图快捷键被应用抢占？** 系统级快捷键保留字表（17.6），应用注册冲突时拒绝并提示。

**存储与数据（10 问）**

**Q41：写合并 5 秒窗口内断电丢 5 秒数据？** 这是设计内的诚实取舍：丢的是"最近 5 秒的元数据"，结构永不损坏；文案如实告知（宪章第十二章）。
**Q42：ext4 crate 发现上游 bug？** 版本锁定 + 上游 issue 义务（18.4）+ 只读降级兜底。
**Q43：NTFS 只读挂载读到 BitLocker 加密盘？** 不支持解锁，明确提示在 Windows 域操作。
**Q44：DATA 分区满时正在保存？** 预检 + 保存对话框即时报剩余空间，失败不产生半文件（判例 16 同源）。
**Q45：回收站本身把盘占满？** 回收站配额 10% 自动清理最旧项，清理有提示。
**Q46：文件名含非法字符（Windows 视角）？** 接力时转换表清洗 + 提示，不静默改名。
**Q47：符号链接循环？** 遍历深度上限 + 循环检测，文件管理器与索引共用实现。
**Q48：U 盘寿命（TLB 磨损）？** 写合并本身就是寿命保护；SMART 直通监控，健康度进系统监视器。
**Q49：用户手动挂载了另一个 U 盘？** 热插只读挂载（ext4/FAT），写支持白名单制。
**Q50：镜像更新到一半断电？** vx-updater 双镜像校验（22.2），旧镜像完好可回滚。

**网络与安全（10 问）**

**Q51：恶意 Linux 应用扫端口？** 进程级网络权限表（10 章补），默认仅出站，监听需授权。
**Q52：Wine 应用下载 exe 自己运行？** 兼容环境内自洽运行可以，逃逸出前缀的执行请求一律拦截（安全边界=前缀边界）。
**Q53：DNS 被劫持？** hickory-dns 支持 DoH，设置中心可开；企业网环境如实降级明示。
**Q54：rustls 证书过期导致应用瘫痪？** 三要素报错 + 时间同步检查引导（Q14 关联）。
**Q55：星图 JSON 被篡改指向恶意条目？** 目录文件哈希校验，更新包签名。
**Q56：体验日志记了敏感内容？** 日志只记交互行为与结果，正文/密码不落盘（宪章第十三章红线），实现层用类型系统强制（敏感串类型不实现序列化）。
**Q57：调试串口/日志把内存全倒出来？** panic 现场信息白名单字段制，不做全量 dump 落盘。
**Q58：来路不明的 vxapp 包？** 来源三级（10 章补）：签名/白名单目录/用户双确认，第三级明示风险话术。
**Q59：USB 外设是恶意键盘（HID 注入）？** 阶段内不做防注入（硬件级攻击超出模型），威胁模型如实登记残余风险。
**Q60：Wi-Fi 固件加载失败拖垮启动？** 网络服务可降级原则（25.1），WiFi 失败不阻断桌面。

**性能与资源（10 问）**

**Q61：VSCode 开 50 个标签内存超配额？** 配额降速而非 OOM（19.3），应用自身有标签休眠。
**Q62：llvmpipe 在 4K 屏跑不动？** 1080p 为设计分辨率，4K 屏降档 + 明示（11 章硬件矩阵标注）。
**Q63：后台更新抢走前台 IO？** IO 调度优先级（前台类 > 后台类），BOT 队列归前台。
**Q64：启动时四板斧校验拖慢开机？** 校验并行化 + 预算内打点（19.4），超标即优化项。
**Q65：内存泄漏缓慢性累积？** 24 小时挂机零增长判据（22.3）+ 系统监视器可视化。
**Q66：瞬时大量 fork 拖垮装载器？** 进程表上限 + fork 风暴熔断（Q22 同源）。
**Q67：TCP 大量 TIME_WAIT 耗尽端口？** smoltcp 参数调优 + 判例复测，异常计数可视化。
**Q68：字体图集无限膨胀？** 图集 LRU 上限，汉字常用集常驻。
**Q69：日志把 U 盘写满？** 日志分级轮转（体验日志批量异步 + 总量上限，宪章第十三章代价红线）。
**Q70：一个应用把 CPU 打满，桌面卡？** 合成器线程优先级最高，应用再重也不掉帧——软渲染下的"保桌面"铁律。

**会话与恢复（10 问）**

**Q71：恢复会话后窗口位置乱（分辨率变了）？** 几何信息带屏幕指纹，不匹配则重排并告知。
**Q72：快照恢复一半失败？** 逐项恢复、逐项报告，成功项保留（25.4 原子性分层）。
**Q73：用户体验日志没开，出问题无据可查？** 日志默认开、可关；关时明示"诊断能力降级"。
**Q74：崩溃报告无限弹（连环崩）？** 同一应用 5 分钟内三次崩溃即静默收集 + 单次汇总提示。
**Q75：用户在保护屏期间拔盘？** 保护屏本就假设最坏情况，无附加损坏；重启自恢复。
**Q76：关机画面"可以拔电了"用户不拔？** 无害——已冲刷完成，停留即可。
**Q77：休眠（suspend）支持吗？** STAR I 明确不支持（U 盘整机 + 固件行为不可控），合盖即关机语义，明示。
**Q78：时钟不联网漂移几分钟能忍吗？** RTC 存在即够用；交接快照校准（Q14）；NTP 可选。
**Q79：恢复提示每天弹出烦人？** 恢复提示只在存在未恢复项时出现，且"今天不再问"选项（引导只出现一次原则）。
**Q80：会话快照含隐私（窗口标题）？** 标题可含敏感字串——快照落交接分区（本地），不出盘；设置可关标题记录。

**运营与生态（10 问）**

**Q81：星卡数据造假（自吹兼容）？** 判例脚本公开可复跑，星卡数字必须出自 vxbench，复跑不符即下架评级。
**Q82：上游 Wine 断代（项目停更）？** 版本锁定表使我们有完整的本地快照，短期无碍；长期走 Fork Proposal 程序（18.4）。
**Q83：用户装了星图外的 exe？** 允许（开放性红线），走来源三级确认，星卡无档案时明确提示"未评级软件"。

## 第 32 章 三文档阅读指南（怎么读这套书）

MD1/MD2/MD3 是一套书，不是三本散装文档。不同的人在不同的时刻只需要其中一块，本指南给四条阅读路径。

**路径一：决策者路径（Variable 本人，约 40 分钟）。** 只读 MD1：卷首语 → 第 1、2 章（是什么）→ 第 3、4 章（双域怎么转）→ 第 5 章（软件怎么覆盖）→ 第 7 章（分几步走）→ 第 13 章（风险）→ 附录 C（三文档关系）。其余章节备查不预读——决策者需要的是骨架与红线，不是每个字段。

**路径二：施工者路径（AI 或未来协作者，开工前 2 小时）。** 先 MD1 全文过一遍（宪法必须通读），再精读自己负责的工作包对应的 MD2 篇章（MD3 每个工作包标注了对应的 MD2 篇号），最后读 MD3 的第 4 章（泳道与节奏）和第 5 章（验收协议）。施工中随时回查 MD1 对应章节——本指南不配"速查卡"，因为 MD3 每包的"宪法锚点"字段已经把回查页码写死。

**路径三：评审者路径（未来可能出现的第二双眼睛，90 分钟）。** MD1 第 14 章（ADR）+ 第 29 章（路线终审）+ 第 31 章（红队百问）——这三章是全部关键决策的浓缩，读完即可质询任何一条路线；再按兴趣下钻 MD2。

**路径四：未来用户路径（ STAR I 交付之后）。** 用户不需要读任何 MD——他们读的是星图、设置中心的帮助与 36 章的用户手册。这套 MD 是工程宪法，不是说明书；说明书在系统里，跟着系统走。

三份文档的更新纪律已在 16.2 与附录 C 定死，此处只补一条人性化的：**任何一方的修订必须留下"为什么改"**——纯 diff 没有动机记录，半年后就是悬案。

## 第 33 章 里程碑判据与验收流程终版（判据 1-5 的完整展开）

第 7 章给过四阶段路线与五条总判据的名字，本章把它们展开成可执行的验收定义——每一判据的"通过"由谁、在什么机器上、按什么步骤判定。

### 33.1 五判据展开

**判据 1（阶段 1）——接力直通零盲区。** 判定步骤：实机连续 20 次交接（VARIX→Windows→VARIX 为一轮），全程无盲写、无未预期黑屏、无引导丢失；四板斧加固后 0xED 全程绝迹；防自锁闸门注入测试（人为破坏引导目标）20 次全部拒绝盲写。通过标准：20/20，0 例外。判定机器：联想 Y7000 + thinkplus 1TB（唯一权威环境）。

**判据 2（阶段 2）——桌面日用成立。** 判定：十二件套原生应用全部按 22.3 公共标准过验收；21 章场景一至四走查全"顺畅"；合成器/wineserver/断电/拔盘四类杀死演练全过（26.5）；19.1 预算表核心六项（启动、空闲 CPU、空闲内存、拖动帧率、切换延迟、键入回显）实测达标。

**判据 3（阶段 3）——兼容腿立住。** 判定：十二星卡首轮判例 100% 实跑完毕；VSCode 判例 SC-001~010 全绿且实测预算达标；Linux 静态/动态两类直插验收载体全过（24.6）；红队百问 Q21-Q30 复核无新增阻断。

**判据 4（阶段 4）——生态与发布成立。** 判定：星图目录与星卡制度运转一轮完整周期（含一次季度升级窗演练）；vx-updater 全流程（含断电回滚）实测；20 维度验收全表逐项打分 ≥ 标准线；第 9 章体验宪章十四章逐章走查全绿。

**判据 5（贯穿）——体验日日可用。** 阶段 2 起每周一次"真实一天"走查（按 21 章场景脚本），体验日志的挫败信号 Top3 必须进入下周施工单——这条判据不判"能不能用"，判"是不是一直好用"。

### 33.2 验收流程的五步仪式

任何判据的验收走同一套仪式：① 准备——把判据拆成检查单，逐项有测量方式；② 执行——按单实测，数据留档（vxbench 导出 + 走查记录）；③ 复核——第二天换时间复测关键项（防环境侥幸）；④ 裁决——全过则判据标记通过并 git tag（里程碑 tag：m1-handoff、m2-desktop、m3-compat、m4-release）；⑤ 归档——验收记录进 docs/acceptance/，失败项进 MD3 偏差专栏。五步缺一不可，"我觉得可以了"不构成第④步。

## 第 34 章 威胁场景推演十二例（安全章的实战面）

第 10 章补给了权限矩阵与脚本规范，本章换一个视角：假设十二个具体的"坏人或坏运气"场景，逐个推演系统的反应。威胁模型的正确用法不是列技术名词，是讲故事——每个故事都问"系统会怎么死、数据会怎么丢、用户会看到什么"。

**场景 1：捡到 U 盘的人。** 故事：U 盘丢失，陌生人插到自己电脑。推演：U 盘在他人 Windows 下显示 ESP/WINESP 两个 FAT 分区与不可读的 ext4 分区；交接分区内的快照含窗口标题（可关）与剪贴板残留——**这是真实暴露面**。处置：设置中心提供"交接快照随会话清除"开关（默认开），敏感用户可关标题记录（Q80）；文档明示 U 盘整机不是加密系统，机密数据请勿入盘。残余风险如实登记。

**场景 2：恶意 exe 被用户主动安装。** 故事：用户从网上下载了一个可疑软件装进 Wine。推演：它在 Wine 前缀内可为所欲为（前缀=它的世界），但出不了前缀（Q52）：读不到 DATA 之外的真实路径映射（D: 只映射到 DATA，用户确认后才可写）、碰不到内核、碰不到其他域。处置已在设计内；星图外的安装走来源三级确认（Q58）。

**场景 3：恶意 Linux 二进制。** 故事：用户 vxrun 了一个来路不明的 Linux ELF。推演：Linuxulator 柜台是它的全部 syscall 世界，未实现的 syscall 直接 ENOSYS；网络默认仅出站（Q51）；进程配额限制破坏力。它能看到什么取决于挂载视图（/compat 封闭树 + 授权路径）。

**场景 4：星图目录投毒。** 故事：更新包被中间人篡改，星图条目指向恶意载荷。推演：目录哈希校验 + 更新包签名（Q55），验签失败拒载并显示原目录；签名私钥离线保管。DNS 劫持路径被 DoH（Q53）与固定校验和双保险收窄。

**场景 5：USB 外设 BadUSB。** 故事：插上伪装键盘的设备瞬间打字执行命令。推演：HID 设备接入提示浮层（首次接入需确认），但已建立信任的设备无再确认——**残余风险如实登记**（Q59），硬件级防御（认证线缆等）超 STAR I 范围。

**场景 6：物理拆解/直读。** 故事：攻击者拆 U 盘直读闪存。推演：全盘未加密，ext4 内容可读。这是定位决定的：U 盘整机系统优先可用性与可修复性，加密（LUKS 类）列为 STAR I start 评估项，不在 STAR I 做半吊子。

**场景 7：固件级攻击（植入 BIOS）。** 故事：固件被预植恶意代码。推演：超出操作系统防御范围（固件在引导链上游），威胁模型如实标注"不在防御边界内"；边界红线（引导设施不可侵犯）同时禁止我们越权去"清理"固件。

**场景 8：Wine 应用提权幻觉。** 故事：Windows 恶意软件假装要 UAC 提权。推演：虚拟 UAC 无真权可提（Q30），弹窗明示"兼容环境无管理员概念"。

**场景 9：侧信道与键盘记录。** 故事：某个直插级应用试图全局键盘监听。推演：输入事件按焦点投递（C-8），无全局监听接口；体验日志只记"有键入"不记内容（Q56 同源）。全局热键走保留字表申请制。

**场景 10：网络内网攻击者。** 故事：同网段攻击者扫描 VARIX。推演：默认监听端口数为零（无 SSH 服务、无 SMB），出站为主；确需监听的服务逐个列在文档的"网络面清单"，每项带关闭开关。

**场景 11：供应链——上游库被投毒。** 故事：锁定的某个上游版本被发现含后门。推演：季度窗口的升级评估含上游安全公告核查；事件响应：版本回滚到上一锁定 + 星卡批量复评 + 公告。锁定制的最大价值此刻兑现：我们永远知道自己在用哪个精确版本。

**场景 12：内部威胁——我们自己的失误。** 故事：施工脚本写错路径删错文件。推演：脚本防呆（参数校验、遗言日志）+ 脚本只允许白名单路径 + DATA 用户区操作前二次确认（28.2 收编条款）；git 全量历史兜底代码级损失。最大的单一防线是过程透明（SOUL 红线）：静默吞错被制度性禁止。

十二个推演的共同结论：STAR I 的安全姿态是"**清晰的边界 + 诚实的残余风险**"——不吹不可破，只承诺每一层防什么、不防什么写在明处。

## 第 35 章 开发环境与工具链（造系统的车间）

写 VARIX 的每一行代码在哪里写、怎么构建、怎么测试、怎么上机——本章把车间布置定案。车间的质量决定出厂质量，这里的事故（构建产物不可复现、测试环境漂移）在工程后期是灾难性的。

### 35.1 构建链

主机端（Windows 11 + Rust 工具链）：`cargo build` 出内核 ELF → Limine 工具打包出 `varix.img`（build/ 已在产）→ 实机 dd/写盘工具落 U 盘。构建脚本以 `build-windows.bat` 为入口，逐步迁移为 `just`/`make` 类任务定义（保留 bat 兼容）。铁律：**构建可复现**——同源码同工具链必出同哈希镜像（Rust 锁定 toolchain 文件），发布镜像记录完整构建环境指纹。

### 35.2 三层测试环境

第一层 QEMU：日常开发的主战场——内核 panic、引导链、交接逻辑 90% 在 QEMU 里验证（OVMF + Limine 镜像直启），快照式回滚让"杀死演练"零成本；第二层实机 Y7000：阶段判据的权威环境，所有"实测达标"必须出自它；第三层冷备环境：一台旧笔记本（硬件矩阵 11 章的最低配样本），防"只在 Y7000 上才对"的过拟合。三层各司其职：QEMU 管逻辑正确，实机管体验成立，冷备管普适性。

### 35.3 实机部署与回滚流程

实机更新走 vx-updater 的同源流程（22.2）：新镜像校验落盘 → 保留上一版镜像 → 启动异常可从 Limine 菜单选回滚镜像。开发期另有快速通道：U 盘第二分区直写内核 ELF（免全镜像重建），仅限开发模式，发布流程禁用。

### 35.4 代码质量闸门

合入主干的每一行过四道闸：`cargo fmt`/`clippy` 零告警（风格与静态检查）；单测随码（内核核心模块行覆盖 ≥ 60%，转译层 ≥ 80%）；QEMU 冒烟套（启动到桌面首帧 + 20 个核心判例自动跑）；体验守门（涉及交互面改动必须附走查记录，20 维度第 3 项）。闸门可以慢，不可以跳——跳闸门的合入等同事故，走复盘。

### 35.5 仓库与文档的物理布局

本仓库即车间：kernel/（内核）、launcher/（引导）、src/（Variable 与前端资产）、portable/（Windows 域脚本）、docs/（MD1/2/3 与 ADR、验收记录）、_attic/（退役与实验区——四板斧脚本从这里收编）。规则：_attic 的东西不进发布；docs 的东西必须与实现同步（16 章纪律）；一切构建产物（build/、dist/）可随时删除重建，源之外无圣物。

## 第 36 章 用户支持与故障自查（系统替用户先想办法）

支持体系的最高形态是用户不需要支持——问题在系统内已给出路。本章定义 STAR I 的三层自救体系与人工支持的最后一道防线。

### 36.1 第一层：就地解释

每一个错误对话框自带"下一步"链接，直接跳到对应设置页或修复动作（不是死链接到不存在的帮助文件）：网络失败 → 跳网络设置并附诊断按钮；应用崩溃 → 跳重开与星卡；存储异常 → 跳只读模式说明与重启修复入口。就地解释的文案遵守 27.1 三要素模板——用户读完知道发生了什么、为什么、下一步。

### 36.2 第二层：诊断中心

设置中心内置"诊断中心"页，四个入口：① 健康总览——存储/网络/音频/兼容四系统的红绿灯（来自各服务降级态），一眼定位问题域；② 启动报告——最近一次启动的时间线（19.4 打点可视化），"为什么今天开机慢了"不再靠猜；③ 挫败回顾——体验日志里的 Top 挫败点（宪章第十三章的用户可见面），用户能看到系统看见了什么；④ 导出诊断包——一键打包日志（脱敏后）到 DATA，供人工支持时提交。

### 36.3 第三层：常见故障手册（内置）

手册不联网、不上网查，就在系统里（设置中心 → 帮助），首批收录二十条高频故障，每条格式统一：现象 → 一分钟自查 → 自修步骤 → 何时该求助。首批条目从判例与红队百问反推：交接后引导菜单不见了、应用启动报缺 DLL、Wine 应用打不出中文、NTFS 盘看不到文件（只读提醒）、开机时间变长、网络连不上、声音没有、快捷键冲突、U 盘空间告急、镜像更新失败……手册随版本更新，新故障模式进入手册的前提是先有判例或修复项。

### 36.4 人工支持的最后防线

STAR I 的支持者是项目本身（单 AI + Variable）。约定三件事：诊断包是求助的标准附件（没诊断包的问题先补包）；重复三次以上的同类求助必须转化为手册条目或系统修复项（支持数据反哺产品）；支持过程中的每一条裁决归档为判例——支持体系与判例体系是同一套知识库的两个入口。

## 第 37 章 版本与发布工程（从代码到一部 U 盘）

开发在仓库里，生活在 U 盘上——中间隔着发布工程。本章定案版本规则、发布流程与回滚承诺。

### 37.1 版本号规则

`STAR I · 阶段.序号`：阶段号 1-4 对应四阶段，序号阶段内递增。开发版加日期后缀（`2.7-20260923`）。判据通过触发里程碑 tag（33.1）。版本号印在：设置中心"关于"、启动报告、诊断包——报问题时版本自明。

### 37.2 发布产物

每次发布的产物四件：系统镜像（varix.img，可写盘）；变更说明（CHANGELOG.md，用户视角写作——"修复了什么、改变了什么、已知问题"，不写 commit 流水）；星图快照（当前软件评级与版本锁定表）；验收摘录（本版过了哪些判据与演练）。四件同版本号归档，缺一不发布。

### 37.3 发布流程七步

① 冻结——主干停新功能，只收修复；② 回归——QEMU 冒烟全套 + 实机核心场景（21 章场景一至五）；③ 打包——复现构建（35.1 可复现铁律），双环境哈希比对；④ 试运行——实机日用 48 小时（Variable 本人的真实使用就是试运行），体验日志无新增阻断；⑤ 发布——四件产物归档 + git tag + U 盘升级（经 vx-updater，老版本保留可回滚）；⑥ 公告——变更说明入仓；⑦ 复盘——本版发现的过程问题回写 MD3 偏差专栏。七步里第④步是灵魂：**我们发布的每一个版本，都是发布者自己已经用过的版本。**

### 37.4 回滚承诺

任何发布版本保留上一版完整镜像；升级后 72 小时内发现阻断级问题，vx-updater 一键回滚（数据分区不动）；回滚操作本身不超过五分钟且不需要联网。这条承诺写进用户手册——它是"数据安全与信任"（宪章第十二章）在发布侧的兑现。

### 37.5 发布节奏

不追日历，追判据：阶段内序号版按需发（修完值得发的就发），里程碑版只在判据通过时发。宁可跳票，不发已知阻断的版本——跳票损失的是时间，坏版本损失的是信任（信任建立要几个月，摧毁只要一次）。

## 第 38 章 术语通俗解读（三十个词，说人话）

本总案读者不止是工程师。这一章把全文最常见的三十个术语用大白话重讲一遍——如果某个词在别处看不懂，回这里查。

**双域接力**：电脑同一时刻只能活在一个系统里，要么 VARIX 要么 Windows；想换另一个就重启一次，重启时把"我做到哪了"写在小纸条（交接分区）上带过去。像两个人换班，班次不重叠，但交接本齐全。

**OneShot（单次引导）**：VARIX 内核写给引导器的一张"下次开机只执行一次"的便签——重启后引导器照便签引导一次 Windows，然后把便签撕掉。好处是不留永久痕迹、不跟固件抢位置。

**防自锁闸门**：写便签之前先检查"便签指向的地方真的存在吗"，不存在就不写。防的是无限重启死循环（我们真摔过一跤，第 3 章补有案底）。

**NVRAM 过滤**：联想固件对自建引导项爱答不理（F12 菜单不显示），OneShot 便签恰好绕开这个脾气——不走固件登记，走引导器自己读。

**Linuxulator（转译柜台）**：Linux 应用开口说的是 Linux 方言，VARIX 柜台在中间逐句翻译成自家话。应用自己不知道对面不是 Linux。

**Wine**：让 Windows 程序以为自己在 Windows 里的"布景板"——窗口、菜单、注册表都演得像，程序就正常唱戏。五百万行老牌开源项目，我们搭台不拆台。

**前缀（prefix）**：每个 Windows 软件分到的"片场"，它的 C 盘其实是片场里的道具目录，砸了重建就行，伤不到真摄影棚。

**Servo**：开源浏览器引擎，我们拿它当"网页壳"——需要网页能力的软件（Steam 商店页之类）把页面交给它渲染，不用再养一个 Chrome。

**Mesa / llvmpipe**：Mesa 是图形世界的公共设施公司，llvmpipe 是它家的"纯 CPU 画图工"——没有显卡加速时，靠 CPU 硬画。慢工出细活，够 STAR I 用。

**relibc**：Rust 写的 C 标准库，原生程序的"标准餐具"。程序要的 printf、malloc 都从这里来。

**smoltcp**：小而完整的 TCP/IP 网络协议栈，VARIX 网络层的地基。

**rustls / cosmic-text / ext4 crate**：TLS 加密通话库 / 中西文排版库 / Google 出品 ext4 文件系统读写库——三件都是"借力清单"上的成品家具，拎包入住。

**VXWM**：VARIX 自家的窗口协议——应用和桌面之间关于"画在哪、点了谁、拖了什么"的通话规则，总共不超过 24 句话。

**合成器**：桌面上真正"拼图"的那个进程——每个应用画自己的那块，它负责把所有块按前后顺序拼成完整画面。

**浮层出路**：任何弹出来的东西（菜单、气泡、对话框）必须有一套完整的消失方式：点外面消失、Esc 消失、再点一次消失。没有出路的浮层是 bug。

**W^X**：内存的铁律——一块内存要么可写、要么可执行，不能两者兼得。防"边写边执行"的攻击套路。

**BOT / UAS**：U 盘和电脑对话的两种协议。UAS 快但对我们的 U 盘水土不服（0xED 报错），BOT 慢但稳如老狗——四板斧的第一板就是强制降级到 BOT。

**四板斧**：给 Windows 域做的一套稳定性加固——U 盘协议降级、关闭省电断流、拉长超时、防引导自愈。实机验证 0xED 绝迹。

**三腿战略**：软件怎么在 VARIX 里跑——原生腿（专门构建）、兼容腿（转译/Wine）、兜底腿（切 Windows 域）。每款软件明确站哪条腿，不装糊涂。

**星图 / 星卡**：应用目录 / 每款软件的"体检报告"——哪条腿、过没过测试、真实速度，白纸黑字。

**判例**：遇到一类问题时的正式裁决，之后同类问题都照办。像法院判例，防止同一坑摔两次。

**ADR**：架构决策记录——改"宪法条款"的唯一通道，每条写清背景、选项、结论，改错有据可查。

**60 万行**：STAR I 终态代码量目标。现在 36 万，中间每 5 万行都有可发布的状态（第 39 章）。

**体验宪章**：14 条体验铁律（浮层、键盘、手感、错误呈现……）——测试测不出"用着舒不舒服"，宪章管这块。

**20 维度验收**：交付前的打分表，从需求理解到整体感受二十项，任何一项不达标不交付。

**vxbench**：自家基准测试工具——启动多快、内存多少、帧率几帧，每个数字有测量脚本撑腰。

**体验日志**：系统记下每次交互顺不顺畅（不记你输入了什么内容），挫败信号自动浮出——系统自己知道自己哪里让用户烦。

**交接快照**：切域前把"窗口清单、剪贴板、草稿"打包写进交接分区，另一边开机时读回——双域接力的小纸条本体。

**vxrun**：Linux 软件的启动员——为每个应用搭好隔离的文件视图、注入环境变量、再拉起进程。

**vxapp / 星图安装**：VARIX 的软件包格式与内置安装服务——装、升、卸一条线，卸载无残留。

**36 万（起点，已在手）**：VARIX 内核引导成立、双域接力实测可用、稳定性四板斧落地、Variable 双宿显示屏通路雏形。它是"能跑的骨架"。

**40 万（阶段 1 收口）**：OneShot 直通交接全面替换 BootNext 主路径，防自锁闸门全量升级，Windows 域加固包收编成产品级脚本。价值：**换域这件事从"能行"变成"可靠"**。

**45 万（阶段 2 前半）**：合成器 + VXWM 就位，浮层物理约束生效，十二件套原生应用前六件（终端、文件、编辑、星图、设置、监视器）可用。价值：**VARIX 第一次像桌面，不像演示**。

**50 万（阶段 2 收口，判据 2 达成）**：十二件套全齐，体验宪章十四章逐章落地，20 万行增量的体验打磨完成。价值：**不接 Windows 也能过一天**。

**54 万（阶段 3 前半）**：Linuxulator 柜台覆盖核心 syscall 面，vxrun 与封闭依赖树就位，静态类直插全绿。价值：**Linux 世界的大门打开**。

**56 万（阶段 3 收口，判据 3 达成）**：Wine 支架定型，VSCode 直插全绿，十二星卡首轮定级。价值：**生产力工具真正住进来**。

**58 万（阶段 4 前半）**：星图运营面完成（评级、复评、季度窗口流程演练），vx-updater 与发布七步跑通一轮。价值：**系统学会自我更新**。

## 附录 A 判例库补编（第 11-20 例）

第 5 章补已收录判例 1-10，本附录续编。判例格式沿用：场景 → 裁决 → 依据 → 影响面。

**判例 11：Windows 程序里打中文。** 场景：Wine 运行的软件需要中文输入。裁决：IME 由 VARIX 合成器层提供，候选窗是 VARIX 自绘浮层，Wine 窗口只接收最终提交文本；禁止 Wine 侧自装输入法 DLL。依据：Wine 与 IME 解耦后，输入法缺陷不会污染兼容腿，反之亦然；TSF/XIM 桥接是已知深坑。影响面：输入子系统、VXWM 提交文本消息、判例 SC 全系中文输入项。

**判例 12：双域剪贴板接力。** 场景：用户在 VARIX 复制了一段文字/文件，切到 Windows 域想粘贴。裁决：不做实时共享（物理互斥做不到），交接流程在重启前把剪贴板内容写入交接分区 handoff.json/clipboard 目录，Windows 侧 Variable 启动时读取并提示"有一条来自 VARIX 的剪贴板"。反向同理。依据：接力式双域的物理约束，小文件中转是最诚实方案。影响面：交接协议、Windows 侧交接助手。

**判例 13：Steam 登录二维码。** 场景：Steam 登录需要展示扫码页面。裁决：Servo 壳承载登录页（WebView 能力足够），登录态 cookie 存 VARIX 侧会话存储；客户端主界面同路径。依据：Chromium 级深坑不碰，登录页复杂度可控。影响面：Servo 支架、星卡 SC-Steam。

**判例 14：VSCode 代理与网络环境变量。** 场景：VSCode 扩展商店走代理。裁决：直插级应用继承会话环境变量（HTTP_PROXY 等标准集），不做 VSCode 专属代理配置界面。依据：Linux 版 VSCode 本就吃环境变量，直插级一致性优先。影响面：会话服务环境变量注入表。

**判例 15：主题跟随。** 场景：应用想跟随系统深浅主题。裁决：主题作为 VXWM 绑定时下发的环境状态（颜色 token 集 + env 注入），应用自取；系统切换主题广播变更事件。依据：一致性词典——全系统只有一套主题 token。影响面：VXWM、vx-SDK、Wine 主题垫片（注册表色值映射）。

**判例 16：大文件复制中断电。** 场景：拷贝 20GB 文件途中拔电。裁决：写合并层保证元数据与数据一致的检查点间隔 ≤ 5s；恢复挂载后文件要么完整要么回到检查点，绝不出现"半文件假装完整"；复制对话框重启后提示未完成任务。依据：ext4 数据模式 + 写合并检查点。影响面：存储子系统、文件管理器任务恢复。

**判例 17：U 盘拔出保护。** 场景：系统运行中 U 盘被直接拔出（用户的真实事故面）。裁决：块层立即上报失联，系统 1 秒内全屏接管显示"存储已移除"保护屏，冻结全部写请求并保留内存现场信息，禁止继续假运行；重启后 ext4 日志恢复。依据：静默假运行会产生更多损坏，诚实的急停是损失最小路径。影响面：存储、合成器、会话管理。

**判例 18：Windows 大更新重置引导。** 场景：Windows 域大版本更新可能重写 BCD、重置引导顺序。裁决：防自愈闸（BCD 校验值比对 + 更新后复检脚本）+ VARIX 侧每次启动校验交接目标签名；闸被拆时交接流程拒绝盲写并提示修复步骤。依据：Boot2001 事故的工程化总结。影响面：交接协议、Windows 域加固手册。

**判例 19：游戏反作弊软件。** 场景：EAC/BattlEye 类内核反作弊在 Wine 下运行。裁决：明确不承诺，星卡标注兜底级；不做反作弊对抗研究。依据：反作弊依赖内核级信任链，与用户态兼容边界冲突，且对抗行为违反平台条款。影响面：星图评级规则、用户预期管理。

**判例 20：打印机与外设长尾。** 场景：用户接打印机、扫描仪等。裁决：STAR I 明确不承诺，驱动矩阵（第 11 章）之外的外设统一提示"接入 Windows 域使用"；不做半吊子支持。依据：外设长尾是无底洞，诚实的边界比虚假的兼容更有价值。影响面：设备管理器文案、用户预期管理。

### C.1 三份文档的分工与引用规则

| 文档 | 回答的问题 | 修改权限 |
| --- | --- | --- |
| MD1 总案（本文） | 是什么、为什么、守什么规矩 | 只走 ADR |
| MD2 技术详案 | 具体怎么实现，字段级 | 施工回写 + 方案修订，偏差 > 20% 报 MD1 |
| MD3 任务分布与工程量 | 谁在哪一步做多少、怎么验收 | 施工事实回写（实际行数、偏差） |

引用规则：MD2 与 MD3 里的任何设计若与 MD1 冲突，以 MD1 为准，冲突本身是缺陷要登记；MD1 引用的技术细节若与实现后的现实不符，以现实为准并回写 MD1。

## 结语：STAR I 完成时的世界

总案写到这里，全部章节与附录把"是什么、为什么、怎么做、怎么验"全部铺完。结语不留技术，只回答一个问题的完整版：**这一切造好之后，一个普通的夜晚是什么样的。**

晚上九点，Y7000 通着电，thinkplus U 盘插在侧口。开机，二十秒后 VARIX 桌面亮起——星图记住你昨天在写的东西，VSCode 恢复了三个窗口，光标停在昨晚那行没写完的代码后面。内置终端里 git push，十五秒后远端已见提交。想起明天要交的压缩包，7-Zip 从星图点开，进度条走完的时候你顺手把结果拖进了文件管理器——两个窗口，一个是 Wine 的，一个是原生的，拖放毫无异样。

十点半，想玩会儿游戏。任务栏点"切换到 Windows"——保存、冲刷、交接画面十秒，Windows 起来时 Variable 已经在跑，右下角一条提示："来自 VARIX 的剪贴板有一条内容"。玩到十二点半，关游戏，Variable 侧栏点"重启到 VARIX"。二十秒后，桌面回来了，浏览器标签（Servo 壳）还在原位。

凌晨十二点四十，合上笔记本。系统冲刷完毕，出现"可以合盖了"的画面——U 盘安安静静躺在侧口，六十万行代码沉睡在 ext4 里，等着下一个晚上九点。

没有一处需要你等待时盯着黑屏猜；没有一个弹窗关不掉；没有一次切换丢过任何东西；没有一个软件骗你说"兼容"却跑不起来。它是快不是因为它激进，是稳不是因为它保守——它好用的每一条原因，都写在这四十章里，有判据、有判例、有 ADR、有走查记录撑着。

这就是 STAR I。**不是一部"能用的 U 盘系统"，是一部愿意每天被使用的作品。**

技术字段级的每一块砖，MD2《技术详案》接着讲；每一块砖由谁在哪个台阶上砌、砌到什么程度算完，MD3《任务分布与工程量》接着排。总案在此合卷。

## 附录 E ADR 完整演练（三条真实待决问题的成例）

第 14 章是 ADR 摘要，本章给三条真实待决问题的**完整成例**——既是把悬而未决的问题当场裁决，也是给未来的 ADR 作者看格式怎么写。每条含：背景、选项、裁决、理由、后果、状态。

### ADR-011 交接分区的文件系统选型

**背景**：双域接力需要一块两域都可读写的状态交换区（快照、剪贴板、诊断包）。候选：FAT32 / exFAT / ext4。
**选项分析**：FAT32——Windows 原生读写、VARIX 读写实现现成（只读已有、写实现小），单文件 4GB 上限；exFAT——无 4GB 限制，但 Windows 写日志行为怪异且开源实现许可存疑；ext4——VARIX 主力，但 Windows 域读写需第三方驱动（交接助手分发驱动不可控）。
**裁决**：FAT32，容量 1GB。
**理由**：交接数据天然是小块文件（快照 JSON、文本剪贴板、小诊断包），4GB 上限无实际影响；两域零依赖读写是最高优先级——交接链是全局最脆弱的一环，不能在文件系统层再加一丝不确定。
**后果**：大文件不走交接分区（用户文件接力走判例 12 的目录引用而非实体拷贝）；分区表固化进 17.3 布局总表。
**状态**：已裁决（2026-09），推翻需新 ADR 并复核判据 1 全部实测。

### ADR-012 输入法引擎：自研极简 vs 移植 Rime

**背景**：中文输入是日用刚需。候选：自研极简拼音 / 移植中州韵（Rime）/ 接系统级框架（ibus/fcitx 类）。
**选项分析**：自研——声韵组合 + 冻结词库两三千行可成，零外部依赖，可控性最高，智能度低；Rime——能力强（方案、词库生态），但 C++ 体量大、配置体系复杂、移植与维护成本高；系统框架——为多引擎设计的重量级基建，STAR I 只有一个引擎，框架税白缴。
**裁决**：自研极简拼音（17.6 方案），词库 3 万条冻结版。
**理由**：STAR I 的输入法验收线是"稳定、零延迟、永不崩"（16ms 上屏），不是"智能整句"。极简实现最容易达到这条线；Rime 的能力上限在 U 盘系统当前阶段是浪费，且引入一个 C++ 大件违背借力清单的"成十件、不引一件重装"精神。
**后果**：智能整句、云词库明确不承诺；接口层保留"引擎可替换"抽象（输入子系统与引擎之间留薄接口），STAR I start 若需 Rime 走替换而非重构。
**状态**：已裁决（2026-09），候选窗 STAR I start 复议。

### ADR-013 星图数据格式：JSON 目录 vs SQLite 库

**背景**：星图目录（18.5）承载软件条目、星卡、评级，数据增长后（数百条）需要稳定载体。候选：开放 JSON 文件集 / SQLite 单库。
**选项分析**：JSON——人可读、git 友好、开放格式红线天然满足、离线更新包即文件分发；SQLite——查询强、事务强，但二进制格式 diff 不友好，开放性打折（导出永远可以做，但"原生即开放"更好）。
**裁决**：JSON 文件集（一软件一文件 + 一索引文件），规模红线：超过 500 条再评估迁库。
**理由**：STAR I 量级（首批 12 + 年度增长几十条）远未到需要 SQL 的时刻；开放格式是宪章第十四章红线，JSON 是它的最直接兑现；git 管理星卡历史即审计日志。
**后果**：索引文件承担查询（按名称/评级过滤，量小无需更强）；schema 版本字段进每个文件（Q18 协商机制复用）。
**状态**：已裁决（2026-09），含内置迁库触发条件（500 条）。

三条成例的共同点值得刻进习惯：**每个 ADR 都自带推翻自己的条件**（复核判据、复议窗口、触发阈值）——决策不是判死刑，是给未来留一份带出路的承诺书。

## 附录 H VXWM 消息全集（24 条窗口协议词条）

VXWM 的消息种类是协议的宪法边界（C-3：超 24 条须 ADR）。本附录给全部 24 条消息的词条——名称、方向、职责。方向约定：C→S 为客户端发往合成器，S→C 为合成器发往客户端。字段级编码（字节序、报文布局）在 MD2 篇 5。

**绑定与生命周期（5 条）**

1. **bind（C→S）**：客户端报到——申报身份、版本、需要的表面能力，领回全局对象。协议的握手起点。
2. **surface_create（C→S）**：申请创建表面，附带建议尺寸与用途类别（顶层/浮层/嵌入），合成器裁决实际属性。
3. **surface_destroy（C→S）**：销毁表面，释放配额；合成器回收缓冲记账。
4. **close_request（S→C）**：合成器转达用户关闭意愿（点叉、Alt+F4），客户端自行决定收尾——关不关由应用协商，强制杀另有通道。
5. **ping/pong（双向）**：活性心跳，合成器据此判定客户端假死（宪章"看起来没反应"的同罪检测）。

**绘制与提交（4 条）**

6. **buffer_attach（C→S）**：提交新缓冲（共享内存句柄 + 尺寸 + 格式）。
7. **damage（C→S）**：申报脏区——本协议省 CPU 的核心机制，脏区外绝不重画。
8. **commit（C→S）**：原子提交——缓冲与脏区一起生效，杜绝半帧。
9. **frame_callback（S→C）**：合成器通知"该画下一帧了"，客户端按节奏绘制，不做忙等。

**输入事件（4 条）**

10. **pointer_motion（S→C）**：指针进入/移动，含逻辑坐标与命中的表面。
11. **pointer_button（S→C）**：按键按下/释放，含按下序列号——客户端凭序列号识别"同一次点击"（防抖依据）。
12. **key_event（S→C）**：键盘事件，焦点窗口独享；IME 组合期事件被输入子系统截留不透传。
13. **text_commit（S→C）**：IME 提交的最终文本（判例 11 的协议落点），Wine 与原生同路径。

**窗口状态与几何（5 条）**

14. **configure（S→C）**：合成器裁决窗口几何/状态（尺寸、最大化、平铺位置），客户端必须服从并重排。
15. **ack_configure（C→S）**：客户端确认服从，未确认前合成器不给旧几何送输入——防止"窗口变了内容没变"的错位窗口。
16. **state_request（C→S）**：客户端申请状态变更（请求最大化、请求全屏），批准与否合成器定。
17. **focus_change（S→C）**：焦点进出通知，客户端据此切换激活态渲染。
18. **z_order_hint（C→S）**：浮层类客户端的层级建议（tooltip 永在上等），建议权在客户端、裁决权在合成器。

**剪贴板与拖放（4 条）**

19. **clipboard_offer（C→S）**：客户端申报"我复制了"，附内容类型清单。
20. **clipboard_select（S→C）**：合成器把剪贴板所有权授予焦点窗口（显式转发，防后台偷读）。
21. **drag_start（C→S）**：客户端发起拖放，附载荷描述。
22. **drop_event（S→C）**：落点表面收到的放下事件，含动作（复制/移动）协商结果。

**浮层语义与诊断（2 条）**

23. **popup_grab（C→S）**：菜单/气泡类浮层申请"抓住"交互——抓住后点外部即触发关闭（合成器强制执行宪章第 2 章出路，客户端无法逃逸）。
24. **diagnostics（C→S）**：客户端自报异常（渲染卡顿、缓冲堆积），进体验日志——客户端主动喊疼，不只等合成器发现。

24 条的分组本身就是设计说明：生命周期 5、绘制 4、输入 4、几何 5、剪贴板拖放 4、浮层诊断 2。任何"要不要加第 25 条"的讨论先过三问：现有 24 条组合真的做不到吗？做得到的代价是什么？加条的 ADR 准备好了吗？

## 附录 J 一页纸摘要（给只有五分钟的读者）

**这是什么**：《Varix STAR I》是 VARIX 双域系统的第一代完整总案——把"自研内核 + Windows 桌面 + Wine 兼容层"的 U 盘整机系统，从愿景写成可施工、可验收的工程宪法。三部曲：MD1 总案（本册，立规矩）、MD2 技术详案（字段级怎么造）、MD3 任务分布与工程量（谁在哪步造多少）。

**核心形态**：一台联想 Y7000，一个 thinkplus 1TB U 盘，开机自检后由 Limine 引导菜单二选一——VARIX 内核域（自研 Rust 系统）或 Windows 域（Variable 桌面所在）。同刻互斥、重启接力、交接分区传状态、防自锁闸门拒绝一切盲写。

**软件从哪来**：三腿战略。原生腿（vx-SDK 构建的十二件套）；兼容腿（Linux syscall 转译柜台承载 Linux 官方版软件如 VSCode，Wine 支架承载 Windows 软件，Servo 壳承载网页形态）；兜底腿（切 Windows 域运行，如实标注）。

**代码量与节奏**：36 万行起步，60 万行收口，四个里程碑（m1 接手直通、m2 桌面日用、m3 兼容立住、m4 发布闭环），每五万行一个可发布状态，判据 1-5 分阶段验收。

**体验底线**：体验宪章十四章 + 20 维度验收协议 + 红队百问 + 真机走查 34 项——测试证明逻辑，走查证明体验，体验日志证明"一直好用"。

**借力清单**：Wine、Servo、Mesa、relibc、smoltcp、rustls、cosmic-text、ext4 crate、hickory-dns——只用不改、版本锁定、季度升级窗、回馈上游。VARIX 自研的火只烧在四个地方：双域接力、VXWM 窗口协议、syscall 转译、体验落地。

**铁律六条**：内核最小化（兼容全在用户态）；不碰 Linux 内核代码（GPL 立场）；交接目标未验证不写引导变量；NTFS 只读；数据可开放可导出；20 维度不过不交付。

**当前状态**：36 万行实机在跑，0xED 绝迹（四板斧），Variable 弹窗已通（VC 运行库），判据 1 的工程改造（OneShot 直通）蓄势待发——施工令下达后按 MD3 泳道推进。

## 附录 L 判例库第三批（第 21-30 例）

**判例 21：终端里的中文列宽。** 场景：代码注释里中英混排，对齐错位。裁决：等宽场景中文一律按两格计宽（27.2），终端与编辑器共用同一计宽实现，禁止各自为政。依据：计宽双实现必然错位。影响面：vx-term、vx-edit、VSCode 直插垫片。

**判例 22：NTFS 盘"看不见文件"的用户误会。** 场景：用户在 VARIX 找 Windows 分区文件，发现可读不可写，误以为坏了。裁决：vx-files 对 NTFS 挂载点强制显示"来自 Windows 域（只读）"角标，写入动作给一行解释而非报错。依据：C-6 是设计不是缺陷，界面必须把设计说出来。影响面：vx-files、Wine 的 W: 盘呈现。

**判例 23：应用申请开机自启。** 场景：软件想随系统启动。裁决：自启白名单制——申请进启动表需用户在设置中心逐项确认，列表可见、可关、可排序（宪章第十二章"占用透明"）。依据：静默自启是 Windows 生态最被痛恨的行为之一，VARIX 不复制它。影响面：25.1 启动表、设置中心。

**判例 24：系统更新与星卡复评联动。** 场景：VARIX 自身更新（尤其内核/柜台层）后，兼容判例是否还有效。裁决：凡触及 Linuxulator、Wine 支架、VXWM 的更新，星图自动把受影响路径的星卡置"待复评"黄标，复评完成转绿。依据：评级有效期以"上次验证于哪个版本"为准。影响面：星卡 reviewed_at 语义、更新器联动。

**判例 25：Wine 应用崩溃后前缀疑似损坏。** 场景：应用反复崩溃，用户怀疑前缀坏了。裁决：诊断中心提供"前缀自检"（结构完整性 + 注册表可读性）；自检不过即建议重建（23.2），不做前缀内手术。依据：手术成本与风险高于重建（≤ 3 分钟）。影响面：诊断中心、23.7 判据。

**判例 26：快捷键冲突仲裁。** 场景：应用注册的系统级快捷键与保留字表或他应用冲突。裁决：系统保留字表（17.6）优先级最高且不可覆盖；其余按"先注册先得"，冲突注册直接拒绝并指名冲突方。依据：Q40 的裁决化；全局一致性（宪章第 10 条）要求快捷键词典唯一。影响面：输入子系统、vx-SDK 文档。

**判例 27：用户想删 ESP 分区里的文件。** 场景：vx-files 能看到 ESP，用户想"清理"。裁决：ESP 与引导相关路径列为关键区——默认隐藏，显式开启"显示系统分区"后只读呈现，删除操作引导到带确认的专用工具并二次警告。依据：引导设施红线（边界章）的文件系统层落实。影响面：vx-files、引导工具。

**判例 28：外接显示器。** 场景：Y7000 接 HDMI 显示器。裁决：STAR I 阶段 2 支持外接**镜像**（同画面复制，合成器成本最低），阶段 3 支持扩展桌面；扩展前的多屏配置界面不做半吊子。依据：软渲染预算（19.1）按单屏核定，扩展桌面需重新核定预算。影响面：合成器显示输出、设置中心显示页、19 章预算注记。

**判例 29：蓝牙。** 场景：用户接蓝牙鼠标/耳机。裁决：STAR I 明确不承诺蓝牙（驱动链与 WiFi 同级复杂，收益排位低于判据 1-5 相关项），设备矩阵如实标注"阶段外"，设置中心显示"蓝牙：未启用"。依据：诚实的边界优于虚假的兼容（判例 20 同精神）。影响面：11 章硬件矩阵、设置中心文案。

**判例 30：电池与电源状态。** 场景：笔记本不插电使用，用户想看电量。裁决：阶段 3 前不承诺电池计量（EC 读取链复杂度与判据无关），系统常驻提示"建议插电使用——U 盘整机在直流下性能最稳"；阶段 3 加入基础电量百分比。依据：诚实预期管理；插电使用同时规避瞬断风险。影响面：任务栏状态区、手册。

## 附录 N 初次上手指南（新用户的第一小时）

这套文档的读者大多是建设者，但总得有一个篇章写给"第一次插上这块 U 盘的人"。本附录是上手指南的骨架（成品的用户版随系统内置在 36.3 帮助手册里），它同时是 21 章场景的用户视角对照。

**第 1 分钟：插盘开机。** 把 U 盘插进电脑，开机连按 F12 选择 U 盘启动（联想机型的通用姿势）。看到引导菜单：默认 VARIX，什么都不做，五秒后自动进入。第一次启动会久一点（建立缓存），属正常现象。

**第 3 分钟：认识桌面。** 任务栏从左到右：开始、终端、文件、星图、设置，右下角是输入法、网络、音量、时间。先点一次星图——它的首页就是这张系统的"地图"：五个评级是什么意思（18.1）、哪些软件已经能跑（十二星卡）、想跑的软件在哪一级。

**第 8 分钟：联网。** 设置中心 → 网络。有线即插即用；WiFi 阶段 3 前可用手机 USB 共享（数据线连手机，手机开"USB 网络共享"）——这是临时但可靠的路。右上角网络图标确认在线状态。

**第 12 分钟：中文输入。** 任意输入框按 Ctrl+空格切换拼音。第一次用会弹出输入法说明（只弹一次）。候选窗出现在光标正上方，永不跑出屏幕。

**第 15 分钟：装一个软件。** 星图 → 搜"code" → 看 VSCode 的星卡（真实数字）→ 点安装 → 完成后出现在星图与开始菜单。卸载同样在星图里一键完成，无残留（SC-133）。

**第 25 分钟：写点什么。** 打开 VSCode，新建文件保存到"主目录"。注意保存是即时的——系统在背后合并小写入保护 U 盘，你只管写。顺手在终端里 git clone 一个仓库试试网络全链路。

**第 35 分钟：试一个 Windows 软件。** 星图里找一个兼容级（Wine）的应用，比如 7-Zip。它的窗口长得像 Windows 的——这就是兼容腿该有的样子。打中文、拖文件、出声音，全都该正常；不正常的部分看星卡"已知边界"，那里写的是实话。

**第 45 分钟：换一次域。** 任务栏 → 切换到 Windows。跟着交接画面走完五步（它在做什么，21.5 有完整说明）。Windows 起来后 Variable 会提示来自 VARIX 的剪贴板。玩一圈，从 Variable 里"重启到 VARIX"回来看看会话恢复。

**第 55 分钟：知道出事怎么办。** 设置中心 → 帮助：二十条高频故障的自查手册。再点一次诊断中心——记住这个地方，任何"感觉不对"先来这看红绿灯和启动报告。

**第 60 分钟：安心交给你。** 关机走任务栏关机项，出现"可以拔电了"再拔。U 盘可以随身带走——整个系统、你的文件、你的配置，都在这一块盘里。下次任何一台 Y7000 级别的电脑，插上就是你熟悉的那个世界。

## 附录 O 常见误区澄清（十条问答式纠偏）

本总案篇幅长，误读的点 predictable。十条高频误区，一次说清。

**误区一："VARIX 里跑的是 Windows。"** 不是。VARIX 域里没有 Windows——跑的是 Linux 软件经转译柜台、Windows 软件经 Wine 的"演员"。真 Windows 在另一个域里，靠重启接力去。

**误区二："兼容层是在系统里装了个虚拟机。"** 不是。转译柜台和 Wine 都是普通用户态程序，没有虚拟机的第二内核、没有双重性能税（29.1 是我们否决虚拟机的完整理由）。

**误区三："借力等于把别人源码抄进内核。"** 不是。借力是用户态整库集成 + 版本锁定 + 回馈上游；内核只进 smoltcp 这类 no_std 库级组件，一行 Linux 内核代码不碰（29.2）。

**误区四："60 万行=我们手写 60 万行。"** 不是。36 万现有 + 24 万增量是 VARIX 侧工程量；Wine、Mesa 等上游的数百万行是"站在上面"，不算进也不需要维护。

**误区五："双域接力 = 双系统（像装两个 Windows）。"** 不同。双系统是并列选择、互相不可见；双域是接力协作——有交接协议、有快照、有闸门，剪贴板能跟人走。

**误区六："OneShot 变量很危险，会改坏引导。"** 它恰恰是安全设计：写一次、用一次、作废，不占固件登记、不碰内置引导项；写之前还有防自锁闸门三条件把关（Q1-Q10）。

**误区七："Wine = 能跑所有 Windows 软件。"** 不是。Wine 有强区（Win32 传统应用）也有墙（内核反作弊、深度驱动依赖）——所以有星卡制度，把"能跑到什么程度"写成公开的实话。

**误区八："软渲染 = 卡。"** 不是同义词。软渲染的上限低（所以预算表卡得死），但预算内（1080p、常规桌面负载）是流畅的——55fps 拖窗、16ms 键入回显是硬判据不是愿望（19.1）。

**误区九："STAR I 完成后就可以堆功能了。"** 恰恰相反。STAR I start 的每一项都有立项门槛（20.4），"功能多"从来不是目标，"每天好用"才是。

**误区十："文档写完 = 差不多了。"** 文档是宪法不是房子。施工令下达后按 MD3 泳道走，判据不通过不交付——文档的完备恰恰说明我们清楚离终点还有多少步。
