## F3461 分域挂载总设计（框架与各域用例集的挂载架构）

**定位**：挂载架构：域侧声明用例集（DomManifest）、框架侧统一注册表合并（注册表 = A5 自有段 + 挂载段）——ktest 从 A5 私有基建升格为全域基建的架构面。
**语义边界**：本条是总设计；协议细节在 F3462、各域核对在 F3463–F3465。挂载是**声明制**（域声明、框架合并）而非**侵入制**（框架不看域内部实现——域用例的写法对框架透明，只要 manifest 合规）。
**判据**：
- J1：M-220 挂载全链路：两域（A5 + 模拟域 X——判据行声明模拟域为验证用假域）manifest 声明 → 注册表合并 → 执行器选择可见 → 跑通——四步链零特判。
- J2：架构文档三节：挂载模型/注册表合并语义/主权边界（域保留什么、框架接管什么）。
**纯功能行数**：340（模型 ~130 + 合并语义 ~110 + 用例 ~100）
**依赖与嫁接源**：F3406 注册表（合并目标）；F3441 执行器（挂载后的消费方——选择器对挂载用例零感知差异）；F3462 协议。
**风险与回退**：合并冲突（两域同 id——id 空间冲突）——回退：id 前缀域名制（M-xxx 的域前缀已是惯例——判据行给 id 规则冻结：`<域>-<族>-<序>`，合并时前缀即命名空间，冲突在 manifest 校验期拒绝）。
**正文**：挂载模型（判据行原文）：每域一份 DomManifest（F3462 定义三要素）——框架启动时读入全部 manifest → 逐域把域用例指针集挂入统一注册表（挂载 = 追加注册表段，段头记录域标识——注册表从"A5 独有数组"升格为"分域段表"）；合并语义：段间 id 全域唯一（前缀制保证）、段内顺序 = 域内声明序（F3443 声明序语义在挂载域内保持——域内顺序主权在域）；合并后全域视角（选择器/执行器/账本对"哪段来的"只有记账兴趣没有行为差异——判据行声明零特判：执行器的代码路径不出现 if domain== 分支——挂载用例与 A5 用例走同一条执行路径，这是框架归 A5 的工程含义）。主权边界（判据行内嵌表）：域保留——用例实现/判据语义/域内标签/域内依赖；框架接管——注册/选择/隔离/执行/超时/账本/上报（B11–B13 全部能力对挂载域自动生效——挂载即享受全套框架税后服务，这正是各域愿意迁移的动因：迁移成本一次性，换来隔离页/超时看门狗/flaky 账等全套基建）。为什么模拟域 X 是必需验证物（判据行论证）：用 A5 自有域验证挂载是自指（A5 用例本来就在注册表里——挂载链路的"域外"特性没被真正测试）；模拟域 X（三个假用例）是第一个真正的域外挂载——M-220 的全链路验证因此有效。现有内核接入：无（挂载面新框架 `testing/mount/`）。Windows 对比：TAEF 的测试套发现机制（机器上发现测试 DLL）同方向——它发现二进制，我们声明清单（内核态没有动态发现，声明制是内核的诚实选择）。M-220 复测：四步链 + 模拟域 + 零特判核对（代码走查）+ id 冲突拒绝。

## F3462 挂载协议（域侧注册 API：用例集/标签/依赖三声明）

**定位**：挂载协议 v1：DomManifest 三要素（①用例集清单：域内全部用例的 id/入口指针/budget/np 位 ②域标签：域级 tag 集合 ③跨域依赖：本域用例 requires 的他域用例）——协议冻结后各域照表挂牌。
**语义边界**：只定义协议；协议实现（manifest 结构与校验器）在本条、消费在 F3461。协议 v1 冻结（扩展 = 新要素追加、既有要素语义不变）。
**判据**：
- J1：M-221 协议正反例：合规 manifest 挂载成功；缺要素三变体（缺清单/缺标签/缺依赖声明）在校验期被拒（拒绝信息指明缺项）。
- J2：协议签名冻结表（manifest 结构字段表 + 校验规则表）。
**纯功能行数**：340（结构定义 ~130 + 校验器 ~110 + 正反例 ~100）
**依赖与嫁接源**：F3406 kcase!（用例元数据——manifest 引用的每条用例必须已在域内 kcase! 注册，manifest 是清单不是第二注册处——判据行声明这一"单一事实源"原则）；F3413 kskip（依赖语义源）。
**风险与回退**：manifest 与实际用例漂移（清单说了三条实际注册两条）——回退：校验器双向核对（清单 → 注册表逐条存在性 + 注册表 → 清单逐条覆盖性——双向，多清单少清单都拒——判据行给双向校验的规则）。
**正文**：manifest 结构（判据行内嵌）：`DomManifest { domain: &str, cases: &[CaseRef], domain_tags: &[&str], cross_deps: &[DepEdge] }`——CaseRef = `{ id, fn_ptr, budget_ms, np, requires_local }`（域内依赖直接引用、跨域依赖进 cross_deps：`DepEdge { from: id, to: 外域id }`——判据行给两级的理由：域内依赖高频且域内可解，跨域依赖低频且需要治理（F3472）——分开登记是治理学）。校验规则表（判据行内嵌五条）：①三要素齐备（缺任一拒）②用例集与 kcase! 注册双向一致（如上）③id 前缀 == domain（命名空间一致）④标签 ∈ F3471 词表（非法拒）⑤跨域依赖方向合规（F3472 层次图——校验器现在就拒，不等执行期）。为什么协议要"校验期拒绝"而非"运行期容错"（判据行论证）：manifest 是契约——契约错误在挂载时刻（启动期）暴露，代价是一次启动失败+清晰报错；容错方案（缺什么补默认值）把契约错误转成运行期的诡异行为（缺标签 → 选择器选不到 → 用例静默不执行 = 假绿）——静默不执行是测试基建最危险的失败模式，校验期拒绝是它的天敌。单一事实源原则（判据行论证）：manifest 引用 kcase! 注册的用例而非自行注册——若 manifest 可第二处注册，同一用例两处登记必然漂移；引用制让 kcase! 是唯一注册点、manifest 是唯一清单点——职责分开、事实单一。现有内核接入：无。Windows 对比：TAEF 的测试元数据 XML（测试清单）同形态——它文件制我们结构体制（内核无文件系统依赖——桩内存盘除外）。M-221 复测：正例挂载 + 三缺项拒绝 + 双向校验 + 标签拒绝。

## F3463 A1 挂载与联签核对（A1 域用例迁移核对面）

**定位**：A1 域迁移的联签核对：A1 既有用例清单 × 新框架清单的逐条对账（数量一致/断言数一致/标签映射一致）+ 抽样迁移验证——A1 是最大迁移户（判据行给 A1 既有用例规模的登记位），联签是两域共同签认的迁移物证。
**语义边界**：A5 出核对协议与账本模板；A1 出原清单与迁移改写（**用例语义主权在 A1**——判据行重申判例：A5 不代 A1 写判据，只核账）；抽样比例 10%（判据行给抽样规则：域内分层抽样——按模块分层每层抽 10%）。
**判据**：
- J1：M-222 A1 抽样迁移验证：抽样集在新框架执行 → 判定与原框架逐条一致（PASS 对 PASS/FAIL 对 FAIL——原清单的已知结果基线比对）。
- J2：联签清单三一致（条数/断言总数/标签映射零漂移——任何漂移在联签期暴露而非迁移后）。
**纯功能行数**：340（核对协议实现 ~120 + 抽样机制 ~100 + 验证用例 ~120）
**依赖与嫁接源**：F3462 协议（manifest 机制）；A1 既有用例清单（联签对端——判据行给清单获取方式：A1 域的登记表导出）；F3466 迁移账本（核对结果入账处）。
**风险与回退**：原清单基线缺失（A1 既有用例无统一结果基线——原框架的判定史零散）——回退：基线先建（迁移前先用旧框架全量跑一轮，产出判定基线——基线是迁移等值的比对物，没基线就没有"等值"可言——判据行把基线先行列为迁移前置条件）。
**正文**：联签流程（判据行原文五步）：①A1 导出原清单（id/断言数/标签/模块四列）②A5 生成核对协议实例（F3462 manifest 模板填充 A1 数据）③两域并签（清单逐条比对——三一致判据）④抽样迁移改写（A1 主导、A5 提供框架税清单——迁移改写点表：断言宏替换映射表 kassert→kexpect 等，判据行给映射表）⑤等值验证（F3467 机制应用于抽样集）——五步全过 → 迁移账本登记绿行。抽样分层规则（判据行原文）：A1 按模块分层（清单的模块列）× 每层 10% 随机抽样（种子化——抽样本身可复现 F3444 同律）；抽样集跑新框架与基线逐条比对。为什么联签在迁移前而非迁移后（判据行论证）：迁移后核对 = 木已成舟再挑刺（改写已完成，发现不一致要回炉整批）；联签前置 = 清单在纸面先对齐，改写只是对齐后的执行——把对账成本放在最便宜的时刻（纸面对账比代码回炉便宜一个量级）——这与"验收物证先行"的整体纪律同构。A1 规模登记位（判据行声明）：A1 既有用例数与断言总数在联签时刻登记入迁移账本头（数字以联签实数为准——本判据不预设具体数字，防骨架阶段的数字变成虚构账）。现有内核接入：A1 既有测试入口（F3476 桥接的对端）。Windows 对比：代码库迁移的清单核对（API 迁移的 inventory 对账）同流程学；HLK 无此层（它不做测试框架迁移）。M-222 复测：五步流程留痕 + 分层抽样可复现 + 逐条等值 + 联签登记。

## F3464 A2 挂载与联签核对

**定位**：A2 域迁移的联签核对：与 F3463 同协议同五步（清单联签 → 抽样迁移 → 等值验证 → 账本登记）——A2 规模较 A1 小（判据行同样留实数登记位），流程复用零特判。
**语义边界**：完全复用 F3463 协议（本条是协议在 A2 的实例化——不新增协议内容）；A2 特有的只有清单本身与抽样层（按 A2 模块分层）。
**判据**：
- J1：M-223 A2 抽样迁移验证：抽样集新框架执行与基线逐条一致（同 M-222 判据）。
- J2：A2 联签三一致 + 与 A1 联签的流程一致性核对（两域走同一五步——流程漂移检测：A2 联签记录的步骤结构与 A1 完全同构）。
**纯功能行数**：320（清单接入 ~100 + 抽样与验证 ~110 + 对账用例 ~110）
**依赖与嫁接源**：F3463 核对协议（协议源——本条消费不改）；A2 既有清单。
**风险与回退**：A2 特有判定形态（如 A2 有依赖真实中断时序的用例——桩环境判定与基线不等值）——回退：环境敏感用例单独标记（迁移账本加"环境依赖"列——此类用例的等值验证推迟到闸口（真机复跑对基线）——判据行给推迟登记的规则：延迟验证不是豁免，是换闸口执行——双轨制的迁移版）。
**正文**：实现路径：F3463 的五步流程在 A2 的实例化（判据行给实例化差异清单：仅清单数据、分层维度、抽样种子三项不同——协议、账本、判据全部复用）；环境敏感用例处理（判据行原文）：A2 清单中标记 `hw_timed` 类的用例（依赖真实时序——桩期虚拟时间下它们的等值验证无意义——虚拟时间消灭了它们要测的东西）→ 迁移账本登记 `parity=deferred(gate)` → 等值验证在闸口期真机复跑完成——这是双轨制在迁移语义上的自然延伸：开发期验证逻辑等值、闸口期验证时序等值，两类等值分开负责。流程一致性核对（判据行论证）：三域联签若各走各的流程，账本三段不可比（审计时无法横向核对）；强制同构（A2 的联签记录结构与 A1 完全同构——字段序、步骤序、留痕格式）让迁移账本成为可横向审计的单一材料——同构性本身是 J2 判据。为什么 A2/A4 各立条目而非三域一表（判据行论证）：三域规模与风险不同（A1 最大、A2 中、A4 有环境敏感集）——合一表会把 A4 的特殊处理混进公共流程；分条目让各域的特有风险（A4 的 deferred 集）有明确的归属页——账本的可读性优先于条目数的紧凑。现有内核接入：A2 既有测试入口。Windows 对比：无（同 F3463）。M-223 复测：五步实例化 + deferred 集登记 + 流程同构核对。

## F3465 A4 挂载与联签核对

**定位**：A4 域迁移的联签核对：同协议同五步 + A4 特有的环境敏感集处理（A4 是设备/驱动域——硬件时序依赖用例占比最高，deferred(gate) 集最大）——迁移账本的 deferred 列在本域首次大量使用。
**语义边界**：复用协议；A4 特有项 = deferred 集的登记与闸口验证计划（判据行给 deferred 集的闸口清单要求：每条 deferred 用例的真机验证前置条件登记——依赖什么硬件）。
**判据**：
- J1：M-224 A4 抽样迁移验证：非 deferred 部分的抽样等值（deferred 部分不在桩期验证——判据行声明抽样范围排除 deferred）。
- J2：deferred 闸口清单（每条用例的硬件前置条件表——闸口执行的输入）+ 联签三一致（非 deferred 部分）。
**纯功能行数**：320（清单接入 ~100 + deferred 处理 ~110 + 验证用例 ~110）
**依赖与嫁接源**：F3463 协议；A4 既有清单；F3413 requires（硬件依赖的既有声明——deferred 判定的输入）。
**风险与回退**：deferred 判定过宽（可桩期验证的也被推迟 → 桩期覆盖缩水）——回退：deferred 判定规则冻结（`hw_timed` = 判据显式依赖真实时间/真实设备响应的——判据行给判定标准：requires 位图含硬件依赖位 && 判据引用真实时序——两个条件同时成立才 deferred；仅标记硬件依赖但判据是逻辑断言的仍桩期验证）。
**正文**：实现路径：A4 清单导入 → 逐条 deferred 判定（两条件规则——判据行内嵌：`def = requires_hw && asserts_time`）→ 非 deferred 集走标准五步 → deferred 集登记（闸口清单：id/硬件前置/原判定基线三列——基线取 A4 原框架在真机上的既有记录，无记录的用例基线标 unknown（闸口首跑建立））；deferred 集规模登记（判据行声明：本判据不预设规模数字——以清单实数入账）。判定标准为何要双条件（判据行论证）：单看 requires_hw 会把"硬件存在性检查"（插了没插——逻辑断言）误判为 deferred（它桩期完全可验——桩设备树的存在性是真的）；单看 asserts_time 会把"桩期时序"（fake_tick 逻辑时序）误判为可验（它依赖的其实是真时钟）——双条件交集才是"桩期无法等值验证"的准确集合，deferred 过宽过窄都是账本失真。闸口清单的前置条件列（判据行论证）：闸口时机器有限（真机窗口稀缺）——前置条件表让闸口批次可以按硬件分组执行（同前置条件的用例一批）——闸口效率的账面预优化。现有内核接入：A4 既有测试入口。Windows 对比：HLK 的设备测试矩阵（按设备分批的测试计划）同分组学。M-224 复测：双条件判定核对 + 非 deferred 等值 + 闸口清单齐备 + unknown 基线登记。

## F3466 迁移账本（逐用例迁移登记：原断言数→新断言数）

**定位**：迁移账本：全部迁移用例的逐条登记（id/原框架断言数/新框架断言数/等值状态/迁移批次五列）——迁移工程的单一事实源；1 万+ 断言硬指标的迁移侧证据就住在这本账里。

## F3470 断言密度审计（每域断言密度与覆盖充分性量化）

**正文**：实现路径：密度表生成（判据行原文）：`for dom in domains { rows: cases=count(dom), asserts=sum(dom), density=asserts/cases }`——四列 + 全库中位数行 + 异常带标记列；异常带（判据行内嵌）：`low = density < median/3`（每用例断言太少——可能测试过浅：一个用例只断言一个终值）、`high = density > median*3`（每用例断言过多——可能断言拆分或过度断言内部状态——过度断言的坏处：实现细节被锁死，无害重构触发假红）；复核名单输出 = 提问清单（域 + 密度值 + 偏离倍数——交给域维护者回答"为什么"——回答入 B15 收口材料）。为何密度要设域级而非库级单值（判据行论证）：不同域的被测物密度天然不同（同步原语域的每用例断言点天然多——状态机状态多；日志域天然少——输出即结果）——库级单值会把域间合理差异误报成异常；域级密度 + 全库中位数的相对偏离 = 把"和同伴比"作为基准——同伴中位数是自适应基线（库在长，基线随长）。代理指标的哲学（判据行论证）：覆盖的真指标是"断言测的是不是该测的"——那是语义判断，机器做不了；密度是它最便宜的代理（数字即得），代理的用法是引发复核而非替代判断——判据行声明这一"代理不越权"的边界，这是对指标游戏化的制度化防御。现有内核接入：无。Windows 对比：代码覆盖率工具的密度视图（每模块测试密度）同形态同局限（业界同样声明密度非覆盖）。M-229 复测：四列对账 + 中位数计算 + 双侧异常带 + 提问清单输出。
