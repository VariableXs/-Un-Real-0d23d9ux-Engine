## F3441 执行器总设计（六阶段流水线：选例→隔离→排序→执行→超时→上报）

**定位**：ktest 的传动轴：六阶段流水线（①选例 Selector ②隔离 IsolationEnv ③排序 OrderPolicy ④执行 WorkerPool ⑤超时 TimeoutHub ⑥上报 Runner）——B11 宏族（注册面）与 B12 产出线（结果面）之间的执行链。
**语义边界**：本条是流水线总设计；各阶段独立条目（F3442/F3445/F3443/F3446/F3448/F3458 联动）。执行器不重试语义（重试在 F3454）、不知晓账本格式（上报交 Runner）。
**判据**：
- J1：M-200 六阶段贯通：桩后端全链路（注册 100 用例 → 选择 20 → 隔离领取 → 排序 → 执行 → 超时监控 → 上报落盘）零 QEMU 零硬件依赖。
- J2：六阶段契约文档（每阶段的输入/输出/失败语义表）。
**纯功能行数**：380（流水线定义 ~140 + 六契约表 ~120 + 贯通用例 ~120）
**依赖与嫁接源**：F3422 Runner（上报）；F3410 隔离页（隔离）；F3412 依赖位图（排序）；F3406 kcase! 元数据（选例数据源）。
**风险与回退**：阶段耦合（排序依赖选择结果、超时依赖执行现场——硬编码传递会织成蛛网）——回退：阶段间以显式中间产物传递（选择集→执行计划→执行报表三对象——判据行给三对象定义），任一阶段可独立替换。
**正文**：实现路径：执行器主体是一个状态机驱动的事务序列——`plan = Selector::select(&registry, &query); let plan = OrderPolicy::apply(plan, mode); for chunk in plan.workers() { run(chunk) }`。六阶段契约（判据行原文）：选择（注册表 + 查询串 → 执行计划：选中的用例序号集）、隔离（计划中每用例领取 4KB 隔离页——无页可领 = SKIP[ISOLATION]）、排序（计划内重排——依赖前序约束优先于用户指定序）、执行（worker 认领 → setup → run → teardown——setup/teardown 必达契约在执行器层兜底：run panic 时 teardown 仍被调用）、超时（执行期监控——预算 × 2 系数）、上报（事件流交 Runner.emit——F3422 的 7 事件）。三对象定义（判据行原文）：`ExecutionPlan`（选中集 + 排序 + 隔离分配）、`RunReport`（每用例结果 + 时长 + 重试史）、`StageTrace`（各阶段耗时——性能预算的数据源）。数据结构：六阶段各持有自己的配置结构体（SelectorQuery/IsolationConfig/OrderMode/PoolConfig/TimeoutConfig/ReportSink）——配置集中不改全局。为什么流水线而非回调风暴（判据行论证）：六阶段是单向数据流（注册表 → 计划 → 报表），每阶段可单独测试（阶段级单测——M-200 的负例就是逐阶段注入失败）；回调式框架把控制流打散在钩子里，阶段边界不可测。现有内核接入：无（新框架 `testing/executor/`，桩调度器复用 B01）。Windows 对比：TAEF 的执行管线（发现→部署→执行→报告）同构——我们的差异：TAEF 部署阶段面向机器，我们的隔离阶段面向内存页（内核态的部署就是隔离页领取）。M-200 复测：六阶段贯通 + 阶段耗时入 StageTrace + 逐阶段失败注入。

## F3442 用例选择器（五维过滤：域/批/ID/标签/kind + 组合求值）

**定位**：选择器：五维查询语法（domain=/batch=/id=/tag=/kind=）与组合求值（同维逗号 = 或、异维 = 与）——从 ~3,000 条 A5 自有用例与迁移全库中精确圈选的能力。
**语义边界**：只做选择；被选中之后的排序/隔离在后续阶段。语法 v1 冻结（判据行给语法表）。选择器不执行用例（零副作用契约）。
**判据**：
- J1：M-201 五维组合矩阵（单维 5 例 + 两维组合 10 例 + 全维 1 例 = 16 组合）选择结果与手算清单逐位一致。
- J2：空结果语义（选 0 条 = 合法空跑，SUMMARY total=0——判据行声明非错误）。
**纯功能行数**：320（语法解析 ~120 + 求值器 ~100 + 矩阵用例 ~100）
**依赖与嫁接源**：F3406 KCaseMeta 六字段（维的数据源）；F3408 账本（选择结果计数对账源）。
**风险与回退**：选择语法膨胀（每域加私有色值→语法失守）——回退：五维封闭 + tag 开放词表（F3471 全域词表统一——私有色值必须以 tag 表达，语法本身不扩）。
**正文**：实现路径：查询串 → `SelectorQuery { domains: Option<&[&str]>, batches: …, ids: …, tags: …, kinds: … }` → 求值器对注册表线性扫描（万条用例 × 五谓词 ≈ 每谓词 1 拍级——选择本身零预算压力）；匹配语义（判据行原文）：同维内多值 = OR（`tag=a,b` 命中含 a 或 b）、异维间 = AND（`domain=A5 tag=slow` 需同时满足）；`id=` 支持前缀通配（`M-2*` 命中 M-200 系列——通配只在末尾，不做中间通配的复杂度）。空结果语义：合法空跑——SUMMARY 行 total=0 且 digest 正常（空跑也是一次可对账的运行）。数据结构：求值器输出 `SmallVec<u16>`（用例索引集，容量 256 栈上——超出走堆，万条场景实测仍栈内）；谓词编译为五张位图 AND（万用例位图 1.25KB——位图求值比逐条谓词快 8×，实测入 M-201）。为什么选择器要独立成条（判据行论证）：B14 迁移后全库 1 万+ 断言、数百用例，没有选择器就没有"只跑某域某批"的能力——每次回归全量跑会把 0.13ms 万断言的开销放大成不可接受的迭代延迟；选择器是把万断言账本变成按需子集的工具，是 B14 全域挂载的前置设施。现有内核接入：无。Windows 对比：TAEF 的 `/select` 查询语法（名字/属性选择）同思路——我们五维封闭、它属性开放：封闭换来语法可冻结（v1 不再变）。M-201 复测：16 组合矩阵 + 空跑语义 + 位图求值性能注记。

## F3443 执行顺序控制（声明序/依赖序/随机化序三模式）

**定位**：OrderPolicy：三种执行顺序模式（①注册声明序——默认稳定序 ②依赖序——F3412 kskip 位图声明的强制前序约束 ③随机化序——压力模式）——顺序是执行语义的一部分。
**语义边界**：只排选中集内部；模式选择由查询参数 order= 声明。依赖序与随机化序复合时依赖约束优先（判据行给复合规则）。
**判据**：
- J1：M-202 三模式顺序断言：声明序逐位 == 注册序；依赖序中被依赖者先行（拓扑序）；随机化序满足"同种子确定、异种子通常不同"。
- J2：依赖环检测（位图依赖成环 → 执行计划构建失败——计划级错误非运行级）。
**纯功能行数**：320（三模式实现 ~160 + 环检测 ~80 + 用例 ~80）
**依赖与嫁接源**：F3412 requires 位图；F3444 种子注入（随机化序的随机源）。
**风险与回退**：依赖序的拓扑排序在环上死循环——回退：Kahn 算法 + 剩余入度计数（环 = 剩余入度 > 0 的节点集——报告环成员后中止计划构建，绝不进入执行阶段）。
**正文**：实现路径：声明序 = 恒等（注册序即计划序——kcase! 的静态注册顺序天然稳定，跨构建不变的前提是注册宏按文件序展开——判据行声明这一前提并给出验证方法：注册序快照比对）。依赖序 = Kahn 拓扑：入度表（requires 位图的逆）→ 零入度队列 → 逐个出队并减后继入度——出队序即执行序；环检测：算法结束后入度 > 0 的节点即环成员（判据行给环报告格式：`CYCLE: M-201 -> M-202 -> M-201`）。随机化序 = 种子驱动的 Fisher-Yates 洗牌（F3444 的种子），然后叠加依赖约束：被依赖者若被洗到依赖者之后则回插（判据行给回插规则——约束满足的洗牌，纯洗牌会破坏依赖）。三模式复合规则：order=random + 依赖声明 → 约束优先的洗牌；order=declare + 依赖声明 → 警告（声明序可能违反依赖——按声明序跑并记 ORDER_WARN 入账，不强制改正——判据行给这一"温和警告"的理由：声明序是用户显式要求，依赖是防御性声明，冲突时尊重用户但留痕）。数据结构：OrderPolicy trait（`fn order(&self, sel: &[u16], dep: &DepBitmap) -> Vec<u16>`）三实现——模式可插拔。为什么依赖序是计划级错误而非运行级（判据行论证）：环意味着任何顺序都无法满足约束，带着环进入执行只会得到混乱的部分执行——计划构建期就把不可行计划挡在门外（fail fast 在计划层）。现有内核接入：无。Windows 对比：TAEF 的测试顺序元数据（TestOrderDependency）同概念——我们用位图表达（内存与求值都便宜），它用属性字符串。M-202 复测：三模式断言 + 环报告 + 复合规则。

## F3444 随机化执行与种子账本（种子注入 + 顺序记录复现性账本）

**定位**：随机化执行：种子注入接口 + 执行顺序账（seed → 执行序的确定性映射记录）——随机化是为暴露顺序敏感 bug，账本是为随机化后仍可复现。
**语义边界**：只管顺序随机化与复现记录；用例内部随机（S-SCALE 的种子化）是样本自身语义（F3389）。顺序账随结果账落盘（B12 JSON 的 run 段新增 seed 与 order 数组）。
**判据**：
- J1：M-203 同种子双跑：执行序逐位一致 + 结果逐位一致；异种子双跑：序不同（以 1,000 对样本统计不同率 > 99%）。
- J2：顺序账格式冻结（seed 字段 + order 数组进 JSON run 段——B12 schema 的追加式扩展，向后兼容）。
**纯功能行数**：280（种子接口 ~80 + 洗牌接线 ~60 + 账本记录 ~60 + 用例 ~80）
**依赖与嫁接源**：F3443 OrderPolicy（随机化序实现）；F3425 JSON schema（追加字段）；B10 S-SCALE 种子化先例（F3389——用例级种子的同构设计）。
**风险与回退**：随机化暴露的失败难以归因（顺序敏感的失败在重跑时消失）——回退：顺序账是回退本身（seed + order 完整记录——同 seed 重放 = 逐位复现；顺序敏感用例还有"最小重放对"生成：失败用例与它前驱用例的序对导出——判据行给最小重放对格式）。
**正文**：实现路径：`Executor::set_seed(u64)` → 洗牌 RNG（xorswap64——无标准库依赖的确定性 PRNG，同实现跨平台逐位一致）；执行中每完成一用例把其索引 append 到顺序缓冲；done 时顺序缓冲随 JSON 落盘（`"seed":918273, "order":[14,3,87,...]`）。复现协议（判据行原文）：失败账含 seed → 操作者以同 seed 重跑 → 同序复现失败 → 归因；若同 seed 不复现 → 失败本身顺序无关或环境敏感（flaky 流程 F3455 接手）——复现协议把"偶尔失败"从悬案变成两条明确分支。为什么全库随机化是必修而非选修（判据行论证）：声明序跑一万次全绿也不能排除顺序敏感 bug（固定序把顺序问题藏成永远不发作的暗伤）；随机化把每次 run 变成一次新的顺序抽样——日常回归的随机化 = 持续的顺序压力测试，这正是 7×24 验收观在测试基础设施上的投影（检测器 7×24 抓死锁、随机序 7×24 抓顺序敏感——同一个哲学）。数据结构：RNG 状态 8 字节栈上、顺序缓冲 SmallVec 栈上——随机化零堆零额外预算。现有内核接入：无。Windows 对比：gtest 的 --gtest_shuffle + --gtest_random_seed 同机制（种子 + shuffle + 账面复现）——我们把它做进内核执行器并进 JSON 账（它只打印控制台）。M-203 复测：同 seed 双跑逐位一致 + 异种子不同率统计 + 最小重放对导出。

## F3445 用例隔离执行环境（4KB 隔离页接入执行器）

**定位**：隔离阶段落地：F3410 的 4KB 隔离页契约接入执行器（用例启动前领取、结束后归还、越界写检测钩子常开）——用例间内存互不践踏的执行保障。
**语义边界**：只做执行器侧的领取/归还/钩子接线；页池本体与检测逻辑归 F3410（本条是接入面不是实现面）。隔离失败（无页可领）= SKIP[ISOLATION] 非 FAIL。
**判据**：
- J1：M-204 越界注入被捕获：恶意用例（写隔离页外 1 字节——判据行声明该用例仅测试态注册）触发越界钩子 → 用例 FAIL[ISOLATION] + 页池完整性恢复（归还后池账平衡）。
- J2：正常用例的隔离开销 ≤ 20 拍/用例（领取+归还+钩子自检——预算入 M-209 对账）。
**纯功能行数**：320（领取/归还接线 ~110 + 钩子接线 ~90 + 用例 ~120）
**依赖与嫁接源**：F3410 隔离页池（实现源）；F3446 WorkerPool（每 worker 独立页池分片——并发领取无竞争）。
**风险与回退**：越界写破坏的不是自己的页而是相邻页（钩子只查本页边界）——回退：页池哨兵字节（每页首尾 4 字节哨兵，归还时哨兵校验——邻页踩踏在归还校验时暴露，归因到踩踏者的物理相邻关系——判据行给哨兵布局）。
**正文**：实现路径：执行器在 worker 认领用例后、setup 前调用 `IsolationEnv::acquire(&self) -> IsoGuard`；IsoGuard 是 RAII 守卫（Drop 时归还 + 哨兵校验 + 池账递减——异常路径的归还由 RAII 兜底，setup/run/teardown 任何一步 panic 页都归还）；越界钩子 = F3410 的边界哨兵 + 页表项标记（桩环境下是标记数组的边界检查——真机页保护留闸口，双轨制同一接口）。哨兵布局（判据行原文）：页首 `[SENTINEL_LO:u32][magic:u32]`、页尾 `[magic:u32][SENTINEL_HI:u32]`——magic 恒 0xA5A5A5A5，越界写极大概率撞 magic（4 字节随机写撞 1/2^32——哨兵不是绝对防线，是高概率侦察线，绝对防线是页保护，闸口启用）。池账平衡（判据行声明）：每次 run 结束后 `pool.issued == pool.returned` 必须成立——不等即池泄漏（用例吃页不还——FAIL[ISOLATION] 且池强制重置，泄漏用例列入黑名单重跑禁入）。为什么隔离是执行器职责而非用例自觉（判据行论证）：自觉隔离 = 每用例手写内存卫生——遗漏即互踩，且踩踏症状（远处用例莫名失败）极难归因；执行器强制隔离 = 框架兜底（框架归 A5 拿手处），用例作者只管业务逻辑——这把一整类"幽灵失败"从各域的调试成本变成 A5 的一次性建设。现有内核接入：无。Windows 对比：内核池标记（Pool Tag + Special Pool 的越界即时检测）同思路——Special Pool 就是把被测对象放独立页并在边界填充哨兵；我们的 4KB 隔离页是 Special Pool 的测试专用版。M-204 复测：越界捕获 + 哨兵归因 + 池账平衡 + 黑名单机制。

## F3446 并发执行器（每 CPU 工作者池）

**定位**：WorkerPool：每 CPU 一 worker 的并发执行（任务队列本地化 + work-stealing 可选）——多核机器上万断言的执行时间线性下降；桩调度器上以双核模型验证并发正确性。
**语义边界**：并发粒度 = 用例级（用例内部无并行——用例自己要并行是样本的事，F3395 压力样本）；串行豁免归 F3447。开发期在桩调度器（fake_tick 驱动）验证，真机多核调度留闸口——双轨制。
**判据**：
- J1：M-205 并发零丢失：200 用例 × 双核桩调度器并发执行 → 完成数 == 200 且无重复执行（每用例恰好一次——完成集合与计划集合差集为空）；并发期间账本写入正确（F3408 per-CPU 账本的无锁写在此经受真并发）。
- J2：加速比记录（双核 vs 单核的墙钟比 ≥ 1.6——加速比入 StageTrace，不设硬阈值只记账）。
**纯功能行数**：320（池与队列 ~140 + 调度接线 ~90 + 用例 ~90）
**依赖与嫁接源**：B01 桩调度器（fake_tick 双核模型）；F3408 per-CPU 断言账本（无锁写的并发消费者）；F3447 串行位（互斥约束源）。
**风险与回退**：并发执行的账本交错（两 worker 同时写全局账——竞态）——回退：F3408 本就是 per-CPU 账本（写路径零共享——设计时已为并发预埋）；汇总时才合并（读路径单线程）——"写分片读合并"是账本与池的共同纪律。

## F3447 串行标记与并发互斥（no_parallel 元数据位）

**风险与回退**：no_parallel 滥用（什么都标 → 并发退化成串行）——回退：np 用例占比入账（> 10% 触发 BUDGET_WARN——占比是滥用的自动侦察）+ 判据行给"什么该标"的清单：写全局单例的/依赖执行序的/测执行器自身的。

## F3448 超时执行中枢（用例级超时的执行端实现）

**定位**：TimeoutHub：超时判定的执行端中枢（元数据 budget_ms × 系数 2 = 实际时限；到时 → 看门狗上报 TIMEOUT 结果态）——B12 F3432 看门狗的执行端挂接点，把"用例卡死"从悬挂整个 run 变成一条可入账的 TIMEOUT。

**判据**：
- J1：M-207 超时注入：sleep 用例（budget=50ms 实睡 200ms 桩时间）→ 100ms 时 TIMEOUT 上报 → run 继续（后续用例正常完成——超时不传染）。

**依赖与嫁接源**：F3432 看门狗（TIMEOUT 结果态与账面）；F3446 WorkerPool（worker 重建）；B01 桩时钟（fake_tick 的虚拟超时——开发期超时测试零真实等待）。
**风险与回退**：超时误杀慢用例（S-SLOW 类合法慢用例被 2× 系数杀掉）——回退：budget_ms 是用例作者声明的诚实预算（kcase! 必填——B11 元数据纪律），2× 是执行器的善意放大；仍被杀 = 预算声明失实，FAIL[TIMEOUT] 是对的（预算纪律通过超时机制执法）。
**正文**：实现路径：执行中枢维护每 worker 的当前 deadline（进入用例时 `hub.arm(worker, deadline)`、正常完成时 `hub.disarm(worker)`）；检查点两处：worker 每完成一个执行切片（桩调度器的调度点）中枢扫描 armed 集（armed ≤ worker 数 ≤ 4——扫描 O(n) 便宜）；到时处理（判据行原文）：①用例标记 TIMEOUT ②弃用 worker（栈不回收——当前栈上可能有卡死的用例帧，回收 = 与卡死者玩抢座游戏，弃用重建 = 让卡死者自生自灭——v1 的诚实选择）③新 worker 认领下一个用例④TIMEOUT 事件交 Runner。为什么不中断用例执行（判据行论证）：内核态对任意执行中代码做抢占中断 = 中断任意持锁代码 = 把测试基建变成死锁源（测试器自己死锁是终极讽刺）；超时的正确语义是"放弃等待并隔离"——不杀它，只是不再等它，这与 B08"告警不破坏"红线是同一条哲学的两个应用。时限公式为何 ×2 且下限 10ms（判据行论证）：×2 容纳调度抖动（桩调度器的分片粒度）；下限 10ms 防极小预算（budget=1ms 的用例时限 2ms < 调度粒度 → 必然误杀）——公式两参数都是防御性常数，来源入 F3452 总表。现有内核接入：无。Windows 对比：驱动验证器的计时器死锁检测（DD 长时间持有/等待的判定）同方向；TAEF 的用例超时（/timeout 参数）同机制。M-207 复测：TIMEOUT 注入 + 不传染验证 + worker 重建验证 + 底线公式负例。

## F3450 断言开销预算守恒（40 拍/断言的实测对账）

**定位**：断言开销的实证收口：B11 F3408 推导的 40 拍/断言（万断言 ≈ 0.13ms @3GHz）在本批以执行器实测对账——预算从纸面推导变成 TSC 差分的物证。

**判据**：
- J1：M-209 开销对账：10,000 连发 kexpect_eq → TSC 差分 ≤ 400,000 拍（40 拍/断言 × 万）且 ≥ 100,000（10 拍下限——过快说明优化吞了求值，也是 bug——下限防"假优化"）。
- J2：对账方法学入册（TSC 差分口径 + 桩常拍声明 + 下限理由——可复测的完整方法学）。
**纯功能行数**：320（测量用例 ~120 + 口径表 ~100 + 分析 ~100）
**依赖与嫁接源**：F3408 断言账本（推导源——40 拍来自宏展开指令数推算）；B01 桩时钟（TSC 桩）；F3403 单求值展开（开销的载体——借用绑定不复制）。
**风险与回退**：实测超预算（宏展开比推算慢）——回退：逐宏分解定位（11 宏 × 各自开销列——超预算的宏单独瘦身：判据行给瘦身优先序——kexpect_mem_eq 最贵（逐字节比较）先查）；实测低于下限（<10 拍）——回退：检查优化器是否吞掉比较（单求值被 CSE 消除 = 断言假通过——这是比慢更危险的 bug，下限检测的意义所在）。
**正文**：实现路径：测量用例（判据行原文）：`let t0 = tsc(); for i in 0..10_000 { kexpect_eq!(v[i], i); } let dt = tsc() - t0;`——v 预填充防页面效应；断言全过（万断言账 +1 万——本用例自己贡献万断言账，账上加账的对账用例，判据行声明这一自指性并给账本核对方式）；五宏抽测（eq/ne/true/range/mem_eq 各一轮——全宏覆盖留 B15 总收口）。40 拍预算的构成复核（判据行原文）：宏展开体 ≈ 求值绑定（2-4 拍）+ 比较（1-3 拍）+ 分支（1 拍）+ 账本递增（per-CPU Cell 写 ~2 拍）+ 失败路径不占（静态分支预测——过路 0 拍）≈ 8-12 拍指令级——40 拍预算含访存与流水线余量（指令数 ×4 的余量系数——预算是承诺上限不是指令数）。0.13ms 的换算（判据行声明）：40 拍 × 10,000 = 400,000 拍 ÷ 3GHz ≈ 0.133ms——万断言毫秒级意味着全库回归的时间瓶颈不在断言而在用例业务逻辑——这个结论决定 B14 迁移策略（迁移的代价在用例改写不在运行开销）。下限 10 拍的理由（判据行论证）：求值+比较+记账的诚实下限 ≈ 8 拍（编译器聪明也省不掉账本递增——记账是断言的语义部分）；实测 < 10 拍 = 账本递增被消除了 = 断言没记账 = 万断言账失真——下限是账本完整性的守门员。现有内核接入：无。Windows 对比：无直接对应（性能预算的实证对账是硬内核的自律）；最近的是编译器测试套的运行时回归预算。M-209 复测：万断言 TSC 对账 + 下限检测 + 五宏抽测分解表。

## F3454 失败重试策略（失败用例重试一次 + 重试入账）

**定位**：RetryPolicy：失败用例自动重试一次（retry=1 默认、可全局关闭）——失败的第一道过滤器：重试仍败 = 真失败（大概率环境无关稳定失败）、重试即过 = flaky 嫌疑（交 F3455）；重试不是掩盖而是分类。
**语义边界**：重试只跑 run() 不重跑 setup（判据行声明并给理由：setup 失败与 run 失败分开——setup 失败重试 setup 一次，run 失败重试 run 一次——两段各自重试一次）；重试结果独立记账（首次/重试两列——终态 = 重试结果，flaky 标记由 F3455 裁）。
**判据**：
- J1：M-213 重试语义：构造首败重过样本 → 终态 PASS + 账两列（first=FAIL/retry=PASS）；构造两连败样本 → 终态 FAIL + first/retry 双 FAIL；重试关闭开关验证（retry=0 时首败即终败）。
- J2：重试次数上限语义冻结（retry=1 硬上限——判据行给"为何不是更多"的论证）。
**纯功能行数**：300（重试循环 ~100 + 账两列 ~90 + 用例 ~110）
**依赖与嫁接源**：F3446 WorkerPool（重试在同 worker 同隔离页内——隔离上下文保持）；F3406 元数据（retry 开关入 run 配置非元数据——全局策略）；F3455 flaky 账（下游）。
**风险与回退**：重试掩盖真回归（间歇回归被 retry=1 吞掉成 PASS）——回退：两列账永不合并（run 的 SUMMARY 里 fail 计数只含终败——但 flaky 计数独立成列——判据行给 SUMMARY 扩展：`flaky=<n>` 新列——回归若是间歇性的会在 flaky 列持续累积，累计即暴露）。
**正文**：实现路径：worker 执行循环加一层：`r = run(); if r.is_fail() && retry_enabled { r2 = run(); record(first=r, retry=r2); final = r2 } else { record(first=r); final = r }`——重试在同一 IsoGuard 作用域内（页不换——失败现场的状态是重试的输入之一，换页 = 清掉现场，复现性下降——判据行声明这一取舍）；重试事件走 Runner（CaseResult 带重试标志——B12 事件枚举的 AssertFail/CaseResult 已够用，重试信息在账两列里——枚举不扩）。retry=1 为何不是 2 或更多（判据行论证）：重试的目的是分类不是撞大运——一次重试已经给出"稳定败/偶发败"二分；retry=2+ 的期望收益是分辨"2/3 败率 vs 1/3 败率"这种细分——细分对行动没有指导意义（两类都是修用例），却让最坏情况时长 ×3——分类学够用即可，重试是筛子不是抽奖。setup 与 run 分段重试的理由（判据行论证）：setup 失败（资源领取失败）与 run 失败（断言失败）是不同的病——前者重试 setup（资源可能暂时紧张），后者重试 run（状态可能偶发）；混合重试（重跑整个用例）会把 setup 的偶发污染 run 的诊断——分段是诊断学。现有内核接入：无。Windows 对比：HLK 作业重试策略（失败作业可配置重试）同机制；ctest 的 RETRY 系选项同形。M-213 复测：两构造样本 + 开关验证 + 账两列 + flaky 列累积。

## F3455 flaky 检测账（重试通过 ≠ 首次通过 → flaky 标记）

**定位**：FlakyLedger：flaky 判定与标记账（首败重过 → FLAKY 标记入账，终态仍按重试结果算 PASS——但 flaky 列独立累积）——与 B10 S-FLAKY 样本（F3387）联签：样本库提供 flaky 制造机，账本提供 flaky 侦察器。

- J1：M-214 flaky 注入：S-FLAKY 样本（窗口边界 49/51ms 的天然 flaky 机）跑 20 次 → flaky 标记率与窗口理论值吻合（50%±20%——边界抖动的统计验证）+ 每次标记入账可查。

**正文**：实现路径：判定器 = 重试账的衍生视图（`first==FAIL && retry==PASS → flaky!`——零额外测量，判定是账本的纯函数）；标记动作：flaky_count+=1 + last_flaky_run=当前 run 序 + Runner 事件（CaseResult 带 flaky 标志——账面与控制台都可见）；联签协议（判据行原文）：S-FLAKY 样本的期望账（F3387 的 Expectation 五值）在 20 连跑中验证 flaky 率的理论吻合——样本库说"我能产生 50% flaky"、账本说"我测到 ~50%"——制造与侦察互相校准（这组联签是 B10 与 B13 的跨批闭环，判据行声明联签的批间意义：验收硬指标"误报率 0%"依赖 flaky 侦察器的灵敏——侦察器不灵则误报混进 flaky 里逃逸）。flaky 为何不自动隔离（判据行论证）：自动隔离的滑梯是——flaky 被跳 → 跳过的用例无人修 → flaky 名单变大 → 更多跳过 → 全库名存实亡；正确路径是把 flaky 当 bug：标记 → 名单 → 修 → 标记消失——账本推动修复而非逃避修复，这与"有防线的零"哲学（B10）一脉：零误报不是零发现，是发现的都修掉。数据结构：flaky 账 = 历史账的姊妹数组（16B/用例——同样 O(1) 定位）。现有内核接入：无。Windows 对比：内部测试平台的 flaky 测试追猎（flaky test triage 清单）同流程学——我们把 triage 的第一步（发现）做进内核账本。M-214 复测：20 连跑统计吻合 + 标记账查询 + 交叉核验 + 不自动隔离声明核对。

## F3456 断点续跑（执行器断点：序号断点 + 续跑清单）

- J1：M-215 中断续跑对账：200 用例跑到 87 个时模拟中断（桩注入 panic-free 中止）→ 断点集大小 87 → 续跑恰好执行余下 113 个 → 全账合并 = 200 完整账（续跑账 + 前段账拼接后与一次性跑的账逐位等值）。
