## F3421 双后端总设计（QEMU 后端真机后端统一抽象，开发期零 QEMU 双轨制）

**定位**：双轨制的产出线化：后端 = 执行环境 + 输出通道的统一抽象——开发期桩后端（纯 Rust 单机进程，零 QEMU）、真机后端（闸口物理机）同接口异实现；ktest 用例两后端行为一致是双轨制的核心承诺。
**语义边界**：本条是设计总纲；Runner 接口在 F3422、串口实现在 F3423。后端不改变用例语义（判据行声明：用例对后端透明——同一二进制可跨后端跑，编译期仅 feature 选默认后端）。
**判据**：
- J1：M-180 桩后端全链路：用例注册 → 桩后端执行 → KV 行输出 → JSON 账落盘——四步零 QEMU 零硬件依赖（纯宿主进程可跑——判据行声明桩后端的宿主环境要求）。
- J2：设计文档四节：抽象定义/后端清单/双轨制承诺/真机路径。
**纯功能行数**：440（抽象定义 ~150 + 后端清单 ~130 + 双轨承诺 ~90 + 真机路径 ~70）
**依赖与嫁接源**：F3417 接口约定 v0.9（升级依据）；F3422 Runner；双轨制纪律（总纲）。
**风险与回退**：桩后端与真机后端的行为分叉（环境差异导致用例结果不同）——回退：后端透明性契约（判据行：用例禁止探测后端——探测即用例 bug）+ 差异白名单机制（硬件依赖类用例经 F3413 requires 声明——机制化的环境差异，非分叉）。
**正文**：抽象定义（判据行原文）：后端 = `Runner`（F3422 接口）的具体化——桩后端（`HostRunner`：宿主进程内执行、输出到内存缓冲——开发期的主力，B01–B15 全部判据在它上面跑）、串口后端（`SerialRunner`：目标机 COM1 输出——闸口真机的产出线）、内存盘后端（`MemDiskRunner`：目标机直接落盘——真机的完整版产出线）。双轨制承诺的精确化（判据行原文）：①开发期（本批至 B15 收口）：桩后端跑全部判据——零 QEMU 零硬件；②闸口期：真机后端复跑全库（B15 F3499 的验收对照）——两期用同一用例集、同一账本格式——双轨不是两套测试，是一条产线的两个工位。真机路径声明：SerialRunner 的物理写口（16550 寄存器）v1 全桩（寄存器模型模拟）——真寄存器写是闸口动作（硬件安全红线内的合法写，但留给闸口执行）。为什么后端抽象是双轨制的工程本体（判据行论证）：没有统一抽象，桩环境的验证结果无法宣称"真机也成立"（验证的生态位断裂）；抽象统一后，桩验证 = 真机预演（同一判据集），闸口只做"环境差异"的最后核对——闸口工作量从"全量重验"压缩为"差异核对"（判据行给工作量对比）。现有内核接入：无（新框架 `testing/runner/`）。Windows 对比：HLK 的"主机-目标"架构（宿主驱动目标机执行）是我们双后端概念的商业级对照——我们的差异：宿主也是后端（桩），不止是调度端。M-180 复测：四步全链 + 宿主进程内零硬件符号（链接检查）。

## F3422 后端抽象 trait（Runner 接口设计）

**定位**：Runner trait：init（后端初始化）/emit（输出事件——KV 行与 JSON 片段的统一入口）/flush（冲刷）/done（收尾签名）四方法——后端契约的最小完整集。
**语义边界**：只做 trait 与三实现（桩/串口桩/内存盘桩）的骨架；协议内容在 F3424、JSON 在 F3425。trait v1 冻结（判据行给冻结声明与扩展路径）。
**判据**：
- J1：M-181：同一套 10 用例跑三后端 → 三份输出经各自适配层规范化后逐语义等值（KV 行集合等值 + JSON 账等值）——后端透明性兑现。
- J2：trait 签名冻结（v1）——变更 = ADR；四方法的最小性论证（每个方法删掉会缺什么——判据行给论证）。
**纯功能行数**：360（trait 定义 ~110 + 三实现骨架 ~150 + 等值验证 ~100）
**依赖与嫁接源**：F3417 约定书；F3424/F3425 协议。
**风险与回退**：emit 的粒度歧义（行级还是字节级）——回退：emit 语义 = 结构化事件（枚举 RunnerEvent：CaseStart/AssertFail/CaseResult/SuiteSummary...——判据行给事件枚举表），行/JSON 的格式化是 emit 下游——语义级接口而非文本级。
**正文**：实现路径：`trait Runner { fn init(&mut self, meta: &RunMeta); fn emit(&mut self, ev: RunnerEvent); fn flush(&mut self); fn done(&mut self) -> RunDigest; }`——RunMeta（版本戳 F3434 载体）、RunnerEvent 枚举（判据行给全表：RunStart/CaseStart/AssertResult/CaseResult/CaseSkipped/Summary/Digest——7 事件）、RunDigest（汇总签名——账本摘要）。三实现骨架：HostRunner（内存 Vec 缓冲 + 宿主 stderr 镜像）、SerialRunner（帧化文本——F3423）、MemDiskRunner（F3427 落盘）。四方法最小性论证（判据行原文）：init——无则版本戳与依赖检查无处安放；emit——唯一数据入口不可少；flush——串口与盘的批量语义需要显式冲刷点；done——收尾签名（账完整性凭证）与异常检测（未 done = 异常结束——F3433 续写的判据）——删任何一个都断链。冻结声明：v1 四方法 + 7 事件 + 2 结构 = 后端契约全量，扩展 = 新事件变体（枚举加臂，trait 不变——判据行给扩展性设计）。现有内核接入：无。Windows 对比：TAEF 的执行器日志接口（I_logging）同抽象层。M-181 复测：三后端语义等值 + 事件枚举覆盖核对。

## F3423 串口输出后端（COM1 文本协议）

**定位**：串口后端：16550 类寄存器桩 + 帧化文本协议（起始帧/数据帧/结束帧 + 转义规则）——真机产出线的通信面（v1 全桩，寄存器真写留闸口）。
**语义边界**：只做串口后端桩；协议内容复用 F3424 KV 行。波特率/寄存器布局桩常量在本条（真机标定留闸口——判据行声明）。
**判据**：
- J1：M-182：输出帧格式验证（起始/数据/结束三帧结构）+ 转义（数据含帧界符时转义）+ 反向解析（帧 → 原始事件）一致；寄存器桩访问计数（真机闸口的写口清单预登记）。
**纯功能行数**：320（帧协议 ~130 + 寄存器桩 ~100 + 用例 ~90）
**依赖与嫁接源**：F3422 Runner；A4 串口桩（既有——判据行给复用登记）。
**风险与回退**：真机串口速率与桩差异（吞吐不匹配）——回退：流控预留（XON/XOFF 桩级支持——真机流控闸口验证）；判据行给流控声明。
**正文**：实现路径：帧协议（判据行原文）：起始帧 `\x02KTEST|v1|<runid>\x03`（STX/ETX 界定）→ 数据帧 `\x02<kv-line>\x03` × N → 结束帧 `\x02DONE|<digest>\x03`；转义：数据中的 \x02/\x03 → \x1b\x01/\x1b\x02（ESC 前缀转义——判据行给转义表）。寄存器桩：16550 模型（THR 传输保持寄存器/LSR 线路状态——写 THR 即帧字节序列化、LSR 应答模拟）——桩的访问序列记录 = 真机写口的"预演谱"（闸口时按谱核对真寄存器行为——判据行给预演谱的用途声明）。为什么帧化而非裸流（判据行论证）：串口是字符流（无消息边界），帧化给解析器边界 + digest 给完整性（结束帧的 digest = F3422 done 签名——账完整性凭证在传输层的落地）。现有内核接入：A4 的 16550 桩复用（判据行给复用点：寄存器模型与读写原语，帧协议为 B12 新增）。Windows 对比：KD（内核调试器）的串口协议帧化同思路（边界+完整性是调试传输的通用需求）。M-182 复测：帧结构 + 转义往返 + 预演谱记录。

## F3424 结果协议：行式 KV 输出格式

**定位**：行式 KV 协议：五类行（CASE/PASS/FAIL/SKIP/SUMMARY）的精确格式冻结——人读与机器读两用的结果流（串口与桩后端共用的行级协议）。
**语义边界**：只做行协议；JSON 账在 F3425（两种形态的关系：行 = 流式实时、JSON = 收尾全量——判据行给双形态分工）。协议 v1 冻结。
**判据**：
- J1：M-183：协议往返：事件流 → KV 行 → 解析器回读 → 事件流等值（往返一致）；五类行格式样例冻结（判据行内嵌）；非法行被解析器拒绝。
**纯功能行数**：280（五类行定义 ~110 + 解析器 ~90 + 用例 ~80）
**依赖与嫁接源**：F3422 事件枚举（行 = 事件的文本投影）；A1 既有格式（F3435 兼容源）。
**风险与回退**：字段扩展破坏解析器（新字段插中间）——回退：字段追加式规则（新字段只许追加行尾——判据行给前向兼容规则，解析器忽略未知尾字段）。
**正文**：五类行格式（判据行原文）：`CASE <domain>-<batch>-<id> kind=<k> budget=<ms>`、`PASS <id> asserts=<n> dur=<us>`、`FAIL <id> asserts=<n>/<f> at=<file>:<line> msg=<diag>`、`SKIP <id> reason=<r>`、`SUMMARY total=<N> pass=<p> fail=<f> skip=<s> asserts=<A> digest=<d>`——行尾字段追加式（前向兼容）。解析器：行首关键字分派 + 字段序解析（未知尾字段忽略——兼容规则落地）+ 非法行（缺关键字/字段畸形）拒绝并计数（PARSER_REJECT——解析器自身的健壮性入账）。双形态分工（判据行论证）：行协议在用例执行时实时输出（串口场景的观察者能实时看进度——HLK 场景的人机协作）；JSON 在 done 时落盘（机器核对用）——实时流 + 全量账 = 两种消费模式。现有内核接入：A1 既有格式的兼容映射归 F3435。Windows 对比：TAEF 的控制台输出行协议同形态。M-183 复测：往返等值 + 五类行样例 + 非法拒绝 + 尾字段兼容。

## F3426 JSON 序列化器（无依赖手写、栈上预算）

**定位**：手写 JSON 序列化器：零外部依赖（无 serde——内核 no_std 约束）、零堆分配（写调用方缓冲）、栈预算 2KB（递归深度 ≤ 4——判据行给深度与预算的绑定）。
**语义边界**：只做序列化（写）；解析只做校验器需要的最小子集（F3428）——全量解析器不做（判据行声明：内核内不需要通用 JSON 解析，账的读端在验收机——宿主工具链）。
**判据**：
- J1：M-185：序列化-最小解析往返一致（数字/字符串/数组/对象四型）；栈峰值 ≤ 2KB（栈水位计测量）；转义正确性（引号/反斜杠/控制字符）。
**纯功能行数**：360（写器 ~160 + 转义 ~100 + 用例 ~100）
**依赖与嫁接源**：F3425 schema；F3405 缓冲惯例。
**风险与回退**：深度嵌套超栈（schema 非法输入）——回退：深度计数器硬断（>4 拒写 + 记账——防御式深度，判据行给拒绝行为）。
**正文**：实现路径：`JsonWriter { buf: &mut [u8], pos, depth }`——流式写（对象/数组/字符串/数字/布尔五原语 + 键值便利方法）；字符串转义表（判据行给表：`"`→`\"`、`\`→`\\`、控制字符→`\u00XX`、中文/UTF-8 直通——判据行声明 UTF-8 直通的理由：诊断串可能含源码标识符，UTF-8 安全转义 = 保持原字节）；数字格式（整数全支持/浮点不支持——F3402 已声明无浮点判据）。栈预算：写器本身迭代（无递归——schema 的五段结构固定，用模板化写函数逐段展开——判据行给模板化论证：schema 固定则写函数可完全静态化，递归无从发生，深度计数器是防未来误用的保险丝）。往返验证的最小解析器：只识别 schema 已知键 + 值类型——校验器共用（F3428 复用——判据行给复用声明）。现有内核接入：无。Windows 对比：手写序列化是内核开发常态（no_std 生态）；宿主侧对照物是 serde_json——判据行声明两侧分工（内核写、宿主读）。M-185 复测：四型往返 + 栈水位 + 转义表逐项 + 深度拒绝。

## F3427 结果落盘（内存盘文件写入）

**判据**：
- J1：M-186：写-读往返一致（落盘账 == 回读账）；滚动（第三次写后 last-2 存在、最旧被顶替）；写失败（盘满桩）→ 记账不崩。
**纯功能行数**：280（写入器 ~110 + 滚动 ~90 + 用例 ~80）
**依赖与嫁接源**：F3422 MemDiskRunner；A2 内存盘桩；F3433 续写。
**风险与回退**：写一半崩溃（断电场景）——回退：写临时文件 + 原子改名（rename 语义——判据行给原子性方案：last.json.new → rename → last.json，改名是崩溃安全的提交点）+ 部分账的续写辨认（F3433）。
**正文**：实现路径：写入流程：`open(/var/ktest/.tmp) → 写账 → flush → rename(.tmp → last.json)`——原子改名方案（判据行论证：改名在同一内存盘上是指针操作级原子，崩溃要么旧账完整要么新账完整——不存在半账作为 last.json——经典的 commit-point 模式）；last-1/last-2 的滚动：rename 前 last → last-1、last-1 → last-2（链式轮替）。回读接口：`read_last() -> Result<Account>`——宿主侧验收工具（闸口）从串口或盘提取账后与运行摘要核对的入口。盘满路径：桩容量限制注入 → 写失败 → DISK_FULL 记账 + 上一份账保留（失败不毁旧账——判据行给该语义：凭证库的"至少一份完整"保证）。现有内核接入：A2 内存盘桩（复用登记——A2 未交付期用静态缓冲桩 64KB——判据行给桩容量与 64KB 预算的呼应：F3425 的万断言账 ≤ 64KB 正好一页）。Windows 对比：写临时文件 + MoveFileEx 原子替换是 Windows 生态的标准崩溃安全写——同模式。M-186 复测：往返一致 + 滚动三份 + 盘满保旧账。

## F3428 结果账校验器（schema 合法性自查）

**定位**：校验器：账的 schema 合法性（逐段字段/类型/值域）+ 计数自洽性（sum(case asserts) == summary、digest 复算一致）——结果账的"数字要核对"关卡（账自己能证明自己没坏）。
