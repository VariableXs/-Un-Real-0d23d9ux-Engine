## F3361 时间窗模型：TSC 时钟基准与窗口定义

**定位**：时间观测的语义宪法：基准钟（TSC 经 F3204 封装）、窗口三级制（微窗 1ms/秒窗 1s/分窗 60s）、时间量纲与换算表——B09 全部条目的时间语义源头。
**语义边界**：本条是模型；记账在 F3362/F3363、告警在 F3364+。模型承认的时钟缺陷（TSC 跨核非严格同步——不变性假设声明）写入不做清单。
**判据**：
- J1：M-120：窗口边界行为——事件恰在窗口边界（±1 拍注入）的归属规则明确且稳定（边界归左窗口）；三级窗口换算表核对。
- J2：模型文档四节：基准/窗口/量纲/缺陷声明。
**纯功能行数**：320（模型定义 ~120 + 窗口实现 ~110 + 边界规则 ~90）
**依赖与嫁接源**：F3204 TSC 封装（B01 唯一读钟点）；F3212 直方图（窗口聚合体例）。
**风险与回退**：TSC 跨核漂移（真机上 TSC 不变性依赖 CPU 特性）——回退：模型声明"假设 TSC 不变核"（目标硬件支持——判据行给 CPUID 检查计划，真机闸口验证），开发期桩时钟恒定。
**正文**：模型定义（判据行原文）：①基准钟 = TSC（F3204 封装的 `read_tsc()`，RDTSC 指令，~20 拍）；②窗口三级：微窗（1ms——等待/持有记账的采样窗）、秒窗（1s——告警去重窗 F3365、退避基准 F3370）、分窗（60s——误报率统计窗 F3374）；③量纲换算：TSC 拍 → 纳秒（目标硬件标定频率，v1 = 3GHz 假设 + 闸口标定覆盖——换算系数是单一常量，判据行给标定协议）；④边界规则：事件 tsc ∈ [窗口起点, 窗口终点) 归该窗（左闭右开——边界归左，M-120 验证）；⑤缺陷声明：TSC 跨核假设不变（不变核 = invariant TSC CPUID 位），多核时钟读序的微漂（±几十拍）对 ms 级窗口无影响——论证记录。为什么用 TSC 而非 tick：tick 粒度（ms 级）对"等待 10ms 告警"的判据太粗（±1 tick = ±100% 误差），TSC 拍级精度让阈值判据可信。现有内核接入：F3204 是既有唯一读钟点（B01 交付），本条零新增钟。Windows 对比：Windows 的时间观测（ETW 时间戳 = TSC 或 QPC）同基准哲学；其 KeQueryInterruptTime 的 tick 精度即我们弃用的方案——判据行给弃用理由对照。M-120 复测：边界注入 ±1 拍 × 100 次，归属 100% 稳定 + 换算表逐级核对。

## F3362 长等待账本（每锁等待时长记录）

**定位**：等待时长的账本化：每锁实例记录"每次阻塞等待的时长"（F3343 挂边 tsc → F3344 摘边 tsc 差），聚合为分布桶 + 时间窗计数——时间告警的数据源。
**语义边界**：只做记账与聚合；阈值告警在 F3364、修正（抖动）在 F3368。记账点复用边生命周期（零新增钩子——判据行声明复用）。
**判据**：
- J1：M-121：注入已知等待时长（桩控制摘边延迟）× 100 → 账本记录与注入值逐条对账（±窗口精度）；分布桶计数正确。
**纯功能行数**：340（记账结构 ~120 + 聚合桶 ~120 + 用例 ~100）
**依赖与嫁接源**：F3343/F3344 边生命周期；F3212 直方图体例；F3361 窗口。
**风险与回退**：等待中调度修正（F3368）与记账的次序——回退：记账先记原始值、修正独立字段（raw_wait/adjusted_wait 两列）——原始事实与修正值都保留，审计可回放。
**正文**：实现路径：挂边时 `edge.tsc = now`（F3343 已有）；摘边时 `wait_raw = now - edge.tsc` → 写入锁实例的 `WaitLedger { raw_dist: Histogram(16 桶), adjusted_dist, window_counts: [u32; 3] }`（16 桶对数间隔：1us..1s，判据行给桶边界表）。聚合三窗口：微窗内等待次数（当前 1ms 窗）、秒窗累计、分窗累计——窗口滚动时归位（F3361 滚动规则）。为什么记录原始+修正双列（判据行论证）：告警用修正值（F3368 过滤后，防误报），审计用原始值（事实不可篡改）——观测面"事实与判断分离"的原则，判据行原文记之。与 B08 的关系：账本读边 token（F3251）关联锁实例——账本是图数据的时间投影（图知道"谁等谁"、账本知道"等多久"）。现有内核接入：`cpu/sync.rs` 旧票锁无等待时长记录（自旋不睡眠），桥点登记"新能力"。Windows 对比：ETW 的 Contention 事件含等待时长（Start/Stop 事件对）——离线分析模式；我们内核内实时账本，判据行声明实时性动机（7×24 告警需要 in-kernel 判定）。M-121 复测：桩控制摘边延迟（50us/5ms/500ms 三档 × 33 次 + 1 边界）逐条对账 + 桶计数和 = 注入数。

## F3363 长持有账本（longest_hold 升级接管，对接 F3204）

**定位**：持有时长账本：把 B01 F3204 的 max/total 升级为分布账本（对齐 F3362 结构）——长持有（锁被占着不放）与长等待（被卡着等）是死锁观测的两面。
**语义边界**：只做账本升级；记账点在 F3204/F3248（已有），本条不加钩子只换聚合结构。旧字段（max_hold/total_hold）保留兼容（观测面不断档）。
**判据**：
- J1：M-122：长持注入（持有 200ms 释放）→ 账本分布桶命中 + 旧 max_hold 字段同步更新（双写一致）；M-008 复跑零 diff（兼容证明）。
**纯功能行数**：320（账本结构 ~110 + 双写桥 ~110 + 用例 ~100）
**依赖与嫁接源**：F3204 TSC 差值记账；F3248 钩子；F3362 同构结构。
**风险与回退**：双写（旧字段+新账本）的开销——回退：双写 = 同一次差值计算的两个写入点（+8 拍），可忽略；判据行给开销核算。
**正文**：实现路径：F3248 的释放链记账点扩展：`hold_raw = now - guard.tsc0`（原逻辑）→ 同时 `hold_ledger.record(hold_raw)`（新账本）→ 旧 max/total 照旧——双轨并存。分布桶同 F3362（16 桶对数），两列（raw/adjusted——持有的修正含义不同：持有者的"被抢占时间"同样修正，判据行给持有修正的定义：持有者被调度走的时间不计入持有时长，因为"占着不放"的恶意判定应基于"能跑却不放"）。接管语义（判据行声明）：本条不是重写 F3204 而是"升级聚合层"——F3204 的读钟与差值计算原封不动，账本是其下游——"桥-接管-退役"三步法中"接管"的样板（桥=F3248、接管=本条、退役=无（旧字段永久兼容保留，退役动作取消——诚实修订，判据行留痕））。现有内核接入：`cpu/sync.rs` 的 longest_hold 字段接管映射归 F3379。Windows 对比：ETW 无持有时长事件（Contention 是等待侧）——持有时长观测是 Windows 的盲区（要靠 WPA 抽样推断），我们内核内直接记——能力增量，判据行声明。M-122 复测：双写一致断言 + M-008 复跑（兼容回归）。

## F3364 告警阈值分级（warn/critical 两级 + 每锁可调）

**定位**：时间告警的阈值体系：全局默认两级（warn=10ms/critical=100ms）+ 每锁覆盖接口——阈值的治理面（谁定、怎么调、怎么审计）。
**语义边界**：只做阈值判定与分级；告警动作在 F3369、风暴抑制在 F3370。阈值单位 = 修正后时长（F3368 修正生效）。
**判据**：
- J1：M-123：注入 15ms/150ms 等待 → warn/critical 各触发且互不误触；每锁覆盖（某锁阈值改 20ms）→ 同 15ms 不再 warn。
**纯功能行数**：300（阈值结构 ~90 + 判定逻辑 ~110 + 覆盖接口 ~100）
**依赖与嫁接源**：F3362/F3363 账本；F3361 窗口。
**风险与回退**：阈值默认值拍脑袋风险——回退：默认值 = 开发期实测分布的 P99×2（判据行给默认值推导：M-060 压测的等待 P99 ≈ 5ms → warn=10ms）；真机闸口用实测分布重标定——阈值是"有推导依据的常量"不是魔法数。
**正文**：实现路径：`Thresholds { warn: u64, critical: u64 }`（全局）+ 锁实例 `override: Option<Thresholds>`；判定：`if t >= eff.critical { Critical } else if t >= eff.warn { Warn }`。为什么两级（判据行论证）：一级无法区分"需要关注"与"需要行动"；critical 用于 B08 联合判定升级（F3367——critical 的锁是图扫描的优先集），warn 用于观测趋势。每锁覆盖的治理：覆盖接口是 F3376 冻结面（受限 pub(crate)+调试口），覆盖动作记账（谁改了谁的阈值——审计要求，判据行给覆盖审计记录格式）。默认值推导（判据行实录）：M-060 加速模式等待 P99 = 2.3ms（加速倍率换算真机 ~5ms）→ warn = 2×P99 = 10ms；critical = 20×P99 = 100ms（"等待 20 倍正常时间"的语义）。现有内核接入：无。Windows 对比：Windows 无内建阈值告警（依赖人工 WPA 分析）；Driver Verifier 的死锁检测无阈值概念（等就是等）。我们把"多长算异常"变成可配置可审计的参数——验收文档可读性投资。M-123 复测：两级触发 + 覆盖生效 + 覆盖审计记录存在。

## F3365 告警去重（同一参与方窗口内只报一次）

**定位**：告警去重：同一锁（或同一环签名）在秒窗内只报一次，重复计数静默——防告警风暴的第一道闸。
**语义边界**：只做去重；风暴升级（退避）在 F3370。去重键 = (锁实例, 级别)；环告警（B08）的去重（F3349）与本条的关系：环用环签名键、时间告警用锁键——两套键两个去重表，判据行声明不合并的理由。
**判据**：
- J1：M-124：同锁同窗 5 次告警 → 报 1 次 + 静默 4 次（suppressed=4）；跨窗（下一秒窗）再告警不受去重影响。
**纯功能行数**：300（去重表 ~110 + 判定 ~100 + 用例 ~90）
**依赖与嫁接源**：F3361 秒窗；F3349 去重表体例（B08 同构复用）。
**风险与回退**：去重键太粗（同锁不同等待者被合并）——回退：v1 键 = (inst, level)——同锁的多个等待者同时超阈是"该锁慢"这一事实的多次重复，合并正确；等待者维度的告警在联合视图（F3366）里看（视图不去重）——告警压缩、视图全量，两层分工，判据行声明。
**正文**：实现路径：`DedupTable { keys: [(u64 hash, tsc); 32], ring }`——告警入口查表：命中（同 hash 且同秒窗）→ suppressed++ 不输出；未命中 → 记键输出。容量 32 环形（溢出 = 键种类爆发，强制输出——宁可重复不可吞，B08 F3354 的反向取舍同哲学：常态压缩、异常全量）。与 B08 环去重的关系（判据行声明）：环签名哈希含路径结构（多锁），时间告警键是单锁——语义不同（"这组锁互等"vs"这把锁慢"），合并会丢信息，两表并存。跨窗豁免：秒窗滚动后键自然过期（tsc 判界）——持续 10 秒的慢锁每秒告警一次（每窗一次），观测者看到"持续告警流"而不是"一次然后沉默"——告警的持续性本身就是信息，判据行给这个设计决策的论证。现有内核接入：无。Windows 对比：ETW 无去重（收集端分析工具负责）；Windows 事件日志的 Event ID 去重是收集端行为——我们内核内去重，判据行声明理由（7×24 无收集端假设）。M-124 复测：5 次/窗去重 + 跨窗再报 + 容量溢出强制输出。

## F3366 等待-持有联合视图（谁在等谁、谁占着不放）

**定位**：联合诊断视图：给定锁实例 → 一次性给出"当前等待者列表（各等多久）+ 当前持有者（持有多久）+ 阈值状态"——排障时的第一查询口。
**语义边界**：只做查询视图；数据源 = B08 图（等待关系）+ F3362/F3363 账本（时长）——视图是两源联查，无新数据。视图全量不去重（F3365 判据行声明）。
**判据**：
- J1：M-125：构造 2 等待者 + 1 持有者场景 → 视图返回 2 等待者（时长各对）+ 1 持有者（时长对）+ 阈值状态；数据与账本/图逐项一致。
**纯功能行数**：360（查询接口 ~130 + 渲染 ~130 + 用例 ~100）
**依赖与嫁接源**：F3342 图；F3362/F3363 账本；F3336 dump 体例。
**风险与回退**：两源联查的撕裂（图与账本快照时刻差）——回退：联查在单次扫描点执行（同批次快照）——撕裂限于一次扫描周期内，判据行声明容差。
**正文**：实现路径：`fn joint_view(inst) -> JointView { waiters: 图出边 × 账本时长（token 关联）, holder: 持有者身份 × F3363 时长, thresholds: F3364 生效值 }`——渲染三段式（对齐 F3336/F3317 惯例）：`== waiters (2) == cpu5 task12: waiting 45ms [warn] ...`、`== holder == cpu2 task7: holding 210ms [critical]`、`== thresholds == warn=10ms critical=100ms (override)`。联合视图的排障价值（判据行给使用剧本）：告警"pool_lock 等待 45ms [warn]" → 视图查询 → 见持有者已持 210ms [critical] → 判断方向 = 持有侧问题（长持）而非等待侧——一步视图免两次查询，诊断效率是 15 章体验标准的观测章核心。撕裂容差：图快照与账本记录同为扫描批数据（F3351 快照 + 账本窗口聚合）——同批一致、跨批微差，渲染时标注快照序号（可追溯）。现有内核接入：无。Windows 对比：WinDbg `!locks` 的单锁展开（owner + waiters + 各自时长）正是本视图的手工形态——我们把"调试器手工活"内核内自动化，判据行给 `!locks` 互译表。M-125 复测：三身份场景逐项一致 + 快照序号标注存在。

## F3367 时间窗与环检测联合判定（疑似→确认升级）

**定位**：两检测器的联合：时间告警（critical 级）的锁集合作为 B08 扫描的优先集——"疑似集合"引导全图扫描的资源倾斜，联合判定的报告合并。

**判据**：
- J1：M-126：构造"critical 时间告警 + 真环"场景 → B08 扫描优先集含该锁 → 检出提前（首窗即确认）；联合报告含时间侧数据（等待时长）。
**纯功能行数**：380（优先集接口 ~130 + 扫描联动 ~140 + 报告合并 ~110）
**依赖与嫁接源**：F3346 扫描驱动；F3364 critical 集合；F3347 报告。
**风险与回退**：优先集引导造成扫描偏食（非优先集的环延迟检出）——回退：优先集只提前不替代（全图扫描照常在窗口内轮转——判据行给调度：每窗 4 扫中 2 扫优先集、2 扫全图——偏食受控）。
**正文**：实现路径：F3364 的 critical 触发 → 锁实例入 `suspect_set`（容量 16 环形，临界集）；F3346 的扫描调度改为 `if !suspect_set.is_empty() { 扫描优先集诱导的子图（从疑似节点出发的连通分量） } else { 全图 }`——子图扫描 = 全图的局部化（环若含疑似节点必在连通分量内）；无疑似时全图常规。提前性验证：默认流程环需 2 次扫描确认（F3354），疑似集内的环首扫即入候选、次扫确认——确认延迟从"等窗口轮转"缩为"等下一扫"（判据行给时序对比）。报告合并：B08 检出报告 + 时间侧附注（环中各锁的当前等待时长——F3366 联查复用）——"结构 + 时间"一页报告。松耦合声明：B08/B09 可独立运行（B09 关闭时 B08 照常、反之时间告警独立）——模块独立性是 7×24 可运维的要求（判据行论证：任一模块故障不拖垮另一）。现有内核接入：无。Windows 对比：无对应（Verifier 单机制）；联合判定是 A5 双检测器的架构红利。M-126 复测：疑似集含入断言 + 提前确认时序 + 报告合并字段完整。

## F3368 抖动过滤（调度延迟导致的伪长等待）

**定位**：零误报的时间侧关键：等待者被调度走的时间不计入等待时长（可运行时间修正）——"等了 50ms"里可能有 40ms 是没轮到跑，只该算 10ms。
**语义边界**：只做修正计算；修正的数据依赖 = A3 的任务运行/就绪切换时刻（桩先行——判据行声明依赖与桩协议）。修正用于告警判定（F3364），原始值保留（F3362 双列）。
**判据**：
- J1：M-127：注入"等待 50ms 但其中 40ms 被调度走"场景 → raw=50ms/adjusted=10ms → 阈值 10ms 恰不触发（修正生效防误报）；未修正对照（关修正开关）→ 误告警（对照组证明修正的必要性）。
**纯功能行数**：320（修正计算 ~130 + 桩协议 ~100 + 用例 ~90）
**依赖与嫁接源**：F3362 raw/adjusted 双列；A3 调度时刻（桩）；F3361 窗口。
**风险与回退**：桩协议与 A3 实装偏差（切换时刻定义不一致）——回退：修正接口 v1 冻结（`on_run(cpu)`/`on_preempt(cpu)` 两时刻注入），A3 实装时对接验收用 M-127 复跑——协议先行，实装对表。
**正文**：实现路径：等待挂边后记录 `tsc0`；等待期间每核维护 `run_accum`（本窗运行时长累加——A3 桩注入）；摘边时 `adjusted = raw - (当前 run_accum 窗内未被调度份额)`——精确算式（判据行原文）：修正 = 等待总时长 - 该等待者在此期间的"不可运行"时长；不可运行 = 被抢占间隔的并集（桩给切换序列，修正器算并集——区间合并 O(切换次数)，切换少可接受）。为什么这是零误报的关键（判据行论证）：8 核 8 任务下等待者被抢占是常态（调度周期毫秒级），"调度饿"造成的伪长等待概率不低——不修正的时间告警在长跑里必然误报，修正是"7×24 零误报"时间侧的必要条件（与 B08 确认窗口并列为零误报两大支柱，判据行原文记之）。对照组设计（M-127）：修正开关关闭跑同场景必误报——对照证明修正不是装饰。现有内核接入：桩协议 = SleepPort 的扩展事件（on_run/on_preempt——A3 联签需求登记 F3375）。Windows 对比：Windows 的 Context Switch ETW 事件可离线做同类修正（WPA 的 CPU 使用率归一）——我们内核内实时化；其 DPC 看门狗不做此修正（误报其设计接受），我们不做误报。M-127 复测：修正开/关对照 + 修正值算式核对（区间并集手算对照）。

## F3370 告警风暴抑制（指数退避重复告警）

**定位**：持续告警的退避：同一告警源持续触发时按指数退避（1/2/4/8 秒窗）重复输出——F3365 去重是"窗内压缩"，本条是"跨窗降频"，两级防风暴。
**语义边界**：只做退避；去重在 F3365。退避上限 8 秒窗（不再翻倍——上限声明）。恢复规则：告警源消失后退避计数清零。
**判据**：
- J1：M-129：持续告警源 10 秒 → 输出时刻序列符合退避（0/1/3/7/15 秒边界近似）；源消失 → 计数清零（恢复即时性）。
**纯功能行数**：260（退避状态 ~90 + 序列逻辑 ~90 + 用例 ~80）
**依赖与嫁接源**：F3365 去重表（退避状态挂同表）；F3361 窗口。
**风险与回退**：退避掩盖恶化（warn 退避期间升级为 critical 被延迟）——回退：升级免退避（级别变化即报——判据行规则：warn→critical 的第一次升级必报，不受退避限制）。
**正文**：实现路径：去重表键扩展退避字段 `backoff_pow: u8`；同键重复告警：`下次可报时刻 = now + (1<<pow) 秒`，命中静默后 `pow = min(pow+1, 3)`（上限 8 秒）；级别升级 → pow 清零立即报。退避序列（判据行）：持续源在 0s/1s/3s/7s/15s… 处输出（指数间隔），M-129 用桩时钟验证序列。上限 8 秒的理由：退避是降噪不是静音——8 秒一次的持续告警仍能给"7×24 监控"稳定的信号流，再大就失去常驻观测的意义（告警节奏与监控轮询节奏的配合，判据行论证）。升级免退避的论证：退避假设"同类告警冗余"，升级是"事态变化"——冗余可压、变化必报（与 F3354 候选溢出的"宁可误报不可漏报"同方向）。现有内核接入：无。Windows 对比：ETW 的 Event Tracing 无退避（收集端管理）；Windows 错误报告（WER）的抑制有类似节流——判据行声明我们内核内实作的动机（无收集端）。M-129 复测：序列对账（±1 窗容差）+ 升级免退避验证 + 恢复清零验证。

## F3372 时间账本内存预算与滚动淘汰

**定位**：账本的内存纪律：WaitLedger/HoldLedger/去重表/候选表全部静态预算（判据行给总表）+ 老记录滚动淘汰（LRU 槽位——账本容量有限但永远服务最新数据）。

- J1：M-131：注入 > 表容量的键数（去重 40 键 > 32 槽）→ 最老键被淘汰且强制输出协议生效（F3365 溢出规则）；账本总内存恒定（分配计数不变）。

**风险与回退**：淘汰误删活跃键（高频告警源被老键挤掉）——回退：淘汰选"最老未命中"而非"最老"（LFU 混合——命中刷新时间戳，判据行给规则）。
**正文**：预算总表（判据行原文）：WaitLedger 每锁 ~200B × 50 锁 = 10KB；HoldLedger 同 10KB；去重表 32×24B ≈ 1KB；候选表 16×48B ≈ 1KB；优先集 16 键 ≈ 0.5KB；分片克隆区 96KB（F3351）——B09 总预算 ≈ 120KB（B08 的 110KB 之外），两检测器合计 ~230KB < 全域 1% 预算线（F3352 占比声明的延续）。淘汰规则：①时间窗数据——窗口滚动天然淘汰（分窗归零重计）；②去重/候选/优先集表——LFU 混合 LRU（命中刷 tsc，淘汰选 tsc 最老）——高频源常驻、冷源让位。零 unbounded 增长的声明（对接 F3373）：全部结构静态定容，任何键数增长被容量封顶——"增长有界"是设计不变量。现有内核接入：无。Windows 对比：ETW 缓冲区的环形复用同哲学（容量封顶 + 淘汰最旧）。M-131 复测：溢出淘汰 + 内存恒定断言（堆计数/池计数不变）。
