## F3241 mutex 结构体与睡眠锁基座

**定位**：mutex 族的根条目——定义 `Mutex<T>` 睡眠锁类型与"快路径无锁、慢路径睡眠"的总体行为契约，是 B03 后续 19 条的结构底座。
**语义边界**：只定义结构、构造、fast path 与慢路径的分派框架；等待队列细节归 F3242、交接协议归 F3246、统计归 F3248/F3256。不做读写语义（B04）、不做自适应自旋（F3250 独立）。
**判据**：
- J1（可运行）：`Mutex::new` 为 const fn，`lock()` 在无争用路径上不触碰调度器即返回 `MutexGuard`；ktest 用例 M-001（单核获取-持有-释放 1,000 轮 + 双核争用 200 轮）通过。
- J2（可观测）：fast path 与 slow path 各自有计数器，M-001 运行后两计数与操作次数吻合。
**纯功能行数**：380（结构体与状态字定义 ~90 + const 构造与 fast path ~80 + 慢路径分派框架 ~110 + 路径计数与判据行 ~60 + 文档注释 ~40）
**依赖与嫁接源**：F3201 原子底座、F3202 SpinLock RAII 体例承接；嫁接 `cpu/sync.rs` 的 AtomicU32 状态字风格。
**风险与回退**：状态字编码若含糊会导致后续所有条目歧义——回退：状态字编码表在批内唯一化（本条为唯一定义点），其余条目引用不重定义。

**正文**：实现路径上，第一步定义状态字：`state: AtomicU32`，编码 0=自由、1=已锁、2=已锁且有人排队（locked-with-waiters），三态足够支撑 F3249 的 FIFO 交接与 F3250 的自旋判断，避免 Linux mutex 那种把 owner 指针揉进状态字的高位技巧——我们的编码表要一眼可读，因为 A5 的定位是"判据宪法"的地基，可读性优先于省一个字。第二步数据结构：`Mutex<T> { state: AtomicU32, waiters: WaitQueue, owner: OwnerCell, stats: MutexStats, _data: UnsafeCell<T> }`，`WaitQueue` 在 F3242 充实，本条先给占位结构与不变式（空队 + state<2 时必须空队）。第三步接入现有内核：仿 F3219 桥的登记法，在 `cpu/sync.rs` 桥点表加 mutex 一行，但本批不改旧文件行为；`Mutex<T>` 本体放新文件 `kernel/varix/src/sync/mutex.rs`，与 B01 的 lock 事件环形缓冲（F3211）通过事件枚举对接。第四步 Windows 对比：Windows 内核的 KMUTEX 是基于 dispatcher object 的睡眠锁，`KeWaitForSingleObject` 承担慢路径、IRQL 在等待时降为 PASSIVE_LEVEL；我们的对应设计是——fast path 类似 `ExAcquireFastMutex` 的 interlocked compare-exchange，慢路径不降 IRQL 概念（我们无 IRQL 分级，改用 F3247 的上下文断言），并把 Windows 的 dispatcher header 简化为显式 `WaitQueue` 字段。验收对照：J1 的 M-001 在 B11 的 ktest 新面注册，可重复、可观测（路径计数断言）、可复测（失败注入重跑）。本条不实现唤醒，唤醒语义严格走 F3246 的 A3 交接协议，防止 A5 越界造醒。

## F3242 慢路径等待队列挂接与唤醒边界协议

**定位**：实现 mutex 慢路径的等待队列：争用失败者如何入队、队首如何被交接锁的所有权，以及与 A3 的挂起交接点。
**语义边界**：只管队列与所有权交接的锁侧逻辑；真正的挂起（schedule-out）与唤醒实现是 A3 的地盘，本条调用 F3246 定义的协议接口完成交接。不处理超时（超时是 F3246 协议四态之一，由协议层承载）。
**判据**：
- J1：三核场景下三个等待者入队序 = 挂起序；M-002 验证队列入队原子性与交接返回。
- J2：交接协议返回码 WOKEN/TIMEOUT/CANCEL/SPURIOUS 四态各有用例覆盖（SPURIOUS 用桩注入）。
**纯功能行数**：400（WaitQueue 节点与入队 ~130 + 所有权交接 CAS 链 ~120 + 挂起调用点与返回分派 ~90 + 判据行 ~60）
**依赖与嫁接源**：F3241 结构体；F3246 协议；B01 F3204 TSC 时钟封装。
**风险与回退**：交接竞态（唤醒与 try_lock 抢锁）是 mutex 最经典 bug 源——回退：交接采用"队首专属交接位"设计，非队首永不尝试拿锁，消除交接窗口。

**正文**：实现路径：入队时先 `state.compare_exchange(1, 2)` 抢占 locked-with-waiters 标记，失败说明锁已被交接走则重试 fast path；入队成功后构造 `WaiterNode { prev, next, owner_cpu, seq }` 挂入 FIFO 双向链表，链表头由锁内嵌 `WaitQueue` 持有，队列自身用 `SpinLock<NodePool>` 保护（复用 B01 的 F3202）。数据结构要点：节点从静态池分配（每 CPU 预留 16 个），池耗尽的降级路径在 B02 F3236 已有先例，本条引用同款策略。所有权交接：释放路径发现 `state==2` 时，从队首取节点、把所有权写入该节点的"专属交接位"、调用 F3246 协议唤醒该等待者；等待者醒来后从交接位拿锁——保证只有被交接者能拿锁，其余竞争者一律重走 fast path，这就是消除"惊群抢锁"的核心机制。现有内核接入：交接位复用 `cpu/sync.rs` 的 owner 字段语义（next/owner 票据思想），但实现独立于旧票锁，桥点只登记不改动。Windows 对比：Windows KMUTEX 慢路径走 `KiWaitTest` 与 dispatcher wait list，唤醒由 `KiReadyThread` 完成，与我们的差异在于它把交接嵌入调度器；我们把交接留在锁侧、调度器只做"睡与醒"两个动词，这正是"锁归 A5、醒归 A3"判例的结构化落地——A5 管账（谁该醒），A3 管动作（去醒）。M-002 的复测方式：注入 SPURIOUS 返回（等待者醒来发现交接位无效），断言其重入等待而非抢锁，此为防回归的关键负例。

## F3243 RAII guard 与对称释放路径

**定位**：`MutexGuard<'a, T>` 的 RAII 释放：drop 即 unlock，杜绝手工 unlock 入口，保证加解锁对称性由类型系统背书。
**语义边界**：只做 guard 的 Drop 实现与 Deref/DerefMut；不做 guard 的跨线程转移（Send 边界声明在本条内做"不做"决定并留 ADR 记录位）。
**判据**：
- J1：M-003：获取→drop→再获取循环 1,000 次，每次 drop 后 state 归零、统计入账；存在编译期证明：`Mutex` 无公开 `unlock` 方法。
- J2：guard 存续期间 `Deref` 到 T，drop 后 Deref 不可能（借用检查保证），M-003 附编译期断言。
**纯功能行数**：300（guard 结构与 Deref ~80 + Drop 释放链 ~120 + Send/Sync 边界与判据行 ~100）
**依赖与嫁接源**：F3241/F3242；体例承接 B01 F3202 的 guard 设计。
**风险与回退**：Drop 中调用释放链若 panic 会造成状态撕裂——回退：释放链全程无 panic 点（不用索引、不分配），并用 debug_assert 包裹不变式。
**正文**：实现路径：`Drop for MutexGuard` 里依序做四件事——统计入账（持有时长经 F3204 TSC 差值）、等待边注销（F3251 反向操作）、释放或交接（state==2 时走 F3242 交接、否则 CAS 1→0）、事件入环（F3211 LOCK_RELEASE）。次序不可换：先记账后放锁，否则观测面会看到"已释放但未记账"的瞬态。数据结构：guard 内只存 `&'a Mutex<T>` 与获取时刻的 TSC 快照，零堆分配。现有内核接入：与 B01 F3202 的 spin guard 共用统计记账 trait（`LockStatsSink`），保证 B01–B03 三族锁的观测格式统一，这是 B07 锁层次表能统一打点的前提。Windows 对比：Windows C 语境没有 RAII，依赖 `KeReleaseMutex` 的手工对称调用，驱动 bug 里"获取后异常路径漏释放"是 Driver Verifier 的重点检测项；我们的 drop 即释放从类型系统层面消灭该类 bug，等价于 Rust 驱动（WDK 的 rust 支持）承诺的能力，但我们在内核本体就享受它。边界声明：guard 不实现 Send（不跨线程转移所有权转移持锁权），理由写入判据行：跨线程交锁应显式走"释放-再获取"，让等待边账本诚实，这与 Windows 交给调度器隐式处理的语义不同但更可审计。M-003 复测：故意在 Drop 里注入统计失败桩，验证释放仍完成（记账失败不阻塞放锁），防"观测拖垮正确性"的回归。

## F3244 所有权记录与持有者账本

**定位**：每把 mutex 记录"现在谁持有"——持有者 CPU 编号与获取序号，供观测、死锁报告（B08 F3347）与长持告警（F3248）消费。
**语义边界**：只记录与清账；不做持有合法性强制（那是 B07 层次校验器的事）、不做 owner 揉状态字的位压缩（编码表在 F3241 已定，不重定义）。
**判据**：
- J1：双核争用 200 轮，任意时刻账本 owner == 实际持锁 CPU；M-004 断言采样点正确率 100%。
- J2：释放后账本清零且保留 last_owner 供事后观测。
**纯功能行数**：320（OwnerCell 结构与写点 ~100 + 采样一致性判据行 ~90 + last_owner 与清账 ~80 + 文档 ~50）
**依赖与嫁接源**：F3241 结构体；`cpu/smp.rs` 的 CPU 编号读取（GS base）。
**风险与回退**：owner 写点若与 state CAS 不原子，观测会有瞬态漂移——回退：owner 写点固定在"CAS 成功之后、返回 guard 之前"的单一定义点，漂移窗口明示为可接受并写入判据行。
**正文**：实现路径：`OwnerCell { cpu: AtomicU32, seq: AtomicU64, last_cpu: AtomicU32 }`；获取链上 CAS 成功后立即写 cpu 与 seq（seq 取每 CPU 单调计数），释放链上先搬 last_cpu 再清零。三个写点全在 F3241/F3242/F3243 已确定的路径定义点上，本条不改路径只插桩，符合"手术式改动"纪律。数据结构：不用指针而用 CPU 编号，因为我们的任务上下文模型里等待者按 CPU 记账（与 A3 协议一致），指针会引入生命周期管理负担且无法在 NMI 类观测里安全解引用——NMI 安全预留的诚实边界在 B07 F3334 有同款声明。现有内核接入：`cpu/sync.rs` 旧票锁的 owner 字段（u32 ticket 号）与我们的 owner（CPU 号）语义不同，桥点登记表里明确标注两者不可混用，防止后续接管时误把旧语义读进新账本。Windows 对比：Windows 的 KTHREAD 等待块体系里，mutex 的 owner thread 记录在 dispatcher header，`!mutex` 调试器扩展能打印 owner 与 waiters——我们等价的观测面在 F3256，输出格式对齐 `!mutex` 的三段式（owner/等待数/状态），方便熟悉 WinDbg 的验收者读账。J1 的采样正确率验证法：观察点设在每轮争用的第三核上定时采样，读 owner 后立即用同一 CPU 的"我是否在持锁"自查询校验，200 轮零漂移即通过。本条成本预算：写点合计 3 条原子 store，纳入 F3418 的断言开销账本统一度量。

## F3245 try_lock 原子 fast path

**定位**：非阻塞尝试获取：单条原子交换实现，成功拿锁、失败立刻返回，绝不入队、绝不睡眠、绝不登记等待边。
**语义边界**：只做 try 语义与计数；不实现 try_lock 超时变体（超时语义属 F3246 协议层的 TIMEOUT 态，不单独造 API）。
**判据**：
- J1：M-005：空闲时 1,000 次 try 全成；持有时全败且 state 不变、无队列节点残留。
- J2：try 失败不产生 LOCK_SLEEP 事件（事件账本断言）。
**纯功能行数**：240（try_lock 本体 ~70 + 两态计数 ~70 + 判据行与事件规避断言 ~100）
**依赖与嫁接源**：F3201 原子底座；F3211 事件面。
**风险与回退**：try_lock 与慢路径交接的竞态可能造成"try 成功但交接位已写"——回退：try_lock 只允许 CAS 0→1，永不触碰 state==2 态，交接窗口物理隔离。
**正文**：实现路径：`try_lock` = `state.compare_exchange(0, 1, Acquire, Relaxed)` 一条指令路径，成功后写 owner（F3244 定义点）、记 try_hit 计数；失败则记 try_miss 并立即返回 false，全程不碰 WaitQueue、不碰 F3246 协议——这是"绝不登记等待边"的类型级保证，B08 的等待图因此天然不吸收 try 失败者，避免图被高频 try 流量污染。数据结构：无新增结构，仅 stats 里加 try_hit/try_miss 两计数。现有内核接入：`cpu/sync.rs` 旧票锁无 try 语义（ticket 锁天然阻塞），本条在桥点登记表标注"旧锁无对应物"，接管时若旧调用点需要 try 语义，映射到新 mutex 而非给旧票锁打补丁——这是"升级接管不重写、但语义缺口用新件补"的判例。Windows 对比：Windows 的 `KeTryToAcquireFastMutex` 语义与我们一致（成功返回 TRUE、失败不等待、IRQL 提升至 APC_LEVEL 的副作用我们不引入，改由 F3247 上下文断言承载"我是否允许在此尝试"的问题）；NT 的 try 失败同样不入 wait list，与我们"try 不进等待图"的设计同构，这一点写入判据行作为跨系统一致性佐证。复测方式：M-005 在事件账本断言"try 失败零 SLEEP 事件"，并在争用注入下重跑验证 try_miss 计数增长与失败次数相等——计数与事实对账，是 A5 判据宪法的最小单元示范。

## F3246 与调度器交接协议（醒归 A3 桥）

**定位**：A5↔A3 的正式边界协议：定义 `sleep_on(waiter)` 与 `wake_protocol(w)` 两个唯一交接点、四态返回码语义，是"锁归 A5、醒归 A3"判例的接口化。
**语义边界**：A5 定义协议与消费方；挂起/唤醒的内部实现、调度队列、优先级决策全部归 A3，本条不写一行调度代码。协议接口签名在本条冻结（并入 F3257 签名表）。
**判据**：
- J1：M-006 用桩调度器验证四态分派：WOKEN 正常续跑拿交接位；TIMEOUT 到点返回；CANCEL 由释放侧撤销等待；SPURIOUS 醒而无锁重入等待。
- J2：协议返回码枚举与文档一一对应，桩注入各态均可复现。
**纯功能行数**：380（协议接口与返回码 ~110 + 桩调度器 ~130 + 四态分派消费逻辑 ~90 + 判据行 ~50）
**依赖与嫁接源**：F3242 交接位；A3 的接口由总纲 §4 A3 域说明引用（A3 未开工，本条以桩先行，双轨制允许）。
**风险与回退**：A3 实装时协议签名若被迫变更——回退：本条声明"协议 v1 冻结于本批"，变更须 ADR 且默认 P0（沿用 ktest 冻结接口同款纪律，§16.1）。
**正文**：实现路径：定义 `pub trait SleepPort { fn sleep_on(&self, w: &Waiter) -> WakeReason; fn wake_protocol(&self, w: &Waiter) -> bool; }`，mutex 慢路径只经此 trait 与调度世界对话；开发期提供 `StubSleepPort`（可控返回四态），A3 实装后 feature 切换。数据结构：`WakeReason { WOKEN, TIMEOUT, CANCEL, SPURIOUS }` 四态枚举——比 Linux 的"醒来自己查"多一层显式语义，因为我们要让 B08 死锁报告能区分"被唤醒但没拿到"与"被撤销"，这是可审计性的要求。SPURIOUS 的处理契约：醒来发现交接位无效则原位重睡（重走 F3242 入队），绝不借机抢锁，防止惊群。现有内核接入：`cpu/sync.rs` 旧票锁的自旋等待不经调度器（纯自旋），本条在桥点登记"旧锁无睡眠交接"，未来接管高争用调用点时按 F3250 自适应自旋策略分流。Windows 对比：Windows 的 `KeWaitForSingleObject` 返回 STATUS_ALERTED/STATUS_USER_APC/STATUS_TIMEOUT/STATUS_SUCCESS 等多态，我们的四态是其子集裁剪——裁掉用户 APC（无用户态）与告警态（A3 职责内另行建模），保留超时、正常、撤销、伪醒四态并在判据行给出与 NT 状态码的映射表，供验收者对照。J2 复测：桩注入 SPURIOUS 连续 3 次，断言等待者三次重睡且队序不变（F3249 公平性不受伪醒破坏）——这是 B03 里最尖锐的一个负例用例。

## F3247 中断上下文禁用断言

**定位**：在中断上下文调用 `mutex.lock()` 慢路径是错误——本条提供编译标记 + 运行断言双层防护，并在调试档记账。
**语义边界**：只防护 mutex（睡眠锁）；自旋锁的中断规则归 B01 F3207/F3208。断言触发后的策略是"记账+报错路径"，不做恢复（错误上下文的恢复是 A4 域的事）。
**判据**：
- J1：M-007：桩中断环境调用慢路径触发断言并记 INVAL_CTX 账；非中断环境同一调用不触发。
- J2：断言开销仅在 debug 档存在（编译期裁剪），release 档零开销由构建产物检查确认。
**纯功能行数**：240（上下文探测 ~70 + 断言与记账 ~80 + 编译档裁剪与判据行 ~90）
**依赖与嫁接源**：F3208 中断上下文锁类型注解（类型层先行）；`cpu/idt.rs` 的上下文标志读取。
**风险与回退**：上下文探测若依赖 A4 未交付的中断状态接口——回退：本条自带最小"当前是否在中断帧"探测（读 IDT 栈帧标志），与 A4 实装后并轨，探测函数标注为可替换点。
**正文**：实现路径：第一层是类型层——F3208 已定义 `InterruptContext` 标注类型，本条把 mutex 的 lock 入口参数绑定到"不可中断上下文"的类型约束，让编译期先拦一道；第二层是运行层——慢路径入口检查 `in_interrupt_frame()`（读自 `cpu/idt.rs` 的栈帧标志位），为真则走 `debug_assert!` + INVAL_CTX 账目 + 统一报错路径（走 F3256 观测面，不直接 panic，把现场留给验收者）。数据结构：INVAL_CTX 计数器挂在全局锁诊断账本（与 B07 的违例账本同库不同段）。现有内核接入：探测点读取 IDT 栈帧标志是既有机制（F3208 桥点已登记），本条不新增 IDT 改动，只读不写——硬件安全红线内。Windows 对比：Windows 规则是"KMUTEX 只能在 IRQL <= APC_LEVEL 获取"，`KeAcquireFastMutex` 会把 IRQL 提到 APC_LEVEL 并在释放时还原， Drivers 违规获取会触发 BugCheck 0x1A/0x11 等；我们没有 IRQL 数值体系（A4 域规划中的中断分级不与本条耦合），改用"上下文类型断言"表达同一约束，语义上更接近 Rust 类型化嵌入式里的"上下文令牌"模式。J2 的 release 零开销验证：构建产物符号检查（断言符号不得出现于 release 段）+ 开销测量归 F3418 账本。复测方式：M-007 先正例后反例同轮跑，账本差额 == 1，防止"断言永远触发"的假阴性。

## F3248 持有时间统计与长持告警钩子

**定位**：每次持有时长的 TSC 记账、每锁 max/total 汇总，以及超阈值时触发可注册的告警钩子——B09 时间窗告警账本的消费端预留点。
**语义边界**：只做 mutex 侧记账与钩子触发；告警去重、风暴抑制、时间窗模型归 B09（F3361–F3380）。与 B01 F3204 的 hold-time 账本共用底层 TSC 封装，不重复造钟。
**判据**：
- J1：M-008 注入持有时长超阈值的持锁者，钩子被触发且携带 (锁名, 时长, 持有者) 三元组；正常持锁不触发。
- J2：max_hold 更新单调性断言：任意时刻读到的 max ≥ 历史任一已结束持有的时长。
**纯功能行数**：320（TSC 差值记账 ~90 + max/total 汇总 ~80 + 钩子注册与触发 ~100 + 判据行 ~50）
**依赖与嫁接源**：F3204 TSC 账本（读钟封装复用）；F3244 owner（三元组来源）。
**风险与回退**：钩子在持锁路径上执行若失控（钩子本身又拿锁）会自锁——回退：钩子契约声明"钩子内禁止获取任何锁"，并配 M-008 负例（钩子里拿同一锁 → 记账告警而非挂死）。
**正文**：实现路径：获取时记 TSC 快照（存于 guard，见 F3243），释放时差值入账：`total_hold += d; if d > max_hold { max_hold = d; }`，然后 `if d > threshold { hook((lock_name, d, owner)) }`。数据结构：`MutexStats { contentions, max_hold, total_hold, try_hit, try_miss }` 与 B01/F3205 的 per-lock 对齐，让 B07 层次表能一表读全族。钩子是全局单槽注册（一次一个消费者），B09 接管时注册时间窗账本写入器；多消费者聚合留待 B09 设计（本条不做，边界诚实）。现有内核接入：`cpu/sync.rs` 旧票锁已有 `longest_hold` 字段（F043 时代产物），本条的 max_hold 是其新族对等物，桥点登记表标注字段映射（longest_hold ↔ max_hold），接管时数据可平移。Windows 对比：Windows 上长持检测主要靠 Driver Verifier 的死锁验证选项 + 性能分析用 WPA/ETW 的锁事件（Contention 事件含等待时长），内核本体不做 per-lock 阈值告警；我们把告警钩子做进内核本体，是为了 7×24 无人值守验收（死锁检测器零误报的配套观测），这是本项目相对 Windows 常规实践的一个主动增强，判据行注明"对标 ETW Contention 事件的内核内省版"。J2 单调性复测：并发 8 核随机持锁 5,000 轮后统一读 max，与账面逐轮重放的 max 对账一致。

## F3249 FIFO 等待队列公平性

**定位**：把 F3242 的"队首专属交接"升格为公平性契约：严格入队序交接、无插队、无饥饿，并给出公平性的可测定义。
**语义边界**：公平性只约束 mutex 慢路径排队；自旋等待（F3250）不受 FIFO 约束（自旋者不在队）；票锁的公平语义（F3203）是 B01 的既有事实，本条不复述不重定义。
**判据**：
- J1：M-009：三等待者 A→B→C 入队，交接序必为 A→B→C；1,000 轮压力零逆序。
- J2：等待深度（队长度）可观测，交接后队长度 -1，账实相符。
**纯功能行数**：340（公平性交接不变式 ~100 + 逆序检测器 ~110 + 队长观测与判据行 ~130）
**依赖与嫁接源**：F3242 队列与交接位；F3227（B02 公平性共同记账）的跨批口径。
**风险与回退**：绝对 FIFO 在高争用下可能拉低吞吐——回退：本批坚持公平优先（A5 的死锁检测验收要求行为可预测，公平性是可预测性的前提），吞吐权衡写入 F3250 自适应自旋的对冲说明，不做"半公平"混合态（复杂度失控先例拒绝）。
**正文**：实现路径：公平性不变式定义为一句话——"交接位只写队首，队首唯一"；逆序检测器在交接时断言被交接者 seq == 队首 seq，违例即记账（这属于不变式被破坏，理论上不可达，断言是保险丝）。数据结构：`WaiterNode.seq` 全局单调分配（与 F3244 的 owner seq 同源计数器，避免两套时钟），检测器比对 O(1)。现有内核接入：`cpu/sync.rs` 旧票锁的公平性由 ticket 序天然保证（next/owner 差值即队长），桥点登记表把"队长"观测口径对齐到新族 wait_depth，统一 B07 的观测面。Windows 对比：Windows 的 KMUTEX 等待队列语义上是 FIFO 但文档不承诺严格公平（调度器可引入乱序唤醒），内核内 in-stack queued spin lock（`KeAcquireInStackQueuedSpinLock`）也是近似公平；我们给出"零逆序"的硬判据并配 1,000 轮压力用例，把公平性从"习惯"升格为"契约"，这正是 ktest 1 万+ 断言扩容运动想要的样本——每一条行为契约都长出一条断言。M-009 的逆序注入测试：人为交换交接位目标（注入桩），断言逆序检测器触发并记账——契约的反向验证与正向验证同等重要。队长度 wait_depth 观测与 F3256 导出面打通，供 B08 的图规模预算（F3352）消费。

## F3250 自适应自旋（adaptive spinning）

**定位**：等待者在睡眠前先自旋观察"持有者是否还在核上跑"，在则多旋、不在则立刻睡——用持有者状态预测减少不必要的调度往返。
**语义边界**：自旋计数策略与状态探测在本条；睡眠交接仍走 F3242/F3246。不对票锁/qspinlock 生效（它们有自己的后端策略，B01/B02 已定）。
**判据**：
- J1：M-010：持有者持锁时被调度走的场景，等待者走睡眠路径；持有者在核场景，等待者自旋成功路径——两条路径注入均可复现且记账分开（spin_acquire vs sleep_acquire 计数）。
- J2：自旋上限固定常量（可配置但默认 64 次 pause），无自适应参数漂移（可预测性优先，判据行声明）。
**纯功能行数**：400（持有者状态探测 ~130 + 自旋循环与上限 ~90 + 两路径记账 ~100 + 判据行 ~80）
**依赖与嫁接源**：F3206 pause/等待策略（指令级复用）；F3244 owner（探测目标）；A3 的"任务在核上"查询（以桩先行，协议同 F3246）。
**风险与回退**：探测接口依赖 A3——回退：本条定义 `is_on_cpu(cpu) -> bool` 最小协议查询（v1 同 F3246 冻结），A3 未实装期间桩返回常量，用例覆盖桩两态。
**正文**：实现路径：慢路径入口先自旋循环：`for _ in 0..SPIN_MAX { if try_lock() { spin_acquire++; return; } if !is_on_cpu(owner_cpu) { break; } pause(); }`——两个退出条件：拿到锁、或持有者下核（继续等它回来不如去睡）。退出后走 F3242 正常入队睡眠。数据结构：spin_acquire/sleep_acquire 两计数入 MutexStats；SPIN_MAX 为编译期常量。刻意不做 Linux `osq` 那样的自适应优化者队列——那是 qspinlock 的一部分（B02 F3223 已有对应物），mutex 侧保持简单可审计，复杂度预算让给 B08 死锁检测器，这是 A5 内部的复杂度分配决策，判据行留痕。现有内核接入：`cpu/sync.rs` 旧票锁无自旋上限概念（自旋到拿到为止），桥点登记表注明新族策略与旧锁差异，接管调用点时按"旧调用点默认自旋=0（立即睡）还是 64"给出迁移建议表，默认 64 但可全局关（debug 档关自旋，让睡眠路径充分暴露）。Windows 对比：Windows mutex 慢路径直接进等待（dispatcher 等待），不做内核 mutex 的自适应自旋；自适应自旋在其语境属于 spin lock 的优化版与 `ExTryQueueSpinLock` 语义族。我们主动引入自适应自旋的动机是双核真机（目标硬件）上调度往返的实测成本高于自旋——该动机标注为"待真机闸口验证的假设"，用例 M-010 的两路径记账就是为闸口对比准备的数据面。复测：注入 is_on_cpu 抖动（真→假→真），断言等待者先旋后睡不重旋（避免活锁抖动），负例记入 M-010。

## F3251 等待边登记接口（供 B08 死锁检测消费）

**定位**：mutex 阻塞等待时向等待图账本登记"等待者→持有者"边，获得/释放时注销——B08 环检测的边供给源，本条定义边接口并保证账实平衡。
**语义边界**：只定义边的登记/注销接口与平衡性契约；图的存储、环算法、报告归 B08（F3342–F3351）。rwlock 侧的边登记在 B04 F3272 复用本接口。
**判据**：
- J1：M-011：N 轮争用后边账本净变化为零（登记数 == 注销数），无悬挂边。
- J2：try_lock 失败不产生边（与 F3245 契约联动断言）。
**纯功能行数**：340（边接口定义 ~90 + 登记点/注销点插桩 ~120 + 平衡性账本 ~80 + 判据行 ~50）
**依赖与嫁接源**：F3242 等待路径（登记点）；F3243 释放路径（注销点）；B07 F3324 统一打点（接口对齐预告）。
**风险与回退**：边账本本身若用锁保护，可能在死锁场景先于检测器死锁——回退：边账本采用无锁分片（per-CPU 分片 + 合并），与 B08 F3351 的分片设计合一，本条只定接口。
**正文**：实现路径：接口 `fn wait_edge_register(holder: LockId, waiter: WaiterId)` / `fn wait_edge_unregister(...)`，登记点唯一（F3242 入队成功后），注销点两处（F3243 释放时的主动注销 + 交接完成时的等待者侧注销），注销必须携带登记时返回的边票据（token）防误删。数据结构：边票据 `EdgeToken(u64)` 全局单调，账本按 token 记账，平衡性 = 登记集合与注销集合的差集为空。现有内核接入：`cpu/sync.rs` 旧票锁自旋等待不产生边（自旋不算等待——与 B08 的"等待=睡眠等待"图模型一致，判据行声明该语义并留 ADR 记录位：若 B08 需要把长自旋也建模为边，走 ADR 扩展）。Windows 对比：Windows 的死锁检测（Driver Verifier Deadlock Detection）在验证器层挂钩获取/释放记录等待关系，原理与我们的边登记同构，但它在验证器进程态做图分析、且只对注册过的资源类型生效；我们的边账本在内核态实时维护、对 B03/B04 全族生效，B10 样本库会以它为检出率基准。J1 平衡性复测：随机 8 核 5,000 轮争用 + 强制超时打断（TIMEOUT 态）混合场景，注销必须覆盖 TIMEOUT/CANCEL 路径——这条是平账的最大风险点，M-011 专门构造 TIMEOUT 中断等待的用例验证注销不遗漏。

## F3252 双锁按序获取 helper

**定位**：提供 `lock_two_ordered(a, b)`：按锁地址全序获取两把 mutex，从 API 层面消灭 ABBA 死锁的最常见形态。
**语义边界**：只做双锁按序；三锁及以上不做（组合爆炸，交给 B07 层次规则与 B08 环检测兜底）；与 B02 F3233 的 lock_two_ordered 是同名不同族（那是 qspinlock 版），本条为 mutex 版，两版共享"地址序"的同一全序定义（判据行交叉引用）。
**判据**：
- J1：M-012：两核分别以 (a,b) 与 (b,a) 顺序调用 helper，各 500 轮零死锁零交叉等待（等待边账本瞬时最大深度 ≤1）。
- J2：helper 内部释放序为获取逆序，M-012 断言事件账本中 release 对 acquire 的栈序。
**纯功能行数**：240（地址序比较与获取 ~80 + 逆序释放与回滚 ~80 + 判据行 ~80）
**依赖与嫁接源**：F3233（全序定义复用）；F3241 lock 本体。
**风险与回退**：获取第二把失败（try 失败）需要回滚第一把——回退：第二把走 try_lock（F3245），失败即释放第一把重来，永不阻塞持单锁等第二锁，这是"不做交叉等待"的结构保证。
**正文**：实现路径：`if a as *const _ < b as *const _ { let g1 = a.lock(); let g2 = b.try_lock(); ... } else { 对称 }`——try 失败路径：drop g1、退避（pause 若干次）、重入。数据结构：无新增；回滚次数计数入 helper 级统计（观测重试率）。现有内核接入：现有内核双锁点扫描由 F3259 桥条目交付清单，本条 API 就位后，扫描清单中的双锁点逐个标注"可直接换 helper / 需层次声明 / 需环检测兜底"三分类。Windows 对比：Windows 驱动世界对双锁问题用"锁序等级"约定 + Driver Verifier 的层次检查，没有标准库级 lock_two helper；我们把它做成库函数是因为 Rust 的 drop 安全让"try 失败自动回滚"可以无泄漏地表达，等价能力在 NT 语境要靠 `KeReleaseSpinLock` 的手工对称。M-012 的"零交叉等待"断言实现：等待边账本（F3251）在任意采样点不出现同一等待者挂两边的记录。复测：注入 a==b 同锁调用（重复锁），helper 断言拒绝并记账——重入拒绝是 F3232 同锁重入检测在 mutex 侧的对等物，本条契约里显式包含。

## F3253 诚实边界：不做优先级继承的声明条目

**定位**：显式声明 mutex 族不做优先级继承（priority inheritance），交付"设计声明 + 反向用例 + 未来扩展 ADR 记录位"三件套——把"不做"变成可验收的诚实内容，防虚报。
**语义边界**：本条是边界声明条目，交付物为声明文档、反转场景的行为定义、以及 B08/B09 在反转场景下的告警行为契约；不实现任何优先级传递。
**判据**：
- J1：M-013：构造低优先级持锁 + 高优先级等待的经典反转场景，系统行为 = 高优先级等待者按 F3246 正常等待 + B09 时间窗告警可触发；用例断言"无优先级调整发生"（优先级账本零变化）。
- J2：声明文档列出未来若做 PI 的三条前置条件（A3 优先级账本、唤醒协议扩展、层次表兼容），缺一不做。
**纯功能行数**：220（声明文档 ~90 + 反向用例 ~80 + 前置条件与判据行 ~50）
**依赖与嫁接源**：A3 的任务优先级模型（桩先行）；B09 F3364 告警阈值。
**风险与回退**：反转导致长尾延迟被误判为死锁——回退：B09 的抖动过滤（F3368）消费本条的反转特征描述（反转场景的等待时长分布），本条输出该描述作为交付物之一。
**正文**：为什么不做：优先级继承要求唤醒协议携带优先级参数并在等待链上逆向传播，这会把 F3246 的四态协议扩张成带参数协议，A3 未实装优先级账本前做 PI 是空中楼阁；且 PI 在 Windows 语境也非 mutex 默认（NT 的 KMUTEX 无 PI，PI 是其实时扩展 KMUTEX_EX 与某些 RT 衍生内核的能力），我们与 Windows 主线行为对齐，不为"看起来先进"引入半成品机制。数据结构：无新增结构；交付物是文档 + 反向用例 + 反转特征描述（等待时长分布基线，供 B09 阈值调参参考）。现有内核接入：现有内核无优先级概念（A3 未开工），桥点登记"本条无接管物"。Windows 对比：Windows 驱动遇到反转的工程答案是"别用 mutex 做长持有，改 work item 或缩短临界区"，DLA（Deadlock Avoidance Level）/锁序约定兜底；我们的同款工程答案写入声明文档的"替代方案"节——短临界区优先、长操作出临界区、实在要等走 completion（B06 F3303）。J1 复测要点：断言"优先级账本零变化"需要 A3 桩提供优先级读口（v1 协议内），若 A3 实装后账本有变化即用例失败——这条把"不做"钉进测试，防止未来实现悄悄加了 PI 却没人知道（可审计性反向应用）。

## F3254 调试模式：非法睡眠点检测

**定位**：为"不允许睡眠的上下文"提供 mutex 慢路径的运行时拦截：标记上下文 + 慢路径断言 + 记账，把"在不能睡的地方睡了"变成可检出的错误。
**语义边界**：与 F3247 的分工：F3247 拦"中断上下文"，本条拦"任何被标记为非睡眠的上下文"（中断只是其一，还有 A3 桩调度器标记的不可抢占区、启动早期区）。标记机制在本条定义。
**判据**：
- J1：M-014：在标记上下文调用 lock 触发慢路径断言 + NOSLEEP_VIOLATION 记账；未标记上下文同调用正常。
- J2：fast path 不受标记影响（能 try 成就合法），断言只挂慢路径入口。
**纯功能行数**：320（标记机制 ~100 + 慢路径检查点 ~90 + 记账与判据行 ~130）
**依赖与嫁接源**：F3247 的探测桩；F3241 慢路径分派点；B07 F3332 调试开关分级（挂其 debug 档）。
**风险与回退**：标记遗漏导致误放行——回退：标记采用"默认安全"策略：启动早期与中断帧默认标记，其余上下文默认允许（误报比漏报好排查，判据行声明取舍）。
**正文**：实现路径：上下文标记用每 CPU 的 `NoSleepMask` 位图，提供 `mark_no_sleep(tag)` / `clear_no_sleep(tag)`，慢路径入口 `if nosleep_active() { 记账 + 断言 }`。数据结构：位图 + 违例账本（时间戳/CPU/tag/锁名四元组，与 B07 违例报告格式 F3328 预对齐）。标记 tag 枚举首版四值：IRQ（对齐 F3247）、EARLY_BOOT、NOSCHED（A3 桩标记）、EXPLICIT（调试者手动）。现有内核接入：`cpu/idt.rs` 中断帧探测复用 F3247 的读口；启动早期标记挂接点在 F3259 桥条目的清单里登记（启动路径调用点扫描）。Windows 对比：Windows 的等价物是"IRQL 检查"——在 >= DISPATCH_LEVEL 页错误或等待即 BugCheck（0x1A MEMORY_MANAGEMENT 等典型蓝屏），`ASSERT(KeGetCurrentIrql() <= APC_LEVEL)` 是驱动常用断言；我们用位图标记而非数值 IRQL，语义等价"当前上下文是否允许等待"，表达力上少一个数值序但多一个多标签并集能力（IRQL 是全序标量，我们用集合论替代，判据行给出映射：DISPATCH_LEVEL 以上 ≈ IRQ tag 置位）。J2 复测：M-014 的正反例对 + fast path 在标记上下文 try 成功的合法用例（防止标记把 try 也误杀）。

## F3255 事件环形缓冲接入（复用 F3211 面）

**定位**：把 mutex 全生命周期事件（ACQUIRE/RELEASE/SLEEP/WAKE 四类）接入 B01 建立的锁事件环形缓冲，统一观测数据源。
**语义边界**：只做事件发射点接入；环形缓冲本体、溢出策略、导出格式归 B01 F3211 与 B15（F3487–F3490），本条是消费端适配。
**判据**：
- J1：M-015：单线程获取-释放 1,000 轮，事件账本序 = 操作序（按 seq 核对），四类事件计数与操作数对账。
- J2：事件发射零分配（静态槽位），M-015 断言无堆计数变化。
**纯功能行数**：220（四发射点插桩 ~90 + 事件载荷定义 ~70 + 判据行 ~60）
**依赖与嫁接源**：F3211 环形缓冲（B01）；F3244 owner（载荷字段）。
**风险与回退**：发射点若在关键路径失控膨胀（每锁每事件）——回退：发射受 B07 F3332 调试档控制，off/perf 档零发射。
**正文**：实现路径：四发射点——ACQUIRE 在 owner 写点后（F3244 定义点）、RELEASE 在统计入账前（F3243 次序契约）、SLEEP 在 F3246 sleep_on 调用前、WAKE 在 wake_protocol 调用前。载荷统一五元组 `(seq, cpu, lock_id, event, owner_cpu)`，与 B01 的事件结构同型，让 B07 统一打点（F3324）能一表扫全族。数据结构：无新结构，事件枚举加 4 个 mutex 变体。现有内核接入：环形缓冲本体在 B01 已接 `cpu/sync.rs` 的锁事件流（F3211 桥点），本条只是把 mutex 事件汇入同一缓冲——观测面"一个口进、一个口出"，验收者读账不用学第二套格式。Windows 对比：Windows 内核锁事件观测靠 ETW 的 `PerfInfoLogSpinLock` 类通道与 WPA 离线分析，事件从内核缓冲刷到 ETW 缓冲再落盘；我们的环形缓冲是内核内自持 + F3489 读路径 dump，省掉 ETW 的多级转发，代价是没有用户态工具链生态——这个取舍在判据行写明：A5 的观测面服务于内核自检（ktest）与 7×24 告警，不做用户态分析器（那是未来域的事）。J1 的 seq 核对法：事件 seq 与 F3244 的 owner seq 同源，单线程场景操作序全序可排，1,000 轮逐对核对（ACQUIRE 紧跟 RELEASE）。复测加入负例：debug 档关闭发射时，用例自动降级为"计数器对账"而非事件对账——用例须知道自己在哪个档跑，这是 ktest 用例元数据（F3407）的动机实例。

## F3256 统计导出与观测面

**定位**：每锁统计（contentions/max_hold/total_hold/try_hit/try_miss/wait_depth）的统一导出接口，观测格式对齐 WinDbg `!mutex` 风格，服务验收读账与 B09 告警数据供给。
**语义边界**：只做导出接口与格式；统计字段的产生在各功能条目（F3244/F3245/F3248/F3249），本条不重复记账。全局汇总视图（跨锁聚合）归 B07 观测导出（F3336）。
**判据**：
- J1：M-016：注入已知争用场景后，导出值与注入参数匹配（contentions == 注入轮数等三组对账）。
- J2：导出接口只读（&self），并发调用安全且不打断被观测锁的操作。
**纯功能行数**：240（导出结构与方法 ~90 + 格式化输出 ~80 + 判据行 ~70）
**依赖与嫁接源**：MutexStats（各条目累计）；F3328 报告格式（对齐预告）。
**风险与回退**：导出读取非原子多字段会有撕裂快照——回退：快照契约声明"逐字段原子读，字段间不做跨字段事务保证"，撕裂可能性与容忍度写入判据行（观测不是判定，B08 判定走边账本不走统计快照）。
**正文**：实现路径：`fn snapshot(&self) -> MutexStatsSnapshot`，逐字段 Atomic load；`fn format(&self, buf) -> usize` 输出三段式：锁名/owner、等待深度、统计六项。格式样例在判据行内嵌：`mutex <name> owner=cpu3 wd=2 cont=17 max=1200us total=3400us try=95/5`。数据结构：快照结构体与格式化器，零分配（写调用方缓冲）。现有内核接入：`cpu/sync.rs` 旧票锁的 contentions/longest_hold 字段读法在桥点登记映射（旧字段 → 新快照字段），未来接管后旧观测调用点可平移。Windows 对比：`!mutex <addr>` 输出 owner thread/waiters/state，`!locks` 遍历全部锁——我们的等价物是 F3336 的全局 dump（B07），本条提供单锁视图；把 NT 调试器扩展的字段顺序作为格式基准的理由：验收手册（15 章体验标准）要求"熟悉 WinDbg 的人零学习成本读账"。J1 对账设计：注入场景三组——200 轮争用（contentions 对账）、1 次长持注入（max 对账）、try 5/95 混合（try 两计数对账）。复测加并发读压测：8 核同时 snapshot 5,000 次，无 panic 无数据竞态（用 ktest 的并发用例模板）。
