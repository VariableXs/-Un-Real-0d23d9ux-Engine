## F3321 锁类别总表（五类选型矩阵）

**定位**：A5 锁族的总目录：五类原语 × 五个维度的选型矩阵，作为内核开发者（含跨域 AI）的"选锁宪法"，也是 F3271 决策树的全景版。
**语义边界**：只做矩阵与抽检用例；具体选型逻辑已在 F3271（rwlock/seqlock）与本批判据行，矩阵是索引不是重复。
**判据**：
- J1：M-080：五场景抽检（中断短临界区→spin、长临界区可睡→mutex、读多写少单次语义→rwlock、小值高频读→seqlock、读侧零锁→rcu）各断言矩阵推荐与契约一致。
- J2：矩阵五维完备：上下文约束/临界区时长/并发语义/观测面/现有内核典型点。
**纯功能行数**：380（矩阵本体 ~150 + 五维定义 ~110 + 抽检用例 ~120）
**依赖与嫁接源**：B01–B06 全部族；F3271 决策树；F3308 盘点清单（典型点）。
**风险与回退**：矩阵教条化（场景不合五维）——回退：矩阵附"例外条款"节（性能敏感先测量，测量工具 = ktest 面），与 F3271 同款反教条声明。
**正文**：矩阵核心行（判据行实录摘要）：spin——上下文=任意（含中断）、时长=极短（几十拍）、并发=互斥、观测=F3205/F3211、典型点=IDT 路径/统计聚合；mutex——上下文=仅进程（F3247 断言）、时长=可长、并发=互斥+FIFO 公平、观测=F3256、典型点=对象池管理；rwlock——上下文=读侧任意写侧进程、时长=中、并发=多读单写、观测=F3276、典型点=位图/页表候选；seqlock——上下文=读侧任意写侧进程、时长=读侧可重复、并发=无锁读、观测=F3270 retries、典型点=时钟值；rcu——上下文=读侧不可睡、时长=读侧极短、并发=零锁读、观测=F3292/F3293、典型点=链表遍历/发布订阅。每格都引用到具体条目号——矩阵是"活的索引"，验收者点格即达判据。现有内核接入：典型点列来自 F3308/F3279 两份清单的汇总视图。Windows 对比：Windows 的选择指南散于 WDK 文档（DISPATCH_LEVEL 语境用 spin lock、PASSIVE 用 fast mutex/ERESOURCE），我们把散落指南矩阵化为单页宪法——15 章体验标准的"一页读懂"要求。M-080 复测：五场景用例各含"错误选型的反例断言"（如中断里选 mutex → F3247 断言触发）——矩阵的每格都长出牙齿。

## F3322 锁层次编号体系设计（lock class 编号分配器）

**定位**：`LockClass(u16)` 的分配体系：编译期宏分配唯一编号 + 全局上限（256 类）+ 分配登记表——层次规则的编号底座。
**语义边界**：只做编号与登记；层次规则本体在 F3327。运行期动态分配不做（v1 静态分配——内核锁点是有限的、可枚举的，判据行给论证）。
**判据**：
- J1：M-081：宏分配 10 类，编号唯一性断言（重复分配编译失败——compile_fail 类用例）；上限 256 超限断言。
- J2：登记表含（编号/名/所属域/允许上下文）四列，查询接口 O(1)。
**纯功能行数**：360（LockClass 类型与宏 ~130 + 登记表 ~110 + 唯一性机制 ~80 + 判据行 ~40）
**依赖与嫁接源**：F3209 const 初始化与静态注册（B01 的注册基建复用）；F3323 锁名。
**风险与回退**：编号耗尽（256 不够）——回退：u16 空间 65536，256 是 v1 注册表容量（静态表尺寸），扩容 = 改常量重编译，判据行声明该成本可接受。
**正文**：实现路径：`lock_class!(NAME, "idt.lock", Domain::A4, Ctx::Irq)` 宏展开为：static 项（LockClass 常量）+ link_section 登记（或简单 static 数组 + 计数器——v1 用后者，判据行说明 link_section 方案的取舍：依赖链接器 section 排序，稳定性换简洁性，v1 不赌链接器行为）。编号分配 = 计数器递增（编译期求值，const fn），重复名编译失败（静态互斥由 const 求值的唯一性保证——两个同名 static 项在 Rust 是编译错误，天然防重）。为什么静态分配（判据行论证）：内核锁点在源码中可枚举（grep lock 调用点），静态编号让层次边可在编译期声明、违例可在运行期 O(1) 判定；动态分配（Linux 的 lockdep 是动态注册）灵活但不可枚举审计——我们选可审计性。现有内核接入：F3209 的静态注册基建复用（登记表同库）。Windows 对比：Windows 无正式 lock class 体系（锁序靠文档约定 + Driver Verifier 运行时抓）；对照物是 Linux lockdep 的 class 概念（动态）——我们静态化的差异与理由（可枚举、编译期防重）写入判据行，这是相对 lockdep 的主动裁剪。M-081 复测：compile_fail 用例（同名宏两次）+ 上限注入（临时改上限常量触发断言）。

## F3323 静态锁名注册表（lock_name! 宏扩展至全家族）

**定位**：锁实例的命名面：`lock_name!` 宏从 B01 的 spinlock 专用扩展到四族通用，产出 (实例, LockClass) 绑定并注册——观测与层次的命名统一层。
**语义边界**：只做命名绑定；class 分配在 F3322。实例与 class 的关系：同类多实例（每个 SpinLock 实例绑定一个 class）。
**判据**：
- J1：M-082：四族各建一实例（绑定同 class 的不同实例），注册表查询返回正确 (名, class) 对。
- J2：无 class 绑定的锁实例（裸构造）在 debug 档记账告警（LOCK_NO_CLASS）——防漏挂。
**纯功能行数**：200（宏扩展 ~90 + 绑定机制 ~70 + 告警 ~40）
**依赖与嫁接源**：F3215（B01 的 lock_name! 原型）；F3322 登记表。
**风险与回退**：实例名与 class 名混淆（观测输出歧义）——回退：观测格式规定 `实例名[class名#编号]`（F3336 dump 采用）。
**正文**：实现路径：宏 `lock_name!(name, class)` 展开为构造函数包装：`SpinLock::new_named(data, class, name)`——四族各加 new_named 变体（API 冻结表 F3318 的预留槽启用登记）。裸构造告警：debug 档下 `new`（无名构造）记账 LOCK_NO_CLASS（不阻断——过渡期既有代码兼容，判据行声明迁移窗口）。为什么实例要绑 class：层次规则按 class 判定（同类两实例间无层次约束——同 class 锁不互相嵌套是规则的一部分，F3327 引用），观测按实例名显示——class 管"规则"、名管"读账"，两轨并行。现有内核接入：cpu/sync.rs 旧票锁的命名建议归 F3339 清单。Windows 对比：无对应（Windows 锁无命名惯例，调试靠地址）；观测性投资是 A5 判据宪法的立场。M-082 复测：四族绑定查询 + 裸构造告警记账各一组。

## F3324 获取路径统一打点（获取事件 → 等待图账本）

**定位**：四族锁获取路径的统一打点钩子：阻塞等待时登记等待边（复用 F3251 接口）、成功获取时压持有栈（F3325）+ 记录 class——层次校验（F3327）与等待图（B08）的统一数据入口。
**语义边界**：只做打点钩子与调用点；栈本体在 F3325、校验在 F3327。try 成功路径也打点（压栈）但不登记等待边（F3245 契约延续）。
**判据**：
- J1：M-083：四族混合获取序列，打点序（事件账本）与实际获取序全序一致；held 栈内容与实际持有集合同构。
- J2：打点开销入 F3331 预算账（本条不测量只留接口）。
**纯功能行数**：360（钩子接口 ~110 + 四族调用点 ~140 + 一致性验证 ~110）
**依赖与嫁接源**：F3251 边接口；F3325 栈；F3211 事件缓冲。
**风险与回退**：打点遗漏（新族忘接）——回退：打点钩子收敛为单一入口 `on_acquire(class, ctx)`，新族接入审查清单化（F3339 的注册表即清单）。
**正文**：实现路径：`fn on_acquire(class: LockClass, wait: bool)`——内部三动作：①wait=true 时边已由 F3251 登记（此处只补"等待结束"标记）；②压 per-CPU 持有栈；③事件发射（ACQUIRE, class）。四族调用点：spin（F3202 guard 构造处）、mutex（F3241 fast/slow 成功处）、rwlock（F3262 读/写成功处，载荷带 R/W 位）、rcu（不压栈——RCU 读无锁实例，判据行声明其打点缺席是设计而非遗漏：RCU 不参与层次规则，它无死锁语义）。一致性验证方法：用例内固定获取序列 → 事件账本回放 → 与栈快照逐点比对。现有内核接入：调用点清单 = F3339 注册表。Windows 对比：Windows 的等价数据面 = Driver Verifier 的获取记录；我们内核态常开（perf 档）——观测哲学差异（Verifier 是测试时工具、我们是常驻面）判据行声明。M-083 复测：四族 12 步序列全序核对 + 栈快照同构断言。

## F3325 持有集合（held locks stack）每 CPU 记录

**定位**：per-CPU 持有栈：当前核持有的锁 class 序列（嵌套序），层次校验的查询源与死锁报告（B08 F3347）的现场数据。
**语义边界**：只做栈结构；打点在 F3324、弹出在 F3326、校验在 F3327。栈深度上限 16（判据行给依据：实际嵌套 ≤ 4，16 是 4 倍余量）。
**判据**
- J1：M-084：三层嵌套持有快照正确（栈内容 = L1→L2→L3），跨核隔离（各核栈独立）。
- J2：栈溢出防御（>16 记账 STACK_OFLOW 且断言）——溢出即结构问题，绝不静默。
**纯功能行数**：380（栈结构 ~120 + 压弹与溢出 ~130 + 快照接口 ~90 + 判据行 ~40）
**依赖与嫁接源**：F3213 per-CPU 体例；F3322 class。
**风险与回退**：栈内容与实际持有的漂移（打点遗漏导致栈脏）——回退：guard RAII 保证压弹对称（类型系统背书），漂移仅可能来自手工路径——审计点收敛在 guard 构造/析构。
**正文**：实现路径：`HeldStack { classes: [LockClass; 16], insts: [*const c_void; 16], top: u8 }`——双轨记录（class 管规则、实例指针管报告）；压：`on_acquire` 内 `stack.classes[top]=class; stack.insts[top]=inst; top+=1`。快照接口：`fn snapshot() -> HeldSnapshot`（供校验器与报告读）。为什么栈序即持有序：guard RAII 保证嵌套获取必然后进先出释放——栈结构与此天然同构（判据行给论证：若出现错序释放即 guard 被手工 drop，F3326 的错序检测兜住）。现有内核接入：无（新结构）。Windows 对比：Windows 调试的"每线程持有锁列表"（!locks 按线程展开）是事后视图；我们的栈是实时账——B08 检测器的边供给依赖实时性。M-084 复测：三层嵌套（spin+mutex+rwlock 混族）快照核对 + 各核隔离断言（8 核同时持有不同序列，快照互不污染）。

## F3326 释放路径统一打点与集合弹出

**定位**：释放路径的统一打点：栈弹出（含错序检测——弹出的 class 必须是栈顶）+ 边注销（F3251 配对）+ 事件发射。
**语义边界**：只做释放打点；对称性由 guard 保证（F3325 判据行），本条的错序检测是手工路径的保险丝。
**判据**：
- J1：M-085：正常序弹出序列全对；构造错序弹出（手工 drop 内层 guard 后 drop 外层——正常 RAII 是外先内后，弹出序 = 获取逆序）→ 错序检测触发记账 RELEASE_MISORDER。
**纯功能行数**：300（释放钩子 ~100 + 错序检测 ~100 + 用例 ~100）
**依赖与嫁接源**：F3325 栈；F3251 注销；F3211 事件。
**风险与回退**：错序检测误报（RAII 合法嵌套释放序被误判）——回退：语义精确化——RAII 释放序 = 获取逆序 = 栈顶先弹；"错序"仅指弹出的 class ≠ 栈顶 class（即有 guard 被提前 drop）——判据行给正反例对照，M-085 两线验证。
**正文**：实现路径：`fn on_release(class, inst)`：①查栈顶 == class && inst 匹配？②匹配 → 弹出 + 边注销 + RELEASE 事件；③不匹配 → RELEASE_MISORDER 记账 + 仍弹出栈顶（保守恢复：栈结构完整性优先于精确语义，判据行声明该取舍——脏栈比断栈危险）。inst 匹配的必要性：同 class 双实例嵌套（理论上规则禁止但防御性检查）——指针级匹配防 class 相同实例不同的错弹。现有内核接入：四族 guard 的 Drop 已在各族释放链挂边注销（F3243 等），本条打点与之并存（一个释放两个动作：族内记账 + 族外打点——判据行说明两层的分工：族内管族语义、族外管跨族层次）。Windows 对比：无对应。M-085 复测：构造提前 drop 场景（手工 drop 内层 guard——用 unsafe 绕过借用检查模拟真实错误）→ 记账触发；正常三层逆序释放 → 零记账。

## F3327 层次规则校验器（新边 vs 已声明层次序）

**定位**：死锁预防的核心规则执行：获取阻塞锁时校验"新锁 class 必须严格大于持有栈内所有已持有 class"（全序规则）——违例即记账（v1 记账不阻断，FULL 档可配置断言）。
**语义边界**：只做运行期校验；边声明（哪些序合法）在 F3329、违例报告在 F3328。同 class 嵌套即违例（自锁预防——与 F3232 重入检测呼应，判据行交叉）。
**判据**：
- J1：M-086：构造违例（先拿低 class 再拿高 class 逆序对）→ HIER_VIOLATION 记账且报告（F3328 格式）内容完整；合法序零记账。
- J2：校验为 O(栈深) 线性扫描，预算入 F3331。
**纯功能行数**：400（规则本体 ~140 + 扫描实现 ~110 + 档位行为 ~90 + 判据行 ~60）
**依赖与嫁接源**：F3325 栈快照；F3322 class 全序（u16 自然序）。
**风险与回退**：规则过严（合法场景被误报——如同类两把锁确需嵌套的罕见场景）——回退：F3329 的"已知合法边"清单提供豁免机制（白名单边 = 声明过的同类嵌套允许），豁免需 ADR。
**正文**：实现路径：获取阻塞锁入口：`let snap = held_snapshot(); for c in snap.classes { if class <= c { 违例报告(class, c, snap); break } }`——u16 全序让规则一行写完：新锁必须 > 所有已持有。为什么全序而不是偏序（判据行架构论证）：偏序（Linux lockdep 的图模型）表达力强但需要环检测（那就是 B08 的事）；全序是偏序的强约束特例——违反全序必违反偏序，反之不然。我们 v1 用全序（预防层，宽松开发期即抓）、B08 用等待图环检测（检测层，抓全序豁免边上的真环）——两层漏斗：全序过滤掉绝大多数、环检测兜底剩余。这个漏斗架构是 B07/B08 的分工宪法，判据行原文记之。同 class 嵌套：`class <= c` 包含等号 → 同类嵌套即违例（自锁预防），豁免走白名单。现有内核接入：规则对旧票锁的适用性——旧锁无 class（F3339 给分配建议），注册前不校验（透明过渡）。Windows 对比：Driver Verifier 的死锁检测是纯运行时等待图（无层次预防层）；我们的漏斗双层的预防层是超 Windows 的能力（对齐 lockdep 但静态化）。M-086 复测：逆序对构造（A(class=2) 持有下拿 B(class=1)）→ 记账含完整报告；白名单边（声明后）同场景零记账——豁免机制双向验证。

## F3328 层次违例报告格式（诊断信息设计）

**定位**：违例报告的五元组格式设计：时间戳/核号/持有链（栈快照）/新锁 (class,inst)/修复建议——让看到报告的人 30 秒内定位问题。
**语义边界**：只做格式与输出；触发在 F3327。报告的存储（违例史环形区，容量 8 条）在本条。
**判据**：
- J1：M-087：注入违例 → 报告五元组全项非空且持有链序正确（与栈快照一致）；违例史滚动（第 9 条覆盖第 1 条）。
**纯功能行数**：280（格式定义 ~100 + 输出实现 ~100 + 违例史 ~80）
