## F3402 断言宏族总表（kexpect_eq/ne/true/false/null/notnull）

**定位**：六基础断言宏：kexpect_eq（相等）/ne（不等）/true/false（布尔）/null/notnull（指针空判）——ktest 词汇表的第一层，覆盖 80% 断言需求。
**语义边界**：只做六宏本体；扩展宏在 F3403/F3404、报告在 F3405（六宏复用其报告器）。eq 对浮点不做（内核 v1 无浮点判据需求——判据行声明）。
**判据**：
- J1：M-161：每宏一正例一反例（正=通过、反=失败路径触发报告且计数正确）——12 用例全绿（反例以"失败被正确记录"为通过标准）。
- J2：宏展开零堆分配、失败路径堆计数不变。
**纯功能行数**：380（六宏展开 ~200 + 失败路径接入 ~100 + 用例 ~80）
**依赖与嫁接源**：F3405 报告器；F3408 计数。
**风险与回退**：宏展开的求值副作用（kexpect_eq(a++, b) 双求值）——回退：宏契约声明"参数仅求值一次"并用逗号表达式技巧保证（判据行给展开骨架与单求值证明用例）。
**正文**：宏签名（判据行原文）：`kexpect_eq!(actual, expected)` / `kexpect_ne!` / `kexpect_true!(cond)` / `kexpect_false!(cond)` / `kexpect_null!(p)` / `kexpect_notnull!(p)`——统一前缀 kexpect 的命名理由：与 std 的 assert 区分（内核测试面独立词汇）+ k 前缀与 ktest 品牌一致。单求值展开骨架：`do { let _a = &($actual); let _e = &($expected); if !(_a == _e) { fail!(...) } } while(0)`——借用绑定使求值恰一次（M-161 附单求值验证用例：副作用计数器参数）。失败路径：调 fail!（F3405 报告器）→ 记账（F3408）→ 按模式（F3409）续跑或中止——三段式失败管线是六宏与后续所有宏的公共底座。为什么 true/false 与 null/notnull 独立成宏而不让 eq 覆盖（kexpect_eq(x, true)）：专用宏的诊断串更强（kexpect_null 的失败报告直接说"期望空指针，实际 = 0x..."，eq 版只会打印两值）——诊断质量是判据宪法的要求（判据行声明）。现有内核接入：testing/ 旧断言（若有 assert 类）映射归 F3416 迁移清单。Windows 对比：TAEF 的 VERIFY_ARE_EQUAL 系列语义对齐（VERIFY 前缀=continue 模式、ASSERT 前缀=strict 模式——我们 F3409 两模式与 TAEF 同构，判据行给映射）。M-161 复测：12 用例 + 单求值 + 零分配。

## F3403 kexpect_range/align 宏（数值域与对齐断言）

**定位**：数值域与对齐断言：kexpect_range!(v, lo, hi)（闭区间）与 kexpect_align!(p, n)（n=2^k 对齐）——内核数值判据的两个高频特形（地址对齐、容量边界）。
**语义边界**：只做两宏；内存块在 F3404。align 的 n 参数校验（非 2 的幂 → 编译期拒绝）在本条。
**判据**：
- J1：M-162：range 边界四例（lo-1 败/lo 过/hi 过/hi+1 败）+ align 三例（对齐过/不对齐败/n 非 2 幂编译失败——compile_fail）全绿。
**纯功能行数**：280（两宏 ~140 + 编译期校验 ~70 + 用例 ~70）
**依赖与嫁接源**：F3402 六宏的失败管线复用；const 判定（2 的幂检查 const fn）。
**风险与回退**：range 的 lo>hi 逆序参数（逻辑错被静默放过）——回退：debug_assert!(lo <= hi) + 判据行声明（逆序区间恒失败——宁可失败不可静默）。
**正文**：实现路径：`kexpect_range!(v, lo, hi)`：`lo <= v && v <= hi`，失败报告含三值（actual/lo/hi）——三值报告是 range 宏的诊断优势（普通 eq 复写需要两个断言且丢失区间语义）。`kexpect_align!(p, n)`：`(p as usize) & (n-1) == 0`；n 的 2 幂校验用 const fn（`n.is_power_of_two()`——const 求值，编译期拒绝非 2 幂——compile_fail 用例 M-162 附）。对齐断言的场景驱动（判据行给三例）：页对齐（F3351 克隆区 4K）、缓存行对齐（F3205/F3268 的 64B）、per-CPU 布局（F3282 的 64B 隔离）——三场景都是 B01–B10 已交付的判据，本宏让它们获得专用断言词。现有内核接入：无（新词汇）。Windows 对比：TAEF 无对齐专用宏（写 VERIFY_IS_TRUE((p & 63) == 0)）；我们词汇化对齐判据——判据宪法"每个常见判据长成专用词"的实例。M-162 复测：四 + 三 + compile_fail 一（kind=compile_fail 元数据——F3407 支持的验证）。

## F3404 kexpect_mem_eq（内存块比较断言）

**定位**：内存块等值断言：kexpect_mem_eq!(a, b, len)——块比较 + 首差异偏移报告（"第 37 字节起不等：0x41 ≠ 0x42"）。
**语义边界**：只做块等值；结构体等值用 eq（derive）；超大块的截断报告（首 3 处差异后省略——判据行声明）。
**判据**：
- J1：M-163：相同块通过；差异块报告首差异偏移正确（构造第 37 字节差异 → 报告 offset=37）；多差异截断（5 处差异报前 3）。
**纯功能行数**：260（块比较 ~100 + 差异定位 ~90 + 用例 ~70）
**依赖与嫁接源**：F3405 报告器；F3408 计数。
**风险与回退**：报告缓冲溢出（差异多）——回退：报告缓冲定长（64B 摘要——F3405 的缓冲契约）+ 截断计数（"...+2 more"）。
**正文**：实现路径：`kexpect_mem_eq!(a, b, len)`：逐字节比较（u8 步进——SIMD 不用，判据行声明：失败路径需要偏移定位，逐字节最简且通过路径由 F3418 预算兜底——40 拍含比较调用），首差异即停 → 报告 (offset, a[i], b[i]) + 继续扫描计差异总数（截断报前 3）。失败报告样例（判据行内嵌）：`MEM_EQ FAIL @test.cases+0x12: len=64 offset=37: 0x41 != 0x42 (total_diff=5, showing 3)`。场景驱动：样本结果账的内存校验（M-060 的校验和场景）、上下文页清零验证（F3411 的隔离检查——"页必须全零"用 mem_eq 对零页）——两场景已在 B01–B10 判据行出现，本宏是对既有判据写法的词汇化收编。现有内核接入：无。Windows 对比：TAEF 无内存块宏（memcmp + 布尔）；专用宏的偏移诊断是内核开发刚需（结构体布局错误的定位效率）。M-163 复测：三段（相同/单差异/多差异截断）。

## F3405 断言失败报告格式（文件/行/期望/实际）

**定位**：断言失败报告器：四元组（file/line/expected/actual）+ 扩展字段（用例名/域/断言序号/诊断串）——失败可读性的统一出口（全部宏共用）。
**语义边界**：只做报告器；输出通道复用 logger 桥（B15 接管后升级）。报告缓冲定长契约（128B 摘要 + 定长头部）在本条。
**判据**：
- J1：M-164：注入失败 → 报告含 file（编译期定位）/line/期望值/实际值/用例名五要素非空；缓冲不溢出（长值截断带省略标记）。
**纯功能行数**：320（报告结构 ~110 + 渲染 ~110 + 缓冲契约 ~100）
**依赖与嫁接源**：Rust 宏的 file!/line!（编译期定位）；F3412 诊断串；logger 桥。
**风险与回退**：file!/line! 在宏嵌套中失真（嵌套宏指向中间层）——回退：全部宏的单层展开纪律（kexpect_* 直接是用户调用的最外层——判据行给展开深度 1 的声明与检查用例）。
**正文**：实现路径：`fn fail!(file, line, case, expect_str, actual_str, ctx)`——file!/line! 在宏展开处求值（F3402 的展开骨架里内嵌）；渲染四元组 + 上下文：`FAIL [A5-B03-M-005] sync/mutex.rs:88: try_lock 应失败 — expected: Err(Busy), actual: Ok(guard)`。缓冲契约：头部定长（64B：case/file/line/序号）+ 值摘要 64B（超长截断 + "...(+N)"）——总 128B 静态缓冲零分配。为什么 file/line 是判据三件套的隐藏第五件（判据行论证）：可复测（三件套）的前提是失败可定位——file/line 让失败到代码的路径最短，ktest 面的 1 万+ 断言若失败不可定位，面越大越不可运维——报告器是断言面的可运维性投资。用例名的自动携带（从 F3407 元数据上下文——执行器注入，判据行给注入机制：fail! 读当前用例上下文——F3411 的上下文页）。现有内核接入：logger 桥输出（B15 升级分级——WARN 级别）。Windows 对比：TAEF 失败输出格式（文件/行/表达式三段）对齐——我们加用例名与断言序号（TAEF 无序号——批量失败时序号定位第几个断言，运维性增量）。M-164 复测：五要素断言 + 长值截断 + 深度 1 检查。

## F3406 用例注册宏 kcase!（静态注册表 + 分域命名空间）

**纯功能行数**：380（宏展开 ~150 + 注册表聚合 ~130 + 查询 ~100）

## F3409 断言失败不中断模式（continue 模式与严格模式）

**定位**：失败处理的两种模式：continue（记录失败续跑——信息收集最大化）与 strict（首败即停——快速反馈），用例级可配 + 全局默认——失败语义的治理面。

- J1：M-168：同一 5 断言用例（第 2 断言失败）——continue 模式跑完 5 断言（失败 1 过 4）；strict 模式停在第 2（后 3 未执行——执行计数证明）。
**纯功能行数**：300（模式机制 ~110 + 用例级配置 ~100 + 用例 ~90）
**依赖与嫁接源**：F3405 失败管线；F3407 元数据（模式字段——经标签位图承载，判据行给标签位）。
**风险与回退**：continue 模式的失败级联（第 2 断言失败导致后续断言无意义地失败——错误级联噪音）——回退：反模式文档（F3419）声明"continue 适用于独立断言序列"（断言间有依赖时用 strict——使用纪律而非机制强制）。
**正文**：实现路径：失败管线的模式分支：`if mode == Strict { fail! + 记账 + return-from-case }` else `{ fail! + 记账 + 继续 }`——return-from-case 的实现：宏展开含提前返回（用例函数的返回协议——`CaseResult` 类型，判据行给协议：Ok=全过/Err(Report)=strict 失败/Err(Skip)=跳过）。模式配置：用例级经标签位（STRICT 位——F3407 位图）+ 全局默认（B13 运行参数——接口约定 F3417）。TAEF 映射（判据行）：VERIFY_*=continue、ASSERT_*=strict——我们的标签位对齐其前缀语义。continue 的价值场景（判据行给实例）：M-060 压测的四表断言（多组独立对账）——一个失败不应掩盖其他失败（信息最大化）；strict 的价值：M-104 的环检出断言（失败后状态不可信——继续跑产生噪音）——两模式各有地盘，使用纪律归 F3419。现有内核接入：无。Windows 对比：如上 TAEF 映射。M-168 复测：两模式行为对照 + 执行计数证明 + 标签位配置验证。

## F3410 用例前后置钩子（setup/teardown）

**纯功能行数**：300（钩子机制 ~110 + 必达契约 ~100 + 族级 ~90）
**依赖与嫁接源**：F3338/F3399 的测试钩子需求单（兑现条目）；F3411 上下文页。
**风险与回退**：teardown 里再失败（清理代码有 bug）→ 状态泄漏扩散到下用例——回退：TEARDOWN_FAIL 记账 + 隔离页强清零（F3411 的机械清零兜底——逻辑清理失败时物理清零保底，双保险判据行声明）。
**正文**：实现路径：执行器（B13）的用例生命周期：`setup(ctx)? → run(ctx) → teardown(ctx)`（teardown 无条件执行——setup 成功路径上）；setup 失败 → `Err(Setup)` → teardown 跳过（判据行论证：setup 失败 = 环境未建立，teardown 清理半成品可能制造新错误——跳过是保守正确；泄漏由 F3411 页清零兜底）。族级钩子：`kcase_group!(组名, setup_fn, teardown_fn, [用例...])`——组 setup 一次、组 teardown 一次（组内用例共享贵重资源——判据行给场景：桩调度器初始化一次跑 10 用例）。teardown 必达的契约价值（判据行论证）：B01–B10 大量用例依赖清零（违例史/账本/图）——若失败路径跳过清理，用例间泄漏制造 flaky——必达契约 + 机械清零双保险让 flaky 从机制上被压制（ktest 面可运维性的关键承诺）。现有内核接入：F3338 需求单兑现（teardown 清零钩子迁入正式机制）。Windows 对比：TAEF 的 setup/teardown/cleanup 三层（class/module/test）——我们两层（case/group）对齐其主两层。M-169 复测：必达性（失败路径 teardown 执行）+ setup 失败跳过语义 + TEARDOWN_FAIL 计数 + 族级一次性验证。

## F3418 性能预算：单断言纳秒级开销测量

**定位**：断言开销的量化预算：通过路径 ≤ 40 拍（2 原子 + 比较 + 计数）/失败路径 ≤ 600 拍（+报告渲染）——1 万+ 断言不拖垮运行时间的成本背书。
**语义边界**：只做测量与预算；测量方法内嵌（ktest 基准用例——与 F3331 同法）。拍数随主频换算 ns（判据行给 3GHz 换算：40 拍 ≈ 13ns）。
**判据**：
- J1：M-173：三宏基准（eq/true/mem_eq）各 10,000 次 → 通过路径平均 ≤ 40 拍；注入失败 × 100 → 失败路径平均 ≤ 600 拍；分解表（求值/比较/记账/报告）交付。
**纯功能行数**：280（基准用例 ~110 + 分解测量 ~90 + 预算表 ~80）
**依赖与嫁接源**：F3204 TSC；F3331 测量体例；F3417 预算口径。
**风险与回退**：真机拍数差异——回退：预算以拍计 + 闸口重标（F3331 同款双轨预留）。
**正文**：实现路径：基准用例 = 循环内单宏调用夹 TSC 差值（排除循环开销——空循环基线扣除，判据行给基线扣除法）；分解测量 = debug 构建的段计时（求值段/比较段/记账段/报告段——F3331 同款分段计）。预算推导（判据行）：通过路径——参数求值 ~5 + 比较 ~3 + 计数 RMW ~10 + 分支 ~2 = 20 拍（40 上界 = 2 倍余量）；失败路径——+报告渲染（128B 缓冲写 ~200）+ 事件发射（可选档 ~150）+ 模式分支 ~50 = 400 拍（600 上界）——推导式与 M-173 实测对照（推导与实测偏差 > 30% = 测量方法审查——判据行给偏差审查规则）。1 万断言的总预算：10,000 × 40 拍 = 40 万拍 ≈ 0.13ms（3GHz）——断言开销对全库运行时间（秒级）的贡献 < 0.01%——"断言面近乎免费"的量化结论，判据行原文记之（这是"为什么敢写 1 万+"的性能答案）。现有内核接入：无。Windows 对比：TAEF 无官方断言开销数据（其开销含进程隔离远大于宏开销）——我们的拍级预算是内核内测试的专属精细化。M-173 复测：三宏基准 + 分解对照 + 偏差审查。
