## F3261 rwlock 结构与读偏好语义定义

**定位**：`RwLock<T>` 根条目：定义状态字编码与"读可并发、写独占、写者优先"的行为契约，是 B04 全批的结构底座。
**语义边界**：只定义结构与状态迁移；排队细节在 F3263/F3265、统计在 F3268。RCU 读侧方案（F3274）与 seqlock（F3269）独立交付，不混入本条。
**判据**：
- J1：M-020：三态迁移（自由→读持→写待/写持）各态可达且断言状态字符合编码表；可重复运行。
- J2：状态编码表唯一（本条为唯一定义点），其余条目引用不重定义。
**纯功能行数**：400（状态字编码与结构 ~140 + 三态迁移逻辑 ~130 + 判据行与文档 ~130）
**依赖与嫁接源**：F3201 原子底座；F3241 mutex 的结构体例与统计字段口径。
**风险与回退**：读计数与写者位共用一个字可能出现编码溢出——回退：读计数限 2^30 并在获取路径断言上限，溢出即记账拒绝（防御式上限优于静默溢出）。
**正文**：实现路径：状态字 `state: AtomicU32` 编码——bit31 = WRITER，bit30 = WRITER_WAITING，bit0–29 = 读者计数；编码表在判据行固化：`自由=0；读持=0x00000001..0x3FFFFFFF；写持=0x80000000；写待=0xC0000000|n`。数据结构：`RwLock<T> { state, writer_owner: OwnerCell, waitq: WaitQueue, stats: RwStats, _data: UnsafeCell<T> }`——writer_owner 复用 F3244 的 OwnerCell（一物两用，跨批统计口径统一），waitq 是读写共用的单队列（优先仲裁靠 F3265 的让位逻辑而非双队列，队列结构减半是刻意取舍，判据行声明理由：单队列天然保 FIFO 公平，双队列引入仲裁歧义）。现有内核接入：新文件 `sync/rwlock.rs`，桥点登记进 F3259 的登记表扩展行；与 B01 锁事件缓冲共用事件枚举空间。Windows 对比：Windows 内核的 ERESOURCE 是标准读多写少原语（`ExAcquireResourceSharedLite` 等），语义为共享获取可递归、独占获取需 IRQL <= APC_LEVEL；我们不引入递归读（读递归与 F3232 重入检测冲突，留给未来 ADR），IRQL 约束由 F3247/F3254 的上下文断言表达。ERESOURCE 的 SharedWaiters/ExclusiveWaiters 双链表设计即上述"双队列"，我们单队列的理由即对它的回应：内核本体小而可审计优先。M-020 的复测：三态迁移各用桩注入一次到达路径（读者到达/写者到达/写者离开），状态字逐位断言。

## F3262 读锁 fast path（原子加减读者计数）

**定位**：读锁获取的快路径：单条 CAS 把读者计数 +1，释放时 -1，无队列交互，读并发零等待。
**语义边界**：只做无争用读路径；存在等待写者时的让位逻辑归 F3265；统计记账点在本条内插桩。
**判据**：
- J1：M-021：8 核并发读 1,000 轮全走快路（无一次入队），读计数峰值对账（峰值 ≤ 8）。
- J2：读获取释放均为单原子操作（判据行给指令级预算：≤2 条原子指令/侧）。
**纯功能行数**：320（快路 CAS 与上限断言 ~100 + 释放递减 ~70 + 记账插桩 ~80 + 判据行 ~70）
**依赖与嫁接源**：F3261 编码表；F3201 原子底座（Acquire/Release 序选择）。
**风险与回退**：读计数上限断言在高核数下可能误伤——回退：上限 2^30 远超 8 核现实，断言仅防御未来扩展，触发即 ADR 议题。
**正文**：实现路径：`read_lock` = `loop { let s = state.load; if s & (WRITER|WRITER_WAITING) == 0 { if state.cas(s, s+1, Acquire) { break } } else { 走 F3265 让位路径 } }`；`read_unlock` = `state.fetch_sub(1, Release)`，若减到 0 且 WRITER_WAITING 置位则触发 F3266 批量放行（放行逻辑归 F3266，本条只留调用点）。数据结构：无新增。内存序选择：获取 Acquire、释放 Release——读侧不需要 AcqRel 全栅栏，这是对照 F3201 序包装的成对约定，判据行写明两点的序配对表（与 F3237 的序审计方法同源）。现有内核接入：页表遍历与位图查询是现有内核"读多写少"的主要候选点（F3279 扫描清单交付），本条不接入调用点，只提供能力。Windows 对比：Windows 读侧快路是 `ExAcquireResourceSharedLite` 的内联 fast path，争用时走 ExpWaitForResource 慢路；其实现细节封闭，但性能特征（读快路零内核调用开销）一致。我们的判据 J2 把指令级预算写死（≤2 条原子指令），这是把 Windows "实践上很快"升格为"判据上必快"的 A5 风格——1 万+ 断言运动的哲学：每条性能承诺都长成一条可测断言。M-021 复测要点：峰值计数用读侧快照采样（F3276 的 snapshot 扩展），8 核同时持有时采样应见到 8；释放对账为 acquire 计数 == release 计数 == 8,000。

## F3263 写锁与写者优先仲裁

**定位**：写锁获取：独占语义 + 写者优先仲裁（写者到达即阻断新读者），保证读流下写者不会被无限推迟。
**语义边界**：仲裁只做"到达置位 + 新读者让位"；饥饿上界保证归 F3265；写者间排队走 F3242 的 FIFO 队列（复用不重造）。
**判据**：
- J1：M-022：读持有时写者到达（WRITER_WAITING 置位），后续新读者全部入队不进快路；写者最终获锁。
- J2：写-写竞争走 FIFO（同 F3249 公平契约），M-022 断言两写者获锁序 = 到达序。
**纯功能行数**：400（写获取 CAS 链 ~120 + WRITER_WAITING 置位与读侧感知点 ~110 + 写者间排队复用 ~90 + 判据行 ~80）
**依赖与嫁接源**：F3261/F3262；F3242 队列；F3244 owner（writer_owner 写点）。
**风险与回退**：写者置位后读者仍可能已在快路中段——回退：快路 CAS 每次重读 state，置位后 CAS 天然失败，让位逻辑接管，无需额外窗口控制（判据行证明该竞态被状态机吸收）。
**正文**：实现路径：`write_lock`：先 CAS `0→WRITER` 试独占（无读者无写者时直进）；失败则置 `WRITER_WAITING`（`fetch_or`），然后按 F3242 入队睡眠，醒来重试独占 CAS。置位原子性：`fetch_or(WRITER_WAITING)` 与读侧 `cas(s, s+1)` 的竞争窗口——读者先读 s（无写位）后 CAS，若期间写者置位，CAS 的 compare 值已过期必失败，读者重读见到写待位走让位——状态机的单字原子性天然吸收该竞态，判据行给出这段证明作为 J1 的理论部分。写者间公平：第二写者到达时第一写者可能未持锁（还在队里），两写者都入队按 FIFO 交接（交接位机制与 F3242 全同）。现有内核接入：`cpu/sync.rs` 无读写锁遗产，桥点登记"新能力、无接管物"。Windows 对比：Windows ERESOURCE 的独占获取同样有"到达即断新读"的语义（ExSetResourceOwnerPointerExclusive 类机制配合），其写优先由 ExpBoostOwnerThread 等内部策略保障；我们用显式 WRITER_WAITING 位让"写者优先"从一个内部策略变成一个可观测的状态位——M-022 的注入断言就是这个位的判据化。J2 的写-写 FIFO 复测：双核同发写请求 200 轮，事件账本核对到达序 == 获锁序。

## F3264 RAII 读/写 guard

**定位**：`RwReadGuard<'a,T>` 与 `RwWriteGuard<'a,T>` 的 RAII 封装：drop 对称释放、Deref 权限分级（读 guard 无 DerefMut）。
**语义边界**：只做 guard；F3273 的调试标记在本条留钩子点（guard 类型标注），本体归 F3273。
**判据**：
- J1：M-023：读/写 guard 获取-持有-释放 1,000 轮计数对账；编译期证明：读 guard 无 DerefMut 实现。
- J2：写 guard 提供 DerefMut；drop 次序契约（先记账后放锁）与 F3243 一致。
**纯功能行数**：300（双 guard 结构与 Deref ~100 + Drop 双路径 ~100 + 权限分级与判据行 ~100）
**依赖与嫁接源**：F3243 体例；F3261–F3263 路径。
**风险与回退**：读 guard 误得 DerefMut 会让"读锁写数据"通过编译——回退：类型系统层面物理禁止（读 guard 不实现 DerefMut），并配 M-023 编译失败断言（compile_fail 测试）。
**正文**：实现路径：两 guard 各持 `&'a RwLock<T>` 与 TSC 快照；Drop 读路径 = F3262 的 read_unlock 链，写路径 = F3263 的写释放链（含交接/唤醒调用点）。权限分级是本条的灵魂：`RwReadGuard` 只有 `Deref<Target=T>`，写数据必须持有写 guard——这是把 Windows 语境里"约定 + Driver Verifier 事后抓"的问题前移到编译期解决。Windows 对比：ERESOURCE 的读获取（Shared）与写获取（Exclusive）在 C 语境无类型区分，驱动"以 Shared 持有却改数据"是常见 bug，Driver Verifier 的资源验证选项事后检测；Rust 的借用权限模型从类型上排除该类，等价于 NT 生态内 rust-for-windows 绑定的承诺，但我们在内核本体即得。Drop 次序契约：记账（F3268）→ 事件（F3275）→ 放锁——与 F3243 的次序一字不差，跨族一致性是 B07 统一打点的前提，判据行交叉引用。M-023 复测：compile_fail 用例是 ktest 特殊类（编译期断言），注册元数据标注 kind=compile_fail，B11 的执行器需识别该类（对齐 F3415 的宏族自测设计）。

## F3265 写者饥饿防护（读侧让位）

**定位**：把"写者优先"从置位语义升格为有上界的契约：存在等待写者时新读者一律入队，写者获得锁的等待时间有可测上界。
**语义边界**：只管读侧让位与写者延迟上界；上界数值的测量报告归本条交付，调参建议归 B13 性能预算面。
**判据**：
- J1：M-024：持续读流（7 核循环读）+ 写者注入 100 次，每次写者获锁延迟 ≤ 上界 T_w（判据行给默认值与测量方法）。
- J2：让位路径与快路路径分开计数（yield_count vs fast_read），M-024 对账。
**纯功能行数**：340（让位判定 ~90 + 上界测量与断言 ~110 + 计数分离 ~80 + 判据行 ~60）
**依赖与嫁接源**：F3261/F3263；F3204 TSC（延迟测量）。
**风险与回退**：上界 T_w 取值过严导致读吞吐下降——回退：本条只断言"有界"不断言"最优"，T_w 默认值 = 2 倍单轮读临界区时长，实测分布入判据行，调参走 B13。
**正文**：实现路径：读路径看到 WRITER_WAITING 置位即走让位：`yield_count++; 走 F3242 入队`——读者入队后由写者释放时的 F3266 批量放行接回。上界的构成分析（判据行理论基础）：写者等待 ≤ 当前在临界区读者数量 × 单读者临界区时长（在读不递归前提下有限）+ 队列交接开销，我们测量上界而非估算上界——M-024 的 100 次注入就是 100 个实测样本，最大值即经验上界，断言"不超 2 倍中位数"作为稳定性判据。数据结构：yield_count 与写者延迟直方图桶（对齐 B01 F3212 的等待直方图结构）。现有内核接入：无接管物（新能力），桥点登记。Windows 对比：Windows ERESOURCE 的饥饿防护在 ExpWaitForResource 内部（文档不承诺上界），实务中驱动写者靠"短临界区纪律"自保；我们给出实测上界契约是超 Windows 文档承诺的，理由与 F3248 相同：7×24 零误报验收需要可预测性背书。M-024 复测的反向样本：不注入读流时写者延迟基线（对照组），证明上界断言不是恒真——对照组数据入判据行。

## F3266 读侧批量放行（写者离开唤醒策略边界）

**定位**：写者释放时的唤醒策略：一次性唤醒全部等待读者（批量放行），唤醒动作经 F3246 协议逐个递交（醒归 A3 的边界保持）。
**语义边界**：只做写→读的批量交接；读→写的唤醒（最后读者触发写者唤醒）是单点唤醒，在本条顺带定义；批量唤醒的实现原子性（先摘队再唤醒）在本条。
**判据**：
- J1：M-025：写者释放时 N 个等待读者全部被唤醒（WakeReason=WOKEN 各自收到），无遗漏无重复。
- J2：批量唤醒期间队列结构不变式保持（摘队原子后逐个 wake，中断点可见状态一致）。
**纯功能行数**：300（批量摘队 ~100 + 逐个协议递交 ~80 + 最后读者单点唤醒 ~60 + 判据行 ~60）
**依赖与嫁接源**：F3242 队列；F3246 协议；F3261 状态字（WRITER 位清除时序）。
**风险与回退**：唤醒过程中新写者到达——回退：摘队先于 WRITER 位清除，新写者入队排在被唤醒读者之后（公平性保持），该次序契约写判据行。
**正文**：实现路径：写释放 = `writer_owner 清账 → 批量摘队（整队取走，队列瞬间变空）→ 清 WRITER/WRITER_WAITING 位 → 逐个 wake_protocol`。摘队与清位的次序是本条的竞态要害：若先清位，新读者会在"队还有人"的窗口涌入快路，造成被摘队者与快路读者并存（合法但浪费）；若先摘队后清位，窗口内新读者看到旧位直接入队（空队入队合法），语义一致且无浪费——选后者。最后读者单点唤醒：read_unlock 减到 0 且 WRITER_WAITING 置位时唤醒队首写者（单点，走 F3246）。现有内核接入：唤醒递交全部经 SleepPort trait，本条不新增协议面（v1 冻结纪律）。Windows 对比：Windows ERESOURCE 释放时的唤醒批量（ExpWaitForResource 唤醒所有共享等待者）与我们同构；其"starve prevention"细节封闭，我们把摘队-清位次序写成判据行证明——A5 的风格：策略可以简，但次序必须可证。M-025 复测：N=3 桩注入，事件账本核对三个 WOKEN 与零 SPURIOUS；再注入"唤醒中途新写者到达"场景断言其入队而非抢位。

## F3267 irqsave 变体

**定位**：读写锁写侧的 irqsave 变体（获取前关中断、释放后恢复），对齐 B01 F3207 的自旋锁 irqsave 体例。
**语义边界**：只做写侧 irqsave（读侧禁中断收益低、禁读侧是误用高发区，判据行声明）；中断开关原语复用 A4 域既有能力（桩先行）。
**判据**：
- J1：M-026：桩中断环境获取 irqsave 写锁成功且中断标志被保存；释放恢复原标志（含"原本就关中断"的幂等情形）。
- J2：变体与普通变体共用状态机（无平行实现），编译产物符号核对确认。
**纯功能行数**：260（获取包装 ~80 + 恢复与幂等 ~80 + 判据行 ~100）
**依赖与嫁接源**：F3207 体例；F3263 写锁；中断标志读写口（A4，桩先行）。
**风险与回退**：A4 中断接口未实装——回退：同 F3246 桩先行模式，接口 v1 冻结进 F3277 签名表。
**正文**：实现路径：`write_lock_irqsave(&self) -> (RwWriteGuard, IrqFlags)`——获取前 `flags = save_irq(); disable_irq();`，guard drop 时恢复。幂等情形：进入时中断本就关，恢复时不得开中断——保存/恢复 flags 而非盲开，就是 B01 F3207 已验证的正确模式，本条机械复用（判据行引用其用例编号）。数据结构：无新增（IrqFlags 类型来自 B01）。现有内核接入：现有内核写临界区内已有手工关中断点（扫描清单归 F3279），本条就位后清单标注替换建议。Windows 对比：Windows ERESOURCE 要求 IRQL <= APC_LEVEL 且其获取不自动提 IRQL（与 KSPIN_LOCK 的 DISPATCH_LEVEL 语义相反），驱动需自行 KeRaiseIrql——我们不做 IRQL 数值，irqsave 变体的语义等价"手工提 IRQL 的库化"：把容易错的保存/恢复对包成 RAII，这是对 Windows 惯例的工程化改进，判据行写明映射（irqsave ≈ KeRaiseIrql(DISPATCH)+获取的合并物）。M-026 复测：三情形——开中断进入、关中断进入、嵌套两层 irqsave——恢复值逐层正确。

## F3268 持有时间与争用统计

**定位**：rwlock 的读写分离统计：cont_r/cont_w（争用）、max_r/max_w（长持）、fast/yield（读路径分布），口径与 MutexStats 同族。
**语义边界**：只做记账与聚合；导出格式归 F3276。读侧记账点在 F3262 插桩、写侧在 F3263，本条定义字段与口径不重复插桩。
**判据**：
- J1：M-027：注入场景（读争用 100 轮 + 写争用 50 轮）六计数对账精确匹配。
- J2：读/写计数物理分离（不同缓存行，对齐 F3205 体例），伪共享检查用例通过。
**纯功能行数**：280（字段定义与口径 ~90 + 注入对账用例 ~110 + 伪共享检查 ~80）
**依赖与嫁接源**：F3205 缓存行对齐体例；F3262/F3263 插桩点。
**风险与回退**：读侧高频记账可能成为吞吐瓶颈——回退：读侧记账用 per-CPU 计数（对齐 F3213 体例），全局读数 = 求和；写侧低频用直接原子。
**正文**：实现路径：`RwStats { cont_r, cont_w, max_r, max_w, fast_read, yield_count }`，读侧四项走 per-CPU 桶（读路径高频，8 核无争用时记账开销摊到各自缓存行），写侧两项直接原子（低频）。求和接口 `total_reads()` 遍历 per-CPU 桶——非原子一致快照（撕裂容忍，判据行声明与 F3256 同款口径：观测不是判定）。max_r/max_w 用 TSC 差值（F3204 读钟）。现有内核接入：字段命名与 F043 旧票锁 contentions/longest_hold 对齐（+_r/_w 后缀），接管映射表归 F3279 登记。Windows 对比：ETW 的锁事件在 Windows 里不区分读写侧（ERESOURCE 事件统一通道），我们分离记账的理由是 A5 验收要分别证明"读并发无损"与"写公平有界"两件事——数据分离是证明分离的前提，判据行写明这条因果关系。M-027 复测：争用注入 = 双核同时读同一锁（cont_r 增长条件：CAS 失败重试次数 > 0 的轮次）——争用的定义在判据行精确化（不是"两核都读了"而是"有重试发生"），防止计数口径含糊。

## F3269 seqlock 结构与写序号协议

**定位**：`SeqLock<T>` 与写序号协议：写者每次写前后序号各 +1（偶=稳定、奇=写中），读者读前读后验序号判一致性。
**语义边界**：只做写序号协议与结构；读重试循环归 F3270。seqlock 无等待队列（读者不阻塞写者、写者不阻塞读者，只靠重试）——"无队列"本身是语义边界，判据行声明。
**判据**：
- J1：M-028：写 1,000 次后序号 == 2,000（每写 +2）且全程偶数快照可读；序号单调性断言。
- J2：写侧互斥由内嵌 SpinLock 提供（序号不管互斥只管版本），职责分离断言。
**纯功能行数**：400（结构体 ~110 + 写序号协议 ~110 + 内嵌互斥衔接 ~100 + 判据行 ~80）
**依赖与嫁接源**：F3202 SpinLock（写互斥）；F3201 原子底座（序号）。
**风险与回退**：序号溢出（32 位写满）——回退：64 位序号，物理不可能溢出（每微秒 1 次写也需 58 万年），判据行给算术。
**正文**：实现路径：`SeqLock<T> { seq: AtomicU64, inner: SpinLock<T> }`——写路径：`inner.lock(); seq.fetch_add(1, Release)（变奇）; 写数据; seq.fetch_add(1, Release)（变偶）;`；读路径在 F3270。数据结构要点：序号与数据的关系是"版本标签"，互斥交给 SpinLock——这与 Linux seqlock 的 `write_seqlock`（内含自旋）结构一致，但显式分字段让职责可见。数据类型要求：T 须 `Copy`（读者读到的可能是撕裂版本之外的旧完整版，非 Copy 类型无法安全值拷贝）——类型约束写进结构定义，判据行声明这是 seqlock 的本质限制而非实现缺陷。现有内核接入：现有内核时钟数据（`cpu/clock.rs` 的_ticks 类字段）是 seqlock 候选场景（单写多读、值小可拷贝），F3279 清单标注。Windows 对比：Windows 无标准 seqlock 原语（内核开发者手写序号模式，如 ExInterlocked 系列配合版本计数；NTFS 等组件内部有变体）；我们把民间模式库化并给出可测契约，M-028 的"每写 +2"断言就是 Linux `write_seqlock/read_seqbegin` 语义的判据化表达。J2 复测：写侧并发 200 轮（SpinLock 互斥生效）+ 序号与写次对应表核对。

## F3270 seqlock 读重试循环

**定位**：seqlock 读侧 begin/retry 协议：读前取序号（须偶）、读数据、读后再验序号，不一致则重试——无锁读的一致性协议。
**语义边界**：只做读协议；重试次数无上界是协议性质（写者风暴下读者可能长期重试）——该性质的风险声明与缓解（写侧限速建议）在本条判据行，不做内核内强制限速。
**判据**：
- J1：M-029：1 写者 100Hz + 4 读者并发 5 秒，读者全部收敛（无饿死），重试计数分布入账。
- J2：读到的一致性快照满足应用层不变式（用例自带校验和字段验证：值对内部一致）。
**纯功能行数**：380（begin/retry 协议 ~120 + 重试记账 ~90 + 内存序配对证明 ~90 + 判据行 ~80）
**依赖与嫁接源**：F3269 结构；F3201 内存序包装。
**风险与回退**：写风暴导致读者重试爆炸——回退：本条交付重试计数观测（retries 桶），B13 预算面可据此设定写侧限速建议；内核内不做强制（强制限速引入新同步点，违背 seqlock 无锁初衷）。
**正文**：实现路径：`fn read(&self) -> T { loop { let s1 = seq.load(Acquire); if s1 & 1 == 1 { pause(); continue; } let v = unsafe { *inner_data.read() }; let s2 = seq.load(Acquire); if s1 == s2 { return v; } retries++; } }`——两次 Acquire load 夹住数据读，序号不变即快照一致。内存序证明（判据行核心）：数据写先于第二次 +1（Release 保证序），读侧 s1 在数据读之前（Acquire 保证序）——若 s1==s2，则数据读落在两次版本写入之间且版本稳定，故快照完整。unsafe 块的安全论证：inner 的 SpinLock 写侧保证无并发写撕裂值语义（对 Copy 类型单值读天然原子性依赖——若 T 大于机器字，需复制循环，判据行声明 T 建议小值的工程约束）。现有内核接入：同 F3269 候选点。Windows 对比：Windows 的等价模式出现在时钟读取路径（KUSER_SHARED_DATA 的版本对读取）与驱动手写双读校验；我们提供库化原语并把内存序证明写成判据——ktest 1 万+ 断言运动里，"证明性断言"（把正确性论证变成可跑的检验）是高价值样本。M-029 复测的收敛定义：5 秒内每读者完成 ≥ 1,000 次成功读且 retries 分布中位数 < 10；校验和字段 = 数据内嵌 (value, ~value) 对。

## F3271 seqlock 与 rwlock 选型指南

**定位**：决策树条目：给"读多写少"场景一个可执行的选型方法（rwlock vs seqlock vs 留给 RCU），减少误用。
**语义边界**：本条是决策文档 + 对照用例，不新增机制；决策树覆盖三选（rcu 列为"高级选项"指向 B05）。
**判据**：
- J1：M-030：同一场景两实现对照跑（一致性要求高 → rwlock 版通过；容忍重试 → seqlock 版吞吐更高），对照数据入判据行。
- J2：决策树四问完备：读侧能否重复？写频率？临界区大小？是否需要写侧等待？
**纯功能行数**：240（决策树文档 ~100 + 对照用例 ~90 + 判据行 ~50）
**依赖与嫁接源**：F3261/F3269；B05 预告（RCU 语义边界 F3281）。
**风险与回退**：决策树教条化误导选型——回退：树末节点附"何时无视本树"节（如：性能敏感处先测量后选型，测量工具即 ktest 面本身）。
**正文**：决策树四问：①读侧能否接受重试或重复读？不能→rwlock（读侧单次语义保证）；能→②写频率 > 1%？是→rwlock（seqlock 重试率随写频率线性涨）；否→③临界区小且 T 可拷贝？是→seqlock（无锁读吞吐最高）；④需要写侧等待语义（如资源释放时序）？是→rwlock，否→seqlock。每问附反例：①的典型反例是"读侧要基于读到的值做指针解引用"（值可能失效——这正是 RCU 要解决的，指向 B05）；②的反例是时钟更新（写频极低，seqlock 完胜）。现有内核接入：对照用例用 clock.rs 候选点数据形态构造（不接真数据，防桥前依赖）。Windows 对比：Windows 内核文档对 ERESOURCE vs 快速互斥体 vs 手写序号的选择建议散见于 WDK 文档与 OSR 论坛，无官方决策树；本条把社区知识固化为可测的决策资产——ktest 面里"文档条目带对照用例"是 F3419 使用规范条目的同款体例。M-030 复测：对照跑用同一数据形态（64B 记录 + 校验对），seqlock 版读吞吐应 ≥ rwlock 版 3 倍（8 核读 1 写），倍数作为判据行基线（真机闸口重测）。

## F3272 死锁预备：rwlock 等待边登记

**判据**：
- J1：M-031：读写混合争用 500 轮后边账本平账（登记数 == 注销数），token 无悬挂。

**风险与回退**：读等待建模争议（多个读者等同一写者 = 一对多边）——回退：v1 契约"每读者一条独立边，共享目标锁节点"，图规模预算（F3352）按此上界预留，扩缩走 ADR。
**正文**：实现路径：写等待登记点在 F3263 入队后；读让位登记点在 F3265 入队后；注销点：写获得锁时、读进入快路时、TIMEOUT/CANCEL 撤销时（三处，与 F3251 的 TIMEOUT 平账教训对齐——B03 M-011 已证明撤销路径是漏注销高发区）。边载荷：`EdgeToken` 高位类型位（R/W），v1 契约写判据行。一对多模型：写者持锁 + 3 读者等待 = 3 条边（读等待者→写者）；读者持锁 + 写者等待 = 写者→3 读者各一条边（写需要所有读者退出）——这个方向语义是 B08 环检测能覆盖"读-写交叉死锁"（写者持 A 等 B，B 的读者链等 A）的关键，判据行给两个构造性死锁场景示意。现有内核接入：无接管物。Windows 对比：Windows Driver Verifier 对 ERESOURCE 的死锁检测把共享/独占等待统一进资源等待图（其 !locks 扩展可见 SharedWaiting/ExclusiveWaiting 计数）；我们的类型位设计对齐其可观测性字段。M-031 复测：专门构造"读者让位途中写者被取消"（TIMEOUT 注入）场景核平账——让位与撤销的交叉是最大泄漏风险。

## F3273 调试模式：读锁上下文非法写访问标记

**定位**：双层防护的写权限防线：编译层（读 guard 无 DerefMut，F3264 已做）+ 调试层（检测经 unsafe/裸指针绕过类型系统的写访问并记账）。

**判据**：

**正文**：实现路径：`RwLock` 注册"只读保护窗口"（调试档下写路径先查 `write_guard_active()` 标志，无写 guard 却发生写 = 违例记账）。检测语义精确化：检测点在"写动作发生时"（guard 层面的写路径包装 unsafe 写原语），能抓"用我们提供的写原语 + 伪造指针"的绕过；抓不住完全独立的任意地址写（那需要 A2 页保护）——诚实边界写入判据行：本条是"原语级防线"不是"内存级防线"。数据结构：违例账本复用 F3254 格式（时间戳/CPU/tag/对象名）。现有内核接入：无接管物。Windows 对比：Windows 检测"Shared 持有却写 ERESOURCE 保护数据"无内核内机制（Driver Verifier 在验证器进程核对获取记录与访问记录的时序交叉，事后分析）；我们做实时原语级检测，覆盖面窄但反馈即时——实时性 vs 覆盖面的取舍写判据行，真机闸口若 A2 页保护可用则升级。M-032 复测：正例（伪造指针写触发记账）+ 反例（合法写 guard 写不触发）+ 档位矩阵（debug 触发/release 零符号）。

## F3274 诚实边界：不做每 CPU 读副本完整 RCU（B05 承接）

**定位**：声明条目：B04 的读侧优化止步于 rwlock/seqlock；读侧零锁化（RCU）的完整方案归 B05（F3281–F3320），本条交付边界声明 + 前置条件 + 对照说明。
**语义边界**：声明条目，交付物 = 声明文档 + 反向证据用例；不实现任何 RCU 组件。
**判据**：
- J1：M-033 反向证据：构造"读侧需要解引用指针"场景，rwlock/seqlock 均需持锁/重试才能安全——证明边界必要性（为什么必须有 RCU）。
- J2：前置条件清单三条：宽限周期机制、回调设施、内存序原语完备——缺一不做，清单入声明文档。
**纯功能行数**：220（声明文档 ~90 + 反向用例 ~80 + 前置条件 ~50）
**依赖与嫁接源**：B05 F3281（承接方）；F3271 决策树（第①问的延伸）。
**风险与回退**：边界声明被误解为"读侧问题未解决"——回退：声明文档明确"读侧已解的问题（并发、公平、一致快照）与未解问题（锁开销本身）"两分法。
**正文**：为什么 rwlock/seqlock 不够：两者读侧仍要动共享字（rwlock 加减计数、seqlock 两次 load + 重试），在极端读并发下共享状态字本身成为瓶颈（cache line 弹跳，F3226 已在 qspinlock 语境测过同类现象）；RCU 的读侧完全零共享（只动 per-CPU 标记），这是质的边界而非量的优化。前置条件三条对应 B05 的 F3284（GP 状态机）、F3287（回调）、F3291（内存序原语）——声明文档给出映射，让 B05 的开工条件显式化。反向用例 M-033 的构造：链表查找场景——rwlock 版读时持读锁、seqlock 版读时重试循环、两者都无法回答"我读到的节点在读完前是否被释放"（指针生命周期问题），该问题的解即 RCU 宽限周期——用例以"三版本对照的失败模式"呈现边界。现有内核接入：无。Windows 对比：Windows 无内核级通用 RCU（晚期引入的精简 RCU 用于特定子系统，驱动不可用），驱动读侧优化惯例是 ERESOURCE + 缩临界区；我们做完整 RCU 是相对 Windows 主线驱动的增强，判据行注明动机（读侧 7×24 观测负载是本项目的主读场景）。J2 复测：清单逐项核对 B05 对应条目存在且未开工——声明条目自身的"可运行性"用跨批核对承载，这是声明条目的验收形态。
