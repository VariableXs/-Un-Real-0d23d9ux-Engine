## F3581 内存水位账总设计（per-pool 水位/四级线）

**定位**：内存水位的总账：per-pool（每内存池一张）维护当前用量与四级水位线（NORMAL 60%/WATCH 75%/HIGH 90%/CRITICAL 97%——以池容量为分母），越线即事件——内存压力的"温度计"（OOM 之前先看见）。
**语义边界**：水位账是**观测层**（读 A1 分配器的用量计数——不自计数——单真源原则：A1 的账是事实，水位账是投影，两账不一致=F3596 自检的活）；四级线的**语义分层**（判据行内嵌）：NORMAL=常态无动作；WATCH=关注（记峰值、加密采样——观测升级不告警）；HIGH=告警（WARN 双下游+F3592 预算对账自动触发——让运维与检测器都看见）；CRITICAL=行动（ERROR+通知 OOM 编排准备——CRITICAL 是"预 OOM"不是 OOM 本身——真 OOM（分配失败）是 A1 的事件，水位线是它的前哨）；线的**常量冻结**（60/75/90/97 四值编译期常量——改线值走修订流程不是配置项——线的语义要稳定才能积累运行经验）。
**判据**：
- J1：四级线语义表（级×阈值×动作×下游四列——判据行内嵌）；M-339 四级全链（注入逐级上升的用量序列→四级依次越线→各级动作与下游各按表执行→账记录每级越线时刻）。
- J2：线值冻结断言（编译期常量+运行期改值 API 不存在——"不存在的 API"式封闭，F3523 同律）。
**纯功能行数**：340（四级语义表 ~120 + 全链用例 ~120 + 投影论证 ~100）
**依赖与嫁接源**：A1 分配器用量账（数据源）；F3484 RingMgr 水位两级（75%/90% 同构先例——本批扩为四级并推广到全池）；F3487 RateTable（告警节流）；F3596 自检（对账对端）；F3584 联动（越线的下游执行者）。
**风险与回退**：线值不当（97% 太高——CRITICAL 触发时已无回旋）——回退：线值来自运行经验（B01–B15 的池压力数据回看——97% 定义的依据：A1 分配器在 97% 之上大分配成功率骤降（碎片效应）——CRITICAL 线在"还来得及"的位置）；per-pool 差异（不同池的 97% 语义不同——元数据池 97% 是灾难、对象池 97% 是常态）——回退：线值 per-pool 可配但**默认表冻结**（默认表与 F3577 九格表同风格——判例：默认统一、例外显式登记）；越线抖动（用量在 90% 线附近震荡→告警反复）——回退：滞回带（越线 90% 触发、回落 85% 解除——3% 滞回——F3487 节流之外的时域滤波）。
**正文**：水位账的结构（判据行原文）：`WaterLevel {cap: usize, used: AtomicUsize, level: AtomicU8, peak: u32, hyst: u8}`——cap/used 从 A1 投影（A1 更新 used 是分配热路径的既有动作——水位账**零额外税**——这是"观测不写"红线的技术落点：水位账不产生任何分配路径上的新写）；level 是滞回后的稳定态（原始 used 直接越线判断+滞回带平滑→level——下游只读 level 不读原始值——下游语义稳定）。四级语义表（判据行内嵌全文，与骨架 J1 逐值一致）：| 级 | 阈值 | 动作 | 下游 |——NORMAL <60%/无动作/无；WATCH ≥75%/峰值记录+采样加密（F3582 周期 1s→0.2s）/峰值账（F3583）；HIGH ≥90%/WARN 告警双下游/WARN→B15 日志+检测器事件（F3584 执行）；CRITICAL ≥97%/ERROR+编排预通知/演练框架（F3585 的真实触发背景）。为什么四级不是三级（判据行论证）：WATCH 与 HIGH 之间差的是"观测升级"与"告警"的本质不同（观测升级零打扰、告警有打扰成本——合并则要么告警太早（狼来了）要么观测太晚（错过峰值语境）——四级的代价是一张表，收益是语义正交）。滞回的实现（判据行展开）：`level = f(used%)` 是**单向棘轮**——升级即时（90.1% 即 HIGH——压力上升要快报）、降级带滞回（<85% 才回 WATCH——压力回落常是暂态抖动——棘轮防告警振荡）；M-339 的注入序列设计成"升-抖动-回落"三段，验证升级即时性与降级滞回性同时成立。J2 的封闭断言：线值表是 `const LEVELS: [(u8, fn); 4]`——运行期改线值的 API 不存在（表是 const——修改企图在编译期即败——与 F3523"不存在 deref"同族：最彻底的防护是不给入口）。M-339 复测：四级表+全链越线+滞回棘轮+线值冻结+零税断言（分配热路径拍数不变）。

## F3582 水位采样器（周期采样/事件驱动双模）

**定位**：水位账的取样节奏控制器：周期模（每 1s 全池巡检一轮）+事件驱动模（alloc/free 大宗变动时即时取样）双模并行——观测节奏与系统压力自适应。
**语义边界**：采样**读账不写账**（读 used 计数——原子读零锁——热路径零税红线的执行细节：采样器是"读者"，A1 是"记账者"，采样动作不出现在 A1 的路径上）；"大宗"的判据（判据行内嵌：单次 alloc/free ≥池容量 1% 或 ≥64KB——小分配不触发事件模（周期模兜底）——事件模的触发阈值本身是常量）；双模**不重复记账**（事件模取样与周期模取样写同一账——幂等：同一时刻的两次取样=一次（时间戳去重——取样是"记录状态"不是"计数事件"））；WATCH 级加密采样（F3581 语义：周期 1s→0.2s——加密是采样频率参数不是新通道）。
**判据**：
- J1：双模语义（周期 1s 基线+事件阈值 1%/64KB——判据行内嵌）；M-340 双模触发验证（周期取样按拍发生+注入大宗分配→事件取样即时发生+双模去重）。
- J2：零税断言（采样器开关关闭时分配路径拍数逐位不变——观测可关）。
**纯功能行数**：320（双模调度器 ~110 + 用例 ~110 + 去重论证 ~100）
**依赖与嫁接源**：F3581 水位账（采样目标）；B17 F3530 时钟 trait（周期计时的唯一入口——禁私取时间）；F3597 接入表（采样挂点登记）。
**风险与回退**：事件风暴（碎片抖动期大宗 alloc/free 频发→事件取样洪水）——回退：事件取样自身节流（RateTable 同表 F3487——最小间隔 10ms——事件模的"即时"上限是 100Hz 不是无限）；周期漂移（时钟源切换导致周期失真）——回退：F3530 时钟 trait 单源（采样器不感知时钟实现——假时钟下周期取样用虚拟拍驱动（确定性测试的基础））；采样遗漏（关中断窗口内的大宗变动错过事件取样）——回退：周期模兜底（事件模是加速器不是保证——下轮周期必补——两模互补的诚实声明：事件模保证**及时**、周期模保证**最终**）。
**正文**：双模的分工逻辑（判据行论证）：周期模回答"稳态下水位长什么样"（1s 粒度的趋势线——够用且便宜）；事件模回答"刚发生的大动作把水位推到哪了"（1%/64KB 阈值的设计：低于阈值的变动对水位线的影响小于半级滞回带（60% 线的 3% 滞回=大池 1% 量级）——不值得即时取样——阈值与滞回带自洽——判据行给这个自洽的算式：阈值取"足以推动半级水位"的最小变动，事件取样只发生在"可能越线"的时点——观测火力对准危险区）。实现（判据行原文）：`Sampler {mode: Periodic(1s), evt_thresh_pct: 1, evt_thresh_bytes: 64K}`——`fn on_alloc(pool, size) { if size >= thresh { sample(pool); } }`——sample() 内部先查时间戳去重（同 tick 幂等）再写账。M-340 的三段验证：段一关事件模只跑周期模——取样次数==周期数（确定性假时钟下逐拍核对）；段二开双模注入 3 笔大宗分配——事件取样恰好 3 次（阈值过滤精确）；段三同 tick 内周期+事件重叠——账只记一次（去重生效）。J2 的零税测量：采样器全关状态与基线（无采样器）的分配路径拍数 diff==0——观测税为零的**实测**而非声称（B18 F3547 同族：税要测）。加密采样的边界（判据行展开）：WATCH 加密到 0.2s 是周期参数变更不是新模（采样器的 mode 枚举只有 Periodic/EventDriven 两值——封闭词表——加密改的是周期值——参数化封闭：模式封闭+参数开放——F3521 槽位配额同构的"结构冻结内容活"）。M-340 复测：三段验证+零税实测+节流生效+双模去重+假时钟确定性。

## F3583 峰值账（历史峰值/watermark 记录）

**定位**：per-pool 历史峰值的记录账：任何时刻的 used 最高点（带时间戳）——"这台系统这辈子最挤的时候有多挤"——容量规划与预算对账的原始素材。
**语义边界**：峰值**只增不降**（watermark 语义——回落不抹峰值——峰值回答"曾经"不回答"当前"——当前归 F3581）；峰值**带时间戳**（何时达到的峰值——没有时间的峰值无法与负载场景关联——时间戳使峰值成为"事件"不是"数字"）；重启清零的诚实（峰值是运行期概念——重启后从零计——跨启动的峰值归持久化层（不在本批范围——判例：A5 不做持久化策略，只提供 `peak` 读取口））；WATCH 加密采样的峰值精度（采样间隙的尖峰可能漏采——峰值的精度=采样精度的函数——判据行给诚实的精度声明：峰值是**采样峰值**不是真峰值（事件模把大宗变动的尖峰补上了——双模互补让采样峰值逼近真峰值但不保证相等））。
**判据**：
- J1：峰值语义（只增不降+时间戳+per-pool 独立）；M-341 峰值正确（注入已知峰值序列→账记录恰为最大值+时间戳对齐）。
- J2：单调断言（任意读序下 peak 单调不减——并发下 CAS max 语义）。
**纯功能行数**：220（峰值结构 ~80 + 用例 ~80 + 精度声明 ~60）
**依赖与嫁接源**：F3581/F3582（峰值的数据来源）；F3592 预算对账（峰值的消费者）；F3598 RunDigest（峰值入摘要）。
**风险与回退**：并发峰值竞态（两 CPU 同时更新 peak——丢失最大值）——回退：CAS max 循环（`while old < new { CAS(peak, old, new) }`——lock-free 单调——J2 的并发断言直接测这个）；时间戳精度（峰值时刻的 ts 粒度粗——秒级时间戳配毫秒级尖峰）——回退：时间戳用 F3530 时钟 now()（与账其他字段同源——平局键 (ts,cpu,seq) 同构 B16——峰值的时间戳是"取样 ts"不是"真峰值 ts"——诚实标注）；峰值滥用（拿峰值当容量规划唯一依据——采样间隙偏差）——回退：峰值报表带采样密度标注（F3595 报告格式——峰值旁边印采样率——让读者知道这个数字的置信基础）。
**正文**：峰值账的结构（判据行原文）：`PeakBook {peak: AtomicUsize, peak_ts: AtomicU64, peak_pool: PoolId}`——更新路径：`fn observe(used, ts) { let mut p = peak.load(); while used > p { match peak.compare_exchange(p, used) { Ok(_) => { peak_ts.store(ts); break; } Err(x) => p = x } } }`——CAS max 的经典 lock-free 单调模式（无锁——争用下退避为"下个观察点再试"——峰值允许滞后一轮观察——峰值的实时性要求本来就低（它回答"曾经"））。M-341 的序列设计：注入 used 序列 [30%, 75%, 60%, 90%, 80%, 65%]——断言 peak 最终 90%、peak_ts 对齐 90% 那一拍的 ts、且中途 60%/80% 两个回落点**没有**更新 peak（只增不降的负例验证——J1 的"回落不抹"是断言点不是注释）。并发场景（J2 展开）：8 CPU 各注入随机 used 更新——最终 peak==序列真最大值（竞态丢失即不等于——这是 J2 的强断言：不测"大概率对"测"必然对"——CAS 循环的正确性论证：每个失败者读到更新的 p 重试——最大值最终被某个成功者写入——证明见任何 lock-free 教材——判据行给一句本体论证：CAS max 是"每个线程都试图把最大值顶上去"的共谋——共谋的终点必然是全局最大）。精度声明入报表（判据行展开）：峰值数字旁边的采样密度（本峰值时间窗内取样 N 次——N 越密置信越高——事件模命中的尖峰标"E"（事件取样捕获）vs 周期取样标"P"——两个来源的峰值可区分——排查时知道这个峰值是"大动作撞出来的"还是"趋势磨出来的"——峰值的考古价值在于区分两种故事）。M-341 复测：单调序列+CAS 并发+时间戳对齐+来源标注+精度声明入报。

## F3584 水位告警联动（越线→B15 日志/检测器事件）

**定位**：水位越线与下游的双通道联动：越 HIGH 线→WARN 日志（B15）+检测器事件（B17 账路）双下游；越 CRITICAL→ERROR 同双下游——告警的"必达但节流"投递层。
**语义边界**：双下游**都发**（日志给人看、检测器事件给机器对账——两通道语义不同不可互替——判例：B15 是人类叙事、B17 事件是结构化证据——同一事实两种表示是设计不是冗余）；节流**同表**（F3487 RateTable——水位告警与日志告警共用节流账——同一根源的告警不因双通道而双倍风暴——节流是按"根源"不按"通道"）；联动**不阻塞**（越线判定在观察路径——下游投递 fire-and-forget——投递失败不重试不阻塞（日志丢了是损失、水位判定卡住是事故——分级：观测的可靠性要求低于控制——诚实声明）；CRITICAL 的编排预通知（F3585 演练框架的"真实背景"通知——不是自动触发演练——演练何时跑是策略决定——通知只报告"条件已具备"）。
**判据**：
- J1：联动契约（HIGH→WARN+事件/CRITICAL→ERROR+事件——双下游各一+节流同表）；M-342 联动验证（HIGH 越线→双下游各一且节流生效——同根源第二次越线被节流）。
- J2：不阻塞断言（下游投递延迟不影响水位判定路径时延）。
**纯功能行数**：280（投递层 ~100 + 用例 ~100 + 节流论证 ~80）
**依赖与嫁接源**：B15 F3489 保真日志（通道一）；B17 检测器事件路（通道二——F3356/F3368 的 confirm/suspect 字段直传先例）；F3487 RateTable（节流）；F3581（越线源头）。
**风险与回退**：告警风暴（多池同时越线——告警×池数）——回退：池维度节流（RateTable 键含 pool_id——每池独立配额——但总配额仍有上限（全局 RateTable 容量——超限即静默丢弃+丢弃计数——丢弃不静默：丢弃本身记入账——观测的观测））；下游失效（日志 ring 满——WARN 投递失败）——回退：失败计数+CRITICAL 级失效升级（WARN 丢了记数、CRITICAL 丢了**升级**为检测器事件强制入账——CRITICAL 的必达优先级高于日志 ring 的容量语义——B15 的 TRUNC 纪律对 CRITICAL 让位（判例留痕：这不是破坏 B15 封顶——是 CRITICAL 事件在 B15 侧以 TRUNC 换入——封顶纪律内的优先级协商））；误告警（水位账错误→假告警）——回退：F3596 自检先行（自检不过的账不发告警——告警的可信度以账的健康为前提——健康检查是告警的先决门）。

## F3585 OOM 演练框架总设计（限额注入/压力曲线/杀手/恢复）

**定位**：OOM 全链演练的状态机：限压（注入内存限额）→压力（F3586 曲线驱动）→杀手触发（F3587 评分选择）→恢复（F3588 验证）→对账（全链账平衡）——把"内存耗尽"从生产事故变成**排练过的剧本**。

**判据**：
- J1：演练四段状态机（五态+合法转移表——判据行内嵌）；M-343 演练全链（限额 50%→压力渐增→杀手触发→恢复→对账全绿）。
- J2：状态机封闭断言（非法转移拒绝+转移有账——每步转移留痕）。
**纯功能行数**：340（状态机 ~120 + 全链用例 ~120 + 对账清单 ~100）
**依赖与嫁接源**：F3586 曲线（压力段驱动）；F3587 杀手（触发段执行者）；F3588 恢复验证（恢复段判官）；F3594 隔离池（全链的内存真源）；F3593 seed 确定性（全链可复现的前提）；F3595 报告（全链的产出）。

## F3586 压力曲线生成器（渐增/阶跃/尖峰三型）

## F3587 OOM 杀手选择器测试（评分公平性/最小受害者）

**定位**：OOM 杀手选择器的测试面：评分函数（内存占用×优先级权重）的公平性验证+最小受害者原则+关键任务保护——"杀谁"这个决定的正确性证明。

- J2：决定论断言（同候选集同状态→同 victim——评分无随机项）。
**纯功能行数**：320（契约表 ~100 + 用例 ~120 + 公平性论证 ~100）
**依赖与嫁接源**：A3 杀手评分器（被测对象）；F3585 触发段（调用时机）；F3574 判据库方法论（正例缰绳同律）；F3450 预算（rss 数据源的对账口径）。
**风险与回退**：评分绑架（大内存任务永远先死——大任务被系统性歧视）——回退：这正是公式的设计（最小受害者=释放最多内存的牺牲最小化——"杀大的"在内存危机里是公平的——判据行给"公平"的定义：受害者对系统的**累积贡献损失**最小化——大任务死了重跑代价高——所以公式里 priority_weight 是重跑代价的代理——公式=损失最小化不是随机怜悯）；权重表失当（weight 值拍脑袋）——回退：权重表带依据注释（每级 weight 的业务理由——如 idle=0.1（丢了无所谓）/batch=0.5（可重跑）/interactive=2.0（人等着）/critical=∞（保护清单——∞ 的实现=白名单不在评分集内——两机制等价择一实现））；评分时的账竞态（评分期间 rss 变了）——回退：评分用快照（评分器的输入是账快照——评分期间变化不进入本次决定——快照语义+下次演练再评——实时性让位于一致性）。

**语义边界**：对账是**单向只读**（预算线是真源（F3450 冻结）、峰值是观测——对账不改两边——发现偏差出报告不调参——调预算走 A1/F3450 的修订流程——判例：对账是镜子不是旋钮）；±20% 带的**统计语义**（F3547 同构：预算是设计估计、实测有波动——带内=估计有效；INSUF（insufficient data 或 out of band 双义——判据行消歧：本条 INSUF 专指 out-of-band，样本不足单列 LOWDATA）；对账**周期**（演练对账时+定期低频（每 1000 次 alloc 拍）——不是每个分配都对账（对账是批处理不是热路径）。
**判据**：
- J1：对账契约（峰值 vs 预算线/±20% 带/INSUF 标记——F3547 同构声明）；M-350 预算对账（构造峰值恰在带内→绿/带外→INSUF+报告）。
- J2：只读断言（对账前后预算线与峰值账逐位不变）。
**纯功能行数**：300（对账器 ~100 + 用例 ~100 + 带语义 ~100）
**依赖与嫁接源**：F3450 预算（真源）；F3583 峰值账（观测端）；F3547 ±20% 带先例（统计语义同构）；F3598 RunDigest（对账结果入摘要）。
**风险与回退**：带值一刀切（不同池波动特性不同——统一 20% 对稳态池太松/对抖动池太紧）——回退：带值 per-pool（默认 20%+池级覆盖（F3577 默认表同风格——默认统一例外登记）；峰值 lucky-shot（单次尖峰把峰值顶出带——不代表常态）——回退：峰值**分位**对账（除绝对峰值外取 P99 水位对账——绝对峰值+P99 双指标——尖峰与常态分开评——判据行：一个数字回答一个问题）；预算线过时（预算定于设计期、现实已演化）——回退：INSUF 持续 N 期→升级告警（带外不是一次性的丢人、连续带外=预算与现实脱节——升级为 ERROR 让人来看——对账的升级链）。
**正文**：对账器（判据行原文）：`fn reconcile(pool) -> Verdict { let peak = peakbook(pool).peak; let budget = F3450.budget(pool); if peak > budget * 1.20 { INSUF(peak, budget) } else if samples < MIN { LOWDATA } else { OK } }`——三态判定；P99 伴随：`p99 = percentile(samples, 99)`——verdict 含双指标 {peak_verdict, p99_verdict}。M-350 剧本：构造池预算 10MB、注入峰值序列使绝对峰值 11.5MB（带外）但 P99 8MB（带内）→断言 verdict={INSUF, OK}——双指标分叉的实例（绝对峰值超了但常态健康——报告会把"那次尖峰"单独指出（时间戳+来源标注 E/P——F3583 的考古标注在此变现）；反向：峰值 9MB 带内但 P99 9.5MB 且样本 200——{OK, OK} 绿。带语义的深层论证（判据行展开）：±20% 不是宽容是**假设检验**——预算线的价值在于它是承诺（各池说好各用多少）——实测出带=承诺与现实不符——要么预算错了要么用法错了——两者都要人知道——INSUF 的措辞故意不判断谁错（对账器不知道谁错——它只报告不符——归因是人的工作——工具的诚实=报告事实不替人下结论——F3547 的统计账哲学在此域复用）。LOWDATA 语义：MIN=100 样本（F3547 最小样本门槛同值——同构到底——连常量都同源——判据行声明两个 ±20% 是**同一个统计哲学**在两个域的实例：剖析对账与内存对账——方法论复用的自觉）。J2 只读：对账前后 F3450 表 hash 与峰值账 hash 不变——镜子不留指纹。对账结果的去向：写入 RunDigest 摘要字段（F3598 的四字段之一）+演练报告（F3595）——INSUF 永不静默（判据行：静默的对账=没对账——结果必须有处可查）。M-350 复测：双指标分叉+带内外+LOWDATA+只读 hash+去向完整。

## F3593 OOM 演练确定性（seed/序列冻结）

**定位**：演练全链的确定性保证：seed→曲线指令账→杀手评分→恢复验证→对账结论——同 seed 双跑逐段对齐——演练成为**可复现实验**（复现配方原则在 OOM 域的落实）。
**语义边界**：确定性的**覆盖范围声明**（判据行内嵌：曲线生成（PRNG 消费点一）/杀手评分（无随机——F3587 J2）/水位采样时点（假时钟拍驱动）/对账结论（纯函数）——四段全确定；**不确定的显式排除**（并发调度的交错不进入结论——演练的任务编排固定单线程序（多任务在账上模拟并发、执行上串行——"账上并发、时上串行"是桩测试的经典纪律——交错不进结论所以不需要复现交错）；seed 的**全域唯一消费**（全链只 F3538 PRNG 一个随机源、曲线生成是其唯一消费者——多随机源=复现地狱——单源纪律）；序列冻结（同 seed 生成的指令账逐字节恒定——账可存档可 diff）。
**判据**：
- J1：确定性契约（seed→全链结论唯一+单随机源+账上并发时上串行）；M-351 复现验证（同 seed 双跑全链逐段对齐——曲线账 hash/评分序/对账结论三对齐）。
- J2：seed 敏感性抽样（不同 seed→不同曲线账（种子不是摆设——变化性验证——确定性的另一面是"参数真的起作用"））。
**纯功能行数**：300（确定性机制 ~100 + 复现用例 ~100 + 单源审计 ~100）
**依赖与嫁接源**：B17 F3538 PRNG（唯一随机源）；F3571/F3526 确定性先例（两级复现语义的家族纪律）；F3586 曲线（PRNG 消费点）；F3587 评分（无随机性是确定性的组成）。
**风险与回退**：隐性随机源（时间戳进入结论——ts 漂移破坏复现）——回退：假时钟（演练全程虚拟拍——ts 是拍号不是墙钟——B17 时钟 trait 的 fake 实现在此全额兑现——判据行：假时钟是确定性之母）；对账结论含环境因子（池初始状态不同→同 seed 不同果）——回退：演练起点标准化（每跑前隔离池重置+账清零——初始态是契约一部分——seed 只控制曲线不控制起点——起点写进用例三元组）；PRNG 接口漂移（F3538 实现变化→同 seed 不同流）——回退：PRNG 算法冻结（xorshift64 的流对 seed 恒定——算法变更=破坏所有历史复现——F3538 的冻结条款在此域的利害重申）。
**正文**：确定性链条（判据行原文）：`seed --(F3538 xorshift64)--> 曲线指令账 --(执行@假时钟)--> 账面演化 --(评分@快照)--> victim 序 --(恢复+对账@纯函数)--> 结论`——链上每环纯或冻结；存档物：指令账（可 diff）/victim 序/对账 verdict——三件套是"演练指纹"——双跑对齐=指纹逐项相等。M-351 剧本：seed=0xCAFED00D 跑全链→存指纹 F1；重置隔离池→同 seed 再跑→指纹 F2；断言 F1==F2 逐项（账 hash 相等、victim 序相等、verdict 相等）——**三重相等**而非"结论差不多"（判据行：确定性是逐字节的是"近似可复现"——近似=没锁住某个隐性随机源——M-351 的强断言逼出隐性源）；再加 J2：seed'=0xCAFED00E（差 1）→曲线账 hash 必不同（雪崩效应——xorshift 的流敏感性——种子变而流不变=PRNG 坏了——J2 顺带体检随机源）。"账上并发、时上串行"的展开（判据行论证）：真实 OOM 是并发事件（多任务同时抢内存）——演练若真并发执行，交错序即成隐性随机源（复现死于调度）——演练的解法：任务的分配/释放请求按**逻辑时间戳**排队、执行器串行消费——账面效果与并发等价（每笔 alloc/free 的时序关系保持）、执行面无交错（复现只锁逻辑序不锁物理交错——物理交错本就不该进结论——它是噪声不是信息——判据行给这个取舍的哲学：复现复现的是**因果**、不是**竞争**——竞争的统计归 F3571 的 ±3σ 并发语义、因果的精确归本条的单线程冻结——两级复现语义各司其职）。M-351 复测：双跑三重指纹+差 1 seed 雪崩+假时钟全程+起点重置+单源审计（grep 演练路径无第二 PRNG 实例）。

## F3594 演练安全红线（演练期禁真分配器破坏——隔离池）

**定位**：演练的最高安全条款：全部演练活动（压力分配/killer 场景/DMA 桩流量）只在**隔离池**内进行——真池（系统真实分配的内存）在演练全程零感知——"消防演习不能真放火"。
**语义边界**：隔离池的**资源真实独立**（预分配的独立页域——不与真池共享页/位图/账——隔离是物理的不是逻辑的（逻辑隔离（同一个池加标记）是筛子——判据行给隔离的物理性论证：真池零感知的可验证定义=真池的页位图逐位不变——物理隔离才可能过这个断言）；真池零感知的**断言化**（演练全程后台线程逐拍 hash 真池位图与账——hash 变=红线破=演练即停即 FAIL——红线不是承诺是**实时监测的断言**）；演练者的权限边界（演练编排代码只见隔离池句柄——真池句柄不在其类型可达范围（类型系统隔离——API 层面拿不到——F3523 指针陷阱同律：拿不到的东西无法误用）；配额（隔离池容量上限=真池 25%——演练自身不能成为内存大户——上限常量+超限拒绝）。
**判据**：
- J1：红线契约（隔离池物理独立+真池位图 hash 全程恒定+演练 API 类型级不可达真池）；M-352 隔离断言（演练全程真池 hash 零变化）。
- J2：越界负例（构造试图触真池的演练指令→执行期拒绝+审计留痕）。
**纯功能行数**：300（隔离机制 ~110 + 监测断言 ~100 + 负例 ~90）
**依赖与嫁接源**：A1 池管理（隔离池的分配——A1 提供池类型、演练只消费）；F3585 全链（红线的管辖对象）；F3564 红区页（隔离池边界的 MMU 级加固——可选——隔离池前后无权页——越界即页错——硬件兜底）；F3597 接入表（隔离池登记）。
**风险与回退**：隐式共享（某子系统把隔离池页混入常规分配路径）——回退：池句柄类型区分（IsolatedPool 与 Pool 不同类型——混用编译期拒绝——类型即防线）；hash 监测的漏拍（监测线程自身被饿——窗口内越界未察）——回退：监测在演练状态机同一拍内联执行（不是后台线程——每拍状态机推进前先 hash——同步监测无窗口——判据行：异步监测有缝隙、内联监测无缝隙——性能可接受（hash 64K 位图=μs 级））；演练依赖真池数据（某用例需要"真池也满"的联合场景）——回退：这类场景**不允许**（联合场景=真池参与=红线破——真池满的场景用"模拟真池压力"替代（真池只读观测+隔离池内重演）——需求的边界诚实：有些场景演练不了、写进能力边界声明而不是妥协红线）。
**正文**：红线的三层实现（判据行原文）：层一**类型隔离**：`struct IsoPool(Pool)`——新类型包装——演练 API 签名只收 `&IsoPool`——`Pool`（真池）无法传入（编译错误——"错误在编译期发生是最便宜的"）；层二**内联监测**：状态机每拍：`assert_eq!(hash(real_pool_bitmap), baseline_hash, "红线破")`——hash 基线在演练 LimitSet 态冻结；层三**MMU 兜底**（可选启用）：隔离池域前后各一无权页（F3564 红区页复用）——即使前两层全漏（代码 bug），越界访问页错即崩——崩在演练里好过坏在真池里——三层纵深：类型挡住 99%、监测挡住余下 99%、MMU 挡住最后的 bug——判据行给纵深防御的算术：每层独立失效概率乘积=残余风险趋零。M-352 剧本：跑 F3591 的 L1 用例全程（最长链）→断言每拍 hash==基线（逐拍记录 hash 序列——终验序列全等）→演练报告附"真池零感知证明"段（hash 序列摘要——证明是可存档的证据不是口头承诺）。J2 越界负例：恶意指令（测试代码模拟）`pressure.alloc_on(real_pool)`——类型层即编译失败（第一个负例在 CI 编译期验证——编译失败也是验收断言——判据行：负例有两种跑法——编译期拒绝的跑法是"构建必须失败"）；绕过类型（unsafe 转换——测试代码里 unsafe 触真池）→运行期层二拦截（hash 变→演练 Abort+审计记录越界点栈——审计记录=越界未遂的存档）。25% 配额：隔离池容量在 LimitSet 时校验 ≤真池 25%——超限 LimitSet 拒绝（演练参数的合法性门——配额防止"演练池配太大、真系统饿死"的间接伤害——判据行：红线保护的是"不被演练破坏"、配额保护的是"不被演练挤饿"——两种伤害都要防）。M-352 复测：三层纵深逐层验证+hash 序列存档+编译期负例+运行期负例+配额门。
