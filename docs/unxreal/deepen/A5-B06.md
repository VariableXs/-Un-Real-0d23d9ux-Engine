## F3301 RCU 压测编排（读多写少 8 核场景）

**定位**：RCU 一（B05）交付后的系统性压测：8 核读 + 写者发布换指针，验证"读侧零阻塞、GP 健康、回调不积压"三大生产级承诺。
**语义边界**：只做编排与度量（复用 B05 数据面）；不新增 RCU 机制。写者速率、读者数、对象数为可调参数（判据行给默认矩阵）。
**判据**：
- J1：M-060：默认矩阵跑 10 秒：读延迟 P99 ≤ 2×fast path 基线（基线 = 空 RCU 临界区往返）；GP 完成数与发布轮次匹配（每轮发布 ≤ 1 GP 内收敛）；回调积压峰值 ≤ 2×每轮对象数。
- J2：压测报告四表（延迟分布/GP 时长/回调积压/违例账目）交付。
**纯功能行数**：420（参数矩阵与编排 ~140 + 四表采集 ~140 + 判据断言 ~90 + 判据行 ~50）
**依赖与嫁接源**：B05 全套；F3293 GP 时长分布；F3204 TSC。
**风险与回退**：真 tick 下 10 秒压测受 GP 节拍限制轮次不足——回退：fake_tick 加速模式（F3298 体例）与真 tick 模式双跑，判据以加速模式为主、真 tick 模式留真机闸口复测。
**正文**：默认矩阵（判据行）：8 读核 + 1 写核、对象 64B × 每轮 16 个、写者每 1,000 次读一发、总时长 10 秒（加速模式下折算 GP 轮次 ≥ 100）。三大承诺的度量设计：①读侧零阻塞——读延迟分布与空临界区基线对齐（RCU 读只有 nest 增减，无等待点，理论 P99 ≈ 基线；若 P99 超基线 2 倍说明有隐藏共享点，用例失败即发现问题）；②GP 健康——F3293 的 GP 时长分布 P99 ≤ 5×tick 间隔（迟滞 CPU 由 F3296 离线契约兜底）；③回调不积压——F3288 批量执行的预算（64/轮）× GP 频率 ≥ 发布速率，积压峰值断言验证预算足够。数据结构：四表采集器（直方图桶 + 计数器），复用 F3212/F3293 体例。现有内核接入：无新增（纯消费 B05 面）。Windows 对比：Windows 读侧压测无 RCU 对应物，对照思路是其 HLK 的并发压力套件（负载矩阵 + 通过判据），我们把"负载矩阵"判据化——1 万+ 断言运动中，压测编排是断言的放大器（一次压测 = 数百万次隐式断言执行）。M-060 复测：矩阵三档（读 4/8 核 × 写频低/高）各跑一轮，四表逐档核对；写频高档预期 GP 更密但回调积压仍受控——这是预算断言的尖锐化样本。

## F3302 RCU 与锁混合场景验证

**定位**：混合同步原语的现实形态验证：RCU 读 + mutex 保护写者间互斥 + spinlock 保护细粒度统计——三原语协同的死锁零检出与数据一致。
**语义边界**：只做混合场景用例；三原语本体不变。场景构造刻意含"锁顺序变化"（写者拿锁序随机），检验 B08 未来环检测的数据供给形态（此为死锁检测器的前置演练，判据行声明）。
**判据**：
- J1：M-061：8 核 30 秒（加速模式）混合负载：违例账目零新增、数据校验和一致（对象内容哈希与写序对账）、边账本平账（F3251 契约在混合场景成立）。
- J2：场景含至少 2 处锁序变化（构造性），报告标注位置。
**纯功能行数**：300（场景构造 ~110 + 三断言 ~110 + 判据行 ~80）
**依赖与嫁接源**：B05 + B03 + B01 全套；F3251 边账本。
**风险与回退**：混合场景 flaky（非确定性）——回退：判据用"不变式成立"而非"特定序列"（死锁零检出/账本平账/校验和一致都是不变式），非确定性下判据稳定。
**正文**：场景设计：共享结构 = 链表（RCU 读遍历）+ 节点插入互斥（mutex，F3252 helper 按序双锁）+ 每核统计（spinlock 保护聚合）。写者 A 流程：mutex 拿插锁 → RCU 发布新节点 → call_rcu 释放旧节点；写者 B 流程：反向锁序拿两把辅助锁（构造性变化点 1）；读者：RCU 遍历 + 偶尔拿统计锁（变化点 2）。三断言意义：违例账目零新增 = 无原语级错误；校验和一致 = 发布序正确（RCU assign/deref 配对的端到端验证，比 M-050 的原语级测试更系统）；边账本平账 = 等待图数据供给在混合负载下诚实（B08 环检测将消费此数据，若平账破坏则检测器必误报——这是"检测器 7×24 零误报"验收的上游保障，判据行写明这条因果链）。现有内核接入：无新增。Windows 对比：Windows 混合原语场景的验证靠 Driver Verifier 全开 + 长稳压力；我们把"混合场景不变式"做成可重复用例——HLK 惯例的内核内化。M-061 复测：两处锁序变化点各单独关闭重跑（变量隔离），确认断言对每个变化点独立敏感。

## F3303 completion 结构与 done/done_all 语义

**定位**：`Completion` 完成量：`done: AtomicU32` + 等待队列；`complete()`（done+1，唤醒一个等待者）与 `complete_all()`（置 MAX，唤醒全部并永久满足）两语义的精确实现。
**语义边界**：只做结构与两 complete 语义；等待在 F3304、超时在 F3305。done 的饱和语义（MAX = u32::MAX 表示"永久完成"）在本条判据行定义。
**判据**：
- J1：M-062：complete × 3 后 3 个 wait 各消费 1；complete_all 后任意多 wait 立即返回（且后续 complete 不再计数增长——饱和粘滞）；M-062 两态断言。
- J2：done 计数溢出防御（complete_all 后 complete 为 no-op），判据行给溢出路径证明。
**纯功能行数**：340（结构 ~100 + complete 两语义 ~130 + 饱和粘滞 ~70 + 判据行 ~40）
**依赖与嫁接源**：F3242 队列体例；F3201 原子底座。
**风险与回退**：complete 与 wait 的计数竞争（唤醒后计数被吞）——回退：wait 的消费判定 = "done > 0 则 fetch_sub 成功"（原子取票），取不到票回队列，取票法天然无丢信号。
**正文**：实现路径：`complete()`：`if done.load != MAX { done.fetch_add(1); 唤醒队首（F3246 协议） }`；`complete_all()`：`done.store(MAX, Release); 唤醒全部`。wait 侧（F3304）：`loop { let d = done.load(Acquire); if d == MAX { return Done } if d > 0 { if done.cas(d, d-1).is_ok() { return Done } continue } sleep_on(...) }`——MAX 粘滞：MAX 是"取不尽的票池"，后续 complete 直接 no-op（J2 溢出防御：MAX+1 会绕回 0 造成灾难，no-op 是唯一正确处理，判据行给证明）。语义分界（验收要点）：complete = 一次性事件（N 次 complete 供 N 个 wait）；complete_all = 状态翻转（完成后永不等待）——驱动场景对应"单个 IO 完成"vs"设备下线通告"。现有内核接入：无（新能力）。Windows 对比：Windows 的 KEVENT（KeSetEvent/KeWaitForSingleObject）是最近亲：KEVENT 的 NotificationEvent ≈ complete_all（状态粘滞），SynchronizationEvent ≈ complete（单次取票）——判据行给完整映射表，Windows 背景的验收者可用 KEVENT 直觉读本条。M-062 复测：取票法的竞态验证 = 8 核 500 轮 complete/wait 交错，计数守恒（complete 总数 = wait 成功总数 + 队列余票）。

## F3304 completion 等待与唤醒边界（醒归 A3 桥）

**定位**：`wait_for_completion` 的睡眠等待实现：经 F3246 协议（SleepPort）入队睡眠，唤醒后取票重验——"醒归 A3"边界在 completion 侧的落地。
**语义边界**：只做等待路径；结构在 F3303。等待者的公平性沿用队列 FIFO（F3249 契约引用不重定义）。
**判据**：
- J1：M-063：桩调度器下 wait→complete 全链路：等待者睡眠（SLEEP 事件）→ complete 唤醒（WAKE 事件）→ 取票成功返回；事件账本验证协议使用无旁路。
- J2：虚假唤醒（SPURIOUS 注入）后重验取票，不丢不重。
**纯功能行数**：320（wait 主体 ~120 + 取票循环 ~90 + 协议衔接 ~70 + 判据行 ~40）
**依赖与嫁接源**：F3246 协议；F3303 取票法；F3303 队列。
**风险与回退**：唤醒先于入队（complete 快于 wait）的丢信号——回退：wait 先查票后睡眠的两步序在协议消费侧保证（睡眠前最后查票），与 F3289 的次序证明同款，判据行引用。
**正文**：实现路径：`wait_for_completion(c) { loop { 取票成功→返回；票空→入队→sleep_on 协议→醒后重验 } }`——醒后重验是取票法的核心：唤醒只是"可能有票"的提示，真相以原子取票为准（SPURIOUS 注入下重验失败则继续睡，M-063 负例）。次序证明（丢信号防御）：入队（队列锁内）→ 查票 → 睡眠：complete 的取票路径（fetch_add done）与唤醒路径（队列锁内摘节点）串行化——若 wait 查票时票已发，直接取走不睡；若未发，complete 的唤醒必在 wait 入队后（队列锁序保证），不丢。与 F3289 的 synchronize 同款模式，判据行交叉引用（A5 内部"无丢信号等待"的标准三步：登记-查验-睡眠）。现有内核接入：无。Windows 对比：KeWaitForSingleObject 的等待块机制与我们的协议消费同构（前批 F3246 已析）；本条补充的对照是 KeWaitForMultipleObjects 的多等不做（v1 单等，多等列 ADR 记录位——8 核规模无需求）。J2 复测：SPURIOUS × 3 注入，最终取票成功且 SLEEP 事件 = 4（初睡 + 3 重睡）。

## F3305 completion 超时语义

**定位**：`wait_for_completion_timeout(c, ticks)`：限时等待，返回剩余 tick（成功）或 0（超时）——F3246 协议 TIMEOUT 态的消费示范。
**语义边界**：只做超时封装；计时的 TSC→tick 换算在本条（判据行给换算与精度声明）；超时后的状态（票未取走）如实保留（不取票不记账干扰后续）。
**判据**：
- J1：M-064：注入"永不 complete" → 返回 0 且耗时 ∈ [T, T+容忍]；注入"半程 complete" → 返回剩余值 > 0。
**纯功能行数**：240（超时封装 ~90 + TSC 换算 ~80 + 用例 ~70）
**依赖与嫁接源**：F3304 主体；F3204 TSC；F3246 TIMEOUT 态。
**风险与回退**：超时精度受 tick 粒度限制——回退：判据行声明精度 = tick 粒度（±1 tick），细粒度需求列 ADR 记录位。
**正文**：实现路径：wait 主体加截止检查：睡眠前算剩余 tick，sleep_on 携带截止（协议 v1 的 TIMEOUT 由桩调度器按截止注入——A3 实装后由其定时器承载，判据行标注此依赖）；醒来分派：WOKEN → 走取票（可能票仍未到 → 继续算剩余再睡）；TIMEOUT → 返回 0。返回语义对齐 Windows：NT 的 KeWaitForSingleObject 返回 STATUS_TIMEOUT 或 STATUS_SUCCESS（无剩余值概念），Linux 的 wait_for_completion_timeout 返回剩余——我们选 Linux 语义（剩余值对调用者有用：级联超时计算），判据行给两系映射。精度声明：TSC 计量、tick 交付——v1 的"超时"本质是 tick 定时（A3 定时器未实装），精度承诺 = 粒度不 = 绝对精度，诚实边界。现有内核接入：无。Windows 对比：如上。M-064 复测：容忍带 = ±1 tick，两态各 100 轮全收敛——超时用例的 flaky 防治（容忍带声明）是 ktest 用例设计的要点，判据行记之。

## F3306 信号量（计数信号量）结构

**定位**：`Semaphore { count: AtomicI32, waitq }` 计数信号量：count 表示可用许可，down 减 up 增，count ≤ 0 时 down 等待。
**语义边界**：只做结构与基本语义；公平交接在 F3307；与 mutex 的边界（信号量不绑定持有者）在判据行声明。
**判据**：
- J1：M-065：count 迁移验证：初始 2 → down × 4（2 成功 2 等待）→ up × 2（等待者各醒一个）→ 全链计数与等待数对账。
- J2：count 的负值语义 = 等待者数的镜像（判据行给不变式：count < 0 ⟹ 队长 == -count）。
**纯功能行数**：300（结构 ~90 + down/up 路径 ~120 + 不变式验证 ~90）
**依赖与嫁接源**：F3242 队列；F3201 原子底座。
**风险与回退**：count 修改与入队的原子性竞争——回退：down 的决策点唯一（fetch_sub 的返回值决定等或不等），判据行给竞态吸收证明。
**正文**：实现路径：`down()：if count.fetch_sub(1, Acquire) <= 0 { 入队睡眠（醒来重验）}`；`up()：let old = count.fetch_add(1, Release); if old < 0 { 唤醒队首 }`。竞态吸收证明（判据行核心）：down 与 up 并发时，fetch_sub/fetch_add 的原子性保证每个许可恰被一个等待者消费——down 者 A（fetch_sub 后 old=-1，等待）与 up 者 B（fetch_add 后 old=-1→0，唤醒 A），A 醒后重验（取票式：确认 count 有余或被交接）——交接设计与 F3242 的队首专属交接位同构（up 直接把许可写给队首节点，其余人继续等），零惊群。负值不变式：fetch_sub 使 count 变负的次数 = 等待者入队数，up 使 count 回升的次数 = 唤醒数——M-065 按此对账。与 mutex 边界：信号量无 owner 概念（up 可以来自任何核，不必是 down 者）——这正是它与 mutex 的本质区别，判据行给"何时用哪个"一句话：需要配对释放 → mutex；许可池语义 → 信号量。现有内核接入：无。Windows 对比：Windows KSEMAPHORE（KeReleaseSemaphore/KeWaitForSingleObject 配合）语义全同，其 Limit 参数（上限拒绝）我们 v1 不做（无界信号量，判据行声明差异）。M-065 复测：不变式在每步操作后采样验证（8 核并发 500 轮不变式零违例）。

## F3307 信号量 down/up 与公平排队

**定位**：信号量的 FIFO 公平交接：up 唤醒严格队首、队首专属许可交接、零逆序——F3249 公平契约在信号量侧的复用落地。
**语义边界**：只做公平性；结构在 F3306。
**判据**：
- J1：M-066：三等待者场景交接序 = 入队序，1,000 轮压力零逆序（与 M-009 同法不同族）。
- J2：交接位机制复用验证（信号量节点与 mutex 节点共享 WaiterNode 类型——单类型多族的架构证明）。
**纯功能行数**：320（交接实现 ~110 + 逆序检测复用 ~110 + 架构验证 ~100）
**依赖与嫁接源**：F3249 契约与检测器；F3306 交接设计。
**风险与回退**：无（复用已验证机制——本条的价值恰在证明基建复用性，判据行声明）。
**正文**：实现路径：up 的唤醒 = 取队首节点 → 许可写入其交接位 → wake_protocol；等待者醒后从交接位取许可（不走 count 竞争）——count 在交接后同步 +1（保持不变式）。逆序检测器：F3249 的 seq 比对原样挂信号量交接点。架构验证（J2 的意义）：WaiterNode 从 B03 mutex 起设计为族中立类型（字段不绑 mutex 语义），B04 rwlock（F3262 让位路径）、B06 completion/信号量三族复用同一节点与队列——"一次基建、四族受益"是 A5 框架化的实证，判据行给四族复用清单。现有内核接入：无。Windows 对比：KSEMAPHORE 的等待序由调度器等待队列保证（近似 FIFO）；我们的零逆序硬判据同 M-009 哲学。M-066 复测：压力轮中注入 SPURIOUS（等待者假醒重睡）后队序不变——公平性对假醒的免疫力是判据尖锐化。

## F3308 workqueue 接管桥：现有延迟工作机制盘点

**定位**：workqueue 批的起点：盘点现有内核的"延迟/异步工作"形态（tick 内批处理、延迟释放路径、自旋中的推迟操作），三分类（应迁 workqueue / 应留原地 / 待议）并给接管建议。
**语义边界**：只盘点与建议；接管动作在各域决议后执行（框架归 A5，挂牌归各域）。workqueue 本体从 F3309 开始。
**判据**：
- J1：盘点清单交付：≥ 3 类调用点（含 tick 路径的延迟批处理、RCU 回调执行的宿主候选），每点含现状/风险级/建议。
- J2：清单与 B05 F3299 桥的候选点交叉核对（不重复登记，冲突处标注）。
**纯功能行数**：300（盘点扫描 ~130 + 三分类与建议 ~100 + 交叉核对 ~70）
**依赖与嫁接源**：F3259/F3279/F3299 三步法体例；`cpu/clock.rs`、`panicseq.rs`、B05 回调执行点。
**风险与回退**：盘点遗漏隐式延迟点（间接调用链深）——回退：两轮扫描（首轮 grep 关键词，二轮人工核读调用链 ≥ 2 层的命中点），清单声明覆盖率方法。

## F3309 每 CPU 工作队列骨架（软中断上下文边界）

**风险与回退**：执行循环在 tick 内过长拖慢心跳——回退：执行预算（每 tick 最多 N 个工作项，N=8 默认，F3311 细化），超预算顺延。

## F3310 工作项提交与去重（PENDING 位）

**定位**：工作项提交语义：同项重复提交合并（PENDING 位原子置位判重），执行后清位——防"同一工作项排队两份"的经典错误。
**语义边界**：只做提交与去重；去重的粒度 = 工作项对象级（同一 WorkItem 实例），不同实例不去重（判据行声明）。
**判据**：
- J1：M-068：同项并发提交 100 次 → 队列中恰 1 份；执行后 PENDING 清位可再提交。
- J2：PENDING 置位与挂队原子序（先置位后挂队；挂队失败回滚位），判据行给两步序证明。
**纯功能行数**：300（WorkItem 结构 ~90 + 提交去重 ~120 + 回滚与用例 ~90）
**依赖与嫁接源**：F3309 队列；F3201 CAS。
**风险与回退**：执行后清位与新提交的竞争（清位瞬间提交丢失）——回退：清位顺序 = 先摘队后清位，提交者看到位清后再挂——两步交错的最坏结果 = 多一次提交（幂等工作项可容忍）或零丢失，判据行给交错矩阵证明无丢失情形。
**正文**：实现路径：`WorkItem { next, func, pending: AtomicBool, ctx }`——`submit(item)：if pending.cas(false,true) { 挂队 } else { 已在队，合并返回 }`；执行循环取项执行前保持 pending=true，执行完 `pending.store(false)`。交错矩阵证明（判据行）：执行者（摘队→执行→清位）与提交者（置位→挂队）在四步两线上的 6 种交错逐一分析：唯一风险交错 = 提交者置位后、执行者清位前提交者挂队——此时执行者已摘旧实例，新挂队实例将被下轮执行（多执行一次，幂等容忍）；丢失情形不存在（挂队 CAS 无条件成功）。幂等要求由此而生：工作项契约声明"可能偶尔重复执行"（比 Windows 的 exactly-once 弱，判据行声明该取舍的理由：无锁实现的简洁性换幂等要求，重复危害 < 丢失危害）。现有内核接入：无。Windows 对比：IoQueueWorkItem 的去重语义官方文档 = "同一 work item 不会排队两份"——与我们 PENDING 位语义精确对齐，判据行引用作为契约佐证。M-068 复测：交错矩阵的每种交错用桩构造（注入点在四步间），断言"零丢失"全交错成立。

## F3311 工作项执行与并发度控制

## F3312 队列排空（drain）与销毁语义

**定位**：`drain(q)` 等待存量清零与 `destroy(q)` 拒新提交——队列生命周期的收尾语义，防"销毁后仍有项执行"的 use-after-free。

- J1：M-070：drain 期间新提交被拒（返回错误）且存量执行完；drain 返回后队列空证（深度 = 0 且执行计数 = 提交计数）。
- J2：destroy 后 submit 返回 DEAD 错误且永不挂队（状态粘滞）。
**纯功能行数**：260（drain 语义 ~100 + destroy 状态机 ~90 + 用例 ~70）

**风险与回退**：drain 与执行的竞争（drain 判空时项刚提交）——回退：drain 先置 DRAINING 位（拒新提交）再等清零——位先行保证判空后的存量封闭，判据行给证明。
**正文**：实现路径：`drain() { q.state.cas(Active, Draining)?; loop { if 深度==0 && 执行空闲 { return } sleep_on(完成信号) } }`；`destroy() { drain()?; state.store(Dead); }`。位先行证明：Draining 置位后无新提交 → 存量单调递减 → 判空后永不再增 → 空证成立（M-070 的执行计数对账即空证的运行时表达）。执行空闲判定：队列空且当前无执行中项（per-CPU busy 位）——两项与判空缺一不可（判据行给反例：只判空时执行中项会被漏等）。destroy 的 DEAD 粘滞：状态机 Active→Draining→Dead 单向（判据行给迁移图），Dead 拒一切。现有内核接入：无。Windows 对比：IoQueueWorkItem 生态的队列拆除惯例（KeFlushQueuedDpcs 类等待 + 不再提交约定）无标准库化；我们把"位先行 + 双条件空证"库化。M-070 复测：并发 drain × 3（多等待者）全收敛且无死等（完成信号经 F3246 协议）。
