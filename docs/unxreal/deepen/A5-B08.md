## F3341 死锁检测器总设计（等待图模型与不做的事）

**定位**：死锁检测器的语义宪法：等待图模型（节点=锁实例、边=任务级等待关系）、检测原理（环=死锁）、v1 不做清单——B08/B09/B10 三批的总纲。
**语义边界**：本条是模型定义；结构在 F3342、算法在 F3345。v1 不做：①检出后自动恢复（杀任务/回滚——依赖 A3 任务模型与破坏性动作，红线禁止）；②图外对象（非锁资源如信号量以外的自定义资源——v1 图覆盖四族锁 + completion/信号量）；③优先级反转纠正（F3253 边界延续）；④概率化/抽样图（v1 全量边）。
**判据**：
- J1：M-100 模型验证：教科书 AB-BA 两锁死锁在模型下 = 2 节点 2 边 1 环，检出路径与模型推演一致。
- J2：设计文档四节齐：图模型/检测原理/不做清单/与 B07 漏斗关系（F3353 引用）。
**纯功能行数**：360（图模型定义 ~130 + 检测原理 ~100 + 不做清单 ~90 + 判据行 ~40）
**依赖与嫁接源**：B07 地基（F3251 边、F3325 栈、F3322 class）；B03 边契约。
**风险与回退**：模型与实现漂移（实现做了模型没说的）——回退：模型文档是判据源头，实现条目逐条引用本条（本批所有条目判据行回指本条）。
**正文**：图模型精确定义（判据行原文）：节点 = 锁实例（class + 指针身份）；边 = 「等待者 → 持有者」方向（等待者想要、持有者占着）；边权 = 挂边时刻（TSC，B09 时间窗用）。死锁判定 = 边集存在环 = 一组锁互相形成等待闭合（A 等 B、B 等 A 的 2 环或 A→B→C→A 的 3+ 环）——环中每条边的两端任务都无法推进，即死锁。方向选择（谁→谁）的论证：沿边走 = 沿"阻塞链"走（我等谁、他等谁），DFS 沿边即沿阻塞链溯源，环 = 链闭合——方向与直觉（持有→等待）相反但溯源语义自然，判据行声明方向约定防实现歧义。任务维度：v1 等待者用 CPU+任务上下文标识（A3 桩级），图节点仍以锁为中心（边挂任务对）。不做清单逐条理由：①恢复动作违反"告警不破坏"红线且依赖 A3 深化；②自定义资源图的接入面未冻结；③PI 纠正是 F3253 决定；④全量边在 8 核规模预算内（F3352 验证）不必抽样。Windows 对比：Driver Verifier 的死锁检测模型与本模型同构（资源+等待者+环）；我们补了确认窗口（F3354）与告警不破坏（F3349）——Verifier 检出即蓝屏（BugCheck），我们持续运行，这是 7×24 验收的要求。M-100 复测：AB-BA 构造（双核互持互等）→ 图快照核对（2 节点 2 边）→ 检出报告路径 = [A→B→A]。

## F3342 等待图数据结构（节点=锁，边=持有→等待）

**定位**：图本体：邻接表结构（节点 = 锁实例标识，出边 = 该锁的等待者列表），节点/边从静态池分配（F3352 预算）。
**语义边界**：只做结构；边登记在 F3343、扫描在 F3345。节点的身份键 = (class, 实例指针)——同 class 双实例是不同节点。
**判据**：
- J1：M-101：建 100 节点 200 边图 → 查询（出边数/边存在性）→ 删边 → 计数对账全对。
- J2：节点/边操作零堆分配（池化），判据行给池容量（节点 256 / 边 512）与依据。
**纯功能行数**：380（节点结构 ~110 + 邻接表 ~130 + 池挂接 ~100 + 判据行 ~40）
**依赖与嫁接源**：F3352 池；F3322 class（节点身份）；F3351 分片。
**风险与回退**：实例指针作为键的稳定性（锁实例地址固定——静态锁成立，栈上临时锁不成立）——回退：v1 契约"图只接受静态/长生命周期锁实例"（new_named 注册过的），栈上锁阻塞等待 = 罕见错误（自旋栈锁才可能），不入图——判据行声明该限制。
**正文**：实现路径：`WgNode { class: LockClass, inst: *const c_void, edges: EdgeList, flags }`、`WgEdge { waiter: WaiterId, tsc: u64, next }`——邻接表 = 节点的出边单链（等待者链）。节点池 256 / 边池 512 的依据（判据行）：8 核 × 常驻锁 ~30 实例 + 用例临时锁 ~20 = 50 常态节点，256 = 5 倍余量；边 = 等待者数（常态 < 8），512 = 极端压力余量——池耗尽的行为归 F3352（降级不崩）。EdgeList 头插法 O(1) 挂边；查边 = 遍历出边链 O(出度)（等待者少，可接受）。WaiterId = (cpu, 任务序号) 的 u32 编码（判据行给编码表）。现有内核接入：无（新结构，`sync/dlgraph.rs`）。Windows 对比：Verifier 的资源图内部结构不公开；Linux lockdep 的图是 class 级（我们实例级更精细——同类两实例的环 lockdep 看不见，我们看得见，判据行声明这是相对 lockdep 的能力增量，代价是节点更多——池预算即为此付）。M-101 复测：建查删三段 + 零分配断言（堆计数不变）。

## F3343 边登记 API（acquire 阻塞时挂边）

**定位**：挂边路径：阻塞等待（四族慢路径入队成功后）调用 `wait_edge_register`（F3251 接口）——图边与等待事实的绑定。
**语义边界**：只做挂边；接口签名属 F3251（B03 冻结），本条是图侧实现与四族调用点的接通。try 失败不挂边（F3245 契约）。
**判据**：
- J1：M-102：四族各构造一次阻塞等待 → 图快照各含 1 边（方向 waiter→holder、tsc 有值）；try 路径零边。
**纯功能行数**：340（图侧登记实现 ~140 + 四族接通 ~120 + 验证 ~80）
**依赖与嫁接源**：F3251 token 接口；F3342 图；F3324 打点（挂边时机在其钩子内）。
**风险与回退**：挂边与持有变化竞态（挂边瞬间 holder 已释放）——回退：挂边内容是"挂边时刻的快照"（此刻的 holder），释放路径的摘边（F3344）会清掉它——瞬态边由确认窗口（F3354）过滤，模型诚实承认瞬态存在而非消灭它。
**正文**：实现路径：F3324 的 on_acquire 钩子中 wait=true 分支 → F3251 的 register 内部 → 图实现：查/建 holder 节点 → 头插边 (waiter, tsc) → 返回 EdgeToken。四族接通：spin（无慢路径——spin 全自旋不睡眠，判据行明确：spin 不挂边，其"等待"是图外计数 F3355）、mutex（F3242 入队后）、rwlock（F3263 写等待/F3265 读让位后）、rcu（无阻塞语义不挂）。即：实际挂边族 = mutex/rwlock/completion/信号量（B06）四族——模型总设计（F3341）的"图覆盖四族锁 + completion/信号量"在此精确化。挂边开销：节点查建 ~40 拍 + 插边 ~20 拍 = 60 拍（入 F3331 预算账）。现有内核接入：无。Windows 对比：Verifier 挂钩获取路径记录等待——同点位；我们的四族覆盖声明与 Linux lockdep 的"所有 mutex 类原语"覆盖声明对齐。M-102 复测：四族各一等待（桩阻塞）+ try 对照（零边）+ 方向断言（waiter→holder 不反）。

## F3345 环检测算法（DFS 三色标记）

**定位**：环检测本体：三色 DFS（白=未访/灰=在栈/黑=完成），灰遇灰 = 环——从任一节点出发的闭环发现算法。
**语义边界**：只做算法；触发在 F3346、报告在 F3347。算法的内存安全（递归深度）→ 迭代化实现（显式栈——内核禁深递归，判据行声明）。
**判据**：
- J1：M-104：构造 2 环/3 环/5 环各检出（路径正确）；无环 DAG 图 1,000 次扫描零检出（误报为零的算法级证明）。
- J2：迭代化（无递归）——静态检查（无 fn 递归调用）+ 栈深预算 ≤ 节点数。
**纯功能行数**：400（三色状态 ~110 + 迭代 DFS ~150 + 环路径回溯 ~100 + 判据行 ~40）
**依赖与嫁接源**：F3342 图；F3351 分片快照。
**风险与回退**：扫描期间图在变（边增删）——回退：扫描基于 F3351 的快照（合并后冻结视图），扫描中图变化不影响本轮（下轮看到）——快照扫描的一致性基础，判据行声明。
**正文**：实现路径：`fn find_ring(snap: &GraphSnap) -> Option<RingPath>`：全节点遍历，白起点入栈标灰，沿出边走：遇白→压栈标灰；遇黑→剪枝（已完成无环）；遇灰→环！（从当前节点回溯到该灰节点的路径即环）。环路径回溯：显式栈中该灰节点的位置到栈顶的序列 = 环路径（判据行给栈位置回溯的索引算法：记录每节点的入栈序，环 = 序列 [灰节点序..栈顶]）。三色的理由（vs 简单 visited）：白/灰/黑区分"在当前路径上"（灰）与"已证实无环"（黑）——黑剪枝让无环子图只扫一遍，复杂度 O(V+E) 线性。1,000 次 DAG 零检出是算法正确性的统计证明（M-104），配合构造环的定向检出。现有内核接入：无。Windows 对比：Verifier 的环检测同样 DFS 系；Linux lockdep 的图搜索也是 DFS——算法是共识，差异在我们实例级 + 迭代化 + 快照化。M-104 复测：三环构造（2/3/5 节点）路径逐边核对 + DAG 1,000 次零检出（负例统计）——这两个数字（检出 100% / 误报 0%）就是 F3359 的 J2 判据来源。

## F3346 环检测触发时机与频率控制

**定位**：检测的触发与节流：新边挂载即触发候选扫描 + 窗口频率上限（每窗口最多 N 次全图扫描，默认 N=4）——及时性与开销的平衡。
**语义边界**：只做触发与节流；窗口长度与确认窗口（F3354）的关系：频率窗口是"每窗口最多扫 4 次"，确认窗口是"环需跨 2 次扫描存在"——两个窗口独立参数，判据行给出默认值组合与理由。
**判据**：
- J1：M-105：高频挂边压力（1,000 边/秒注入）下实际扫描次数 ≤ 频率上限 × 窗口数；低频场景每新边必扫（及时性）。
**纯功能行数**：320（触发点 ~100 + 频率控制 ~120 + 用例 ~100）
**依赖与嫁接源**：F3345 算法；F3204 TSC（窗口计时）。
**风险与回退**：节流导致漏检延迟（环在节流期未扫到）——回退：确认窗口（F3354）本身要求环跨多次扫描，节流延迟被窗口语义吸收；且死锁是持续状态（不会消失），延迟扫描 = 延迟告警而非漏告——判据行论证节流的安全性。
**正文**：实现路径：挂边后置 `scan_pending = true`；扫描驱动（tick 挂接，同 F3286 协作模式）：`if scan_pending && 本窗口扫描数 < 4 { 扫描; scan_pending=false }`。窗口 = 100ms（TSC 判界）。默认参数组合论证（判据行）：N=4/100ms = 最高 40 扫/秒——每次扫描 O(V+E) ≈ 300 节点 500 边量级 ≈ 万拍级，40 次/秒 = 40 万拍/秒 ≈ CPU 占比 < 0.03%（3GHz 假设）——预算成立；确认窗口 2 次扫描 = 环至少持续 ~50ms 才告警——瞬态边（<50ms）天然过滤。及时性保证：新边挂载后下个扫描点必扫（scan_pending 置位）——最坏延迟 = 窗口长度。现有内核接入：tick 挂接点与 F3286/F3309 共用登记（F3339 清单）。Windows 对比：Verifier 的检测是等待时同步检查（每次等待即查）——零节流但只在测试时开；我们常驻必须节流——哲学差异判据行声明（测试工具可以奢侈，常驻观测必须节俭）。M-105 复测：压力段（挂边风暴）扫描计数对账 + 低频段每边必扫断言。

## F3348 自锁（同锁重入）即时判定

**定位**：自锁特判：waiter == holder（同任务同锁重入等待）→ 无需 DFS 即刻检出——死锁的最简形态走 O(1) 快路。
**语义边界**：只做特判；与 F3232（qspinlock 重入检测）/F3252（mutex 双锁 helper 的重入拒绝）的关系：那些是 API 层拒绝（阻止发生），本条是检测层捕获（发生即报）——三层防线（API 拒绝/层次违例/检测器）中的最后一层，判据行给三层关系图。
**判据**：
- J1：M-107：同任务对同锁二次 lock（绕过 API 层注入）→ DL_SELF 即报（无扫描延迟）。
**纯功能行数**：280（特判逻辑 ~100 + 报告 ~90 + 用例 ~90）
**依赖与嫁接源**：F3343 挂边（挂边时判定）；F3347 报告。

## F3349 检出后动作策略（告警不破坏：红线声明）

**定位**：检出的动作契约：告警三件套（日志 + 事件 + 计数）+ 绝不杀任务/绝不强制破锁/绝不重启（红线）——检测器的行为宪法。
**语义边界**：只做动作策略；报告格式在 F3347。策略与"7×24 零误报"的关系：告警是唯一动作 = 系统在检出后必须能继续跑（哪怕带着死锁），任何破坏性动作都会把观测工具变成故障源。
**判据**：
- J1：M-108：检出真环后系统继续运行 ≥ 5 秒（其他核正常工作、新任务正常调度桩）、告警三件套齐（日志可读/事件入账/计数+1）。
- J2：策略文档（本条判据行）声明"任何未来版本也不得引入破坏性动作"——红线永久性声明。
**纯功能行数**：320（动作实现 ~120 + 三件套 ~110 + 持续运行验证 ~90）
**依赖与嫁接源**：F3347 报告；B15 日志面（告警通道预留——日志批未开工前用现有 logger 桥）；F3211 事件。
**风险与回退**：告警风暴（同环反复检出）——回退：同环去重（路径哈希相同只计一次告警，窗口内），对齐 B09 F3365 的去重设计（预告引用）。
**正文**：实现路径：检出 → `log(DL_RING, 报告) + event(DL_RING) + stat.detected++ + 去重表登记`——四动作序列。去重：环路径哈希（节点序列哈希）入去重表（容量 16 环形），命中即 suppressed++（静默计数——去重本身可观测，防"去重吞掉新环"的反向风险：同哈希但 tsc 差 > 10s 视为新告警——判据行给去重豁免规则）。为什么"不破坏"是红线（判据行论证）：①杀任务需要任务模型完整性保证（A3），v1 无此保证，杀错 = 人为故障；②强制破锁会破坏持锁者的一致性状态（临界区中断）；③重启更荒谬——观测工具触发系统自毁是对"验收"的背叛。7×24 验收场景：检测器带伤运行也要持续告警——这是"观测与控制分离"的架构原则（检测器只有眼没有手）。现有内核接入：告警走现有 logger 桥（F3259 登记，B15 接管后升级分级日志）。Windows 对比：Verifier 检出即 BugCheck（蓝屏 = 破坏性动作的极端形态）——适合开发期、不适合常驻；我们的"只告警"是对其哲学的常驻化改造，判据行声明与 Verifier 的这一根本差异。M-108 复测：检出后 5 秒系统健康检查（其他用例继续跑）+ 去重验证（同环 3 次检出 → 告警 1 次静默 2 次）。

## F3350 检测器自身无锁化设计（检测器不得引入新死锁）

**定位**：检测器的自指安全：其内部数据（图/池/去重表）不得引入新的锁序关系——检测器自己成为死锁源是对使命的背叛。设计契约：检测器数据操作全无锁（原子/CAS/分片）或单写者。
**语义边界**：只做检测器内部的无锁契约与自证；被检测对象的锁不属于检测器（它只读快照）。
**判据**：
- J1：M-109：检测器运行全周期（含扫描/检出/告警）其自身边账本平账（若用了任何锁——应为零）+ grep 审计（检测器代码无 lock 调用点）。
- J2：无锁契约文档：图操作 = per-CPU 分片 + 快照合并（F3351）、去重表 = 单写者（扫描核）——设计级证明两处无竞争。
**纯功能行数**：380（契约文档 ~120 + 无锁实现审计点 ~140 + 自证用例 ~120）
**依赖与嫁接源**：F3351 分片；F3352 池（池操作 CAS）。
**风险与回退**：无锁实现的复杂度 bug（ABA 等）——回退：v1 单写者原则（挂边多写者但每边独立位置无共享写写；扫描单核快照读）——并发面刻意收窄到"多写无共享 + 单读快照"，绕开 ABA（无复用即无 ABA——池回池判据行论证：边池回用是唯一复用点，token 永不复用故摘边按 token 唯一匹配，ABA 不成立）。
**正文**：契约实现（判据行原文级论证）：①图写侧——挂边/摘边只动"自己 CPU 的分片"（F3351）→ 无跨核写写；②扫描读侧——单扫描核取各分片快照（原子读指针）→ 合并视图是"时刻近似一致"（判据行承认撕裂：快照不是瞬时全局一致，环判定可能漏掉撕裂瞬间的真环——由确认窗口多次扫描弥补，这个"以时间换一致"的设计是快照方案的核心权衡，判据行原文记之）；③去重表——仅扫描核写（单写者）④池——CAS 取还，token 唯一防 ABA。自证用例：检测器运行时其"内部锁调用点计数"应为零（grep + 运行计数双证）。现有内核接入：无。Windows 对比：Verifier 运行在验证器进程（内核外）无自指问题——我们的常驻内核内检测器必须自证，这是"常驻化"的代价与责任。M-109 复测：全周期平账 + 静态审计（grep dlgraph.rs 无 lock 调用）。

## F3351 每 CPU 等待图分片与全局合并

**定位**：图的物理布局：per-CPU 分片（各核的边存本地）+ 扫描时快照合并——F3350 无锁契约的数据结构落点。
**语义边界**：只做分片与合并；算法在 F3345。分片键 = 挂边核（边归挂边者分片）。
**判据**：
- J1：M-110：跨核挂边 200 条 → 分片计数和 = 200；合并快照节点/边数与各分片和一致。
- J2：快照合并的开销预算（≤ 200 拍 @ 500 边规模），入 F3331 账。
**纯功能行数**：360（分片结构 ~130 + 快照合并 ~130 + 一致性验证 ~100）
**依赖与嫁接源**：F3213 per-CPU 体例；F3342 图。
**风险与回退**：合并瞬间的边增删（快照撕裂）——回退：F3350 已声明"以时间换一致"（确认窗口弥补），本条只保证"单分片内快照原子"（每分片一个 AtomicPtr 指向不可变快照——写时复制，判据行给 COW 方案的内存开销核算：快照 = 图克隆 500 边 ≈ 12KB × 8 核，可接受）。
**正文**：实现路径：`Shard { snap: AtomicPtr<GraphSnap>, dirty: AtomicBool }`——挂边/摘边改"本地工作副本" + 置 dirty；扫描驱动（单核）：`for shard in shards { if dirty { shard.snap = clone(current); dirty=false } 合并快照 }`——COW 快照让扫描读侧零锁零撕裂（读的是不可变克隆），写侧延迟克隆（dirty 才克隆）。内存核算（判据行）：克隆 12KB × 触发频率（40 扫/秒 × dirty 率）——常态 dirty 率低（无死锁时边少变化），实际克隆频率 < 1/秒，内存恒定 8 × 12KB = 96KB 上限。合并 = 各分片克隆的节点并集（节点键去重——同锁实例被两核挂边的合并语义：边集合并，节点合一，判据行给合并规则表）。现有内核接入：无。Windows 对比：无直接对照（其内核外架构无此问题）。M-110 复测：分片和 == 合并数 + 克隆触发计数对账（dirty 才克隆的验证）。

## F3352 图内存预算与池化（防检测器撑爆内存）

**定位**：检测器的内存纪律：节点/边静态池（F3342 容量）+ 耗尽降级契约（记满即停新边 + DEGRADED 记账，绝不绝境崩溃）。

**判据**：

- J2：池耗尽计数可观测（degraded_events）——降级本身不能是静默的。
**纯功能行数**：300（池实现 ~110 + 降级契约 ~100 + 用例 ~90）
**依赖与嫁接源**：F3342 池容量；F3236 池耗尽回退体例（B02 同款）。
**风险与回退**：降级期恰有真死锁（漏检窗口）——回退：降级声明显式化（记账 + 告警一次）+ 降级仅停新边不停已挂边的扫描——存量环仍可检出，判据行论证"降级不撤防"。
**正文**：实现路径：池 = 静态数组 + free 链（CAS 取还——F3350 契约）；耗尽：`register 边时取节点失败 → degraded = true + 记账（首次告警，后续计数不刷屏）`；恢复：`摘边回池后 free 非空 → degraded = false`。降级语义表（判据行）：新边拒（漏检增量）、存量边照扫（存量防护不撤）、DEGRADED 事件一次 + 计数——"可见的降级"优于"静默的崩坏"。池参数：节点 256/边 512（F3342）+ 分片克隆区 8×12KB（F3351）= 总预算 ~110KB——A5 全域内存预算（240,000 行的物理承载）中的观测面份额，判据行给全域占比声明（< 1%）。现有内核接入：无。Windows 对比：Verifier 的池耗尽行为 = 蓝屏（资源不足即崩溃哲学）；我们降级续跑——7×24 哲学第三处体现（前两处：F3349 不破坏、F3350 不自锁）。M-111 复测：风暴注入至耗尽（降级触发）→ 回落（恢复）→ 全程不崩 + degraded_events ≥ 1。
