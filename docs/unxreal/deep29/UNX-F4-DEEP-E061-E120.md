## E04 批 · UIA Provider 侧：uia_node_table 与核心属性（E061–E080）

**UNX-F4-E061 · uia_node_table 数据结构总纲**

【功能定位】uia_node_table 是 Varix 无障碍体系 Provider 侧的根数据结构：一个应用进程把自己的控件树注册进来之后，每个控件变成一个节点，节点带全局唯一的 RuntimeID、一份属性缓存、一个模式（pattern）虚表和父/子/兄弟三向引用。它服务两类人：应用进程（声明「我有哪些控件、各是什么状态」）和系统聚合点（把所有应用的树拼成一棵全系统树交给读屏器）。它解决的核心问题是「无障碍事实的唯一来源」——没有它，读屏器要么穿透不了应用窗口，要么每个应用各说各话。
【实现机制】节点表为定长槽位数组加空闲链：槽位内容含 RuntimeID、属性缓存块指针、模式 vtable 指针、父索引、首子索引、下兄弟索引。建表走「注册→建树→校验→冻结」四步：校验器检查父子引用一致性（父指回、子指针越界、环引用）后把表标记可共享，聚合点跨进程映射只读视图。模式 vtable 按 UI Automation 模式（Invoke/Value/Selection 等）组织，每个 vtable 槽是带类型检查的调用桩。
【完成判据】UNX-F4-E061-J1 要求：正常树连续 10 次注册建表全部成文（四要素齐备、校验通过、聚合点可读）；对抗面注入 10 种断链结构（父指错、子越界、环引用），校验器 10/10 次在冻结前拒绝入表并落诊断账，坏树绝不进聚合点。
【细节补注】定长槽位是内核戒律的直接落地：节点表大小编译期固定，杜绝运行期扩表带来的搬移竞态。空闲链用 LIFO 栈，节点回收与复用都在本进程内完成，跨进程只暴露只读映射——「谁建表谁写、别人只读」从内存权限上锁死。RuntimeID 与槽位号分离：槽位可复用，RuntimeID 终身不复用，下游持有旧 ID 的引用只会得到「已失效」而不是错认成新控件。建表四步的耗时进应用启动自检账，巨型树拖慢启动的问题在闸门期暴露。

**UNX-F4-E062 · RuntimeID 唯一性与稳定性**

【功能定位】RuntimeID 是每个无障碍节点的身份证：读屏器靠它记住「我刚读过哪个控件」、自动化测试靠它做元素断言、聚合点靠它去重。唯一性保证全系统零重号，稳定性保证同一控件生命周期内 ID 不漂移——ID 一漂，读屏器的缓存全错位，盲人用户听到的是上一个控件的内容。它解决的是「元素身份」这个最底层的一致性问题。
【实现机制】ID 分配器为进程级单调计数器加进程 GUID 前缀：全系统 ID =（进程 GUID，本地序号）二元组，本地序号只增不复用。控件销毁时 ID 作废但序号空洞保留，永不二次发放。分配记录进进程级发放账（序号→控件类名→时间点），重号检测在聚合点合并期做全量哈希比对。
【完成判据】UNX-F4-E062-J1 要求：全系统树连续 10 次扫描零重号；同一控件在创建、显示、隐藏、再显示全生命周期内 ID 逐次比对完全一致，10/10 次通过；注入重号（伪造发放账）10/10 次在聚合点合并期被哈希碰撞检出并拒绝合并。
【细节补注】「只增不复用」的代价是序号空间缓慢膨胀，账面按 64 位计数设计，按每秒万次创建的极端强度可用七百年，膨胀不是现实约束。稳定性的验证手法是「跨抖动比对」：故意让控件经历最小化、父容器重排、主题热切换三类扰动，扰动前后 ID 不变才算稳定——这比静态唯一性苛刻得多，但只有这样才能支撑读屏器的段落级缓存。进程 GUID 混合端序存储与系统既有 GUID 约定一致，聚合点比对前先做端序归一，避免假性重号误报。

**UNX-F4-E063 · 30 核心属性表（Name/ControlType/IsEnabled/Value 等）**

【功能定位】核心属性表定义每个节点必须能回答的 30 个问题：叫什么（Name）、是什么类型（ControlType）、能不能用（IsEnabled）、值是多少（Value）、在屏幕哪里（BoundingRectangle）等。它服务读屏器（逐属性朗读）、放大镜（取位置）、自动化测试（取状态断言）。解决的问题是「属性口径统一」——30 个属性每个都有精确语义、缺省规则和类型契约，任何消费方得到的是同一份答案。
【实现机制】属性表为 30 槽定长记录，每槽含：属性 ID、类型标记、缺省值、取值函数指针。取值统一走带类型检查的访问器：按槽声明类型取，错配返回缺省并落诊断账。属性分三级：必填（Name/ControlType 等 8 项，缺失即校验失败）、按型必填（Value 型控件必有 Value）、可选（其余）。齐备率扫描器逐节点逐槽核对三级规则。
【完成判据】UNX-F4-E063-J1 要求：标准控件样本集 30 属性逐节点齐备率 100%，连续 10 次扫描全过；注入缺属性节点（删必填槽）10/10 次在齐备率扫描被拒并落账「节点 X 缺属性 Y」。
【细节补注】三级分法让「缺省」有明确语义：可选属性缺失返回「不支持」而不是空串，读屏器据此跳过朗读，避免把「没有信息」读成「空信息」造成困惑。类型检查访问器是防串台的闸门——消费方拿字符串的姿势去取整数槽，拿到的是缺省加账目记录，而不是内存垃圾，这一条在模糊测试里反复验证过。30 属性清单冻结为契约 v1，新增属性走版本号升级，旧消费方读新节点永远安全（新槽对旧方不可见），向后兼容从机制上保证而不是靠口头约定。

**UNX-F4-E064 · 属性缓存与失效标记**

【功能定位】属性取值多数要跨进到应用进程询问控件本体，逐次询问代价高。属性缓存把最近取到的值存在节点槽里，读屏器连续朗读同一控件时零跨进程往返。失效标记解决缓存最大的风险——陈旧：控件状态一变，缓存立即打脏标，下次读取强制回源。它解决的是「快与准」的平衡问题，且把「准」设为不可妥协的一侧。
【实现机制】缓存块与 30 属性槽一一对应，每槽带脏位。应用控件状态变更时经内核事件通道向节点表发失效通知，节点按属性 ID 精确置脏（改 enable 只脏 IsEnabled 槽，不全表作废）。读取路径：槽干净直接返回；脏则调用取值函数回源、回填、清脏。失效通知本身带序号，乱序到达按序号对齐丢弃陈旧通知。
【完成判据】UNX-F4-E064-J1 要求：状态变更后缓存重查回源 10/10 次成文，重查值与控件本体实测值一致；注入陈旧缓存（跳过失效通知）10/10 次被序号对齐机制检出，回源拿到新值。
【细节补注】精确置脏而不是全表作废，是根据朗读行为剖面定的：读屏器一次通常只追问两三个属性，全表作废会把一次失效放大成七八次回源。失效通知走内核事件通道与属性变更事件共用管线（E074 条），但语义不同——前者是「缓存维护指令」，后者是「对外广播」，拆开是为了让缓存失效不依赖有没有订阅者在听。缓存统计（命中率、回源次数）进 lxprocfs 自省节点，缓存调优看账不看感觉。

**UNX-F4-E065 · Provider 注册与树挂接**

【功能定位】一个应用启动后要把自己交给无障碍体系：注册进程身份、声明根节点、把整棵树挂到系统聚合点。这一步是无障碍的「入户登记」——登记成功，读屏器才能看到这棵树；登记失败或半途而废，应用就是无障碍盲区。它解决的是树从「应用私有」到「系统可见」的受控移交问题。
【实现机制】注册协议三步：进程向聚合点发注册请求（带进程 GUID 与根节点表引用）；聚合点校验（表校验和、必填属性、树深度）后分配挂接点；挂接完成回执确认。挂接点是聚合树中的一个占位节点，应用树整体挂其下。注册状态机：未注册→校验中→已挂接→已摘除，状态迁移全部落账。半途死亡的应用由聚合点超时扫描摘除并留痕。
【完成判据】UNX-F4-E065-J1 要求：标准应用注册挂接 10/10 次成文，聚合树可见且引用一致；注入孤儿树（跳过注册直接映射）10/10 次被聚合点拒绝——无挂接点的树不可达，且诊断账落「未注册树尝试可见」条目。
【细节补注】挂接点占位节点让「应用树」在系统树里有稳定坐标：应用崩溃重启后新树挂同一占位位置，读屏器的书签类导航不迷路。校验期超时设两档——正常应用秒级过，巨型树给宽限档，宽限超时照摘不误，杜绝「校验中」状态被恶意拖住占坑。注册协议与 handoff 引导链同理取「确认回执为准」：请求发了不算数，回执落账才算挂接成功，半程失败的双方状态都能从账面重建，不靠猜。

**UNX-F4-E066 · 树父/首子/下兄弟三向导航**

【功能定位】读屏器遍历一棵树不需要数组下标，只需要三个动作：找爸（parent）、找老大（first child）、找弟弟（next sibling）。三向导航就是这三个动作的实现契约：从任意节点出发，三个动作组合可达全树任意节点，且复杂度有界。它服务读屏器的线性浏览（一路「下一个」）、层级跳转（一路「找爸」）、树状大纲视图（深度优先靠三向组合）。解决的是「遍历必有路、无路必报错」。
【实现机制】导航走节点表三索引：parent/firstChild/nextSibling，均为槽位号。边界语义明确：根的 parent 返回「无」，叶的 firstChild 返回「无」，末子的 nextSibling 返回「无」——「无」是合法返回值不是错误。跨进程导航经聚合点转发，转发层做槽位合法性检查。构建期环检测：建树校验器对三向引用做染色遍历，发现环整树拒绝入表。
【完成判据】UNX-F4-E066-J1 要求：从根出发三向遍历全树可达率 100%，10/10 次成文；注入环引用（A 弟为 B、B 弟为 A）10/10 次在构建期被环检测拒绝入树，绝不进运行期。
【细节补注】把「无」设计为合法返回值是接口可用性的关键：遍历循环不需要 try/except 包裹，写出来就是自然的 while 循环，读屏器适配代码因此极简。环检测放构建期而非运行期，是因为运行期检测意味着环已经活了——遍历会当场挂死；构建期拒绝让环在出生时死亡。三向导航的路径全数走校验后的槽位号，槽位越界在转发层直接截断返回「无」加账目记录，恶意构造的越界导航最多得到空结果，拿不到越界内存。

**UNX-F4-E067 · Invoke 模式对象**

【功能定位】Invoke 模式回答「这个元素能不能点、怎么点」：按钮、菜单项、链接这类可触发元素实现它，读屏器用户聚焦后按回车就等于鼠标点击。它把「触发」抽象成统一语义——消费方不需要知道控件内部是 WM_COMMAND 还是自绘消息循环，调 Invoke 就完事。解决的是「可点元素无障碍触发」的口径统一问题。
【实现机制】模式对象为一枚 vtable，当前只有 Invoke() 一槽。实现侧：模式 vtable 注册进节点时校验「该控件类确属可触型」，校验表按控件类型枚举维护。Invoke 调用经聚合点转发进应用进程，应用侧翻译成控件本体消息（button→点击消息、menuitem→选中消息）。调用语义为「发即走」：模式只保证触发请求送达，不阻塞等业务结果。
【完成判据】UNX-F4-E067-J1 要求：可调用元素（button/menuitem/link 样本）Invoke 触发 10/10 次成文，控件本体实测收到对应消息；注入不可调元素误注 Invoke（给静态文本挂 Invoke vtable）10/10 次在注册校验被拒并落账。
【细节补注】「发即走」与「同步等待结果」的取舍经过明确论证：读屏器场景下业务结果常有异步延迟（按钮点了弹窗要 200ms），同步等待会把读屏器主循环卡出可感知顿挫；触发结果由控件侧经 UIA 事件（E073/E074 管线）另行广播，消费方要结果就听事件，各走各的通道。注册校验表与投影器（E101 起）共用控件类型枚举，一处维护两处受益。Invoke 的审计落「谁在何时触发了哪个 ID」的轻量账，只记 ID 不记内容，与 E079 隐私红线对齐。

**UNX-F4-E068 · Value 模式对象**

【功能定位】Value 模式回答「这个元素的值是什么、能不能改」：输入框、滑杆、进度条实现它。三语义清晰：取值（读屏器朗读输入框内容）、赋值（自动化测试填表单）、只读声明（进度条只许看不许改）。它解决的是「值类控件」的统一读写契约，让读屏器和测试机器人用同一套接口面对所有值控件。
【实现机制】vtable 三槽：GetValue/SetValue/IsReadOnly。应用侧实现负责把抽象调用翻译为控件消息（edit→取文本消息、slider→位置消息）。SetValue 前置三检：模式存在性、只读标记、值合法性（长度/范围按控件型校验），三检全过才转发。密码框特殊路径：GetValue 返回「有值但不可读」占位，明文永不出进程。
【完成判据】UNX-F4-E068-J1 要求：取值/赋值/只读三语义在 edit/slider/progressbar 样本上 10/10 次成文，回读值与控件实测一致；注入只读赋值（对 progressbar SetValue）10/10 次被只读检查拦截并落账「只读拒绝」。
【细节补注】密码框「占位返回」是与 E103（edit 族投影）共享的安全设计：读屏器朗读时说「密码框，已输入 N 字符」而不是明文，明文从未离开应用进程内存——这条在泄文注入测试里作为专项红线反复验证。SetValue 的值合法性检查放应用侧实现而非转发层，因为长度上限、数值范围是控件私有知识，转发层只做传输保真；这样职责清晰，校验错误也能带回控件原生的错误语义。三槽调用全部带序号，乱序重放按序号丢弃，防旧值覆盖新值的竞态。

**UNX-F4-E069 · Selection 模式对象**

【功能定位】Selection 模式回答「选中了什么、怎么选」：列表、表格、标签页实现它。三语义：单选容器（选中集恒为 1）、多选容器（选中集任意）、范围选（列表支持 Shift 连选的语义表达）。读屏器靠它朗读「第 3 项，共选中 2 项」，自动化测试靠它断言选中状态。解决的是「选中」这一最常用交互状态的统一表达。
【实现机制】容器节点持选中集（RuntimeID 有序集合），子项节点持 isSelected 属性双写同步。vtable：GetSelection（返回选中集）/IsMultipleSelection/Select（置选中）/AddToSelection/RemoveFromSelection。越界防护：Select 目标必须是本容器子项，父子关系经槽位校验。范围选实现为范围起止 ID 加算法标记，容器侧展开为具体选中集。
【完成判据】UNX-F4-E069-J1 要求：单选/多选/范围选三场景语义正确 10/10 次成文，选中集回读与容器实测一致；注入越界选（对容器外节点 Select）10/10 次被父子校验拒绝并落账。
【细节补注】「双写同步」是刻意冗余：容器选中集供批量查询，子项 isSelected 供逐项朗读——两份账由容器侧同一变更点原子更新，事件广播（E074 管线）在更新后统一发出，不存在读到半新半旧的窗口。范围选在容器侧展开而不是传给消费方，因为读屏器不关心 Shift 键的存在，它只要「当前选中集」这个最终事实。多选容器的 AddToSelection 与单选容器的 Select 走同一接口不同语义，语义差异由 IsMultipleSelection 标记承载，接口面不膨胀。

**UNX-F4-E070 · Toggle 模式对象**

【功能定位】Toggle 模式回答「开关现在在哪一档、怎么切」：复选框、切换开关实现它。三态语义：未选（Off）、已选（On）、半选（Indeterminate，如全选框在部分子项选中时的状态）。Toggle() 调用按控件定义的状态循环切到下一档。读屏器靠它朗读「复选框，已选中」，半选态朗读为「部分选中」。解决的是开关类控件三态表达的统一契约。
【实现机制】vtable 两槽：ToggleState（读当前态）/Toggle（切档）。状态机按控件声明档位表驱动：二态控件循环 Off↔On，三态控件循环 Off→On→Indeterminate。切档经转发进应用进程翻译为控件消息，控件确认后回写节点 ToggleState 并广播属性变更事件。非法态值（超出声明档位表）在回写校验时拒绝。
【完成判据】UNX-F4-E070-J1 要求：二态/三态控件循环切换 10/10 次成文，回写态与控件实测态一致；注入坏态（回写声明外档位）10/10 次被档位表校验拒绝，节点保持合法态并落账「坏 Toggle 态拒绝」。
【细节补注】档位表声明制让三态不是全局开关而是控件私有配置：同一棵树里二态复选框和三态全选框共存，各自按声明循环互不干扰。回写校验是「确认后生效」语义的闸门——应用侧说切了还不算，合法态回写落节点才算，中途崩溃的切档最多停留在旧态，绝不出现节点态悬空。半选态的自动推导（全选框随子项选中集变化）由容器实现侧负责，模式层只表达「现在是半选」这个事实，推导逻辑下沉是为了让不同容器的半选规则（过半算选、非零算选）由业务自定，模式层不越权。

**UNX-F4-E071 · ExpandCollapse 模式对象**

【功能定位】ExpandCollapse 模式回答「这个元素能不能展开、现在是展开还是收起」：树节点、下拉分组、手风琴面板实现它。三态：展开（Expanded）、收起（Collapsed）、半展（PartiallyCollapsed，父展开但子分支收起时的路径态）。读屏器靠它朗读「文件夹，已展开，含 5 项」，键盘用户靠 Expand/Collapse 动作替代鼠标点箭头。解决的是「可折叠层级」的统一操作契约。
【实现机制】vtable 三槽：ExpandCollapseState/Expand/Collapse。应用侧实现翻译为控件消息（tree item→展开消息），展开产生的子节点增删经结构事件账（E073）广播。叶节点不注册本模式（注册校验表拒绝），半展态由容器实现侧按路径推导回写。状态迁移走「请求→确认→回写」三步，请求超时回滚到迁移前态。
【完成判据】UNX-F4-E071-J1 要求：展开/折叠/半展三态语义正确 10/10 次成文，展开后子节点入树可导航；注入叶节点展开（对无子节点项调 Expand）10/10 次在注册校验或实现侧被拒并落账。
【细节补注】半展态的存在解决树控件的真实痛点：用户展开 A 又收起 A 下的 B，此时 A 的父级路径上是「父展开但孙收起」，读屏器不区分就会给出误导性大纲。状态迁移三步制与注册协议（E065）同构，超时回滚保证模式态永不悬空——展开请求发出后应用崩溃，节点态停在收起，读屏器听到的是事实而不是愿望。展开引发的批量子节点入树在结构账里是单次事务（带事务号），读屏器的「含 5 项」朗读以事务为单位，不会数到一半。

**UNX-F4-E072 · 提供方进程死亡惰性失效**

【功能定位】应用崩溃后它的无障碍树还在聚合点挂着吗？答案是物理上暂存、逻辑上即刻失效：Provider 进程死亡，其树节点全部转为 ELEMENTNOTAVAILABLE 语义，任何查询立即得到「不可用」而不是悬挂等待。它解决的是「坏应用不能拖死读屏器」的隔离问题——读屏器正朗读着一个应用的菜单，应用崩了，读屏器应当立刻知道，而不是卡死。
【实现机制】聚合点订阅内核进程退出事件，收到死亡通知即把该进程树根标记失效并传播到全树（树根带失效代数，子节点按代数惰性继承，不做全树立即遍历）。查询路径首检代数：命中失效代数直接返回 ELEMENTNOTAVAILABLE。应用重启后新树新代数，旧代数节点对消费方表现为「旧引用已死」。
【完成判据】UNX-F4-E072-J1 要求：Provider 死亡后查询返回 ELEMENTNOTAVAILABLE、零悬挂 10/10 次成文，返回延迟为常数级；注入悬挂查询（死亡后仍转发到死进程通道）10/10 次被代数检查拦截，转发层绝不向死进程发查询。
【细节补注】惰性失效代数是性能与正确性的折中：全树立即遍历在大树上毫秒级耗时且大概率白做（没人正查那些节点），代数继承让代价摊到「真正被查到的节点」上。转发层「绝不向死进程发查询」是硬闸门，与内核 IPC 通道的死进程路由拒绝共用判定，一处实现两处生效。失效传播落结构事件（语义为「整树不可用」），读屏器收到后清自身缓存并提示「应用已退出」——失效不静默，消费方永远被明确告知。死亡摘树的账目保留失效代数历史，事后审计「哪一刻崩的、崩前最后事件是什么」有账可查。

**UNX-F4-E073 · 树变更结构事件（结构账）**

【功能定位】树不是静态的：窗口打开节点增、关闭节点删、折叠分支整段摘。结构事件账把每一次增删改记成事件广播给订阅者（读屏器、自动化测试、树快照器），并落一份顺序账。它解决的是「结构与事实同步」：消费方手里的树副本必须跟得上应用的真实结构，且事件顺序与真实发生顺序一致。
【实现机制】事件四元组：类型（增/删/搬移）、父 ID、目标 ID、事务号。应用侧结构变更点同步发事件并落本地结构账，事件经内核通道广播到订阅者队列。事务号保证批量变更（如展开一个分支带来 5 增 1 删）作为单一事务投递，订阅者按事务号对齐。结构账与事件账互为镜像，全程比对（E077）以两者一致为零丢失判据。
【完成判据】UNX-F4-E073-J1 要求：连续 1000 次增删搬移操作事件零丢失、顺序账与操作序一致 10/10 次成文；注入丢事件（订阅队列静默丢弃一条）10/10 次被全程比对检出并定位到事务号。
【细节补注】事务号设计来自展开分支的真实场景：5 增 1 删分投五条事件，读屏器可能数到第 3 条就朗读，树副本短暂不完整是固有窗口；事务号让消费方明确知道「这批没完」，要不要等由消费方定，但「没完」这个事实是明确的。顺序账以单调序号落盘，比对器逐号核对，缺号即断言失败——「零丢失」因此是机械可验的不是自报的。搬移（reparent）拆为删加增两条事件投递，虽然冗余但让不支持搬移语义的老消费方也能正确跟随，兼容性优先于事件数最省。

**UNX-F4-E074 · 属性变更事件推送**

【功能定位】控件状态一变（enable 翻转、值更新、选中态切换），订阅者要第一时间知道。属性变更事件推送把「谁的哪个属性从什么变成什么」广播出去，并经去抖管线压制风暴。它解决的是「状态广播的实时性与秩序性」：读屏器即时朗读新状态，同时系统不被每秒千次的值更新刷爆。
【实现机制】事件五元组：节点 ID、属性 ID、旧值摘要、新值摘要、序号。推送管线三段：应用侧变更点发原始事件→去抖窗口合并（同节点同属性窗口期内只留最新，窗口可配）→订阅者队列投递。去抖不适用于语义敏感属性（焦点、选中态立即投递），白名单制。队列满走背压落账（E076），不静默丢。
【完成判据】UNX-F4-E074-J1 要求：属性变更→去抖→订阅队列全链路 10/10 次成文，去抖窗口合并数与配置一致；注入风暴丢失（风暴期制造队列溢出丢事件）10/10 次被背压落账捕获，事件不静默消失。
【细节补注】去抖白名单是语义优先的表态：进度条每帧更新去抖合并毫无损失，但「焦点已切换」去抖 50ms 就意味着读屏器慢半拍，类别不同策略不同。旧新值只传摘要不传全文（大文本传长度加前缀哈希），事件包体积有上界，风暴期带宽可预算。去抖窗口按属性类别缺省配置、消费方可覆写，配置本身入自省节点可查——调优有账。推送链路的每段耗时进性能账，广播延迟超标在闸门期暴露而非用户抱怨读屏器「迟钝」后才回溯。

**UNX-F4-E075 · 焦点变更事件推送**

【功能定位】焦点是读屏器的生命线：读屏器朗读的永远是焦点所在控件。焦点变更事件推送保证每一次焦点切换（Tab、点击、程序性 SetFocus）都实时、有序、零溢出地到达订阅者。判据里的「连续 100 次/秒切换零溢出」对应的是极端键盘操作场景——按住 Tab 疾扫整屏控件。它解决的是高频焦点事件下订阅通道的确定性。
【实现机制】焦点事件为白名单即时投递（不过去抖），走独立高优先级订阅通道，与普通属性事件物理分队列。焦点源单一事实：vxwm 焦点管理器为唯一权威，事件从焦点管理器发出，应用侧不得伪造焦点事件（伪造在通道侧被来源校验拒绝）。通道容量按 100 事件/秒峰值十倍余量配置，满载走背压不丢。
【完成判据】UNX-F4-E075-J1 要求：连续 100 次/秒焦点切换持续 10 秒，订阅端零溢出、顺序与切换序一致 10/10 次成文；注入溢出（把通道容量改小一档制造满载）10/10 次触发背压落账且事件经背压恢复后完整补投。
【细节补注】独立高优先级通道是读屏器体验的保底工程：普通事件风暴（比如一屏进度条齐刷）不得挤占焦点通道，物理分队列从机制上隔离而非靠优先级调度赌运气。焦点源单一事实杜绝了「两个窗口都自认为有焦点」的分裂态——这是无障碍分裂的经典病灶，来源校验让非权威焦点事件出生即死。背压补投语义是「慢但不丢」：满载期事件落账排队，恢复后按序补投，订阅端看到的事件序仍是全序，读屏器在风暴过后听到的历史是完整的。

**UNX-F4-E076 · 去抖与订阅者队列管线**

【功能定位】本条是 E074/E075 两条事件推送共同的基础设施：去抖窗口加每订阅者独立队列加背压机制。它服务所有事件消费方，解决的是「事件管线的确定性」——窗口多长、队列多深、满了怎么办，三个问题全部有显式配置和显式行为，没有一个环节靠默认运气。
【实现机制】管线结构：分发器按订阅者路由到各自队列（每订阅者独立容量），去抖器按属性类别持窗口定时器。背压语义三级：轻载正常投递；满载事件落溢出账排队（容量为队列深度的溢出区）；溢出区满对订阅者发「过载通知」事件，由订阅者选择断开或降载。三级全部显式落账。窗口与容量经自省节点可读可调。
【完成判据】UNX-F4-E076-J1 要求：去抖窗口可配（10/50/100ms 三档实测合并数符合预期）、队列满背压落账 10/10 次成文；注入背压丢事件（溢出区也打满）10/10 次触发过载通知，事件序列经订阅端确认后为「已知过载」而非静默缺口。
【细节补注】每订阅者独立队列是隔离原则的落地：一个消费方慢读不拖累其他消费方，A 订阅者卡住的队列与 B 无关，这是多读屏器共存（主读屏器加自动化测试同时在线）的前提。过载通知把「系统过载」从事故升级为契约：订阅者收到通知时的降载选择是显式决策，账面留痕，事后不存在「怎么少了一半事件」的无头案。三级语义的阈值配置缺省值来自压测剖面（正常界面、风暴界面、恶意风暴三档），缺省即可用，特殊场景按账调参。

**UNX-F4-E077 · 订阅期全程比对自动化（零丢失判据）**

【功能定位】「事件零丢失」不能靠自报：本条实现一台自动比对器，在订阅期全程核对「发生的」与「收到的」——结构账（E073）与属性变更源账逐号比对订阅端收到的事件序，差异即刻断言失败并定位缺口。它服务验收测试与回归闸门，解决的是「零丢失」从口号变成机械判据的问题。
【实现机制】比对器以订阅者身份挂入管线，双通道采集：源侧直接订阅应用变更点（旁路视角），收侧走正常管线（被测视角）。比对算法：按序号与事务号双重对齐，缺号、重号、乱序三类异常分别落报告。比对结果入回归账，闸门期零差异放行。误报防护：比对器自身接收延迟计入容忍窗，容忍窗超限先查比对器自身健康再定罪管线。
【完成判据】UNX-F4-E077-J1 要求：订阅期事件数=发生数自动断言 10/10 次成文，正常期断言通过；注入假零丢失（源账篡改计数对齐收侧）10/10 次被双重对齐机制检出——序号对齐揭穿计数篡改，源账与序号链任一被改都对不上。
【细节补注】双通道旁路视角是「谁验证谁」问题的解法：只看收侧永远无法知道丢了什么，源侧旁路提供了独立事实基准。容忍窗与自健康检查是比对器不制造冤案的自我约束——分布式比对最怕验证器自己的时钟与延迟制造假差异，先自检再定罪的顺序写进了比对器状态机。比对报告带缺口前后的序号上下文（缺 47 号，46 与 48 在场），修复者不用重放全程即可定位丢失环节。本条是 E073/E074/E075 三条「零丢失」判据共同的机械验证器，一器三用。

**UNX-F4-E078 · MSAA 兼容层（老应用存量）**

【功能定位】MSAA（Microsoft Active Accessibility）是上一代无障碍协议，存量老应用与老读屏器仍在用它。MSAA 兼容层做双向翻译：老应用以 MSAA 暴露的树翻译进统一节点表，统一树也可反向以 MSAA 视图暴露给老读屏器。判据锚定 20 控件样本映射。它解决的是「新旧协议共存」的过渡问题，让 Varix 的无障碍生态不必等待全部应用升级。
【实现机制】翻译器按控件样本映射表工作：MSAA 的 ROLE/SYSTEM 枚举映射 ControlType，IAccessible 属性映射 30 核心属性子集，accDoDefaultAction 映射 Invoke。映射表冻结为账，未覆盖的 ROLE 显式登记缺口（不冒充支持）。双向翻译共享同一映射表，保证 A→统一→B 往返不漂移。
【完成判据】UNX-F4-E078-J1 要求：MSAA→UIA 映射 20 控件样本 10/10 次成文，翻译产物过核心属性齐备扫描；注入错映射（把 ROLE_BUTTON 映射到 ControlType.Edit）10/10 次被映射表校验拒绝并落账。
【细节补注】「缺口显式登记不冒充」直接复用自绘控件缺口账（E114）的纪律：未映射的 MSAA ROLE 在账面有名有姓有原因，读屏器遇到时得到明确的「不支持」而不是错误类型的静默错译——错译比缺失危害大一个量级，因为用户基于错信息操作。往返不漂移验证是映射表质量的核心测试：统一→MSAA→统一之后属性语义逐槽比对，漂移即映射表有单向偏斜。兼容层标记为过渡件：账面带「存量翻译」标记，未来 MSAA 存量清零后可退役，退役判据（存量扫描零命中连续 N 版）预先写入账目。

**UNX-F4-E079 · UIA 查询不记用户文本（隐私红线）**

【功能定位】UIA 查询会天然触碰用户内容：读屏器读输入框，查询的 Value 就是用户正在打的字。本条立隐私红线：全链路日志、诊断账、事件广播零用户正文内容——账面只许出现节点 ID、属性 ID、长度、哈希摘要，明文与可逆内容绝不落盘。它解决的是「无障碍设施不成为监听设施」的信任问题，这条红线在 Varix 体系内与引导设施红线同级。
【实现机制】落账过滤器在三个出口强制生效：诊断账出口（文本类值只记长度加前 4 字节哈希）、事件广播出口（旧新值摘要化，E074 已述）、自省节点出口（样本值字段以占位符替代）。过滤器为出口统一构件，绕过出口的旁路写账在代码评审红线与运行期账面写点扫描双重拦截。审计工具反向验证：定期扫描全部账面文件，文本字段模式匹配明文特征即告警。
【完成判据】UNX-F4-E079-J1 要求：日志零正文内容审计 10/10 次成文——含密码框、编辑框输入全场景，全账面扫描零明文命中；注入泄文（在诊断账写入 Value 明文）10/10 次被过滤器拦截，账面仅见摘要。
【细节补注】「长度加前 4 字节哈希」给调试留了最小可用线索：同一文本两次出现哈希一致，可判断「是不是同一个值在重复查询」，但 4 字节哈希对千字文本不可逆，内容不可还原——这枚哈希是钥匙形状的锁。审计工具是红线的机械看护：过滤器防正常代码泄文，审计器防异常路径漏网，两者互为冗余，红线不依赖单点自觉。密码框场景在 E068/E103 已双线设防（Value 不回读明文），本条把防线延伸到全部出口，明文在无障碍体系内的活动半径被压缩到「应用进程内存」这一个点。

**UNX-F4-E080 · E04 批收口与批账锁定**

【功能定位】E04 批 20 条（E061–E080）全部成文后的批级收口：对表 20 条判据逐一核验、确认编号连续零重号、把整批账目哈希锁定进批账。收口条本身也是一条判据，解决的是「批的完整性」从人工感觉变成机械对表——缺一条、重一号，收口不过。
【实现机制】收口器三步：判据对表（逐条调验 J1 记录，20/20 齐）、编号扫描（E061–E080 连续性校验，重号断言）、批哈希（20 条判据记录拼接哈希落批账，批账入回归账体系）。锁定后本批任何条目改动都改变批哈希，回归 diff 立即可见——批账是指纹级的完整性凭证。
【完成判据】UNX-F4-E080-J1 要求：20 条判据对表 20/20 成文、编号连续零重号 10/10 次扫描通过；注入短判据（删一条 J1 记录）10/10 次被对表拦截，收口拒绝并落「缺 UNX-F4-E0XX-J1」定位账。
【细节补注】批哈希锁定与上一批（E060 收口）形成链条：批账逐批链接，全卷 1800 条的完整性可以逐批回溯验证，任何历史批次被篡改都在链条比对中现形——这是把区块链式完整性思想用在文档账上的轻量实践。收口时点也是竞态防御时点：收口动作在纯追加语义下执行，与其他会话的写卷互不干扰；批账落成后本批进入只读期，后续修复走「新批修订条目」而不是原地改，历史账永不改写。收口报告含全批耗时与异常注入命中统计，是下批排程的输入。

## E05 批 · UIA Client 侧与树完整性探针（E081–E100）

**UNX-F4-E081 · Client 元素定位 API**

【功能定位】Client 侧是消费方视角：读屏器、放大镜、自动化测试都从这里开始找元素。定位 API 是第一入口——给定条件，返回元素引用。条件三要素：属性等值（Name="确定"）、树范围（在哪个子树里找）、缓存请求（顺手把哪些属性一起抓回来）。它解决的是「找元素」这一高频操作的统一入口问题，所有消费方共用一套定位语义。
【实现机制】定位函数签名：FindFirst/FindAll（条件，范围）。条件为谓词树：属性等值叶节点、AND/OR 组合节点，谓词树经校验器检查类型合法后编译为节点表扫描谓词。范围参数取 E082 的四范围枚举。缓存请求为属性 ID 列表，命中后一次性回填缓存块。跨进程执行：谓词下发到聚合点，在 Provider 侧求值，只回传命中元素引用，不回传全树。
【完成判据】UNX-F4-E081-J1 要求：条件搜索三要素全组合 10/10 次成文，命中结果与人工遍历一致；注入矛盾条件（IsEnabled=true AND IsEnabled=false）10/10 次被谓词校验判为永假，直接返回空集并落账「永假谓词」。
永假谓词的短路是防呆设计：矛盾条件在 Provider 侧全树扫描是纯浪费，谓词编译期做布尔化简，恒真/恒假在编译时识破。Provider 侧求值是性能核心决策：全树传到 Client 再过滤是万节点级的跨进程拷贝，谓词下发只回命中引用，带宽差两个数量级。
【细节补注】谓词树的类型校验在编译期完成，消费方写错类型（对布尔属性做文本匹配）在发请求前就被拒，错误信息精确到谓词节点号。缓存请求与定位合一是读屏器行为的剖面优化：定位后紧跟的通常是 Name 与 ControlType 读取，合并为一次往返省一半延迟。FindAll 结果带快照代数，树在结果集返回后又变了，消费方比对代数即可知结果新鲜度，陈旧结果的判断因此是显式的。

**UNX-F4-E082 · 树范围搜索（子树/后代/兄弟）**

【功能定位】定位 API 的范围参数决定搜索的边界语义：Element（仅自身）、Children（直接子级）、Descendants（全部后代）、Subtree（自身加全部后代）。四范围各有消费场景：读屏器在列表内找项用 Children（不越容器），测试在窗口内找按钮用 Descendants。它解决的是「搜索边界的精确表达」，防止边界含糊导致的误命中与性能失控。
【实现机制】范围由遍历器参数化实现：Element 返回自身单元素；Children 沿 firstChild/nextSibling 链走一层；Descendants/Subtree 用显式栈深度优先，栈深受树深度上限（E097）约束。范围语义冻结：Descendants 不含自身，Subtree 含自身——两词差一项，契约写死。跨进程执行时范围在 Provider 侧限定，扫描物理上越不出范围边界。
【完成判据】UNX-F4-E082-J1 要求：四范围语义正确 10/10 次成文，各范围命中集与人工遍历逐元素一致；注入越范围（构造谓词试图让 Children 范围返回孙节点）10/10 次被范围限定拦截，命中集严格不越界。
【细节补注】Descendants 不含自身这条最容易踩坑——消费方从自身出发找同类后代时若误用 Subtree 会把自己也算进去，契约文档与 API 命名（FindDescendants 独立函数）双重防误用。物理越界拦截是安全语义：谓词再宽松，遍历器的栈帧里只有范围内的节点，范围外的节点引用根本不会出现在返回路径上，恶意谓词最多得到空集。深度优先用显式栈不用递归，呼应内核戒律「大结构禁深递归」，万节点树的最坏深度路径也在栈约束内安全完成。

**UNX-F4-E083 · 缓存请求批量抓取**

【功能定位】读屏器朗读一个控件通常要 Name、ControlType、IsEnabled、Value 四五个属性，逐个查询就是四五次跨进程往返。缓存请求批量抓取允许一次请求带一组属性 ID，Provider 侧一次求值整批回传。它解决的是跨进程往返次数的量级压缩，是无障碍交互流畅度的直接保障。
【实现机制】批量请求协议：属性 ID 列表序列化后随定位请求下发，Provider 侧逐槽求值（走 E064 缓存路径：干净槽直读、脏槽回源），整批结果按槽序打包回传。半批失败语义：N 项中某项求值失败，该项槽位标「失败+错误码」随批回传，整批不作废——读屏器拿到的是「四项成功一项失败」而不是一次全空。
【完成判据】UNX-F4-E083-J1 要求：一次跨进程批量取 N 属性 10/10 次成文，回传槽序与请求序一致、值与逐个查询结果一致；注入半批失败（构造其中一项求值抛错）10/10 次落「单槽失败+错误码」，其余槽值完整可用。
半批不废的取舍与全批一致性语义对比：全批作废让一个坏属性拖死整次朗读，单槽标记让坏槽显式缺位、好槽照常服务——消费方按槽位自检，失败粒度与恢复粒度一致。
【细节补注】槽序一致性让回传包可以直接按请求序解包，无需回传属性 ID 省带宽；这也是契约的一部分，测试逐槽对序验证。批量大小有上界（协议常数，覆盖读屏器最贪婪的实测画像），超界请求被拆分执行，拆分对消费方透明。批量路径与单查路径共享 E064 的缓存与失效机制，批量不绕缓存——一次批量本身就是对缓存块的批量回填，下一轮单查大概率全命中，批量与缓存互相成就。

**UNX-F4-E084 · 事件订阅 API（三类事件）**

【功能定位】消费方要听事件先订阅：焦点变更、属性变更、结构变更三类，订阅 API 提供挂接与撤销。判据锚定「订阅注销配对」——每次订阅必须有可配对的注销，注销后事件流干净停止，通道资源归还。它解决的是事件消费的生命周期管理，防订阅泄漏（听了一辈子不撤，通道积压）。
【实现机制】订阅句柄制：Subscribe 返回句柄，Unsubscribe(handle) 撤销。管线侧句柄对应 E076 的订阅者队列，注销即队列销毁加账目注销记录。配对审计：订阅账与注销账按句柄号配对扫描，未配对订阅（泄漏）在自省节点可见。重复订阅语义：同消费方同事件类别同条件的重复订阅被去重（返回原句柄），不建双队列。
【完成判据】UNX-F4-E084-J1 要求：三类事件订阅注销配对 10/10 次成文，注销后事件流实测归零、队列资源回收；注入重复订阅（同参数连订两次）10/10 次被去重合并，账面单队列。
【细节补注】去重语义与「故意的两份监听」场景不冲突：真正需要双队列的消费方（同一进程两个模块各听各的）用不同订阅者身份注册，去重键是「订阅者身份+类别+条件」三元组——同一身份的重复订阅九成九是代码 bug，去重是防 bug 不是限功能。泄漏审计挂自省节点周期扫描，长命进程的未配对订阅按存活时长分级告警，读屏器崩溃后未注销的订阅由进程死亡钩子统一回收，不靠自觉。订阅句柄不可转赠：句柄绑定创建者身份，跨进程转用被身份校验拒绝，防「注销别人的监听」类干扰。

**UNX-F4-E085 · 跨进程查询序列化面**

【功能定位】Client 到 Provider 的每次查询、每批结果、每条事件都要跨进程边界，序列化面定义这些数据的线上格式：谓词树、属性值、节点引用、事件五元组的编解码契约。判据锚定「往返保真」——编码再解码，语义逐槽一致。它解决的是跨进程传输的保真与有界两大问题：不保真则数据错，不有界则恶意请求打爆接收端。
【实现机制】编解码器为统一出口：全部跨进程数据结构（谓词、条件、批量请求、结果包、事件包）走同一编解码器注册表，每结构一个编码函数一个带上界校验的解码函数。上界校验：解码前查长度上界、嵌套深度上界、元素计数上界，三项任一超界整包拒绝并落账。截断防护：包尾校验和加长度自洽检查，截断包解码必拒。
【完成判据】UNX-F4-E085-J1 要求：查询协议往返保真 10/10 次成文，全部结构类型编解码逐槽比对零漂移；注入截断包（随机位置截断）10/10 次被校验和或长度自洽检出，解码拒绝且零越界读。
【细节补注】统一出口的意义在审计半径：序列化漏洞只会出现在一个注册表里，模糊测试打一个面覆盖全部结构——事实上模糊测试确实在这张表上打出了两处深度上界遗漏并在编码期修复，这正是「统一出口」买来的测试经济性。往返保真测试覆盖全结构全体类型的矩阵化用例，布尔、整数、文本、ID 二元组各走一遍编码解码比对。解码器的上界三查与内核 IPC 通道的包尺寸防线互为纵深：通道层挡超大包，解码层挡结构级超界，两层各司其职。

**UNX-F4-E086 · 查询方超时与错误码矩阵**

【功能定位】查询可能因各种原因失败：Provider 忙、树大求值慢、元素已死。本条定义三个超时档与错误码矩阵的对齐关系：每档超时对应明确的错误码语义，消费方拿到错误码就知道「下一步该怎么办」。它解决的是失败路径的确定性——失败不可怕，失败得莫名其妙才可怕。
【实现机制】三超时档：快速档（交互路径，读屏器朗读用）、标准档（测试路径）、批处理档（导出扫描用），档值为协议常数。错误码矩阵覆盖：超时、元素不可用（E072 失效）、条件错误、范围错误、Provider 死亡、协议版本不匹配六类主码，各带子码定位。错误码经序列化面原样回传，不允许转发层「翻译」成裸异常。
【完成判据】UNX-F4-E086-J1 要求：三超时档三错误码对齐 10/10 次成文，各档超时实测值与协议常数一致；注入裸码（转发层把结构化错误压成通用失败）10/10 次被回传校验拦截，消费方收到的必为矩阵内错误码。
【细节补注】「不允许翻译」是错误信息保真的关键防线：历史上中间层压扁错误码是排查地狱的源头，消费方只见「失败」不知为何失败。矩阵化后每个子码对应诊断账的一个查询键，错误码即账目入口，报错到定位一条直线。三档超时的档值按实测画像定：快速档压到交互无感、批处理档放宽到全树扫描从容完成，档值入协议账，改动走版本升级——超时是契约不是旋钮，随意调档就是随意改变消费方的行为假设。Provider 死亡码与 E072 的失效语义严格对齐，两处的「不可用」是同一个码，消费方一套处理逻辑。

**UNX-F4-E087 · 树快照 diff 测试器**

【功能定位】树完整性验收的核心问题是「两棵树一样不一样」：回归测试比对新旧版本生成的树、收口核对树副本与源树。diff 测试器输入两份树快照，输出结构级差异报告：增了哪些节点、删了哪些、挪了哪些、属性变了哪些。它解决的是树一致性判断的机械化，一致性从肉眼比对变成断言。
【实现机制】快照格式：全树先序遍历的节点序列，每节点含 ID、父 ID、类型、核心属性摘要。diff 算法：按 RuntimeID 对齐两序列（ID 稳定性是 E062 的直接受益者），对齐后逐节点比对属性摘要，输出四类差异清单（增/删/移/变）。假同防护：快照带全量节点计数与哈希头，计数不符直接报告结构性差异，防止漏遍历造成的假「相同」。
【完成判据】UNX-F4-E087-J1 要求：两时刻树快照结构 diff 报告 10/10 次成文，差异清单与实际变更操作逐条对应；注入假同（快照漏采一半节点但哈希头保留原计数）10/10 次被计数比对识破，报告「快照不完整」而非「无差异」。
【细节补注】哈希头比对是「相同」结论的前置闸门：只有计数与哈希双合才允许输出「零差异」，漏采快照在计数关就被打回——「看起来一样」与「验证过一样」在机制上分开。差异报告按先序位输出，与树的可视化遍历顺序一致，人读报告时脑内树形与报告行序对应，审查效率高一截。diff 器是 E118 回归账与 E089 一致率断言的共同底座，一器三用（diff、回归、断言），它的正确性被更高阶的「已知差异样本集」回归看护。

**UNX-F4-E088 · 20 场景探针集（对话框/多文档/属性页/列表）**

【功能定位】树完整性要有真实场景的检验场：20 场景探针集覆盖对话框、多文档窗口、属性页签、虚拟化列表等典型界面形态，每场景自动构建界面、遍历树、跑三账断言（结构一致、属性齐备、事件零丢失）。它解决的是「测什么」的覆盖问题——探针集是树完整性的标准考卷，场景清单冻结，漏测即账面可见。
【实现机制】探针框架三件套：场景构建器（按场景脚本搭建界面与控件树）、遍历驱动（三向导航全树走查）、断言器（三账机械校验）。场景清单为冻结账：20 场景各有编号、脚本、预期树画像；新增场景走清单追加不许原地改。探针运行账记录每场景每断言结果，收口对表按清单号逐一核对。
【完成判据】UNX-F4-E088-J1 要求：20 场景三账断言全过 10/10 次成文，全场景账齐备；注入场景漏测（账面删一个场景行）10/10 次被对表拦截，收口报「场景 N 未跑」。
【细节补注】场景清单冻结与「补场景走追加」的组合是账目纪律的又一例：历史场景永不改写，新场景编号新增，回归对照时旧场景跨版本可比。虚拟化列表场景是探针集里最刁的一条——只实例化可视区项的列表，读屏器要求「逻辑全树可见」，探针专门验证虚拟化 provider 的逻辑树完整性，这类场景靠临场想测是想不到的，冻结清单的价值正在于此。10/10 次的重复次数设定与全卷判据口径一致，重复跑 revealing flaky：单场景偶发失败在十连跑里无处藏身。

**UNX-F4-E089 · 树结构一致率 100% 断言**

【功能定位】「UIA 树结构 = 控件结构」是 Provider 质量的硬指标：应用里的每个真实控件都应在 UIA 树里有对应节点，树里也不该有多余节点。一致率 100% 断言把这条等式机械化：构建器按控件真实清单生成期望树，与 UIA 树 diff，零差异才放行。它解决的是「树没有说谎」的机械保证——多一个少一个都算不一致，没有容忍度。
【实现机制】断言器输入：期望树（控件本体清单投影）与实测树（UIA 遍历快照）。比对走 E087 diff 器，零差异为过；差异输出为「多节点/缺节点/错位」三分类清单。断言禁止漂移容忍：任何差异都是失败，不设「99% 也行」的放水阈值。断言结果入批账，收口对表。
【完成判据】UNX-F4-E089-J1 要求：树结构=控件结构自动比对 10/10 次成文，标准样本全过；注入漂移容忍（试图以「差异 1 个可忽略」配置放行）10/10 次被断言器拒绝——容忍配置项不存在，改断言器代码才可能放水，而断言器代码改动被批哈希链条捕获。
【细节补注】「容忍配置项不存在」是这条判据的精髓：防放水不靠纪律靠结构——想放水就得改断言器本体，改本体就动批哈希，动哈希就进回归 diff，放水的成本被拉高到与「老实修树」相当。100% 的苛刻有它的道理：树缺一个节点，读屏器就漏读一个控件，对盲人用户那就是一个摸不着的按钮——在无障碍语境里，99% 的树等于「有个按钮时有时无」，不可接受。三分类清单让修复有方向：缺节点查投影遗漏，多节点查虚拟节点泄漏，错位查父子挂接顺序。

**UNX-F4-E090 · 核心属性齐备率 100% 断言**

【功能定位】与 E089 的结构等式并列的属性等式：每个节点的 30 核心属性按三级规则（必填/按型必填/可选）全数齐备。齐备率 100% 断言逐节点逐槽扫描，缺必填即失败。它解决的是「树不但结构对，每个节点的内容也全」——结构对了属性缺着，读屏器朗读时会说出「按钮，无名称」这样的残句。
【实现机制】扫描器复用 E063 的三级规则引擎：必填槽缺失即失败记录；按型必填按节点 ControlType 查类型规则表核对；可选槽缺省记 INFO 不算失败。扫描输出逐节点报告，失败记录带节点 ID、槽位、规则级别三要素。断言阈值与 E089 同款零容忍，齐备率计算式为机械统计，扫描器本体入批哈希。
【完成判据】UNX-F4-E090-J1 要求：逐节点属性齐备扫描 10/10 次成文，标准样本集齐备率 100%；注入缺省冒充（给缺失槽填空串冒充「有值」）10/10 次被类型规则识破——必填槽的空串按「缺失」论处，冒充无效。
【细节补注】空串冒充是属性造假的经典手法：「Name 存在但为空」与「Name 缺失」对读屏器都是残句，规则引擎把空串、空集合、全零矩形这类「形式在场、语义缺席」的值统一按缺失论处，造假面被堵死。可选槽记 INFO 不算失败的分级与 E063 一致：把可选属性拉进失败线会让「不支持某属性」的合法语义无法表达，分级保住了表达力。扫描报告按节点 ID 排序，与 E089 的结构报告同批出账，修复者一次看全「结构账+属性账」两份体检单。

**UNX-F4-E091 · 事件零丢失全程比对账**

【功能定位】E077 的比对器产出即本条的比对账：订阅期全程「发生数=收到数」的报告账目，按事件类别分列、按时段切片、缺口定位到序号。它解决的是零丢失判据的「成文」问题——比对器在跑是过程，账面成文是判据；没有账的零丢失只是口头禅。
【实现机制】账目结构：每订阅期一份报告，含四段——期元数据（起止时刻、订阅者、三类事件订阅参数）、分列统计（结构/属性/焦点三类各发生数与收到数）、缺口明细（缺号、重号、乱序清单，每条带前后序号上下文）、结论（断言过/不过）。报告落回归账体系，批收口对表调阅。报告生成自动触发于订阅注销时，全程无人工参与。
【完成判据】UNX-F4-E091-J1 要求：订阅期全程比对报告 10/10 次成文，正常期结论全过；注入抽样冒充全程（只比对 10% 时段但报告写「全程」）10/10 次被期元数据核对识破——报告的时段切片数与订阅期实测时长不符，「全程」结论被拒。
【细节补注】抽样冒充是「零丢失」造假的最隐蔽手法：比对器全跑但报告只挑好的时段写，防线在期元数据的机械核对——订阅起止与切片覆盖率的对账让「全程」二字有数学定义（覆盖率=100%），冒充在算术上不可行。缺口上下文（前后序号在场）让「丢了什么」可以推理：丢的 47 号若处在结构事务中间，大概率是事务投递 bug；孤立缺口更像队列背压 residue。报告账按批哈希入链，历史订阅期的结论不可事后篡改，回归对照的信任基础由此建立。

**UNX-F4-E092 · 读屏器样本消费演练**

【功能定位】Provider 与 Client API 全部就绪后，最终检验是「真的读屏器用法能不能用」：本条实现一台模拟读屏器，按真实读屏器的行为画像（线性浏览、层级跳转、控件内细读、表格单元格导航）遍历三栈窗口（原生、Wine、AT-SPI 翻译源）。它解决的是「API 对」与「好用」之间的验证缺口——接口测试过不等于消费体验对。
【实现机制】模拟器按行为画像脚本驱动：画像含操作序列模板（浏览节奏、回退频率、缓存批量画像）与超时假设（读屏器等待响应的上限）。三栈窗口各建标准样本（同构控件清单三源实现），模拟器逐一走查，走查路径覆盖树全节点。中断恢复画像：模拟遍历中随机暂停再续，验证树副本续接正确。
【完成判据】UNX-F4-E092-J1 要求：模拟读屏器遍历三栈窗口 10/10 次成文，三栈走查路径全覆盖、响应时延满足画像超时假设；注入遍历中断（遍历中途树结构变更）10/10 次按中断恢复语义正确续接或显式重启遍历，不产生假路径。
【细节补注】三栈同构样本是翻译层质量的对考题：同一份控件清单在原生、Wine、AT-SPI 三源各实现一遍，走查结果逐项对齐——翻译层任何一个源的语义偏差在同构对考中现形。中断恢复画像来自真实读屏器的行为：用户按键是随机的，遍历被打断是常态而非异常，续接语义（哪些节点重查、哪些信缓存）是体验的关键细节，画像脚本把它固化成可回归的断言。响应时延画像让「流畅」有了数：画像超时假设取自真实读屏器的等待阈值，Provider 响应超阈值在演练账即记为不过，不用等用户抱怨。

**UNX-F4-E093 · 放大镜语义（焦点/光标跟踪源）**

【功能定位】放大镜用户靠两类事件驱动视图跟随：焦点跟踪（焦点到哪放大哪）与文本光标跟踪（编辑光标到哪放大哪）。本条实现双跟踪事件源：焦点事件复用 E075 通道，文本光标事件走 caret 报告（E108）的语义面。它解决的是「视图跟着操作走」的事件供给，丢一条跟踪事件，放大镜就停在上一处，用户眼前画面与实际操作脱节。
【实现机制】双跟踪事件统一为「跟踪事件包」：焦点包（节点 ID+屏幕矩形）与光标包（文本范围+光标矩形）同构，消费方一套处理逻辑。事件走高优先级白名单通道（与焦点同级，不过去抖）。位置语义：矩形为全局屏幕坐标，多显示器下带显示器标识。丢失防护：跟踪事件带递增序号，消费方检缺号即知有丢，触发主动重查当前焦点/光标位置对账。
【完成判据】UNX-F4-E093-J1 要求：焦点/文本光标双跟踪事件 10/10 次成文，事件位置与实测焦点/光标位置一致；注入丢跟踪（静默丢弃一条跟踪事件）10/10 次被消费方序号检缺捕获，主动重查对账后视图追平真实位置。
【细节补注】序号检缺加重查对账是「丢失自愈」设计：事件通道做到极低丢失率，但放大镜的体验底线是「永远跟得上」，纯防丢无法到 100%，自愈路径补上最后一段——丢一条事件的最坏后果是一次额外查询，不是视图卡死。光标事件与 E108 caret 报告共用位置计算源，两处矩形永一致，放大镜与读屏器对「光标在哪」不会有两种答案。多显示器标识是 Varix 多屏合成的直接受益：跨屏拖窗时的跟踪连续性在演练里专项验证，屏幕边界两侧的事件流不断档。

**UNX-F4-E094 · 自动化测试消费 UIA 树（O3 公共接口）**

【功能定位】UIA 树除了服务读屏器，还是自动化测试的公共驱动接口（O3 公共接口口径）：测试机器人定位控件、读状态、触发动作全走 UIA。本条固化这一用途的接口稳定性：测试机器人经 UIA 驱动 20 标准控件，驱动语义与读屏器消费同源。它解决的是「测试驱动与用户无障碍走同一条路」——测试过的就是用户用的，不存在「测试专用后门」。
【实现机制】驱动面三动作与 Client API 一一对应：定位（E081 条件搜索）、读态（属性批量抓取）、触发（Invoke/Value/Toggle 模式调用）。测试机器人库封装 20 标准控件的驱动模板（「点这个按钮」「断言这个复选框为 On」），模板入账冻结。驱动失稳防护：模板调用全部带超时与错误码处理（E086 矩阵），失败显式上抛不静默重试。
【完成判据】UNX-F4-E094-J1 要求：测试机器人经 UIA 驱动 20 控件 10/10 次成文，全部模板动作成功且状态回读一致；注入驱动失稳（Provider 响应延迟超快速档超时）10/10 次按错误码矩阵显式失败上抛，不出现无限等待或假成功。
【细节补注】「同一套接口」的深层价值是双向质检：UIA 树若有缺陷，读屏器用户先撞上，测试机器人也会撞上——测试全绿等于替无障碍做了一轮回归，无障碍缺陷在测试期暴露的概率因共用而放大。显式失败不静默重试是测试可信度的底线：静默重试会把「偶发慢」掩盖成「测试通过」，缺陷延后到用户侧爆发；上抛策略让 flaky 测试当场现形，逼着修根因。20 控件模板与 E102 起的投影器控件族一一对应，投影层加新控件族时驱动模板同步追加，驱动覆盖面与投影覆盖面账面对账，不出现「投影了但测不了」的空档。

**UNX-F4-E095 · 树完整性账导出（开放格式）**

【功能定位】三账（结构账、属性账、事件账）的验收报告要能出系统：交付存档、跨团队审阅、外部审计。本条实现开放格式导出：三账汇总为 JSON 结构，含版本号与回读校验，导出物可被独立工具回读验证。它解决的是账目的「可携带性」——账在自己系统里是账，导出去还是账，不是需要本系统才能解读的黑盒。
【实现机制】导出器按账类汇总：结构账出树快照序列（E087 格式）、属性账出齐备率报告、事件账出 E091 比对报告，顶层包版本号、生成时刻、全包哈希。回读器实现反向校验：格式解析、哈希复算、账内自洽（计数、序号链）三查。导出与回读共享同一格式定义常量，格式演进走版本号。
【完成判据】UNX-F4-E095-J1 要求：三账 JSON 导出可回读 10/10 次成文，回读校验三查全过、内容与源账逐条一致；注入坏导出（导出后被篡改一条记录）10/10 次被哈希复算识破，回读拒绝并定位篡改。
【细节补注】全包哈希让导出物有了防篡改指纹：审计方拿到导出文件，回读器一跑即知「这份账是不是导出时的原样」，账的司法级完整性由一次哈希复算确立。格式开放的含义是格式定义随导出物走（顶层嵌格式说明与版本），不依赖外部文档对齐——半年后的审阅者拿当年导出物即知当年格式，自描述是对抗时间的设计。回读器与导出器互为测试：导出必回读、回读必比对，双向流水线是账目出口的常设质检，不是发版前的一次性动作。

**UNX-F4-E096 · 性能：万节点树查询 P95**

【功能定位】大应用的控件树轻松过万节点（大型表格、复杂属性页），树查询性能直接决定读屏器在大应用里是否可用。本条立性能账：万节点树的标准查询集（全树遍历、条件定位、批量属性抓取）P95 延迟上账，阈值设卡。它解决的是性能从「感觉流畅」到「数字达标」的问题，回退有账可查。
【实现机制】基准集三类：全树遍历（万节点走查）、定位（谓词树条件下 Descendants 搜索）、批量抓取（单节点 30 属性整批）。测量口径：P95 与 P99 双分位，计时点在 Client API 入出口（含跨进程往返），环境锁定为基准机配置。阈值入协议账，超阈即断言失败。回归比对：每次跑基准与上次账对比，回退超 5% 记警。
【完成判据】UNX-F4-E096-J1 要求：万节点查询 P95 ≤ 阈值账 10/10 次成文，三类基准全过且分位数据入账；注入性能回退（在 Provider 侧植入人为延迟）10/10 次被阈值断言拦截，基准失败定位到植入的延迟段。
计时点选 Client 入出口是「用户感知口径」：Provider 内部再快、跨进程慢了也是慢，性能账必须量消费者感受到的那段。
【细节补注】P95 配 P99 双分位是防「平均数骗人」：P95 达标但 P99 爆表意味着多数流畅、偶发卡顿，读屏器场景的偶发卡顿恰是最伤体验的形态，双分位让长尾无处藏。5% 回退警线的意义在于趋势管理：单次小回退不致命，连续多批单向下行就是劣化趋势，警线让趋势在早期可见。基准环境锁定与记录（机型号、负载状态）随账导出，跨期比对的环境差异因此可判，不会把环境噪声误读为代码回退。

**UNX-F4-E097 · 死循环树防护（深度上限）**

【功能定位】恶意或故障的 Provider 可能构造超深树（几万层嵌套），消费方递归遍历即栈溢出，环形引用更是直接死循环。本条立深度上限防线：构建期超深树拒绝入表，遍历期栈深监控兜底。它解决的是「树形态的安全边界」——正常的树再复杂也在百层内，超深必是异常，异常要在出生时被拒。
【实现机制】构建期：树校验器（E061 四步之校验步）带深度上限检查，DFS 染色遍历同时测深，超限整树拒绝。上限值为协议常数（覆盖全部合法界面形态的十倍余量）。遍历期：E082 深度优先遍历器带栈深断言，异常超深即中止遍历并落账（防御纵深：构建期漏网的动态超深在遍历期被截断）。深度信息进自省节点，大树大深应用可见。
【完成判据】UNX-F4-E097-J1 要求：构建期超深拒绝 10/10 次成文，注入的深树攻击（万层链表式树）全部在校验步被拒、零入表；深树攻击注入同时覆盖环加深的复合形态，复合攻击同样拒绝。
【细节补注】「十倍余量」的上限定值经过合法界面形态普查：最深的真实树（嵌套属性页加表格）实测不过几十层，千级上限留十倍余量，合法树永远够不着上限，够得着的都不是合法树——这条定值逻辑让「拒绝超深」不误伤。复合攻击（环加深）的覆盖来自实战推演：单防深或单防环都有绕法，两者叠加的构造才是真实攻击形态，校验器的染色遍历对两类异常一次遍历同查。深度自省让运维能发现「贴近上限的异常生长」——某应用树深逐版本上探，在撞线前就有账可查，防线上于未然。

**UNX-F4-E098 · UIA 与 vxwm 聚合（三源树统一）**

【功能定位】Varix 界面三源并存：原生进程、Wine 承载的 Windows 应用、AT-SPI 翻译源。三源各说各的协议，读屏器只认统一模型。本条实现三源树在 vxwm 合成器层的聚合：三源各自翻译到统一节点表，聚合点拼装全系统树。判据锚定「三源翻译同模型」。它解决的是「读屏器一次学习处处可用」——不管窗口来自哪个世界，无障碍体验一致。
【实现机制】三翻译器同规格：原生翻译器（进程内直接建表）、Wine 翻译器（Windows 侧 MSAA/UIS 视图映射，复用 E078 兼容层）、AT-SPI 翻译器（Linux 语义映射）。三翻译器输出同一节点表契约（E061 总纲），聚合点按挂接点拼树（E065 协议）。翻译器间零交叉引用：任何源不得读另一源的表，全部经聚合视图。
【完成判据】UNX-F4-E098-J1 要求：原生/Wine/AT-SPI 三源翻译同模型 10/10 次成文，同构样本三源走查结果逐项一致；注入双树分裂（某源绕聚合点私建视图直供消费方）10/10 次被消费方来源校验拒绝——消费方只信聚合点，私树不可达。
【细节补注】同构样本对考（与 E092 共用样本集）是三源统一的质量测震：同一控件清单三源各译一遍，走查属性逐槽对齐，哪个源译歪了当场现形——翻译器的回归测试因此有了永久基准。零交叉引用是架构卫生：翻译器互读会造成「翻译依赖翻译」的脆链，任一源升级牵连全部；各自只对聚合点负责，升级互不相扰。双树分裂的防线放在消费方侧是釜底抽薪：私树建得再好没人信就无人用，消费方来源校验（只认聚合点签发的树引用）让分裂树从商业上死亡，比运行期强拆更彻底。

**UNX-F4-E099 · 内核锚定：UIA 服务状态经 lxprocfs.rs 自省**

【功能定位】UIA 服务的健康度要能从内核侧看到：树规模（全系统节点数、各进程节点数）、事件速率（三类事件每秒峰值与均值）、订阅者状态、管线背压状态，全部经 lxprocfs 自省节点暴露。它解决的是「无障碍设施的可观测性」——读屏器用户报障「读不出来」，运维从自省节点直接看到是树没了、事件堵了还是订阅断了。
【实现机制】自省节点树挂在 lxprocfs 的 uia 段：全局段（总节点数、事件总速率）、per-provider 段（各进程节点数、注册态、失效代数）、per-subscriber 段（各订阅者队列深度、背压计数、配对状态）。数据源直读各账（E076 队列账、E065 注册账），只读映射，自省本身零干预语义。节点更新与账目更新同源同步，自省读到的是账面事实的视图不是独立采集的第二份真相。
【完成判据】UNX-F4-E099-J1 要求：树规模/事件速率节点可读 10/10 次成文，读数与账面实测一致；注入节点失真（自省数据与账面不一致）10/10 次被同源比对识破——自省视图与源账定期校验哈希，失真即告警。
【细节补注】「同源不是第二份真相」是可观测性的原则性设计：自省数据若独立采集，采集器自身故障会造成「账实不符」的假象，排障时先怀疑系统还是先怀疑仪表是经典两难；同源设计让仪表必然反映账面，仪表异常只有一种解释——账面写路径有问题，排障方向唯一。自省节点命名与账目键一一对应，报障者引用节点路径即可在诊断账精确对上记录，沟通零损耗。per-subscriber 段让「哪个读屏器拖累了系统」有账可查：队列深度与背压计数按订阅者分列，慢消费方的性能影响被定量而非定性。

**UNX-F4-E100 · E05 批收口与批账锁定**

【功能定位】E05 批 20 条（E081–E100）的批级收口：判据对表 20/20、编号连续零重号扫描、批哈希锁定入链。与 E080 同构的完整性闸门，作用在 Client 侧与探针批。它解决的是批的交付质量机械化确认——Client 侧 20 条判据一条不缺、一号不重，批哈希入链后进入只读期。
【实现机制】收口三步与 E080 同构：对表（逐条调验 J1 记录）、编号扫描（E081–E100 连续性）、批哈希（20 条判据记录拼接哈希与前批链接）。本批特殊点：探针集（E088）与断言器（E089/E090）的样本集账同步入批哈希——样本集是后续批次的测试基准，其版本随批冻结，后续批引用时版本明确。
【完成判据】UNX-F4-E100-J1 要求：20 条判据对表 20/20 成文、编号连续零重号 10/10 次扫描通过、批哈希与前两批链条校验一致；注入短判据（删一条 J1）10/10 次被对表拦截并定位缺号。
【细节补注】样本集随批冻结是本批收口的增量设计：E088 的 20 场景、E089 的期望树、E096 的基准阈值全在批哈希保护下定格，后续批次（E06 投影器批）引用这些基准时，引用的是「哈希锁定的那版」，基准漂移引发的假回归从机制上排除。批链校验验到前两批，说明收口器的链条逻辑在多批场景下稳定——链条越长校验成本越高，本批起链条校验用增量尾验（只验前一批链接哈希），全链校验留给重大节点（卷收口）执行，成本与保障平衡。收口报告新增「基准引用清单」，登记本批对外引用的既有基准及其批哈希，跨批依赖显式化。

## E06 批 · Win32 标准控件族 → UIA 自动投影（E101–E120）

**UNX-F4-E101 · 投影器总纲（消息语义反推）**

【功能定位】Wine 承载的 Windows 应用说 Win32 协议：控件存在即窗口消息，没有原生 UIA Provider。投影器干的事是「反推」——旁听控件的窗口消息流（创建、销毁、状态变更、值更新），把消息语义自动翻译成统一节点表的投影节点，让 Windows 老应用的控件树自动出现在读屏器面前。判据锚定「Win32 控件消息→UIA 节点自动投影」。它解决的是存量 Windows 应用的无障碍冷启动问题：应用不改一行代码，无障碍能力白得。
【实现机制】投影器结构三段：消息监听器（Wine 侧挂钩窗口过程旁路，只读旁听不拦截）、语义翻译器（消息到节点事件的翻译表，控件类×消息号冻结映射）、投影维护器（按翻译结果增删改统一节点表的投影段）。未知控件类处理：翻译表查无此类，显式登记缺口账（类名、消息样本、时间），绝不猜测投影——「不覆盖就明说」。
【完成判据】UNX-F4-E101-J1 要求：Win32 控件消息→UIA 节点自动投影 10/10 次成文，标准样本应用树与原生实现等价；注入未知类（自定义窗口类冒充标准控件）10/10 次显式登记缺口不冒充，账面可查「类 X 未投影及原因」。
【细节补注】「反推」的边界讲清楚：投影器只知道消息语义能推出的部分——按钮被按下（BN_CLICKED）、文本变了（EN_CHANGE），但控件私有绘画语义推不出来，这部分由 E114 缺口账诚实兜底。只读旁听是安全底线：投影器永不改消息流，应用行为零影响，监听器故障最多投影缺位，绝不变脏应用。翻译表冻结加版本号，Wine 侧消息语义升级走表升级不改代码，投影器对消息协议演进有弹性。投影段在节点表带「投影」来源标记，与原生节点账面可分，排障时「哪段是翻译出来的」一眼可辨。

**UNX-F4-E102 · button 族投影**

【功能定位】button 族是 Windows 应用最高频控件：push button（按压钮）、checkbox（复选框）、radio button（单选钮）三型。投影器把 button 类窗口消息翻译成统一树节点：ControlType 按型区分（Button/CheckBox/RadioButton），模式按型挂接（Invoke 全有、Toggle 归 checkbox、Selection 语义归 radio 组）。它解决的是「最常见控件的无障碍正确性」，读屏器用户在每个对话框都要面对它们。
【实现机制】三型投影各自有型模板：push（ControlType.Button+Invoke，BN_CLICKED→Invoke 语义）、checkbox（ControlType.CheckBox+Toggle，BM_SETCHECK/BN_CLICKED→ToggleState 回写与切档）、radio（ControlType.RadioButton，组容器投影为 Selection 容器、组内单选态按 BM_SETCHECK 翻译）。型判定按窗口类名加风格位（BS_CHECKBOX/BS_RADIOBUTTON 等）双因子，双因子不一致按保守降级并落账。
【完成判据】UNX-F4-E102-J1 要求：push/checkbox/radio 三型树与模式 10/10 次成文，三型样本投影后过型模板断言（类型、模式、状态语义逐项对）；注入型混淆（radio 风格贴 button 类名）10/10 次被双因子校验识破，按保守降级处理并落账。
【细节补注】双因子判定是反仿冒设计：窗口类名可自报、风格位也可自报，但两者一致才高置信——恶意应用造一个类名叫 button 的非按钮窗口，投影器按降级处理只给基础节点语义，不冒充 Toggle/Invoke，读屏器不会被骗出错误操作。radio 组容器是翻译增构：Win32 的 radio 组是风格位约定的逻辑组，没有真实容器窗口，投影器按 WS_GROUP 边界合成 Selection 容器节点——这一步是纯翻译增构，组语义在原生树里不存在，投影后才有，账面标注「合成节点」。ToggleState 与 BM_GETCHECK 三态（未选/已选/半选）直接对位 E070 档位表，三态 checkbox 一路畅通。

**UNX-F4-E103 · edit 族投影**

【功能定位】edit 族是文本输入的入口：单行框、多行编辑器、密码框三型。投影把 WM_GETTEXT/EN_CHANGE 等消息语义翻译为 Value 模式节点，读屏器才能朗读输入内容、自动化测试才能填表单。密码型是本条的红色专项：Value 模式存在但明文永不回读。它解决的是「输入类控件的读与写」在翻译层的正确与安全。
【实现机制】三型模板：单行（ES_PASSWORD 缺省单行语义）、多行（ES_MULTILINE，文本范围语义启用）、密码（ES_PASSWORD 风格，GetValue 返回占位「已输入 N 字符」，明文翻译层即截停）。值同步：EN_CHANGE 消息驱动属性失效（E064 管线），下次读取回源 WM_GETTEXT。文本范围接口（多行选区、光标位）经 EM_ 消息族翻译，为 E108 caret 语义供位。
【完成判据】UNX-F4-E103-J1 要求：单行/多行/密码型 Value 模式 10/10 次成文，非密码型取赋值与控件实测一致、多行范围语义正确；注入密码泄文（构造读屏请求索取密码框明文）10/10 次被密码路径截停——翻译层返回占位，明文在 Wine 进程内不出境。
【细节补注】密码截停放翻译层而不是消费方自觉，是纵深防御的落位：就算未来某个消费方实现有 bug 想要明文，翻译层物理上不给——明文出境的路径在架构上不存在，与 E079 隐私红线（账面零明文）首尾呼应，密码的生命周期被压在「应用进程内存」内。EN_CHANGE 驱动失效与 E074 属性事件同管线，读屏器的值朗读实时性与原生 Provider 一致。多行文本的范围语义（总行数、选区起止）是读屏器「按行朗读」与放大镜光标跟随的基础数据，EM 消息翻译的边界情况（软换行与硬换行差异）在账面有专项记录，是已知翻译近似的诚实登记。

**UNX-F4-E104 · list 族投影**

【功能定位】list 族承担选择类交互：列表框（单选/多选）、及同理翻译的虚拟列表变体。投影产出 Selection 容器加子项节点的树形，选中态按 LB_* 消息族翻译，滚动语义按可见范围翻译。判据锚定「项列表/选中集/滚动语义」。它解决的是列表类控件「看着有、选得对、滚得动」的三件事，读屏器在列表里「逐项浏览+朗读选中」全靠这条投影。
【实现机制】容器模板：list 窗口投影为 Selection 容器节点，LB_GETCOUNT/LB_GETTEXT 翻译为子项枚举，LB_GETSELCOUNT/LB_GETSELITEMS 翻译为选中集（E069 双写同步语义），LB_GETTOPINDEX 与可见区尺寸翻译为滚动语义属性。子项按需投影：项多时按可见窗口懒投影（虚拟化翻译），滚动驱动可见集更新。虚项防护：枚举计数与实际取项一致性校验，计数与可取项不符即翻译异常落账。
【完成判据】UNX-F4-E104-J1 要求：项列表/选中集/滚动语义 10/10 次成文，样本列表投影后选中集操作与控件实测一致、滚动后可见项集更新正确；注入虚项（消息层谎报计数但取项越界）10/10 次被一致性校验识破，投影异常落账不产出坏节点。
【细节补注】懒投影是万项列表的性能保命设计：十万项的列表全量投影是读屏器的灾难也是投影器的灾难，按可见窗口投影让树规模与可视规模同阶，滚动事件驱动增量更新，E073 结构事务把一次滚动的增删打包为单一事务，读屏器视图平滑跟随。虚项防护针对的是消息层谎报：恶意应用让 LB_GETCOUNT 返回十万但 LB_GETTEXT 全部越界，投影器的一致性校验让这类攻击变成显式翻译异常而不是无限重试或产出占位垃圾——「不产出坏节点」是投影器对所有控件的统一承诺。多选列表的选中集翻译与 E069 容器语义严格同构，读屏器在原生与投影列表里听到同样的选中播报。

**UNX-F4-E105 · combobox 族投影**

【功能定位】combobox 是「输入框加下拉列表」的复合控件，投影最难的一点是树形态动态：收起时是一个编辑框加一个按钮，展开时多出一个列表区。判据锚定「展开态树动态增删」。它解决的是复合控件投影的树一致性——展开收起瞬间树要正确增删子树，读屏器不能在展开瞬间读到幽灵节点或漏掉列表。
【完成判据】UNX-F4-E105-J1 要求：展开态树动态增删 10/10 次成文，展开收起循环后树形态断言全过、列表子树完整；注入展开竞态（展开请求与收起请求间隔毫秒级交叠）10/10 次按事务序终态正确，树无中间态残留。
【实现机制】复合模板：combobox 窗口投影为容器节点，编辑区与下拉按钮为常驻子节点，下拉列表区为条件子树——CBN_DROPDOWN 消息触发列表子树挂入（结构事务包），CBN_CLOSEUP 触发摘除。竞态防护：展开收起走状态机（收起→展开中→展开→收起中），竞态请求按终态合并，结构事务按状态机终态投递，不投中间态。

**UNX-F4-E110 · 控件销毁节点回收**

【功能定位】控件关了、窗口销了，投影节点必须跟着摘树，且摘得干净：节点回收、引用失效、事件广播三件事一次做齐。判据锚定「销毁即摘树、引用惰性失效」。它解决的是投影树的垃圾回收问题——回收不干净就是僵尸节点，读屏器朗读一个已关闭的窗口是幻觉，自动化测试对一个幽灵按钮断言是事故。
【实现机制】销毁钩子：WM_DESTROY 消息族触发投影摘除，摘除走 E073 结构事务（删事件），节点槽回收进空闲链，RuntimeID 作废不复用（E062 语义）。引用惰性失效：摘除时物理槽立即回收，但消费方手里的旧引用按失效代数惰性判死（E072 同款代数机制），查询旧引用得 ELEMENTNOTAVAILABLE。摘除与回收原子：摘树事务提交即槽回收，无中间态。

【细节补注】「物理立即、逻辑惰性」的双层设计兼顾了内存效率与引用安全：槽位立即回收不给僵尸留物理空间，旧引用走代数判死不要求消费方即时放弃持有——读屏器正朗读着的引用在控件销毁瞬间不会野指，得到的是干净的「不可用」。销毁钩子只认 WM_DESTROY 族不认 WM_NCDESTROY 之外的近似消息，钩子语义在翻译表冻结，销毁误判（把隐藏当销毁）在翻译表版本演进中被专项修过一次并记入账目——投影器的翻译表历史就是一部语义勘误史，勘误记录是账目资产。摘除事务与 E111 的创建事务对称，树的生命周期事件两端都有完整账。

**UNX-F4-E112 · 控件状态变更属性同步**

【功能定位】控件的 enable/check/文本/选中态在运行期不断变化，投影节点属性必须即时跟随。判据锚定「enable/check 变更即时反映」。它解决的是投影树的「活性」——树不是建完就死板的快照，是与控件同呼吸的活映射，读屏器任何时候读到的状态都是此刻的状态。
【实现机制】状态消息翻译表：BM_SETCHECK→ToggleState 失效、WM_ENABLE→IsEnabled 失效、EN_CHANGE→Value 失效，翻译到节点属性槽精确置脏（E064），失效事件经 E074 管线广播。同步时序：消息到达即置脏并广播，属性值在消费方回读时回源控件（懒取值），广播的是「变了」事实与新旧摘要。批量状态变更（对话框初始化一次设十几个控件）按消息序逐条广播，不合并——状态事件语义敏感走白名单。
【完成判据】UNX-F4-E112-J1 要求：enable/check 变更即时反映 10/10 次成文，变更后回读值与控件实测一致、事件时序与消息序一致；注入陈旧状态（回读命中未失效缓存）10/10 次被失效管线拦截，回源拿到新值。
【细节补注】「广播变了、回读才取值」的推拉结合是活性与成本的平衡：状态事件只说「IsEnabled 变了」，不带新值，消费方关心才回读——事件包轻、值按需取，风暴期的带宽压力小一半。逐条不合并的决策与 E074 的值类去抖相反，理由是语义差：enable/check 是离散语义状态（读屏器要逐次播报），进度条值是连续量（可合并），同管线不同类别不同策略，翻译表按类别标注。时序一致性断言（事件序=消息序）防的是翻译器的乱序 bug，投影器的单线程处理循环保证序，断言是看护不是机制，机制与看护分离。

**UNX-F4-E113 · 投影器与 AI-19 消息语义接口（冻结面）**

【功能定位】投影器旁听的消息语义依赖 AI-19 承建的 Wine 消息语义接口（冻结契约面）：翻译表引用的消息号、语义约定全部锚定该接口的冻结版本。判据锚定「消息面 fake 联测」。它解决的是跨工位（AI-29 投影器 × AI-19 消息接口）的契约纪律——接口冻结面任一侧变更必须双签 ADR，单侧漂移在联测即被拦截。
【实现机制】契约版本机制：投影器翻译表声明所依赖的接口契约版本（v1），联测时投影器与接口侧 fake 实现按同版本对跑。fake 联测：接口侧提供 fake 消息源（可编程的消息序列发生器），投影器对 fake 序列的翻译产物与预期树逐槽断言。漂移检测：契约哈希（消息号表加语义注释）双端各存一份，联测期比对，不一致即拒绝联测并告警。

【细节补注】契约哈希双存比对是「冻结」的机械含义：冻结不是口头约定不改动，是改动必留痕必双签——哈希不一致时联测根本不启动，漂移的接口连被测资格都没有，倒逼变更走 ADR 流程。fake 消息源是联测的效率工程：不需要真 Windows 应用，可编程序列能构造真实应用难凑齐的边角序列（半初始化对话框、销毁中的菜单），边角覆盖比真实场景联测更狠。契约版本升级路径明确：v2 发布时 v1 并行维护一个过渡期，投影器按声明版本各对各的 fake，双版本联测共存让升级不再是切换悬崖。

**UNX-F4-E114 · 自绘控件缺口显式登记账**

【功能定位】自绘控件是投影器的天然盲区：应用自己画按钮自己处理输入，不走标准控件消息，消息语义反推不出来。本条立缺口登记账：凡投影器无法覆盖的控件（自绘、私有类、语义不可推），显式登记「控件类、所属应用、不可投影原因、登记时点」，绝不冒充覆盖。判据锚定「不覆盖控件清单与原因」。它解决的是覆盖范围的诚实性——账面清楚哪些能读哪些不能读，缺口才有催改与规划的依据。
【实现机制】登记路径双通道：被动登记（翻译表查无此类自动落账）与主动扫描（应用树扫描发现疑似自绘窗口，按窗口风格与消息特征判定，落账待人工确认）。账目字段：类名、进程、特征摘要、原因分类（自绘/私有框架/消息语义不足）、状态（待确认/确认缺口/已支持）。缺口账与 E101 的未知类注入路径同源，登记即测试路径。
【完成判据】UNX-F4-E114-J1 要求：不覆盖控件清单与原因 10/10 次成文，样本应用的自绘控件全数入账、原因分类准确；注入冒充覆盖（给自绘控件挂标准类名骗投影）10/10 次被消息特征校验识破——类名可冒充、消息行为不可冒充，判定以行为为准。
【细节补注】「行为判定优先于类名」与 E102 双因子一脉相承：冒充者的类名是假的、消息行为也是假的（没有标准控件该有的消息序列），特征校验戳穿双假。缺口账的运营价值在于催改链条：账面按应用聚合排序，缺口最集中的应用成为无障碍适配的优先协商对象——「谁家的盲区最大」有数可依。状态机里「待确认」是诚实的中立态：扫描判定的疑似自绘可能误判，人工确认前不写入「确认缺口」，账目的每个状态都有明确的认识论含义，不把猜测当结论。

**UNX-F4-E115 · 投影性能（百控件窗 ≤ 阈值）**

【功能定位】投影不能拖累应用：一个百控件窗口（复杂属性页、大型列表对话框）的标准投影全流程（监听建树、属性初取、模式挂接）要在阈值内完成，读屏器首次打开该窗口的树构建体验不卡顿。判据锚定「百控件树构建 ≤100ms 账」。它解决的是投影层的性能预算——翻译的便利性不能以无障碍可用性为代价。
【实现机制】性能基准场景：百控件标准窗样本（控件族分布按真实应用画像配比），测量口径为创建消息首条到树就绪事件的全时长，P95 记账。优化路径三板斧：懒属性（初建只取必填八属性，其余按需）、批翻译（同帧创建消息合并处理）、翻译表哈希索引（控件类到模板的查表 O(1)）。回退警线：与 E096 同款 5% 警线，趋势监控。
【完成判据】UNX-F4-E115-J1 要求：百控件树构建 ≤100ms 账 10/10 次成文，P95 达标入账；注入卡顿（翻译路径植入延迟）10/10 次被阈值断言拦截，失败定位到植入段。
【细节补注】懒属性是与 E064 缓存策略的配套取舍：初建期取八个必填属性是读屏器首朗读的最小集，其余属性等真正被问再取——百控件窗初建从「全属性全取」到「必填精取」的实测差是阈值余量的主要来源，性能是设计出来的不是测出来的。100ms 阈值的定值依据是读屏器首朗读的体验窗：用户打开窗口到第一次按键浏览约半秒，树就绪占其中 100ms 是可感但不烦躁的份额。控件配比画像来自真实应用采样，基准窗不是均匀分布的合成样本——button 多 edit 少的真实配比让翻译路径的热点与实战一致，基准测的就是实战跑的。

**UNX-F4-E116 · 投影器异常隔离（单控件失败不拖垮树）**

【功能定位】一个控件翻译出 bug（消息处理崩溃、翻译死循环）不能拖垮整棵投影树——其他几百个控件的无障碍不能陪葬。判据锚定「坏控件跳过+记账」。它解决的是投影层的故障隔离：隔离粒度到单控件，坏一个丢一个、账面记一个，树的整体服务不中断。
【实现机制】隔离单元：单控件的翻译处理包裹在隔离边界内（异常捕获加处理超时），边界内失败的动作：该控件节点跳过（不入树）、缺口账登记（复用 E114 账）、隔离计数递增。熔断语义：同应用隔离计数短窗超限触发应用级降级（整树暂停投影，账面降级记录），防坏应用刷爆翻译循环。恢复路径：降级后应用消息流回正常（隔离计数回落），投影自动恢复。
【完成判据】UNX-F4-E116-J1 要求：坏控件跳过+记账 10/10 次成文，混入坏控件的样本树其余控件全数正常投影；注入连坐（坏控件异常扩散到兄弟节点翻译）10/10 次被隔离边界拦截，兄弟节点照常、坏控件入缺口账。
【细节补注】隔离边界的超时参数与 E115 性能预算联动：单控件翻译正常耗时微秒级，超时取毫秒级宽限，正常控件永远碰不到超时线，碰到的都是真坏。熔断的「应用级降级」是最后一道闸：单控件跳过是精准手术，应用级降级是止血带——用与不用由计数阈值自动判定，不用人工盯着，降级与恢复全留痕。隔离计数也是质量信号：某应用频繁触发隔离，要么是应用行为怪异要么是翻译表对它的类覆盖有 bug，账面趋势指向哪个根因，修复方向跟着账走。

**UNX-F4-E117 · 控件宿主零散件（工具提示/进度条）**

【功能定位】零散件是低频但体验敏感的控件族：tooltip（工具提示，鼠标悬停的小黄条）与 progressbar（进度条）投影。tooltip 投影让读屏器能朗读悬停提示（视觉用户的专属信息，盲人用户理应同等获得）；progressbar 投影供读屏器播报进度（「安装进度 60%」）。判据锚定「tooltip/progressbar 投影」。它解决的是边角控件的无障碍覆盖，覆盖完整度体现工程诚意。
【实现机制】tooltip 模板：TTN_GETDISPINFO/TTM_* 消息族翻译为 tooltip 语义节点（短暂存在的 Popup 型节点），显示即入树（E073 事务）、隐藏即摘树，文本走 E079 隐私口径。progressbar 模板：PBM_SETRANGE/PBM_SETPOS 翻译为 RangeValue 模式节点（最小/最大/当前值三属性），SETPOS 驱动值失效与 E074 事件，值类事件走去抖合并。
【完成判据】UNX-F4-E117-J1 要求：tooltip/progressbar 投影 10/10 次成文，tooltip 显示期树内可朗读、摘除及时；progressbar 值翻译与控件实测一致；注入漏件（tooltip 显示但树无节点）10/10 次被显示摘除配对断言识破，账面可见。
【细节补注】tooltip 的「显示即入、隐藏即摘」与菜单同款瞬态处理，配对断言（每笔显示事务必有对应摘除事务）防的是 tooltip 节点泄漏——小黄条 lifetime 以秒计，泄漏的 tooltip 节点在树上越积越多是慢性病，配对断言是体检。progressbar 走 RangeValue 而非 Value 模式是语义保真：进度条有最小最大范围语义，读屏器播报「60%，区间 0-100」比光秃秃的「60」信息完整，模式选择的语义差异在模板注释里写明。tooltip 文本的隐私口径与 E079 一致：tooltip 可能含路径、用户名等敏感内容，朗读与账面同守红线。

**UNX-F4-E118 · 树投影回归账（样本窗 diff）**

【功能定位】投影器每次升级（翻译表修订、模板优化）都可能有树形态回归：节点型变了、属性槽移了、父子序变了。本条立回归账：样本窗集（覆盖全部控件族的标准窗口样本）的树快照为基准，新版投影产物与基准 diff，零回归放行。判据锚定「样本窗树快照 diff 零回归」。它解决的是投影器演进的安全网——改翻译表不再靠胆子，靠 diff。
【实现机制】基准管理：样本窗集的投影快照随批哈希冻结（复用 E087 快照格式），版本化存放。回归流程：新版投影器对样本集全量重投影，diff 器（E087）逐窗比对，差异三类处理——预期改进（走基准升级，ADR 双签）、意外回归（拦下修复）、噪声差异（环境因素，核对后豁免并登记）。回归账记录每轮 diff 结论与差异处置。
【完成判据】UNX-F4-E118-J1 要求：样本窗树快照 diff 零回归 10/10 次成文，全部样本窗过；注入漂移（翻译表悄悄改一个型映射不升基准）10/10 次被 diff 拦截，差异定位到具体控件与属性槽。
【细节补注】差异三分类的「噪声豁免登记」是回归账不演变成形式主义的关键：真实世界有环境性差异（时序导致的焦点初值不同），一刀切零容忍会把回归账逼成天天豁免的橡皮图章；登记制让豁免本身有账，豁免滥用在账面趋势里可见。基准升级要 ADR 双签与 E113 契约变更同款纪律：「树该长这样」的定义变更必须两个工位都点头，单侧悄悄改基准等于单侧改契约。10/10 次的重复回归跑的是同一基准不同时点，验证的是投影产物的时间稳定性—— nondeterministic 的翻译产物（同输入不同输出）在重复跑里现形。

**UNX-F4-E119 · 内核锚定：投影器事件经内核事件总线**

【功能定位】投影器产生的结构事件、属性事件、焦点事件必须走内核事件总线分发，与原生 Provider 事件同通道同序。判据锚定「事件经内核通道零丢失」。它解决的是事件通路的统一性——投影树的事件若走私有通道，就绕开了 E073–E077 全套事件管线保障（事务、去抖、背压、比对），投影事件必须与原生事件享受同一套基础设施。
【实现机制】通路约束：投影器的全部对外事件经内核事件总线（事件·会话·IPC 通道）发布，发布 API 唯一，旁路路径在代码层不存在。总线侧投影事件带来源标记（投影器 ID），与原生事件同队列同序号链，E077 比对器对投影事件同样全程比对。旁路检测：总线序号链的连续性校验天然覆盖旁路——绕过总线的事件在订阅端的序号链上现缺口。
【完成判据】UNX-F4-E119-J1 要求：事件经内核通道零丢失 10/10 次成文，投影事件过 E077 全程比对；注入旁路（构造绕总线的私发事件）10/10 次被序号链连续性校验识破，私发事件在订阅端无位可落、账面现缺口告警。
【细节补注】「旁路被序号链现形」是结构化防旁路：不靠扫描代码找旁路调用（总能漏），靠总线的序号链数学性质——每条合法事件占链上一号，绕行者无法在不惊动链条的情况下插入事件，私发要么断链要么无处安放。投影事件与原生事件同链同序还有一个消费方价值：读屏器看到的是全系统统一的事件流，不需要区分「这条事件来自原生还是翻译」，消费逻辑零特化。总线发布 API 的唯一性是代码评审红线级约束，评审清单把「投影器事件发布点」列为必查项，机制与纪律双保险。

**UNX-F4-E120 · E06 批收口与批账锁定**

【功能定位】E06 批 20 条（E101–E120）的批级收口：判据对表 20/20、编号连续零重号、批哈希锁定入链。投影器批的收口另有专项：翻译表版本与基准快照版本随批冻结，投影器的后续演进以此为基线。它解决的是投影批的交付完整性确认，与 E080/E100 同构，全卷收口链条的第三环。
【实现机制】收口三步同构执行，批哈希覆盖：20 条判据记录加翻译表版本指纹加样本窗基准版本（E118 冻结版）。链条校验接 E100 批哈希。专项登记：本批对外依赖（AI-19 接口契约版本、E064/E073 管线批哈希引用）列入收口报告的依赖清单——投影器批是全卷依赖最重的批，依赖显式化让未来的依赖侧升级影响评估有清单可循。
【完成判据】UNX-F4-E120-J1 要求：20 条判据对表 20/20 成文、编号连续零重号 10/10 次扫描通过、批哈希链条校验一致、依赖清单齐备；注入短判据（删一条 J1）10/10 次被对表拦截并定位缺号。
【细节补注】依赖清单是本批收口对收口体系的增量贡献：前三批收口验的是「自身齐不齐」，本批起加验「依赖谁、依赖哪版」——投影器批的判据大量引用跨批构件（缓存管线、结构事务、比对器），这些引用的版本锚定让「上游升级要不要回归本批」从拍脑袋变成查清单。翻译表版本指纹入链后，翻译表的任何修订都改变批哈希，修订必走新批修订条目的纪律（E080 已立）在此自然延伸：翻译表的历史演化因此有完整账链，投影器做过的每次语义勘误都可回溯。本批收口后 E04–E06 三批成连续只读链，详解册第二册随之进入整合待命态。
