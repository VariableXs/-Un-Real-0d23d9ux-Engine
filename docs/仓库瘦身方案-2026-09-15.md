# 仓库瘦身方案（2026-09-15）

> 基于实测数据制定。工作区总占用 **27 GB**，但真正的源码只有几十 MB——绝大部分是构建产物、测试产物与历史遗留。以下按「收益大→小」分四步，每步都标注风险与验证方式。

## 一、实测数据（诊断结论）

| 位置 | 占用 | 性质 |
|---|---|---|
| `src-tauri/` | **15 GB** | 几乎全是 `src-tauri/target/`（7900+ 编译中间文件，已 gitignore，纯磁盘垃圾） |
| `kernel/` | **8.2 GB** | `kernel/target/` 与 `userspace/*/target/`（已 gitignore） |
| `_attic/` | **1.7 GB** | 过程产物归档（含截图 png、历史构建产物）；其中 **270 个文件仍被 git 跟踪，共 37 MiB** |
| `code-analysis/` | 1.3 GB | `code-analysis/target/`（已 gitignore） |
| `launcher/` | 182 MB | `launcher/target/`——**历史上曾被提交**，rlib/rmeta 大对象至今留在 git 历史 |
| `node_modules/` | 134 MB | 正常，gitignore |
| `.git/` | 107 MB | pack 97.7 MiB；另有 **4 个孤儿 `.idx`（对应 .pack 丢失）** |
| `varix.iso` / `build/` | 各 12 MB | 构建产物，已 gitignore |
| 源码合计 | ~30 MB | `src/` 14M + `docs/` 8.8M + `tools/` 7.6M |

**核心结论：**
1. 磁盘 97% 的体积是可再生的 `target/` 目录，删了随时可重建；
2. git 仓库本身（107MB）不算肥，但历史里混入了 launcher 的编译产物（最大单 blob 13MB rlib），且 pack 有损坏残留；
3. `_attic` 里 37MiB 跟踪文件中大量是与 `docs/` 重复的「功能全景图」副本和一个 8.8MB 的日志。

## 二、方案

### 第 1 步：清 target/（磁盘收益 ~24.5 GB，风险：零）

只删可再生构建产物，下次构建自动重建：

```bash
cargo clean --manifest-path src-tauri/Cargo.toml
cargo clean --manifest-path kernel/Cargo.toml        # 若 workspace 含 userspace 则一并清
cargo clean --manifest-path code-analysis/Cargo.toml
cargo clean --manifest-path launcher/Cargo.toml
```

- 注意：清理后首次 `cargo test/build` 会全量重编（kernel ktest 约需数分钟）。
- 建议：同一天内不再跑的 target 才清；正在开发的会话保留自己的。

### 第 2 步：_attic 去 git 跟踪（git 体积收益 ~35 MiB，风险：低）

原则：`_attic` 本来就是"过程产物"，**留在磁盘、移出 git** 即可，物理不删。

```bash
git rm -r --cached _attic
echo "_attic/" >> .gitignore
git commit -m "chore: _attic 过程产物移出版本控制（保留本地）"
```

优先级最高的是两个：
- `_attic/docs/Typora_Hook_Log.txt`（8.8 MB 日志，纯垃圾，可直接物理删除）；
- `_attic/docs|plans/` 下 4 组与 `docs/UNREAL-X-15000-功能全景图-*` 逐字节重复的副本（~9.5 MB × 3 处），本地去重后只留 `docs/` 正本。

### 第 3 步：修复 .git 损坏残留（风险：低，但动 .git 前先备份）

`git count-objects` 报告 4 个 `.idx` 找不到对应 `.pack`。处理：

```bash
cp -r .git /d/backup/git-backup-$(date +%Y%m%d)     # 先整库备份 .git
rm .git/objects/pack/pack-7a1b9b7e*.idx             # 仅删 4 个孤儿 idx
git fsck --full                                      # 校验无 missing 对象
git gc --prune=now                                   # 重新打包，顺带收紧
```

`git fsck` 全绿才继续；报 missing 就从备份恢复。

### 第 4 步（可选，重操作）：清洗 git 历史中的构建产物

历史里有 `launcher/target/**/*.rlib|.rmeta` 等大 blob（≥10 个、单最大 13MB）。清洗需**重写全部历史 + force push**，所有协作者必须重新 clone。仅当 `.git` 在第 3 步后仍 >100MB 或未来要公开仓库时才值得做：

```bash
git filter-repo --path launcher/target --invert-paths   # 需 pip install git-filter-repo
```

日常开发阶段**不建议**执行——107MB 的 pack 对 GitHub 完全无压力，收益/风险比不划算。

## 三、执行顺序与验证清单

| 步骤 | 收益 | 风险 | 验证 |
|---|---|---|---|
| 1 清 target | −24.5 GB 磁盘 | 零 | `cargo test -p ca-core`、`ktest --lib` 全绿（全量重编后） |
| 2 _attic 出库 | −35 MiB git | 低 | `git status` 干净、`git ls-files _attic \| wc -l` = 0 |
| 3 修 .git | 消除损坏隐患 | 低 | `git fsck --full` 零报错、push 正常 |
| 4 历史清洗 | pack 97→~60 MB | 高（重写历史） | 暂缓，条件触发再做 |

## 四、长效机制

1. `.gitignore` 已较完善（target/node_modules/dist 均已覆盖），无需大改；第 2 步补一行 `_attic/` 即可。
2. **约定**：今后新增过程产物直接放 `_attic/`（已不入库），截图/日志不再进 git。
3. `pre-commit` 钩子可加一条：拦截 >5MB 的 blob 入库（`git diff --cached --stat` 或预提交检查文件大小）。
4. 磁盘维度：建议在 `build-windows.bat` 旁加一个 `clean-all.bat`（纯 ASCII+CRLF）封装第 1 步，随手可清。
