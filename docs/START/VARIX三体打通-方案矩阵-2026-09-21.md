# VARIX 三体打通 · 方案矩阵（Windows 11 + Variable/Tauri + VARIX 内核）

> 定位：本文是《VARIX双域系统施工总案.md》的**决策补充**，不改总案——总案的架构逻辑、阶段划分、验收框架继续有效。
> 本文回答三个问题：①「Windows 11 整个放 U 盘」有哪几条技术路线、怎么选；②「Variable 在内核里独立打开」的路线怎么走；③三体打通还欠哪些账、按什么顺序还。
> 状态：**方案待拍板**。任何一条未获用户确认前不施工。

## 0. 用户诉求 ↔ 总案映射（先对齐，避免重复发明）

| 用户原话 | 工程目标 | 总案对应位置 | 现状 |
|---|---|---|---|
| 内核是隔离 | VARIX 是独立 OS，Windows 完全不开机也能用软件 | 阶段 2（用户态/驱动/真盘 FS）+ 阶段 5（Wine 通道） | 大部分已实机（记事本闭环 VERDICT PASS） |
| Variable 在内核里**独立打开** | U 盘引导默认进 Variable 桌面，全程无 Windows 参与 | 阶段 3（Servo 承载 React 前端 + Tauri IPC 垫片） | **定稿未施工，当前最大欠账** |
| Windows 11 整个放 U 盘 | WIN_ENGINE 300GB 分区放完整 Windows | 阶段 0「WINDOWS 卡」+ 阶段 6（隐形引擎镜像） | 分区已就位（U 盘实测 300GB NTFS），**镜像未部署** |
| 三体全面打通 | 引导/存储/数据/体验多桥双世界同语义 | 阶段 0/4 + 垫片协议 + handoff | QEMU 层通；实机层 L0 配置桥断 |

**结论：用户要的终态与总案终局形态完全一致**（"一块 1TB U 盘插任意电脑：开机默认进 VARIX+Variable 桌面；日常软件走 Wine；高兼容软件走隐形 Windows 引擎；游戏/反作弊重启进纯 Windows"）。本文不推翻任何设计，只补齐两块决策面：Windows 镜像的部署路线选择、Variable 上内核的执行策略。

## 1. Windows 11 进 U 盘：四条技术路线全对比

目标分区：U 盘 WIN_ENGINE（NTFS，300GB，已存在）。

### W1 · WTG 工具部署（Hasleo WinToUSB / Rufus Windows-To-Go）

- 做法：用 Hasleo 把 Win11 完整部署到 WIN_ENGINE 分区；ESP 内补一份 bootmgr+BCD 指向它；bootselect「WINDOWS 卡」→ BootNext 走 U 盘自己的 Windows 引导项。
- 优点：**工具成熟、当天可完成**；驱动/激活绑定本机（Legion）风险低；得到的是标准完整 Windows 11。
- 缺点：微软官方已弃用 WTG 机制（技术上仍可用，属"遗留但有效"）；大版本功能更新在 USB 盘上成功率一般（失败就地重部署即可，差分链可兜底）。
- 前置：①确认 thinkplus 1TB 是 SSD 盒而非普通 U 盘（4K 随机 <5MB/s 则体验不可接受，先跑一次 CrystalDiskMark）；②BitLocker 部署时直接不启用（U 盘整机物理可控）；③快速启动关闭（HiberbootEnabled=1 遗留项）。

### W2 · VHDX 文件化部署（总案原设计，阶段 6 引擎镜像）

- 做法：Windows 装进 WIN_ENGINE 上的 VHDX（差分三级链 Base→Apps→User，阶段 1 遗留未勾项）；同一份 VHDX 双用途——bootselect 可直接引导（完整 Windows 通道），也可被 Hyper-V/引擎编排拉起（隐形引擎通道）。
- 优点：**总案定稿路线**；差分链天然对接 SNAPSHOT 快照与灾备（阶段 9 已全绿）；"一份镜像两个用途"（独立引导 + 后台引擎）是 W1 给不了的；换盘/重置 = 换 VHDX 文件。
- 缺点：三级差分链未施工；VHDX 引导链（ESP BCD → VHD 启动）比 W1 多一层；部署工程量大于 W1。
- 备注：QEMU 侧已有 VHD 直读与引导验证经验（vpc 格式走通），实机 VHDX 引导技术路径成立。

### W3 · 传统完整安装（setup 直接装进 USB 分区）

- 做法：像装普通系统一样把 Win11 setup 到 WIN_ENGINE。
- 优点：最"正常"的 Windows，Windows Update 最顺。
- 缺点：无差分/快照结构；安装过程对 USB 目标盘有阻碍需绕；**与隐形引擎通道（阶段 6）不兼容**——引擎要的是可编程挂载的镜像，不是裸安装；拔盘时正在更新的系统易损坏。
- 评级：不推荐（放弃结构化优势，换不来任何 W1/W2 没有的东西）。

### W4 · 不部署（对照项）

- 内置盘 Windows + 开机自启 / Shell 模式承担"Variable 体验"；U 盘只跑 VARIX。
- 仅当 W1/W2 的 USB 性能实测不可接受时的退路。不作为主线。

### 推荐组合

- **主线 W2**（总案原设计，一份镜像双用途，结构化优势全保留）；
- **先行 W1** 作为快速通道（第 1 批先用 Hasleo 让 U 盘拥有可引导的完整 Windows，bootselect 三卡真机闭环；W2 差分链在第 3 批接手后，W1 部署可保留为独立引导项或回收）。
- W3 弃用；W4 仅作性能兜底预案。

## 2. Variable 在内核里独立打开：路线对照与执行策略

### 先说清一个工程事实（物理边界，不可绕）

Tauri 应用本体（exe + WebView2 运行时）**不可能直接在 VARIX 内核里运行**——WebView2 是闭源 Chromium，深度依赖 Windows 系统库。能"独立打开"的是 Variable 的**界面与功能**，工程上只有两条真路：

### R1 · Servo 承载同一份 React 前端（总案阶段 3 定稿主线）★

- 架构：`内核系统服务 ← Tauri IPC 垫片 ← Servo(Variable React 前端) ← GOP 帧缓冲`。
- 核心价值：**不 fork 前端**——同一份 959 个 TS/TSX 文件跑在两个世界上（Windows 侧 Tauri 原版 / 内核侧 Servo 版），垫片实现同一 invoke 协议（554 方法三色映射：✅内核原生 / 🔶组合映射 / ❌暂缺降级，首版目标 ✅+🔶 ≥30% 覆盖桌面壳闭环）。
- 总案 12 个施工步骤已排好序（垫片定版 → 三色审计 → KV 服务 → vwmStore 迁移 → 输入管道 → 渲染通路 → 三件套 → BootScreen → 多窗合成 → 降级 i18n → 性能基线 → 里程碑验收）。
- 关键复用件现状：垫片协议单源已定版（tools/shim-protocol.source.json，三段式错误码）；KV 服务已落（kvsrv，复用 fs23_journal）；VFS 白名单（vfsguard）在位——阶段 3 的地基比总案撰写时更厚。

### R2 · ushell 原生渐进（保底线）

- 现状：内核 ring3 自绘桌面三件套已实机走查（任务 27，20/20）。
- 作用：不依赖任何大型移植的**零依赖保底桌面**——Servo 线任何阶段受阻，内核侧永远有一个能开机即用的 Variable 风格桌面兜底；同时承担引导期 UI、handoff 交接画面等"Servo 起来之前"的全部界面职责。
- 与 R1 并行不冲突：R2 是壳（长期保留），R1 是真前端（逐步长大后接管桌面内容区）。

### R3 · Wine 跑 Tauri/WebView2

- 评级：**❌ 不推荐，且明确不做**。WebView2 闭源组件追着 Windows 版本跑，Wine 化永不收敛；Wine 通道（阶段 5，已实机）的目标是常规 Win32 应用，不是承载 Variable。此结论入档防止未来重复论证。

### 执行策略（推荐）：R4 = R1 主线 + R2 保底 + 垫片协议唯一契约

- R1 按总案阶段 3 的 12 步推进，不分叉、不缩水；
- R2 继续作为引导期/兜底层，视觉语言与 Variable 对齐（已有 win11 外壳契约）；
- 两个世界共用同一套 invoke 语义（shim-protocol 单源），杜绝双实现漂移。

## 3. 三体打通五桥现状（通 / 半通 / 断）

| 桥 | 内容 | QEMU | 实机 | 欠账（关闭欠账的方案已定） |
|---|---|---|---|---|
| L0 引导配置 | boot-select.json 双侧读写 | 通 | **断** | 方案 A：boot-select.json 副本放 ESP + limine.conf `module_path` 挂载 + 部署脚本同步（内核侧 read_via_limine 已就绪等挂载点） |
| L1 存储共享 | SHARED exFAT 单一事实源 | 通 | **半通** | 内核读已实机（fs/exfat_ro.rs，只读语义+SnapshotArea 写过渡）；内核直读写 = 三期 xHCI MSC 后挂真 USB 块设备（fs 层已就绪，缺的是块设备层） |
| L2 输入画面 | 16B 帧 + 输入协议 | 通 | **半通** | 真机 PS/2 键盘通；USB 键鼠/触控板 = 二期 xHCI（仅 HID，任务 19 评估报告 6-8 天） |
| L3 应用能力 | 垫片协议 + apps.json + Wine 链 | 通 | **通** | 内核侧记事本已实机 VERDICT PASS；持续扩面按三色映射驱动 |
| L4 体验连续 | handoff + 自启 + Shell 模式 | 代码就绪 | 未部署 | handoff 三件套（内核 handoff.rs + dualboot.rs + 前端）已完整待提交；部署依赖 L0 |

**打通的终态体验（用户视角）**：插 U 盘开机 → bootselect 四卡（VARIX+Variable / U 盘 Windows / 内置盘 Windows / 固件设置）→ 默认进 VARIX，内核引导 → Variable 桌面独立亮起（Servo 版，无 Windows 参与）；选 Windows 卡 → U 盘上的完整 Win11 → 自动全屏 Tauri Variable（自启/Shell 模式）；两世界同一套设置、同一份文件（SHARED）、同一张应用清单（apps.json）；内核待机交接可 handoff 进 Windows，反之 Windows 关机后可 BootNext 回内核（B4 反向交接，可选项）。

## 4. 分期施工建议（对齐总案阶段号，不发明新阶段）

- **第 0 批（拍板后 1-2 天）**：①handoff 三件套提交入库；②L0 方案 A（ESP 副本 + limine.conf module_path + 部署同步）施工；③U 盘内核重建重刷（当前 U 盘 F4F96E69 落后本地两版本：鼠标接线 + handoff）；④关闭快速启动（HiberbootEnabled）。
- **第 1 批（1-3 天）**：W1 路线把 Win11 部署进 WIN_ENGINE（Hasleo，前置=SSD 盒性能实测）；ESP 补 U 盘 Windows 引导项；bootselect 三卡实机真引导走查（含 handoff 交接目标确认为 U 盘 Windows）。
- **第 2 批（阶段 3 启动，数周级）**：按总案 12 步推进 Servo 线（步骤 1-7 优先：垫片定版→三色审计→KV→vwmStore→输入→渲染→三件套闭环）；R2 ushell 同步做视觉对齐。
- **第 3 批（阶段 6 启动）**：W2 三级差分链（阶段 1 遗留项）→ 引擎编排底座（Hyper-V 过渡）→ 无缝窗口；W1 部署按届时决策保留或回收。
- **长线并行**：二期 xHCI HID（真机 USB 键鼠）→ 三期 xHCI MSC（内核直读 SHARED）→ 内核 VMX 评估（阶段 6 终局项）。
- 每批完成即过三线门禁 + 实机验收归档 docs/acceptance/（总案既有流程）。

## 5. 物理边界（诚实清单，方案不违反）

- Tauri/WebView2 二进制本体不进内核；进内核的是 Variable 的前端与功能（R1/R2）。
- 双 OS 同时活窗、不重启切换系统：永远不成立（两套内核互斥持有硬件）。
- 内核侧触控板（I2C 总线）不支持；真机内核键鼠依赖二期 xHCI，此前用 PS/2 口/外接 PS/2 兼容设备。
- 快速启动（HiberbootEnabled=1）与 U 盘整机语义冲突，第 0 批一并关闭。
- U 盘上的 Windows 遵守"拔盘即走、零残留"（ramcache 只缓不落盘，阶段 6 已定）。
