## 1. 「Tauri Variable 可以完全相同地放到内核里吗」——精确回答

### 1.1 先拆解 Variable 由什么组成

| 层 | 内容 | 规模 |
|---|---|---|
| 前端（界面层） | 界面设计、UI 组件、交互逻辑、动画、多语言、状态管理（vwmStore 等） | 959 个 TS/TSX 源文件 |
| 画界面的引擎 | WebView2（微软闭源浏览器内核，负责把前端画成像素） | Windows 专属组件 |
| 干活的后端 | 文件、窗口、输入、嵌入第三方软件、安装器、隐私保险箱等真功能 | Rust 编写，650 个 `#[tauri::command]` |

### 1.2 三层各自的命运（方案 R1 / 总案阶段 3）

| 层 | 放进内核的方式 | 相同程度 |
|---|---|---|
| **前端（界面层）** | **原封不动复用**——同一份代码同时在 Windows（Tauri）和内核（Servo）两个世界运行，不 fork | **100% 相同**（git diff 必须为零改动，vitest 全绿证明语义不变） |
| 画界面的引擎 | WebView2 装不进内核（闭源且依赖 Windows）→ 由 **Servo**（开源、Rust 编写的浏览器引擎）顶替同一位置 | 引擎不同，**画出来的结果逐屏像素级对照验收** |
| 干活的后端 | 650 个命令 → 前端经"IPC 垫片"用**同一套 invoke 协议**访问**内核系统服务**（文件/窗口/输入/KV 存储均已实机） | 协议相同；命令面逐条三色登记（见 1.3） |

**一句话：界面设计、UI、交互"完全相同"是架构承诺且可验收；换的是引擎与后端这两块"底座"，且替换件的输出质量有像素级对照与三色映射两道闸把关。**

### 1.3 「完全相同」的三道保障闸（怎么防止缩水）

1. **前端零分叉**：内核侧跑的就是仓库里那份前端，任何"为内核改前端"的冲动都被禁止——适配全部发生在垫片层。验收 = `git diff` 前端目录零语义改动 + vitest 全绿。
2. **三色映射**：650 个命令用 `tools/audit.cjs` 逐条登记——✅内核原生（文件/窗口/输入）/ 🔶组合映射（多个内核服务拼出来）/ ❌暂缺（统一降级错误 + 前端如实提示"此功能需 XXX"+ 多语言词条）。禁止未登记的静默缺失；首版目标 ✅+🔶 ≥30% 覆盖桌面壳/文件管理器/设置页闭环。
3. **像素级对照**：内核版桌面与 Windows 侧运行图逐屏截图对照（任务栏/开始菜单/窗口壳），动画时长曲线一致（spring 4% 过冲沿用），125% DPI 与 2560×1440 双分辨率检查。

### 1.4 能力面的诚实对照（哪些能力内核版有对等物、哪些暂缺）

| Windows 版能力 | 内核版对等物 | 状态 |
|---|---|---|
| 文件管理 | 内核 VFS + SHARED 卷（exFAT 只读已实机；三期 USB MSC 后全通） | 地基已实机 |
| 窗口管理（贴靠/最小化/Z 序） | 内核显示服务 + vwmStore 语义移植（阶段 3 步骤 9） | 待施工 |
| 键盘鼠标输入 | PS/2 已实机；USB 键鼠 = 二期 xHCI（真机） | 半通 |
| 跑第三方 Windows 软件 | Wine 通道（记事本已实机 VERDICT PASS）+ 隐形引擎通道（QEMU 已验） | 对等物存在 |
| 嵌入第三方软件窗口（拥有式嵌入） | Windows 版专属（依赖 Win32 桌面）；内核侧 = 隐形引擎无缝窗口承担 | 语义对等，实现路径不同 |
| 安装器重定向/注册表快照/隐身会话等 Windows 深度能力 | ❌ 暂缺 → 如实降级提示 | 三色映射管理 |
| 设置/主题/多语言/启动仪式 | 垫片同语义（settings://changed、boot://event 频道已定版） | 协议就绪 |

## 2. 阶段 3（Servo 线）十二步施工序精讲

总案已排好的顺序，每步"做什么 + 为什么"：

1. **垫片协议定版**——invoke 命名空间保持现有 `command_name` 原文、参数 JSON 序列化、错误三段式（OK|MAPPED_ERR|MISSING）、事件反向通道。为什么第一步做它：它是前端不改代码的根基，且单源生成已落地（tools/shim-protocol.source.json），只差内核侧对齐。
2. **三色审计**——跑 audit.cjs 产出 650 命令逐条归属表。为什么：后续每一步的工作量由这张表驱动，缺什么补什么，不做拍脑袋开发。
3. **内核 KV 存储服务**——前端 localStorage 语义的内核等价物（值 ≤1MB + WAL 持久化）。地基已比总案撰写时厚：kvsrv 已落地（复用 fs23_journal 账本）。
4. **vwmStore 持久化迁移**——窗口几何从 localStorage 透明桥到 KV，前端零改动。为什么：保证"重启后窗口布局还原"在内核世界同样成立。
5. **输入事件管道**——内核输入服务 → 消息通道 → 前端 DOM 事件（键/鼠标/滚轮/剪贴板），焦点模型定谁收键。与 Wine 通道共用同一输入总线（一份代码两处用）。
6. **渲染通路**——Servo 输出 → 共享帧缓冲 → 内核显示服务合成提交；先单窗口全屏，后多层合成；脏矩形刷新不整屏刷。
7. **第一批保底命令面**——桌面壳/文件管理器/设置页三件套在垫片下闭环可用（文件浏览走 VFS 白名单）。这是"Variable 在内核里独立打开"第一次真正亮起来的里程碑。
8. **BootScreen 对接**——内核拉起链各阶段发 `boot://event` 同语义进度，启动仪式动画体验与 Windows 侧一致。
9. **窗口合成多窗版**——多窗口 + Z 序 + 最小化保活（Windows 侧 display:none 语义的裸机等价物）。
10. **降级提示多语言**——全部 ❌ 命令统一降级错误 + 词条 + "此功能需 XXX 阶段"如实文案。
11. **性能基线**——首帧时间/交互延迟/窗口开关耗时三项基线在目标硬件归档（后续回归门禁的初始值）。
12. **里程碑整合验收**——真机引导默认进 Variable 桌面，三件套可用，vitest 全绿，三色占比如实公示。

**依赖关系**：1→2→3/4→5→6→7 是关键路径；8/9/10/11 可与 5-7 并行；R2（ushell 骨架）全程并行保底，Servo 未接管前桌面由它承担。

## 4. W1 / W2 Windows 部署路线：原理与步骤清单

### 4.1 W1 整装写入（快速通道）

- **原理**：U 盘 WIN_ENGINE 分区（NTFS 300GB）被工具当成一块普通硬盘，完整安装 Windows 11；同时在 U 盘 ESP 里登记一个 Windows 引导项（bootmgr+BCD）。开机菜单选 WINDOWS 卡 → BootNext 指向该引导项 → 重启一次 → U 盘上的 Windows 起来 → 自启/Shell 模式让 Variable 全屏。
- **步骤清单**（拍板后执行）：
  1. 前置实测：AS SSD 选 thinkplus 的分区（X:/W:）跑一轮——顺序 ≥400MB/s 且 4K ≥15MB/s 才立项（SSD 盒标准；普通 U 盘直接否决）；
  2. Hasleo WinToUSB：选官方 Win11 镜像 → 目标选 WIN_ENGINE 分区 → 模式选"Windows To Go"（去掉 BitLocker 选项）；
  3. 部署脚本在 U 盘 ESP 写入 bootmgr+BCD 指向 WIN_ENGINE；
  4. bootselect 配置（boot-select.json）确认 WINDOWS 卡目标为 U 盘 Windows（handoff 目标参数化，见矩阵文档）；
  5. 第一次引导进 U 盘 Windows：装 Lenovo 驱动、开 Variable 自启、关快速启动、关休眠；
  6. 全链走查：三卡菜单进 U 盘 Windows → Variable 全屏 → 关机 → 拔盘插内置盘系统互不干扰验证；
  7. 验收归档 docs/acceptance/。
- **风险与对策**：大版本更新失败率偏高 → 更新前 SNAPSHOT 快照，失败就地重部署（半小时级）；USB 4K 随机弱 → 系统盘场景可接受，编译/游戏等重负载走内置盘。

### 4.2 W2 差分镜像（总案主线，阶段 6 组件）

- **原理**：Windows 11 装进 VHDX 虚拟盘文件，且拆成三层叠差分——Base 母本层（干净系统，只读永不改写）→ Apps 差分层（装过的软件）→ User 差分层（日常改动）。系统运行时 = 三层叠加视图。好处：①Base 永远干净，丢掉上层即"恢复出厂"；②同一份镜像两个用途——开机直接引导（完整 Windows 通道）或被 Hyper-V 挂载成"隐形引擎"（Windows 没开机、它的软件窗口无缝出现在 Variable 桌面里）；③对接 SNAPSHOT 快照与灾备体系（阶段 9 已全绿）。
- **步骤清单**（第 3 批执行）：
  1. 补阶段 1 遗留：三级差分链创建脚本（Base→Apps→User，容量配置化+幂等）；
  2. Base 母本制作：官方镜像安装进 Base.vhdx（脚本化，一次成型后只读封存）；
  3. 差分挂载引导验证：QEMU 先行（vpc/VHD 直读经验已有）→ 实机 BCD 挂差分链引导；
  4. 引擎编排底座：挂载 → VM 拉起 → 就绪探针（心跳）→ 休眠/恢复（内存快照写差分盘）；
  5. 无缝窗口链路：全屏画面流 → RemoteApp 窗口级 → 输入反向注入（IME 专项）；
  6. ramcache（只缓不落盘、关机即清、拔盘零残留字节级校验）；
  7. 与 W1 共存决策：W2 落地后，W1 部署保留为独立引导卡或回收（届时按使用体验拍板）。
- **风险与对策**：差分链未施工是最大未知 → 步骤 1 先做可行性小闭环（创建+挂载+叠加视图+回滚四件套验证）再铺开；冷启动 20-40s → UI 如实提示+占位卡（总案已设计）。

### 4.3 两线关系

共用同一块 300GB 分区不冲突：W2 落地前 W1 先服役（第 1 批即有完整 Windows 可引导）；W2 落地后按届时体验决策 W1 去留。W3（裸安装）弃用——放弃差分/快照/引擎复用全部结构化优势，换不来任何新能力。

## 5. R2 ushell 保底线（与 R1 并行）

- **定位**：内核 ring3 自绘桌面（已实机：文件/设置/关于/重启/关机）。Servo 线任何阶段受阻，内核永远有一个能开机即用的 Variable 风格桌面兜底。
- **职责**：引导期 UI（三卡菜单、handoff 交接画面）+ Servo 接管前的桌面 + 视觉语言与 Variable 对齐（win11 外壳契约：win11-settings.css、start-menu 类名契约）。
- **不做的事**：不承担"跑同一份前端"的目标（那是 R1 的）——避免双实现漂移，界面语义以垫片协议为唯一契约。
