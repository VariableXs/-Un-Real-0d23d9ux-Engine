## 本轮发现并修复的缺陷（4 个，全部实机复测）

### 缺陷 1：任务栏窗可见但内容全透明（`taskbar_win.rs` apply_shown）

- **现象**：呼出后任务栏窗存在、z 序正确，但画面全透明。
- **根因**：`visible(false)` 创建的窗口，wry 的 WRY_WEBVIEW 子窗同样保持隐藏；裸 `SetWindowPos(SWP_SHOWWINDOW)` 只显示外层壳。
- **修复**：显示/隐藏改走 `win.show()` / `win.hide()`（tauri API 连 WebView2 一起显隐），TOPMOST 重排随后 `SetWindowPos` 补。0.58 的 `SetWindowPos` 返回 `Result`，按 `if let Err(e)` 记日志。

### 缺陷 2：呼出状态横跳（`taskbar_win.rs` 光标守护）

- **现象**：光标贴热区时每 1.35s collapsed↔summoned 刷屏。
- **根因**：SUMMON_GRACE_MS 超时回落条件未排除「光标仍在热区」——呼出意图持续中被误判超时。
- **修复**：回落条件加 `!in_hotzone`。

### 缺陷 3（A6 主缺陷）：未激活窗口的 WebView2 吞物理点击（`taskbar_win.rs` 悬停激活）

- **现象**：穿透位已清、光标几何精确落在按钮上、WindowFromPoint 指向本窗 Chromium 子窗，但物理点击后菜单不弹；CDP 程序化 click() 却正常。
- **取证（CDP+ctypes 行为矩阵，exp4–exp11）**：事件计数器显示——窗口**非前台**时点击整体丢失或 down 可达 up 被截断（click 不合成，ev 0~1 条）；**SetForegroundWindow 后**点击 100% 完整可达且 React onClick 正常执行。PostMessage 直达 Chrome_RenderWidgetHostHWND 亦可通（输入管线本身完好）。结论：未激活窗口的 WebView2 物理鼠标投递不可靠。
- **修复**：光标守护新增「悬停激活」——光标在交互区（hitmap）稳定悬停 ≥250ms 且窗口非前台 → `win.set_focus()`（tao 内置 SetForegroundWindow + ALT 兜底）；快速滑过（<250ms）不触发，不抢输入焦点；每轮幂等检查前台状态（窗口意外失焦后自动补激活，见缺陷 4）。
- **验证**：呼出→悬停→物理点击全链路 verify 七项全绿；applog 铁证「光标悬停交互区 → 任务栏窗带到前台（保障点击可达）」。

### 缺陷 4：FOCUS_GRANTED 单边门控导致失焦后二次点击丢失

- **现象**：A10 串测中第二次物理点击（关菜单）偶发无效。
- **根因**：激活标记只在「光标离开交互区」时复位；窗口中途意外失焦后光标仍悬停 → 不会重新激活 → 点击再次被吞。
- **修复**：删除单边标记，改为每轮 `GetForegroundWindow` 幂等判断，非前台且悬停超时即补激活。
- **验证**：A10 重跑 ALL_PASS=true（含 menu_closed_by_click）。

### 过程教训（非代码缺陷）：QA 探针坐标误判

- `querySelector('[aria-label="开始"]')` 命中的是 **DIV.taskbar-center 容器**（467px 宽，容器错误挂了与按钮相同的 aria-label），按其 rect 中心点击落在叠于其上的 Variable Write 按钮上——前几轮「点击 V 菜单不弹」的实验数据混入了这一系统性坐标偏差。教训：hit-test 类验收必须以 `elementFromPoint` 交叉验证目标元素身份，不能只信 selector rect。
