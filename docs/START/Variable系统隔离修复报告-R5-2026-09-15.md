# Variable 系统"完全隔离"修复报告（R5 轮 · 2026-09-15）

> 背景：用户反馈 Steam 与 Wallpaper Engine 始终和 Windows 关联——Steam 从桌面启动后落回宿主桌面，WE 的悬浮层/壁纸逃出 Variable 覆盖范围。本轮把"逃逸通道"逐一定位并以代码修复 + 实机验证闭环。

## 一、逃逸通道诊断（实机复现 → 根因）

| 通道 | 现象 | 根因 |
|---|---|---|
| ① Steam `.url` 快捷方式 | 双击后 steam.exe 启动但不收编，落回 Windows（R4-B2） | `embed_launch` 对非 `.lnk` 登记项走 `shell_execute_path`，`.url` 交 Windows 协议关联从宿主侧拉起；窗口匹配用 `xxx.url` 永远命中不了 Steam 家族窗 |
| ② WE 悬浮层（Ctrl+1 提示条） | 悬浮条盖在任务栏上方 | 该提示条属外部点击穿透窗（WS_EX_TRANSPARENT，不吞点击）；真正的层序问题是兼容模式取消 Variable 置顶后 Windows shell 整个露出 |
| ③ 托盘旧 Steam 窗 | 单例重开收编后黑帧 | Steam 家族 L1 直嵌分支在 `needs_reveal` 唤醒检查之前 return，上会话藏到 -32000 的托盘旧窗未唤醒直接重父化 → Chromium occlusion 停渲染 |
| ④ Windows 任务栏露出 | 启动第三方后 Windows 任务栏顶出来 | `tp_launch` 启动第三方时撤销桌面置顶；兼容模式豁免了"桌面聚焦恢复置顶"逻辑，嵌入成功后无人收回 |

## 二、修复清单（全部实机验证）

| # | 修复 | 落点 |
|---|---|---|
| 1 | `.url` Steam 产物在 `embed_launch` 入口探针（复用 `steam_probe`，改为 `pub(crate)`）→ 转交 `steam_open_url` 收编看护通道，返回 `steam:handoff` 由前端关闭占位窗避免双窗 | `system.rs` / `embed.rs` / `thirdApps.ts` |
| 2 | 新增 `tame_wallpaper_engine_windows()`：把 WE 进程名下持 WS_EX_TOPMOST 的顶层窗降为普通层（HWND_NOTOPMOST，位置尺寸不动）；`apply_compat_mode` 与 compat watcher 每 3s 幂等重放 | `compat.rs` |
| 3 | 兼容模式不再取消置顶让位：`apply_compat_mode` 改为断言桌面 `always_on_top(true)`（GPU 冲突判定逻辑不变）；lib.rs 桌面聚焦恢复置顶删除兼容态豁免 | `compat.rs` / `lib.rs` |
| 4 | Steam 家族 L1 直嵌前先 `needs_reveal` → `restore_window + jiggle_window` 唤醒停渲染旧窗（与 R3-B11 治理同构） | `embed.rs` |
| 5 | 新增 `reassert_desktop_topmost()`：`embed_launch` / `embed_adopt` 接入成功后收回置顶（抵消 tp_launch 的撤销），Windows 任务栏不再露出 | `embed.rs` |
| 6 | 兼容横幅三语文案同步新策略（压制悬浮层、桌面保持覆盖） | `i18n/dictionaries.ts` |

## 四、已知边界（诚实口径）

- Steam 客户端内以 L1 真实嵌入运行（窗口重父化），游戏窗口经 WinEventHook 同树收编——受 Win32 桌面架构所限，这是"运行在 Windows 之上"能达到的最强隔离形态。
- WE 的桌面壁纸仍绘制在 WorkerW 层（Windows 桌面底层的机制），但被 Variable 全屏不透明桌面覆盖后用户不可见；其置顶悬浮层已全部压制。
- 点击穿透型外部悬浮条（KoCovCheatSheet 等）不吞点击，不影响交互，已实测确认。
- 若嵌入失败（回退独立窗口），为让回退窗可见会暂时让位置顶——此时用户点回桌面（桌面聚焦）即恢复覆盖，属设计内的退路。

## 七、追加修复：orphaned 重收看护（19:35–20:05 实机验证）

**问题**：Steam 冷启动会先创建主窗、嵌入成功后再自毁重建（steamwebhelper 接管），旧会话按 orphaned 移除后，WinEventHook 自动重嵌通道因无注册会话而失效——重建的新主窗永远逃逸（r5_run4 实机复现：占位卡"已回到自身窗口"，新窗 hwnd=4328742 滞留宿主）。

**修复**（`src-tauri/src/shell/embed.rs`）：新增 `spawn_readopt_watcher` —— orphaned 且进程树仍存活时派生看护线程，每秒轮询同 root pid 树的新可见主窗（带标题栏），命中即广播 `embed://popup` 走前端既有收编流程；45s 未现则交给 D-3 看门狗，进程树消失则自然退出。

**实机验证**（r5_run5）：
```
[embed] readopt vwm-tp:tp-…-mu2mgqks0: 重收重建主窗 hwnd=921158 → 广播 embed://popup
[embed] attach vwm-tp:…: hwnd=921158 → 层级 L3（composited framework window）
[embed] attach vwm-tp:…: L3→L1 真实嵌入（Steam 家族）hwnd=921158
```
重收链路全程闭环。门禁：cargo test 253 passed / cargo check 0 错。

**已知待打磨**：重收生成的 embed_id 出现 `vwm-tp:vwm-tp:` 双前缀（功能不受影响，下轮统一 norm）；orphaned 后前端占位卡与新收编窗并存，可考虑复用原占位窗。
