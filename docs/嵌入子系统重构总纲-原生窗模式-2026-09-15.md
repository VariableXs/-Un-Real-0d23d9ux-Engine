## Part 0 — 一句话目标

> **第三方软件在 Variable 里运行时，显示它自己的窗口外观——它自己的标题栏、它自己的「最小化 / 最大化 / 关闭」三个按钮、它自己的边框。Variable 不绘制任何窗口 chrome（无标题栏、无红绿灯、无缩放把手、无圆角边框）。移动与缩放通过拖动软件自己的标题栏与边框完成。**

用户原话逐条落地：

| 用户原话 | 技术含义 | 落地方式 |
|---|---|---|
| 「整个框都删了，都用软件自带的」 | 软件自身的 `WS_CAPTION`/`WS_THICKFRAME`/`WS_SYSMENU` **一个都不剥**；Variable 虚拟窗对第三方应用**零 chrome** | Part 5.1 不剥样式；Part 5.2 不渲染 chrome |
| 「包括缩小、全屏还有退出」 | **− □ × 三个按钮全部软件原生、全部真实可用**（一个都不少） | 改「拥有关系」取代「父子关系」，见 D-1 修订 |
| 「界面尺寸可以自己拖动」 | 保留 `WS_THICKFRAME`，由软件自己的边框承担缩放 | Rust 不再剥 `WS_THICKFRAME` |
| 「什么红绿灯等等自己写的都不要」 | `vwm-titlebar` / `vwm-lights` / `vwm-rz` / 圆角边框 —— 对第三方应用**全部停用** | Part 5.2.2 |

> ### ⚠️ 对 v1.0 的正式更正
>
> v1.0 的「决策 D-3」曾建议**砍掉软件的最小化按钮**（移除 `WS_MINIMIZEBOX`），理由是 `WS_CHILD` 子窗口的最小化语义不可靠。
>
> **该建议已撤回。** 那个技术障碍的根源在于把软件做成了**子窗口**。v1.1 改用**「拥有关系」（ownership）**——软件不再是需要被拽听话的子窗口，而是保留完整原生行为的独立顶层窗口。**障碍被机制改变本身消除，而非通过妥协绕过。**
>
> **结论：− □ × 一个都不少，全部软件原生，全部真实可用。**

## Part 1 — 现状（精确，带坐标）

### 1.1 当前 L1 主路径做了什么

**文件**：`src-tauri/src/shell/embed.rs:1022-1040`

```rust
fn restyle_and_reparent(app: &tauri::AppHandle, new_hwnd: isize) -> bool {
    ...
    let style = GetWindowLongPtrW(h, GWL_STYLE) as isize;
    let new_style = ((style as u32)
        & !(WS_CAPTION.0 | WS_THICKFRAME.0 | WS_MINIMIZEBOX.0 | WS_MAXIMIZEBOX.0 | WS_SYSMENU.0))
        | WS_CHILD.0;                                    // ← 关键：把软件自己的 UI 全剥了
    SetWindowLongPtrW(h, GWL_STYLE, new_style as isize);
    let _ = SetParent(h, hwnd_from(desktop));
    let _ = SetWindowPos(h, HWND::default(), 240, 140, 900, 600, SWP_FRAMECHANGED | SWP_NOZORDER);
    true
}
```

**这一行 `& !(...)` 是整个问题的根源**：它把软件的标题栏、边框、最大化/最小化/关闭按钮**全部删除**。软件被"肢解"成一个只有客户区的裸窗口，于是 Variable 必须自己画一套替代品：

| 被剥掉的原生能力 | Variable 被迫造的替代品 | 代码位置 |
|---|---|---|
| `WS_CAPTION` 标题栏 | `vwm-titlebar` 假标题栏（含 app 名、色带、红绿灯） | `VirtualWindowFrame.tsx:656-736` |
| `WS_THICKFRAME` 缩放边框 | 8 个 `vwm-rz` 把手 | `VirtualWindowFrame.tsx:882-888` |
| `WS_MINIMIZEBOX` | 🟡/🔴 虚拟灯 | 同上 |
| `WS_MAXIMIZEBOX` | 同上 | 同上 |
| `WS_SYSMENU` 关闭 | 🟢 虚拟灯 | 同上 |
| 窗口外观 | `border-radius / border / box-shadow` | `vwm.css:13-29` |

### 1.2 由此产生的连带耦合

| 耦合 | 位置 | 说明 |
|---|---|---|
| **标题栏高度 38px 硬编码三处** | `vwm.ts:165` `VWM_TITLEBAR_H = 38`；`vwm.css:43` `height: 38px`；`VirtualWindowManager.tsx:623-625` `(win.y + 38)` / `(win.h - 38)` | 三处手工同步，改一处必崩另外两处 |
| **占位卡** | `VwmAppContent.tsx:132-134` → `TpPlaceholder` | 软件没进来时显示的「xxx 已退出」黑底卡片 + 按钮 |
| **嵌入窗边界 = VWM rect − 38** | `VirtualWindowManager.tsx:619-626` | 因为有了假标题栏，嵌入区必须让出 38px |

### 1.3 与之并存的正确写法（已存在！）

**文件**：`src-tauri/src/shell/container.rs:189-205`

```rust

    ...

```

**文档注释第 4 行明确写着「不剥其样式」**。这段代码就是本次重构要推广到全路径的基础。

## Part 2 — 目标形态（可验收的定义）

### 2.1 视觉定义

重构后，一个第三方软件窗口在 Variable 中呈现为：

```
┌─────────────────────────────────────────┐
│  ▣ MyApp                     −   □   ×  │  ← 软件自己的标题栏（真实原生，非 Variable 绘制）
├─────────────────────────────────────────┤
│                                         │
│   软件自己的界面内容                     │  ← 软件的客户区
│                                         │
└─────────────────────────────────────────┘
   ↑ 拖动这里可拉伸窗口尺寸（软件自己的边框）
```

**明确不包含**：
- ❌ `vwm-titlebar`（Variable 假标题栏）
- ❌ `vwm-lights`（红黄绿三个虚拟灯）
- ❌ `vwm-rz`（8 个 Variable 缩放把手）
- ❌ `vwm-window` 的 `border-radius` / `border` / `box-shadow`
- ❌ 标题栏高度偏移 38px

### 2.2 行为定义

| 操作 | 期望行为 | 由谁实现 |
|---|---|---|
| 拖动软件自己的标题栏 | 窗口移动（限制在 Variable 工作区内） | 软件原生 `DefWindowProc` |
| 拖动软件自己的边框 | 窗口缩放 | 软件原生 `WS_THICKFRAME` |
| 点软件自己的最大化 □ | 窗口放大填满 Variable 桌面 | 软件原生 |
| 点软件自己的最小化 − | 最小化到 Variable 任务栏 | **Variable 接管**（见决策 D-3） |
| 点软件自己的关闭 × | 软件自行决定是否退出 | 软件原生 `WM_CLOSE` |
| Variable 任务栏点图标 | 最小化 / 还原 | Variable 既有能力，**不变** |

### 2.3 保留项（不得破坏）

以下能力保持不变，是本次重构的**回归红线**：

- Variable 任务栏条目
- Alt+Tab / 窗口聚焦切换
- 窗口贴靠（左半屏/右半屏/四角/顶部最大化）
- 标签组 / 多选编组
- 布局快照
- 「软件不能逃出 Variable」隔离底线（R5/R6/R7 的成果）
- 有框模式（如果保留的话）必须零变化

## Part 3 — 可行性证明

### 3.1 代码层证明

`container.rs:189` 的 `wrap_child` 已在生产路径中使用（L2 分支，由 `attach_by_tier` 的 `CompatTier::L2` 调用，`embed.rs:1146-1159`），且日志显示其工作正常。它证明：

> **保留原生样式 + 仅添加 `WS_CHILD` + `SetParent` 是一条已被验证可行的路径。**

本次重构不是发明新机制，而是把这条**已验证路径**从 L2 分支提升到全路径。

### 3.2 与历史实机结论的一致性

诊断报告 R3-B11 的终局结论（已写入 memory）：

> 「唤醒后的 Steam CEF 主窗 reparent 进桌面画面/输入全通」
> 「历史『CEF 一律 L3、L1 重父化呈现纯黑』是渲染挂起的误判」

代码注释（`embed.rs:1163-1171`）亦确认 CEF 家族应走 **L1 真实嵌入**。本次重构是这一结论的自然延伸：**既然真实嵌入对最难搞的 Chromium 都成立，就更没必要保留会因误判导致黑屏的 L3 主路径。**

### 3.3 为什么这同时是性能优化

当前 L3 路径（诊断报告 R-B）：每帧 8.3MB → base64 11MB 字符串 → IPC → 前端 200 万次 JS 循环 → 3 次全量拷贝。

原生窗模式下：
- **零拷贝、零序列化、零 JS 循环**
- 由 Windows 合成器直接合成，走 GPU
- 延迟从 ~100ms 级降到显示器刷新率水平

这不是"先解决架构再优化性能"，而是**同一个修改同时解决两者**。

## Part 4 — 架构决策（含未决决策点）

### D-1 【v1.1 重大修订】不再用 `SetParent` 父子关系，改用**拥有关系（ownership）**

**决定**：第三方窗口**不再是** Variable 桌面的 `WS_CHILD` 子窗口，而改为由 Variable 桌面窗口「拥有」：

```rust
// 不是 SetParent(hwnd, desktop) + WS_CHILD
// 而是：让 variable 桌面成为它的 owner，窗口自身保持完整顶层语义
SetWindowLongPtrW(h, GWLP_HWNDPARENT, desktop as isize);
```

**为什么这是关键改动**（对比表）：

| | 旧法（`SetParent` + `WS_CHILD`） | 新法（`GWLP_HWNDPARENT` 拥有） |
|---|---|---|
| 窗口身份 | Variable 桌面的**子窗口** | 独立**顶层窗口**，仅被拥有 |
| 软件自己的标题栏 | 需靠"不剥样式"勉强保留 | 天然保留 |
| 最小化 − | ❌ 子窗语义不可靠（v1.0 的死结） | ✅ **纯原生，正常工作** |
| 最大化 □ | ⚠️ 只能填满父窗客户区 | ✅ **纯原生全屏** |
| 关闭 × | 可用 | ✅ **纯原生** |
| 拖动边框缩放 | 可用 | ✅ **纯原生** |
| 始终显示在 Variable 之上 | 天然（子窗在父窗内） | ✅ 被拥有窗口恒定显示在 owner 之上 |
| 是否出现在 Windows 任务栏 | 不会 | ✅ 不会（被拥有的窗口不进 Windows 任务栏） |
| 是否被父窗客户区剪裁 | 是（逃不出桌面） | ❌ **否**，可延伸到 Variable 桌面之外 |

**拥有的三个甜区**恰好全部满足需求：原生按钮全可用 + 永远在 Variable 之上 + 不脏污染 Windows 任务栏。

**已核实**：全仓库当前**无任何 `GWLP_HWNDPARENT` 使用**，这是一条干净的新路径。

**代价与治理**：唯一失去的是"被桌面客户区剪裁"。治理方式有三（按推荐度）：

| 治理手段 | 做法 | 评价 |
|---|---|---|
| **① 位置同步（推荐默认）** | 仍由 `EmbedBridge` 用 `SetWindowPos` 驱动窗口到 VWM rect；Variable 是"位置的主人" | 与现状心智一致，贴靠/编组/布局快照全部继续可用 |
| ② 边界钳制 | 在 `WinEventHook` 的 `EVENT_SYSTEM_MOVESIZEEND` 里把越界窗口拉回工作区 | 配合 ① 使用 |
| ③ 不治理 | 允许窗口自由定位（含跨越 Windows 区域） | 最原生，但会打破"一切在 Variable 内" |

**建议默认 ① + ②**：日常窗口行为与现在一致，同时按钮与缩放全部回归原生。

### D-2 【已定】是否保留双模式

**决定**：**全局单一模式**——第三方应用一律走原生窗模式。不保留"有框/无框"开关。

**理由**：用户明确「整个框都删了」。保留双模式会让两套路径并存，回归面翻倍，违背"整合"诉求。

**代价**：`VirtualWindowFrame` 的标题栏/红绿灯/把手对第三方应用彻底停用，但对 Variable 自有应用（explorer/设置/工具等）**保持不变**。

### D-3 【v1.1 替换】三个按钮全部原生 —— 仅剩"状态回传"

既然窗口已是原生顶层窗，− □ × **由软件自己处理，Variable 不插手**。Variable 只做一件事：**把软件的状态变化回传给自己**（让 Variable 任务栏知道它最小化了、让它 Alt+Tab 列表同步）。

**实现手段（已核实可行）**：扩展现有的 `SetWinEventHook`。

`embed.rs:997-1006` 已有成熟的 out-of-context 钩子：**跨进程有效、无需 DLL 注入**。

```rust
let hook = SetWinEventHook(
    EVENT_SYSTEM_MINIMIZESTART,      // 软件自己点了 −
    EVENT_SYSTEM_MINIMIZEEND,        // 还原
    HMODULE::default(),
    Some(on_state_change),
    0, 0,
    WINEVENT_OUTOFCONTEXT,
);
```

需新增监听的事件：

| 事件 | 触发时机 | Variable 的动作 |
|---|---|---|
| `EVENT_SYSTEM_MINIMIZESTART` | 用户点了软件自己的 − | 同步 VWM 状态为 minimized（任务栏图标态更新） |
| `EVENT_SYSTEM_MINIMIZEEND` | 从最小化还原 | 同步为 normal |
| `EVENT_SYSTEM_MOVESIZESTART/END` | 用户拖边框/标题栏（尺寸变了） | 把新 rect 写回 VWM `win.x/y/w/h` ← **这一步让"自己拖动"与 Variable 布局体系共存** |
| `EVENT_OBJECT_DESTROY` | 窗口销毁 | 现有会话 watcher 已覆盖 |

> **关键点**：`MOVESIZEEND` 这条回调正是「界面尺寸可以自己拖动」能被 Variable 正确记住的原因——软件自己缩放后，Variable 的窗口状态跟着更新，贴靠/布局快照/持久化才不会失真。

**Variable 任务栏点击还原时的反向同步**：`ShowWindow(hwnd, SW_RESTORE)`（现有 `embed_visible` 已用 `SW_SHOW/SW_HIDE`，语义直接扩展）。

### D-4 【需你确认】Variable 自有应用是否也去框

**决定**：**不去**。`explorer`、设置中心、时钟、计算器等 Variable 自研应用的窗口保持现有 `vwm-titlebar` + 红绿灯外观。

**理由**：这些是 HTML 应用，没有"自己的原生标题栏"可用，去框等于没有标题栏。

### D-5 【已定】L3 画面捕获的处置

**决定**：从"主路径之一"降级为**仅在 `SetParent` 失败时的最后兜底**，并**不再默认启用**。

**理由**：诊断报告 R-A/R-B 已证明 L3 是误判黑屏与性能问题的联合来源。原生窗模式覆盖了绝大多数场景后，L3 只在极少数 `SetParent` 失败的情况下临时启用，且必须带黑帧检测→自动回退。

## Part 5 — 详细改造规格

### 5.1 Rust 侧

#### 5.1.1 核心改动：`restyle_and_reparent` → `prepare_native_child`

**文件**：`src-tauri/src/shell/embed.rs:1022-1040`

**当前**（剥样式）：
```rust
let new_style = ((style as u32)
    & !(WS_CAPTION.0 | WS_THICKFRAME.0 | WS_MINIMIZEBOX.0 | WS_MAXIMIZEBOX.0 | WS_SYSMENU.0))
    | WS_CHILD.0;
```

**改为**（保留原生外观 —— **并且连 `SetParent` 都不再使用**）：

```rust
/// 原生窗模式（v1.1）：把第三方窗口「挂靠」到 Variable 桌面 —— 采用拥有关系
/// （GWLP_HWNDPARENT）而非父子关系（SetParent + WS_CHILD）。
///
/// 依据 D-1：子窗口会剥夺软件的原生最小化语义（v1.0 的死结）；
/// 拥有关系下窗口仍是完整顶层窗，− □ × 与拖动边框全部由软件原生处理。
/// Variable 获得：①窗口恒显示在桌面之上 ②不进 Windows 任务栏。
/// 代价：不再被父窗客户区剪裁 → 由 EmbedBridge + MOVESIZEEND 治理位置（D-1 治理①+②）。
fn attach_native_window(app: &tauri::AppHandle, hwnd: isize) -> bool {
    let Some(desktop) = desktop_hwnd(app) else { return false };
    unsafe {
        let h = hwnd_from_isize(hwnd);
        // 关键：不修改 GWL_STYLE —— WS_CAPTION / WS_THICKFRAME /
        // WS_MINIMIZEBOX / WS_MAXIMIZEBOX / WS_SYSMENU 全部原样保留。
        // 建立拥有关系（不添加 WS_CHILD，不做 SetParent）
        SetWindowLongPtrW(h, GWLP_HWNDPARENT, hwnd_from(desktop).0 as isize);
        // 确保可见（初始占位尺寸；随后由 EmbedBridge 的 embed_bounds 覆盖）
        let _ = SetWindowPos(h, HWND::default(), 240, 140, 900, 600, SWP_NOZORDER);
    }
    true
}
```

**与旧的 `restyle_and_reparent` 相比，三处本质差异**：
1. **完全不碰 `GWL_STYLE`** —— 一个样式位都不改，所以软件的标题栏与 − □ × 原封不动。
2. **不使用 `SetParent` / 不添加 `WS_CHILD`** —— 改设 `GWLP_HWNDPARENT`。
3. **不传 `SWP_FRAMECHANGED`** —— 没有样式变化需要通知。

**若 M3 Gate 发现拥有关系不满足需求**，回退路径为最小改动版：保留 `SetParent` + `WS_CHILD`，但**不剥样式**（即 `container.rs:189 wrap_child` 的做法）。此时唯一妥协=最小化仍不可靠。**仅在确认拥有关系走不通时才走此路径。**

**调用点替换**（原 `restyle_and_reparent` 的 4 处）：
- `embed.rs:1256` L1 主路径
- `embed.rs:1045` `reembed_into_session`
- `embed.rs:1196` CEF 家族 L3→L1
- `embed.rs:1223` `needs_reveal` 降级

## Part 7 — 状态机与消息流

### 7.1 嵌入会话状态（不变）

后端仅发三态，位置 `embed.rs:829-837`：

| state | 含义 | 前端动作 |
|---|---|---|
| `running` | 窗口正常呈现 | 清占位卡 + 重同步边界 |
| `orphaned` | 窗口消失但进程存活 | 显示占位卡 |
| `exited` | 进程树全亡 | **自动关闭占位窗**（R7 硬约束，已实现） |

前端第四态 `failed`（`thirdApps.ts:89`）在 `attached === false` 时写入。

### 7.2 原生窗模式下的完整链路

```
用户点击开始菜单图标
  │
  ├─ openVwmTpNew("tp:xxx")          开 VWM 虚拟窗（无 chrome，纯几何容器）
  │
  ├─ ipc.embedLaunch(id, winId)      Rust: embed_launch
  │     ├─ tp_launch_inner           创建进程
  │     ├─ wait_new_window           找到主窗 hwnd
  │     └─ attach_by_tier
  │            └─ attach_native_window  ★ 不改任何 GWL_STYLE
  │                                       GWLP_HWNDPARENT = 桌面（拥有关系）
  │
  ├─ EmbedBridge effect               （不再 -38）
  │     └─ ipc.embedBounds(x, y, w, h)  ← 完整 VWM rect，驱动窗口位置
  │
  └─ 用户看到：软件自己的窗口（自己的标题栏、自己的 − □ ×）
        │
        ├─ 拖软件标题栏 → 软件原生移动 → MOVESIZEEND → 回写 VWM rect
        ├─ 拖软件边框   → 软件原生缩放 → MOVESIZEEND → 回写 VWM rect   ← 让 Variable 记住新尺寸
        ├─ 点 −         → 软件原生最小化 → MINIMIZESTART → VWM 置 minimized
        ├─ 点 □         → 软件原生最大化/全屏
        ├─ 点 ×         → 软件原生 WM_CLOSE → 会话 watcher → exited → 占位窗自动关闭
        └─ Variable 任务栏点图标 → embed_visible(SW_RESTORE/SW_HIDE) 反向同步
```

### 7.3 「谁主谁从」的双向同步表

| 场景 | 主动方 | 通道 | Variable 侧动作 |
|---|---|---|---|
| Variable 移动/缩放/贴靠窗口 | Variable | `embed_bounds` → `SetWindowPos` | 无（已由请求驱动） |
| 软件自己被拖/被缩放 | 软件 | WinEventHook `MOVESIZEEND` | 回写 `win.x/y/w/h` |
| 软件自己最小化 | 软件 | WinEventHook `MINIMIZESTART` | `minimized = true` |
| 任务栏点图标还原 | Variable | `embed_visible` → `ShowWindow(SW_RESTORE)` | `minimized = false` |
| 软件自己关闭 | 软件 | 会话 watcher（既有的 2s 轮询） | `exited` → 自动关占位窗 |
