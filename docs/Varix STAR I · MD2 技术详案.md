## 篇 1 引导链工程详案

**职责一句话：从按下电源到内核第一行代码执行，这条链上的每一个字节——固件交接给谁、引导器读什么配置、内核镜像长什么样、单次引导变量怎么写怎么消费——全部在本篇定案。**

### 1.1 引导链全景与每段的职责边界

整条引导链分四段。第一段是固件自检（POST）：联想固件按 NVRAM 里的引导顺序找设备，我们的 thinkplus U 盘排在 USB 启动位，固件读它的 ESP 分区（FAT32，GUID 不变）并加载其中的引导器。这一段完全在固件手里，我们唯一能做的是保证 ESP 结构规范——文件都在该在的位置、分区表干净、FAT32 参数标准，让固件挑不出毛病。实测自检约四秒，这是预算（MD1 第 19.4 节）里不可压缩的常量。

第二段是 Limine 引导器接管：读同分区的 limine.conf，画菜单，倒计时，然后按选中条目加载内核。Limine 是我们的引导器选型（借力清单成员），选它的理由在总案已述——这里补工程理由：它的 Boot Loader Interface（BLI）协议给内核传递的信息丰富且版本化（BASE_REVISION 机制保证向后兼容），帧缓冲申请在引导期完成（内核醒来就有 1080p 画面可用，交接画面与启动 logo 因此零成本），以及关键的 LoaderEntryOneShot 单次引导变量——篇 1.5 专述。

第三段是内核早期启动：Limine 把内核 ELF 的段加载到指定地址、把 HHDM（更高半直接映射）基址、帧缓冲信息、内存图放进协议约定的结构，然后跳进内核入口。内核从入口到自举完成（页表重建、自己接管内存分配器）的一段代码必须小心：此时只有 Limine 给的有限信息，不能依赖任何未初始化的假设。

第四段是内核初始化到用户态：驱动枚举（USB、块设备、HDA、网卡）、四板斧校验（读 Windows 域加固状态）、根文件系统挂载前的准备、把控制权交给 vx-init。这一段结束时，"引导"才算完成，启动打点时间线在此时封口（篇 1.8）。

### 1.2 Limine 8.x 协议的工程要点

内核与 Limine 的全部约定通过"请求帧"（requests）表达：内核镜像里放一组标记结构，Limine 扫描并按需应答。我们使用且只使用以下请求，新增请求必须过 ADR：

第一条是 BASE_REVISION：声明我们针对的 BLI 协议版本（8.x 基线）。Limine 若不认识这个版本，会在应答结构里留下"不支持"标记，内核入口第一件事就是检查它——协议版本不匹配就拒绝启动并在屏幕上打出人话，绝不带病运行。这条检查是引导可靠性的第一道闸。

第二条是 framebuffer 请求：申请图形输出。Limine 在引导期初始化显示模式（实机锁定 1920×1080，BPP 32），把帧缓冲物理地址、间距（pitch）、像素格式交给内核。交接画面、引导菜单背景、内核 panic 保护屏共用这一份帧缓冲——引导期申请一次，全程不用再碰显示初始化，这是"开机就有画面"的工程前提。

第三条是 hhdm 请求与 memmap 请求：更高半直接映射基址与内存图。内核的内存管理（MD1 第 17.2 节的装载器与分页）完全建立在这两个应答上。第四条是 kernel_address 与文件相关请求：定位自身镜像（自校验用，篇 12 的可复现构建哈希比对需要它）。第五条是模块请求：为将来的内核模块预留的加载通道，STAR I 阶段保持空载，但通道就位。

工程红线一条：**内核不使用任何未在本清单登记的协议特性**。Limine 的特性面很宽（SMP、五级分页、GPU 特性等），每多用一个，引导链的测试面翻一倍——总案第 2 章"最小可用内核"的立场在协议层就是这个清单的长度。

### 1.3 limine.conf 逐字段注解

引导配置是用户看得见的引导层界面，也是交接协议的"地面端"。逐字段定案：

timeout 字段设为 5：菜单停留五秒，倒计时归零选默认条目。五秒是体验取舍——比固件四秒自检略长，用户来得及按键；比常用引导器默认的十秒短，不拖日常启动。按任意键立即停表选中（WD-005）。

第一个条目是 /kernel/varix：VARIX 内核本体。条目内 protocol 字段用 limine 协议（非 multiboot），path 指向 ESP 内的内核文件路径，内核文件名带版本号（varix-<构建号>.elf）并由启动脚本符号链接成固定名——保留历史版本文件以支持回滚（篇 12）。条目注释字段写人类可读的版本说明，菜单上不显示但磁盘上可查。

第二个条目是 Windows 11 (USB)：交接目标。它不指向 VARIX 的任何东西，而是指向 WINESP 分区（GUID 636786cb-e967-49f6-b0df-7608909d1f11）里的 Windows 引导文件。这个条目的存在性就是防自锁闸门校验的一部分——VARIX 每次启动读配置确认该条目与其指向的文件真实存在（WD-003 的灰显逻辑：不存在则菜单灰显条目并写人话提示，交接流程同步拒绝），绝不假装它还在。

配置文件头部还有 interface_version 与 hash 字段：前者固定协议版本，后者是配置文件自身的校验和——配置被意外篡改时启动画面给出警告（不阻断启动，但交接流程会把"配置校验失败"计入闸门判定）。

### 1.4 ESP 布局与文件清单

ESP 是固件与 Limine 的共同地盘，布局保持极简：/EFI/BOOT/BOOTX64.EFI 是固件兜底加载的引导器入口（可移动介质的标准路径，U 盘系统必须走这条路——内置盘才有 NVRAM 引导项兜底，我们只有这个标准路径）；/limine.conf 与 /limine.sys（Limine 的二次加载体）在根目录；/kernel/varix-<构建号>.elf 内核镜像；/varix/handoff/ 是交接画面的静态资源（字体、警示图）；/TOOLS/ 存放引导修复工具的自包含镜像（篇 12 的修复介质）。目录树之外不进任何东西——ESP 是引导专用区，用户数据、快照、缓存一律不落此处，把攻击面与误操作面都压到最小。

### 1.5 LoaderEntryOneShot 单次引导机制

这是交接协议的地面核心，值得逐句讲清。

机制本体：Limine 支持在自身配置旁维护一个单次引导变量。VARIX 内核在运行期把这个变量的值写成某个条目的标识（例如"下一次引导选择 Windows 11 (USB) 条目"），然后正常重启。重启后 Limine 读到该变量，引导它指向的条目，**随即把变量作废**——再下一次开机回归默认条目。变量是"一次性的命令条"，不是持久状态。

它解决了什么问题：传统方案是写固件的 BootNext NVRAM 变量——下次引导一次性进指定项。但联想固件对第三方写入的 NVRAM 引导数据有过滤行为（实锤记录见 1.6），且 NVRAM 写入有量限与损坏风险（Q7）。OneShot 变量完全活在引导器自己的文件层（ESP 内），固件根本看不见它，自然也不受固件过滤；文件层写入比 NVRAM 写入更可控、可校验、可撤销。

与 BootNext 的关系：BootNext 路径保留为兜底（现有 handoff.rs 的能力不删），OneShot 优先。优先级逻辑在篇 2 的交接状态机里：OneShot 写入成功且校验通过才走直通路径，否则降级 BootNext，再不行才允许人工路径（Limine 菜单选择）。三条路径的存在本身就是判据 1 的"零盲区"——任何一条路径失效都有下一条接住。

消费即焚的验证：交接流程写完变量后重启，VARIX 下次启动（从 Windows 域交接回来时）读该变量，预期是"不存在"——如果仍然存在且值未消费，说明上次引导没有经过 Limine 的消费逻辑（异常信号），写入诊断事件。这个"回读验证"是 Q1（OneShot 写了但固件没交给 Limine）的地面自检。

### 1.6 联想固件过滤实锤记录（工程备忘）

把实机观察固化成文，防止后来者重新踩坑。观察一：通过标准工具写入的 NVRAM 自建引导项，在 F12 临时启动菜单里不显示——固件接受写入但不呈现，引导顺序管理界面同样不可见。观察二：使用超长 FilePathList 的引导条目写入后行为不稳定，缩短描述符（控制条目数在四个以内）后写入可被接受但仍不显示在 F12。观察三：BootNext 写入在实机上偶发被忽略（写入返回成功、重启后未生效）——发生概率低但不可忽略，这正是交接协议不允许"单点信任 BootNext"、必须有三路径降级设计的直接原因。观察四：内置引导项（Windows Boot Manager 等）始终正常——固件对"自己认识的"和"外来者"区别对待。

由这些观察得出两条工程结论：其一，**一切引导可靠性设计都不能依赖"固件会听话"**，OneShot 文件层方案因此成为主路径；其二，**内置引导项与固件本体是禁区**（总案边界红线），任何清理、优化、"顺手修复"都不允许触碰固件 NVRAM 的原生条目——我们只在固件给我们留的缝隙里活动，缝隙之外一步不迈。

### 1.7 防自锁闸门的引导层实现

闸门在交接前验证的三条件，在引导层的实现口径：条件一，目标存在——读 limine.conf 确认 Windows 条目存在，读其指向的 WINESP 分区确认引导文件存在且可读；条件二，目标可信——引导文件的哈希与上次成功交接时记录的哈希比对，不一致不阻断但降级为"用户确认后放行"（Windows 更新换引导文件是正常事件，但要人眼过目）；条件三，回路可回——确认 VARIX 自己的条目完好（回程的路必须先修好再出门）。三条件的判定结果与失败原因写入诊断事件，交接画面显示人话摘要。注入测试矩阵（20 组破坏场景：删条目、改 GUID、截断文件、填满 ESP 等）作为判据 1 的一部分在实机执行（MD1 第 33.1 节）。

### 1.8 启动打点时间线

预算要对账，打点要先行。打点点位固定十一个：固件交棒（Limine 最早可打的时间点）、菜单选择完成、内核入口、页表与内存自举完成、驱动枚举完成、四板斧校验完成、块设备就绪、根文件系统挂载完成、vx-init 启动、合成器首帧、桌面就绪。每个点位一个单调时钟时间戳，写入内核日志环形缓冲，启动完成后落 ext4 的启动报告文件（诊断中心可视化，MD1 第 36.2 节）。打点的实现纪律：时间戳采集函数必须零分配、无锁、常数时间——打点代码自己成为启动慢的原因是本末倒置。

### 篇 1 判据勘误回写（WP-106 对练连带 · 2026-09-24 · QEMU 真引导实证）

**B-101 判定语义勘误（红项处置）**：WP-101 交付的 `base_revision_confirmed` 按"确认 = 三词全零"判定，宿主测试用自洽字面量全绿；WP-106 对练首次 QEMU 真引导即 BOOT REFUSED——实证 Limine 12.9 确认后标记实为 `[magic0, used_rev=1, 0]`，**非全零**。协议原文（PROTOCOL.md "Base protocol revisions"）：支持所请求 revision 时**引导器只把第 3 成分（请求号）清零**；且支持 base revision 3+ 的引导器**强制把第 2 成分改写为实际使用的 base revision**。官方判定宏 `LIMINE_BASE_REVISION_SUPPORTED(VAR) ((VAR) == 0)`（VAR = 第 3 成分）与本实证互证。修复：判定改为 `marker[2] == 0`（未处理/不支持/确认三态全覆盖），测试字面量换为协议真实形态（`[0xf9562b2d5c95a6c8, 1, 0]` 判确认）。**教训入库**：宿主单测的自洽字面量不等于引导器语义——凡是与外部系统有 ABI 契约的判定，必须在真实对端上做一次对练才能记"绿"。

## 篇 2 交接协议字段级详案

**职责一句话：双域接力的全部数据面与控制面——交接分区里每一个字节的含义、交接状态机的每一个状态、每一条异常路径的归宿——本篇是交接协议的唯一权威定义。**

### 2.1 交接状态机全景

交接是一个五步状态机，状态名即代码里的枚举值，任何中间态都有明确出口。状态一 idle（常态）：一切照旧，交接入口按钮可见。状态一到状态二的迁移由用户确认触发（点击"切换到 Windows"或反向按钮）。状态二 preserving（保全中）：采集会话状态写交接分区，可取消（用户反悔则一切照旧，分区里留下一个标记为废弃的半成品快照，下次交接时清理）。状态三 flushing（冲刷中）：**此状态不可取消**——文件系统日志冲刷一旦开始必须完成，界面显示"正在安全保存，请勿断电"，防抖规则在此生效（重复点击只显示进度）。状态四 arming（武装中）：闸门三条件判定、写 OneShot 变量、校验写入——任何一步失败则迁移到 aborted 状态并给出人话原因与下一步指引，系统继续正常运行（武装失败等于没发生）。状态五 rebooting（重启中）：显示交接画面直至内核交出最后控制权，此状态只有一个出口——重启。

五个状态、七个迁移、零个无出口状态。状态机实现为一颗显式的转移表（代码里表驱动，不散落 if），每次迁移写一条体验日志事件（谁触发、从哪到哪、耗时多少）——宪章第十三章的浮层生命周期要求在这里以状态机生命周期兑现。

### 2.2 交接分区与快照文件的完整定义

交接分区是 FAT32 小分区（选型理由见 MD1 附录 E 的 ADR-011），布局两个目录加三份固定文件：/vx-snap/（VARIX 写的快照）、/var-snap/（Windows 域 Variable 助手写的快照）、/diag/（双方都可写的诊断包暂存）。两侧各写各的目录（Q11 的单写方原则），读对方目录只读不写——文件系统层的权限分离，配合校验和，构成最简单也最可靠的互信模型。

快照文件（handoff.json）的完整字段定义如下，字段一经定案只增不改不删（向后兼容红线）：schema_version，整数，当前值 1，跨域协商的锚点——读到不认识的更高版本时按"能读多少读多少"降级处理并在恢复提示里注明。created_at，UTC 时间戳带时区标记，交接时刻。source_domain，字符串枚举，取值 varix 或 windows，快照作者。windows，数组，每项含 app_id（应用唯一标识，原生应用取 vxapp 的 id，Wine 应用取"Wine/〈前缀名〉/〈程序名〉"复合标识）、title（窗口标题字符串，用户可在设置里关闭标题采集，关闭后此字段为空串）、geometry（x、y、宽、高、所在显示输出标识的整数组合）、workspace（整数工作区号）、focused（布尔，是否焦点窗口）。drafts，数组，每项含 path（草稿文件在共享可读路径下的位置——注意草稿必须落在对方域读得到的路径：VARIX 侧草稿落 DATA 分区约定目录，Windows 侧同样，两侧约定目录名在 schema 常量表里）、sha256（内容哈希，恢复时校验文件没换）、app_id。clipboard，对象，kind 枚举取值 text 或 files；text 时 content 字段直接放文本（上限 256KB，超出则截断并置 truncated 标记——剪贴板接力不做大文件搬运，那是文件接力的活）；files 时 content 是路径数组（同样指向共享可读路径）。restore_hint，字符串，给对方域恢复提示框的文案。integrity，字符串，整个 JSON 文本（不含本字段）的 SHA-256，读方先验哈希再解析——分区损坏时宁可放弃恢复也不解析半截数据（Q6）。

字段表的维护纪律：本节是唯一权威定义，代码里的结构体、Windows 侧助手的实现、测试夹具三处与它对表；新增字段走小修订（版本号递增），语义变更走 ADR。

### 2.3 保全流程的实现细节

窗口清单采集：合成器是唯一知情者——它维护全部表面的注册表，保全时直接从合成器取（应用不需要配合，崩溃中的应用也能被记录）。标题采集走 VXWM 的表面元数据（应用绑定时报的标题），敏感应用可在绑定申请时声明 title_private 标记，合成器据此输出空标题（Q80 与场景十一的隐私红线在协议字段层的落点）。几何采集取当前布局快照，多显示器场景记录输出标识，恢复时输出指纹不匹配则触发重排（Q71）。

草稿保全：应用主动登记（vx-SDK 提供 draft_register 接口，传入路径与哈希）而不是系统扫描——系统猜不出什么算草稿。VSCode 这类自带恢复机制的应用可以不登记（它的草稿它自己管），登记与不登记都在恢复提示里如实呈现。剪贴板保全：文本直接入快照；密码管理器类窗口（进程名匹配已知列表 + 窗口类标记双条件）的复制默认跳过（Q13），跳过时快照里记录"clipboard_skipped_reason"字段，让用户知道不是系统吞了内容。

### 2.4 冲刷与闸门的代码路径

冲刷顺序是硬性的：应用层缓冲冲刷（vx-SDK 的会话结束回调）→ ext4 日志提交 → 交接分区 FAT 表冲刷 → 块层队列排空 → 最后才允许进入武装状态。每一步有超时（合计预算十五秒，MD1 第 21.5 节的全程二十五秒里给它一半多——数据安全的时间要舍得给），超时则停在 flushing 状态报错，绝不"差不多就重启"。

闸门三条件的代码路径在 MD2 篇 1.7 定了口径，这里补交接层的衔接：三条件全过 → 写 OneShot 变量 → 读回校验（写入即验证，不等重启才发现）→ 进入 rebooting。读回不一致则立刻降级 BootNext 路径重试一次，再失败则 aborted 并给三路径全部失败的人话诊断（这种情况按 Q1 的设计预期为零——但代码必须写它）。

### 2.5 视觉接力的实现

交接画面的设计原则是"全程有画面、全程有进度、全程说实话"。画面脚本四帧：第一帧"正在保存您的工作"（preserving 进入时，进度条取保全子任务的完成度）；第二帧"正在安全保存到 U 盘"（flushing，进度条走冲刷各步）；第三帧"正在准备切换"（arming，无进度条——这步要么几秒完成要么报错，装进度条就是撒谎）；第四帧"正在切换到〈目标域〉"（rebooting，静止画面加一个呼吸动画，直到画面消失重启接管）。四帧共用交接画面的模板，文案走字符串表（MD1 第 27.1 节），错误分支复用三要素模板。实现位置：交接画面运行在合成器之上的独立全屏层（占有最高 z 序与输入独占），内核侧不再画任何交接 UI——这与 MD1 第 28.1 节"内核自绘 UI 退役"的名册条目对齐。

### 2.6 反向交接与 Windows 侧助手

Windows 域的"重启到 VARIX"由 Variable 侧的交接助手执行，它实现的协议面刻意窄：读取 VARIX 快照（只读）、写 /var-snap/ 快照、执行重启（经 BootNext 或菜单默认项——Windows 侧不写 OneShot 变量，那是 VARIX 引导链的内部机制，Windows 侧走 BootNext 且 VARIX 启动时对 BootNext 残留做消费验证）。窄协议的理由：Windows 侧的运行环境不可控（更新、权限、安全软件），暴露面越小越可靠；交接的智能全部在 VARIX 侧，Windows 侧只当"接力棒"。助手崩溃的处理：VARIX 启动时检测 /var-snap/ 无快照且时间戳异常，提示重装助手（Q12），不阻塞 VARIX 启动。

### 2.7 异常矩阵

四种异常的归宿：交接中断电（Q2）——保全未完成则无快照，另一侧启动时按"无快照"处理；冲刷中断电则 ext4 日志重放兜底（篇 7.6）；武装中断电则 OneShot 要么没写要么完整写入，无中间态。OneShot 残留（Q1 与 1.5 的回读验证）——写诊断事件并清理。双向同时请求（Q10）——交接入口在 preserving 状态即锁定，第二次请求被拒绝并提示。快照损坏（Q6）——完整性校验失败则放弃并提示，快照文件保留供诊断。

**schema 冻结补刀（本包定案——篇 2.2 未定死的实现契约，冻结于此，两端同源）**：

2. **草稿共享目录定名**：`/vx-drafts/`（VARIX 侧）与 `/var-drafts/`（Windows 侧）——与快照目录命名对称，进 schema 常量表。
3. **状态计数口径**：正向主干五步 = idle→preserving→flushing→arming→rebooting；aborted 是 arming 失败的错误分支状态（计入枚举、不计入主干）。七迁移 = 主干四边 + preserving 取消边 + arming 失败边 + aborted 中止确认边；rebooting 的出口是物理重启（协议终点事件），aborted 的出口是用户确认。

5. **重复键一律拒绝**：写方永不产生重复键（确定性序列化），读方（Rust 解析面与 Python object_pairs_hook）见到即拒——integrity 剥除规则依赖确定性。

## 篇 3 Windows 域加固实录

**职责一句话：Windows 域是双域的另一半，但它跑在 U 盘上时有一身出厂习惯不合适——本篇把实机验证过的加固手段逐项定案，从"救火脚本"升格为"产品级加固包"。**

### 3.1 加固的哲学：先把事故史读一遍

Windows 对"从 U 盘启动"这个形态的支持是出厂即有的，但默认参数是按内置硬盘调的。U 盘的物理特性（BOT 协议的半双工、USB 总线的电源管理、块设备的响应延迟）与内置盘截然不同，于是出现了一类怪病：系统正常运行几分钟后，U 盘块设备集体失联，事件日志里躺着一串 0xED 类错误，然后系统假死或蓝屏。这类事故在实机上反复出现，四板斧就是逐条根治它的处方——每一条都先在实机复现、再定位根因、再验证药效，全部通过后才收入加固包。加固包的形态是一个带防呆与回滚的 Python 脚本集（_attic 收编，MD1 第 28.2 节），由 Windows 侧的交接助手在部署时调用，也支持手动执行。

### 3.2 第一板斧：UAS 到 BOT 的强制降级

根因：Windows 10/11 对 U 盘默认启用 UASP（USB Attached SCSI Protocol），而实机的 U 盘主控在 UASP 路径下长时间运行后出现协议级失联（0xED 事件的直接来源）。处方：让系统改用 USB 大容量存储的老协议 BOT——慢一点，但稳如老狗，且 U 盘整机对块设备吞吐的真实瓶颈根本不在协议快慢上（篇 7 的预算表说得清楚）。

实现走注册表重定向而非删文件：uaspstor.sys 的服务注册项 ImagePath 指向 ubstor 系（把 UAS 驱动的启动改为手动并让 usbstor 接管存储设备），全程零文件操作。为什么坚持不删 uaspstor.sys 文件本身：实机尝试时确认它是三硬链接的系统文件，删除会伤及系统完整性且被系统文件保护机制拒绝——零文件操作原则（MD1 第 28.2 节）由此立下：**凡能用注册表与策略解决的，不碰文件；凡碰文件的，先列清单拿确认。**

落地字段：目标机器的 SYSTEM 配置单元（U 盘 Windows 域的注册表）在离线装载（reg load 到临时键）下修改 storahci 与 UASP 相关联动项，Start 值与 ImagePath 逐一重定向，写完卸载落盘，重载复核。复核读数是判定的唯一标准——写完不读回等于没写（用户雷区：凭印象确认）。

### 3.3 第二板斧：禁用 USB 选择性挂起

根因：Windows 的电源管理会在认为 USB 设备空闲时挂起端口，U 盘从挂起中唤醒的时序在某些主控组合下超时，表现为"放到那儿不动几分钟，一保存文件就卡死"。处方：电源计划里禁用 USB 选择性挂起（离线状态下写注册表的 Power 设置项），同时对 U 盘对应的设备实例写 DisableSelectiveSuspend 标记。副作用评估：待机功耗略增——U 盘整机系统不在乎这个，省电模式换稳定性是笔划算的买卖。复核点：挂起标记在设备管理器层与电源计划层都要生效，只改一处是常见错误。

### 3.4 第三板斧：块设备 IO 超时加固

根因：U 盘 BOT 协议下大块写入（比如 Windows 的批量元数据刷盘）偶发长时间响应，默认 IO 超时值（注册表 Disk 的 TimeOutValue，默认十进制约 10 秒级别）判死太快，一判死就重置设备，一重置就是连环 0xED。处方：TimeOutValue 提到 0x50（八十秒级）——给 U 盘足够的"喘息时间"，让它慢慢写完而不是被误杀。这个值的确定过程：先取 0xf 观察仍有误杀，再阶梯上调到 0x50 后绝迹，中间值未做精细寻优——稳定性判据是"绝迹"而非"最优"，取已验证值不贪快。连带项：Disk 驱动的超时相关键一并加固，避免非分页缓冲池不足引发的次生重置（SrbFlavor 类参数按实机验证清单设置）。

### 3.5 第四板斧：BCD 防自愈闸

根因：Windows 的大版本更新与服务优化会重写引导配置数据（BCD）与引导顺序——我们的交接地面（Limine 菜单的 Windows 条目、引导顺序）可能被"好心修复"掉（判例 18 与 Q3 的来源）。处方两层：其一，部署时把关键 BCD 项（交接分区引导项的存在性、超时值、默认项）的哈希记录在案；其二，VARIX 每次启动时校验该哈希（读交接分区的记录文件），不一致则交接入口显示"检测到 Windows 侧引导配置变动"，一键重打闸门脚本。闸门哲学与防自锁一脉相承：**不阻止 Windows 做它要做的事（大更新该让它更新），但每次启动都检查它有没有顺手拆我们的家，拆了就修回来。**

### 3.6 VC 运行库六件套

事故史：Variable 在 Windows 域首次启动时弹窗报 VCRUNTIME140.dll 缺失——系统是精简部署，缺 C++ 运行库。处方：运行库六件套离线部署（vcruntime140、vcruntime140_1、msvcp140、msvcp140_1、msvcp140_2、concrt140），文件来源为官方 redistributable 解包，逐文件 SHA-256 校验后落 Windows 域 System32 与 SysWOW64（六十四位与三十二位各就各位），实机验证 Variable 弹窗成功。工程化要点：部署脚本同样带校验（先验包内文件哈希、再验落盘哈希、最后用依赖探测函数验证加载成功），三段全绿才算部署完成——"文件复制过去了"不算数，"程序能加载它"才算数。

### 3.7 脚本工程纪律（从救火到产品）

加固包脚本的四条纪律：其一，遗言机制——每一步 try/except 包裹，任何异常写入带时间戳的遗言日志后再退出，绝不无声死亡（v1 脚本因 U 盘瞬时掉线无声崩溃的教训，MD1 第 28.2 节）；其二，装载纪律——reg load 的临时键用完必须 unload，异常路径也要 unload（之前因残留装载键导致"文件被占用"连环误案，诊断时先查残留装载是标准动作）；其三，写后必读——每项修改落盘后重载复核，输出前后对照；其四，幂等可重跑——脚本对已加固的项跳过而非报错，重复执行无副作用（复检场景必然重跑）。

### 3.8 复检清单

Windows 域每次大版本更新（或用户手动跑过"优化工具"）后执行复检：四板斧逐项读回、VC 运行库加载探测、BCD 闸哈希比对、交接分区可达性——四项全绿则域间互信维持，任何一项红则提示重跑对应加固项。复检入口两处：VARIX 侧闸门自动提醒（3.5），Windows 侧助手的"域健康"按钮。

## 篇 4 Linux 系统调用转译层（Linuxulator）

**职责一句话：让 Linux 用户态二进制在 VARIX 上以为自己住在 Linux 里——四个 syscall 类别、一张差异表、一套测试方法，本篇是转译柜台的唯一权威设计。**

### 4.1 设计立场与方法论来源

转译柜台的方法论对标两个成熟前辈：FreeBSD 的 Linuxulator（几十年历史的 Linux 二进制兼容层）与 WSL1（Windows 的系统调用转译方案）。共同精髓一句话：**在内核边界装一个翻译柜台，应用讲 Linux 方言，柜台逐句翻译成本地方言，应用毫无察觉。**我们研读两者的公开文档与行为规范，不读也不引入 Linux 内核源码（总案第 10 章与第 29.2 节的 GPL 立场）——语义对齐 Linux 用户态约定（手册页与 POSIX 规范是行为准绳），实现全部自研于 VARIX 内核接口之上。

柜台放内核态（MD1 第 17.4 节的决策）：ABI 引导识别到 Linux ELF（解释器为 ld-linux 系）后，进程的系统调用入口切到柜台处理路径，翻译结果直达内核对象——没有中间层、没有跨态往返，这是转译开销压到两微秒级的结构前提。

### 4.2 四百个系统调用的分类治理

Linux 用户态约定约四百个系统调用入口，逐个治理不现实也无必要——按"依赖频率乘实现难度"分四类处理：

第一类是**改名直通类**（约四成）：文件读写（open、read、write、close、lseek、stat 系）、进程基础（getpid、exit、wait 系）、内存（mmap、munmap、brk、mprotect）、时间与环境（gettimeofday、clock_gettime、getenv 类）——这些调用的 VARIX 原生语义本就与 Linux 对齐（vx-SDK 刻意按 POSIX 设计，MD1 第 24.2 节），柜台只做参数格式转换与 errno 原值直通（C-4 契约），实现成本接近零。

第二类是**语义适配类**（约三成）：信号系（Linux 信号表与 VARIX 信号的映射，实时信号区间对齐）、进程克隆系（clone 的标志子集支持：新线程与新进程两种形态，其余标志位返回不支持错误）、文件描述符高级操作（poll、select、epoll 系列——epoll 在柜台内实现为事件环的封装，语义子集支持常用的水平触发与边缘触发，简化项如实返回对应错误码）、杂项（uname 返回约定字符串、sysinfo 给出内核账本数据）。

第三类是**柜台自实现类**（约两成）：Linux 特有但用户态依赖重的——futex（对齐 VARIX 内核 futex 原语）、memfd 与匿名对象、procfs 与 sysfs 的文件语义（返回柜台合成的伪文件内容，篇 4.4）、伪随机与加密熵源接口。

第四类是**明确拒绝类**（约一成）：io_uring 全族（返回 ENOSYS——异步 IO 框架的语义深度与 U 盘整机的 IO 模型不合，应用应有退化路径，MD1 第 24.4 节）、cgroup 与 namespace 管控族、模块加载族、bpf 族。拒绝不是失败——**每一项拒绝都在差异表登记，应用撞墙时得到指名的错误与文档指引（Q23），这是"诚实的边界"的柜台层兑现。**

### 4.3 errno 与 ABI 细节纪律

转译的正确性藏在细节里，三条纪律是红线：其一，errno 编号原值直通（C-4）——柜台内部错误码与 Linux errno 的映射表唯一且全覆盖，应用按 Linux 语义分支的行为保持一致；其二，结构布局对齐——stat、sigaction、termios 等穿越边界的结构体按目标 ABI 的字段布局逐字节对表（含机器字长、对齐填充），映射函数自动生成（结构定义单一来源，生成器保证三处一致：柜台、测试、文档）；其三，长度参数不信任——一切带长度字段的调用做边界校验后再进内核对象，外部输入全清洗（总案安全章的柜台落点）。

### 4.4 伪文件系统面（proc、sys、dev 的柜台实现）

Linux 应用的运行期待 /proc、/sys、/dev 的存在。柜台不建真文件系统，而是在 vxrun 的挂载视图里挂"合成目录"：读请求由柜台按当前内核状态即时合成内容。/proc 提供的子集及语义：self（指向进程自身目录）、〈pid〉 目录（cmdline、status、stat——数据取自进程账本，字段按 Linux 格式排版）、cpuinfo、meminfo、mounts、uptime。/sys 提供设备枚举最小集（block、class/net 的设备名与关键属性）。/dev 提供 null、zero、full、random、urandom（熵源接内核 CSPRNG）、shm。每个合成文件登记在伪文件清单（MD1 第 24.3 节），清单外路径按"文件不存在"返回——应用依赖了没实现的面时得到的是标准错误而非诡异行为（Q23 的另一半）。

### 4.5 vxrun 与封闭依赖视图

启动包装 vxrun 的四件事（MD1 第 24.2 节）在本篇的工程细化：第一步构造挂载视图——/compat/linux/〈应用名〉/ 下的根树（应用自带库与应用文件）挂为可见根，VARIX 的 /home、/dev 合成目录、伪 proc/sys 按只读或授权方式桥入；第二步环境注入——PATH、HOME、LANG、代理与主题变量按会话服务下发的注入表设置（判例 14）；第三步 ABI 登记——把进程的 ELF 解释器指到封闭树内的 ld-linux，向柜台注册该进程的 ABI 身份；第四步移交内核装载器（MD1 第 17.2 节的 ELF 路）。封闭树磁盘占用上限 800MB（Electron 级），超限星卡登记——这是磁盘配额治理（19.3）的直插级条款。

### 4.6 测试方法与验收

柜台的测试三层：单元层——每个系统调用翻译函数的参数与返回值用例（含边界与错误路径），errno 映射表全覆盖测试；语义层——LTP（Linux Test Project）测试集的合规子集离线跑（测试代码是测试不是 Linux 内核，使用合规），失败用例逐个归因：柜台缺陷修柜台，语义取舍登记差异表；应用层——验收载体（MD1 第 24.6 节：二十个静态 CLI、VSCode、Java 与 Python 运行时）真实运行，行为与 Linux 参考机对照。微基准：syscall 往返延迟两微秒上限（19.1）用专用基准测（空调用百万次取 P95）。

## 篇 5 显示栈与 VXWM 实现

**职责一句话：从合成器的主循环到客户端提交的一个像素，中间的每一条协议报文、每一块共享内存、每一次脏区合并，本篇讲到能直接开写的深度。**

### 5.1 合成器主循环与帧生命周期

合成器是一颗单线程事件泵加一条合成管线。事件泵的输入源四类：VXWM 报文（客户端动作）、输入事件（来自输入子系统）、帧回调时钟（垂直节奏或软件定时）、内部超时（看门狗心跳、动画推进）。主循环每一圈做的事固定：排空事件队列并归并状态变更、按脏区集合决定本帧是否需要合成、需要则执行合成管线并翻页、然后睡到下一个事件。**"不需要就不合成"是空转成本压到单核百分之五以下的结构基础**——静止桌面时主循环长眠，只有光标层独立小步走。

一帧的生命周期分四步。第一步收集：把本帧要处理的客户端缓冲提交（buffer_attach 加 damage 加 commit 的组合）收齐，未提交的应用沿用上一帧内容。第二步合成：按 z 序把每个表面变换（位置、缩放、透明度）后拷贝进后备帧——软渲染下这是纯内存搬运加混色，内存带宽是唯一稀缺资源，所以拷贝严格限制在脏区并集内，并优先用带预取的行拷贝。第三步后处理：光标层、拖放预览、交接画面这类系统层最后叠加。第四步提交：脏区写回真实帧缓冲并翻页，给相关客户端发帧回调（frame_callback），宣告"这帧你的内容已上屏，可以画下一帧了"。帧计时打点在第二与第四步各一枚，vxbench 的拖动帧率判据（55fps）读的就是这两点的间隔分布。

### 5.2 VXWM 报文编码与共享内存缓冲

协议编码定案：报文定长头（类型、序号、长度、发送方对象标识）加变长体，体按类型定案字段序，全部小端、无指针、自描述校验和尾缀——报文可在诊断日志里原样落盘回放（体验日志与协议日志同格式，调试时可以"重放一天"）。二十四类消息的枚举与语义在 MD1 附录 H 定案，本篇定编码层三件事：其一，报文上限 4KB，超限的大载荷（如剪贴板文件清单）走"报文里放引用、内容走共享内存环形区"的旁路；其二，序号单调，乱序与重复在协议层拒绝并计数上报——静默丢包与静默重放都是缺陷；其三，版本协商在 bind 时完成，客户端与合成器的协议小版本不一致时按"双方都认识的子集"降级，降级事实写进诊断。

客户端缓冲是共享内存对象：应用向系统申请一块匿名共享内存（上限与配额走 19.3），把它包装成表面缓冲提交。合成器与应用各自持有映射，所有权语义清晰——提交后缓冲归合成器读到下一帧回调为止，客户端在此窗口内不许复用（双缓冲起步，三缓冲给需要高帧率的动画应用，数量进表面配额）。这条所有权纪律防住一类经典腐坏：应用边画边被合成，用户看到半帧。

### 5.3 脏区合并与帧率策略

脏区合并策略三档：单表面小脏区直接并进本帧；大面积滚动（终端、长列表）识别为"平移模式"，用整块搬移代替逐行混算；全屏动画（交接画面、系统过渡）切全帧模式。帧率策略与之联动：脏区驱动帧（有活才画）、动画期节流到 sixty、拖动窗口时跟随输入事件率但上限封顶——封顶值即预算表帧率上限，超载时优先保输入响应而不是保完整帧率（掉帧可接受，手感迟滞不可接受，宪章第八章的 P95 原则）。所有策略参数集中在一个调参表里，实测调优不动代码只动表。

### 5.4 文字渲染管线与字形图集

文字最终呈现走 cosmic-text：它的职责是整形（哪个字符用哪个字形、阿拉伯连字、中文标点压缩）与排版（折行、对齐、混排间距），输出字形与位置的列表；我们的职责是把这些输出变成屏幕像素。管线四步：应用请求文本布局（传入字体链、字号、约束宽度）→ 布局结果缓存（同参数命中缓存零成本）→ 字形光栅化（每个字形一次，结果进字形图集——一张大纹理式的内存图，LRU 上限六十兆，常用汉字集常驻）→ 位块输出（从图集拷到目标缓冲，带色彩与透明度）。判据挂钩：中文折行与避头尾由 cosmic-text 规则保证（MD1 第 27.2 节），等宽混排两格计宽在布局请求的参数里显式声明（判例 21），125% 与 150% 缩放时字号走缩放因子而字形按目标像素尺寸重新光栅化（不是位图拉伸——拉伸的字在缩放下是糊的，重新光栅化的字是锐的）。

### 5.5 光标、浮层物理强制与输入路由

光标是合成器的私有表面，位置每输入事件更新、渲染每帧叠加，光标移动永远不经过客户端——软渲染下"应用卡死光标也卡"是不可接受的，宪章"点击百毫秒内有反馈"的最后一道保障就是光标永不卡。浮层物理强制（MD1 第 17.1 节）的实现：popup_grab 报文让合成器建立抓取关系表，抓取存在期间，抓取区域外的任何点击由合成器直接转译为"关闭浮层"事件发给浮层所有者，Esc 键同理——客户端拿不到"忽略外部点击"的能力，宪章第二章的出路清单从协议层就是真的。输入路由按焦点链：键盘事件投给焦点窗口，指针事件按命中测试投给对应窗口，命中测试在合成器（它唯一知道全局 z 序），窗口拿到的永远是"已被裁决"的事件流。

### 5.6 会话快照与合成器的恢复

合成器被看门狗拉起时的恢复路径依赖两个持久面：表面注册表（窗口清单、几何、缓冲引用）每变更即写内存映射的恢复文件（不是每帧写盘——写盘走写合并，五秒窗口内崩溃最多丢五秒的布局变更，可接受）；已提交缓冲在共享内存里与合成器生命周期解耦（内核记账），新合成器起来后按注册表重接。恢复判据就是 D-04：三秒内窗口回位、焦点恢复到崩溃前的窗口。

## 篇 6 网络栈实现

**职责一句话：smoltcp 在内核里怎么接驱动、socket 系统调用怎么到柜台、DNS 与 TLS 怎么给上层一个干净的地板——本篇把"能上网"拆到可验收。**

### 6.1 栈与驱动的接缝

smoltcp 以库形态编进内核（MD1 第 17.4 节决策），它需要一个"设备"抽象来收发包，我们写的是这层适配而非协议本身：驱动的接收中断把帧搬进环缓冲，适配层把帧喂给栈；栈要发帧时适配层把帧交给驱动的发送队列并管理完成回报。接缝处两条纪律：其一，零拷贝优先——环缓冲的描述符直接交给栈引用，只在必要时复制，BOT 时代的教训（拷贝一层丢一层性能）在这里提前规避；其二，背压显式——环满时丢弃并计数，丢弃计数进系统监视器，静默丢包是诊断时最恨的黑洞。

驱动清单按硬件矩阵排期：RTL8168 有线（Y7000 板载，第一批）、USB 网卡（RNDIS 与 NCM 两类，手机共享的关键通道，第一批——判例侧它是 WiFi 空窗期的用户生命线）、Intel 无线（第三批，固件从 linux-firmware 载入，装载器校验固件哈希）。无线适配的复杂度（扫描、认证、漫游状态机）集中在驱动侧，栈与 socket 层无感。

### 6.2 socket 系统调用面

内核 socket 面按 POSIX 语义实现（MD1 第 17.4 节），柜台改名直通率因此极高。实现要点五条：其一，描述符表统一——socket 与文件共用描述符空间，poll 与 close 等聚合调用天然一致（Linux 应用对此有强预期，混表是兼容性高频坑）；其二，非阻塞与事件——socket 支持非阻塞标志与 O_NONBLOCK 语义，柜台 epoll 封装的事件环以内核完成队列为源（篇 4.2 第二类），边缘触发的"只报一次"语义如实实现；其三，缓冲与水位——收发缓冲按 socket 类型配默认值，SO_RCVBUF 类选项可调，上限受会话内存配额约束；其四，错误语义——连接被拒、超时、网络不可达的 errno 全按 Linux 值（C-4），应用的重试逻辑行为不变；其五，监听授权——默认仅出站，监听 socket 创建需应用权限清单声明（MD1 第 10 章补矩阵的柜台执行点），未声明则返回权限拒绝错误并在诊断事件记录。

### 6.3 DNS、TLS 与会话级服务

DNS 解析走 hickory-dns 用户态库（借力清单），会话服务内置解析缓存与 DoH 开关（Q54）：默认用系统 DNS，设置中心可切 DoH；解析失败的三要素文案里带"请检查网络或切换 DoH"的下一步。TLS 全线 rustls：系统证书库随 VARIXSYS 分发（Mozilla 根证书集的开源快照，更新随季度窗口），rustls 的证书校验失败时给应用完整链信息——诊断能力是库白送的，用好它。代理支持按环境变量标准（HTTP_PROXY 系），会话服务统一注入（判例 14），应用无感。

### 6.4 诊断三件套

vx-ping（ICMP 回显与统计）、vx-route（路由表与接口状态）、vx-capture（抓包落盘，pcap 格式，与通用分析工具互通）是网络判例的取证基础（MD1 第 17.4 节）。实现要点：三件套走内核诊断通道而非普通 socket（raw 权限收敛在系统工具里），输出全部机器可读（JSON 行）加人类可读双格式——星卡脚本可以直接消费，人也能直接看。判例挂钩：Steam 登录（SC-041）、git 推拉（SC-005）等网络相关判例的失败归因第一步都是三件套取证。

### 6.5 无网与弱网的诚实呈现

离线态是头等公民：网络服务降级（MD1 第 25.1 节）时桌面明确标注"离线"，星图的应用更新按钮变灰并说明原因，vscode 等直插应用的网络失败得到三要素报错——绝不出现"转圈十分钟后超时"的黑箱。弱网（高丢包）场景：栈参数（重传、窗口）按 smoltcp 默认起步，判例复测时如遇弱网病再调——先测量后调参，不凭感觉动旋钮。

## 篇 7 存储与文件系统实现

**职责一句话：块设备层、ext4 读写、写合并缓存、NTFS 只读桥、掉电恢复——数据安全红线（宪章第十二章）在这条链上每一环都有落点。**

### 7.1 块设备层：BOT 通道的管理

块设备层向上提供"可排队、可冲刷、可监控"的块接口，向下管 USB 大容量存储的 BOT 通道。BOT 的特性是半双工命令与数据交替（命令块、数据块、状态块三段式），并发能力弱，所以层内做三件事把"弱通道"管理出"好表现"：其一，队列深度自适应——默认深度四，实测最优点随盘体质浮动，调参表管理；其二，请求合并与排序——相邻逻辑块的写请求合并成大请求（BOT 喜欢大块顺序传输），读写交错时按"读优先"调度（读是交互路径，写是后台路径，Q63 的调度落点）；其三，超时与重试分离——单命令超时用短值快速重试，连续失败计数到阈值才上抛设备异常，把"偶发慢"消化在层内而不惊动上层。

四板斧的 VARIX 侧联动：VARIX 内核的 USB 存储驱动本来就实现 BOT（没有 UAS 模式可言），但启动时的四板斧校验（读 Windows 域加固状态）要确认"两个域讲同一个协议"——VARIX 走 BOT 而 Windows 域跑 UAS 的组合就是 0xED 事故的根源，校验不过则在启动报告黄牌并提示复检（篇 3.8）。

### 7.2 ext4 读写：集成与日志策略

ext4 的实现主体是 Google ext4 crate（MD1 第 17.3 节决策），我们写的是三层包装：挂载层（超级块校验、特性旗标白名单——ext4 的特性矩阵庞大，我们只开白名单内的特性： extents、日志、哈希树目录，其余特性遇到即挂载失败并人话提示，绝不对未知特性硬解析）、块映射层（crate 的块读写回调对接我们的块设备层与缓存层）、路径层（crate 的目录操作包装成 VFS 接口）。

日志策略两阶段：阶段一挂载时重放已提交事务（保证一致性），运行期写路径采用"日志元数据、数据按检查点"模式——这是断电窗口五秒（Q41）的来源，也是诚实文案的依据：最近五秒的元数据与数据可能未落，结构永不损坏。阶段二（判据 2 之后的可选增强）评估数据全日志模式——写吞吐换更强断电保证，是否启用由实测数据说话，不预设立场。

写路径的配额与限额：单目录文件数告警线（五万）、单文件上限（DATA 分区余量的九成，防止一个失控写满全盘）、总量水位线（九成触发全盘清理提醒，回收站配额联动）。限额触发一律报错加指引，绝不静默丢写。

### 7.3 写合并缓存：结构与触发

写合并缓存是块设备层与 ext4 之间的写路径枢纽，结构是"按目标块排序的延迟写队列加检查点账本"。写入路径：上层写请求进队列（元数据写与数据写都进）→ 五秒窗口内相邻块合并 → 三种事件触发落盘——窗口到期、队列水位到线、应用显式冲刷（fsync 语义）。检查点账本记录每次落盘的事务边界，断电重放时按账本恢复到最近检查点（判例 16 的"回到检查点而非假装完整"）。读路径独立：读缓存按 LRU 管理（上限自适应，19.3 的 512MB 档），预读粒度四兆（U 盘顺序读是长项，预读命中率是 VSCode 冷启动预算的关键变量）。

诚实性纪律：fsync 是硬承诺——应用显式冲刷必须真的落盘完成后才返回成功，写合并窗口对 fsync 让路。牺牲一些合并收益换"应用以为存了就是存了"的直觉正确，这笔账永远算得过来。

### 7.4 NTFS 只读桥与 FAT 交接分区

NTFS 桥实现为 VFS 层的只读驱动（用户态解析器加内核缓存，读路径为主）：支持基本卷解析、MFT 读取、常压缩属性、长文件名；不支持的特性（加密卷、特殊重解析点）按"该条目不可读"呈现并说明——局部诚实优于全局假装。挂载点固定 /windows（VARIX 侧命名），只读属性在 VFS 层强制（C-6），任何模块申请写句柄直接拒绝并记安全事件。

交接分区（FAT32）的读写实现独立成小模块：FAT32 是简单文件系统，自实现读写二百行级，换取交接链零依赖（ADR-011 的理由落地）。FAT 表冲刷是交接流程冲刷步的最后一跳（篇 2.4），冲刷完成的时点即"数据已在盘上"的物理承诺点。

### 7.5 掉电与失联的恢复路径

断电恢复路径：上电 → 块层自检 → ext4 挂载尝试 → 日志重放（按检查点账本）→ 重放成功则正常挂载、失败则转只读模式挂载并全屏黄条提示（26.1 矩阵）→ 挂载结果与重放统计写入启动报告。一百次断电抽测（WD-052）按此路径全过是判据 2 的组成。

U 盘失联路径（判例 17）：块层检测到通道死亡（命令连续失败且总线无响应）→ 一秒内向系统广播失联事件 → 合成器全屏接管保护屏（冻结输入、显示三要素文案）→ 内核停止一切写调度（内存里的账本保留，等重启按日志重放）。保护屏期间系统不做任何"侥幸继续"的动作——存储没了，任何继续都是制造损坏。

## 篇 8 图形加速与多媒体实现

**职责一句话：STAR I 的图形答案是"CPU 软渲染打满全场"，本篇定软渲染的具体接法、R3 硬加速攻坚线的摸底边界，以及视频与音频两条多媒体链路的实现。**

### 8.1 软渲染的接法：谁用哪条路径

全系统的图形需求分三层，各走各的软渲染路径，互不混线。第一层是系统层（合成器、原生应用界面）：不用任何图形 API——合成器直接做位块与混色（篇 5.1），原生应用的矢量 UI 走 vx-SDK 的绘制原语（矩形、路径、文字，CPU 实现），这条路径最短最可控，性能预算全部按它核定。第二层是兼容层窗口内容：Wine 的三维需求走其 GL 后端（wined3d），GL 实现用 Mesa 的 llvmpipe（CPU 软光栅，借力清单成员）——llvmpipe 提供的是 OpenGL 语义的 CPU 实现，Win32 常规应用（7-Zip、记事本、PotPlayer 界面）的渲染需求远在它的舒适区内；Direct3D 重度应用明确不在承诺面（MD1 第 23.6 禁区第三条的精神，星卡如实标注）。第三层是 Electron 与 Servo：它们的绘制管线自带 CPU 路径（软件合成），直插时关闭 GPU 加速开关走纯软件路径（24.5 专项已定），我们提供的是窗口面与输入面，绘制它们自理。

三层的共同纪律：**任何一层都不得绕过合成器直接写屏**（C-1 契约）——Wine 应用画得再快，最终也要经表面提交进合成管线。这条纪律是崩溃恢复、浮层强制、录屏诊断全部成立的前提。

### 8.2 R3 攻坚线摸底（只摸不建）

STAR I 为 R3（硬加速）只做摸底三件事，一行驱动代码不写（MD1 第 20.1 节的立场）：其一，硬件清单固化——Y7000 的核显为 Intel UHD 630 系（Mesa iris 驱动的标准支持对象，借力路径清晰），独显为 NVIDIA 消费卡（开源驱动支持度差，明确列为低优先级，文档如实记录）；其二，合成器的提交后端抽象——篇 5.1 的合成管线第四步（提交）定义成 trait，CPU 后端之外预留 GPU 后端接口位，R3 到来时换后端不换管线；其三，验收指标预研——GPU 后端的验收口径（帧率、延迟、功耗）提前拟好，避免届时"能跑就算成功"的降格验收。摸底产出是一份立项包（附录 G 的 S406），不是代码。

### 8.3 视频链路：软解与呈现

视频播放（PotPlayer 判例 SC-091 的底层支撑）走软解路径：解码器按容器与编码格式选择，H.264 与 H.265 常见档位软解在实机核（标定 CPU 占用，八核里给解码两核上限）可达实时；解码输出帧经表面提交进合成器，与普通应用同路（C-1 再次生效，视频窗口也逃不出浮层与快照体系）。解码库选型走 FFmpeg 的 LGPL 动态链接形态（借力清单追加条目，许可立场：动态链接加独立进程边界，与总案许可纪律相容，细节在 ADR 登记册补一条）。字幕与音轨同步的容差八十分之一秒内（SC-093），画面拖动响应三要素文案兜底（解不动的高规格视频如实告知而非花屏）。

### 8.4 音频链路：HDA 驱动与混音器

HDA（High Definition Audio）驱动的实现骨架：控制器层管 CORB 与 RIRB 两条命令环（下发编解码命令、收回响应）加 DMA 位置上报（精确知道播到哪一格，延迟测量的硬件依据）；编解码器层做引脚配置（耳机、麦克风、内置喇叭的开关与路由，Y7000 的 Realtek 编解码器配置表固化进驱动），拔插感知走引脚状态中断——耳机插入自动切换输出（SC 侧判据）。混音器守护进程（MD1 第 17.5 节）的流模型：每流一环形缓冲、独立音量与静音、优先级抢占（通话流压低媒体流不静音它），混音输出定长周期送驱动 DMA。Wine 桥把 Windows 音频 API 语义映射为流（SC 侧判据），延迟预算四十毫秒的测量用"应用提交时间戳与 DMA 位置对照"自动采样。USB 音频类第三批（矩阵注记），蓝牙音频不承诺（判例 29）。

## 篇 9 输入子系统与输入法实现

**职责一句话：从键盘扫描码到窗口里的一个汉字，这条链上的每一环——驱动事件、布局表、IME 引擎、合成文本投递、快捷键仲裁——本篇定到能开写的深度。**

### 9.1 事件流与驱动接缝

输入子系统是全系统的事件源头，接缝定义三种驱动事件源：PS/2 控制器（键盘、触摸板，Y7000 内建设备的传统通道）、USB HID（外接键鼠，报告描述符解析后归一化）、电源与功能键（亮度、音量键走平台通道）。三源归一到统一事件结构：时间戳（单调时钟）、设备标识、事件类型（按下、释放、重复）、键值（物理键位编码）。物理键位（布局无关的 scancode 语义）是事件流的标准形态——布局翻译与 IME 都在驱动之后的环节做，换布局不换驱动，判例 26 的快捷键仲裁也建立在物理键位上（物理键位是"全局词典"的稳定主键）。

事件流单向纪律（C-8 契约）的实现：事件只从驱动流向输入子系统再流向合成器，内核接口层不提供任何"注入事件到指定窗口"的调用——窗口伪造输入给别的窗口在接口层就不存在（Q59 的残余风险仅剩物理 HID 注入，威胁模型已登记）。系统级功能（截图快捷键、交接入口）消费事件的方式是注册过滤器而不是截改事件流——过滤器可以"消费"（事件到此为止）或"放行"，不能改写。

### 9.2 布局表与键位翻译

键盘布局是数据不是代码：JSON 布局表（随 VARIXSYS 分发，用户可加）按物理键位到字符的映射组织，含四层（常态、Shift、AltGr、Ctrl 组合的弃用声明）。布局表 schema 五字段：层定义、死键支持（拼音方案用的声调死键预留）、修饰锁状态机（大小写锁定与数字锁定的行为全在表内声明，状态机实现在子系统）、别名（多键位输出同字符时的规范键位声明——快捷键文档以规范键位为准）、版本号。内置美式英文与简中拼音两套布局，切换即时生效（会话级设置）。判例 21 的计宽纪律与此无关但相邻：布局表管"哪个键出什么字符"，等宽计宽管"字符占几格"，两者在任何界面不得混实现。

### 9.3 IME 引擎：极简拼音的完整设计

自研极简拼音引擎（ADR-012）的内部结构分四层。第一层输入缓冲与切分：用户键入的字母串按声韵母表做最大匹配切分（zh、ch、sh 与韵母组合的歧义按最长韵母优先，实测词库驱动校准），全拼为主、简拼（首字母）为辅。第二层音节到候选的检索：词库是冻结的三万条目文本库（词、拼音序列、词频档位三元组，构建期编译成前缀索引），检索按"音节序列完全匹配优先、模糊音关闭"取候选集，词频档位排序——不做运行期学习（第一版没有用户词频，诚实标注）。第三层候选装配：整词候选、单字候选、联想候选三段式分页，每页九个（数字键选重），页内序稳定（同一输入串的页序不抖动）。第四层提交：候选上屏经 text_commit 报文投给焦点窗口（判例 11 的协议落点），输入串的编辑（退格、分词符隔音）在缓冲层完成，永不污染应用窗口。

引擎的三条硬性能线：键入到候选首屏 ≤ 100 毫秒（WD-011）、上屏 ≤ 16 毫秒（一帧内）、内存常驻 ≤ 32 兆（词库索引映射只读共享页，多进程零复制）。候选窗是合成器浮层（popup_grab 抓取，屏幕夹紧），定位跟随焦点窗口上报的光标锚点——Wine 窗口的光标锚点经 Wine 桥上报，协议同一路径（判例 11 的实现闭环）。

### 9.4 快捷键仲裁与焦点纪律

快捷键总表（交互词典的键盘侧）三列：保留字表（系统级：切换输入法、截图、交接入口、亮度音量）、应用申请表（应用 bind 时声明，冲突按先注册先得拒绝并指名，判例 26）、用户自定义表（设置中心，覆盖应用申请表）。仲裁顺序：用户自定义 > 保留字 > 应用申请。IME 组合期（缓冲非空）的键盘事件一律进引擎不进仲裁——组合期触发快捷键是经典误触（宪章第六章），在仲裁入口直接分流。焦点纪律的落地：焦点变更事件与输入投递同源（合成器裁决，篇 5.5），Tab 序按窗口声明的控件序，焦点环渲染由 vx-SDK 控件基类统一实现（应用想丢焦点环都难——宪章第四章的物理强制思路与浮层出路同构）。

## 篇 10 Wine 支架与兼容运营实现

**职责一句话：Wine 会话服务、前缀模板、四路垫片、星卡流水线——兼容腿从"能跑"到"可运营"的全部工程件，本篇逐个落地。**

### 10.1 Wine 会话服务：wineserver 的生命周期管家

Wine 会话服务是惰性启动的系统服务（MD1 第 25.1 节启动表第十项）：第一个 Wine 应用请求到达时才拉起 Wine 环境，进程树是会话服务派生的 wineserver 单例（C-5 契约的执行者）加若干应用进程。管家的四项职责：其一，派生与记账——每个 Wine 应用组（wineserver 加组内进程）建立记账卡（进程树、内存合计、启动时间），配额超限按 19.3 降速条款处理；其二，心跳看门狗——对 wineserver 每秒探活（管道握手），失联两秒判定，五秒内按空协调态重建（MD1 第 17.2 节 P-03），重建后逐组发恢复协商，组内应用响应超时的如实标记"该应用未能恢复"（诚实呈现，不假装全恢复）；其三，环境一致性——会话内的环境变量、显示桥接参数、音频路由由管家统一下发，应用不得私改（改了也在下次会话被模板覆盖）；其四，会话结束清算——交接或关机时按篇 2 保全口径收尾， wineserver 优雅退出，残留进程强杀前先快照窗口清单。

### 10.2 前缀模板与生成器

前缀生成器把"每个应用一个独立片场"制度化：模板含 Windows 版本伪装值、字体注入表（MD1 第 23.5 节的宋体雅黑到开源映射）、代码页映射（中文文件名判例 SC-053 的关键）、默认环境、DPI 绑定声明。生成器按模板实例化前缀（目标路径 /home/wine/〈应用名〉），实例化产物带模板版本号——模板升级后旧前缀标记"可升级"，升级即重建（23.2 的重建优于手术）。模板外的前缀自改（应用自带安装器改注册表属正常业务）与模板级篡改（绕过生成器手工造前缀）分清界限：前者记录星卡，后者在会话服务处被拒绝。

### 10.3 四路垫片清单

显示垫片：Wine 的 Wayland 驱动对接 vx-wayland-bridge（篇 5 协议），窗口装饰统一（合成器绘制标题栏）、光标统一上报、DPI 绑定（缩放因子到 Wine DPI 虚拟值的换算在桥内完成）。输入垫片：IME 提交文本经 text_commit 路径直达 Wine 窗口（判例 11），Wine 侧零输入法 DLL；快捷键走应用申请表（Wine 窗口的系统级键申请需显式声明）。音频垫片：Windows 音频 API 到混音器流的映射（篇 8.4），每流音量在系统监视器可见。剪贴板垫片：Wine 剪贴板与 VXWM 剪贴板的双向桥，类型支持纯文本与位图（文件清单类走拖放协议），转发遵循显式授权语义（篇 5.2 的所有权纪律）。四路垫片的共同形态：全部在 VARIX 侧实现，Wine 源码零修改（23.6 禁区第一条的工程兑现）——垫片失效只影响桥接功能，不污染 Wine 本体，升级 Wine 时垫片随版本锁定表重新校验。

### 10.4 星卡流水线：判例的可执行化

星卡不是手写文档，是流水线产物。判例脚本框架：每条判例（SC-xxx）是一个可执行用例（脚本加断言加预期资源画像），框架负责准备环境（前缀模板实例化、网络模拟开关、数据夹具）、执行、采集（退出码、界面可达性探针、vxbench 采样：冷启动时长、内存峰值、CPU 空闲占用）、出报告。流水线三档：首轮定级（十二星卡全量）、复评定级（上游升级或 VARIX 更新触发，MD1 判例 24 的联动）、抽检（月度随机抽三分之一样例复跑防漂移）。评级发布是流程终点也是唯一人工环节：脚本报告全绿且无未解释偏差才允许评级转绿——机器跑机器看，人对诚实性负最后责任。

### 10.5 崩溃归因与上游回馈

Wine 应用崩溃的归因五分类：应用自身缺陷（星卡登记，等待上游修复）、Wine 缺陷（上游 issue 义务，18.4）、垫片缺陷（我们修，垫片测试补用例）、资源越限（配额提示，非缺陷）、未知（进诊断中心待归因池）。五分类在崩溃报告界面即呈现（用户看得到归因而不是黑箱错误码）。回馈流程：上游 issue 模板（含最小复现、环境指纹、变通方案）入库，季度窗口统计回馈命中率——回馈不是姿态，是维护成本的对冲（上游修了我们就少维护一个补丁）。

## 篇 11 原生应用框架（vx-SDK）实现

**职责一句话：原生腿的地基——目标三元组、运行时库、应用清单、控件基类、权限模型、调试链路，SDK 的每一件东西都按"十二件套是第一用户"的标准打磨。**

### 11.1 目标三元组与运行时库

vx-SDK 的核心是一个 Rust 目标三元组（架构加系统加 ABI 的目标规范文件）加配套 sysroot。目标规范定义：代码模型、重定位形态、系统库链接约定——Rust 编译器拿到它，就能产出 VARIX 可执行文件，这是"原生级"三个字的编译器层含义。运行时库两层：底层 relibc（借力清单，提供 C 标准 ABI——大量 Linux 世界的源码因此可以原生编译，这是原生腿兼容策略的隐性红利）、上层 vx crate（VARIX 专属：VXWM 客户端、VFS 接口、vxapp 运行时、诊断接口）。两层之间的分工红线：POSIX 语义进 relibc，VARIX 特性进 vx crate——应用不直接碰内核接口，一切经库（C-4 与安全模型的执行面）。

sysroot 里随 SDK 分发的还有交叉工具链说明与最小示例集（终端 echo、窗口 hello、后台服务三个模板）——SDK 的第一印象决定了未来生态的第一印象，模板代码按 20 维度第 8 项（代码质量）的标准写，示例即门面。

### 11.2 vxapp.toml 完整规范

应用清单是星图安装服务的输入（MD1 附录 F.2 定字段骨架），本篇定字段语义与校验规则。id：反域名字符串（org.varix.vxterm 风格），全局唯一，构建期查重。name 与 version：星卡同步的展示面。leg：三腿归属声明，native 之外取值由星图服务拒收（清单是原生级凭证）。entry：启动命令，只允许"可执行文件相对路径加参数"，环境变量引用显式列举（注入表核对）。icon：多尺寸图标清单（十六、三十二、四十八、二百五十六四档，缺档构建期告警——任务栏与星图需要不同档）。limits：资源申请（内存、表面、进程数上限），与 19.3 配额对账，虚高申请构建期打回。permissions：权限申请逐项声明（网络监听、可写路径、设备访问），安装时呈现给用户确认（Q58 的来源三级在这里落地为"清单即合同"：申请什么给什么，运行期越权即拒）。schema_version：格式版本。reserved：商店形态扩展区（20.2），SDK 校验器对预留区透传不解析。

校验器是 SDK 的守门员：全部字段类型、取值域、交叉一致性（icon 尺寸、limits 与 entry 的资源匹配、permissions 与 API 使用面）构建期全查，不合规产物根本到不了星图——星图目录的整洁从源头保证。

### 11.3 控件基类与界面原语

vx crate 的 UI 层提供有限控件集（按钮、输入框、列表、对话框、标签页、菜单——交互词典的控件清单，新控件类型过 ADR），每件控件的默认行为内嵌宪章要求：焦点环默认渲染（B-907）、三态齐备（常态、悬停、禁用；输入框加错误态与占位符）、按压反馈（缩进一像素与色阶变化）、动画时长取词典值（进场一百二十毫秒、退场八十毫秒，缓动曲线统一）。主题 token（颜色、字号、间距的命名集合）由系统下发，应用只能引用 token 不能硬编码色值——深浅主题切换时全系统一致（判例 15 与 WD-061 的 SDK 层保障）。布局系统用约束求解（声明式行列表格），125% 与 150% 缩放下自动重排——宪章第七章"缩放不破版"在布局层就是求解器的输出性质。

### 11.4 应用生命周期与调试链路

生命周期四态（启动、活跃、暂停、退出）加两个系统回调（会话保全回调——篇 2.3 草稿登记在此调用；权限变更回调——用户在设置中心调整权限时通知应用自我调整）。生命周期由 vxapp 运行时托管，应用代码只在回调里做事——托管层保证退出路径必然经过保全回调（数据安全红线在框架层兜底）。调试链路三件：结构化日志（应用日志进统一诊断流，级别与采样可控）、崩溃报告自动生成（栈回滚符号化随构建产物分发）、QEMU 远程调试（开发期应用跑在 QEMU 系统镜像里，主机 gdb 直连——三层测试环境的第一层对应用开发者同样开放）。

## 篇 12 测试与验收实施

**职责一句话：测试金字塔的每层怎么建、判例编号体系怎么跑、20 维度验收怎么执行成证据——本篇把"能跑测试的一律跑通"（用户工作守则）落成基础设施。**

### 12.1 测试金字塔与各层职责

四层结构，越往下跑得越快、越多、越早。第一层单元测试：随码随写，内核核心模块（内存、调度、VFS、转译柜台）行覆盖 ≥ 60%，柜台翻译函数 ≥ 80%（篇 4.6），纯函数优先（可测性设计进代码评审清单）。第二层集成测试：子系统接口级（VXWM 报文回放、写合并缓存的事务语义、交接状态机全迁移覆盖——B-201），在宿主机跑（不需要真内核，模拟驱动桩），秒级完成。第三层系统测试：QEMU 里的整机镜像（篇 12.2），分钟级，每日构建跑全套。第四层实机验证：Y7000 权威环境，只跑"必须真机"的项（性能预算、USB 通道行为、交接全程、体验走查）——真机时间稀缺，用前三层把真机上的意外压到最低。

层的铁律：**下层的 bug 不许漏到上层再发现**——集成层能测的报文语义问题在 QEMU 层才暴露，视为集成层用例缺口，补用例与修 bug 同单完成。这条纪律防"测试金字塔倒挂"（全靠真机试）的慢性病。

### 12.2 QEMU 冒烟套

QEMU 冒烟套是系统层的主体：整机镜像（与发布同构，篇 13.2 的可复现构建产物）加 OVMF 固件直启，测试用例按"引导 → 冒烟动作 → 断言"组织。固定场景包：启动到桌面（十一打点全采集、预算粗核）、交接五步全流程（与模拟的 Windows 侧环境对练——交接助手在 QEMU 里有测试替身）、杀死演练（合成器、wineserver、断电、拔盘各若干次）、崩溃恢复、升级回滚演练。QEMU 快照机制让"断电"变成廉价操作（保存状态回滚即模拟断电），杀死演练因此可以跑出实机一百次的量级——实机只做最终抽测（WD-050 到 052 的实机复核）。冒烟套与判据编号对齐：每个用例声明它守护的 B-xxx 或 WD-xxx，判据改版时用例缺口一目了然。

### 12.3 实机脚本纪律

实机自动化脚本继承 Windows 加固包的四条纪律（篇 3.7：遗言、装载纪律、写后必读、幂等）加两条实机专属：其一，破坏性操作白名单——脚本只允许对白名单路径与配置动手，实机上"顺手清理"是事故之源；其二，双人规则——实机执行的影响面清单在脚本头部声明（动哪些分区、改哪些配置），执行前输出待执行清单等确认（对人的防呆与对 AI 的防呆同构，总案第 15 章工程文化的落地）。体验走查（WD 系列）人工执行，但记录模板机器生成（按场景分组的检查单），走查结果结构化入库。

### 12.4 二十维度验收的执行化

20 维度每维度定"证据形态"（验收不是打分是交证据）：维度一需求理解——验收标准对照表（MD1 附录 C.2 扩展为逐条勾选表）；维度二功能完整性——判据 1-5 与附录 G 事项完成度对账；维度三交互正确性——WD 走查记录；维度四细节把控——放大三倍截图审（表格化记录）；维度五视觉品质——三主题三缩放矩阵截图；维度六动画品质——帧序列录制审；维度七性能——vxbench 报告（19.1 全表）；维度八代码质量——评审记录与 clippy 零告警输出；维度九可拓展性——扩展点清单与"不改老代码"演练（加一个假想功能的改动面统计）；维度十健壮性——杀死演练汇总；维度十一数据安全——断电与恢复记录；维度十二一致性开放性——契约表审计加导出格式验证；维度十三文案——文案全量导出审（27.1 的字符串表让这步可脚本化）；维度十四无障碍——纯键盘走查与对比度实测；维度十五兼容环境——硬件矩阵实测记录；维度十六安全隐私——权限矩阵审计加日志红线抽查；维度十七错误恢复——错误注入清单；维度十八可观测性——体验日志回放演示；维度十九文档交付物——CHANGELOG 与文档一致性 diff；维度二十整体感受——Variable 本人的真机日用报告。证据齐全才算该维度通过，"感觉没问题"不构成证据。

## 篇 13 部署与发布实现

**职责一句话：从一次提交到一部可发布的 U 盘镜像——构建可复现、镜像可回滚、发布七步有工具撑腰，本篇是发布工程的实现面。**

### 13.1 可复现构建的实现

可复现的铁律（MD1 第 35.1 节）落成四件套：其一，工具链锁定——Rust toolchain 文件钉死编译器版本与组件清单，链接器与打包工具版本入构建环境清单，任何工具升级属于构建链变更走 ADR；其二，环境净化——构建脚本显式设置时区、区域、路径与源码时间戳（归档时间戳取提交哈希派生值），杀掉一切"构建机差异"渗进产物的通道；其三，产物清单与哈希——每次构建输出产物清单（每个文件的大小与哈希），镜像整体哈希入发布记录；其四，双环境比对——Windows 主机构建与 Linux 容器构建各出一版，哈希一致才认"可复现"成立（偶尔因工具链差异难对齐的二进制段，比对逻辑地址与符号表等价性，规则写死在比对脚本）。构建入口从批处理脚本渐进迁移为任务定义文件（任务清单化、依赖显式化），批处理保留为薄兼容层——工具迁移不许影响"一条命令出镜像"的日常体验。

### 13.2 镜像格式与分区写入

发布镜像（varix.img）是全盘镜像：分区表加五个分区（MD1 第 17.3 节布局总表）加引导区。镜像构建的顺序纪律：先造内容后造结构——各分区先在临时目录里生成文件树，再按布局总表打包成镜像，分区尺寸、GUID、文件系统参数全部由构建脚本从单一配置读出（布局改版只改一处）。QEMU 专用 ISO（varix-qemu.iso）是同源衍生品：同样的内核与配置，CD-ROM 形态，供三层测试环境直启——镜像差异只有引导介质形态，内容零差异（测试环境和实机环境同源是冒烟套可信的前提）。写盘工具是自带的（镜像校验、目标盘确认、写入进度、写后校验四段），绝不建议用户拿裸 dd 直接写——目标盘选错是数据安全事故，工具里的确认环节（显示目标盘型号容量等人工确认）是必要摩擦。

### 13.3 vx-updater 的实现

更新器四段流程（MD1 第 22.2 节）的实现要点。下载段：镜像分块下载与断点续传，校验和边下边验；离线更新包形态（星图双模式，MD1 第 18.5 节）是同一套校验逻辑的文件入口。校验段：全镜像哈希加分区级哈希双验，签名验证（更新包签名，Q55），任何一段不过立即终止且不留半成品。落盘段：写入的是**备用槽**——U 盘上的系统分区保留当前运行版与新版两个镜像槽（VARIXSYS 内固定双槽布局），写新槽不动当前槽，落盘后写引导选择记录（下次引导进新槽一次，带自动回退标志）。回滚段：新槽引导后自检（启动报告完整生成加健康自检通过）才把新槽转正；自检失败下次自动回旧槽——回滚是自动的，不依赖用户记得怎么救砖。双槽的空间代价（系统分区 16GB 每槽 7GB 级）在布局总表内消化。72 小时一键回滚（MD1 第 37.4 节）是转正后的兜底：转正记录保留旧槽内容满 72 小时，期间更新器提供手动回滚按钮。

### 13.4 发布七步的工具支撑

七步仪式（MD1 第 37.3 节）每步有对应工具：冻结——分支保护与合入门禁开关（35.4 闸门的冻结模式）；回归——冒烟套加实机核心场景脚本一键跑；打包——13.1 与 13.2 的构建链本体；试运行——实机日用即试运行，体验日志自动汇总成"试运行日报"；发布——产物归档、git 打里程碑标签、更新推送一条命令；公告——变更说明模板（用户视角、三段式：修了什么、变了什么、已知问题）由发布工具强制套用，空白段不允许发布；复盘——本版过程问题回写 MD3 偏差专栏的表单化入口。工具把仪式变成"顺手的事"，仪式才不会被省略。

## 篇 14 性能预算实施

**职责一句话：总案 19 章的每格预算数字，在本篇落到打点、基准与回归门——预算不是表格是代码。**

### 14.1 打点体系与内核账本

预算的可测性靠两件基础设施。打点体系：全系统统一的打点接口（零分配、无锁、纳秒级单调时钟读取），点位在篇 1.8（启动十一点位）与篇 5.1（帧生命周期两点位）之外覆盖全链路——交接五步、应用启动四段（派生、装载、初始化、首帧）、存储路径三段（缓存入队、合并落盘、确认返回）、网络路径两段（栈入队、确认）。打点数据的流向：环形缓冲实时记、启动报告与诊断中心聚合读、vxbench 归档存——一份打点三个消费者，不许各插各的桩。内核账本：内存与 CPU 的分类记账（每子系统、每进程、每缓存的实时占用），账本是 19.3 配额执法的依据，也是系统监视器的数据源——账本接口只有读，写只在内核分配路径（记账开销是分配热路径的一部分，实现按常数时间硬性要求）。

### 14.2 vxbench 微基准设计

微基准层覆盖六类硬指标：syscall 往返（空调用与常调用两版，百万次取 P95——篇 4.6 的两微秒判据）、上下文切换（双进程乒乓，P95）、页分配与释放（各尺寸档）、帧管线（合成器内自测：空帧、单表面帧、十表面帧的分档耗时）、块路径（顺序读写、随机读写、fsync 延迟分布）、网络环回（栈内环回吞吐与延迟）。每个基准的输出是分布不是均值（P50、P95、P99 三线），回归判定按 P95 对基线偏差超 10% 标红（19.2 的阈值）——均值会掩盖长尾，长尾才是手感杀手。基准运行环境固定（QEMU 标准档与实机各一套基线），跨环境数字不许混比。

### 14.3 回归门与预算变更流程

回归门嵌在每日流水（B-1206）与合入闸门（35.4）两处：每日全套基准跑完与基线对表，标红项自动开 issue 并通知；合入前跑受影响子系统的基准子集（按改动路径选择，选择表维护在仓库），红即阻断合入——性能回归与功能缺陷同罪（总案 19.5）。预算数字本身要改时走三处同步（MD1 附录 I 的纪律）：源章节、速查总表、vxbench 基线同时改加 ADR 备案，三处不同步的改动在审计时打回。

## 篇 15 安全模型实施

**职责一句话：总案第 10 章与威胁推演（第 34 章）的每个"处置"，在本篇落到接口、类型与流程——安全不是策略文档是代码事实。**

### 15.1 进程隔离与最小接口

隔离的物理基础是每进程独立页表（内核管理地址空间，进程间互不可见），叠加三层机制。第一层能力型接口：进程能做的事由其 vxapp 的 permissions 声明与运行时授权决定，内核接口按能力对象发放（打开设备、监听端口、写路径都是拿到能力对象才有的事），没有"全局 root 概念"可盗（Q30 虚拟 UAC 的结构性根源）。第二层 W^X 强制：内存页的可写与可执行互斥由内核分配器与装载器联合保证（MD1 第 17.2 节 P-04），JIT 类需求（无，直插级 Electron 的 JIT 在柜台侧按非可写映射加切换原语处理——实现细节随篇 4.2 第二类的适配记录）单独走受限原语。第三层攻击面收缩：内核不导出任何调试类全局接口（调试走进程内诊断与 QEMU），系统调用的参数清洗覆盖率 100%（篇 4.3），接口清单就是攻击面清单——接口数量本身纳入安全审计指标。

### 15.2 权限矩阵的执法点

总案第 10 章补的权限矩阵在四个执法点执行：安装时（清单即合同，用户确认——篇 11.2）、启动时（运行时按声明构造能力集）、调用时（接口层验能力对象，越权即拒并留痕）、审计时（权限使用统计进诊断中心，用户看得到谁用了什么）。四个执法点共享一份权限定义表（权限项、语义、默认值、可授予性），表是唯一权威——矩阵改版只改表。

### 15.3 来源分级与更新签名

可执行来源三级（Q58）的实现：一级签名包（星图分发，签名验于安装与每次启动）、二级白名单目录（用户手动放置于受信路径，首启双确认）、三级临时放行（单次运行，高风险提示文案）。更新链签名：更新包签名私钥离线保管，公钥与根证书库同随镜像分发，验签失败的更新在下载段即终止（篇 13.3）。签名基础设施刻意极简：单根密钥加密钥轮换记录——不建 CA 体系，规模配不上复杂度，复杂度配不上维护能力。

### 15.4 日志红线与隐私的技术强制

体验日志的红线（宪章第十三章：不记内容只记行为）用类型系统强制：敏感数据（键盘缓冲、剪贴板正文、窗口标题的隐私标记位）封装在专用类型里，该类型不实现任何序列化与日志格式化——代码想把它打进日志都编不过。日志红线审计脚本（B-1205 配套）在构建期扫描日志调用点的参数类型，红线类型零出现。这招把"纪律"变成"物理"——与浮层出路、焦点环同一设计哲学：**不指望人永远遵守，让违反成为不可能。**

## 篇 16 终端实现详案（vx-term）

**职责一句话：兼容 POSIX 会话的终端模拟器——网格模型、序列解析、滚动缓冲、性能底线，开发场景的心脏造结实。**

### 16.1 架构与网格模型

终端三段式：伪终端（PTY，内核会话设备，shell 与子进程接它的主从两端）、解析器（输出字节流到网格操作的翻译）、视图（网格到屏幕的绘制，经 vx-SDK 控件提交表面）。网格模型按经典终端语义：字符格含字形索引、前景色、背景色、属性位（粗体、反色、下划线、宽字符标志），网格尺寸随窗口重排（重排时按行的换行软硬标志重流——重流语义按主流终端惯例，壳会话配合重画）。宽字符两格计宽（判例 21 的终端落点）：宽字符格与它的续格在网格层就是两格，混排对齐从模型层正确。

### 16.2 序列解析与兼容面

解析器实现 ANSI 与 VT 系列的常用全集：光标移动与定位、清除与滚动区域、字符属性（SGR 全色：十六色、二百五十六色、二十四位真彩）、模式切换（光标可见性、回绕、备用屏）、标题与剪贴板查询、鼠标上报（按模式三态：无、按键、全事件）。解析器是状态机实现（字节流进、网格操作出，非法序列按"忽略并计数"处理——容错优先于报错，终端的古典美德）。兼容面以"VSCode 内置终端与独立终端行为一致"（22.2 判据）为验收锚：同一解析器实例类型供两处复用——VSCode 走直插路径时它的终端渲染自理，我们保证的是 PTY 层与系统序列行为一致，两层各自的判例对齐。

### 16.3 滚动缓冲与性能底线

滚动缓冲一万行环形存储（文本与属性一体存储，检索按行扫描——一万行线性扫在微秒级，不需要索引）。性能三条硬线：大输出不卡 UI（cat 大文件的吞吐测试：解析器每秒百万级网格操作，视图按帧节流消费——输出速度与绘制速度解耦是关键结构）、键入回显一帧内（16 毫秒，输入回显路径零阻塞）、内存上限（缓冲满后滚动淘汰，网格内存恒定）。选择与复制：按格选区（宽字符续格自动并入）、复制进系统剪贴板、中键粘贴（Linux 惯例）与 Ctrl+Shift+V 双支持——交互词典管外观，终端社区的肌肉记忆管快捷键，两头都要照顾。

### 16.4 会话与 shell

内置 shell 按 POSIX 语义实现（命令解析、管道、重定向、环境与退出码），外部命令经进程装载器拉起（ELF 路），Linux 直插命令经柜台无感混用——用户在同一个 shell 里混用原生与 Linux 工具（直插级生态的体验红利）。会话管理：终端标签页各持独立会话，会话结束回收 PTY；交接保全把"有未结束会话"如实列入快照（恢复提示含"终端会话无法跨域存活"的诚实说明——进程不能跨域，这是物理不是缺陷）。

## 篇 17 文件管理器实现详案（vx-files）

**职责一句话：双文件系统、回收站、搜索、预览——文件管理器的每个功能都踩在"数据安全"与"开放性"两条红线上，本篇定实现。**

### 17.1 VFS 浏览层与双文件系统呈现

浏览层建在 VFS 之上，对 ext4（读写）与 NTFS（只读）统一呈现、差异明示：NTFS 挂载点角标"来自 Windows 域（只读）"（判例 22），写入类操作在只读树上直接禁用置灰并给一行解释。目录列表的排序与过滤规则进交互词典（名称、大小、修改时间、类型四列，点击表头切换，方向记忆）。图标与缩略图：图片类按需生成缩略图（缓存进用户缓存目录，LRU 上限），生成在大文件上有取消与进度——卡死界面的缩略图是高频事故点，异步加节流是底线。路径栏支持直接输入（绝对路径跳转）与面包屑，两态切换无感。

### 17.2 回收站与删除语义

删除永远进回收站（宪章第十二章"可反悔"）：回收站是 DATA 分区的约定目录结构（条目含原路径、删除时间、原文件引用），vx-files 与 vx-SDK 的删除接口统一走它——SDK 层没有"真删"接口，绕过回收站的唯一途径是用户显式使用"永久删除"（二次确认）。回收站配额 10% 自动清理最旧（Q45），清理动作有通知。跨盘移动语义：跨文件系统的"移动"实为复制加删除（删除进回收站），中断续传的检查点语义与判例 16 同源。

### 17.3 搜索与预览

搜索两档：目录内即席过滤（键入即滤，前端内存过滤，毫秒级）与全盘搜索（后台任务，ext4 目录遍历加文件名匹配，结果流式呈现可随时取消——Everything 的兼容级地位不因此受冲击：它是 Windows 语义的深度工具，我们提供的是"够用的先答"）。预览：文本预览复用 vx-edit 的只读视图组件（大文件截断预览并注明），图片预览走缩略图管线，元数据面板（大小、时间、权限、哈希计算按钮）——哈希计算是交接前的常用动作，放显眼处。

### 17.4 交接与外部打开

"在 Windows 域打开"动作：把文件复制到交接共享目录并在快照留引用（判例 12 的文件接力路径），操作有进度与可取消。外部打开（用系统默认应用打开）走 MIME 表：扩展名到应用的映射表内置于星图数据（星卡登记应用支持的类型），未注册类型给"选择应用"对话框——MIME 表是星图目录的又一个消费者，目录即系统配置的开放性红利。

## 篇 18 文本编辑器与小件四枚实现要点

**职责一句话：vx-edit 与截图、图片查看、计算器、时钟——四小件一件都按大件的标准过验收，本篇把各自的关键实现定案。**

### 18.1 vx-edit：大文件与撤销链

**职责一句话：设置中心是用户与系统服务的全部对话界面——每项设置的后端、生效语义、失败回滚，本篇按服务逐项定案。**

## 篇 22 Windows 侧交接助手与 Variable 集成实现

**职责一句话：Windows 域里的"VARIX 联络处"——读取快照、写入快照、发起反向交接、域健康自检，本篇定助手的最小可靠实现。**

### 22.1 助手的形态与边界

助手是 Variable 桌面环境的一个后台服务加一个设置面板，能力刻意窄（篇 2.6 的窄协议）：读 /vx-snap/ 快照（VARIX 写的，FAT 分区在 Windows 下原生可读）并弹恢复提示；写 /var-snap/ 快照（剪贴板、窗口清单、草稿引用——Variable 侧采集，schema 与 VARIX 侧同表）；发起"重启到 VARIX"（写 BootNext 或按部署配置走菜单默认项，VARIX 启动时消费验证）；域健康自检（篇 3.8 复检清单的按钮入口）。不做的：不碰 VARIX 分区（ext4 在 Windows 下不装驱动——助手依赖越少越可靠），不写 ESP（引导修复是专用工具的事，篇 13.5），不做任何"优化清理"类功能（PCClean 类行为是事故之源）。

### 22.2 快照互通的采集细节

Variable 侧的窗口清单采集走其应用框架的窗口枚举（HTML/Tauri 体系的窗口管理接口），剪贴板走系统剪贴板监听（用户确认机制与 VARIX 侧 Q13 对称：密码管理器类来源默认跳过），草稿由 Variable 应用显式登记（与 VARIX 侧 2.3 同 API 语义）。快照写入的完整性：写临时文件加原子换名（FAT32 无日志，原子换名是唯一可靠的完整性手段），写完做全文件哈希并写入 integrity 字段——VARIX 侧读时的校验（B-207）与之闭环。

### 22.3 助手的部署与升级

助手随 Windows 域镜像分发（VC 运行库同批，篇 3.6），升级走 Windows 侧自更新（Variable 的常规通道）——但助手版本与快照 schema 有耦合：schema_version 协商（Q18）保证旧助手读新快照、新助手读旧快照都按"能读多少读多少"降级，两端版本锁定表在 MD1 第 18.4 节登记。助手缺席的降级（Q12）：VARIX 侧启动检测与提示逻辑固定（不阻塞启动），重装指引是一段内置文案加文件位置，不依赖网络。

## 篇 23 诊断中心、帮助手册与体验日志实现

**职责一句话：系统"自己知道自己哪里让用户烦"的三件套——健康总表、启动报告、挫败回顾——背后是体验日志系统的完整实现，宪章第十三章的工程总落点。**

### 23.1 体验日志的事件模型

体验日志记"交互行为与结果"，事件模型七字段：时间戳（单调钟加墙钟双值）、会话标识、界面上下文（哪个应用哪个视图）、对象（哪个元素、哪个浮层）、动作（点击、拖拽、快捷键、开关浮层）、结果与耗时（成功、取消、失败、耗时毫秒数）、体验结论枚举（顺畅、卡顿、无反馈、被打断、报错）。体验结论不是事后分析是事件自带——生成事件的那一跳自己知道顺不顺（耗时与结果当场裁决）。自动挫败信号五类内建：狂点（同位置短时多点）、死点（点击无反馈区域）、反复开关（浮层短时开合超阈值）、放弃路径（流程中途退出）、错误徘徊（错误后原地重复操作）。信号触发即升级为独立事件（原始事件引用加信号类型），Top 挫败点报表由此直接产出（16.3 的月度审计输入）。

### 23.2 隐私红线的技术落实

红线类型系统（篇 15.4）之外，日志面再补三道：字段白名单制（事件模型七字段之外不许扩，扩展走 ADR——字段膨胀是隐私侵蚀的温柔乡）、采样与总量（低危事件采样记，总量上限轮转，宪章"写入不阻塞、总量有上限"）、关闭开关（设置页可关，关闭时明示诊断能力降级——Q73 的落点）。日志的读取面三层：用户（诊断中心的挫败回顾，脱敏聚合视图）、开发者（按会话回放的事件流，本地文件直接读）、审计（季度红线审计的报告输出）。

### 23.3 诊断中心的三页实现

健康总表页：订阅监视器四卡（篇 20.2 同源），每卡展开到服务的降级历史（最近十次状态变化）。启动报告页：最近十次启动的十一点位时间线对比（"为什么今天慢"可视作答），异常打点标红并链到对应手册条目。挫败回顾页：Top 挫败点列表（自动信号聚合）加"已改善"标记（修复版本回写——用户能看到投诉被听见，信任从这里长出来）。三页的数据全部来自体验日志与账本订阅，诊断中心自己不产数据（单一事实源）。

## 篇 26 内核核心：内存与调度实现

**职责一句话：内核两根承重柱——物理与虚拟内存管理、进程调度——的字段级实现，六十万行的地基里最硬的部分。**

### 26.1 物理内存管理：页帧分配器

物理内存分两层管理。底层页帧分配器（4KB 页框为单位，伙伴算法）：Limine 的内存图把可用区间交给分配器建池，分配与释放按阶（order）管理，元数据开销每页不足一字节（位图加自由链混合）。上层内核对象分配器（slab 风格）：常用内核对象（任务结构、文件对象、socket、报文缓冲）按对象尺寸预建缓存池，构造一次复用——内核热路径的分配是常数时间且零碎化，账本（篇 14.1）在此层记账（每池占用实时可查）。两条红线：分配失败路径必须全覆盖（内核代码不允许"分配必成功"假设，失败向上返回错误由调用者裁决——OOM 的优雅优于 panic 的痛快）；DMA 一致性内存单独通道（USB 与 HDA 的 DMA 环需要物理连续与缓存一致性，专用接口供给，混用即缺陷）。

### 26.2 虚拟内存：地址空间与页表

地址空间布局按 HHDM 约定（Limine 协议）：内核高半区（含 HHDM 直映射、内核代码与数据、每 CPU 区）、用户低半区（每进程独立页表，ASLR 起始偏移按次随机）。页表管理要点四条：其一，每进程页表加内核共享区映射（高半区映射全进程一致，切换只刷用户区——切页表的 TLB 代价压到最低）；其二，W^X 在页表权限位执行（篇 15.1），分配器出页时权限即定型，改属性走受限原语并留审计；其三，懒分配与按需调入（用户页先登记后映射，访问缺页时装载——ELF 段的按需分页，MD1 第 17.2 节装载性能的物理基础）；其四，交换策略诚实缺席——U 盘整机不做磁盘换页（BOT 通道拿来做换页是性能自杀），内存压力按配额降速与拒绝（19.3），这条取舍写进威胁模型与性能模型两处（诚实的能力边界）。

### 26.3 调度器与中断

调度器目标明确：桌面交互优先。策略为优先级抢占轮转：优先级分层（合成器与输入链路最高层、交互应用层、后台服务层、批处理层），同层时间片轮转，层间严格抢占——Q70"应用再重也不掉帧"的调度层保证。实现要点：每 CPU 就绪队列（Y7000 八核，负载均衡按层迁移，交互层任务不迁移绑核优先——缓存亲和对手感有实感影响）、时间片按时钟中断推进、实时性仅到"软实时"档（音频流路径的四十毫秒预算由最高层优先级加 DMA 硬件双保险，不承诺硬实时）。中断与计时：APIC 模式（本地 APIC 计时器做时钟源，IPI 做核间调度通知），中断处理分上半（最小立即处理）下半（延后到任务队列）——USB 与 HDA 的中断体量在下半消化，上半只搬数据打戳。时钟供给：单调时钟（打点与调度用）与墙钟（RTC 校准加交接快照对照，Q14）双源分离。

### 26.4 内核可观测与自证

内核不做"沉默的美德"：关键路径全打点（篇 14.1）、异常全分类（可恢复的返回错误、不可恢复的 panic 走保护屏，26.1）、账本全记账。内核自证的最后一道是启动自检（引导链 B-101 之后内核入口的第二次自检：协议应答完整性、内存图合理性、HHDM 可用性——自检不过拒绝继续启动，屏显人话）。这部分实现的代码质量标准最高（评审双签，35.4 闸门加严一档）：内核 panic 的每一次都按事故处理（复盘、根因、回归用例），零容忍"偶发重启不影响使用"的自我安慰。

## 篇 27 进程装载器实现

**职责一句话：ELF 从文件到活进程的每一步——解析、映射、重定位、栈与环境装配、预取缓存——装载器的正确性与速度都在细节里。**

### 27.1 ELF 装载流水线

装载流水线六步。第一步读 ELF 头与程序头表（魔数、机器类型、入口点、段的文件偏移与虚拟地址），畸形文件在第一步即拒（安全清洗第一站）。第二步地址空间规划：按段属性建立映射预案（代码段只读可执行、数据段可写不可执行、BSS 零页——W^X 从这里定型）。第三步按需映射注册：段登记为"缺页时装载"的懒映射（篇 26.2），文件-backed 缺页从装载缓存供给。第四步动态链接：解释器（relibc 的 ld 等价物或封闭树内的 ld-linux）按同一流水线递归装载，全局符号解析按 ELF 语义，直插级应用走封闭树的库（篇 4.5 的 ABI 分界在此交界处咬合）。第五步栈与环境装配：栈顶布局按 ABI 惯例（参数、环境、辅助向量——辅助向量的条目集按 Linux 对齐，直插应用的启动例程对它有强预期）。第六步入口起跳：设置用户态上下文（寄存器现场、TLS 基址），跳入口点——装载器到此功成身退，进程进入调度视野。

### 27.2 装载缓存与预取指纹

冷启动预算（VSCode 十五秒）的关键武器是预取缓存：首次成功启动时记录"段清单指纹"（应用的段映射序列：偏移、长度、目标地址），二次启动按指纹顺序发起异步预读（4MB 粒度，篇 7.3 的读缓存承接），装载缺页命中预读的代价接近零。指纹失效条件：应用文件哈希变化（升级）即弃用重建——指纹只加速，不改变装载语义（错误指纹最多浪费预读，不会装错内容，这条正确性论证写进代码注释）。预算的对账：冷启动打点按"读盘时间与装载时间"分解，预读命中率的报表进 vxbench（B-707 判据的数据源）。

### 27.3 进程与线程的内核对象

任务结构（进程与线程统一模型，Linux 式 task 抽象）：父子关系、退出状态回收（wait 语义，僵尸态的存在与回收纪律——孤儿进程由 init 收养兜底）、资源配额指针（19.3 配额的执行锚点）、信号处置表。线程共享地址空间按 POSIX 语义（clone 的 VARIX 等价接口），线程本地存储、栈池管理、线程退出清理全在内核对象层闭环。进程数配额（fork 炸弹防线，Q22）与 fork 风暴熔断（短时 fork 速率阈值，超限短暂拒绝并告警）在此层执法。

## 篇 28 USB 栈与设备模型实现

**职责一句话：U 盘整机系统最忙碌的总线——控制器、集线器、设备枚举、三大类驱动（存储、HID、网络），USB 栈的稳定性就是整机的稳定性。**

### 28.1 控制器与枚举

控制器覆盖 xHCI（USB3，Y7000 板载口的主力）与 EHCI/xHCI 兼容路径（USB2 设备），TRB 环与事件环的内存管理走 DMA 一致通道（篇 26.1）。设备枚举状态机：插入手事件 → 描述符级联读取（设备、配置、接口、端点）→ 驱动匹配（类码与厂商产品号双轨）→ 实例化。枚举的三条稳定纪律：描述符读取带重试（劣质设备的描述符阶段掉链是常态，重试策略按实机标定）；地址分配与速率协商严格按规范时序（抢跑时序在个别设备上能跑、在另一些设备上是事故，规范时序是唯一可维护路径）；热拔插事件全程打点（U 盘失联判例 17 的检测底座在此）。

### 28.2 大容量存储类（MSC/BOT）

BOT 驱动是块设备层的物理承接（篇 7.1 上游）：命令块包裹、数据传输、状态包裹三段式的状态机实现，重点在错误恢复矩阵——CSW 意义不明时的复位恢复序列（类特定请求：清特性、复位设备、复位恢复的级联），每级恢复带计数上报（恢复频率进健康账本，U 盘体质在系统监视器可见——SMART 之外的第二只眼）。传输效率：批请求合并在块层做（篇 7.1），BOT 驱动只管把每个命令按时序走对——分层清晰，各修各的病。

### 28.3 HID 与网络类

HID 类驱动解析报告描述符（键盘、鼠标、触摸板的通用解析），归一化事件进输入子系统（篇 9.1）；描述符解析器的健壮性标准是"任意畸形描述符不崩、不越界"（模糊测试用例集进冒烟套——外部输入全清洗的红线在 USB 层的第一落点）。网络类驱动（RNDIS、NCM）把 USB 帧适配进网络栈的设备接口（篇 6.1 的适配层，手机共享通道的实现位）。三类驱动的共同纪律：端点错误与卡死的恢复路径全覆盖（挂起恢复、超时、 babble 错误各有着落），USB 层的事故在驱动层消化，不上抛成系统级事件——除非拔盘，那是判例 17 的专属路径。

## 篇 29 电源、固件接口与结束路径实现

**职责一句话：重启、关机、交接重启三种结束的物理执行，ACPI 与固件接口的最小集，以及"可以拔电了"承诺的兑现——结束做得好，下一次开始才干净。**

### 29.1 固件接口的最小集

VARIX 对固件接口（ACPI）的取用保持最小集：重启寄存器（FADT 指定的复位端口）、关机对象（S5 睡眠包的 \_S5 与 PTS 调用）、基本电源状态查询（电池电量在阶段 3 前不承诺——判例 30 的实现注记：ACPI 电池接口的复杂度与判据无关，明确缓期）。最小集的理由不是省事是安全：ACPI 表是固件产的 AML 字节码，解析它的深度每多一寸，固件差异引发的事故面多一片——只取三件东西，取法按规范写死，全行业机器上行为一致。固件接口层同样全打点、全带超时：固件不回应时的超时路径（用户在"正在关机"画面停留超过十秒的处置：屏显"固件未响应，可长按电源强制关机——数据已安全"的诚实指引）。

### 29.2 三种结束路径的物理实现

交接重启（篇 2 状态机末端）与普通重启共用物理执行（写复位寄存器），差异只在执行前的软件收尾（交接多了写 OneShot 与快照清理）。关机路径：保全（快照与草稿）→ 冲刷（篇 2.4 全序列）→ 通知链（服务收到结束通知逐个优雅收尾，超时强收）→ ACPI S5。"可以拔电了"画面的出现条件是冲刷完成加通知链收束——画面的每一秒都有账可查（打点时间线保留到下次启动报告）。崩溃路径（panic）：保护屏（26.2 规范）→ 现场信息写保护内存带 → 十秒倒计时 → 复位寄存器——panic 路径故意不走"优雅收尾"（栈可能已坏），它的安全承诺只有一条：尽快干净地重启，让日志重放兜底。

### 29.3 合盖与电源键

合盖事件（平台通道）：默认语义是"走关机路径"（STAR I 无休眠支持，Q77 明示）——合盖即触发关机确认（有未保存内容时弹确认，干净时直接执行），弹幕文案诚实说明"无休眠支持，合盖将保存并关机"。电源键：短按同合盖语义，长按是硬件强断（固件行为，软件无从干预也不干预）——文档明示长按的后果（数据依赖日志重放兜底，正常情况无损失），用户教育一次性完成。

## 篇 31 网络诊断三件套实现

**职责一句话：vx-ping、vx-route、vx-capture 的内部构造——判例归因的取证能力不在文档里在工具里，本篇把三件工具定到可写。**

### 31.1 vx-ping 与 vx-route

vx-ping 的实现要点：ICMP 回显经内核诊断通道（原始权限收敛在系统工具，篇 6.4），发送间隔、次数、包大小可调，统计输出（发出、收回、丢包率、RTT 三线分布——与 vxbench 同哲学，均值不算数）；支持按接口指定出站（多接口环境归因用）。vx-route：接口列表（状态、速率、地址）、路由表（来源标注：静态、DHCP）、ARP/NDP 邻表——三张表一屏看完，接口别名可读（"有线""手机共享"这类用户命名随设置走，诊断时人看得懂是第一要务）。

### 31.2 vx-capture：抓包与取证

抓包实现为内核旁路通道：命中过滤器的帧在送达栈的同时复制到环形缓冲（零干扰抓包——抓包工具自己拖慢网络是取证的大忌），缓冲满按环形覆盖并计数（诚实告知"早段已覆盖"）。过滤器语法极简（接口、地址对、端口、协议四元组合），BPF 式编译在用户态完成后下发。落盘为 pcap 标准格式（通用工具可读，开放格式红线的工具层落点），大文件分卷。脱敏选项默认开（载荷截断只留头——诊断连通性不需要内容，隐私红线延伸到工具）。取证联动：判例引擎（篇 25.1）可声明"失败时自动抓包三十秒"，星卡报告自动附包文件——归因从"看日志猜"变成"开包看"。

### 31.3 三件套的输出纪律

全部输出双格式（JSON 行机器可读加人读表格），JSON 的字段名进稳定字典（工具间与脚本引用零漂移）；退出码语义化（成功、目标不可达、权限不足、参数错误各自有码，判例脚本靠它分支）。工具全部无交互（参数驱动，管道友好）——判例自动化与人工诊断共用同一入口，"人能用的机器也能用，机器能用的人也能看"。

缺字（链上无字体覆盖该字符）呈现为"带底色的空白格"（业内通行做法）加一次性的诊断提示（该字符的码位与建议字体包——用户能行动而不是干瞪眼）；渲染期错误（字形光栅化失败）降级为系统兜底字形并计数（计数进体验日志，异常率超标自动告警）。字体子系统与 cosmic-text 的分工界面：发现与回退是我们的（数据在系统），整形与光栅化是库的（能力在上游）——界面的契约测试进冒烟套。

## 篇 35 时间与定时器服务实现

**职责一句话：全系统的时间口径只有一个——本篇定时间源、定时器服务与时区处理的实现，让"几点了"在系统里永远是同一个答案。**

### 35.1 时间源与时钟分层

时间源三层：硬件层 RTC（墙钟的落地上限，精度按实机标定）、内核层单调时钟（TSC 经校准，打点与调度的时间基，永不过跳）、会话层墙钟（RTC 加交接快照对照校准，Q14 的实现位——每次交接把双域时间差写进快照，下次启动按差值校准，双域没有 NTP 也保持秒级一致）。对外接口两钟分离（单调给测量、墙钟给显示），混用即缺陷（计时器用墙钟在回拨时的人生悲剧是经典事故，接口层直接分型防混用）。NTP：可选服务（设置页开关，默认关——U 盘整机常离线，时钟策略必须以离线为第一现实），开启时与单调钟的交叉验证留痕。

### 35.2 定时器服务

定时器供给三档：内核定时器（调度与时钟中断，毫秒级轮，红黑树到期队列）、应用定时器（vx-SDK 的 timer 接口，回调在应用事件循环执行——永不跨线程偷跑，宪章的线程纪律）、系统节拍（每秒广播的系统 tick 会话事件——时钟应用、会话空闲统计的统一心跳）。定时器语义纪律：到期不补发（错过即跳过并计数——补发风暴是定时器事故之王）、重复定时器的漂移修正可选（间隔对齐上一次到期时刻，音频与动画类用）、定时器精度承诺如实（毫秒级，不承诺微秒——硬实时的边界再次诚实）。时区与夏令时：时区表随 tzdata 开源数据（季度窗口随更），夏令时换算全在墙钟显示层，单调钟与定时器永远不知夏令时为何物——分层把整类时区事故隔在显示层。

## 篇 37 驱动框架与内核模块通道实现

**职责一句话：全部驱动的共同骨架——驱动生命周期、设备模型、错误上报——以及为硬件矩阵扩张预留的内核模块通道，本篇定框架。**

### 37.1 驱动生命周期与设备模型

驱动框架的核心抽象三件：总线（枚举设备的通道：PCI、USB、平台设备三类总线驱动），设备对象（唯一实例标识、电源状态、驱动绑定），驱动（绑定表加四回调：probe、remove、suspend、resume——suspend/resume 在 STAR I 语义下用于"设备重枚举"而非真休眠，Q77 的边界内语义）。生命周期的铁律：probe 失败留痕不阻断总线（一个设备坏不拖死一类设备）、remove 必须可重入（热拔插的反复横跳是常态不是异常）、引用计数管设备对象生命周期（使用中的设备对象零悬空——U 盘拔出瞬间的驱动路径是最凶险的路，判例 17 的可靠性从这里长出来）。

### 37.2 错误上报与健康账本

驱动的错误统一走健康账本（篇 28.2 的恢复计数是它的一个消费者）：错误事件带设备标识、错误类（超时、CRC、协议错、资源枯竭）、恢复动作与结果。账本的两个用途：实时健康（监视器四卡的设备级下钻）与体质画像（同一设备的错误率时间序列——"这块 U 盘最近变慢了"从玄学变成数据）。错误类枚举表全系统唯一（与 26 章崩溃分类学同构：驱动的错误有分类学，就像崩溃有归宿）。

### 37.3 内核模块通道（预留）

STAR I 内核静态链接全部驱动（U 盘整机硬件面可控，静态的确定性优先），但为硬件矩阵扩张（MD1 第 11 章"Y7000 之外"）预留模块通道：ELF 可重定位目标格式、符号白名单（模块能看到的内核符号显式登记——最小接口原则的内核版）、版本协商（模块与内核的 ABI 版本比对，不匹配拒载）。通道在 STAR I 保持空载不开放——预留是架构姿态，开放是公告行为（开放门槛与签名要求在 STAR II 立项时定），两者分清，内核的攻击面不因"未来可能的开放"提前扩大。

## 篇 39 剪贴板与拖放实现

**职责一句话：跨应用的数据搬运两条路——剪贴板与拖放——的协议语义、所有权模型、大载荷旁路，本篇把"复制粘贴不出事故"定到实现。**

### 39.1 剪贴板的所有权模型

剪贴板在 VXWM 层是一个所有权对象（篇 5.2 的四条报文支撑）：所有权授予走焦点（clipboard_select 只发给焦点窗口），内容分两段——描述段（类型清单与大小，随所有权即时可得）与内容段（按需取，读时经合成器向所有者拉取）。这个模型的三条安全收益：后台窗口读不到剪贴板（显式授权语义，C-8 的姊妹约束）、所有者退出时所有权即时回收（引用悬空零存在）、读内容必须经合成器（审计点单一路径——Q56 的敏感类型判定在此执法）。类型支持纯文本（UTF-8，最大 256KB，超限截断如实标记——大文本走文件路径，剪贴板不是文件系统）与位图（ARGB8888，最大 4096 见方）；文件引用型（文件管理器复制）是第三类：内容是路径清单加类型元数据，粘贴动作转成文件操作（移动语义按修饰键，删除进回收站——剪贴板与回收站语义在此咬合）。

### 39.2 拖放协议与合法落点

拖放（drag_start 到 drop_event 四报文，MD1 附录 H 第 21、22 条）的实现语义：拖动源的载荷描述在拖动开始时定型（拖动中源数据不变——"拖的过程中变内容"是事故源），光标形态三态（可放、不可放、复制或移动提示）由合成器按命中目标的接收声明裁决。合法落点的呈现是强制的：可接收的目标高亮（SDK 控件基类的 drop_target 默认样式），不可接收的区域光标即变——"拖到一半不知道能不能放"的焦虑在协议层消灭。取消语义三路：Esc（源取消并复原，宪章第五章）、放到无效区（自动取消回弹）、源窗口中途销毁（合成器兜底清理）——三路的清理路径共用一套实现，拖放中途的资源零泄漏。跨域拖放（Wine 到原生，场景四）走同一协议：Wine 桥把 Win32 拖放语义翻译到 VXWM 侧，翻译的边界情况（Windows 特有的效果位）映射表公开在星卡注释。

### 39.3 大载荷旁路与性能

位图与文件清单类大载荷走共享内存旁路（篇 5.2 的环形区），报文只传引用——复制一张大截图的剪贴板操作是微秒级（引用传递），粘贴时才真正搬运（按需付费）。性能判据：文本粘贴回显一帧内（16ms 同源判据）、位图粘贴视尺寸节流（大图粘贴有可取消进度——诚实的慢优于冻结的快）。

## 篇 40 无障碍与辅助功能实现

**职责一句话：键盘全程可达、焦点可见、对比度达标、色弱可辨——宪章第四章与第二十条的无障碍承诺在实现层的全套落地。**

### 40.1 键盘可达的工程保证

键盘可达不是测试出来的，是控件基类强制出来的（篇 11.3）：每个控件实例化时自动登记进窗口的焦点环序列（Tab 序按视觉布局自动推导，手工干预需显式声明并留评审标记——默认即正确，例外要交代）。焦点状态机：焦点环内循环、Shift 反向、浮层打开焦点入浮层（popup_grab 联动）、关闭还焦点给触发元素（MD1 体验宪章第四条的协议级落点——还焦点是 VXWM 的语义不是应用的自觉）。快捷键的键盘替代：一切鼠标动作在 SDK 层有等价键盘路径（右键菜单 = Shift+F10，拖放 = 剪贴板剪切粘贴的语义等价），替代映射表进交互词典——"鼠标能触达的键盘也能"由词典保证，不靠开发者记性。

### 40.2 视觉无障碍：对比度、色弱、动效

对比度：主题 token（篇 11.3）的每对前景背景组合在主题构建期自动算对比度（WCAG AA 级 4.5:1 为通过线，大字 3:1）——不达标的 token 组合构建期拒绝，主题作者想做出"看不清的主题"都难。色弱可辨：状态色（成功、警告、错误、进行中）除色相外强制携带形状差异（图标形状与边框样式），红绿色盲在纯色相信息上零依赖——判例与预算表的红色数字同时带形状标记。动效敏感：系统级"减弱动效"开关（设置中心），开启后动画时长压到瞬时与淡入两档，呼吸类装饰动画全停——vx-SDK 的动画原语读这个开关（应用的动画想不理会都做不到，与浮层出路同构的物理强制）。

### 40.3 屏幕阅读与文字缩放

## 附录 B 标准错误文案对照表（三要素模板实例）

错误呈现三要素（发生了什么、为什么、下一步，MD1 宪章第九章）在本册各篇都有场景，本附录给三十个标准错误的人话文案——文案进字符串表（MD1 第 27.1 节），键名按本表固定，任何界面复用同一文案（一致性词典的文案分册）。

## 篇 41 QEMU 模拟环境与设备替身实现

**职责一句话：三层测试环境的第一层（篇 12.1）在 QEMU 里重建整机的实现——模拟设备替身、快照式断电、交接对练环境，冒烟套的可靠性由本篇的地基决定。**

### 41.1 整机镜像与启动替身

QEMU 环境跑与发布同源的镜像（篇 13.2 的 ISO 形态），固件用 OVMF（UEFI 模拟，与实机 UEFI 同语义族——引导链的模拟保真度因此成立）。设备替身清单与实机一一对应：存储替身（virtio 与 AHCI 两形态——AHCI 形态专门模拟 U 盘的慢速行为，可编程注入延迟与错误，BOT 时序病的复现场）、网络替身（用户态网络后端，带宽与丢包可编程——弱网判例的模拟位）、音频替身（输出落 WAV 文件——"有没有出声、出的是不是预期波形"变成可断言的字节对比）、输入替身（编程注入键盘鼠标事件序列——杀死演练与快捷键判例的自动驱动源）。替身的共同纪律：每个替身的注入接口（延迟、错误率、故障时机）进配置文件，冒烟套的用例声明它需要哪种注入——故障注入是一等公民，不是临时 hack。

### 41.2 快照式断电与时间控制

断电模拟的实现：QEMU 的快照保存加"不保存退出"两招组合——保存即断点，不保存退出即断电，断电恢复的验证流程（挂载日志重放、检查点账本、数据完整性）全程可脚本循环，百次断电抽测在 QEMU 里是分钟级事务（实机只做终验，B-1203 的十倍量由此而来）。时间控制的两个用途：时钟快进（七天轮转、季度窗口的演练不必真等七天——定时器与轮转逻辑在虚拟时间轴上验证）、时钟倒拨（墙钟校准与单调钟分离的对抗测试，B-3501 的验证场）。虚拟时间与真实性能数字严格分账：功能正确性在虚拟时间上验，性能预算只在实机标定——两本账不许混。

### 41.3 交接对练环境

交接判据（B-103、B-104、B-206）的对练环境：QEMU 侧起双镜像配置（VARIX 镜像加一个"Windows 域替身"镜像——替身只需实现引导链行为与 /var-snap/ 快照读写，不需要真 Windows），OneShot 写入、单次消费、变量作废、回读验证全流程在替身对上循环验证。替身镜像极简（引导器加一个最小环境），它验的是**协议**不是 Windows 本身——协议验对了，真 Windows 域的对接由实机判据 1 验收（分层各验各的，篇 12.1 的铁律）。

## 附录 C 转译层差异表完整版（能力边界的三张清单）

转译柜台的能力边界需要以"清单"的形态存在——应用撞墙时指名道姓，星卡评级时逐条对照，本附录是篇 4.2 与 4.4 的完整化，三张清单是柜台的官方边界声明，季度窗口随版本复审。

**清单一：改名直通类全表（简目）**。文件与路径族：open、openat、read、write、close、lseek、llseek、stat、fstat、lstat、newfstatat、getcwd、chdir、mkdir、rmdir、unlink、rename、truncate、access、dup、dup2、fcntl、ioctl（白名单子命令）、readdir 系。进程族：getpid、getppid、getuid 系、exit、exit_group、wait4、execve、clone（受限标志集）、kill（限自身进程组）、set_tid_address。内存族：mmap（匿名与文件）、munmap、mprotect、mremap、brk、madvise（常用建议子集）。时间与环境族：clock_gettime、clock_nanosleep、gettimeofday、time、nanosleep、sysinfo、uname。描述符聚合族：poll、ppoll、select、epoll_create、epoll_ctl、epoll_wait、eventfd、pipe、pipe2。合计约一百六十个入口，是柜台覆盖面的主体。

**清单二：语义适配类（实现深度声明）**。epoll 支持水平触发与边缘触发、一次性标志，不支持用户数据指针的旁路优化（语义等价，性能路径简化）；clone 支持新进程与新线程两形态加常用标志（父子存储、清除回调），不支持命名空间类标志；信号支持标准集加实时信号区间，sigaltstack 支持，不支持信号驱动的文件事件改写；madvise 支持 DONTNEED、SEQUENTIAL、RANDOM，其他建议静默接受不动作（Linux 语义允许——建议本来就可忽略）。每条适配的"简做"之处都是语义等价的简化，不是语义背离——背离项一律进清单三。

**清单三：明确拒绝类（返回 ENOSYS 或对应错误）**。io_uring 全族（setup、enter、register）——异步 IO 框架语义深且与 U 盘 IO 模型不合，应用侧应有 poll/epoll 退化路径；io_pgetevents、epoll_pwait2 的超时纳秒扩展（等价改用 pwait）；cgroup、unshare、setns、clone3 的命名空间标志——容器与沙箱基建不提供；kexec、reboot（进程无权重启系统）、init_module、finit_module、bpf、perf_event_open——内核管控与观测接口不对应用开放；vmsplice、splice 的管道零拷贝扩展（普通管道读写可用）；userfaultfd——页错误代理与我们的按需分页实现冲突；membarrier（架构内存序已保证常规场景，扩展等待语义缓期）。每项拒绝的"为什么不"一句话登记：io_uring 是语义深、cgroup 是基建缺、kexec 是权限本质——拒绝都有名有姓，撞墙的报错直接引用本清单条目号。

三张清单的维护规则：清单一是白名单（新直通项加表即生效），清单二是实现深度承诺（降级走 ADR），清单三是拒绝声明（解禁也走 ADR）——三张表的变更都是柜台契约变更，版本号随柜台发布递增。

## 篇 42 会话空闲与性能降档实现

**职责一句话：系统闲下来时把资源让干净，忙起来时把资源给到位——空闲检测、降档策略、唤醒路径的实现，性能预算的"动态面"。**

### 42.1 空闲检测与分级降档

空闲判定不是"没有输入就是空闲"——判定依据三层：输入静默（无键鼠事件）、渲染静默（合成器连续零脏区帧）、任务面（无后台批量任务在跑，更新与索引类任务在会话服务有登记）。三满足且持续三十秒进一级空闲：合成器停整帧（光标层保留）、后台任务恢复运行（更新下载、全盘索引这类"闲时才配干"的活拿到调度许可）；持续五分钟进二级空闲：混音器输出静默检测联动（无声则音频 DMA 停——省电与安静双收）、日志批量落盘窗口放宽。用户回交互（任意输入）立即唤醒到满档，唤醒路径的预算是百毫秒级（一级空闲无深度睡眠，唤醒即满血——U 盘整机不做深度低功耗态，Q77 的边界内取简）。

### 42.2 降档与预算的联动

空闲降档与 19 章预算的关系是"预算管峰值、降档管均值"：预算表验收时按满档口径实测（空闲判据按一级空闲实测——桌面的"空闲 CPU 百分之五"正是在一级空闲下取数），降档的价值是 U 盘寿命与噪声（写合并窗口拉长、批量任务排队到闲时——盘冷下来，风扇静下去）。降档状态在系统监视器可见（当前档位一枚指示），用户永远知道系统此刻在勤快还是省劲——透明的另一面是省劲也透明。

### 42.3 批量任务的闲时调度

闲时任务的准入与礼让：更新下载、目录索引、日志压缩、星卡抽检四类登记为闲时任务，调度规则三条——有输入立即让路（让路是暂停不是终止，恢复续跑）、块层队列里排在前台之后（Q63 的调度落点）、单次连续运行有上限（二十分钟让一次水表防饥饿反转）。任务的进度在系统监视器可见可取消——闲时不等于偷偷干活，"省劲模式下它在做什么"永远可答（宪章第十二章的占用透明）。

## 篇 43 星图社区提交通道实现

**职责一句话：用户与开发者提交兼容性结果的通道（MD1 第 18 章 Q84）——自测脚本包、提交格式、人工复核流水线，生态的双向门。**

### 43.1 自测脚本包

社区提交的前置是标准化自测：星图发布自测脚本包（判例引擎的轻量分发版，篇 25.1 的只读形态——执行预设判例、采集数据、输出标准报告，无写权限不碰系统配置），用户跑完得到一份机器可验的兼容性报告。脚本包的防滥用设计：报告带环境指纹与时间戳（防伪造）、采集范围限定在目标应用（不扫系统其他部分）、报告明示"提交后由人工复核，复核结果可公开可匿名"——开放生态的第一课是让用户的安全感与开发者的效率同时在线。

### 43.2 提交与复核流水线

提交流水线：报告进复核队列（带提交者自述：测了什么版本、碰到什么现象）→ 人工复核（复核员按判例清单抽验关键项，重点核对自述与数据的矛盾点）→ 复核通过则生成候选星卡（评级建议由数据推，人工可改，改动必须留理由）→ 双人复核（评级调升类必须第二人复核——降级单签、升级双签，防止乐观偏差）→ 目录合入。争议处理：提交者对复核结果有异议走申诉（附补充证据），申诉记录与处理结论公开——星卡的公信力来自流程的可见，不只是结论的正确。

### 43.3 提交者的反馈回路

每份提交在星图页可见状态（已收到、复核中、已收录、未收录加理由），收录的星卡标注"社区首发"贡献标识；未收录的给具体差距（缺哪条判例、哪个数据矛盾）——让下一次提交更接近收录，通道才是活的。季度统计（提交量、收录率、Top 贡献者）进生态运营报表（MD1 第 16.3 节审计的生态分册），通道的健康度被运营而不是被遗忘。

## 附录 I 常见实现陷阱清单（二十条预写教训）

按"每个子系统最常摔的跤"预写——写进评审清单，让教训先于事故到位。

1. 引导类：协议版本应答不检查就往下跑——BASE_REVISION 的失败标记被忽略，实机不匹配时半初始化假死（B-101 的存在理由）。
2. 引导类：OneShot 写成功但没写校验——固件静默忽略时全链路装作交接成功（读回校验 B-204）。
3. 交接类：快照写 FAT 不做原子换名——半截快照被对面当真读（B-2202）。
4. 交接类：冲刷超时被"再等等看"吞掉——安全保存变成无限等待（B-203 的停表报错）。
5. 转译类：errno 做了换算表——应用分支行为漂移，一个错误码炸一片应用（C-4 原值直通）。
6. 转译类：辅助向量漏条目——动态链接器在特定路径静默死循环（篇 27.1 第五步的对表）。
7. 显示类：合成器忙等下一帧——空转吃满单核，风扇起飞（事件驱动降帧 B-501）。
8. 显示类：客户端复用未回收缓冲——半帧上屏，压测才现形（所有权窗口 B-504）。
9. 输入类：IME 组合期快捷键照触发——打字打一半弹出系统菜单（组合期分流 B-904）。
10. 存储类：fsync 语义被缓存"优化"——应用以为存了实际没有，断电全盘翻供（B-702 硬承诺）。
11. 存储类：日志重放后直接读写——重放失败的盘被当健康盘写（只读降级 B-701 路径）。
12. 网络类：监听默认全开——诊断时发现一堆"谁开的口"（授权制 B-603）。
13. 音频类：DMA 位置不读——延迟全靠猜，声画同步靠缘分（B-806 的硬件依据）。
14. Wine 类：垫片直接改 Wine 源码——升级一次地狱一次（零侵入 B-1003）。
15. SDK 类：控件焦点环做成可选——应用"忘了"开，键盘用户迷路（默认渲染 B-907）。
16. 发布类：构建时间戳进产物——同源不同哈希，可复现名存实亡（环境净化 B-1301）。
17. 更新类：更新写当前槽——写一半断电直接变砖（双槽 B-1304）。
18. 安全类：日志打整个对象——敏感字段随对象进日志（红线类型 B-1506）。
19. 性能类：基准只看均值——长尾劣化看不见，手感劣化测不出（三线分布 B-1403）。
20. 文档类：实现改了文档不回写——三册变小说，半年后无人信（回写通道 B-3001）。

## 附录 J 全篇实施顺序与依赖图谱（四十三篇怎么排）

单编制不等于乱序——恰恰因为只有一个施工者，顺序就是资源本身：排对了一波顺下去，排错了就是返工地狱。本附录把四十三篇排成五波施工序列，每一波给出成员、出口判据、对里程碑的映射；依赖硬约束单列成清单。凡本图与篇内字段表冲突处，以篇内为准并回写本图（与附录 A 的对账纪律同构）。

**第一波：地基（篇 1、2、3、26、27、29）。** 引导链、交接协议、Windows 加固、内核内存与调度、装载器、电源固件——这一波交付"系统能启动、能交接、能分配内存、能装程序、能体面关机"的最小闭环，对应里程碑 m1-handoff 的全部实现面。出口判据：B-101 至 B-106、B-201 至 B-207、B-301 至 B-307、B-2701 至 B-2703、B-2901 至 B-2904 全绿，外加 QEMU 断电百次（B-4102）通过——第二波起每一步都踩在地基上，地基的判据不许带债过波。

**第二波：桌面骨架（篇 5、9、7、6、37、38）。** 显示栈、输入与输入法、存储、网络、驱动框架、系统日志——桌面"能看、能打字、能存取、能联网"的四梁八柱，对应 m2-desktop 的主干。出口判据：B-501 至 B-507、B-901 至 B-907、B-701 至 B-707、B-601 至 B-607、B-3701 至 B-3703、B-3801 至 B-3803 全绿，其中桌面空闲百分之五（B-501）必须在一级空闲口径下实测（篇 42.2 的口径约定），不许用二级空闲取数美化。

**第三波：桌面血肉（篇 16 至 21、24、34、35、36、39、40）。** 终端、文件管理器、编辑器小件、设置中心、监视器、星图前端、会话管理、字体、时间、显示输出、剪贴板拖放、无障碍——十二件套的主体与宪章体验条款的兑现面。这一波篇多而每篇体量适中，按 MD3 的 WP 分解逐包推进，波内顺序按"先公共件后独立件"排（字体先于输入法引擎收尾、监视器先于降档收尾）。出口判据为对应 B-16xx 至 B-40xx 段全绿，20 维度验收（篇 12）在本波末跑第一轮全量。

**第四波：兼容与生态（篇 4、10、11、33、43）。** 转译层、Wine 运营、SDK、运行时画像、社区通道——m3-compat 的主体。依赖第二波的进程装载就位与第三波的 SDK 框架先行；出口判据 B-401 至 B-407、B-1001 至 B-1007、B-1101 至 B-1107、B-3301 至 B-3303、B-4301 至 B-4303 全绿，LTP 合规子集与 Wine 判例框架的自动执行率达标，星图目录收录第一批社区提交。

**第五波：质量闭合（篇 12、13、14、15、22、23、25、28、30、31、32、41、42）。** 测试金字塔、部署发布、性能实施、安全实施、交接助手、诊断日志、判例引擎、USB 栈、演进机制、取证三件套、安装更新、QEMU 环境、空闲降档——注意 USB 栈（28）排在此处不是不重要，而是它的 BOT 恢复矩阵需要前四波的整机环境当靶子；QEMU 替身（41）同理，替身注入要先有真系统可对照。本波交付 m4-release 的全部证据链：七十二小时烤机、断电百次、回滚演练、双签流程审计、性能预算满档复核。

**依赖硬约束十条**（排序时不可违背）：一，篇 5 依赖篇 26 的物理页分配器先就位；二，篇 4 依赖篇 27 的 ELF 装载先通过对抗测试；三，篇 22 依赖篇 2 的快照 schema 冻结——schema 未冻结前篇 22 不得开工；四，篇 13 依赖篇 41 的断电对练百次通过；五，篇 43 依赖篇 25 判例引擎的只读形态；六，篇 7 的 ext4 依赖篇 26 的块层与页缓存；七，篇 9 的输入法引擎依赖篇 34 的字体回退链；八，篇 32 的安装器依赖篇 3 的四板斧脚本收编完成；九，篇 14 的基准体系依赖篇 5 的打点与篇 26 的调度器计量；十，篇 42 的闲时调度依赖篇 20 监视器的账本订阅面。

**顺序纪律三条**：schema 先行——所有跨篇字段表（交接快照、VXWM 报文、体验日志七字段）先冻结再施工，冻结后变更走 ADR；判据随篇——每篇收工时判据表实测栏不许空格，空格即未完工；图谱回写——实际施工顺序偏离本图超过一波、或依赖硬约束被打破，立即回写本附录并在附录 F 登记。

**返工与插入规则**：波中途发现前置波留了债（判据空格、schema 未冻结），停波还债——还债的工期从本波里扣，不许往后挪，债过两波就是结构性返工；施工中新冒出来的小件（四百行以内、不动 schema、不新增跨篇依赖）按"插入审批"处理：登记附录 F、写明插入理由与被挤掉的排期，由每日对账确认代价可见；超过四百行或动 schema 的新件一律走 ADR 重新排波。单编制最大的风险不是慢，是顺手加塞把波序搅成浆糊——本规则就是防浆糊的，加塞自由与交付纪律之间，永远选后者。

## 附录 K 性能预算与调优旋钮总表（一页账本）

预算数字散在 MD1 第 19 章与本册各篇判据表里，施工中对表要翻两处——本附录把它们集中成一页账本，并补齐散落各处的"调优旋钮"清单：每个旋钮的位置、默认值、可调范围、动了谁的预算。施工期调优只许拧本表列出的旋钮，表外旋钮一律视为魔法数（篇 14 的回归门会拦）。

**满档预算账**（验收口径，全部带判据出处）：桌面空闲单核占用百分之五以下（B-501，一级空闲口径实测）；窗口拖动五十五帧以上（B-502）；二次启动八秒内（B-707，预读命中口径）；唤醒到满档百毫秒内（B-4202）；系统调用转译单次两微秒内（B-405）；fsync 承诺五秒窗口（B-702，写合并上限即承诺上限，两者是同一个数字）；打点开销低于百分之一（B-106 与 B-1401 联动）；日志写入不阻塞交互线程（B-3801 附带纪律）；合成器缓冲零半帧撕裂（B-504）；字形图集尺寸不破上限（B-505，超限先降渲染密度再议扩容）。

**调优旋钮清单**（默认值即验收值，调优后必须重跑对应判据）：写合并窗口（篇 7，默认五秒，可调三至八秒——同时动 B-702 与 B-704 两项，调长省盘、调短保数据，默认即平衡点）；预读窗口（篇 7，默认按启动表十一项覆盖配比——动它先对账 B-707）；字形图集尺寸（篇 5，默认上限见 B-505，只许降不许升——升了挤占桌面内存配额）；混音器缓冲深度（篇 8，默认深缓冲保连续输出，调浅省内存但易欠载，欠载即回滚默认）；日志轮转硬顶（篇 38，三通道各自硬顶，调高前先过 B-3802 的对账）；闲时任务水表（篇 42，默认二十分钟让路一次，调长防饥饿反转失效，调短伤前台）；打点采样率（篇 14，默认全量，压测期可降采样，发布版必须回全量——盲区就是盲区）；候选窗刷新节流（篇 9，默认按帧同步，IME 卡顿先查这里再查引擎）。

**预算冲突仲裁**：旋钮之间打架时按手感 > 吞吐 > 寿命 > 静音的顺序仲裁——手感是宪章第五、六章的兑现面，永远第一；寿命（U 盘写入量）在写合并类旋钮里单独加权，因为 U 盘整机的命根子在盘。任何调优不得突破三条绝对红线（B-502、B-702、B-4202），其余判据在 ADR 记录理由后可申请豁免一次、复审时双人复核。预算账与旋钮清单随施工回写——实测偏离预算两成以上即回写本表并在附录 F 登记，账本不许与现实脱节。

**内存配额账**（与满档预算账并列的第二本账，数字以 MD1 第 19 章内存配额表为准，本段只记纪律）：合成器与显示栈、网络栈缓冲、存储页缓存、Wine 会话、转译层、输入法引擎、日志与账本、体验日志环形缓冲各自有配额上限，超配额的第一反应是降级不是崩溃——每个子系统都要能回答"配额被掐住时先扔什么"（字形图集降密度、页缓存收缩、混音器缓冲回默认，扔的顺序写进各自的实现纪律段）。配额与旋钮清单联动：每拧一个旋钮都要回头查这张账，字形图集升一格就是从桌面配额里划走一块；子系统实测占用连续七天低于配额六成，配额下调走 ADR——配额不是留面子的大锅饭，是随时对账的活账本，U 盘整机的每一兆内存都要知道自己在给谁干活。

**对账节奏**：预算账、配额账、旋钮清单三本账统一为"一日一自对、一波一互对、一里程碑一全对"——每日对账看昨日实测有没有踩线，踩线当天处理，过夜就成惯性；每波出口对账把本波判据的实测值誊进账本，誊写动作本身就是一次复核，笔误当场现形；里程碑对账（m1-handoff 与 m4-release 两处最重）把三本账与 MD1 第 19 章预算总表逐格比对，偏差说明写进里程碑报告。对账节奏与篇 14 的基准回归共用同一条流水线——账本是回归门的纸质形态，回归门是账本的自动形态，两者对不上号时先怀疑账本。三本账任何一本两周期内未更新，视为账本失守——失守的账本比没有账本更危险，因为它披着"有账"的皮。
