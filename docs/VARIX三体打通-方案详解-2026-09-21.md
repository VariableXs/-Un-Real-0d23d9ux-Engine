## 0. 四个问题，一句话答案

| 你的问题 | 一句话答案 |

## 1. U 盘现状（你手这块盘的每一寸用途）

| 分区 | 文件系统 | 容量 | 用途 | 现状 |
|---|---|---|---|---|
| ESP | FAT32 | 1GB | 引导总入口：Limine（引 VARIX）+ 未来补 Windows 引导项 | 在用 |
| VARIX_SYS | NTFS | 64GB | VARIX 内核 + 引导配置 + 内核侧资产（未来含 Servo/前端资源） | 内核 F4F96E69 在位（落后本地两版） |
| WIN_ENGINE | NTFS | **300GB** | **Windows 11 整个放这里**——可独立引导，也可作隐形引擎镜像 | 空置，就等部署 |
| SHARED | exFAT | 560GB | 双世界单一事实源：文件/设置/apps.json/接力队列 | 在用；内核已实机**只读**挂载 |
| SNAPSHOT | NTFS | 余量 | 快照与灾备（差分备份滚动保留） | 在用 |

关键事实：内核对 SHARED 的 exFAT **读已实机通**（fs/exfat_ro.rs，写走 SnapshotArea 过渡）——存储桥缺的只是"USB 块设备层"（三期 xHCI MSC），文件系统层早就绪。

## 2. Variable 分层解剖：什么是"设计"，什么是"程序"

```
Variable 系统 = 四层叠起来的
├── L1 界面层（这就是你说的"设计"）
│     959 个 React/TS/TSX 文件：桌面、开始菜单、任务栏、窗口管理、
│     通知中心、设置页、锁屏、动画曲线、亮暗主题、i18n 三语
│     → 编译产物是标准 web 技术（HTML/CSS/JS/WASM）
├── L2 桥梁层
│     lib/ipc.ts：554 个方法名，全库仅 4 处裸 invoke——界面要能力时
│     喊的名字，两边念的是同一本字典
├── L3 本体层
│     Tauri/Rust 后端 650 个 #[tauri::command]：文件、窗口、嵌入、
│     剪贴板、环境变量、备份恢复……真正干活的手
└── L4 运行时层
      WebView2（微软闭源浏览器内核）——把 L1 画出来的引擎
```

**"设计完全相同放进内核"的含义**：L1 原样进（web 技术谁都能画）；L2 原样进（垫片协议单源已定版）；L3 换人接单（内核系统服务 + 三色映射：✅内核已有直接用 / 🔶组合几个服务拼出来 / ❌暂缺如实降级）；L4 换引擎（WebView2 → Servo，同为 Rust 血统，总案"Servo 可替换"接口已预留）。

**唯一进不去内核的是 L4 的 Windows 特定实现（WebView2 本体）**——它闭源且深度绑定 Windows。这就是"Tauri 程序本体不进内核、Variable 的设计与功能进内核"的准确边界。

## 3. R1 主线（Servo 承载）的原理与 12 步

### 原理链（开机后发生什么）

1. U 盘 ESP 的 Limine 引导 VARIX 内核（14 阶段引导流水线）；
2. bootselect 菜单默认项 = VARIX+Variable → 内核完成域初始化（内存/调度/驱动/fs）；
3. 内核 spawn 用户态 init → spawn **Servo 进程**（ring3 用户态，和 Wine 应用同等待遇）；
4. Servo 加载 VARIX_SYS 里的 Variable 前端产物 → 输出到 GOP 帧缓冲（内核显示服务合成）；
5. 你敲键盘/动鼠标 → 内核输入服务 → 消息通道 → 翻译成 DOM 事件喂给前端；
6. 前端 invoke("file_read") → 垫片 → 内核 VFS（白名单裁决）→ 返回 → 前端渲染；
7. 全程 **Windows 没有开机**，一块盘自己就是一个完整系统。

### 12 步施工序（总案阶段 3 定稿，每步原理）

| 步 | 内容 | 原理要点 |
|---|---|---|
| 1 | 垫片协议定版 | invoke 命名/JSON 序列化/三段式错误（OK\|MAPPED_ERR\|MISSING）/事件反向通道；Rust+TS 类型同源生成防漂移（tools/shim-protocol.source.json 已是单源） |
| 2 | 三色审计 | 跑 audit.cjs 产出 554 方法逐条归属表，✅+🔶 首版目标 ≥30%，覆盖桌面壳闭环 |
| 3 | 内核 KV 服务 | 前端 localStorage 语义（get/set/remove/keys）→ 内核 KV（kvsrv 已落，复用 fs23_journal 账本，断电 ×10 零丢失已验） |
| 4 | vwmStore 迁移 | 窗口几何从 localStorage 切 KV，垫片内做透明桥，**前端代码 diff 零改动** |
| 5 | 输入事件管道 | 内核输入服务→消息通道→DOM 事件；焦点模型（哪个窗口收键）；与 Wine 通道共用同一输入总线 |
| 6 | 渲染通路 | Servo 输出→共享帧缓冲→内核显示服务合成；先单窗全屏后多层；脏矩形提交不整屏刷 |
| 7 | 三件套保底 | 桌面壳/文件管理器/设置页在垫片下闭环（文件走 VFS 白名单）——**这一步完成=内核里打开的就是 Variable 桌面** |
| 8 | BootScreen 对接 | 内核 spawn 链各阶段发 boot://event 同语义进度，启动仪式体验不变 |
| 9 | 多窗合成 | 多 Servo 窗口 + Z 序 + 最小化保活，vwm.ts 状态机语义逐条对照 |
| 10 | 降级 i18n | 全部 ❌ 命令统一降级提示（"此功能需 XXX 通道"），三语词条 |
| 11 | 性能基线 | 首帧/交互延迟/窗口开关三项基线归档 |
| 12 | 里程碑验收 | 真机引导默认进 Variable 桌面，vitest 全绿证明前端零语义改动 |

保底线（R2）：内核 ring3 自绘桌面 ushell 已实机（20/20 走查）——Servo 任何阶段受阻，开机永远有可用的 Variable 风格桌面兜底；它还长期承担引导期 UI 与 handoff 交接画面。

## 4. 数据 / 内存 / 软件互通：三件事三个答案

### 4.1 数据互通 ✅ 实时（这是设计定的，不是远景）

- **原理**：两个系统读的是**同一块物理分区**（SHARED exFAT），不存在"同步两份副本"，天然实时。Windows 侧写入即落盘，内核侧（三期 USB MSC 通后）读到的就是同一字节。
- 配置同实时：boot-select.json（引导配置）、apps.json（应用清单）、白名单规则——单一事实源，两边改一处另一处生效。
- 现状与欠账：QEMU 全通；实机内核读已通（exfat_ro），**写**走 SnapshotArea 过渡，三期 MSC 后直写。
- L0 配置桥欠账（方案 A）：boot-select.json 副本放 ESP + limine.conf module_path 挂载 + 部署同步——1-2 天级。

### 4.2 内存互通 ⚠️ 诚实拆开说

- **物理规律**：一块 CPU 一次只跑一个 OS，物理内存一次只归一个内核。"两个系统同时活着共享内存"只有一种合法形态——**一个系统里的虚拟机**。
- 总案给的正是这个形态：**隐形引擎通道（阶段 6）**——Windows 作为后台 VM 被 Variable 拉起（Hyper-V 过渡，终局内核 VMX），此时 Variable（宿主）与 Windows（客户机）之间是真·实时内存级协作：画面流出来（窗口无缝贴进 Variable 桌面）、输入注进去、热数据 ramcache 进宿主内存（只缓不落盘、关机即清、拔盘零残留）。
- 内核内部进程间：共享内存块 + 消息通道两个原语（阶段 4，授权模型+默认拒绝），这是内核版 Variable 与 Wine 应用之间的"内存互通"。
- **结论**："内存实时互通"= 开隐形引擎时成立；不开引擎时，数据走 SHARED（文件级实时），不走内存。

### 4.3 软件互通 ✅ 三通道（总案核心设计，见图二）

判定规则一句话：**看软件是什么技术做的，它就天生属于哪条通道**。

- 通道一 内核原生：web 技术做的（界面、网页、网页壁纸）→ Servo 直接跑，零翻译；
- 通道二 Wine 兼容层：轻量 Win32 程序 → PE 装载器 + Win32 服务台翻译成内核服务（记事本已实机 VERDICT PASS；每 exe 独立进程 + Job 限额 + prefix 隔离 + compatdb 自动裁决）；
- 通道三 隐形引擎：重型/闭源/深度绑定 Windows 的 → 后台 VM，窗口无缝出现；
- 兜底 纯 Windows：反作弊/3A → bootselect 重启切换（唯一解，物理规律）。

## 5. Steam / Edge / Wallpaper Engine 逐个说

### Edge（浏览器）

- 内核侧日常上网**不需要 Edge**：Variable 跑在 Servo 里，浏览器就是 Servo 的本行——内核版 Variable 的"浏览器"应用 = Servo 多开一个视图，普通网页直开。
- 完整 Edge（同步、扩展、企业策略、播放某些 DRM 视频）→ 通道三隐形引擎窗口无缝用。
- 评级：日常上网内核原生 ✅；重度 Edge 依赖引擎 ✅。

### Steam

- 拆两层看：**Steam 客户端**（界面/库/社区）本质是 CEF(Chromium)+Win32 混合——Wine 生态对 Steam 支持成熟（Linux 世界跑 Steam 客户端就是这套路线，有二十年先例）→ 通道二**远期目标**；前置硬依赖：内核需补 **GPU 加速**（现软件渲染）与**网络栈**（现无）——两者在总案长线里都有位置（GPU 加速=阶段 7 后长线，网络属内核扩域）。
- **游戏本体**：轻量独立游戏→通道二可能跑；3A/反作弊→通道三或纯 Windows；带反作弊→**只有纯 Windows**（物理规律，不承诺）。
- 评级：客户端远期 🔶；游戏按级分流。

### Wallpaper Engine（壁纸引擎）

- 它的壁纸三种格式，三种下落：
  1. **网页壁纸**（创意工坊最大类，本质 HTML/CSS/JS）→ **内核原生直跑**（Servo 渲染，和 Variable 自己同引擎）——这是惊喜项：壁纸生态的大部分内容天然兼容；
  2. **视频壁纸**（mp4）→ 内核补视频解码栈（中期能力项），或引擎通道过渡；
  3. **应用壁纸**（exe 程序）→ 引擎通道。
- Variable 本身有完整壁纸设置体系（win11 外壳契约内），内核版直接继承同一份前端——**"动态壁纸"功能在内核里是 Variable 自己的原生功能**，不依赖官方 Wallpaper Engine 在场。
- 评级：网页壁纸内核原生 ✅；视频壁纸中期 🔶；完整官方引擎→引擎通道 ✅。

### 其他任何软件的通用判定

web 技术→原生；轻量 Win32→Wine（compatdb 登记表逐个扩）；重型闭源→引擎；反作弊→纯 Windows。没有第四种情况。

## 6. "不用 Tauri 版了"的诚实回答

- **短期（阶段 3 施工中）**：不行。三色映射补齐前，内核侧能力有 ❌ 缺口（如实降级），Windows 侧 Tauri 版承担完整能力。
- **中期（三件套闭环后）**：日常"开机进内核用 Variable"成立，重度功能（嵌入第三方软件、Shell 模式、深度 Windows 集成）仍回 Windows 侧。
- **长期（✅+🔶 → 100%）**：**架构上你随时可以只用内核版**——因为同一份代码，切底座零成本，数据同一份。是否弃用 Tauri 版届时是使用习惯问题，不是技术问题。
- **不建议现在定"弃用"**：两条底座共存互为备份，正是"可停性"设计的精髓（任一阶段做完系统都可用）。

## 8. 物理边界重申（本方案不违反任何一条）

- WebView2 本体不进内核；双 OS 同时活窗不成立；不重启切系统不成立；
- 触控板（I2C）内核侧不支持（二期 xHCI 只覆盖 USB HID，外接 USB 鼠标可通）；
- 反作弊软件只在纯 Windows 通道跑；
- "内存实时互通"仅在隐形引擎形态成立；
- 全部软件能力升格受 compatdb 登记表驱动，无静默缺失（❌ 项都写明"谁在哪个阶段补"）。

## 9. 追问解答：Variable 的所有应用能否正常用？内核能否与 Variable 一模一样？（2026-09-21 01:39）

### 9.1 Variable 自带应用（vite MPA 8 入口）在内核里的归属

8 个入口全部是前端 web 应用——**界面 100% 原样进内核**（同一份代码，Servo 承载），功能归属看其背后的命令面：

| 应用入口 | 功能本质 | 内核侧对应能力 | 预期归属 |
|---|---|---|---|
| desktop（桌面壳：任务栏/开始菜单/窗口管理/通知/锁屏） | 窗口+显示+输入+KV | 显示服务/输入服务/KV 全部已有 | 首批 ✅ |
| taskbar（任务栏） | 同上（桌面壳一部分） | 同上 | 首批 ✅ |
| explorer（文件管理器） | VFS 文件浏览/读写 | fs/exFAT（读已实机）+ VFS 白名单 | 首批 ✅（真 USB 数据直读=三期 MSC） |
| app-write（写作） | 文本编辑+文件存取 | VFS+KV 覆盖其命令面大半 | 早期 ✅/🔶 |
| app-mind（思维） | 同类（编辑+存取） | 同上 | 早期 ✅/🔶 |
| app-code（代码） | 编辑+文件树+高亮（纯前端） | 同上 | 早期 ✅/🔶 |
| app-fate | 同类 | 同上 | 早期 ✅/🔶 |
| datavault（保险箱） | 加密存储 | 内核 kvault（AES-256-GCM）同源对应 | 早期 ✅/🔶 |
| 设置页（30+ Tab） | KV+各服务查询/设置 | 逐 Tab 三色映射 | 渐进 ✅ |

要点：四款自研软件是"纯前端重、系统调用轻"型——命令面小且与内核已有服务（VFS/KV/kvault）高度重合，属最早全绿的一批。

**你装进 Variable 的第三方 Windows 软件**：走四通道分流（内核原生/Wine/引擎/纯 Windows），见第 4.3 节与图二。

### 9.2 "内核界面+所有功能做成和 Variable 一模一样"——三层答案

1. **界面层：立即一模一样，且是设计目标。** Servo 版 Variable 与 Windows 侧同代码同像素（验收=逐屏对照）；内核自己的 UI（bootselect 卡片菜单/handoff 交接画面/ushell 兜底桌面）视觉语言已全部对齐 Variable（win11 外壳契约）。终态：内核开机直接进 Variable 桌面，感知上无差别。
2. **功能层：渐进一模一样。** "一模一样"的工程定义 = 同一份前端 + 554 个方法 100% 有归属。收敛路径 ❌（如实降级+登记"谁在哪个阶段补"）→ 🔶（组合内核服务）→ ✅（原生服务）；**前端零改动**，补的全是内核侧。首版验收=桌面壳/文件管理器/设置页三件套闭环（✅+🔶≥30%）。
3. **天花板层：四类永久分流（不硬扛）。** Windows 深度集成类（嵌入第三方窗口/Shell 模式/注册表服务）→ 由 Wine/引擎通道承担对应能力；硬件基建类（GPU 加速/网络/触控板）→ 随内核基建进度补齐；反作弊/DRM → 永远纯 Windows；**其余全部无天花板**。

### 9.3 结论句

**界面第一天就一模一样；功能按登记表收敛到一模一样；四类天花板按通道分流且从不静默。** "内核版=Variable 完全体"是架构保证的终点，不是 hope。
